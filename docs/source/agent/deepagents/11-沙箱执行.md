# 沙箱执行：让 Agent 安全地运行代码

## 1. 先分清三层能力

能写文件、运行 Shell、安装依赖的 Agent，已经不只是「回答问题」的模型，而是能改变运行环境的执行者。把这份能力放进隔离沙箱，既让它编程、分析数据、跑测试，也让宿主机的文件、进程与凭证留在边界之外。

| 层 | 是什么 | 作用 |
|---|---|---|
| Deep Agents Python Backend | 把远程沙箱接到 `create_deep_agent()` | 提供文件工具与 `execute` |
| Deep Agents Code（`dcode`） | 命令行工具在本机跑 LLM 循环 | 把工具调用定向到远程沙箱 |
| LangSmith Sandboxes | 一方托管沙箱产品 | 除 Backend 外，还提供快照、服务 URL、Auth Proxy、挂载、CLI |

## 2. 沙箱是一种 Backend

普通 Backend（State/Filesystem/Store）只实现文件读写；沙箱 Backend 还实现 `execute()`，因此能运行 Shell。

| 能力 | 普通 Backend | 沙箱 Backend |
|---|---|---|
| 文件工具 | 7 个内置工具 | 同样支持 |
| Shell 执行 | 不提供 | `execute` |
| 环境 | Backend 指向的存储 | 与宿主机隔离的远程环境 |
| 典型任务 | 计划、笔记、资料读写 | 编码、测试、数据分析、产物生成 |

传入沙箱 Backend 后，Deep Agents 在每次模型调用前检查是否实现 `SandboxBackendProtocol`；满足协议，模型才会看到 `execute`。沙箱基类会把其他文件操作构造成沙箱内脚本执行，因此接入新 Provider 的核心通常就是可靠实现 `execute()`。

> **不要把 `FilesystemPermission` 当沙箱内的命令隔离**：它约束内置文件工具，不约束 `execute`。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/deepagents_30-flowchart-code-execution.png)

<p>图 2：代码执行主路径</p>

### 2.1 `execute()` 的返回值

Agent 传入 `command` 字符串，得到：合并后的 stdout/stderr、退出码、输出过大时的截断提示。

应用直接调用应检查 `result.exit_code`；Agent 的 `execute` 结果在锁定版本中把退出码放在 `ToolMessage.artifact["exit_code"]`。**工具接口成功返回时消息状态可能仍是 `success`，即使命令退出码非零**——不要只凭消息状态判断程序成功。

过大的输出不会直接塞进上下文，而会保存为文件，提示 Agent 用 `read_file` 分段查看；编译日志、测试报告、大数据输出因此不会挤占窗口。

```python
from deepagents.backends.langsmith import LangSmithSandbox
from langsmith.sandbox import SandboxClient

client = SandboxClient()
sandbox = client.create_sandbox(template_name="deepagents-deploy")
backend = LangSmithSandbox(sandbox=sandbox)

try:
    result = backend.execute("python --version")
    print(result.output)
finally:
    client.delete_sandbox(sandbox.name)
```

## 3. 隔离边界：保护什么，不保护什么

所有沙箱都应把 Agent 的文件系统与 Shell 操作同宿主机隔离：不能读本地文件、访问本机环境变量、干扰其他进程。`rm`、装依赖、测试失败或错误脚本都被限制在远程环境。

但这不等于 Agent 自动可信。沙箱**不能**单独防御两种风险：

| 风险 | 为什么存在 | 要做什么 |
|---|---|---|
| 上下文注入 | 攻击者影响输入后，仍可诱导 Agent 在沙箱内执行命令 | 不把秘密放进沙箱；审查高风险工具；用 HITL |
| 网络外传 | 未限制网络时，可通过 HTTP/DNS 把数据发出 | 不需要网络就阻断；最小化可访问数据；监控出站 |

例如 Modal 支持 `blockNetwork: true`；其他 Provider 也应检查网络控制能力。安全目标不是「沙箱内绝不出错」，而是让错误、恶意输入与不可信产物不能越过宿主边界。

## 4. 快速上手与 Provider

LangSmith 是一方托管示例：

```bash
uv add "langsmith[sandbox]"
```

```python
from deepagents import create_deep_agent
from deepagents.backends import LangSmithSandbox
from langchain_anthropic import ChatAnthropic
from langsmith.sandbox import SandboxClient

client = SandboxClient()
ls_sandbox = client.create_sandbox()
backend = LangSmithSandbox(sandbox=ls_sandbox)

agent = create_deep_agent(
    model=ChatAnthropic(model="claude-sonnet-4-6"),
    system_prompt="You are a Python coding assistant with sandbox access.",
    backend=backend,
)

try:
    result = agent.invoke({"messages": [{"role": "user", "content": "Create a small Python package and run pytest"}]})
    print(result["messages"][-1].content)
finally:
    client.delete_sandbox(ls_sandbox.name)   # 远程资源会持续计费，必须清理
```

模型与 Agent 在宿主侧；只有文件工具和 `execute` 通过 Provider API 落到远程沙箱——这就是后文推荐的 **Sandbox as tool**。

当前 Python 集成共享 Deep Agents 工具语义，但创建/销毁属于各自 Provider：

| Provider | 安装包 | Backend | 创建 / 清理 |
|---|---|---|---|
| LangSmith | `langsmith[sandbox]` | `LangSmithSandbox` | `create_sandbox()` / `delete_sandbox()` |
| AgentCore | `langchain-agentcore-codeinterpreter` | `AgentCoreSandbox` | `start()` / `stop()` |
| Daytona | `langchain-daytona` | `DaytonaSandbox` | `Daytona().create()` / `stop()` |
| E2B | `langchain-e2b` | `E2BSandbox` | `Sandbox.create()` / `kill()` |
| Modal | `langchain-modal` | `ModalSandbox` | `modal.Sandbox.create()` / `terminate()` |
| NVIDIA OpenShell | `langchain-nvidia-openshell` | `OpenShellSandbox` | 上下文清理 `delete_on_exit=True` |
| Runloop | `langchain-runloop` | `RunloopSandbox` | `devbox.create()` / `shutdown()` |
| Vercel | `langchain-vercel-sandbox` | `VercelSandbox` | `Sandbox.create()` / `stop()` |

选 Provider 先确认：运行区域、生命周期与回收、网络与凭证控制、镜像/依赖管理。不要因为示例能跑就假设满足生产数据或合规要求。

## 5. 两种集成模式

| 模式 | Agent 在哪 | 优点 | 代价与适用 |
|---|---|---|---|
| Agent in sandbox | Agent 框架与工具都在沙箱内 | 接近本地环境，运行时紧耦合 | 要构建镜像、提供 HTTP/WS 通信层，API Key 在沙箱内；仅在 Provider 妥善处理通信且必须复现本地环境时考虑 |
| **Sandbox as tool** | LLM 循环、记忆、调度在宿主；执行工具调远程沙箱 | Agent 逻辑即时迭代；密钥与状态留在沙箱外；可并行多沙箱；故障不丢状态 | 每次调用有网络延迟；多数 Deep Agents 应用首选 |

Agent in sandbox 的最小镜像可以是 `FROM python:3.11` + `pip install deepagents-code`，但镜像**不解决密钥问题**：Agent 能读容器环境变量，提示注入同样可能外传。除非确实需要打包运行时，优先 Sandbox as tool。

## 6. 文件有两个平面

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/deepagents_31-framework-sandbox-file-planes.png)

<p>图 3：宿主与沙箱的文件平面</p>

| 调用方 | API | 作用 |
|---|---|---|
| LLM / Agent | `read_file`、`write_file`、`edit_file`、`delete`、`ls`、`glob`、`grep`、`execute` | 只在沙箱内部完成任务 |
| 宿主应用 | `upload_files()`、`download_files()` | 用 Provider 原生传输跨越宿主与沙箱边界 |

**运行前播种输入**（绝对路径 + bytes）：

```python
backend.upload_files([
    ("/src/index.py", b"print('Hello')\n"),
    ("/pyproject.toml", b"[project]\nname = 'my-app'\n"),
])
```

**运行后提取产物**（逐项处理成功/失败）：

```python
results = backend.download_files(["/src/index.py", "/output.txt"])
for r in results:
    if r.content is not None:
        print(r.path, r.content.decode())
    else:
        print("Failed:", r.path, r.error)
```

传输 API 由应用控制、走 Provider 原生通道，不是 Agent 跑的一条 Shell 命令——它也是输入与产物审查的天然边界。

## 7. 生命周期与作用域

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/deepagents_32-comparison-sandbox-scopes.png)

<p>图 4：Thread-scoped 与 Assistant-scoped</p>

| 作用域 | 行为 | 适用 | 风险控制 |
|---|---|---|---|
| Thread-scoped（默认） | 每个对话线程一个沙箱，同一 `thread_id` 后续轮次复用 | 每个用户任务独立 | `idle_ttl_seconds` 自动回收空闲环境 |
| Assistant-scoped | 同一 Assistant 所有线程共用一个沙箱 | 跨对话保留仓库、依赖、缓存 | 配 TTL、快照重置、周期清理 |

Thread-scoped 用稳定 sandbox name 保存 `thread_id` 与沙箱的对应关系：首次创建，后续找到并复用，离开后由 TTL 删除或归档。

Assistant-scoped 用 `assistant_id` 做名字，会保留文件、包与克隆的仓库，因此不能放任增长：设 TTL、定期从快照重建、主动清理磁盘与内存。

## 8. `dcode`：把工具调用指向远程沙箱

`dcode` 在本机跑 LLM 循环、记忆与调度，但文件与 `execute` 实际操作远程沙箱。

| 来源 | 路径 |
|---|---|
| 内置 Provider | langsmith、agentcore、daytona、modal、runloop、vercel |
| 第三方 Provider | 已安装包通过 Python entry point 发布（如 `langchain-e2b`） |
| 配置 Provider | `~/.deepagents/config.toml` 的 `[sandboxes.providers]` |

同名优先级：**配置声明 > 第三方 entry point > 内置**。配置能覆盖默认集成，但 `class_path` 会导入并运行本地 Python，必须只指向受信任模块。

```bash
dcode --install daytona
dcode --install all-sandboxes
dcode --install langchain-e2b --package
dcode --sandbox e2b
```

| 参数 | 含义 |
|---|---|
| `--sandbox TYPE` | 选择 Provider；省略值用配置默认；裸 `--sandbox` 必须放命令末尾 |
| `--sandbox-id ID` | 重连已有沙箱，跳过创建与清理（需 Provider 支持） |
| `--sandbox-snapshot-name NAME` | 使用/创建快照；不能与 `--sandbox-id` 同用 |
| `--sandbox-setup PATH` | 创建后运行设置脚本 |

默认工作目录因 Provider 而异：LangSmith `/root`、AgentCore `/tmp`、Daytona `/home/daytona`、Modal `/workspace`、Runloop `/home/user`、Vercel `/vercel/sandbox`。

> `--sandbox-setup` 适合克隆受信任仓库、装依赖、准备非敏感环境。它会用本地环境变量展开 `${VAR}`，这**不是安全传密钥的机制**——脚本把 Token 写进沙箱，提示注入的 Agent 就可能读取外传。秘密应优先留在宿主工具中。

## 9. LangSmith 托管沙箱

除 Backend 外还提供：

| 能力 | 用途 |
|---|---|
| Snapshots | 从镜像构建文件系统映像，或捕获运行中沙箱并从快照启动 |
| Service URLs | 通过认证 URL 访问沙箱内的 HTTP 服务 |
| Auth Proxy | 为出站请求注入凭证，避免把凭证硬编码进沙箱 |
| Mounts | 挂载 S3、GCS 或公开 Git 仓库 |
| Permissions | 控制工作区成员能否与沙箱交互 |
| CLI / SDK | 创建管理沙箱、交互式控制台、构建快照、隧道 TCP 端口 |
| Harbor | 运行评估与 rollout |

Auth Proxy 是「沙箱要访问已认证服务」时比复制 API Key 更好的选择：沙箱发普通请求，代理转发时加认证头，Agent 看不到秘密；但仍要配合网络策略与最小权限。

## 10. 扩展点

| 需求 | 扩展什么 |
|---|---|
| Python Agent 接入新执行环境 | 实现 `SandboxBackendProtocol`（`BaseSandbox` + `id`/`upload_files`/`download_files`/`execute`） |
| 让用户运行 `dcode --sandbox acme` | 实现并注册 `SandboxProvider` |

`execute()` 返回 `ExecuteResponse(output, exit_code, truncated)`，没有 `error` 字段——命令失败用非零 `exit_code` 表示；上传/下载才用各自的 `error`。未实现 `delete` 时模型会自动看不到删除工具。v0.7 的覆盖、截断语义在沙箱内同样成立：沙箱限制副作用范围，不会把部分搜索结果自动变成全集。

## 11. 可观测性与安全闭环

- **观测**：LangSmith traces 展示 Agent 在沙箱跑了哪些命令、如何调用文件工具；先看 trace 再猜执行过程；
- **凭证优先级**：① 宿主侧认证工具（首选）② Auth Proxy/凭证注入代理 ③ 把凭证注入沙箱（不推荐，可能被提示注入读取外传）。若被迫用第三种，要同时：所有工具加 HITL、阻断/限制网络、最小作用域最短生命周期凭证、监控异常出站；
- **产物默认不可信**：使用前审查代码、报告、构建物与下载文件；不需要联网就关网络；用 Middleware 过滤敏感模式。

沙箱、宿主侧凭证、网络控制、HITL、观测与产物审查共同组成安全闭环——任何单独一层都不足以让 Agent 的副作用自动安全。

## 12. 本篇验收

- [ ] 能区分 Python Backend、`dcode`、LangSmith Sandboxes 三层；
- [ ] 知道沙箱 Backend 多了 `execute`，且 `FilesystemPermission` 管不到它；
- [ ] 会用 `exit_code` 判断命令成功，不只看消息状态；
- [ ] 能说清沙箱保护宿主机、但不防提示注入与网络外传；
- [ ] 理解 Sandbox as tool 与 Agent in sandbox 的取舍；
- [ ] 会区分「Agent 工具」与「宿主 upload/download」两个文件平面；
- [ ] 能按 Thread/Assistant 作用域配置生命周期与 TTL；
- [ ] 知道 `dcode` 的参数、默认工作目录与 setup 脚本的边界；
- [ ] 记住凭证优先留在沙箱外、产物默认不可信。

> **补记**：这一章的主线是「**执行能力与权限边界分开设计**」：沙箱解决「在哪执行、能碰到什么」，凭证与网络解决「能带出什么」，HITL 与产物审查解决「要不要放行」。最常见的误区是把沙箱当万能安全层，或把文件权限当 Shell 权限——两者覆盖的入口完全不同。
