# 任务规划与分解：让 Agent 拆解复杂任务

## 1. 为什么需要规划

简单任务一步到位：「北京今天天气怎么样？」→ 调天气工具 → 回答。

复杂任务需要多步，例如「调研 LangGraph 技术架构，对比三个竞品，写一份 3000 字分析报告」——涉及搜索多个来源、阅读整理、对比分析、组织结构、撰写。没有明确清单时，Agent 容易：

- **遗漏关键步骤**：直接写报告，忘了先搜竞品；
- **重复劳动**：同一个关键词搜三次，因为「忘记」搜过；
- **半途而废**：上下文变长后失去整体进度感；
- **质量不稳定**：有时很好，有时莫名跳过重要环节。

规划让 Agent **先思考再行动**：拆解、执行、追踪、动态调整。

## 2. v0.7 中显式启用任务规划

`TodoListMiddleware` 会同时注入 `write_todos` 工具、`todos` 状态和规划提示词。v0.7 默认不再安装它：

```python
from deepagents import create_deep_agent
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(
    model=model,
    middleware=[TodoListMiddleware()],
)
```

是否启用应由任务与产品需求决定：

| 场景 | 建议 |
|---|---|
| 单步问答、短工具调用 | 保持关闭，避免计划比任务还长 |
| 长程、多阶段、容易漏步骤 | 启用，并用真实任务检查完成率与轨迹长度 |
| 能力较弱、容易失去主线的模型 | 先做 A/B 评测，通常值得尝试 |
| UI 要展示计划、当前步骤与进度 | 启用；此时 `todos` 也是产品状态协议 |

## 3. `write_todos` 工具

启用后 Agent 获得 `write_todos`，但工具存在不代表每个任务都会调用——行为由模型、提示词、任务复杂度共同决定。

**数据结构**：

```python
{
    "content": "搜索 LangGraph 官方文档，整理核心架构和 API 设计",
    "status": "pending"
}
```

**三种状态**：

| 状态 | 含义 | 场景 |
|---|---|---|
| `pending` | 待办 | 刚规划，还没开始 |
| `in_progress` | 进行中 | 正在执行 |
| `completed` | 已完成 | 标记完成 |

常见流转 `pending → in_progress → completed`，模型也可根据新信息调整清单——这不是框架强制的状态机。**`completed` 是 Agent 写入的进度标记**，应用仍需检查产物：报告是否生成、引用能否核实、代码是否通过测试。只看清单全绿不能判断质量。

**典型使用过程**：

1. **制定计划**：把任务拆成 5 条 pending；
2. **逐步执行**：更新当前项为 in_progress → 调搜索/写文件 → 标记 completed；
3. **动态调整**：发现新需求，插入「补充 Durable Objects 资料」。

**持久化**：清单保存在 **Agent State 的 `todos` 字段**，与消息历史分开：

- 同一次运行中后续步骤可继续访问；默认对话总结不会删除 `todos`；
- 多次 `invoke()` 之间自动接续需要 Checkpointer + 同一 `thread_id`；只加 Middleware 不会接续；
- `InMemorySaver` 只在当前进程保存，跨进程恢复要用数据库等持久化 Checkpointer；
- 默认 `general-purpose` 与 `subagents=[...]` 声明的子 Agent **不继承** 主 Agent 的 `TodoListMiddleware`，需要时在子 Agent 自己的 `middleware` 中启用；
- 默认隔离模式下，子 Agent 清单保存在自己的 `todos`，不读主清单、也不写回。

## 4. 引擎盖下：LangChain 中间件

Deep Agents 构建在 LangChain 上，LangChain 的 **Middleware** 是 Agent 能力的插件机制；`create_deep_agent()` 本质是把一组中间件自动组装到 Agent 上。

### 4.1 两类 Hook

| 风格 | Hook | 执行方式 | 适合 |
|---|---|---|---|
| Node-style | `before_agent`、`before_model`、`after_model`、`after_agent` | 编译成图中的独立节点，按生命周期运行 | 校验、状态更新、审计、人工中断 |
| Wrap-style | `wrap_model_call`、`wrap_tool_call` | 包裹一次模型/工具调用，可不调用、调用一次或多次 `handler` | 重试、缓存、降级、请求/响应转换 |

这对 `interrupt()` 尤其重要：Node-style 有清晰的图节点边界，暂停/恢复时容易推断哪些逻辑会重放；Wrap-style 位于 model/tools 节点内部，恢复可能连同 `handler` 一起重新执行。**自定义人工中断优先放 Node-style Hook**。

### 4.2 中间件从哪里来

**默认中间件**：`FilesystemMiddleware`（7 个文件工具 + 权限）、`SummarizationMiddleware`（上下文压缩）、`PatchToolCallsMiddleware`（补齐缺失的工具响应）、Prompt caching 等（取决于模型与 profile）。

**通过专用参数**：`subagents=` → `SubAgentMiddleware`（含默认 general-purpose，提供 `task`）；`skills=` → `SkillsMiddleware`；异步子 Agent → `AsyncSubAgentMiddleware`；`memory=` → `MemoryMiddleware`；`interrupt_on=` → `HumanInTheLoopMiddleware`。

**通过 `middleware=[...]`**：`TodoListMiddleware` 等可选策略按需加入；**与默认 Middleware 同名的实例会在原位置换**默认实例，而不是末尾叠加；替换是完整实例替换，不会按字段合并新旧配置。

### 4.3 PatchToolCallsMiddleware 补什么

模型发出工具调用后，消息历史通常需要一条对应响应，`tool_call_id` 把两条消息关联。如果运行在响应写回前被取消，历史里只剩调用请求。下一次运行前，`PatchToolCallsMiddleware` 在 `before_agent` 检查历史，为缺失响应补一条 `ToolMessage` 说明调用被取消；参数损坏或截断的调用则说明未执行。

它**只补消息记录**：不重新执行搜索，也不把错误结果改成正确结果；已有响应的调用（哪怕返回错误）不属于缺口。补上的取消说明也不能证明外部操作已撤销——服务端可能已处理，只是客户端没拿到结果。

容易混淆的四个职责：

| 情况 | 谁处理 | 注意 |
|---|---|---|
| 有调用缺响应 | `PatchToolCallsMiddleware` | 不重试、不验证结果 |
| 工具调用可重试异常 | 应用配置 `ToolRetryMiddleware` | 写操作要考虑重复执行 |
| 下次运行继续上次状态 | Checkpointer + 同一 `thread_id` | 跨进程需持久化 |
| 工具返回了但内容是否正确 | 校验、评测、人工审核 | 调用成功 ≠ 结果正确 |

**Checkpointer 属于 LangGraph 运行时**，通过 `checkpointer=` 配置，不是 `middleware=[...]` 的一项。恢复也不是回到任意一行：`interrupt()` 恢复会从当前节点开头重放，有副作用的操作要考虑幂等性（第 10 篇）。

### 4.4 TodoListMiddleware 的真实形态

`write_todos` 的底层就是 LangChain 的 `TodoListMiddleware`。无论 `create_deep_agent()` 还是更底层的 `create_agent()`，v0.7 都需要显式添加：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import TodoListMiddleware
from deepagents.middleware import FilesystemMiddleware

agent = create_agent(
    model=model,          # 规划属复杂推理，建议用能力较强的模型
    tools=[],
    middleware=[
        TodoListMiddleware(),
        FilesystemMiddleware(),   # 自动注入 read_file / write_file 等
    ],
)
```

添加后自动获得三样东西：`write_todos` 工具、`todos` 状态（跨次接续由 Checkpointer 负责）、规划指导提示词。

自定义配置只有两个参数：`system_prompt`（规划指导）与 `tool_description`（工具描述）。大多数情况默认就够；只有当规划行为需要特别引导（比如「总是先写测试再写代码」）才改。

### 4.5 两个同名 SummarizationMiddleware

第 4 篇的「对话历史自动总结」由 Deep Agents 的 `SummarizationMiddleware` 负责。LangChain 也有同名中间件，Deep Agents 复用了摘要逻辑，但执行位置与消息处理不同：

| 对比项 | LangChain 版本 | Deep Agents 版本 |
|---|---|---|
| 导入 | `langchain.agents.middleware` | `deepagents.middleware` |
| 执行位置 | `before_model`，独立图节点 | `wrap_model_call`，model 节点内部 |
| 正常摘要后 | 把 State 中旧消息替换为摘要，保留近期 | 保留原始消息，另记摘要与截断位置；本次模型输入用「摘要 + 近期」 |
| 历史保存 | 不写入 Backend | 旧消息写入 Backend，摘要附路径 |

因此 `agent.get_graph()` 里，LangChain 版会出现摘要节点；Deep Agents 版位于 model 节点内部，不会单独出现——图只展示节点结构，不展开节点内部包装。

**手动实例化要设置 `trigger`**：两者默认值都是 `None`，不会主动摘要；`create_deep_agent()` 会为默认摘要器选择触发条件，直接用 `create_agent()` 组装则不会自动获得这组默认配置。图中是否有摘要节点，也不能证明摘要已触发。

想观察摘要，给两者都设 `trigger=("messages", 4)`、`keep=("messages", 2)`，传几轮消息后比较模型实际收到的消息。数字只用于小规模演示；实际按上下文大小与信息保留需求设置。Deep Agents 还会在模型调用抛 `ContextOverflowError` 时摘要后重试——这与按 `trigger` 主动摘要是两条触发路径。

## 5. 规划与上下文管理的协同

长任务执行到第 6 步时，前 5 步的搜索结果、文件操作、思考过程都堆在上下文里。此时第 4 篇的机制介入：

1. **大结果卸载**：大量搜索结果已卸载到文件系统；
2. **对话总结**：仍超过阈值时，旧消息被总结，本次输入改为摘要 + 近期消息（已知窗口时默认 85%，可用 `trigger` 自定义）。

关键在于：**默认总结压缩发给模型的消息，不删除单独保存的 `todos` 字段**。清单帮助 Agent 在总结后继续追踪：总共哪些步骤、哪些完成、下一步做什么。但清单是否及时更新、下一步是否合理仍取决于模型；调试时要把 `todos`、工具调用记录与最终产物放在一起看，不能只看进度标记。

**在 LangChain 中手动组合**（文件工具与摘要器使用同一 Backend，摘要里的历史路径才能读回）：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import TodoListMiddleware
from deepagents.backends import StateBackend
from deepagents.middleware import FilesystemMiddleware, SummarizationMiddleware

backend = StateBackend()
agent = create_agent(
    model=model,
    tools=[],
    middleware=[
        TodoListMiddleware(),
        FilesystemMiddleware(backend=backend),
        SummarizationMiddleware(
            model=model,
            backend=backend,
            trigger=("tokens", 4000),
            keep=("messages", 20),
        ),
    ],
)
```

`trigger` 是何时开始摘要，`keep` 是保留多少近期消息；没有可总结的旧消息就不会生成摘要。比例阈值写 `("fraction", 0.85)`，需要模型 profile 提供 `max_input_tokens`；窗口未知时用 `("tokens", N)` 或 `("messages", N)`。`StateBackend` 把卸载文件存在 State 中，跨进程保存要靠持久化 Checkpointer。

## 6. 完整示例

```python
import os
from langchain_openai import ChatOpenAI
from tavily import TavilyClient
from deepagents import create_deep_agent
from langchain.agents.middleware import TodoListMiddleware

model = ChatOpenAI(
    model="zai-org/GLM-5.2",          # 多步骤规划建议用较强模型
    api_key=os.environ["SILICONFLOW_API_KEY"],
    base_url="https://api.siliconflow.cn/v1",
)

tavily_client = TavilyClient(api_key=os.environ["TAVILY_API_KEY"])

def internet_search(query: str, max_results: int = 5) -> dict:
    """搜索互联网获取最新信息。"""
    return tavily_client.search(query, max_results=max_results)

agent = create_deep_agent(
    model=model,
    tools=[internet_search],
    middleware=[TodoListMiddleware()],
    system_prompt="""你是一位专业的技术研究员。
面对复杂研究任务时，你会：
1. 先用 write_todos 制定研究计划
2. 逐步执行每个步骤，及时更新进度
3. 将搜索结果写入文件系统整理
4. 最终输出完整的研究报告
""",
)

result = agent.invoke({
    "messages": [{
        "role": "user",
        "content": "请调研 Agent 开发领域的三大 Harness 框架（Deep Agents、Claude Agent SDK、Codex SDK），对比核心能力差异，写一份简要分析报告。"
    }]
})
print(result["messages"][-1].content)
```

期望过程是：制定计划 → 执行并更新状态 → 用 `write_file` 保存中间结果 → 综合输出报告。但这些是期望行为，不是固定顺序；运行后应检查实际工具调用、`result.get("todos", [])` 与最终报告，确认清单与产物一致。

## 7. 中间件全景

| 类别 | 中间件 | 用途 |
|---|---|---|
| 默认 | FilesystemMiddleware | 7 个文件工具 + 权限 |
| 默认 | SummarizationMiddleware | 对话历史自动总结 |
| 默认 | PatchToolCallsMiddleware | 补齐缺失的工具响应 |
| 专用参数 | SubAgentMiddleware | `task` + 子 Agent 委派 |
| 专用参数 | SkillsMiddleware | 技能包注入 |
| 专用参数 | AsyncSubAgentMiddleware | 异步子 Agent |
| 专用参数 | MemoryMiddleware | 记忆注入 |
| 专用参数 | HumanInTheLoopMiddleware | 人工审批 |
| 可选 | TodoListMiddleware | 任务规划与追踪 |
| 可选 | PIIMiddleware | 个人信息脱敏 |
| 可选 | ToolRetry / ModelRetry / ModelFallback | 重试与降级 |
| 可选 | ToolCallLimit / ModelCallLimit | 调用次数限制 |
| 可选 | ContextEditingMiddleware | 清理旧工具结果 |
