# 附录：v0.7 更新与迁移

> 一个在线运行的 Deep Agent 升级到 v0.7 后，账单可能下降，也可能没明显变化；它可能继续稳定完成任务，也可能突然不再生成 Todo。原因在于 v0.7 调整了默认 Harness 替应用做决定的范围。

课程从 Deep Agents 0.5 起步，前面章节保留了 0.5、0.6 逐步演进的痕迹。v0.7 延续这条路径并把基线向前推进：减少每轮固定携带的通用上下文，把规划等策略交还给应用，并补齐文件工具与 Middleware 的配置能力。新读者可直接用最新 0.7.x 补丁版本；旧读者应先做迁移检查，再继续实验。

架构变化很清楚：**默认层更薄，原先藏在框架里的策略需要应用显式选择。**

```bash
uv add --upgrade "deepagents>=0.7,<0.8"
uv run python -c "import deepagents; print(deepagents.__version__)"
```

提交 `uv.lock` 或环境快照，才能记录解析到的精确版本。要逐项复现首发 changelog，再在独立临时环境固定 `==0.7.0`。**不要直接在生产环境原地升级**——v0.7 同时改变默认 Middleware、Backend 兼容接口与文件工具输出，单看「能否 import」不能证明迁移完成。

## 1. 四组默认策略变化

| 表面变化 | 设计判断 | 应用要接手什么 |
|---|---|---|
| 默认基础提示词变空、工具说明缩短 | 现代模型更能从 Schema 理解接口，不必重复教程式说明 | 写清业务系统提示词，用 Trace 检查冲突与冗余 |
| Todo 不再默认启用 | 显式计划不是所有任务的普遍增益 | 按任务长度、模型能力、UI 需求决定是否恢复 |
| 同名 Middleware 可原位替换 | 内置栈给合理默认，但不应封死阈值、模型与提示词 | 管理替换实例的完整配置与继承范围 |
| 文件工具更强、更有界 | 高效处理大文件大目录，同时避免无限搜索 | 重新审查删除、覆盖、输出解析、权限与截断 |

逐条浏览 changelog、机械地问「这个功能我用不用」很容易漏掉隐式依赖。先回答：

1. 应用以前依赖了哪些**隐式默认值**？
2. 哪些默认值在任务里仍有价值，应该显式恢复？
3. 哪些地方消费了文件工具的**原始文本或 Backend 兼容接口**？
4. 用什么业务评测证明更轻的 Harness 没改变关键行为？

## 2. 正确理解「基础输入 Token 减少 65%」

官方两个数字描述不同范围：

- 默认 Agent 的工具 Schema 描述从 **4,005 Token 降到 2,302 Token**，降幅 43%；其中 `task` 工具说明从 1,664 降到 389，是最大单项缩减；
- 加上空基础提示词和 Todo 改为可选后，默认 Agent 简单回合输入从 **5,395 降到 1,895 Token**，基础输入降幅约 65%。

这说明「每轮都要携带的框架固定成本」明显降低，但**不能推导出「任意应用总成本下降 65%」**。真实调用还包含用户消息与历史、Skills/Memory/应用提示词、工具参数与结果、子 Agent 轨迹、摘要与重试、提供商缓存与计费。

长程任务本来就有几十万 Token 历史与工具结果时，少掉约 3,500 个基础输入 Token 仍有价值，但占比不会是 65%。

### 2.1 端到端评测看总体趋势

官方评测覆盖三类工作：**Autonomous**（编程、数据分析、长程工具使用）、**Conversational**（模拟用户多轮对话）、**Long-context/Retrieval**（长上下文中检索组合）。Harbor 任务包含运行环境、任务说明与验收脚本，评分看 Agent 修改的文件与环境状态，不只看最终回复；每个任务重复运行以降低非确定性波动。

v0.6.12 与 v0.7 的跨版本对比（36 个任务、每任务 3 次 rollout、四种模型）中，精确结果比「普遍更省」更有指导意义：

| 模型 | Reward | Token | 成本 | 怎么读 |
|---|---:|---:|---:|---|
| `gpt-5.6-luna` | +3.8% | -35.5% | -15.2% | Token 与成本下降明确，Reward 仍在不确定区间 |
| `gemini-3.6-flash` | -6.7% | -4.7% | -8.1% | 三项置信区间都跨零，不能断言变好或变差 |
| `claude-sonnet-4-6` | +3.1% | +31.3% | +36.8% | 两个高难自治任务轨迹更长，抵消了基础 Prompt 节省 |
| `claude-opus-4-8` | -5.1% | -25.4% | -16.4% | Token 下降明确，Reward 与成本仍非普遍结论 |

所有模型 Reward 置信区间都跨零，官方结论是「整体质量没有可测量的回退」，不能改写成「v0.7 让所有模型质量提升」。Sonnet 的结果说明：**基础开销更低不保证轨迹更短。**

### 2.2 升级验收要分开记三类指标

1. **基础开销**：简单回合的 input tokens，验证默认 Harness 确实变轻；
2. **轨迹效率**：完成同一任务的模型轮次、工具调用数、子 Agent 调用数、重试数；
3. **业务结果**：任务是否通过真实验收，而不是最终文本是否看起来合理。

只比第一项，很容易在 Sonnet 一类场景得出错误结论。

## 3. 默认 Prompt 变空

v0.7 移除了原先附加的通用基础提示词，也删掉了与工具 Schema 重复的 Middleware 使用说明。删的是「框架代写的通用做事方法」，不是 Skills、Memory 或文件路径路由等只有运行时才知道的信息。

两条上下文工程原则：**接口优于示例**（清晰的工具名、参数类型、枚举与约束能直接表达动作；大量 few-shot 反而把模型限制在示例路径里）；**避免重复**（同一约束同时写进系统提示词和工具描述，不会得到双倍遵从，却永久增加输入并提高冲突概率）。

### 3.1 自定义提示词现在更「说了算」

以前 `system_prompt` 会与框架基础提示词共同构成上下文，即使不冲突，也可能重复规定语气、规划或工作方式。v0.7 默认基础层为空，应用提示词的含义更直接：

```python
agent = create_deep_agent(
    model=model,
    system_prompt=(
        "你是代码迁移助手。先读取仓库中的版本约束和测试入口，"
        "只修改与迁移目标有关的文件；完成后运行项目已有测试，"
        "并明确报告未能验证的部分。"
    ),
)
```

不要因为「旧版有一段长基础 Prompt」就把旧内容完整复制进应用——那会把 v0.7 刚移除的固定成本与潜在冲突带回来。诊断顺序：

1. 检查工具 Schema 是否已表达约束，不要先重复粘贴；
2. 检查是否依赖旧基础 Prompt 的通用行为（主动验证、进度播报、少问问题）；
3. 只补对业务结果有影响的规则，并建立评测样例；
4. 看 Trace，确认新增提示没让模型产生额外解释、规划或循环。

## 4. Todo 改为可选

`create_deep_agent()` 不再默认安装 `TodoListMiddleware`。没有显式启用时，三样一起消失：`write_todos` 工具、`todos` state channel、Todo 规划提示词。

官方在 GPT-5.6 Terra、Claude Opus 4.8、GLM 5.2 上比较后，没有观察到 Todo 带来统计显著的准确率提升，其中两种模型 Token 使用还更高——框架不再让所有调用为显式规划付费。

| 场景 | 建议 | 原因 |
|---|---|---|
| 单步问答、短工具调用 | 关闭 | 计划可能比任务还长 |
| 长程、多阶段、容易漏步骤 | 启用 | 显式状态帮助跨轮保持目标 |
| 能力较弱、容易失去主线 | 先 A/B 评测，通常值得尝试 | 弱模型更依赖外部脚手架 |
| UI 要展示计划与进度 | 启用 | Todo 同时是产品状态协议 |
| 后台批处理只看最终产物 | 默认关闭，评测决定 | 用户不需要可见计划 |

```python
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(model=model, middleware=[TodoListMiddleware()])
```

### 4.1 注意继承范围

- 默认 `general-purpose` 只继承主 Agent 对默认中间件的同名覆盖；默认栈没有 Todo，所以不会继承主 Agent 显式传入的实例；
- 声明式 `subagents=[...]` 也不继承，需要在自己的 `middleware` 字段启用；默认 general-purpose 要用同名 spec 覆盖；
- 默认隔离模式下各子 Agent 的 `todos` 独立，不读也不写回主清单。

```python
researcher = {
    "name": "researcher",
    "description": "执行需要多个检索与验证步骤的研究任务",
    "system_prompt": "先规划证据收集步骤，再逐项完成并标记状态。",
    "middleware": [TodoListMiddleware()],
}
```

> **例外**：OpenAI Codex harness profile 的系统提示词明确依赖 `write_todos`，所以 profile 会自动保留 Todo。迁移时不要只按包版本猜工具集合，以实际 profile 与 Trace 为准。

如果 Todo 被用于前端进度，升级测试必须覆盖 state channel，不能只确认最终答案仍能生成。

## 5. Middleware 原位覆盖

过去传入自定义 `SummarizationMiddleware` 会因与默认实例重名报重复错误；v0.7 改为按 `.name` 匹配，同名时**在原位置换**默认实例。

```python
agent = create_deep_agent(
    model=model,
    backend=backend,
    middleware=[
        SummarizationMiddleware(
            model=summary_model,
            backend=backend,
            trigger=("fraction", 0.5),
            keep=("messages", 20),
            summary_prompt="总结此前对话，原样保留文件路径、已确认的决定、未完成事项和失败原因。",
        )
    ],
)
```

默认摘要约在窗口使用 85% 时触发。工具结果多、长对话容易出现 context rot 的应用，提前到 50% 可能更稳，但会增加摘要频率与信息损失风险；阈值不是越低越好，要同时检查摘要成本与后续成功率。

### 5.1 覆盖与继承规则

1. `.name` 与内置实例相同：原位置换，保留栈的相对顺序；
2. 没有同名默认实例：插入核心 Middleware 之后、profile/prompt caching/memory 尾部之前；
3. 默认 `general-purpose` 子 Agent 会继承主 Agent 对默认实例的覆盖；
4. 声明式子 Agent 独立构建自己的栈，需在各自 spec 中配置；
5. 必须位于尾部的 Middleware 仍保持既定顺序（如工具排除要在工具注入之后）。

### 5.2 最容易忽略的陷阱：整实例替换

同名覆盖**不是字段级 merge**。传入自定义 `FilesystemMiddleware` 或 `SummarizationMiddleware` 后，框架不会把默认实例中的 Backend、工具说明、权限状态或其他构造参数逐字段补到新实例。

两条规则：**共享同一个 Backend 实例**，避免主 Agent 与 Middleware 读写不同文件空间；**把替换实例当完整配置重新审查**，不要只关注想改的那个字段。

`0.7.0` 中文件权限由框架通过私有配置注入默认 `FilesystemMiddleware`。如果一边用顶层 `permissions=`、一边替换整个文件 Middleware，不能假定拒绝规则会自动合并。更稳妥的是升级到经过验证的最新 0.7.x、避免依赖私有参数，并用真实的允许/拒绝调用做回归——**工具从模型界面消失，不代表权限边界仍然成立。**

## 6. 文件工具：更高效，也更需审查副作用

| 变化 | v0.7 行为 | 对现有应用的影响 |
|---|---|---|
| `write_file` | 目标存在时直接完整覆盖 | 依赖「已存在即报错」的保护会失效 |
| `delete` | 加入默认文件工具，可递归删除目录 | 新增高风险副作用，需要权限、审批或 allowlist |
| `read_file` 分页 | 返回总行数、剩余行数与下一次 `offset` | Agent 可直接跳页或到文件尾部 |
| `grep`/`glob` 超时 | 返回已找到的有效结果并标 `truncated` | 「成功」可能只是部分成功 |
| `grep` 匹配数 | 面向模型默认最多 1,000 个并流式消费本地 `rg` | 宽查询需要主动收窄 |
| 空 `ls`/`glob` | 文本变为 `No files found`，不再是 `[]` | 解析原始输出的代码要改 |
| `read_file` 行号槽 | 行号后两个空格，不再固定宽度加 Tab | 按 Tab 切分的解析器会失败 |

### 6.1 覆盖与精确编辑

- 完整重写：`write_file`；
- 只改局部：先 `read_file`，再用 `edit_file` 精确替换。

这样避免为了重写把整个旧文件作为 `old_string` 发回模型，减少 Token；但也移除了误覆盖保护。配置、凭证、生产脚本等敏感路径不能依赖旧错误行为，应显式用 `FilesystemPermission`、HITL 或只读工具集。

### 6.2 delete 是写操作，目录删除全有或全无

支持删除的 Backend 会向 Agent 暴露 `delete`。递归删除时权限层检查目标与所有后代：任何路径命中拒绝，整个删除都不执行，不会留下删了一半的目录树；符号链接删除链接本身，不跟随目标。

不需要删除时，最小权限是根本不暴露：

```python
agent = create_deep_agent(
    model=model,
    backend=backend,
    middleware=[
        FilesystemMiddleware(
            backend=backend,
            tools=["read_file", "ls", "glob", "grep"],
        )
    ],
)
```

这个 allowlist 只控制内置文件工具，不会删自定义工具。`read_file` 是必需能力不能排除；`execute` 与 `delete` 还受 Backend 能力限制——allowlist 只能收窄，不能把不支持的能力变出来。后续修复确保被排除的工具会从 `ToolNode` 注册表移除，不只对模型隐藏。主 Agent 的同名覆盖会传给默认 general-purpose，声明式子 Agent 仍要单独限制。

### 6.3 部分搜索结果不是错误，也不是全集

```python
result = backend.grep("TODO", path="/workspace")

if result.error:
    raise RuntimeError(result.error)

for match in result.matches or []:
    consume(match)

if result.truncated:
    schedule_narrower_search()
```

不能用「没有异常」推断搜索完整，也不能因 `truncated=True` 丢掉已返回的有效匹配。`CompositeBackend` 会在任一子路由结果不完整时传播 `truncated=True`。

`grep` 的 1,000 匹配上限是 `FilesystemMiddleware` 面向模型的默认值，模型可用 `max_count` 调整；直接调 Backend 默认仍无上限。`context_lines` 在 0.7.0 首先加入本地 `FilesystemBackend.grep()` 的直接调用接口，并没有同时成为所有 Backend 与模型工具的统一参数。

### 6.4 分页元数据优化的是轨迹

`read_file(offset, limit)` 在缺少分页信息时，模型需要猜文件是否还有内容、下一页从哪开始。v0.7 尾部提示报告已读行范围、总行数、剩余行数与下一 `offset`。官方 301 行文件评测中，两种模型都把读取次数稳定降到两次并直接跳向尾部——**更好的工具反馈会改变整个调用轨迹**，所以 Harness 优化不能只看 Prompt Token。

## 7. 会阻塞升级的兼容变化

### 7.1 Backend Factory 被移除

v0.5 起废弃的 Backend Factory 在 v0.7 正式删除：`create_deep_agent()` 接收具体的 `BackendProtocol` 实例，而不是按 runtime 创建 Backend 的 callable。

```python
# v0.6.x 旧写法
agent = create_deep_agent(backend=lambda runtime: StoreBackend(), store=store)

# v0.7
backend = StoreBackend(namespace=lambda runtime: (runtime.server_info.user.identity,))
agent = create_deep_agent(model=model, backend=backend, store=store)
```

这不只是类型收紧：以前隐式的 assistant-id namespace fallback 被移除，应用必须明确文件属于哪个用户、租户或业务范围。**namespace 设计错误可能导致跨用户读取**，不能为了通过类型检查随便填常量。

同时处理：删除 `BackendFactory`、`BACKEND_TYPES`、`FileFormat`、`Unset`；删除 `StateBackend(runtime=...)`、`StoreBackend(runtime=...)` 旧参数；迁移 `ls_info`、`glob_info`、`grep_raw` 与纯字符串 `read()`；删除 `SummarizationMiddleware(history_path_prefix=...)`（历史卸载改用配置的 Backend）；认识到 `FilesystemBackend` 与 `LocalShellBackend` 默认 `virtual_mode=True`。

新文件的 `FileData.content` 用字符串；旧版持久化的 `list[str]` 仍可读取，并在下次覆盖/编辑时转换，无需一次性重写存量文件，但序列化器与自定义 Backend 应同时接受迁移期数据。

### 7.2 原始输出解析器要单独排查

如果应用只把工具结果交回模型，格式变化通常由模型自然适应；如果自己解析 `ToolMessage.content`，检查这些写法：

- 把空目录结果与字符串 `"[]"` 比较；
- 对 `read_file` 每行执行 `split("\t", 1)`；
- 假设行号固定宽度；
- 把 `ToolMessage.status == "success"` 当搜索完整；
- 假设 `write_file` 在文件已存在时一定失败。

机器消费的逻辑优先用 Backend 的结构化结果，不要把给模型阅读的文本当稳定协议。

### 7.3 先静态扫描，再跑真实迁移测试

```bash
rg -n 'BackendFactory|BACKEND_TYPES|FileFormat|Unset|history_path_prefix' .
rg -n 'ls_info|glob_info|grep_raw' .
rg -n 'backend\s*=\s*(lambda|[A-Za-z_][A-Za-z0-9_]*_factory)' .
rg -n 'split\("\\t"|cat -n|No files found|write_file' .
```

搜索结果不是迁移完成证明——它只能找常见旧符号，找不到业务代码对 Todo state、工具存在性或错误语义的隐式依赖。

## 8. 两组按需关注的能力

**Provider 级 Prompt Caching**：AWS Bedrock 用户可通过 `deepagents[aws]` 使用；安装兼容版本的 `langchain-fireworks` 时，会为主/子 Agent 自动加入 Fireworks prompt-cache session affinity。它们只优化特定提供商的缓存复用，验收应查缓存读写 Token、session/thread affinity 与实际账单。

**NVIDIA Nemotron 3 Ultra Harness Profile**：覆盖 NVIDIA/ChatNVIDIA、Baseten、Fireworks、OpenRouter、Nebius、Together，加入工具调用兼容修复、循环控制、最终答案保护与 NIM app-origin 标记。不用 Nemotron 就不是升级阻塞项；用了则关注 profile 可能增加的修复轮次与自动修正后的 Trace。

## 9. 从 0.5/0.6 升级到 0.7 的七步

1. **记录 v0.6 基线**：覆盖短问答、长程多步、子 Agent、大文件分页/大目录搜索、权限拒绝或审批五类任务；保存成功率、Token、轮次、工具数、子 Agent 数、延迟与成本。
2. **隔离环境升级**：用 `>=0.7,<0.8` 取当前补丁并锁快照；只有复现首发行为才用 `==0.7.0`。不要与「同时升级模型、提示词和业务工具」混在一批。
3. **迁移直接报错的 API**：Backend factory、显式 Store namespace、移除符号、`history_path_prefix`、旧 Backend 方法；目标是完成初始化与基本调用。
4. **逐项声明原先依赖的默认策略**：是否需要 Todo（主与每个子 Agent 是否一致）；系统提示词是否缺少旧默认层的关键行为；是否覆盖摘要模型/阈值/提示词；`delete` 与覆盖写入是否符合权限模型；文件工具是否该用 allowlist 收窄。
5. **重写原始输出解析测试**：加入空目录、Tab 缩进文件、分页文件、截断搜索、已存在文件覆盖、递归删除拒绝等样例；结构化结果与面向模型的文本分别测试。
6. **LangSmith 同任务对比**：

| 观察项 | 异常信号 | 可能动作 |
|---|---|---|
| 首轮 input tokens | 没明显下降 | 检查应用 Prompt、Skills、Memory 或工具描述是否占主导 |
| 模型轮次 | 明显增加 | 检查 Todo 移除、工具说明过短或模型进入循环 |
| `write_todos`/`todos` | UI 依赖但已消失 | 显式恢复 TodoListMiddleware |
| 摘要触发点 | 太晚 context rot / 太早丢信息 | 同名覆盖调整 trigger、keep、提示词 |
| 文件搜索 | `truncated` 后仍直接下结论 | 引导缩小路径，或继续分片搜索 |
| 文件副作用 | 意外覆盖或删除 | 收窄工具、加强路径权限、增加 HITL |

7. **渐进放量**：先让一部分流量进入 v0.7，比较同类任务的成功率与成本；基础 Token 下降是好信号，但只有业务结果稳定、轨迹没异常放大，迁移才算完成。

## 10. 最终决策表

| 如果你的应用…… | v0.7 的建议动作 |
|---|---|
| 只做短任务，没有进度 UI | 保持 Todo 关闭，享受更轻默认层 |
| 运行长程任务或较弱模型 | 显式启用 Todo，并用业务评测验证收益 |
| 使用对话摘要 | 用同名 `SummarizationMiddleware` 调阈值，但当作完整实例配置 |
| 解析文件工具原始文本 | 把输出格式迁移列为阻塞项，优先改用结构化结果 |
| 暴露真实文件系统 | 审查 `delete`、覆盖写入、allowlist、路径权限与 HITL |
| 使用 StoreBackend | 移除 factory，设计显式 namespace，做租户隔离测试 |
| 依赖 Provider 缓存或 Nemotron | 验证对应 profile/integration 的 Trace 与账单，不当通用收益 |

v0.7 的实用价值在于重新划清边界：**默认层保持轻量，工具接口说明能力，应用选择策略，评测检查结果。** 模型与任务继续变化时，这种分工比不断扩张的通用系统提示词更容易维护。

## 11. 本篇验收

- [ ] 能解释 65% 是「基础输入」而不是「总成本」；
- [ ] 能说出四组默认策略变化与应用要接手的责任；
- [ ] 知道基础提示词为空后，自定义提示词更直接也更需克制；
- [ ] 会判断是否需要 Todo，并知道它不自动传给子 Agent（Codex profile 例外）；
- [ ] 理解同名 Middleware 是原位置换、整实例替换、不合并字段；
- [ ] 能列出文件工具的七项语义变化与对应风险；
- [ ] 知道 Backend Factory 移除与显式 namespace 的安全含义；
- [ ] 能用静态扫描 + 业务评测完成七步迁移；
- [ ] 记住「工具从界面消失 ≠ 权限边界仍成立」。

> **补记**：v0.7 的迁移难点不在报错，而在**隐式依赖**——旧默认提示词提供的行为、Todo 的 state channel、`write_file` 的报错、`ToolMessage` 的文本格式，这些都不会在 import 时报错。稳妥做法是先记录基线，再按「API 报错 → 默认策略 → 输出解析 → Trace 对比 → 渐进放量」推进，并用业务验收而不是 Token 单项指标做最终判断。
