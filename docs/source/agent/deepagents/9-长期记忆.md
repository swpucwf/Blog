# 长期记忆：跨对话的持久化

## 1. 记忆的三步

Deep Agents 把记忆作为一等公民：Agent 以文件形式读写记忆，Backend 决定文件存在哪里。流程三步：

1. **准备存储与文件**：配置 Backend 与 Store，预置需要加载的记忆文件；
2. **加载记忆**：`memory=` 指定已有文件路径，内容进入系统提示词；`skills=` 指定包含 Skill 子目录的目录，先注入元数据，正文按需读取；
3. **更新记忆（可选）**：通过提示词约定何时写、写到哪个文件，由 Agent 调用 `edit_file` 等工具更新，供后续对话使用。

`memory=["/memories/preferences.md"]` 是**读取配置**。在 0.7.10 中，缺失的记忆文件会被跳过，不会自动创建，缺失路径也不会作为已加载记忆注入提示词。要固定偏好的写入位置，需要同时约定写入路径；只声明 `memory=` 不能保证 Agent 使用这个文件名。

最常见的两种模式：**Agent 级记忆**（所有用户共享）与**用户级记忆**（按用户隔离）。

## 2. 两种「记忆」

### 2.1 短期记忆：Thread-scoped

默认 `StateBackend` 把文件存在 LangGraph 的 Agent State 中，这是短期记忆：同一线程内持久、多轮不丢（靠 Checkpointer）、**按 `thread_id` 隔离**——新线程读不到旧线程的 State 文件；只要 Checkpointer 还保存旧线程状态，回到旧线程仍可读取。

像每段对话一张工作桌：新线程有自己的桌面；旧桌状态还在，回去仍能找到之前的文件。

### 2.2 长期记忆：Cross-thread

需要跨对话保留的信息：用户偏好（「我喜欢简洁的代码风格」）、项目背景（「我们用 React + TypeScript」）、累积研究成果、从反馈中学到的改进指令。这些不应随对话结束消失，需要能跨线程持久化的存储。

## 3. Checkpointer：短期记忆的基础

```python
from langgraph.checkpoint.memory import MemorySaver

agent = create_deep_agent(model=model, checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "conversation-001"}}
agent.invoke({"messages": [{"role": "user", "content": "我叫张三"}]}, config=config)
agent.invoke({"messages": [{"role": "user", "content": "我叫什么名字？"}]}, config=config)
# 能回答"你叫张三"

config2 = {"configurable": {"thread_id": "conversation-002"}}
agent.invoke({"messages": [{"role": "user", "content": "我叫什么名字？"}]}, config=config2)
# 不知道你是谁
```

工作原理：每次执行完一步自动保存状态（消息历史、文件系统状态、启用 Todo 后的清单等）；下次同 `thread_id` 自动恢复。开发用 `MemorySaver`（内存，重启丢），生产用 `PostgresSaver`（数据库）。**关键限制：只在同一个 `thread_id` 内有效。**

### 3.1 上下文管理策略

| 策略 | 做法 | 适用 |
|---|---|---|
| Trim | 只保留最近 N 条，丢弃更早 | 不需要历史上下文 |
| Delete | 用 `RemoveMessage` 精确删除 | 选择性清理（如敏感信息） |
| Summarize | LLM 把旧消息压缩成摘要 | 需要保留语义，最推荐 |

Deep Agents 已内置 Summarize（`SummarizationMiddleware`）：已知模型窗口时默认 85% 触发，否则用固定 token 阈值。正常摘要压缩的是发给模型的消息，State 中原始消息仍保留。

> v0.7 允许同名 `SummarizationMiddleware` **原位置换**默认实例——是整实例替换，不会只覆盖 `trigger` 或摘要模型；自定义时要把 Backend、保留消息数、触发条件与摘要提示词作为一组完整配置重新检查。写入长期记忆文件时，`write_file` 会完整覆盖，追加或局部修订要用 `edit_file`。

自定义裁剪可以用 `@before_model` 中间件，保留首条与最近几条：

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langchain.agents import AgentState
from langchain.agents.middleware import before_model
from langgraph.runtime import Runtime

@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict | None:
    messages = state["messages"]
    if len(messages) <= 3:
        return None
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), messages[0], *messages[-3:]]}
```

### 3.2 自定义 AgentState

可以扩展 `AgentState` 加字段（如 `user_id`、`preferences`），工具通过隐藏参数 `ToolRuntime` 读写：

```python
@tool
def get_user_info(runtime: ToolRuntime) -> str:
    """查询当前用户信息。"""
    user_id = runtime.state["user_id"]
    return "用户：张三，VIP 会员，偏好简洁风格"

@tool
def update_preferences(new_theme: str, runtime: ToolRuntime):
    """更新用户偏好设置。"""
    from langgraph.types import Command
    from langchain.messages import ToolMessage
    prefs = runtime.state.get("preferences", {})
    prefs["theme"] = new_theme
    return Command(update={
        "preferences": prefs,
        "messages": [ToolMessage("偏好已更新", tool_call_id=runtime.tool_call_id)],
    })
```

`runtime.state` 是**读**，`Command(update={...})` 是**写**——工具既能回结果给模型，也能改 Agent 的短期记忆。

## 4. CompositeBackend：长期记忆的核心

### 4.1 运行时身份与 namespace

`StoreBackend` 用 `namespace` 区分用户、Agent 或组织。部署到 LangSmith/LangGraph Server 时 `rt.server_info` 提供 `assistant_id` 与登录用户；本地 `invoke()` 或自托管时可能为空，先封装兜底：

```python
@dataclass(frozen=True)
class MemoryContext:
    user_id: str = "local-user"
    org_id: str = "default-org"

def assistant_namespace(rt):
    return (rt.server_info.assistant_id,) if rt.server_info else ("local-agent",)

def user_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return (rt.server_info.user.identity,)
    return (getattr(rt.context, "user_id", "local-user"),)

def org_namespace(rt):
    return (getattr(rt.context, "org_id", "default-org"),)
```

### 4.2 Agent 级与用户级

**Agent 级**：所有用户共享，namespace 设为 `(assistant_id,)`，同一个 Agent 的所有对话读写同一份记忆：

```python
agent = create_deep_agent(
    model=...,
    context_schema=MemoryContext,
    memory=["/memories/AGENTS.md"],
    skills=["/skills/"],
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/memories/": StoreBackend(namespace=lambda rt: (*assistant_namespace(rt), "memories")),
            "/skills/": StoreBackend(namespace=lambda rt: (*assistant_namespace(rt), "skills")),
        },
    ),
)
```

**用户级**：namespace 用 `(user_id,)`，保证 A 的偏好不会泄露给 B：

```python
routes={
    "/memories/": StoreBackend(namespace=lambda rt: (*user_namespace(rt), "memories")),
    "/skills/": StoreBackend(namespace=lambda rt: (*user_namespace(rt), "skills")),
}
```

### 4.3 路径路由

配置好后，文件操作按路径自动路由：

```python
write_file("/workspace/draft.txt", "...")          # StateBackend，新线程看不到
write_file("/notes.txt", "...")                     # StateBackend
write_file("/memories/preferences.md", "...")       # StoreBackend，跨对话保留
write_file("/memories/project/tech-stack.md", "...")# StoreBackend
```

对 Agent 来说操作完全一样，区别只在路径前缀：`/memories/` 开头会被持久化。

### 4.4 跨对话访问

按「初始化 → 约定写入 → 检查保存 → 新线程读取」走一遍：

```python
store = InMemoryStore()
user = UserContext(user_id="user-123")
namespace = (user.user_id, "memories")
memory_path = "/memories/preferences.md"

# 先创建文件；CompositeBackend 会去掉 /memories/ 路由前缀
store.put(namespace, "/preferences.md", create_file_data("# 用户偏好\n暂无记录。"))

agent = create_deep_agent(
    model=model,
    context_schema=UserContext,
    store=store,
    checkpointer=InMemorySaver(),
    backend=CompositeBackend(
        default=StateBackend(),
        routes={"/memories/": StoreBackend(namespace=lambda rt: (rt.context.user_id, "memories"))},
    ),
    memory=[memory_path],
    system_prompt=(
        f"当用户明确要求记住偏好时，先读取 {memory_path}，再用 edit_file 更新它。"
        "逐字保存用户给出的偏好条目，保留其他已有偏好，不要另建偏好文件。"
        "只有工具写入成功后，才告知用户已记住。"
    ),
)

# 对话 1：保存偏好
agent.invoke({"messages": [{"role": "user", "content": "记住：注释用中文，变量名用英文"}]},
             context=user, config={"configurable": {"thread_id": str(uuid4())}})

# 从 Store 核对写入结果
saved = store.get(namespace, "/preferences.md")
assert saved and "注释用中文" in saved.value["content"]

# 对话 2（全新 thread）：读取偏好
result = agent.invoke({"messages": [{"role": "user", "content": "帮我写一个排序函数"}]},
                      context=user, config={"configurable": {"thread_id": str(uuid4())}})
```

验证要分两件事：第一轮的 Store 检查说明偏好是否写入；第二轮在 trace 中检查系统提示词是否包含该文件与偏好，再观察回答是否遵循。提示词约定仍依赖模型执行，断言失败时检查 `read_file`/`edit_file` 调用。

> 重新运行整段代码会创建新的 `InMemoryStore`，只在当前进程保留。跨线程要复用 Store，跨进程/重启要持久化 Store。0.7.10 的记忆加载会复用 state 中已有的 `memory_contents`，**验证新对话加载必须用新 `thread_id`**，不要拿同一线程继续对话当证据。

## 5. 四种实用场景

1. **用户偏好**：`memory=["/memories/preferences.md"]`，先准备文件并约定更新路径；
2. **自我改进**：Agent 根据反馈更新 `/memories/AGENTS.md`，积累领域知识与沟通风格；
3. **知识库累积**：多次对话往 `/memories/project/tech-stack.md` 追加信息，后续对话基于完整知识回答；
4. **研究项目推进**：加载 `sources.md`、`notes.md`、`report.md`，每次对话结束更新进度。

## 6. 高级用法

### 6.1 记忆的六个维度

| 维度 | 核心问题 | 选项 |
|---|---|---|
| 持续时间 | 保留多久 | 短期 / 长期 |
| 信息类型 | 记什么 | 情景 / 程序性（Skills）/ 语义（事实） |
| 作用域 | 谁能看 | 用户 / Agent / 组织 |
| 更新策略 | 何时写 | 对话中（热路径）/ 对话间（后台整合） |
| 检索方式 | 如何读 | 启动加载（`memory=`）/ 按需（Skills） |
| 权限控制 | Agent 能写吗 | 读写 / 只读 |

### 6.2 组织级记忆

跨所有用户与 Agent 共享，通常设为**只读**以防注入：

```python
memory=["/memories/preferences.md", "/policies/compliance.md"],
routes={
    "/memories/": StoreBackend(namespace=user_namespace),
    "/policies/": StoreBackend(namespace=org_namespace),
}
```

由应用代码预填（部署环境用 SDK `store.put_item`），再用 Permissions 禁止 Agent 写入。

### 6.3 情景记忆

Checkpointer 天然保存每次对话的完整经历。要让过去对话可搜索，可以包装一个搜索工具：按用户查 threads → 取 history → 返回相关记录。对复杂多步任务的 Agent 尤其有用（如代码 Agent 回溯上次调试过程）。

### 6.4 后台记忆整合

| 方式 | 优点 | 缺点 |
|---|---|---|
| 热路径（对话中写） | 即时可用、透明 | 增加延迟，Agent 多任务 |
| 后台整合（对话间写） | 无感知延迟，可跨对话综合 | 下次才可用，需额外 Agent |

整合 Agent 用工具读取用户最近线程，提取事实、去重后合并入记忆；用 Cron 定时触发。注意 **Cron 间隔必须与回溯窗口匹配**（每 6 小时跑就回溯 6 小时）。`threads.search()` 不支持 `updated_after`，要按 `updated_at` 客户端筛选；`get_state()` 才是当前状态，`get_history()` 返回检查点列表。

### 6.5 并发写入

多个线程可并行写记忆，但同一文件可能 last-write-wins 冲突。更稳妥的做法是把「写入热路径」与「整理冷路径」分开：

- **按主题拆文件**，减少同时改同一文件的概率；
- **追加式日志 + 后台合并**：对话中写 `/memories/events/<date>-<thread>.md`，后台去重合并；
- **共享记忆只让后台写**：Agent/组织级尽量只读，普通对话只提交候选更新；
- **敏感记忆加审批**：组织策略、安全规则、长期偏好覆盖用 Permissions 或 HITL。

## 7. 从开发到生产

| 场景 | Store | 说明 |
|---|---|---|
| 本地开发 | `InMemoryStore` | 零配置，重启丢失 |
| 生产 | `PostgresStore` | 真正持久化；首次连接 `store.setup()` 建表 |
| LangSmith 部署 | 平台自动配置 | 省略 `store=` |

```python
from langgraph.store.postgres import PostgresStore
with PostgresStore.from_conn_string(os.environ["DATABASE_URL"]) as store:
    store.setup()
    agent = create_deep_agent(..., store=store, ...)
```

`with` 适合脚本；常驻服务应在启动生命周期初始化、关闭时统一释放。

## 8. 文件格式与外部写入

`StoreBackend` 的文件是 JSON（v2）：`content` 完整字符串 + `encoding` + `created_at`/`modified_at`。不要手写底层 JSON，外部预填一律用 `create_file_data()`。

**Store key 取决于是否经过路由**：

| 配置 | Agent 可见路径 | Store key |
|---|---|---|
| 直接 `StoreBackend` | `/skills/langgraph-docs/SKILL.md` | `/skills/langgraph-docs/SKILL.md` |
| 挂载 `routes={"/skills/": StoreBackend(...)}` | `/skills/langgraph-docs/SKILL.md` | `/langgraph-docs/SKILL.md` |

路由方式误写完整路径，返回时会再补一次前缀，暴露成 `/skills/skills/...`。不同路由用不同 namespace，避免相同相对 key 互相覆盖。

## 9. 最佳实践

1. **路径有描述性**：`/memories/AGENTS.md`、`/memories/preferences.md`、`/policies/compliance.md`；
2. **`memory=` 加载 + 提示词约定写入**：两项各有作用，一起用；严格限制可写路径要靠专用工具或 Backend 权限，提示词不提供保证；
3. **按主题拆文件**：减少并发冲突，也方便按需加载；
4. **多 Agent 隔离**：namespace 加入 `assistant_id`；
5. **选对 Store**：开发 InMemory、生产 Postgres、LangSmith 平台托管；
6. **用 LangSmith 审计写入**：每次写入都是 tool call；审计回答「发生了什么」，权限回答「是否允许」。

## 10. 本篇验收

- [ ] 能说清 `memory=` 是读取配置，缺失文件不会自动创建；
- [ ] 能区分 thread-scoped（Checkpointer）与 cross-thread（Store）；
- [ ] 知道 `thread_id` 隔离与 MemorySaver/PostgresSaver 的差异；
- [ ] 能解释 Trim/Delete/Summarize 三种策略；
- [ ] 会用 CompositeBackend 路由 `/memories/` 并写 namespace 兜底；
- [ ] 能按 Agent/用户/组织三种作用域配置隔离；
- [ ] 会验证写入（查 Store）与新线程加载（新 thread_id）；
- [ ] 知道外部预填的 key 要按路由相对路径；
- [ ] 理解热路径与后台整合的取舍及并发写入策略。

> **补记**：长期记忆的关键是「**写入约定与读取配置分开**」——`memory=` 只负责加载，写不写、写到哪由提示词与工具决定；验证也得分两步：先查 Store 确认写入，再用新 thread 确认加载。工程上最容易踩的两个坑是 CompositeBackend 的 Store key（路由相对路径）和并发写同一文件（用拆文件或后台整合把写序列化）。
