# 虚拟文件系统：上下文工程的核心

## 1. 为什么用文件系统管理上下文

传统 Agent 把所有信息塞进 prompt：文件内容、搜索结果、中间计算全挤在一条不断膨胀的对话历史里。Deep Agents 的解法是**给 Agent 一个文件系统**——这个思路符合人的工作方式：

- 不会把所有资料铺在桌面上，而是分门别类存放；
- 需要时再取出来，用搜索快速定位；
- 中间结果记在便签上。

Agent 也因此按需读取、结构化存储、搜索定位。

## 2. 七个内置文件工具

| 工具 | 用途 | 类比 |
|---|---|---|
| `ls` | 列出目录与元信息（大小、修改时间） | 打开文件夹看看 |
| `read_file` | 读内容，支持偏移量与条数；原生支持图片/视频/音频/PDF/PPT | 翻开资料阅读 |
| `write_file` | 创建文件，或**完整覆盖**已有文件 | 重写整份草稿 |
| `edit_file` | 精确字符串替换 | 用红笔改文档 |
| `delete` | 删除文件或目录 | 清理资料 |
| `glob` | 按模式找文件（如 `**/*.py`） | 按标签找 |
| `grep` | 按字面量搜内容，支持输出与计数 | 全文检索 |

<p>图 1：文件系统工具（早期六工具视角，当前已新增 delete）</p>

> **v0.7 提醒**：图片保留了早期「六大工具」视角。当前版本新增 `delete`，并且 `write_file` 会完整覆盖同路径文件；只改局部内容应使用 `edit_file`。

v0.7 还调整了读取与搜索边界：`read_file` 返回分页信息与下一段偏移量；`grep`、`glob` 可能返回有效但不完整的结果，用 `truncated=True` 明示截断；Agent 侧 `grep` 默认最多保留 1,000 个匹配。**调用成功只代表工具正常执行，不代表拿到全集**——后续应缩小目录或匹配条件继续搜索。

如果应用直接解析工具文本，要更新解析器：空的 `ls`/`glob` 现在返回 `No files found`；`read_file` 行号与正文之间用两个空格而非 Tab。更稳妥的是优先消费结构化 Backend 结果，把面向模型的文本当作展示协议。

工具定义 Agent **能做什么**，权限规则决定一次操作**是否可以做**：`write_file` 与 `edit_file` 默认都是普通操作，但可用 `FilesystemPermission` 对敏感路径拒绝，或执行前暂停等待审批（第 10 篇展开）。

### 2.1 read_file：不只是读文件

**分片读取**：大文件按偏移量与行数读取，避免一次塞满上下文：

```python
read_file("/workspace/report.md")                    # 默认最多前 100 行
read_file("/workspace/report.md", offset=100, limit=50)
```

**原生多模态**：直接返回多模态内容块，让 Agent「看到」图片、「听到」音频、「读懂」文档：

| 类型 | 支持格式 |
|---|---|
| 图片 | png、jpg、jpeg、gif、webp、heic、heif |
| 视频 | mp4、mpeg、mov、avi、flv、mpg、webm、wmv、3gpp |
| 音频 | wav、mp3、aiff、aac、ogg、flac |
| 文档 | pdf、ppt、pptx |

### 2.2 grep：三种输出模式

- `files_with_matches`：只返回匹配文件路径（快速定位）；
- `content`：返回匹配行与上下文（深入查看）；
- `count`：返回匹配数量（概览）。

```python
grep("TODO", glob="**/*.py", output_mode="files_with_matches")
grep("def create_agent", output_mode="content")
```

## 3. 上下文自动管理

虚拟文件系统的价值不只在「存文件」，更在它与上下文自动管理配合。

### 3.1 大结果自动卸载

工具调用的输入或输出超过 20,000 tokens 时（可配 `tool_token_limit_before_evict`），自动：

1. 把完整内容写入虚拟文件系统；
2. 对话历史里替换为**文件路径 + 前 10 行预览**；
3. Agent 需要时可按需读回。

```text
原始结果：[50000 tokens 的搜索结果]

自动卸载后：
"结果已保存到 /workspace/search_results_001.md，
 前 10 行预览：..."
```

完全自动，不需要 Agent 手动管理，但随时可用 `read_file`/`grep` 访问完整内容。

### 3.2 对话历史总结

上下文达到阈值时启动摘要。`create_deep_agent()` 在模型 profile 提供窗口大小时默认使用窗口的 85%；缺少信息时用固定 token 阈值，也可自行配置：

1. 把待总结的旧消息写入 Backend，供后续查阅；
2. 用 LLM 生成结构化摘要（意图、产出物、下一步），附历史保存路径；
3. 把**本次发给模型的内容**换成「摘要 + 近期消息」；正常摘要时 State 中的原始消息仍保留。

要区分「保存的消息历史」与「模型这次看到的内容」：摘要缩短输入，历史文件用于回查细节；能否读回取决于 Backend 是否成功保存、文件是否仍可用。

## 4. 可插拔的存储后端

「虚拟文件系统」是抽象概念，具体存哪里由 **Backend** 决定。

### 4.1 StateBackend（默认）：临时存储

```python
agent = create_deep_agent(model=model)   # 默认就是 StateBackend
```

文件存在 LangGraph 的 Agent State 中：同一线程内持久（多轮不丢）、对话结束即丢失（换 thread 就没了）、主 Agent 与子 Agent 共享。适合大多数场景，是 Agent 的「草稿纸」。

### 4.2 FilesystemBackend：本地磁盘

```python
from deepagents.backends import FilesystemBackend

agent = create_deep_agent(
    model=model,
    backend=FilesystemBackend(root_dir=".", virtual_mode=True)
)
```

直接读写本地文件。`root_dir` 是可访问根目录；`virtual_mode=True` 启用路径沙箱（阻止 `..`、`~` 与越界绝对路径），**强烈建议开启**——默认 `False` 时即使设了 `root_dir` 也没有越界保护。文件修改是永久、不可逆的。

> 安全提示：Agent 可读取 `root_dir` 下所有文件，包括 `.env`、密钥。Web 服务或 API 场景不要用此后端，应改用沙箱后端，并配合 HITL。

### 4.3 LocalShellBackend：本地 Shell

```python
from deepagents.backends import LocalShellBackend

agent = create_deep_agent(
    model=model,
    backend=LocalShellBackend(root_dir=".", virtual_mode=True, env={"PATH": "/usr/bin:/bin"})
)
```

在 Filesystem 基础上额外提供 `execute`：命令交给系统 shell 解释执行，**无任何沙箱隔离**；支持 `timeout`（默认 120 秒）、`max_output_bytes`（默认 100,000）、`env`；`root_dir` 只是工作目录，命令可访问系统任意路径。

> 极高风险：Agent 可执行任意 Shell（删文件、外传数据、耗资源）。**绝不要在生产或多用户系统使用。** 个人机临时使用至少：工作区隔离、`virtual_mode=True`、最小 `env/PATH`、不把密钥放进可访问目录、高风险操作加 HITL；处理不可信代码或对外服务直接换沙箱。

### 4.4 StoreBackend：跨会话持久化

```python
from langgraph.store.memory import InMemoryStore
from deepagents.backends import StoreBackend

agent = create_deep_agent(
    model=model,
    backend=StoreBackend(
        namespace=lambda rt: (rt.server_info.user.identity,),  # 按用户隔离
    ),
    store=InMemoryStore(),   # 开发用；部署到 LangSmith 可省略
)
```

文件存在 LangGraph Store 中：**跨线程持久**，不同对话访问同一份文件；`namespace` 控制隔离，按用户隔离可防数据混用；开发用 `InMemoryStore`，部署到 LangSmith 时平台自动配置。

> `namespace` 从 v0.5.0 起必填。`rt.server_info.user.identity` 在 LangSmith 能拿到，本地 `invoke()` 时 `rt.server_info` 是 `None`，直接访问会报错——本地先兜底 `("local-user",)`。

### 4.5 CompositeBackend：混合路由

```python
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend

agent = create_deep_agent(
    model=model,
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/memories/": StoreBackend(namespace=lambda rt: (rt.server_info.user.identity,)),
        }
    ),
    store=InMemoryStore()
)
```

不同路径走不同后端：写 `/workspace/plan.md` → State（临时）；写 `/memories/preferences.txt` → Store（持久、按用户隔离）；`ls`/`glob`/`grep` 自动聚合所有后端结果并保留路径前缀。既有「草稿纸」又有「记忆库」。

> **v0.7 兼容提醒**：`backend=` 必须直接传实例，`backend=lambda rt: ...` 工厂函数已移除；`StoreBackend(namespace=lambda rt: ...)` 仍支持，它在运行时计算命名空间，不负责创建后端。

### 4.6 沙箱后端

使用 Modal、Daytona、Runloop 等沙箱后端时，除文件工具外还会提供 `execute`，在隔离环境执行 Shell：

```python
agent = create_deep_agent(model=model, backend=sandbox)
# Agent 现在可以: execute("pip install pandas && python analyze.py")
```

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/deepagents_09-comparison-backends.png)

<p>图 3：五种后端对比</p>

| 场景 | 推荐后端 | 理由 |
|---|---|---|
| 学习实验 | StateBackend | 零配置、自动清理 |
| 本地编程助手 | FilesystemBackend | 直接操作项目文件 |
| 跨会话记忆 | CompositeBackend | 临时 + 持久混合 |
| 需要执行代码 | 沙箱后端 | 安全隔离 |
| 生产部署 | Store 或 Composite | 持久化 + 可伸缩 |

## 5. 权限与自定义后端

### 5.1 FilesystemPermission

```python
from deepagents import create_deep_agent, FilesystemPermission

agent = create_deep_agent(
    model=model,
    backend=...,
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/policies/**"],
            mode="deny",           # 禁止写入 /policies/ 下任何文件
        ),
    ],
)
```

规则在工具调用前按声明顺序求值，**first-match-wins**：第一个同时匹配 `operations` 与 `paths` 的规则决定结果；无规则匹配则默认允许。因此更具体的规则要放在更宽泛的规则之前。

| `mode` | 行为 | 适用 |
|---|---|---|
| `allow` | 允许继续 | 为特定路径设显式例外 |
| `deny` | 直接拒绝 | 任何情况下都不应访问的路径 |
| `interrupt` | 暂停等人工决策 | 可操作但必须先审批的敏感路径 |

`interrupt` 需要 Checkpointer，并用 `Command(resume=...)` 恢复（第 10 篇）。

### 5.2 自定义后端

内置后端不够时（接 S3、Postgres），实现 `BackendProtocol`：核心接口是 `ls`、`read`、`write`、`edit`、`grep`、`glob`；要暴露 v0.7 删除能力，还要实现 `delete()` 返回 `DeleteResult`，包装器也必须同步转发或拒绝删除。

### 5.3 PolicyWrapper 与删除边界

> **v0.7 不兼容变更**：默认工具配置下，支持删除的后端会向 Agent 提供 `delete`。在 `FilesystemPermission` 中删除属于 `write` 权限类别，因此**原有的允许写入规则也可能允许删除整个子目录**。

保护 `/workspace/policies` 时，旧示例用 `/workspace/policies/` 前缀能拦住对 `rules.txt` 的写入/编辑/删除，却漏掉两种删除请求：`/workspace/policies`（无末尾斜杠）与 `/workspace`（上级目录）。后端一旦递归删除，两者都会连带移除受保护内容。

正确做法按目录层级判断：写入、编辑时检查目标是受保护目录本身或其后代；删除时再加对祖先目录的检查。命中任一条件，在调用底层后端前拒绝整次操作。

```python
from pathlib import PurePosixPath

def policy_path(path: str) -> PurePosixPath:
    normalized = PurePosixPath("/" + path.lstrip("/"))
    if ".." in normalized.parts:
        raise ValueError("策略路径不能包含 '..'")
    return normalized

def denied_by_directory(path, protected_dirs, *, deleting=False):
    try:
        target = policy_path(path)
    except ValueError:
        return True
    return any(
        target.is_relative_to(directory)
        or (deleting and directory.is_relative_to(target))
        for directory in protected_dirs
    )
```

`is_relative_to()` 包含路径相等，因此 `/policies` 与 `/policies/rules.txt` 都受保护，`/policies-copy` 不会误拦；删除时反向检查，保护 `/workspace/policies` 时也拒绝删除 `/workspace`。

实现方式两种：继承 `FilesystemBackend` 重写 `write`/`edit`/`delete`，或用 `PolicyWrapper` 包装任意 `BackendProtocol`。两者都在调用底层前判断，返回带 `error` 的结果。

若只想关闭内置删除工具，可在 `FilesystemMiddleware(tools=...)` 的工具列表中省略 `delete` 并保留 `read_file`；但这不限制自定义工具或 Shell 中的删除。保留内置 `delete` 时，用权限规则对相应路径设置拒绝或审批。
