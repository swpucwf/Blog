# 文件系统权限：声明式读写边界

## 1. 权限控制的对象

`create_deep_agent()` 通过 `FilesystemMiddleware` 注入内置文件工具。传入 `permissions=` 后，中间件在调用 Backend **之前**检查每次文件操作：

| 操作组 | 覆盖工具 | 典型副作用 |
|---|---|---|
| `read` | `ls`、`read_file`、`glob`、`grep` | 暴露文件名、目录结构或内容 |
| `write` | `write_file`、`edit_file`、`delete` | 新建、修改或删除文件 |

v0.7 的 `write_file` 可完整覆盖已有文件，所以 `write` 组同时保护「创建」与「整文件覆盖」。删除目录采用全有或全无：只要目录内包含不允许删除的后代，整次删除就失败，不能留下部分结果。

> **v0.7 提醒**：同名 Middleware 可原位置换。自定义 `FilesystemMiddleware` 会**替换**默认实例，而不是只覆盖几个字段；不要假定顶层 `permissions=` 会与新实例自动合并。升级后至少用真实的允许、拒绝、覆盖与删除调用做回归测试。

最小只读配置——拒绝所有写：

```python
from deepagents import FilesystemPermission, create_deep_agent

agent = create_deep_agent(
    model=model,
    backend=backend,
    permissions=[FilesystemPermission(operations=["write"], paths=["/**"], mode="deny")],
)
```

读取不受影响，Agent 仍可用 `ls`/`read_file`/`glob`/`grep`，但不能写、编辑或删除。

### 1.1 权限不是通用沙箱

| 入口 | 受 `FilesystemPermission` 控制？ | 应使用 |
|---|---|---|
| 内置文件工具 | 是 | `permissions=` |
| 自定义 LangChain 工具 | 否 | 工具自身校验、`interrupt_on`、Middleware |
| MCP 文件工具 | 否 | MCP Server 权限、工具审批、进程隔离 |
| 沙箱或 `LocalShellBackend` 的 `execute` | 否 | 沙箱隔离、命令策略、网络与凭证控制 |
| Backend 业务级校验 | 不足以表达 | Policy Hook 或 `PolicyWrapper` |

因此「禁止 `write_file` 写入 `/secrets/`」不等于「Agent 无法通过其他工具接触 `/secrets/`」。如果还能调用自定义上传工具、MCP 文件工具或 Shell，必须分别约束这些入口。

> 在锁定的 `deepagents==0.7.15` 中，把权限规则直接用于支持 `execute` 的 Backend 通常会在构造时抛 `NotImplementedError`；`CompositeBackend` 中规则路径全部以已配置路由前缀开头时例外，但仍不保护 `execute`。

## 2. 一条规则的三个字段

| 字段 | 取值 | 作用 |
|---|---|---|
| `operations` | `"read"`、`"write"` | 拦截哪类操作 |
| `paths` | Glob 路径列表 | 覆盖哪些虚拟路径 |
| `mode` | `allow` / `deny` / `interrupt` | 放行、拒绝、暂停等审批 |

路径支持 `**` 递归与 `{a,b}` 交替：

```python
FilesystemPermission(
    operations=["read", "write"],
    paths=["/workspace/**", "/shared/{docs,templates}/**"],
    mode="allow",
)
```

权限路径匹配的是 Agent 看到的**虚拟路径**，不一定等于宿主机真实路径。用 `FilesystemBackend(root_dir="/srv/project")` 时，Agent 访问 `/src/app.py` 由 Backend 映射到根目录；规则仍应围绕 Agent 文件空间设计。

## 3. 求值：first-match-wins

1. 从列表第一条开始；
2. 同时匹配 `operations` 与 `paths` 的第一条立即生效；
3. 后续规则不再执行；
4. **没有任何规则匹配时，默认允许**。

最后一点最容易误配：单独写 `allow /workspace/**` **不会**形成工作区白名单，因为工作区外路径没命中规则，仍按默认放行。真正的白名单要在末尾追加全局拒绝。

### 3.1 正确的工作区白名单

```python
workspace_only = [
    FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
    FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
]
```

第一条放行工作区，第二条拒绝全部剩余。顺序不能交换，否则 `/**` 先匹配，工作区放行永远不会执行。

### 3.2 先保护敏感文件，再放行目录

```python
protected_workspace = [
    FilesystemPermission(
        operations=["read", "write"],
        paths=["/workspace/.env", "/workspace/examples/**"],
        mode="deny",
    ),
    FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
    FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
]
```

稳定顺序：**最具体的敏感路径 → 业务允许路径 → 最宽泛兜底**。

## 4. 四种常见策略

**整机只读**（审计、代码阅读、知识检索）：

```python
read_only = [FilesystemPermission(operations=["write"], paths=["/**"], mode="deny")]
```

**只能访问工作区**（本地编程助手、单项目 Agent）：白名单 + 末尾兜底拒绝，同时防误写与越界读。

**共享知识只读、用户记忆可写**：

```python
agent = create_deep_agent(
    model=model,
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/memories/": StoreBackend(namespace=lambda rt: (rt.server_info.user.identity,)),
            "/policies/": StoreBackend(namespace=lambda rt: (rt.context.org_id,)),
        },
    ),
    permissions=[
        FilesystemPermission(operations=["write"], paths=["/policies/**"], mode="deny"),
    ],
)
```

未限制 `/memories/**`，用户记忆默认可读写；`/policies/**` 只能由应用代码或 Store API 更新。

**拒绝所有文件访问**：同时拒绝读写。这不会从工具列表移除文件工具，而是让命中调用返回权限错误；想减少无效工具选择，还要审视工具与 Middleware 组合。

## 5. `interrupt`：敏感写入交给人审批

`mode="interrupt"` 不立即允许或拒绝，而是触发与工具审批相同的 HITL 中断，适合「通常可以写，但每次都要确认」的路径。

```python
agent = create_deep_agent(
    model=model,
    permissions=[
        FilesystemPermission(operations=["write"], paths=["/secrets/**"], mode="interrupt"),
    ],
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "permission-review-1"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "把临时凭证写入 /secrets/token.txt"}]},
    config=config, version="v2",
)

if result.interrupts:
    request = result.interrupts[0].value["action_requests"][0]
    print(request["name"], request["args"])
    result = agent.invoke(
        Command(resume={"decisions": [{"type": "approve"}]}),
        config=config, version="v2",
    )
```

审查方可返回 `approve`、`edit`、`reject`。权限中断会与 `interrupt_on=` 的自定义工具审批合并，同一套恢复协议处理两类动作。

**路径要有明确锚点**：优先 `/secrets/**` 或 `/projects/*/secrets/**`。`ls`、`glob`、`grep` 与目录 `delete` 等批量操作需要判断整个子树是否可能碰到受保护路径；完全不锚定的 `/**/secrets` 会导致保守的过度中断。

**删除目录全有或全无**：Deep Agents 会检查目标目录及所有后代的 `write` 权限，只要一项被拒绝，整个删除失败，不会「删一半、留下受保护文件」。

## 6. 子 Agent：默认继承，显式配置整体替换

子 Agent 默认继承主 Agent 权限；一旦在 spec 中提供 `permissions`，规则会**完整替换**父规则，而不是追加或取交集。

```python
agent = create_deep_agent(
    model=model,
    backend=backend,
    permissions=[
        FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
        FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
    ],
    subagents=[{
        "name": "auditor",
        "description": "只读代码审计员",
        "system_prompt": "审查代码并报告问题，不要修改文件。",
        "permissions": [
            FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),
            FilesystemPermission(operations=["read"], paths=["/workspace/**"], mode="allow"),
            FilesystemPermission(operations=["read"], paths=["/**"], mode="deny"),
        ],
    }],
)
```

因为是整体替换，子 Agent 的规则必须**独立闭合**：不要只写「额外拒绝写入」，却忘了把工作区读取边界带过来。

## 7. CompositeBackend 与沙箱的边界

当 `CompositeBackend` 的默认 Backend 是沙箱时，权限路径**必须位于已知路由前缀下**：

```python
composite = CompositeBackend(default=sandbox, routes={"/memories/": memories_backend})
agent = create_deep_agent(
    model=model,
    backend=composite,
    permissions=[FilesystemPermission(operations=["write"], paths=["/memories/**"], mode="deny")],
)
```

改成 `/workspace/**` 或 `/**` 会覆盖沙箱默认路由，`create_deep_agent()` 抛 `NotImplementedError`——沙箱提供任意命令执行，单靠文件工具路径规则无法建立真实边界。

**`execute` 不受文件权限约束**：即使内置 `write_file` 被拒绝，也不能推导 Shell 无法写同一路径。两类控制解决不同问题：

- `FilesystemPermission`：约束内置文件工具的路径访问；
- 沙箱策略：隔离宿主机，限制网络、凭证、进程与命令能力。

## 8. 什么时候升级到自定义策略

声明式权限回答「某类操作能否访问某个路径」。判断条件超出这两个维度时，用 Policy Hook、`PolicyWrapper` 或自定义 Middleware。

### 8.1 Policy Hook

它不是 `create_deep_agent(policy_hook=...)` 参数，而是一种 **Backend 扩展模式**：在真正存储 Backend 之前执行策略判断，再决定转发还是返回错误。

```text
内置文件工具
  -> FilesystemPermission：先检查 operation 与 path
  -> Policy Hook（GuardedBackend / PolicyWrapper）：再执行动态业务策略
  -> 实际存储 Backend
```

两者不是替代关系：`FilesystemPermission` 适合稳定、可枚举、可审查的路径基线；Policy Hook 适合频率、内容、调用身份、租户状态或审计等动态条件。没有经过内置文件工具的自定义工具、MCP 工具和 `execute` 仍需单独控制。

### 8.2 两种实现

| 方式 | 适用 | 代价 |
|---|---|---|
| 继承具体 Backend（`GuardedBackend`） | 只用一种 Backend，想复用实现 | 策略与 Backend 类型绑定 |
| 包装 `BackendProtocol`（`PolicyWrapper`） | 同一策略复用于 State/Store/Filesystem | 必须完整转发未拦截方法 |

`GuardedBackend` 继承 `FilesystemBackend`，命中策略返回带 `error` 的 `WriteResult`/`EditResult`，未命中才调用父类。它主要用于展示扩展点；单纯静态路径拒绝优先写 `FilesystemPermission`，更容易审查顺序。

`PolicyWrapper` 自己不存文件，持有 `inner` Backend，实现同一套 `BackendProtocol`：读类操作直接转发，写/编辑先过策略。四个要点：

1. `__init__` 统一给受保护目录补末尾 `/`，避免 `/policies-old` 误判为 `/policies` 子路径；
2. `_deny()` 是集中判断点，可加入用户身份、配额、内容扫描或外部审批状态；
3. `ls/read/grep/glob` 可只转发，说明包装器只介入需要管控的操作；
4. 拒绝时返回对应结果类型的 `error`，允许时原样转发内部 Backend 的结果。

> **CompositeBackend 路由内的路径语义**：把包装器放在 `routes={"/skills/": PolicyWrapper(...)}` 内，CompositeBackend 会先剥离 `/skills/`，包装器看到的是 `/test-skill/SKILL.md`，此时 `deny_prefixes=["/skills/"]` 不会命中。若只是整条路由只读，优先在 Agent 层用 `FilesystemPermission(paths=["/skills/**"], operations=["write"], mode="deny")`；确实要内部动态策略时，可用 `deny_prefixes=["/"]` 覆盖该路由全部写入。

示例尚未实现 `delete()`；若 Backend 与工具集支持删除，必须按同一模式补上 `delete()` 与 `DeleteResult`，否则删除会绕过策略。

| 需求 | 推荐机制 |
|---|---|
| 拒绝写 `/policies/**` | `FilesystemPermission` |
| 写 `/releases/**` 前确认 | `FilesystemPermission(mode="interrupt")` |
| 每分钟最多写 20 次 | Policy Hook / Middleware |
| 按内容做敏感信息检查 | `PolicyWrapper` / Middleware |
| 记录业务审计字段 | `PolicyWrapper` |
| 控制自定义/MCP 工具 | 工具自身策略 + `interrupt_on` |
| 控制 Shell 与网络 | 沙箱与执行策略 |

稳妥的分层：**`permissions` 表达路径基线 → `interrupt` 把少量敏感动作交给人 → Policy Hook 处理动态判断 → 所有绕过内置工具的入口单独控制。**

## 9. 上线前验证

| 测试 | 要证明的保证 |
|---|---|
| 允许路径读写 | 正常业务不被误拦 |
| 敏感路径读取 | `read` 规则没遗漏 |
| 敏感路径写/编辑/删除 | 三个工具都映射到 `write` |
| 已存在文件的 `write_file` | 完整覆盖仍受 `write` 规则保护 |
| 工作区外随机路径 | 末尾兜底真实生效 |
| 规则顺序交换回归 | 特定拒绝不被宽泛允许遮蔽 |
| 含受保护后代的目录删除 | 不产生部分结果 |
| 大目录 `grep`/`glob` | 权限不泄漏路径，调用方处理 `truncated=True` |
| 子 Agent 同路径访问 | 继承/替换符合设计 |
| `interrupt` 的批准/编辑/拒绝 | 暂停与恢复同 thread |
| Policy Hook 两分支 | 动态条件不误拦，也不能被写/编辑/删除旁路 |
| 自定义工具/MCP/`execute` | 每个旁路都有独立控制 |

尤其要加一个「没有显式规则的陌生路径」测试——默认允许的语义最容易暴露伪白名单。

## 10. 与前文的组合

| 场景 | 组合方式 |
|---|---|
| 虚拟文件系统 | Backend 决定存哪里，权限决定内置工具能访问哪里 |
| 中间件 | `FilesystemMiddleware` 在 Backend 调用前执行规则 |
| 子 Agent | 默认继承；专用 Agent 可整体替换为更小权限集 |
| Skills | 共享目录可读但禁止 Agent 修改 |
| 长期记忆 | 用户记忆可写，组织策略与合规文件只读 |
| HITL | 敏感写入用 `interrupt`，复用同一审批与恢复协议 |
| 沙箱 | 权限管文件工具，沙箱管 Shell 与宿主隔离 |

先建立一组权限基线，再按 Agent 职责、存储路由与执行入口逐步缩小边界；不同职责的 Agent 不必共用同一份全局规则。

## 11. 本篇验收

- [ ] 理解 first-match-wins 与「无匹配默认允许」；
- [ ] 会写末尾兜底拒绝，避免伪白名单；
- [ ] 掌握只读、工作区、共享只读/个人可写、全拒绝四种策略；
- [ ] 会用 `interrupt` + checkpointer + 同 thread 恢复；
- [ ] 知道子 Agent 显式 `permissions` 是整体替换；
- [ ] 理解 CompositeBackend + 沙箱只能保护已知路由，`execute` 不受限；
- [ ] 能区分 Policy Hook 与声明式权限的适用边界；
- [ ] 知道删除目录全有或全无，包装器必须实现 `delete`；
- [ ] 能按验证清单做上线前回归。

> **补记**：文件权限的本质是「**路径基线 + 兜底规则 + 旁路清单**」。最容易犯的两个错：只写 allow 却没有末尾 deny（伪白名单），以及以为 `permissions` 能管住自定义工具、MCP 与 Shell（实际只覆盖内置文件工具）。把旁路逐项列出来单独控制，才是完整的读写边界。
