# 范式框架化与工具系统

上一篇把接口定好了：一个 `Agent` 基类、一个 `Message`、一个 `Config`、一个多 provider 的 LLM 客户端。接下来往里填内容——四种范式改写为框架组件，以及支撑它们的工具系统。改造围绕三点：提示词从「针对某个任务」转向通用设计，接口与格式标准化，以及通过参数把提示词和行为开放给使用者配置。

## 1. SimpleAgent：对话是最小的范式

四种范式里最简单的不是 ReAct，而是「直接对话」。`SimpleAgent` 承担这个角色：它把消息拼成 OpenAI 格式、调用模型、记录历史，工具调用是可选项而非必需项。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-simple-agent-workflow.png" width="90%" alt="SimpleAgent 的运行工作流" />

`run` 的前半段几乎就是消息装配：

```python
def run(self, input_text: str, max_tool_iterations: int = 3, **kwargs) -> str:
    messages = [{"role": "system", "content": self._get_enhanced_system_prompt()}]
    for msg in self._history:                       # 历史按序回灌
        messages.append({"role": msg.role, "content": msg.content})
    messages.append({"role": "user", "content": input_text})

    if not self.enable_tool_calling:
        response = self.llm.invoke(messages, **kwargs)
        self.add_message(Message(input_text, "user"))
        self.add_message(Message(response, "assistant"))
        return response
    return self._run_with_tools(messages, input_text, max_tool_iterations, **kwargs)
```

关键在于系统提示词是**动态拼装**的：基础人设之外，把注册表里的工具描述和调用格式一并注入。

```python
def _get_enhanced_system_prompt(self) -> str:
    base_prompt = self.system_prompt or "你是一个有用的AI助手。"
    if not self.enable_tool_calling or not self.tool_registry:
        return base_prompt
    tools_description = self.tool_registry.get_tools_description()
    if not tools_description or tools_description == "暂无可用工具":
        return base_prompt
    return base_prompt + (
        "\n\n## 可用工具\n你可以使用以下工具来帮助回答问题:\n" + tools_description +
        "\n\n## 工具调用格式\n当需要使用工具时，请使用以下格式:\n"
        "`[TOOL_CALL:{tool_name}:{parameters}]`\n"
        "例如:`[TOOL_CALL:search:Python编程]`\n"
        "工具调用结果会自动插入到对话中，然后你可以基于结果继续回答。"
    )
```

这种「在提示词里约定标记、由代码解析标记」的做法，是 ReAct 之外另一条轻量路线：不需要模型原生支持函数调用，只需要它能照着格式输出。解析出的调用被逐个执行，结果以一条 `user` 消息插回对话，再让模型接着回答：

```python
def _run_with_tools(self, messages, input_text, max_tool_iterations, **kwargs) -> str:
    final_response = ""
    for _ in range(max_tool_iterations):
        response = self.llm.invoke(messages, **kwargs)
        tool_calls = self._parse_tool_calls(response)
        if not tool_calls:
            final_response = response          # 没有调用就是最终回答
            break
        clean_response = response
        tool_results = []
        for call in tool_calls:
            tool_results.append(self._execute_tool_call(call["tool_name"], call["parameters"]))
            clean_response = clean_response.replace(call["original"], "")   # 标记从正文里剔掉
        messages.append({"role": "assistant", "content": clean_response})
        messages.append({"role": "user",
                         "content": f"工具执行结果:\n{chr(10).join(tool_results)}\n\n请基于这些结果给出完整的回答。"})
    if not final_response:
        final_response = self.llm.invoke(messages, **kwargs)   # 步数用完再要一次收尾
    self.add_message(Message(input_text, "user"))
    self.add_message(Message(final_response, "assistant"))
    return final_response
```

两个细节值得记住：调用标记必须从正文里删掉，否则它会作为模型「说过的话」残留在历史里，下一轮容易被模仿成格式污染；步数用尽后要再问一次，而不是直接返回空——让模型在已有信息上收个尾，比抛出「超步数」更有用。

## 2. ReActAgent：模板升级，循环不变

ReAct 的核心逻辑在第四章已经跑通，框架化改的是提示词结构与工具访问方式。模板从「一段话」变成带小标题的四块，并明确「每次只能执行一个步骤」：

```text
你是一个具备推理和行动能力的AI助手。你可以通过思考分析问题，然后调用合适的工具来获取信息，最终给出准确的答案。

## 可用工具
{tools}

## 工作流程
请严格按照以下格式进行回应，每次只能执行一个步骤:
Thought: 分析当前问题，思考需要什么信息或采取什么行动。
Action: 选择一个行动，格式必须是以下之一:
- `{tool_name}[{tool_input}]` - 调用指定工具
- `Finish[最终答案]` - 当你有足够信息给出最终答案时

## 重要提醒
1. 每次回应必须包含Thought和Action两部分
2. 工具调用的格式必须严格遵循:工具名[参数]
3. 只有当你确信有足够信息回答问题时，才使用Finish
4. 如果工具返回的信息不够，继续使用其他工具或相同工具的不同参数

## 当前任务
**Question:** {question}

## 执行历史
{history}
```

分节写法比长段落稳，因为模型对「## 工作流程」这类结构的遵循度明显高于夹在段落里的要求。而「每次只能执行一个步骤」是一条反例约束——不加这句，模型倾向于一次吐出多步 Thought/Action，导致解析只能取到第一个，后面的动作被静默丢弃。

循环本身反而是最不需要创新的部分：

```python
def run(self, input_text: str, **kwargs) -> str:
    self.current_history, current_step = [], 0
    while current_step < self.max_steps:
        current_step += 1
        prompt = self.prompt_template.format(
            tools=self.tool_registry.get_tools_description(),
            question=input_text,
            history="\n".join(self.current_history),
        )
        response_text = self.llm.invoke([{"role": "user", "content": prompt}], **kwargs)
        thought, action = self._parse_output(response_text)

        if action and action.startswith("Finish"):
            final_answer = self._parse_action_input(action)
            self.add_message(Message(input_text, "user"))
            self.add_message(Message(final_answer, "assistant"))
            return final_answer

        if action:
            tool_name, tool_input = self._parse_action(action)
            observation = self.tool_registry.execute_tool(tool_name, tool_input)
            self.current_history.append(f"Action: {action}")
            self.current_history.append(f"Observation: {observation}")

    return "抱歉，我无法在限定步数内完成这个任务。"
```

与手写版的差别只有两处：工具从「持有字典」变成「持有注册表」，`execute_tool` 顺手把参数校验、异常兜底也做了；`custom_prompt` 参数让整个模板可替换，做垂直领域微调时不用改源码。循环内 `current_history` 与基类的 `_history` 分开是有意的——前者是本轮的推理轨迹（每轮重置），后者是跨轮对话记录。

## 3. 后两种范式：只换提示词

到 Reflection 与 Plan-and-Solve，代码结构已经没什么可改的，剩下的工作是把第四章那些「紧贴代码生成任务」的提示词改成通用版本，并允许整组替换：

```python
DEFAULT_PROMPTS = {
    "initial":   "请根据以下要求完成任务: {task} ...",
    "reflect":   "请审视以下输出，指出问题与改进方向: {task}\n{output} ...",
    "refine":    "根据反馈改进输出: {task}\n{output}\n{feedback} ...",
}

agent = ReflectionAgent(..., custom_prompts=DEFAULT_PROMPTS)
```

Plan-and-Solve 同理，把它拆成 `{"planner": ..., "executor": ...}` 两组模板。改造成果可以压成一张对应关系：手写版里「提示词 = 类的一部分」，框架版里「提示词 = 可注入的配置」，类只负责流程。这样一来，同一个 `PlanAndSolveAgent` 换成数学专用提示词就是数学助手，换成报告专用提示词就是写作助手，不必复制整个类。

## 4. FunctionCallAgent：交给原生函数调用

前面几种都靠提示词约定格式，再由正则解析。这条路对模型的指令遵循能力要求高，遇到不支持或遵循不佳的模型就脆。`FunctionCallAgent` 换了一条路——用 OpenAI 原生 function calling：把工具描述转成 JSON Schema 随请求一起发送，模型直接返回结构化的调用对象。

```python
def _invoke_with_tools(self, messages, tools, tool_choice, **kwargs):
    client = getattr(self.llm, "_client", None)
    if client is None:
        raise RuntimeError("HelloAgentsLLM 未正确初始化客户端，无法执行函数调用。")
    client_kwargs = dict(kwargs)
    client_kwargs.setdefault("temperature", self.llm.temperature)
    return client.chat.completions.create(
        model=self.llm.model, messages=messages, tools=tools,
        tool_choice=tool_choice, **client_kwargs,
    )
```

它多做四件事：`_build_tool_schemas` 从工具的 `description` 生成 schema，`_extract_message_content` 从响应里取文本，`_parse_function_call_arguments` 解析 JSON 参数，`_convert_parameter_types` 做类型转换。相比 prompt 约束，它的鲁棒性来自协议本身：参数是 JSON、调用是结构化对象，不存在「正则没匹配上」这类失败模式。

两条路线各有代价：提示词路线不绑定供应商，能跑在任何模型上；原生路线更稳，但要求服务端支持 function calling。框架里并存，按模型能力选。

## 5. 工具基类与注册表

工具能不能被模型「理解」，取决于它的自描述程度。基类只要求两件事——怎么执行、需要什么参数：

```python
class Tool(ABC):
    def __init__(self, name: str, description: str):
        self.name, self.description = name, description

    @abstractmethod
    def run(self, parameters: Dict[str, Any]) -> str: ...

    @abstractmethod
    def get_parameters(self) -> List[ToolParameter]: ...

class ToolParameter(BaseModel):
    name: str
    type: str
    description: str
    required: bool = True
    default: Any = None
```

`get_parameters` 是内省接口：它既能让框架在调用前校验参数、补默认值，也能自动生成文档与 schema。有了它，`to_openai_schema()` 才有依据把工具翻译成 function calling 要的结构。

注册表负责管理，并支持两种登记方式——`register_tool` 收完整的 `Tool` 对象（参数定义齐全，适合复杂工具），`register_function` 直接收一个「字符串进、字符串出」的函数（适合把已有函数快速接入）：

```python
class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, Tool] = {}
        self._functions: dict[str, dict[str, Any]] = {}

    def register_tool(self, tool: Tool):
        if tool.name in self._tools:
            print(f"⚠️ 警告:工具 '{tool.name}' 已存在，将被覆盖。")
        self._tools[tool.name] = tool

    def register_function(self, name: str, description: str, func: Callable[[str], str]):
        self._functions[name] = {"description": description, "func": func}

    def get_tools_description(self) -> str:
        descriptions = [f"- {t.name}: {t.description}" for t in self._tools.values()]
        descriptions += [f"- {n}: {i['description']}" for n, i in self._functions.items()]
        return "\n".join(descriptions) if descriptions else "暂无可用工具"
```

`get_tools_description()` 是这套设计的中枢：它的输出被直接拼进提示词，等于把工具箱翻译成模型能读的说明书。工具描述写得含糊，模型就在这一步选错工具——这和第四章的结论一致，只是现在只需在注册时写一次。

## 6. 自定义工具：安全求值

最典型的小工具是计算器。直接用 `eval` 显然不行，`ast` 解析后只放行白名单节点是常见做法：

```python
operators = {ast.Add: operator.add, ast.Sub: operator.sub,
             ast.Mult: operator.mul, ast.Div: operator.truediv}
functions = {"sqrt": math.sqrt, "pi": math.pi}

def my_calculate(expression: str) -> str:
    if not expression.strip():
        return "计算表达式不能为空"
    try:
        node = ast.parse(expression, mode="eval")
        return str(_eval_node(node.body, operators, functions))
    except Exception:
        return "计算失败，请检查表达式格式"          # 失败也返回字符串，不抛异常

registry.register_function("my_calculator",
    "一个数学计算工具，支持加减乘除与 sqrt、pi", my_calculate)
```

三个约定延续了第四章的思路：白名单求值避免代码注入；出错返回字符串而非抛异常，错误信息会作为观察回灌给模型；描述里写清支持范围，模型才不会输入 `integrate(x^2)` 这类它做不到的表达式。

## 7. 多源搜索：降级链

一个搜索工具背后接两个 API，价值不在「多」，而在于可用性。`SearchTool` 的混合模式按优先级尝试，失败则降级：

```python
def _search_hybrid(self, query: str) -> str:
    if "tavily" in self.available_backends:
        try:
            return self._search_tavily(query)
        except Exception as e:
            print(f"⚠️ Tavily搜索失败: {e}")
            if "serpapi" in self.available_backends:
                return self._search_serpapi(query)
    elif "serpapi" in self.available_backends:
        try:
            return self._search_serpapi(query)
        except Exception as e:
            print(f"⚠️ SerpApi搜索失败: {e}")
    return "❌ 没有可用的搜索源，请配置TAVILY_API_KEY或SERPAPI_API_KEY环境变量"
```

后端可用性在建构造时就探明（有 key 且有依赖），不是每次调用才试。更关键的是**结果统一格式化**：Tavily 返回 `answer` 加 `results`，SerpApi 返回 `answer_box` 或 `organic_results`，两套结构在工具内部被压成同一种文本——优先给直接答案，其次给前三条摘要。对上层智能体而言，换后端是不可见的，上下文格式始终一致。

## 8. 编排与并发：工具链、异步执行

单次调用之外，工具的第二种用法是编排。`ToolChain` 用「输入模板 + 输出键」把多个工具串成流水线：每一步的模板从上一步的 `output_key` 取值，缺变量就整链中止。

```python
chain = ToolChain("research_and_calculate", "搜索信息并进行相关计算")
chain.add_step("search", "{input}", output_key="search_result")
chain.add_step("my_calculator", "根据以下信息计算相关数值:{search_result}",
               output_key="calculation_result")
```

这种声明的链路适合**流程稳定**的场景（搜索→抽取→计算→总结），比让模型每步自己决定更省 Token，也更可预测。代价是失去动态调整能力——所以它和 ReAct 是互补关系，而非替代。

耗时工具则需要并发。`AsyncToolExecutor` 用线程池把同步工具包成可等待对象，再 `gather` 一起等：

```python
async def execute_tool_async(self, tool_name: str, input_data: str) -> str:
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(
        self.executor, lambda: self.registry.execute_tool(tool_name, input_data))

async def execute_tools_parallel(self, tasks: List[Dict[str, str]]) -> List[str]:
    return await asyncio.gather(*[self.execute_tool_async(t["tool_name"], t["input_data"])
                                  for t in tasks])
```

四个搜索并行走，总耗时接近最慢的那个而不是四者之和。前提是这些调用彼此独立——有数据依赖的工具必须留在链里串行。

## 9. 工具系统的四条原则

写到这里，工具系统的设计约束可以归纳为四条：

- **单一职责**：一个工具只做一件事，`search` 不要顺手做摘要，`calculator` 不要顺手做单位换算。职责混杂时描述会变长，模型选择准确率随之下降。
- **接口统一**：一律 `run(parameters) -> str`。返回值统一为字符串不是偷懒，而是因为它的唯一消费者是上下文——结构化数据到上下文里终归要序列化成文本，不如在工具内就压好。
- **校验与兜底**：参数在调用前校验类型与必填项，异常在工具内捕获并转成可读错误。工具失败是常态，把失败变成模型能读懂的观察，才有机会自我修正。
- **资源可控**：外部连接复用而非每次重建，长耗时任务走异步，注册表对重名工具给出明确警告而不是静默覆盖。

框架到这里已经有了骨架和工具，但智能体真正难的部分才刚开始：上下文一长就失控，知识不在参数里，跨会话记不住事。下一篇从记忆系统切入——[8-1-记忆系统](/source/agent/从零构建智能体/8-1-记忆系统)。
