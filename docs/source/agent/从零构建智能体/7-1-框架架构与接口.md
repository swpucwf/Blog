# 框架架构与接口

前四篇的范式都是手写出来的：每个类自带提示词模板、循环逻辑、输出解析、工具字典。范式一多，重复就冒出来——工具管理、历史记录、模型调用散在各处，改一处要动几个文件。把公共部分抽出来，就是框架要做的事。这一篇看 HelloAgents 的分层方式与三个核心接口：模型客户端、消息、配置、智能体基类。

## 1. 为什么自己搭一层

现成框架不少，但用起来常卡在四个地方：

- **过度抽象的复杂性**：为追求通用性引入大量抽象层与配置项，完成一件小事要先理解十几个概念。
- **快速迭代的不稳定**：商业框架为抢市场，接口变更频繁，升级一次可能整段代码跑不通。
- **黑盒化的实现**：核心逻辑封装太严，遇到问题只能等文档或社区，排查链路长。
- **依赖负担**：成熟框架拖着大量依赖包，与既有项目共存时容易冲突。

自建的价值则在另一侧：亲手实现每个组件，才真正看清思考过程与工具调用是怎么转起来的；每一行都在自己手里，可以按场景精确调优；模块化、接口抽象、错误处理这些工程技能，也只有写框架时才被迫练一遍。加上垂直领域需要的定制提示词、特殊工具集成、性能与资源的精细控制，通用框架的「一刀切」很难满足。

## 2. 四条设计理念

- **轻量与可读的平衡**：核心代码按章节拆分，只依赖 OpenAI 官方 SDK 与少量基础库。出问题时能直接翻框架源码，不必在依赖树里找答案。
- **站在标准 API 上**：OpenAI 的接口已是事实标准，主流服务商都在兼容它。在这套标准之上构建，而不是另造一套抽象，学会一种用法就能迁移到别处。
- **渐进式路径**：每一章的功能都打包成可 `pip install` 的版本，边写边有可运行的产物，不产生概念跳跃。
- **万物皆为工具**：除 Agent 类本身，其他模块——记忆、RAG、MCP、强化学习——全部收敛成 Tool。这砍掉了大量需要单独学习的抽象层，回到「智能体调用工具」这一条主线。

## 3. 目录即架构

框架采用三层结构，原则是分层解耦、职责单一、接口统一：

```text
hello_agents/
├── core/                  # 核心框架层
│   ├── agent.py           # Agent 基类
│   ├── llm.py             # HelloAgentsLLM 统一模型接口
│   ├── message.py         # 消息系统
│   ├── config.py          # 配置管理
│   └── exceptions.py      # 异常体系
├── agents/                # Agent 实现层
│   ├── simple_agent.py
│   ├── react_agent.py
│   ├── reflection_agent.py
│   └── plan_solve_agent.py
└── tools/                 # 工具系统层
    ├── base.py            # 工具基类
    ├── registry.py        # 工具注册表
    ├── chain.py           # 工具链
    ├── async_executor.py  # 异步执行器
    └── builtin/           # 内置工具（计算、搜索）
```

`core` 只定义契约，`agents` 与 `tools` 依赖契约而不互相依赖。这一条约束让后面每加一种范式或工具，都不需要改核心层。

## 4. 模型层：provider 是配置，不是子类

用 `api_key` 与 `base_url` 两个参数，已经能连上任何兼容 OpenAI 接口的服务。真正麻烦的是各家在环境变量命名、默认地址、推荐模型上的差异——每换一家都要翻文档改代码，通用性就打了折扣。`provider` 参数正是为此引入：把差异收进客户端内部。

扩展新服务商不必改库源码，继承并重写 `__init__` 即可，只拦截自己关心的那个值，其余原样交还父类：

```python
class MyLLM(HelloAgentsLLM):
    def __init__(self, model=None, api_key=None, base_url=None, provider="auto", **kwargs):
        if provider == "modelscope":
            self.provider = "modelscope"
            self.api_key = api_key or os.getenv("MODELSCOPE_API_KEY")
            self.base_url = base_url or "https://api-inference.modelscope.cn/v1/"
            if not self.api_key:
                raise ValueError("ModelScope API key not found.")
            self.model = model or os.getenv("LLM_MODEL_ID") or "Qwen/Qwen2.5-VL-72B-Instruct"
            self._client = OpenAI(api_key=self.api_key, base_url=self.base_url)
        else:
            super().__init__(model=model, api_key=api_key, base_url=base_url,
                             provider=provider, **kwargs)
```

这种「拦截 + 回退」的写法有两个好处：业务代码里用 `MyLLM` 与用原生类完全一致（`think` 等方法全部继承，无需重写）；库升级时自定义逻辑不会丢。

**本地模型**同理。VLLM 与 Ollama 都把模型封装成 OpenAI 兼容的 HTTP 服务，因此对客户端而言只是换了个 `base_url`：

```python
# VLLM：python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen1.5-0.5B-Chat --port 8000
llm = HelloAgentsLLM(provider="vllm", model="Qwen/Qwen1.5-0.5B-Chat",
                     base_url="http://localhost:8000/v1", api_key="vllm")

# Ollama：ollama run llama3
llm = HelloAgentsLLM(provider="ollama", model="llama3",
                     base_url="http://localhost:11434/v1", api_key="ollama")
```

本地服务不校验真实密钥，填个非空字符串即可。两者定位略有差别：Ollama 把下载、配置、服务启动压成一条命令，适合快速上手；VLLM 靠 PagedAttention 与连续批处理把吞吐拉高，是生产部署的选择。相比直接用 Transformers 跑推理，这两个方案在并发下才站得住。

**自动检测**是「约定优于配置」的落地：`_auto_detect_provider` 按优先级推断服务商，`_resolve_credentials` 再据此补全密钥与地址。

```python
def _auto_detect_provider(self, api_key, base_url) -> str:
    # 1. 专用环境变量最可靠
    if os.getenv("MODELSCOPE_API_KEY"): return "modelscope"
    if os.getenv("OPENAI_API_KEY"):    return "openai"
    if os.getenv("ZHIPU_API_KEY"):     return "zhipu"

    actual_base_url = base_url or os.getenv("LLM_BASE_URL")
    # 2. 从 base_url 的域名与端口推断（端口能区分本地部署方案）
    if actual_base_url:
        url = actual_base_url.lower()
        if "api-inference.modelscope.cn" in url: return "modelscope"
        if "open.bigmodel.cn" in url:            return "zhipu"
        if "localhost" in url or "127.0.0.1" in url:
            if ":11434" in url: return "ollama"
            if ":8000"  in url: return "vllm"
            return "local"
    # 3. 兜底：看密钥前缀，仍有歧义就交给通用配置
    actual_api_key = api_key or os.getenv("LLM_API_KEY")
    if actual_api_key and actual_api_key.startswith("ms-"): return "modelscope"
    return "auto"
```

三级优先级的顺序是有讲究的：专用环境变量是显式意图，最可靠；URL 特征次之，靠域名与端口识别；密钥格式最模糊——多家密钥长得像，只能当辅助。有了这层，`.env` 里只写 `LLM_BASE_URL=http://localhost:11434/v1` 与 `LLM_MODEL_ID=llama3`，代码里 `HelloAgentsLLM()` 就能自动认出 Ollama。

## 5. Message：对内丰富，对外兼容

对话历史是智能体最重要的上下文，但直接拿 dict 传递会导致字段随意、格式漂移。用一个模型类收口：

```python
MessageRole = Literal["user", "assistant", "system", "tool"]

class Message(BaseModel):
    content: str
    role: MessageRole
    timestamp: datetime = None
    metadata: Optional[Dict[str, Any]] = None

    def __init__(self, content: str, role: MessageRole, **kwargs):
        super().__init__(content=content, role=role,
                         timestamp=kwargs.get("timestamp", datetime.now()),
                         metadata=kwargs.get("metadata", {}))

    def to_dict(self) -> Dict[str, Any]:
        """转换为 OpenAI API 格式"""
        return {"role": self.role, "content": self.content}
```

三个设计点：`Literal` 把 `role` 的取值锁死在四种，类型检查阶段就能挡住拼错的角色名；`timestamp` 与 `metadata` 是给日志、溯源、后续扩展预留的位置；`to_dict()` 只吐出 API 认识的字段——内部可以有丰富信息，对外保持兼容。

## 6. Config：让零配置也能跑

配置硬编码在代码里，换环境就得改源码。集中成一个带默认值的类，配合 `from_env` 读取：

```python
class Config(BaseModel):
    default_model: str = "gpt-3.5-turbo"
    default_provider: str = "openai"
    temperature: float = 0.7
    max_tokens: Optional[int] = None
    debug: bool = False
    log_level: str = "INFO"
    max_history_length: int = 100

    @classmethod
    def from_env(cls) -> "Config":
        return cls(
            debug=os.getenv("DEBUG", "false").lower() == "true",
            log_level=os.getenv("LOG_LEVEL", "INFO"),
            temperature=float(os.getenv("TEMPERATURE", "0.7")),
            max_tokens=int(os.getenv("MAX_TOKENS")) if os.getenv("MAX_TOKENS") else None,
        )
```

每个字段都有合理默认值，因此不配也能工作；要改行为优先用环境变量，容器化部署时尤其省事——同一个镜像在不同环境靠 env 切换。

## 7. Agent 基类：只有一个抽象方法

顶层抽象决定了下层能有多自由。`Agent` 用 `abc` 定义，只强制子类实现 `run`：

```python
class Agent(ABC):
    def __init__(self, name: str, llm: HelloAgentsLLM,
                 system_prompt: Optional[str] = None, config: Optional[Config] = None):
        self.name = name
        self.llm = llm
        self.system_prompt = system_prompt
        self.config = config or Config()
        self._history: list[Message] = []

    @abstractmethod
    def run(self, input_text: str, **kwargs) -> str:
        """运行Agent"""

    def add_message(self, message: Message):
        self._history.append(message)

    def clear_history(self):
        self._history.clear()

    def get_history(self) -> list[Message]:
        return self._history.copy()
```

四个成员各自对应一种依赖：`name` 用于日志与调试，`llm` 是模型通道，`system_prompt` 是角色设定，`config` 是行为开关。基类把「怎么记历史」实现掉，把「怎么思考」留给子类——这正是继承该做的事。

`**kwargs` 的存在是为了让契约足够窄而子类足够灵活：注册表、最大步数、自定义提示词这些差异化参数不进基类签名，由各自的构造函数声明，`run` 仍是统一入口。

## 8. 这一层的边界

回头看，整套接口的取舍可以概括成四句话：**只留一个基类**（其余能力都做成工具，避免抽象层繁殖）；**契约尽量窄**（`run(input) -> str`，任何范式都能套进去）；**状态归基类**（历史管理不该由每个范式各写一遍）；**差异归构造**（模型差异在 `provider`，行为差异在 `Config`，范式差异在子类）。
