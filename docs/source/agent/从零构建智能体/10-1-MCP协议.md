# MCP 协议

上一篇的代码库维护助手已经能自己看代码、记笔记、跑命令，但它的三件工具全都长在 HelloAgents 里。换一个宿主程序、换一个模型提供方，这套工具就得重新包一遍——每个外部服务写一个 `Tool` 子类、处理 HTTP、认证、错误码，再按各家的 function calling 格式拼一遍 schema。MCP（Model Context Protocol）要处理的就是这一层：工具不再由「某个智能体」私有，而是由「某个服务」对外声明，谁都能连。

## 1. 手写适配器的三个限制

假设要做一个研究助手，需要访问 GitHub、数据库、天气服务。传统写法是三个类：

```python
class GitHubTool(BaseTool):
    def run(self, repo_url): ...     # 大量的 API 调用代码

class DatabaseTool(BaseTool):
    def run(self, query): ...        # 数据库连接与查询

class WeatherTool(BaseTool):
    def run(self, location): ...     # 天气 API 调用

agent.add_tool(GitHubTool())
agent.add_tool(DatabaseTool())
agent.add_tool(WeatherTool())
```

问题不在「写起来累」，而在三个结构性限制：

- **集成成本被重复支付**。每个工具都自己处理 HTTP、重试、认证、超时，同一件事被写了几十遍。
- **能力被锁在预定义集合里**。智能体只能用它被塞进去的工具，运行期无法发现新服务。
- **协作只能手工编排**。研究员 → 撰写员 → 编辑这样的流程，得在外面用代码串起来，智能体自己不会去找「谁能干这个活」。

加上第四个隐性成本：不同模型的 function calling schema 并不一致，换模型就要改工具定义。

协议化的收益正好对应这四条：**统一接口、可互操作、动态发现、可扩展**。

## 2. MCP 统一的是什么

MCP 由 Anthropic 提出，定位类似「智能体的 USB-C」——USB-C 统一的是接口形状，MCP 统一的是「智能体怎么访问外部能力」。

它统一的对象有三层：

- **跨服务**：文件系统、数据库、GitHub、Slack 都以相同的方式声明工具、响应调用。
- **跨模型**：工具描述只写一遍，OpenAI、Claude、本地模型都通过同一个客户端使用。
- **跨进程**：服务器可以是本地子进程，也可以是远程服务，协议不变。

还有一点常被忽略：MCP 不只是 RPC。它允许服务器把**上下文**一起交出来。访问一个代码仓库时，服务器能同时给出文件内容、目录结构、依赖关系、提交历史——调用方拿到的不再是一个字符串返回值，而是一块可以放进提示词的环境信息。

## 3. Host / Client / Server 三层

MCP 把参与者分成三层，用 Claude Desktop 的一个日常场景就能说清：用户问「我桌面上有哪些文档？」

1. **Host**：Claude Desktop 本身。负责接收提问、调模型、管理对话，是用户直接面对的界面。
2. **Client**：Host 内置的协议客户端。当模型表示要读文件，Client 被激活，负责与对应的 Server 建立连接、发请求、收结果。
3. **Server**：文件系统 MCP Server。真正执行目录扫描，把文件列表返回给 Client。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-mcp-architecture.png" width="85%" alt="MCP 三层架构：Host 接收提问，Client 负责协议通信，Server 执行实际操作" />

完整链路是：用户提问 → Host → 模型判断需要文件信息 → Client 连接 Server → Server 执行 → 结果回传 → 模型组织回答 → Host 显示。

这种切法的价值是**关注点分离**：Host 管体验，Client 管协议，Server 管功能。写 Server 的人完全不需要知道 Host 是谁、用的是什么模型。

## 4. 三种能力

MCP 服务器对外暴露的不只是「函数」，共三类：

| 能力 | 性质 | 典型用途 |
| --- | --- | --- |
| Tools | 主动执行 | 查询数据库、写文件、发消息 |
| Resources | 被动数据 | 文档内容、配置、日志片段 |
| Prompts | 指导模板 | 预设的提问模板与工作流提示词 |

区别在于「谁发起」：Tools 是模型决定要调用的动作；Resources 是客户端按 URI 读取的数据，模型只是使用者；Prompts 是服务器提供的提示词模板，由用户或宿主选择注入。

写工具时容易只想着 Tools，把一切都塞成函数。实际上「给模型看的东西」用 Resources 更自然——它不需要参数、不产生副作用，读到就是结果。

## 5. 与 Function Calling 的分工

一个常见疑问：已经在用 function calling，为什么还要 MCP？两者不是替代关系。

Function Calling 是**模型能力**：模型能理解「什么时候该调函数」，并生成符合 schema 的参数。MCP 是**工程协议**：规定工具怎么被描述、怎么被发现、怎么被调用、怎么跨进程传输。

用打电话打比方：Function Calling 是「会打电话」这项技能，MCP 是「电话通信标准」。没有标准，每台设备之间都要定制一根线；有了标准，谁都拨得通。

差异在代码里最直观。同一个 GitHub 搜索，Function Calling 要为每个提供方写一份 schema，再各写一套响应解析：

```python
# OpenAI：parameters + tool_calls
{"type": "function", "function": {"name": "search_github", "parameters": {...}}}
response.choices[0].message.tool_calls[0].function.arguments

# Claude：input_schema + tool_use
{"name": "search_github", "input_schema": {...}}
response.content[0].input                      # 注意字段名全都不一样
```

换成 MCP，schema 由服务器声明，调用方只做同一套动作：

```python
client = MCPClient(["npx", "-y", "@modelcontextprotocol/server-github"])

async with client:
    tools = await client.list_tools()            # 发现，schema 随工具一起来
    result = await client.call_tool("search_repositories", {"query": "AI agents"})
```

换模型不需要改工具，换工具也不需要改模型——这才是「协议」和「能力」分开之后的结果。

## 6. 客户端三连：连接、发现、调用

HelloAgents 基于 FastMCP 2.0 实现客户端，使用只有三步：

```python
import asyncio
from hello_agents.protocols import MCPClient

async def main():
    client = MCPClient(["npx", "-y", "@modelcontextprotocol/server-filesystem", "."])

    async with client:                            # 1. 连接（退出时自动关闭）
        tools = await client.list_tools()         # 2. 发现：名字、描述、参数 schema
        for t in tools:
            print(t["name"], t.get("description"))

        result = await client.call_tool("read_file", {"path": "README.md"})   # 3. 调用
        print(result)

asyncio.run(main())
```

`async with` 不是装饰：MCP 连接有明确的生命周期，进入时握手、退出时释放子进程。忘了关，`npx` 启动的服务器会一直挂在后台。

传输层与协议本身解耦，`MCPClient` 支持五种：

| 传输 | 场景 | 备注 |
| --- | --- | --- |
| Memory | 单测、原型 | 不启进程，进程内直连 |
| Stdio | 本地开发、脚本服务器 | 由客户端拉起子进程，走标准输入输出 |
| HTTP | 远程服务、微服务 | 传 URL 即可 |
| SSE | 流式、长连接 | `transport_type="sse"` |
| StreamableHTTP | 双向流式 | `transport_type="streamable_http"` |

选型其实只有一个问题：**服务器和客户端是不是同一台机器、同一个用户**。是，用 Stdio，最简单也最快；不是，用 HTTP 系，把鉴权和网络边界交给部署层。

需要注意一点：`MCPTool` 只覆盖 Memory 与 Stdio；HTTP/SSE 这类远程传输要走底层 `MCPClient`。原因很实际——远程连接该由谁持有、何时断开，是应用层的事，包装成工具反而藏住了这个决定。

## 7. MCPTool 的自动展开

直接调客户端适合写脚本，但智能体需要的是「工具列表里有这些东西」。`MCPTool` 做的就是这层转接，而且会**自动展开**：

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import MCPTool

agent = SimpleAgent(name="文件助手", llm=HelloAgentsLLM())

fs_tool = MCPTool(
    name="fs",
    description="访问本地文件系统",
    server_command=["npx", "-y", "@modelcontextprotocol/server-filesystem", "."],
)
agent.add_tool(fs_tool)
# 展开为 fs_read_file、fs_write_file 等独立工具，注册进 Agent 的工具表
```

展开之后，模型看到的是普通工具，生成 `[TOOL_CALL:fs_read_file:path=README.md]`；包装器再把这次调用翻译成 MCP 请求：

```
{"action": "call_tool", "tool_name": "read_file", "arguments": {"path": "README.md"}}
```

中间还顺手做了类型转换。模型吐出的参数是字符串（`a=25,b=16`），服务器期待的是数字，包装器按 `inputSchema` 转成 `{"a": 25.0, "b": 16.0}`，否则参数校验会直接失败。

`name` 前缀不是可选的装饰。同时挂两个服务器时，`fs_read_file` 与 `git_read_file` 靠前缀区分；都叫默认值就会撞名，后注册的把先注册的覆盖掉。

有时不想隐式展开，也可以自己拿展开结果逐个注册：

```python
weather_tool = MCPTool(server_command=["python", "weather_mcp_server.py"])

expanded = weather_tool.get_expanded_tools()
if not expanded:
    raise RuntimeError("未发现 MCP 子工具，请检查服务脚本、依赖和启动日志。")

for tool in expanded:
    assistant.add_tool(tool)
```

显式写法的好处是失败可见：服务器没起来、依赖没装、脚本路径错了，都会在这里暴露成空列表，而不是等到模型调用时才报一个含混的错。

## 8. 自己写一个 MCP 服务器

公开服务器覆盖了文件、GitHub、数据库这些通用场景，但业务逻辑、私有数据、专有算法只能自己包。写法比想象中短——一个普通函数加一个装饰性注册就够了：

```python
from hello_agents.protocols import MCPServer

weather_server = MCPServer(name="weather-server", description="真实天气查询服务")

def get_weather(city: str) -> str:
    """获取指定城市的当前天气"""
    ...

def list_supported_cities() -> str:
    """列出所有支持的中文城市"""
    ...

weather_server.add_tool(get_weather)
weather_server.add_tool(list_supported_cities)

if __name__ == "__main__":
    weather_server.run()          # 默认走 Stdio，由宿主拉起
```

关键在于**函数签名就是 schema**：参数名、类型注解、docstring 会被提取成工具描述。docstring 写得含糊，模型就选不准工具——这一点和 7-2 里手写 `ToolParameter` 是同一个道理，只是这里由签名代劳了。

写完先单独测，不要直接塞进智能体：

```python
client = MCPClient(["python", "weather_mcp_server.py"])

async with client:
    print(await client.call_tool("get_server_info", {}))
    print(await client.call_tool("list_supported_cities", {}))
    print(await client.call_tool("get_weather", {"city": "北京"}))
```

服务器能独立响应，再接到 Agent 上。分两步排查，比在「模型为什么不调工具」里猜要快得多。

想给别人用，可以发布到 Smithery（MCP 服务器的分发平台，定位类似 PyPI）。需要补的是 `pyproject.toml`、`smithery.yaml`、`Dockerfile` 和一份 README——都是工程包装，协议部分不用改。

## 9. 生态与使用边界

现成服务器已经不少，找的时候看三个地方：

- **awesome-mcp-servers**：社区精选列表，按功能分类，覆盖面最广。
- **mcpservers.org**：带搜索与筛选的目录站。
- **modelcontextprotocol/servers**：官方维护，质量与文档最稳。

生态早期的现实是**时效性不由协议保证**。社区服务器的 API 变更、依赖升级、维护者失联，都会让一个昨天还能跑的工具今天报错。选型上有个朴素的原则：优先选有大公司或明确团队背书的服务器，个人项目适合参考实现，不适合放进生产链路。

另外三条边界值得提前想清楚：

- **不是所有函数都值得走 MCP**。进程内的纯计算函数直接注册成 Tool 更快；MCP 的收益来自「跨进程复用」，没有跨进程需求就别付这层开销。
- **Stdio 服务器是宿主拉起的子进程**，跑的是本机代码，权限等于宿主。文件系统服务器限定根目录、命令类服务器做白名单，这些约束要在服务器侧落实，协议不负责安全。
- **远程传输的生命周期归应用管**。`MCPTool` 每次调用都启停进程，适合短任务；长时间会话、需要复用连接时，直接用 `MCPClient` 持有连接更合适。

MCP 把「用别人的工具」这件事标准化了，但智能体之间怎么互相说话、怎么发现彼此，协议里还没有答案——下一篇看 A2A 与 ANP 这两种面向智能体网络的协议：[10-2-A2A与ANP协议](/source/agent/从零构建智能体/10-2-A2A与ANP协议)。
