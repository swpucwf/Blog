# 智能体性能评估

前面十篇一路在加能力：范式、工具、记忆、检索、上下文、协议。但每加一样东西，都会冒出一个没有答案的问题——这次改动到底有没有让它变好？改提示词、换模型、加一层检索，凭几个演示例子看不出差别，有时还互相矛盾。评估做的事，就是把这个判断从「感觉」换成「数字」，并且让数字可复现。

## 1. 为什么评估比测试难

传统软件测试的判据是确定的：输入一致，输出必须一致，断言只有真与假。智能体不满足这三条中的任何一条。

- **输出不确定**：同一个问题可以有多种正确表述，逐字比对没有意义。
- **标准因任务而异**：工具调用要看函数名与参数，问答要看语义是否等价，多步任务要看过程是否合理。
- **成本高**：跑一遍评估就是成百上千次模型调用，全量评一次可能花掉几百元。

这三条决定了评估不能靠「写几个断言」，只能靠基准（benchmark）：固定的数据集、固定的指标、固定的评分脚本。有了这套东西，两个版本的差异才有可比性——样本相同、判据相同，唯一的变量是被测对象。

评估能提供的判断有四类：能力是否达标、版本之间谁更好、弱点在哪个类别、以及向别人证明可靠性的依据。最后一类常被忽略：没有评估报告，任何「这个智能体很好用」的说法都只是自述。

## 2. 基准地图：先看它惩罚什么错误

基准很多，选的时候不要看榜单排名，先看它**惩罚哪类错误**——那才是它真正测的东西。

| 方向 | 代表基准 | 规模 | 判据 | 主要惩罚 |
| --- | --- | --- | --- | --- |
| 工具调用 | BFCL | 1120+ 样本 | AST 匹配 | 选错函数、参数错、该调不调 |
| 工具调用 | ToolBench | 16000+ 真实 API | 执行与结果 | 真实 API 场景下的组合调用 |
| 工具调用 | API-Bank | 53 个常用 API | 调用正确性 | 读不懂 API 文档 |
| 通用能力 | GAIA | 466 题，三级难度 | 准精确匹配 | 多步推理、浏览、文件处理 |
| 通用能力 | AgentBench | 8 个领域 | 领域指标 | 跨领域泛化 |
| 通用能力 | WebArena | 真实网页 | 任务完成 | 网页交互 |
| 多智能体 | ChatEval / SOTOPIA | — | 模型评审 / 场景指标 | 对话质量、社交互动 |

指标层面则是四个族：准确性（Accuracy / EM / F1）、效率（响应时间、Token 用量）、鲁棒性（错误率、故障恢复）、协作（通信效率、任务完成度）。

HelloAgents 的评估体系挑了三件有代表性的事来覆盖：

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-eval-system.png" width="85%" alt="HelloAgents 评估体系：BFCL 测工具调用、GAIA 测通用能力、AIME 数据生成测生成质量" />

- **BFCL**：工具调用准不准，指标单一、判据清晰。
- **GAIA**：真实任务能不能做完，难度分级、综合性强。
- **数据生成质量**：用智能体造数据时，怎么判断造出来的东西够不够好。

前两个是「评智能体」，第三个是「用智能体评数据」——同一个评估模块的两种用法。

## 3. BFCL：把函数调用当语法树比

工具调用的判据看起来很简单：函数名对不对、参数对不对。难在「对不对」怎么算。字符串比对会因为参数顺序、引号风格、`2+3` 与 `5` 这类等价写法全部判错，而这些都不该算错。

BFCL 的答案是**抽象语法树匹配**：把预测和标准答案都解析成 AST，比较树的结构与节点值。

$$ \text{AST\_Match}(P, G) = \begin{cases} 1 & \text{if } \text{AST}(P) \equiv \text{AST}(G) \\ 0 & \text{otherwise} \end{cases} $$

树等价要满足三条：

1. **函数名精确一致**：`get_weather` 与 `get_temperature` 是两个函数，不能混。
2. **参数键集合相等**：忽略书写顺序，`f(a=1, b=2)` 等价于 `f(b=2, a=1)`。
3. **参数值语义等价**：`f(x=2+3)` 等价于 `f(x=5)`，`"hello"` 等价于 `'hello'`。

多函数场景再叠一条：调用数量必须相同、每个调用都能配上、但调用顺序可以不同（按集合匹配）。

```
预测: get_weather(city="Beijing", unit="celsius")
标准: get_weather(unit="celsius", city="Beijing")     ✅ 顺序不同，仍匹配

预测: calculate(x=2+3)
标准: calculate(x=5)                                  ✅ 等价表达式，仍匹配

预测: get_temperature(city="Beijing")
标准: get_weather(city="Beijing")                     ❌ 函数名不同
```

数据集是三类字段：`question`（用户请求）、`function`（可用函数签名与描述）、`ground_truth`（期望调用）。评估流程是「加载数据 → 跑智能体 → 解析预测 → AST 匹配 → 汇总指标」。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-bfcl-flow.png" width="85%" alt="BFCL 评估流程：加载数据集、运行智能体、AST 匹配、汇总指标" />

BFCL 把样本分成四类，难度递增：

- **simple**：单函数、单次调用。
- **multiple**：需要连续调用多个不同函数。
- **parallel**：一次并行调用多个函数。
- **irrelevance**：本不该调用任何函数——这一类的难点是「忍住不调」。

指标以准确率为主，再按类别拆开：

$$ \text{Accuracy} = \frac{1}{N} \sum_{i=1}^{N} \text{AST\_Match}(P_i, G_i) $$

分类准确率 $\text{Accuracy}_c$ 把样本按类别切开单独算，加权准确率再按权重合并。实际使用时最有信息量的往往是**分类**：总准确率 85% 可能意味着 simple 100%、parallel 60%，而后者才是真实的瓶颈。

## 4. 跑一次 BFCL

HelloAgents 把整套流程包成一个工具，参数只有三个：被测智能体、类别、样本数。

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import BFCLEvaluationTool

agent = SimpleAgent(name="TestAgent", llm=HelloAgentsLLM())

bfcl_tool = BFCLEvaluationTool()
results = bfcl_tool.run(
    agent=agent,
    category="simple_python",
    max_samples=5,          # 0 表示全量
)

print(f"准确率: {results['overall_accuracy']:.2%}")
print(f"正确数: {results['correct_samples']}/{results['total_samples']}")
```

`run` 内部做了四件事：加载数据集、逐样本评估、导出 BFCL 官方格式、调用 `bfcl evaluate` 做官方复核，最后生成 Markdown 报告。

这里有个容易踩的坑：**依赖冲突**。`bfcl-eval` 要求 `numpy<=2.0.0`，与主项目的依赖版本不兼容，需要单独装：

```bash
pip install "numpy==1.26.4" bfcl-eval
```

为什么非要跑官方 CLI？因为 AST 匹配有很多边界细节（等价表达式、类型转换、并行调用的集合匹配），自己实现的版本稍有偏差，分数就不可比。用官方脚本复核过的数字，才能和排行榜或其他团队的结论放在一起谈。

## 5. GAIA：单步正确不等于任务完成

BFCL 测的是「会不会调函数」，但一个能正确调用搜索工具的智能体，未必能回答「加州人口最多的三个城市总人口是多少」。这需要拆解、检索、计算、汇总。GAIA 就是为这类任务设计的：466 个真实问题，三个难度级别，从几乎零步的任务到需要组合多种工具的复杂任务。

它的判据是**准精确匹配**：先归一化，再比较。

$$ \text{Quasi\_Exact\_Match}(A_{pred}, A_{true}) = \begin{cases} 1 & \text{if } \mathcal{N}(A_{pred}) = \mathcal{N}(A_{true}) \\ 0 & \text{otherwise} \end{cases} $$

归一化规则按答案类型分：

```
"$1,234.56"               -> "1234.56"               数字：去逗号、去单位
"The United States"       -> "united states"         字符串：小写、去冠词、去尾标点
"Paris, London, Berlin"   -> "berlin,london,paris"   列表：逐项归一化后排序
```

这套规则解决的是「答案对但格式不同」的问题——`$1,234.56` 和 `1234.56` 是同一个答案，不该判错。

指标比 BFCL 多一层结构：

- **精确匹配率**：归一化后完全一致的比例。
- **分级准确率** $\text{Accuracy}_\ell$：Level 1/2/3 各自算。
- **难度递进下降率**：

$$ \text{Drop Rate}_{\ell \to \ell+1} = \frac{\text{Accuracy}_\ell - \text{Accuracy}_{\ell+1}}{\text{Accuracy}_\ell} $$

- **平均推理步骤数**：只在答对的样本上统计，用来看「答对是靠猜还是靠推理」。

下降率这个指标很值得单独看。两个智能体 Level 1 都是 90%，一个 Level 3 掉到 20%，另一个掉到 60%，总准确率的差距会被样本数稀释，下降率不会——它直接暴露「多步能力」这一维的强弱。

用法与 BFCL 同构：

```python
from hello_agents.tools import GAIAEvaluationTool

gaia_tool = GAIAEvaluationTool()
results = gaia_tool.run(
    agent=agent,
    level=1,
    max_samples=5,
    export_results=True,
    generate_report=True,
)
print(f"精确匹配率: {results['exact_match_rate']:.2%}")
```

GAIA 需要 `HF_TOKEN` 拉取数据集，评估前要先把环境变量配好。这一步不能省：数据集在 HuggingFace 上，匿名拉取会被限流。

## 6. LLM 当评委：绝对分与相对胜负

前两个基准评的是「智能体答题」，还有一种更常见的工作是「用智能体造数据」——比如生成 AIME 风格的数学题。这时要评的对象变成了数据本身，没有标准答案可对。

HelloAgents 用三种互补的方法：

- **LLM Judge**：让模型按维度打 1-5 分，给绝对评价。
- **Win Rate**：让模型成对比较，生成题 vs 真题，给相对胜负。
- **人工验证**：专家核对答案正确性与推理严密性。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-datagen-eval-flow.png" width="85%" alt="数据生成质量评估流程：生成、LLM Judge、Win Rate、人工验证、综合报告" />

LLM Judge 的四个维度是固定的：

| 维度 | 看什么 |
| --- | --- |
| correctness | 题目本身与答案是否正确 |
| clarity | 表述是否清楚、无歧义 |
| difficulty_match | 难度是否落在目标区间（AIME 第 6-9 题水平） |
| completeness | 解答步骤是否完整、推理是否必要 |

四个维度各 1-5 分，汇总出三个指标：

$$ \text{Average Score} = \frac{1}{N} \sum_{i=1}^{N} \frac{1}{4} \sum_{d=1}^{4} S_{i,d} $$

$$ \text{Pass Rate} = \frac{|\{i : \text{Score}_i \geq 3.5\}|}{N}, \quad \text{Excellent Rate} = \frac{|\{i : \text{Score}_i \geq 4.5\}|}{N} $$

平均分看整体水平，及格率保证下限，优秀率衡量高质量产出。三个一起看才有意义：平均 4.0 但及格率 60%，说明质量分布很不均匀，而不是「整体不错」。

Win Rate 走另一条路——不比绝对分，只比谁更好：

$$ \text{Win Rate} = \frac{\text{Wins}}{\text{Total Comparisons}} $$

理想值是 **50% 左右**：说明生成题目与真题质量相当。显著低于 50% 表示还不如真题；显著高于 50% 反而要警惕——要么生成系统确实强，要么评委有偏袒。

调用上两者都是工具，输入是同一份生成数据与评委模型：

```python
llm_judge_tool.run({
    "generated_data_path": generated_data_path,
    "reference_year": 2025,
    "max_samples": 20,
    "judge_model": "gpt-4o",
})

win_rate_tool.run({
    "generated_data_path": generated_data_path,
    "reference_year": 2025,
    "num_comparisons": 20,
    "judge_model": "gpt-4o",
})
```

选 `gpt-4o` 当评委不是随便定的：评委本身的水平决定评分上限，用弱模型评强模型的产出，结论没有参考价值。此外要留意 LLM Judge 的几类已知偏差——位置偏好（更认可先出现的那份）、长度偏好（更认可更长的答案）、自我偏好（更认可同族模型的输出）。Win Rate 通过交换位置部分抵消位置偏好，人工验证兜住正确性，三者配合才勉强够用。

## 7. 三层骨架：Dataset / Evaluator / Metrics

三个场景看起来差别很大，实现结构却是同一套：

- **数据层（Dataset）**：加载、过滤、抽样，对外只暴露「样本列表」。
- **评估层（Evaluator）**：跑智能体、解析输出、调用判据，产出逐样本结果。
- **指标层（Metrics）**：把逐样本结果聚合成总体、分类、分级指标。

换基准只换这三个组件，报告格式和调用方式都不变。这也是把评估封装成 Tool 的意义：评估本身成为一个可被调用的能力——可以让一个智能体去评估另一个智能体的输出，也可以把评估挂进流水线。

对自定义场景，这套骨架同样适用。比如评一个客服智能体，Dataset 是自己的工单样本，Evaluator 是「调用 + 抽取意图与回复」，Metrics 则是意图准确率、API 调用正确率、人工满意度。不必等一个现成的基准。

## 8. 评估工程化的几条经验

跑通评估脚本只是开始，真正影响结论可信度的是使用方式。

- **一次只改一个变量**。同时换模型、改提示词、加检索，分数涨了也不知道是谁的功劳。A/B 的前提是样本、提示词、温度、判据全部固定，只动一处。
- **小样本迭代，全量决策**。开发阶段 `max_samples=5~20` 足够发现方向性错误；要写进结论或对外宣称，再跑全量。反过来做，成本高且节奏慢。
- **报告要归档**。每次评估的配置、样本数、指标、报告文件都留档（连同代码版本），否则两周后无法解释「为什么上次是 82%」。
- **看分类指标，不看总分**。总分是给外人看的，分类与分级才是给开发看的——它告诉你下一步该修哪里。
- **把评估接进 CI**。设一条阈值，低于就阻断合并。评估的价值一半来自「发现退化」，而退化最常发生在与评估无关的改动里。

成本也要算进去：LLM Judge 和 Win Rate 每次都要额外调用模型，20 个样本的成对比较就是 20 次调用。评估频率和样本量应该与实际决策的重要性匹配。

## 9. 评估的边界

最后要承认评估测不到的东西，否则容易把分数当成目标本身。

- **基准高分不等于产品好用**。基准样本分布与真实流量分布不同，真实用户的表达更随意、上下文更脏。
- **不要拿基准样本调提示词**。看过测试题再改提示词，分数会涨，泛化能力不会——这就是过拟合，只是发生在提示词上。
- **数据污染要警惕**。公开基准的题目可能已进入训练语料，模型「答对」未必是推理出来的。
- **在线指标才是终局**。任务成功率、人工反馈、平均轮次，这些来自真实使用的数字，比任何离线基准都更能说明问题。

更合适的定位是把离线评估当**回归测试**：每次改动都跑一遍，确保没有变差；真实效果仍靠线上数据判断。评估不是一次性验收，而是一条持续运行的护栏。
