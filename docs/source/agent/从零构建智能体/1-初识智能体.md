# 初识智能体

讨论智能体容易滑向两个极端：一边把它神秘化，一边把它等同于「调个 LLM 接口」。先把三件事说清楚——它由什么构成、在什么环境里运行、一轮循环怎么走——再动手写几十行代码，边界自然就清楚了。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/1757242319667-0.png" width="90%" alt="智能体与环境的基本交互循环" />

## 1. 定义与四个要素

AI 领域的标准定义：智能体是任何能够通过**传感器（Sensors）**感知所处**环境（Environment）**，并**自主**地通过**执行器（Actuators）**采取**行动（Action）**以达成特定目标的实体。

拆开看是四个要素：

- **环境**：智能体所处的外部世界。对自动驾驶是道路，对交易算法是市场，对 LLM 智能体多半是文件、API 与用户输入。
- **感知**：摄像头、麦克风、雷达，或各类 API 返回的数据流。
- **行动**：物理设备（机械臂、方向盘）或虚拟工具（执行代码、调用服务）。
- **自主性**：真正赋予「智能」的部分。不是被动响应刺激，也不是严格执行预设指令，而是基于感知与内部状态独立决策。

## 2. 传统智能体的演进阶梯

LLM 热潮之前，这条路线已经走了几十年，且不是并列概念，而是能力逐层叠加：

| 类型 | 决策依据 | 回答的问题 |
| --- | --- | --- |
| 简单反射智能体 | 「条件—动作」规则 | 当前感知触发什么动作 |
| 基于模型的反射智能体 | 内部世界模型 | 世界现在是什么样 |
| 基于目标的智能体 | 目标 + 搜索/规划 | 做什么才能达成目标 |
| 基于效用的智能体 | 效用函数 | 哪种行为结果最满意 |
| 学习型智能体 | 强化学习等反馈信号 | 怎样通过经验自我改进 |

恒温器是第一条，隧道里维持前车判断的自动驾驶是第二条，A* 规划的导航是第三条，多目标权衡的决策者是第四条，AlphaGo Zero 是第五条的代表。学习能力本质上是**元能力**：它可以赋予上面任何一类智能体。

## 3. LLM 驱动的新范式

LLM 智能体与传统智能体的差别不在「有没有循环」，而在决策内核：

| 维度 | 传统智能体 | LLM 智能体 |
| --- | --- | --- |
| 核心引擎 | 工程师显式编程的规则/模型 | 预训练得到的隐式世界模型 |
| 知识来源 | 人工构建的知识库 | 海量语料中的统计模式 |
| 交互方式 | 结构化输入 | 高层级、模糊、带上下文的自然语言 |
| 能力边界 | 确定且有界 | 灵活、通用、可涌现 |

以「规划一次厦门之旅」为例，一个 LLM 智能体会同时做三件事：

- **规划与推理**：把高层目标拆成 `[确认偏好] -> [查询目的地] -> [制定草案] -> [预订票务住宿]`。
- **工具使用**：发现信息缺口就调工具，比如查到「预报有雨」后把室内活动纳入候选。
- **动态修正**：把「这家酒店超预算」当作新约束，重新搜索并调整后续行动。

还有一层容易被忽略：LLM 智能体其实是**神经符号主义**的实践。内核是神经网络，但工作过程吐出的 Thought、计划、API 调用都是明确的符号，可解析、可执行、可审计。

## 4. 分类的三个维度

**按决策架构**：即上一节的五类阶梯。

**按时间与反应性**：关注「立刻行动」还是「想清楚再动」。

- **反应式**：感知到行动近乎直连，延迟低、成本低，但短视。安全气囊、高频交易属于此类。
- **规划式**：先在世界模型里推演多种可能，战略性强但慢。棋手、商业计划属于此类。
- **混合式**：底层快反模块 + 高层规划模块。LLM 智能体的「思考—行动—观察」正是把这个分层压缩进一个微循环：思考阶段做审议，行动与观察阶段拿反馈。

**按知识表示**：知识以什么形式存在于「思想」里。

- **亚符号主义**（连接主义）：知识是网络中的统计模式，擅长模式识别与噪声数据，但不可解释，是黑箱。
- **符号主义**：知识是人类可读的规则与图谱，透明可追溯，但脆弱，遇到未覆盖的情况就失灵（知识获取瓶颈）。
- **神经符号主义**：两者的和解。可以借用卡尼曼的双系统类比——系统 1 是快速直觉（亚符号），系统 2 是缓慢审慎的逻辑推理（符号），LLM 智能体让二者协同。

## 5. 任务环境：PEAS 与四个特性

描述任务环境的标准工具是 **PEAS**：性能度量（Performance）、环境（Environment）、执行器（Actuators）、传感器（Sensors）。以智能旅行助手为例：

| 维度 | 内容 |
| --- | --- |
| 性能度量 | 行程合理度、预算符合度、用户满意度、响应时延 |
| 环境 | 天气与航班 API、地图与预订平台、用户对话 |
| 执行器 | 调用工具、生成方案、写入行程单 |
| 传感器 | 用户输入、API 返回、上一轮的 Observation |

数字环境通常同时具备四个特性，每一个都直接压到设计上：

- **部分可观察**：一次 API 只能看到部分数据，所以需要记忆（记住查过什么）与探索（换条件再查）。
- **随机性**：同样查询两次，票价与余票都可能变，所以需要监控变化并容忍不确定。
- **多智能体**：其他用户、脚本、航司调价系统都在改变环境，所以需要快速响应与策略切换。
- **序贯且动态**：当前动作影响未来，环境自身也在变，所以循环必须短、反馈必须快。

## 6. 运行机制：Agent Loop

智能体不是一次性完成任务，而是跑一个持续循环：

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/1757242319667-5.png" width="90%" alt="智能体循环" />

1. **感知**：接收观察（用户指令或上一步行动的结果反馈）。
2. **思考**：LLM 驱动的推理，内部再分两步——**规划**（更新理解、拆解子任务）与**工具选择**（选工具、定参数）。
3. **行动**：调用选定工具，对环境施加影响。
4. **观察**：环境状态变化后返回新观察，进入下一轮。

工程上要让 LLM 稳定驱动这个循环，关键是**交互协议**：每次输出不再是自由文本，而是固定结构。

```text
Thought: 用户想知道北京的天气。我需要调用天气查询工具。
Action: get_weather("北京")
```

外部解析器捕获 `Action` 并执行，再把原始结果（往往是 JSON）压成一段自然语言观察回灌：

```text
Observation: 北京当前天气为晴，气温25摄氏度，微风。
```

解析、执行、再包装，这三步是「LLM 会说」与「系统能做」之间的转换器；很多智能体不稳，问题就出在这一层。

## 7. 最小实现：三件套 + 主循环

一个能跑的最小智能体只需要三样东西。

**其一，指令模板。** 它同时承担角色设定与协议约定：

```text
你是一个智能旅行助手。分析用户请求，使用可用工具一步步解决问题。

# 可用工具
- get_weather(city: str): 查询指定城市实时天气
- get_attraction(city: str, weather: str): 根据城市和天气推荐景点

# 输出格式
Thought: [思考与下一步计划]
Action: [具体行动，以下二选一]
1. 调用工具: function_name(arg_name="arg_value")
2. 结束任务: Finish[最终答案]

# 约束
每次只输出一对 Thought-Action；Action 必须在一行内；信息足够时必须用 Finish[...] 结束。
```

**其二，工具字典。** 普通函数 + 统一的错误回传约定（网络错误、参数错误都返回可读字符串，而不是抛异常），最后登记：

```python
available_tools = {"get_weather": get_weather, "get_attraction": get_attraction}
```

**其三，OpenAI 兼容客户端。** 一段 `chat.completions.create` 封装，换 `base_url` 与 `model` 就能在官方 API、Ollama、vLLM 之间切换。

主循环的骨架只有几十行，但有四个细节决定成败：

```python
for i in range(5):                              # 1. 最大轮数，防死循环
    llm_output = llm.generate("\n".join(history), system_prompt=AGENT_SYSTEM_PROMPT)

    # 2. 截断模型多吐的 Thought-Action 对
    match = re.search(r'(Thought:.*?Action:.*?)(?=\n\s*(?:Thought:|Action:|Observation:)|\Z)',
                      llm_output, re.DOTALL)
    if match:
        llm_output = match.group(1).strip()

    history.append(llm_output)

    # 3. 解析 Action，先判断终止
    action = re.search(r"Action: (.*)", llm_output, re.DOTALL).group(1).strip()
    if action.startswith("Finish"):
        print(re.match(r"Finish\[(.*)\]", action).group(1))
        break

    tool_name = re.search(r"(\w+)\(", action).group(1)
    kwargs = dict(re.findall(r'(\w+)="([^"]*)"', re.search(r"\((.*)\)", action).group(1)))
    observation = available_tools.get(tool_name, lambda **_: f"错误:未定义的工具 {tool_name}")(**kwargs)

    # 4. 观察回灌
    history.append(f"Observation: {observation}")
```

跑起来是三轮：查天气 → 按天气找景点 → `Finish[...]` 汇总回答。这个过程顺带展示了智能体的四项基本能力：**任务分解、工具调用、上下文理解、结果合成**。

## 8. 两种协作模式

**作为开发者工具**：深度嵌入既有工作流，增强而非取代人。Copilot 强在编辑器内的行级补全，Claude Code 把交互搬到终端并能读整个代码库、跑测试、走 headless 自动化，Trae 主打轻量快迭代，Cursor 则是从头按 AI 原生设计的编辑器。

**作为自主协作者**：只给高层目标，智能体自己规划、执行、反思、交付。关系从「命令—执行」变成「目标—委托」。实现上有三条主流路线：

- **单智能体自主循环**：AgentGPT 式的自我提示迭代。
- **多智能体协作**：角色扮演对话（CAMEL）、组织化工作流（MetaGPT、CrewAI 的虚拟团队与 SOP）、灵活对话网络（AutoGen、AgentScope）。
- **高级控制流**：LangGraph 把执行过程建模为状态图，循环、分支、回溯、人工介入都变成图上的边。

## 9. Workflow 与 Agent 的边界

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/1757242319667-18.png" width="90%" alt="Workflow 与 Agent 的差异" />

一句话区分：**Workflow 让 AI 按部就班地执行指令，Agent 给 AI 自由度去自主达成目标。**

报销审批是典型的 Workflow：金额小于 500 由部门经理批，大于 500 再加财务总监，条件与顺序全部预先固定。旅行助手则是 Agent：没有 `if 天气=晴天 then 推荐颐和园` 这样的硬编码，雨天它自己会推理到博物馆，还依赖预算、偏好等实时信息。

| 判断维度 | 倾向 Workflow | 倾向 Agent |
| --- | --- | --- |
| 条件能否穷举 | 能，且稳定 | 不能，输入高度开放 |
| 结果如何验证 | 规则可判定 | 需 LLM 或人工评判 |
| 错误代价 | 高，要求可回溯 | 可控，有兜底与人工复核 |
| 需求变更频率 | 低 | 高 |

实践中大多数系统是混合：主干走固定流程，把需要判断的节点交给 Agent，再回到流程里。这也是后续几篇反复出现的结构。
