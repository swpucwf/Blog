# 结构化笔记与长程实战

上一篇解决了「这一轮该放什么」，但长程任务还有另一半问题：跨几十轮、跨几天之后，怎么让智能体记得做过什么、还剩什么、卡在哪。靠扩大上下文解决不了——窗口再大也会被塞满，而且越满越不准。工程上的答案是：把状态写到上下文之外，需要时再读回来。

## 1. 三个难点

拿一个真实场景对照：维护一个约 50 个 Python 文件的中型 Flask 应用，需要探索结构、识别技术债、追踪重构进度。

- **信息量超窗口**：几万行代码塞不进任何上下文，只能按需看。
- **状态跨会话**：重构持续数天，会话一断，进度就丢。
- **上下文质量**：每轮都要带回相关历史，但不能被无关内容淹没。

三个难点正好对应三件工具：按需探索用 `TerminalTool`，跨会话状态用 `NoteTool`，上下文筛选用上一篇的 `ContextBuilder`。

## 2. 笔记为什么用 Markdown + YAML

`MemoryTool` 面向对话记忆（工作、情景、语义），适合「发生过什么」；而项目式任务需要的是另一种记录：可被人直接打开看、可进 Git 版本控制、改动成本极低。所以 `NoteTool` 选了纯文件：

- **结构化记录**：YAML 前置元数据供机器解析，Markdown 正文供人阅读。
- **版本友好**：纯文本，天然能进 Git，diff 清晰。
- **低开销**：不需要数据库，一个目录就是全部状态。
- **灵活分类**：靠 `type` 与 `tags` 组织，不预设固定的目录树。

## 3. 存储格式

每篇笔记是一个 `.md` 文件，文件名即 ID：

```markdown
---
id: note_20250119_153000_0
title: 项目进展 - 第一阶段
type: task_state
tags: [refactoring, phase1, backend]
created_at: 2025-01-19T15:30:00
updated_at: 2025-01-19T15:30:00
---

# 项目进展 - 第一阶段

## 完成情况

已完成数据模型层的重构，主要改动包括：
1. 统一了实体类的命名规范
2. 引入了类型提示
3. 优化了数据库查询性能

## 测试覆盖

- 单元测试覆盖率: 85%
- 集成测试覆盖率: 70%

## 下一步计划

1. 重构业务逻辑层
2. 解决依赖冲突问题
```

另有一个 `notes_index.json` 汇总所有元数据：

```json
{
  "note_20250119_153000_0": {
    "id": "note_20250119_153000_0",
    "title": "项目进展 - 第一阶段",
    "type": "task_state",
    "tags": ["refactoring", "phase1", "backend"],
    "created_at": "2025-01-19T15:30:00",
    "updated_at": "2025-01-19T15:30:00",
    "file_path": "./notes/note_20250119_153000_0.md"
  }
}
```

索引的作用有三个：列表与检索不必打开每个文件；元数据集中管理，排序过滤都便宜；还能做完整性校验（索引里有、文件不在了，就是被误删）。

## 4. 七个操作

`create` 的流程最能说明这套设计：生成 ID → 组元数据 → 拼 Markdown → 落盘 → 更新索引。

```python
def _create_note(self, title, content, note_type="general", tags=None) -> str:
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    note_id = f"note_{timestamp}_{len(self.index)}"        # 时间戳 + 序号，天然有序

    metadata = {"id": note_id, "title": title, "type": note_type, "tags": tags or [],
                "created_at": datetime.now().isoformat(),
                "updated_at": datetime.now().isoformat()}

    md_content = self._build_markdown(metadata, content)
    file_path = os.path.join(self.workspace, f"{note_id}.md")
    with open(file_path, "w", encoding="utf-8") as f:
        f.write(md_content)

    metadata["file_path"] = file_path
    self.index[note_id] = metadata
    self._save_index()
    return note_id

def _build_markdown(self, metadata, content) -> str:
    yaml_header = yaml.dump(metadata, allow_unicode=True, sort_keys=False)
    return f"---\n{yaml_header}---\n\n{content}"
```

ID 用「时间戳 + 索引长度」，换来的是文件名本身可按时间排序——出问题时不用打开索引就能按顺序翻。

七个操作覆盖完整生命周期：`create`、`read`、`update`、`delete`、`search`、`list`、`summary`。真正决定长程效果的其实是 `type` 的约定，常用六种：

| type | 记什么 | 为什么单列一类 |
| --- | --- | --- |
| `task_state` | 阶段进度与当前状态 | 跨会话恢复时第一份要读的东西 |
| `conclusion` | 阶段结论 | 避免重复推导，也是决策依据 |
| `blocker` | 阻塞与问题 | 每轮都该优先带到上下文里 |
| `action` | 下一步计划 | 让「接下来做什么」不依赖记忆 |
| `reference` | 参考资料与出处 | 支撑结论的可核查线索 |
| `general` | 其他 | 兜底 |

## 5. 与 ContextBuilder 集成

笔记要进上下文，就得转成 `ContextPacket`。做法很直接——检索相关笔记，包一层打分：

```python
relevant_notes = self.note_tool.run({"action": "search", "query": user_input, "limit": 3})

note_packets = [ContextPacket(
    content=note["content"],
    timestamp=note["updated_at"],
    token_count=self._count_tokens(note["content"]),
    relevance_score=0.7,                      # 笔记整体给较高先验
    metadata={"type": "note", "note_type": note["type"]},
) for note in relevant_notes]

context = self.context_builder.build(user_query=user_input,
                                     custom_packets=note_packets, ...)
```

`relevance_score` 给 0.7 是个有意的先验：笔记是人或智能体主动写下的，信噪比通常高于原始对话，所以值得优先占预算。但也不能给 1.0——那样每轮都会把旧笔记顶上来，挤掉当前轮的新信息。

## 6. TerminalTool：即时检索的第二条路

RAG 是「先索引后检索」，`TerminalTool` 是「不索引，现场看」。三种典型场景：

```python
# 探索代码库
terminal.run({"command": "find . -name '*.py' -type f"})
terminal.run({"command": "grep -r 'class UserService' ."})
terminal.run({"command": "head -n 50 src/services/user.py"})

# 分析日志
terminal.run({"command": "tail -n 100 /var/log/app.log | grep ERROR"})
terminal.run({"command": "grep ERROR /var/log/app.log | cut -d':' -f3 | sort | uniq -c"})

# 预览数据
terminal.run({"command": "head -n 5 data/sales.csv"})
terminal.run({"command": "wc -l data/*.csv"})
```

对比一下就明白差异：`rag_tool.add_document("./project/**/*.py")` 要先把整个仓库索引一遍，耗时、占存储、还会随代码改动而过时；而 `grep`、`head` 这类命令拿到的是**此刻**的真实状态，成本只有一次进程调用。代价是每次都要现算，没有语义检索能力——所以两者不是替代关系，「索引做初筛、终端做精查」才是常见组合。

## 7. 四层安全

让智能体执行 shell 命令是强大但危险的能力。四道闸门从外到内收紧：

```python
ALLOWED_COMMANDS = {
    "ls", "dir", "tree",
    "cat", "head", "tail", "less", "more",
    "find", "grep", "egrep", "fgrep",
    "wc", "sort", "uniq", "cut", "awk", "sed",
    "pwd", "cd",
    "file", "stat", "du", "df",
    "echo", "which", "whereis",
}
```

1. **命令白名单**：只有只读命令，`rm`、`mv`、`chmod` 一律不在表内。白名单而非黑名单，是因为黑名单永远列不全。
2. **工作目录沙箱**：只能访问指定目录及其子目录，`cd ../../../etc` 会被拦。
3. **超时控制**：默认 30 秒，防止 `find /` 这类命令拖住整个会话。
4. **输出上限**：10MB 截断，避免一次 `cat` 把内存和上下文一起撑爆。

执行逻辑把四层串起来，并且**把所有异常都转成字符串**返回。这里用了 `shell=True`：管道、重定向、`grep -r` 这些能力全靠它，但同时命令串会被 shell 解析——所以白名单与目录沙箱不是可选项，而是这套设计成立的前提；换成 `subprocess.run([...])` 的参数列表形式就没有管道了。

```python
result = subprocess.run(command, shell=True, cwd=str(self.current_dir),
                        capture_output=True, text=True, timeout=self.timeout,
                        env=os.environ.copy())
output = result.stdout
if result.stderr:
    output += f"\n[stderr]\n{result.stderr}"
if len(output) > self.max_output_size:
    output = output[:self.max_output_size] + f"\n\n⚠️ 输出被截断（超过 {self.max_output_size} 字节）"
if result.returncode != 0:
    output = f"⚠️ 命令返回码: {result.returncode}\n\n{output}"
return output or "✅ 命令执行成功（无输出）"
```

保留 `stderr` 与返回码很关键：命令失败时，`No such file or directory` 这类信息正是模型调整命令行所需的观察，丢掉它模型只会在同一个错误上反复重试。

## 8. 长程实战：代码库维护助手

把三件工具拼起来，就是 `CodebaseMaintainer`。

<img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/helloagents-longhorizon-arch.png" width="85%" alt="代码库维护助手的三层架构" />

初始化时三个工具各占一块：`MemoryTool` 记对话，`NoteTool` 记项目状态，`TerminalTool` 守着代码目录（超时 60 秒）：

```python
self.memory_tool = MemoryTool(user_id=project_name)
self.note_tool = NoteTool(workspace=f"./{project_name}_notes")
self.terminal_tool = TerminalTool(workspace=codebase_path, timeout=60)

self.context_builder = ContextBuilder(
    memory_tool=self.memory_tool, rag_tool=None,
    config=ContextConfig(max_tokens=4000, reserve_ratio=0.15,
                         min_relevance=0.2, enable_compression=True))
```

`run` 是一条六步流水线，真正有意思的是第一步「按模式预处理」：

```python
pre_context = self._preprocess_by_mode(user_input, mode)   # 1. 按模式收集
relevant_notes = self._retrieve_relevant_notes(user_input) # 2. 检索笔记
context = self.context_builder.build(                      # 3. 构建上下文
    user_query=user_input, conversation_history=self.conversation_history,
    system_instructions=self._build_system_instructions(mode),
    custom_packets=self._notes_to_packets(relevant_notes) + pre_context)
response = self.llm.invoke(context)                        # 4. 调用模型
self._postprocess_response(user_input, response)           # 5. 后处理（可能写笔记）
self._update_history(user_input, response)                 # 6. 更新历史
```

三种模式各自只拉自己需要的证据，避免一上来就把所有东西都塞进去：

```python
if mode in ("explore", "auto"):
    structure = self.terminal_tool.run({"command": "find . -type f -name '*.py' | head -n 20"})
    packets.append(ContextPacket(content=f"[代码库结构]\n{structure}", relevance_score=0.6, ...))

if mode == "analyze":
    loc = self.terminal_tool.run({"command": "find . -name '*.py' -exec wc -l {} + | tail -n 1"})
    todos = self.terminal_tool.run({"command": "grep -rn 'TODO\\|FIXME' --include='*.py' | head -n 10"})
    packets.append(ContextPacket(content=f"[代码统计]\n{loc}\n\n[待办事项]\n{todos}", relevance_score=0.7, ...))

if mode == "plan":
    task_notes = self.note_tool.run({"action": "list", "note_type": "task_state", "limit": 3})
```

检索笔记时有个细节值得抄：**先按 `blocker` 类型取两条，再做语义搜索，最后合并去重**。

```python
blockers = self.note_tool.run({"action": "list", "note_type": "blocker", "limit": 2})
search_results = self.note_tool.run({"action": "search", "query": query, "limit": limit})
all_notes = {n.get("note_id") or n.get("id"): n for n in (blockers or []) + (search_results or [])}
return list(all_notes.values())[:limit]
```

理由是阻塞项与当前查询的词面相似度往往不高——「依赖冲突」和「重构业务逻辑层」几乎不共享词汇，但它比任何语义相关的笔记都更该被看到。这类「不管相关度都要带上」的信息，只能靠类型硬取。

## 9. 长程任务的操作规程

从这套实现里能抽出四条可迁移的经验：

- **状态外置优先于上下文累积**。凡是「下一轮还要用」的结论、阻塞、计划，都立刻写进笔记；凡是「这一轮用完就废」的中间输出，就留在对话里等它自然过期。判断标准只有一条：跨不跨轮。
- **笔记要有类型，而不是只有标签**。`tags` 用于检索，`type` 用于决策——「有 blocker 就先读 blocker」是程序逻辑，标签做不到这一点。
- **检索与探索要分工**。语义检索负责「我记得大概有这么回事」，终端命令负责「让我看看现在到底是什么样」。前者便宜但有延迟（索引可能过时），后者准确但每次都要算。
- **写入成本要低到愿意频繁写**。一个 Markdown 文件、一次 `write`，让「随手记一条」变得没有心理负担。如果写笔记需要建表、改 schema，实践中就不会有人写，长程任务也就退化成每次都从头开始。
