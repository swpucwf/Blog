# RAG 企业级实践

## 1. 三类模型的选型

一套 RAG 系统通常涉及三类模型，各司其职：

| 模型 | 职责 | 选错的后果 |
|---|---|---|
| Embedding | 把文本转成语义向量 | 召回阶段就找不到相关材料 |
| Rerank | 对初筛结果精排 | 相关材料被埋在后面 |
| LLM | 基于上下文生成答案 | 回答不准、不可追溯 |

### 1.1 Embedding：先看 MTEB，再看两个参数

MTEB 是嵌入模型的公共评测基准，覆盖检索、聚类、分类、重排、语义相似度等 8 大类任务，可作为选型的起点：

榜单之外，两个参数直接决定 RAG 表现：

- **维度**：越高语义细节越丰富，但存储与检索成本越高。768 维适合通用场景，医疗、法律等需要精细区分的领域可上更高维度；
- **上下文长度**：单次可处理的最大 token 数，超出部分直接截断。短句问答 512～1024 token 够用，论文、报告这类长文本至少要 2048 token。

常见选择可以按场景对号：中文短文档用 `bge-large-zh-v1.5` 这类社区验证充分的基线；需要混合检索选 `bge-m3`；长文档选支持 8K 上下文的模型；追求极致效果且预算充足则用云端 API。

### 1.2 Rerank：看排序质量，也看延迟

Rerank 模型对 Embedding 召回的候选做精排，输入是「查询 + 候选文档」，输出相关性分数。Agentset 的 Reranker Leaderboard 是参考之一，评测方式是先用 FAISS 取前 50 个候选，再由待测模型重排，同时关注三个指标：

- **nDCG@5/10**：相关文档是否排在前面，衡量「排得准」；
- **Recall@5/10**：相关文档是否被覆盖，衡量「找得全」；
- **Latency**：重排耗时，直接决定端到端延迟。

榜单同样是粗筛。工业上「分数高」与「好用」不总是一回事，选云厂商默认提供的 Rerank API 或社区常用的 `bge-reranker` 系列，往往比自己刷榜更省事。

### 1.3 LLM：私有化还是 API

| 方式 | 适合场景 | 注意点 |
|---|---|---|
| 私有化部署 | 数据隐私敏感、成本可控、需深度定制 | 关注显存与并发，7B/14B 级别常是性价比区间 |
| 云端 API | 快速上线、弹性扩容、持续跟进新模型 | 关注质量、价格、延迟、上下文窗口 |

LMArena 这类人类盲测榜单可以参考，但更实用的做法是**自建 20～30 条业务问题的测试集**，对候选模型跑端到端 RAG 评估——通用榜单在医疗、法律、金融等垂直领域与真实表现差异很大。

成本敏感时用「大小模型搭配」：简单问题走便宜的小模型，复杂问题才调用大模型。

## 2. 运行框架选型

不必从零搭建，现有框架分两类：

**低代码 / 可视化平台**：Dify、Coze、n8n、RAGFlow、FastGPT。优势是上手快、内置多模型接入与工作流编排；RAGFlow 这类在复杂版面解析上有专门优化，适合文档结构复杂的企业知识库。

**代码框架**：LlamaIndex 专为 RAG 设计，连接器与索引结构丰富，适合深度定制；LangChain 生态最全，适合复杂 Agent 与多模块编排，但学习曲线更陡。

选型原则很直接：团队技术储备有限、要快速验证，用低代码平台；需要定制检索策略、对接特殊数据源、优化性能细节，用代码框架。两者也可以组合——低代码验证可行性，代码框架做生产部署。

## 3. 评测：先建最小闭环

评测不必一上来就搭全套体系。一个务实的组合：

- 检索侧用 `Recall@K + MRR@K`，同时看覆盖面与排序质量；
- 生成侧用 `ROUGE-L` 或 `BertScore` 做基线，再用 LLM 裁判看相关性、完整性、忠实度；
- 用「评测 → 发现问题 → 调策略 → 再评测」循环迭代。

指标细节、RAG 三元组与 Ragas 工具，见[系统评估与高级 RAG 架构](/source/agent/RAG技术全栈/9-系统评估与高级RAG架构)；这里只强调一点：没有自己的测试集，评测就只是抄榜单。

## 4. 五个企业级案例

### 4.1 语义缓存：砍掉重复查询

生产环境里大量查询是重复的（客服反复被问「如何退款」），每次都走向量检索与 LLM 调用，成本高、延迟长。

做法是在用户查询与知识库之间加一层语义缓存：用嵌入模型把查询向量化，与缓存中的历史查询比相似度（欧氏距离阈值 0.35 一类），命中则直接返回缓存结果。

一个关键设计：**缓存的是检索结果，不是 LLM 的最终回答**。直接缓存回答会让「用简单语言解释」这类个性化要求失效。实测中相似查询的检索耗时从 0.057 s 降到 0.016 s，大规模场景下可减少 90% 以上的重复访问。

### 4.2 多格式文档解析

企业知识散落在 PDF、PPT、EPUB、HTML 中，传统预处理要么只支持单一格式，要么在转换时丢掉表格与标题层级。

做法是用 Unstructured 统一分区，输出带语义标签的元素（正文、标题、表格），再用 `chunk_by_title` 按章节切块、合并过短片段。解析质量直接决定后面所有环节的上限——这一步省下的功夫，后面用多少提示词都补不回来。

### 4.3 企业文档问答：精度与可追溯

Enterprise RAG Challenge 的冠军方案值得拆开看。任务是 2.5 小时内解析 100 份、每份最多 1000 页的年报，回答 100 个精确问题，且必须给出页码引用。

关键设计有四条：

- **解析用 Docling**，针对跨页表格、嵌套表格、多栏布局做修复；
- **按公司建独立向量库**，避免查询 A 公司时召回 B 公司的信息；
- **检索三步走**：向量取 Top30 → 提取父页面去重 → LLM 重排，两路分数按 0.3:0.7 融合；
- **按答案类型分模板**：数字类问题走「识别指标 → 定位表格 → 提取数值 → 校验单位 → 交叉验证」五步，输出结构化结果并附页码。

值得注意的是，小模型（Llama 8B）也能超过 80% 的参赛者，说明**流程设计比模型规模更决定上限**。

### 4.4 AIOps：图文混合数据

运维文档里不只有文字，还有监控曲线、架构图、性能截图。只处理文字的 RAG 回答不了「CPU 超过 80% 怎么办」这类需要看图的问题。

做法是双通道入库：OCR 提取图中文字（标题、坐标轴标签），再用多模态模型生成图片描述（「折线图显示 CPU 在下午 3 点达到峰值 90%」），与正文一起索引。

检索侧用 BM25（文档块 + 路径过滤）与向量检索双路召回，再用 Rerank 精排；生成分两步，先基于 Top6 生成覆盖面完整的初稿，再结合 Top1 突出核心答案。加入元信息与二次优化后，准确率各提升约 2%。

长文档还用 BM25 做上下文压缩：按句子与查询的相似度筛选拼接，50% 压缩率下准确率 86.48%，比通用压缩工具更快。

### 4.5 多源数据融合：结构化优先

KDD Cup 2024 的冠军方案展示了「知识图谱 + 网页」的协同：网页用父子块检索（子块 200 token 检索、父块 500～2000 token 生成），结构化数据通过 Mock API 查询。

核心策略是**结构化数据优先**：先调知识图谱 API，只有在返回无效时才回退到网页检索。能给出确定性答案的问题（如「诺兰的出生年份」）直接输出，不经过生成；需要网页信息时才走检索 + 分步推理。这大幅降低了幻觉，也提升了响应速度。

## 5. 演进方向

- **Graph RAG**：先抽取实体与关系构建知识网络，再按主题分组、生成摘要，回答需要跨文档串联的问题。与传统 RAG 是分工关系，不是替代。
- **Multimodal RAG**：图像、音频、文本分别编码到共享语义空间，支持用图或描述反向检索，适合运维、医疗等需要图文对照的场景。
- **Late Chunking**：先让长上下文模型编码整篇文档（每个 token 已「看到」全文），再对 token 向量做分块池化。相比「先切后编」，跨段落的指代关系不会丢。

在 BEIR 的长文档数据集上，Late Chunking 带来显著提升；短文本场景则与传统切分持平——**文档越长，收益越大**。代价是推理时间增加 10%～20%。

- **Agentic RAG**：检索从固定步骤变成 Agent 可反复调用的工具，具备规划、决策、自评、改写四种能力，详见[技术全栈的评估与进阶架构](/source/agent/RAG技术全栈/9-系统评估与高级RAG架构)。

## 6. 共同原则

五个案例放在一起，能提炼出几条稳定结论：

1. **数据处理决定上限**：解析、分块、元信息这三步省不得；
2. **混合检索 + 重排是标配**：单路召回几乎总是不够；
3. **结构化数据优先**：能用确定性查询回答的，不要交给生成模型；
4. **按答案类型设计输出**：数字、布尔、字符串用不同模板，可追溯性和准确率同时提升；
5. **流程优于模型规模**：小模型配好流程，能打赢大模型配差流程。

## 写在最后

企业级 RAG 的差距很少来自某个新模型，多来自这些不起眼的工程选择：缓存什么、怎么切块、先查哪个数据源、答案怎么组织。两篇框架实战（LangGraph 客服、LlamaIndex 知识库）与这一篇合起来，覆盖了从选型到落地的完整视角。
