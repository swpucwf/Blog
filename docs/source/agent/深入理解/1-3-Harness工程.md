# Harness 工程：模型之外的竞争力

## 1. 从能跑的 Demo 到可靠的产品

ReAct 循环证明了基本机制有效，但也暴露了明显的脆弱点：模型可能编造不存在的工具或参数、选错工具，遇到错误无法自我恢复。一个能跑的 Demo 和一个可靠的产品之间，隔着巨大的鸿沟。

这些脆弱点正是 **Harness 工程**要解决的问题。把 LLM 抽象为 **Model**，把 Agent 边界内负责支撑模型运行、以及模型与环境交互的代码、配置和服务统称为 **Harness**：

> **Agent = Model + Harness**
>
> **Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**
>
> **Agent ↔ Environment**

最小 Demo 只需要 Model，以及能构造上下文、暴露工具的 Harness；生产系统还要在同一边界内加入约束、验证与纠正。

**Harness 不是「模型之外的一切」**，而是 **Agent 边界内、模型之外**的运行与治理层。它协调 Model 与 Environment 的交互，但不包括环境本身：工具定义、调用适配器、沙箱的权限与重置机制属于 Harness；沙箱内随行动变化的文件与进程、外部数据库、网页、用户与物理世界属于 Environment。物理部署位置不能决定概念归属——即使仿真环境与 Agent 跑在同一进程，它仍然是 Environment。

## 2. 五个功能，一个闭环

| 功能 | 职责与核心原则 | 例子 |
|---|---|---|
| **Context** | 为模型提供感知信息；信息要充分，让每个决策点都基于足够信息 | 系统提示词、知识库、状态栏、旁路查询 |
| **Tools** | 为模型提供观察与行动手段；接口要清晰，命名直观、参数有例子、边界有说明 | MCP 工具、代码解释器、搜索工具 |
| **Constrain** | 设定行为边界；故障安全默认值，所有能力默认关闭，必须显式开放 | 工具执行前需要用户授权 |
| **Verify** | 自动判断操作结果对错；安全检查只看结构化数据，不看模型自由生成的文本 | Linter、类型系统、结果校验 |
| **Correct** | 发现问题时自动修正或回退；确认无法恢复前不暴露中间态 | 静默重试、接续生成、连续失败熔断 |

前两项让 Agent **能做事**——理解任务并采取行动；后三项让它 **不做错事**——约束预防错误，验证发现偏差，纠正让闭环形成。它们不是独立于上下文与工具之外的东西，而是确保上下文与工具在生产环境中可靠运转的工程实践。

在 Agent 产品的成熟度曲线上，两类功能的重要性并不对称。早期框架主要关注上下文与工具：给模型工具、给模型上下文，让它能做事。生产级系统的重心已经转向约束、验证与纠正：确保调用安全、上下文经过管理、错误可纠正。

以 Claude Code 为例，它的 Harness 绝大部分代码都是约束、验证与纠正，而非上下文与工具。工具本身（文件读写、命令执行、搜索）只是一小部分，围绕工具构建的保障机制才是核心：流程状态管理、多层上下文压缩、权限分类、熔断器、错误恢复与回滚。

**行业正在从「能做事」向「可靠地做事」转变，Harness 工程因此成为核心竞争力。**

## 3. 工程范式的五层演进

回顾 AI 应用工程的发展，可以看到一条清晰的弧线：

1. **提示工程**：优化输入给模型的自然语言指令，提升输出质量；
2. **上下文工程**：系统性管理模型能看到的所有信息——系统指令、工具定义、对话历史、外部知识；
3. **Harness 工程**：从「模型能看到什么」扩展到「Agent 如何组织模型运行并与环境交互」，涵盖工具接口、约束、验证、反馈循环与错误恢复；
4. **Loop 工程**：从单次运行扩展到跨轮次的持续自主运转——谁来发现下一件该做的事、何时验证、何时才算真正完成；
5. **Graph 工程**：把 Agent 循环、确定性程序与人工审批组织成显式执行图，节点承担能力，边规定路由与依赖，结构化状态沿边传递并在关键边界持久化。

五个阶段不是替代关系，而是层层包含：提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集，Loop 工程又是 Graph 工程的子集——单个 Agent 循环正是执行图中的一个节点。

每一层都在扩展工程师的关注范围。**当各家模型能力越来越接近、不再是决定性差异时，竞争优势就转移到了模型之外的工程实践。**

一个例证：LangChain 在 Terminal Bench 2.0 上的得分从 52.8% 提升到 66.5%，从排行榜 30 名开外跃升至前 5，改变的不是模型，而是 Harness——让 Agent 自动检查执行结果、检测重复循环、优化思考策略。

## 4. 三条构建原则

成功的 Agent 系统通常遵循三个原则：

**保持简单**。从最简单的方案开始，只在确实必要时增加复杂度。直接的 API 调用优于复杂框架，清晰的代码优于聪明的抽象——每多一层抽象，都会成为以后调试时的新盲区。

**保持透明**。明确显示规划步骤、执行日志与决策轨迹。这不只是为了调试，也是让用户建立信任的前提：黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。

**设计好工具接口（ACI，Agent-Computer Interface）**。从 Agent 视角设计接口，而不是从程序员视角设计传统 API。命名与参数要直观，容易误用的地方要从设计上让错误无法发生——SIM 卡的缺角让卡片只能从一个方向插入，微波炉门没关好就绝不加热。这种「用设计消除错误」的思路叫**防呆**（Poka-yoke）。模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性错误。

## 5. 模型怎么选

模型是 Agent 的智能基座，选对模型往往比优化提示词更有效。模型迭代很快，这里给的是选型思路，不是具体版本推荐。

**闭源模型**：OpenAI 与 Anthropic 是 Agent 开发中最常用的两家，能力通常领先，但成本较高且受 API 策略限制。不要只看排行榜，**要在自己的任务上做评估**。

**开源模型**：与闭源模型的差距在数月量级，成本显著更低，可私有化部署、支持微调，适合成本敏感或有数据合规要求的场景。不同模型的工具调用能力差异很大，选型前务必在具体场景中测试。

**能力之外，还要看策略边界**。模型在基准测试中具备某种能力，不意味着产品允许用户调用：厂商会对网络安全、模型蒸馏、隐私数据、高风险操作设置不同边界；同一个任务在聊天产品、Coding Agent 与 API 中也可能得到不同结果。选型不能只比准确率、价格与速度，还要在真实任务上测试：模型是否愿意执行、接口是否暴露所需能力、服务条款是否允许这种使用。

**绝大多数 Agent 需要支持思考的模型**。多步思考、工具选择等复杂决策，不带思考能力的模型往往表现很差。只有单步简单任务，或 Computer Use 中点击固定位置的简单操作，才可能例外。

**关注输出速度与多模态**。Agent 往往需要多轮推理，每轮都要等待输出完成才能执行下一步；如果一个任务需要 20 轮，每轮慢 2 秒就是多等 40 秒。需要理解图片、音频或视频时，多模态就是硬性要求。

## 6. 与后续内容的关系

Harness 五要素是「构建部分」内部的一个观察视角，不是覆盖全书的另一套目录。它与后续内容大致对应：

| Harness 要素 | 主要内容 | 安全关注点 |
|---|---|---|
| 上下文管理 | 提示工程、状态栏、压缩、Skills | 提示注入、上下文污染 |
| 上下文管理（跨会话） | 用户记忆、RAG、结构化索引、Agentic RAG | 敏感信息暴露、隐私 |
| 工具接口与约束 | 工具分类、权限、MCP、主动发现 | 误操作、未授权访问、不可逆操作 |
| 验证与纠正 | Coding Agent 的 Harness、测试驱动、代码化规则 | 身份冒用、责任归属 |

交互模态（语音、Computer Use、机器人）扩展的是观察与动作空间本身；评估、后训练与持续进化讨论的是「怎么知道 Harness 建对了、怎么让它持续变好」；多 Agent 则把单个 Harness 换成协作结构。

安全不按章划分，而是贯穿全书的横切关注点，按上下文层、执行层、数据层三层组织。

## 7. 补记

Harness 最容易走两个极端：一是把它理解成「越复杂越好」，堆出一套固定工作流，遇到例外就继续加节点，最终通用性越来越差；二是把它理解成「模型变强后就会消失」，于是不愿投入工程约束。两种理解都忽略了同一个事实：**Harness 的价值随模型能力边界移动**。模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

判断一个 Harness 设计是否合理，可以看三个问题：它是否只固化必须始终成立的边界（权限、审计、不可逆操作）；它是否把边界内的决策空间还给模型；它是否有可回滚、可验证的失败路径。
