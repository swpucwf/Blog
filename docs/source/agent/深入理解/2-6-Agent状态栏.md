# Agent 状态栏

## 1. 一个类比：手机顶部状态栏

Skills 解决「Agent 具备哪些可按需加载的能力」；状态栏解决另一个问题：如何让 Agent 随时看到任务进度、环境变化、工具调用计数等**运行时状态**。

提示工程给的是静态指令，Agent 在执行过程中还需要动态感知自身状态与任务进展。框架把这些信息整理成结构化摘要并注入上下文，这就是 **Agent 状态栏**。

<p>图 1：Agent 状态栏架构</p>

最好的类比是操作系统状态栏：手机顶部始终显示时间、电量、信号、通知数量。这些不是 App 的主界面内容，但随时瞥一眼就能掌握设备状态。Agent 状态栏对模型起同样作用：它不是对话主体，而是框架在上下文末尾持续注入的状态摘要——「已经打了 3 次电话」「当前时间 10:30」「TODO 还剩 2 项」。

## 2. 理论基础：检索而非推理

状态栏有效，源于注意力机制的一个本质特性：**上下文学习更像检索，而非推理**。模型擅长从已有内容中查找信息，却不擅长在一次前向传播中主动归纳与总结。这里说的是单次前向如何处理已有上下文，不否定模型可以通过思维链完成多步思考。

一个形象说法：**上下文窗口是一台只有一半的检索引擎**。检索那一半非常强——问什么，注意力就能从成千上万个 token 里把相关记录捞出来，相当于把 RAG 内置进每一次前向传播。但它缺了「提炼层」：上下文里的内容不会被自动数一遍、建索引、总结成结论；任何「关于这些内容的结论」——一共多少条、有没有超标、进展到哪一步——模型每次要用，都得从原始记录现算，代价随内容量增长。

考虑一个场景：系统提示词要求拨打每个商家不超过 3 次。但打了 3 次后，Agent 经常数不清，又打第 4 次，甚至陷入循环。根源是「已经打了几次」没有被提炼出来，而是以原始通话记录分散在上下文里；模型每次决策都要花额外思考 token 扫描、重新统计，效率低且错误率高。

如果在每次电话工具结果里直接标明累计次数（「本次是第 3 次呼叫该商家」），模型立刻发现已达上限，不再继续。

**状态栏的本质，是把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。** 原始轨迹高度冗余——大量 token 只包含少量状态信息；状态栏以极低的额外成本，呈现原本需要扫描数千 token 才能获得的信息。

此外，长上下文里注意力资源有限。上下文越长，关键信息越可能得不到足够权重；早期设定的目标与约束容易被后续工具结果淹没，模型还会过度关注最近内容，对中部信息产生衰减。状态栏把关键元信息放在上下文末尾，空间上更接近即将生成的新 token，能获得更高注意力权重——这是一种「强制性的注意力引导」。

## 3. 状态栏里放什么

**任务规划**：复杂多步任务轨迹很长，Agent 容易关注局部子任务，忘记原始诉求、核心约束与后续工作。把 TODO 列表放在轨迹末尾，持续提醒当前进展与后续目标。

**事件的侧信道信息**：为每个事件附加元数据——精确时间、地理位置、距上次回复的间隔。这些不在主数据通道中传递、但对理解事件很有帮助的辅助信息，让模型理解时序关系与环境背景。

**环境当前状态的观察摘要**：动态环境信息（系统时间、工作目录）、异常操作提醒（「该工具已被重复调用 N 次」）、从隐式状态到显式观察的转换。这一原则同样适用于人类界面：CLI 与 GUI 都致力于让用户清晰感知系统当前状态。

事件的侧信道信息通常随事件追加；任务规划与环境状态则随任务推进不断更新。这些动态信息如何写入会话历史，直接关系 KV Cache 代价。

## 4. 放在上下文的什么位置

一个重要的实现细节：状态栏在 API 层是作为**一条 user 角色的消息**插入上下文末尾的，而不是修改开头的 system 消息。原因正是 KV Cache 约束：改 system 会破坏整个前缀缓存。

这里的 user 角色只是 API 协议层的技术选择，不等同于「来自终端用户的输入」。Harness 是借用 user 这个槽位，注入由框架自动生成的状态信息——内容并非来自真实用户。

```text
messages: [
  { role: "system", content: "You are a customer service assistant..." },  ← 固定
  { role: "user", content: "Help me cancel my Xfinity plan" },
  { role: "assistant", content: null, tool_calls: [...] },
  { role: "tool", content: "Call log..." },
  ...
  { role: "user", content: "Can you call them again to follow up?" },
  { role: "user", content: "<agent_status>
      Current State:
      - phone_call invoked 3 times (Xfinity: 3/3 max)
      - Current time: 2025-09-14 10:30:45
      - TODO: [1] Cancel plan (in_progress)
    </agent_status>" }
]
```

最后一条 role 是 `user`，内容却是框架生成的元信息，用 `<agent_status>` 包裹以便模型识别。它在最末尾，紧邻即将生成的新 token，因此注意力权重最高；又因为是追加而非修改，前面已缓存的内容不受影响。

## 5. 更新的两种实现与缓存代价

「追加不破坏缓存」只在单次注入时成立。状态会变——下一轮 TODO 完成一项、计数加一次，旧状态就过时了。两种更新方式各有代价：

**每轮替换**：每次调用前移除上一轮状态，在末尾追加最新状态。上下文中只有一份状态，永远最新；但移除旧状态会让其后所有缓存失效——与「动态时间戳」同一失效机制，区别是状态在末尾，失效范围通常只覆盖上次注入后新增的一轮，整个前缀仍可复用。

**持久追加**：状态一旦注入就永久留在轨迹中，每轮只在末尾追加新状态。Claude Code 的 `<system-reminder>` 采用这种方式——历史状态保留在会话记录中，从不删改。对缓存完全友好，代价是陈旧状态累积，既占 token，也要求模型自己关注「最新一条」而忽略旧状态。

怎么选？设每条状态为 \(S\) token，两次更新间新增后缀为 \(R\) token，预计更新 \(N\) 次，缓存输入单价为普通输入的 \(\alpha\) 倍。忽略共有成本：

- 替换成本约 \((N-1)(1-\alpha)R\)；
- 追加成本约 \(\alpha S N(N-1)/2\)。

当 \(\alpha SN/2 < (1-\alpha)R\) 时倾向追加，否则倾向替换。粗略判断：**状态很小、两次更新间消息很多、会话长度受控 → 持久追加；状态较大、更新频繁或轨迹很长 → 每轮替换**。实际还要结合服务商计费与命中率。

## 6. 几种实用技术

- **时间戳跟踪**：以 `[2025-09-14 10:30:45]` 格式加在用户消息与工具响应前，不是放进系统提示词。让 Agent 理解时序关系，也为调试审计提供信息；配合时间模拟，能理解「昨天的文件」与「今天的修改」。
- **工具调用计数器**：维护全局字典，记录每个工具调用次数，在响应中标注 `Tool call #3 for 'read_file'`。显式计数能触发模式识别：第一次失败检查路径，第二次列目录，第三次主动放弃并寻找替代方案。深层价值是隐式的成本感知。
- **TODO 列表**：提供 `rewrite_todo_list` 与 `update_todo_status` 两个工具。每项含唯一标识、内容、状态（pending/in_progress/completed/cancelled）与时间戳。TODO 起外部记忆作用；实验数据显示，启用后平均 15 次迭代完成任务，禁用时需 21 次且经常遗漏子任务。
- **详细错误信息**：四层内容——错误类型与描述、完整参数 JSON、调用栈、针对性修复建议（如 `FileNotFoundError` 时建议验证路径、检查工作目录、用绝对路径）。启用后，Agent 在错误场景找到替代方案的成功率从 60% 提升到 95%。
- **系统状态感知**：注入当前时间、工作目录、操作系统、Shell、Python 版本。工作目录尤其关键——执行 `cd` 后自动更新，确保后续操作在正确上下文；系统信息让 Agent 做出平台相关决策（Linux 用 `apt`，macOS 用 `brew`）。

这些技术协同会产生涌现效应：时间戳与计数器结合，让 Agent 理解操作频率与时间分布；TODO 与系统状态结合，让它按环境调整策略；详细错误与计数器结合，让它在多次失败后不仅换策略，还能理解失败原因。

## 7. 两点注意事项

**状态栏尽量用代码维护。** 实在要用 LLM，也要逐条抽取、再由代码汇总，绝不要让它一次性批量统计。实验发现：**模型几乎无条件相信状态栏**——你写「打了 3 次」，它就当真，不会自己重算。LLM 做数量统计本来就容易出错。这也意味着状态栏投毒风险值得认真对待。

**谨慎删除原始上下文。** 状态栏是对原始上下文的一次**有损投影**，只提前算了「你预想会被问到」的维度。如果状态栏够用（计数、状态跟踪），可以把原始记录整段删掉，节省大量 token；但只要有一个问题涉及未计算的维度，仅保留状态栏就会让准确率断崖式下降。

## 8. 补记

状态栏与压缩是同一枚硬币的两面：状态栏把算好的结论**加**进上下文，压缩把臃肿的原始记录**换**成结论。两者都在给「只有一半的检索引擎」补上提炼层，区别是状态栏多由代码确定性地维护，压缩多用一次 LLM 调用蒸馏。

设计状态栏时，先问「哪些结论会被反复使用」。只算一次、用很多次的量（计数、进度、环境），值得放进状态栏；只用一次的细节，留在原始记录里即可。
