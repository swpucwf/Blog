
## 1. Agent 状态栏：通过元信息增强 Agent 轨迹管理

### 1.1 概念引入
![](https://i-blog.csdnimg.cn/direct/f86cd843e22241b3b26a0caae68d8252.png)


Skills的元数据注入通道是通用元信息注入机制，也就是**Agent状态栏**。

-   提示工程解决静态指令；状态栏用于给Agent同步**动态任务状态、执行进展**。
-   问题背景：复杂任务下Agent容易循环、遗忘状态、偏离目标，根源是缺少对任务进展与环境状态的感知。
-   类比：类似手机操作系统状态栏，不是主体对话内容，是持续追加到上下文末尾的结构化状态摘要。
-   和System Prompt区别：系统提示词是固定员工手册；状态栏是实时仪表盘，随任务持续更新。

### 1.2 Agent状态栏理论基础

- 模型注意力机制特点：上下文窗口检索能力强，但**没有自动提炼、统计、建索引的能力**。所有统计、计数需要每次从原始历史中重新扫描计算，开销随上下文长度上涨，容易出错。
- 状态栏核心思想：**将分散在轨迹中的隐式状态，提炼为显式结构化知识**，减少模型扫描原始长文本的负担；把关键信息放在上下文末尾，获得更高注意力权重，实现强制性注意力引导。

> 底层归类：属于**上下文蒸馏（Context Distillation）**。 量化实验结论：

1.  弱模型：状态栏显著提升准确率，涨幅可达40~54个百分点；
2.  强模型：准确率本身较高，主要收益是降低思考token、延迟与成本，下降约一个数量级；
3.  核心变化：无状态栏时思考开销随上下文变长持续增长；启用状态栏后开销基本恒定。

三条落地经验：

1.  **优先用代码维护状态栏，不要交给大模型批量总结**。长历史批量统计LLM容易出错；能用正则/代码计算；如需LLM，只能逐条抽取，代码汇总。
2.  **状态栏属于有损投影**，删除原始上下文前，确认覆盖所有查询维度。若查询维度不在状态栏字段内，准确率断崖下跌；复杂多跳推理场景不适合仅保留状态栏。
3.  **监控状态栏准确率作为生产指标**。模型几乎无条件信任状态栏；数据错误会直接传导到最终结果；警惕状态栏投毒，数据源必须可信，不可被外部污染。

更深层原理：状态栏向模型注入**仅靠推理无法得到的外部观测事实**。模型本身只能重组已有上下文信息；外部仪器观测得到的真实状态信息，才可以突破原有能力天花板。交互是除长思维链、多采样之外的第三条提升路径。

### 1.3 Agent状态栏构成

状态栏包含四类信息：

1.  **任务规划**：TODO清单，记录任务分解、进度、原始目标，防止局部子任务偏离整体目标。
2.  **事件侧信道信息**：时间、间隔、地理位置等辅助元数据，还原事件时序和场景背景。
3.  **环境当前状态**：系统时间、工作目录、工具调用次数、异常告警，隐式状态转为显式记录。
4.  **可用能力清单**：Skills元数据列表，复用同一末尾注入通道，仅在安装/卸载Skill时更新。

-   侧信道信息、能力清单：变动少，对KV Cache友好；
-   任务规划、环境状态：高频动态更新，追加在上下文末尾，更新策略决定缓存成本。

### 1.4 上下文插入位置
![](https://i-blog.csdnimg.cn/direct/dea9970c73744bf18b433e43e7998184.png)


API层面，状态栏是**user角色消息**追加在上下文末尾，不是修改system消息。

> 注意：user角色仅为API技术槽位，并非终端用户输入，是框架自动生成，使用`<agent_status>`标签包裹。 优势：不改动前置system内容，原有KV Cache前缀保持稳定；末尾位置获得最高注意力权重。

### 1.5 两种状态更新实现 & 缓存代价

1.  **每轮替换**：删除上一轮状态消息，末尾追加最新版本。
    -   优点：上下文只保留最新状态，信息无歧义；
    -   缺点：删除旧消息会造成其后缓存失效；适合短会话、状态内容量大场景。
2.  **持久追加（Claude Code方案）**：历史状态永久保留，每轮新增状态追加至末尾，不删不改。
    -   优点：完全不破坏KV缓存；
    -   缺点：陈旧状态不断累积，占用token，要求模型识别最新状态；适合长会话、高频更新场景。

取舍规则：长轨迹、频繁更新 → 持久追加；短轨迹、状态内容大 → 每轮替换。

### 1.6 Agent状态栏实用技术

5项可独立开启的状态栏技术，组合使用会产生涌现效果：

1.  **时间戳跟踪**：给消息附加时间戳，不写入system，避免缓存失效；用于时序理解、调试审计，支持时间模拟。
2.  **工具调用计数器**：统计各工具调用次数，让Agent感知重试次数、感知成本，多次失败后主动切换策略或终止。
3.  **TODO列表管理**：专用工具更新任务清单，作为外部记忆；减少子任务遗漏，降低迭代次数。
4.  **详细错误信息**：包含错误类型、参数、调用栈、修复建议；提升异常场景下寻找替代方案的成功率。
5.  **系统状态感知**：注入当前环境信息（时间、工作目录、操作系统等），适配不同平台执行命令。

### 1.7 从读数到策略：Agent物理时间感知

状态栏可以提供时间、调用次数读数，用来构建Agent**时间感**，分为三轴：

-   紧迫度：根据时间预算调整投入力度；
-   坚持度：区分不可逾越的障碍与临时失败，判断任务是否完成；
-   警觉度：监控工具响应时长，识别超时、异常返回。

关键结论：**仅提供原始读数不足以改变Agent行为**，必须配套对应的操作策略说明。只给时间戳，模型不会自动调整执行节奏；需要「状态读数+操作手册」成对注入。 该缺陷属于模型后训练普遍短板，可通过推理阶段状态栏+策略说明补齐；也可通过稠密奖励蒸馏进模型权重。

### 1.8 设计哲学

状态栏方案无侵入，无需模型微调，直接兼容各类大模型；元信息人类可读，便于调试排查；各项能力可以逐步叠加落地。
