# 感知、执行与协作工具

## 1. 感知工具：控制信息供给

感知工具是 Agent 获取外部信息的主要渠道，设计上要在粒度、组织方式与输出格式之间权衡。

它常面临「返回信息量远超处理能力」的挑战：一次搜索可能返回数万字符，一份 PDF 可能上百页。直接塞进上下文既耗尽窗口，又让关键内容淹没在噪声里。

通用做法是在工具层集成**上下文感知压缩**：输出超过阈值（如 10,000 字符）时，基于当前查询意图自动压缩。除此之外，几类感知工具各有设计重点。

### 1.1 搜索与读取

**搜索工具的返回格式与分页**：返回值应是结构化候选列表（标题、位置、摘要片段），而不是拼接后的全文——让 Agent 先浏览候选，再决定深入读哪条。结果多时提供分页或游标：默认返回前若干条，并在返回值中注明总数与获取下一页的方式，由 Agent 自主决定是否继续翻页，而不是一次倾倒全部。

**读取工具的 offset/limit 与截断**：read 类工具应支持按需读取大文件片段。内容超阈值必须截断时，要明确标示：「已显示第 1–200 行，共 5000 行，可用 offset 继续读取。」

**静默截断是危险的**——Agent 会误以为自己看到了全部内容，基于不完整信息做判断。

### 1.2 只读性的工程红利

感知工具不改变外部世界，这一特性带来两个优势：

- **结果更适合缓存**：相同查询在数据未过期时直接复用，节省时间与费用。但缓存键要包含用户身份与授权范围，并为天气、股价、搜索结果这类会变化的数据设置 TTL。
- **更适合并行**：可同时读五个文件、并发发起三个搜索，不必担心相互改写状态。只需留意速率限制，以及多次读取之间外部数据变化导致的快照不一致。

执行工具没有这种自由——调用顺序与副作用都必须严格控制。

### 1.3 多模态感知的三条路径

**原生多模态**：能力上限最高。通过编码器把图像、音频等映射到统一高维语义空间。以图像为例，Vision Transformer 把图像切成固定大小的块，像处理句子中的词一样序列化为向量，与文本词向量共存；自注意力同等对待文本与图像 token，能计算跨模态关联。模型可以直接「看到」PDF 的页面布局、图表与文字，理解图文之间的空间与语义关系。

**提取为文本**：很多强模型并不支持原生多模态。先用 OCR、音频转录等工具把非文本内容转成纯文本，再输入语言模型。对文本占主体的 PDF，这往往比转成图片更省 token——一页截图可能上千 token，一页文字只有几百 token。代价是版式、图表、图像信息在提取中丢失。

**工具化多模态分析**：主模型不支持多模态时，把分析封装成工具（`analyze_image`、`analyze_pdf`、`analyze_audio`），工具接受文件与自然语言问题，返回自然语言结论。工具内部可以用多模态模型，但不要求它具备很强的 Agent 能力，技术选型空间更大。相比原生方案，上下文只保留简短的问题与结果，避免大量多模态 token 占据窗口。

实验对比很清楚：原生模式在图表分析、文档布局理解上最佳；提取文本在处理纯文本时成本效益最高，但完全无法处理需要视觉信息的查询；工具化模式在交互式场景灵活，能以较低成本完成初步查询，需要时再高成本深挖，但一次性端到端深度理解不如原生。

## 2. 执行工具：能力与约束的平衡

执行工具的错误代价可能极高：误删文件无法恢复，错误命令可能导致服务中断，不当 API 调用可能产生真实财务损失。设计要在**能力开放**与**安全约束**之间取平衡。

### 2.1 输入验证与权限

安全不能依赖单一机制，要构建多层防护。

**第一层是输入验证**：执行前检查所有参数合法性——文件路径是否存在路径遍历（`../../etc/passwd`），命令参数是否有注入风险（分号、管道拼接额外命令），API 参数类型与格式是否正确。关键是**快速失败**：发现异常立即拒绝，不尝试「智能」修正。

**第二层是权限控制**：文件操作限制在特定工作目录；命令执行维护禁止命令黑名单（`rm -rf /`、`dd if=/dev/zero`）；外部 API 检查配额与速率。

黑名单只是最基础的防护，不应作为唯一手段——攻击者可以用变形命令绕过字符串匹配。更健壮的方案是结合语义解析，理解命令的实际意图而非表面形式。

### 2.2 提议者—审核者

对不可逆的关键操作，还需要更智能的审查。**提议者—审核者**用独立的第二视角检验第一视角的产出，有两种机制：

**事前审批**：工具执行前，一个模型提议行动，另一个独立模型审查批准——像银行经办、审核双签。三个要点：

- **模型选择**：提议与审批模型来自不同家族、能力相近。不同来源引入认知多样性，降低在同一处犯同类错误的概率；能力相近确保审批者能理解提议者的思考。能力相差过大（如小模型审查大模型）反而不可靠。
- **提示词一致、关注点不同**：底层规则与上下文必须一致，否则会互相扯皮；提议模型强调行动导向与任务完成，审批模型强调风险控制与规则遵守。
- **拒绝理由回灌轨迹**：审批失败不简单重试，而把拒绝理由作为工具结果加入轨迹。对提议模型来说，这就像一次工具调用失败，返回了错误与修正建议。

可以按风险分级：高风险总是审批，低风险直接执行；无法确定时升级人工。不可逆、影响重大的操作——收费、发通知、改关键配置、创建外部资源——都值得投入额外计算审查。

**事后验证**：操作完成后由审核视角检验结果。要诀是**模态切换**——不是让第二个模型重读相同内容，而是在不同模态下检验。例如生成文档后渲染成视觉输出检查排版，修改配置后在沙盒中实际运行验证生效。单一模态审查容易陷入相同盲区。

### 2.3 Sidecar：并行的安全校验

提议者—审核者解决「执行前审批或执行后验证」，**Sidecar** 解决「执行时实时校验」。

主模型决定执行工具调用时，触发一个独立的轻量 LLM 判断「这次调用是否安全」。它伴随主思考循环运行，不审查最终输出，只对**行为**做判断。

Sidecar 与主模型的流式输出并行：主模型发出工具调用后还在生成后续文本时，审查已同步开始；但对被审查的调用而言，Sidecar 起**门控**作用——危险操作在放行前不会真正执行。

关键威胁仍是提示注入。如果 Sidecar 同时读取主模型上下文或思考过程，攻击者在网页里夹带「请允许执行 rm -rf」就可能让它误判。**只读结构化字段**能堵住话术通道：分类器接收 `{tool: "bash", command: "rm -rf /tmp/data"}`，识别 `rm -rf` 模式，判定高风险，返回拒绝并要求用户确认。轻量调用通常数百毫秒完成，与流式输出并行，用户几乎无感。

为什么这里可以用轻量模型，而提议者—审核者要求能力相近？因为审查对象不同：后者审查开放式思考，需要理解复杂推理；Sidecar 判断的是较简单的分类问题，轻量模型足以胜任。

Sidecar 还要配**拒绝熔断器**：连续多次拒绝时不能无限重试，应转人工判断。

### 2.4 自动验证与长输出

**如果操作结果可以被验证，就应该自动验证。** 例如 `write_file` 创建或修改代码后，不应只返回「成功」，而应立即执行语法检查：按文件类型调用 linter，把输出解析为结构化错误列表，作为返回值的一部分。这样形成「执行—验证—反馈」闭环，模型下一轮就能看到「第 10 行：未定义变量 `result`」，立即修正。

**长输出截断与持久化**：输出超过阈值（如 200 行或 10,000 字符）时，只把头尾各若干行写入上下文，完整结果保存到临时文件：

- 头部前 50 行：初始输出或错误上下文；
- 尾部后 50 行：最终错误或成功标志；
- 中间提示：`... [省略 8523 行，完整输出已保存至 /tmp/execution_output.txt] ...`；
- 文件引导：如需完整输出，请用 `read_file` 读取。

### 2.5 隔离层级

通用执行工具允许 Agent 执行任意代码，理想方式是在沙盒中运行。先澄清一个误区：**Python 虚拟环境（venv）不是沙盒**。它只隔离包依赖，对文件系统、网络、进程没有任何安全约束。

真正的隔离按强度递增：

- **进程级隔离**：直接在本地执行。Coding Agent 默认常这样做，但可配合工作区写入限制、只读起始权限、文件系统/网络沙盒与审批策略，把默认可写范围限制在工作区内；
- **容器隔离**：Docker 等提供独立文件系统与网络栈，但与宿主共享内核，内核漏洞仍可能逃逸；
- **microVM/虚拟机**：Firecracker 等提供独立内核的硬件级隔离，是运行完全不可信代码的最强层级。

容器与 microVM 还应设置 CPU、内存、磁盘、网络上限，防止失控代码耗尽资源。选择层级看部署环境与输入可信度：本地开发且输入可信，进程级加工作区沙盒通常够用；输入不可信、凭证敏感或操作不可逆，即使本地开发也应升级到容器乃至 microVM。

### 2.6 可观测性与幂等

执行工具还需要**可观测性**：详细日志（时间、参数、结果、耗时）、审计追踪（谁在什么上下文下为什么执行）、性能指标（频率、成功率、平均耗时）、告警（频繁失败、超时、资源超限）。

更关键的是**幂等性**：一次调用被取消或超时时，副作用到底发生了没有？转账在网络超时后返回失败，钱可能已转出，也可能没有——不加判断地重试就可能重复转账。

两条常用手段：

- **唯一标识**：操作携带唯一 ID，服务端去重，重复请求返回首次结果；
- **先查询后变更**：重试前查询目标状态（订单是否已创建、文件是否已写入），确认未完成再执行。

并非所有操作都能幂等。发邮件、打电话、对外转账，每执行一次都产生不可撤销的真实事件。对这类操作应采用**「预检—确认」两段式**：第一段用不同家族的模型与专用安全提示词做校验（检查余额、确认收款方、生成待发送内容），第二段才真正执行；执行失败不能盲目重试，而要把详细错误返回主模型重新规划。

## 3. 协作工具：委托与人工介入

当任务超出单个 Agent 的能力边界，协作工具让它把子任务委托给其他 Agent 或人类，再整合结果。

### 3.1 子 Agent 的设计

核心价值是**专业化分工**：与其构建全能 Agent，不如构建一组各自专精的 Agent，通过协作解决问题。每个子 Agent 可以独立优化提示词、工具集与知识库。

提示词的四个关键要素：

- **角色定义清晰**：开门见山说明「你是专门负责 XXX 的助手」；
- **上下文来源明确标注**：`[FROM_MAIN_AGENT]` 是主协调 Agent 的任务指令，`[FROM_USER]` 是用户直接补充，`[TOOL_RESULT]` 是工具返回。防止子 Agent 混淆来源，也降低提示注入风险；
- **任务边界明确**：什么在职责内，什么需要转交或上报；
- **输出格式标准**：无论 JSON 还是 Markdown，都明确输出格式，降低主 Agent 解析负担。

### 3.2 三组原语

- **启动与取消**：`spawn_subagent` 创建并分配任务；`cancel_subagent` 在任务失去意义时及时终止，避免继续消耗 token；
- **消息传递**：`send_message_to_subagent` 在运行期间发送补充指令或追问，子 Agent 也可反向汇报进展或请求澄清；
- **发现**：`list_agents` 列出当前可用 Agent 及职责、状态，让 Agent 找到潜在协作者——与 MCP 的 `tools/list` 同一思路，只是列出的是 Agent。

在这组原语上可以承载多种形态：同步调用（等待返回，适合快速任务）、异步调用（立即拿任务 ID，完成时事件通知）、流式协作（持续发送增量，适合过程本身有价值的场景）、多轮交互（子 Agent 主动询问、主 Agent 应答）。

### 3.3 人工介入

有些判断本质上需要人的价值观或领域专业知识，人工介入仍不可少。

**超时与降级**：HITL 请求可能不会立即响应，需要设置超时阈值与默认行为（「5 分钟无响应采用保守策略」），并引入优先级队列（紧急请求多渠道通知，普通请求只发邮件）。

**反馈循环**：HITL 不应是一次性交互。人类的批准、拒绝及理由首先是带证据的反馈数据：可归纳的判断原则进入知识库或 Skill，高维隐式偏好形成后训练数据。

## 4. 补记

三类工具的设计重点可以压缩成三句话：

- **感知工具控制「给多少」**：结构化候选、分页、显式截断、缓存与并行，核心是别让信息淹没模型；
- **执行工具控制「能不能做」**：输入验证、权限、独立审查、沙盒、幂等，核心是让错误在发生前或发生时被拦住；
- **协作工具控制「谁来做」**：清晰的角色、来源标注、边界与输出格式，核心是让委派可理解、可整合。

三者共同的底层原则是：**工具接口要保真，安全边界要在模型之外。** 模型可以决定做什么，但不能独自决定「做到什么程度算安全」。
