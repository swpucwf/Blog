# 共享与不共享：两种上下文架构

第一篇把「上下文是否共享」列为最基础的架构决策。这一维度往下走，会落到两个很具体的问题：共享时角色如何切换，隔离时 Agent 之间靠什么交换产物、又靠什么互相控制。

## 1. 继承式协作

共享上下文的多 Agent 协作里，每个阶段都是一个独立 Agent（有自己的系统提示词与工具集），但它继承了前序 Agent 的完整轨迹——像接班的同事能翻阅前任留下的所有工作日志。

复杂任务中，Agent 的角色与职责常在阶段之间显著变化。若始终用同一套静态提示词，要么过于笼统缺乏针对性，要么把所有阶段的指导塞在一起变得冗长。多阶段角色转换的做法是：按当前阶段动态切换系统提示词与工具集，让每个阶段都以最合适的身份工作。

核心优势是信息不丢失，任何阶段的细节都能回溯；挑战则在于让当前 Agent 专注于自己的职责，而不被继承来的大量历史干扰——一个继承了「需求分析师」轨迹的「代码审查员」，很容易仍从需求角度而非代码质量角度思考。

## 2. 角色转换：替换提示词，还是加载 Skill

一个常被忽略、却直接改变架构的选择：角色转换究竟是**替换 system prompt**，还是**加载 Skill**？两者都能让同一模型在不同阶段采用不同行为规程，却不是同一种成本模型。

| 选择 | 规程载体 | 工具可见性 | 上下文 / KV Cache 影响 | 约束能力 |
|---|---|---|---|---|
| `transfer_to_agent` | 替换当前 system prompt，通常同时替换工具集 | 只暴露当前角色工具 | 每次切换都改变请求前缀，从变化点起的前缀缓存通常无法复用 | 强：越界工具在 schema 层就不可见 |
| Skill | 固定 system prompt 中的 Skill 目录，按需把 `SKILL.md` 追加到轨迹 | 通常暴露工具全集，或用稳定的工具搜索入口 | 静态前缀保持不变，Skill 内容落在轨迹末尾，已有前缀可继续复用 | 弱：Skill 是行为指令，硬权限仍需 Harness 门 |

选择规则可以总结成一句：角色差异主要来自**知识、流程与写作风格**时，优先用 Skill；角色差异涉及**权限、工具隔离、合规边界**，或需要在运行时强制禁止某类动作时，使用独立 Agent 或 `transfer_to_agent`，并在 Harness 层用代码限制工具调用。

这条规则也解释了为什么「多角色」不等于「多 Agent」：Skill 能解决的是行为规程切换，解决不了权限边界。

## 3. 不共享上下文：Agent 版的进程模型

不共享上下文才是真正意义上的多 Agent 协作。每个 Agent 是独立实体，有自己的上下文、轨迹与状态，彼此无法直接访问对方的「内心活动」，协作完全依赖三种通信机制。

把「通信机制即进程间通信」这条线索再往前推一步，会发现多 Agent 系统与操作系统的对应关系相当完整：

| 操作系统 | 多 Agent 系统 |
|---|---|
| 程序（可执行文件） | 静态前缀（系统提示词 + 工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork（创建子进程） | `spawn_subagent` |
| kill（发送信号） | `cancel_subagent` |
| ps（列出进程） | `list_agents` |
| 退出码与 `wait()` | 子 Agent 返回的结构化摘要 |
| 共享内存 / 消息传递 | 共享文件系统 / 消息 |

这套抽象并不新鲜：私有状态、异步消息、可创建新成员，正是 1970 年代 Actor 模型的基本设定，多 Agent 系统不妨看作它的 LLM 版本。因此操作系统与分布式系统的成熟经验，大多可以直接借用。

进程式隔离带来几项切实好处：每个 Agent 可独立开发与测试，新增能力不必改动现有代码，某个 Agent 出故障也不会把错误状态传染给其他 Agent，多个 Agent 还能真正并发——上下文完全独立，不存在资源竞争。

代价同样明显。最直接的是信息同步：各 Agent 如何对任务状态保持一致理解，信息在传递中会不会丢失或重复。调试也更难，出了问题要翻多个 Agent 的日志才能拼出完整过程。这使接口规范、数据格式与通信协议的设计变得至关重要。

隔离架构依赖两套与拓扑无关的基础设施：**共享文件系统**作为交换产物、与用户交换文件的持久媒介，构成数据平面；**通信与控制机制**支持消息传递、状态查询、执行终止与资源调度，构成控制平面。

## 4. 虚拟文件系统：四类区域

实际系统中，Agent 访问的并非单一存储，而是一棵**虚拟文件系统**：来源、生命周期与权限各异的存储被挂载到同一目录树下，Agent 通过统一的 `read_file` / `write_file` / `list_dir` 访问，底层可能是本地临时盘、持久对象存储、第三方云盘 API 或只读资源包。

这棵目录树相当于 Agent 的地址空间，四类区域则是权限各异的内存段：

- **Agent 专属工作区（Scratchpad）**：实例独享的私有目录，放中间产物、草稿与调试日志，生命周期与实例绑定，对其他 Agent 和用户不可见。它既避免临时文件互相覆盖，也让子 Agent 的试错留在本地，只把最终产物提交到共享空间——这是「子 Agent 返回结构化摘要而非全量轨迹」在存储层的体现。
- **多 Agent 共享空间（Shared Workspace）**：多方共同读写、且用户可见的协作区域，是隔离架构下交换产物的主要媒介。翻译场景里 Glossary Agent 写入术语表、Translation Agent 从中读取，用户也在此上传原件、下载交付物。生命周期与任务绑定，需要持久化，也是并发冲突的高发区，乐观锁与 worktree 隔离都作用在这里。
- **外部挂载资源（Mounted External Resources）**：用户授权接入的第三方信息源（Google Drive、Notion、企业 Wiki 等），经适配器映射为挂载点，Agent 读一篇 Notion 文档，底层是适配器调用对方 API。这一层有三项区别于本地存储的特性：访问受外部权限约束；延迟更高、一致性更弱，每次读取都是一次网络往返，只能按最终一致性对待；以按需只读为主，写回要谨慎，误写会污染用户的真实数据。
- **系统内置资源（Built-in System Resources）**：预置、对所有 Agent 只读共享的资源包，典型代表是 Skills——以文件形式组织的知识文档与脚本，挂在 `/skills` 等路径，按渐进式披露取用；此外还有参考手册、模板库与共享工具定义。全局共享、只读、跨会话稳定，可并发读取而无需并发控制。

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|---|---|---|---|---|
| Agent 专属工作区 | 仅该 Agent | 随实例销毁 | 读写 | 不需要（私有） |
| 多 Agent 共享空间 | 所有协作 Agent + 用户 | 随任务持续，需持久化 | 读写 | 需要（乐观锁 / worktree） |
| 外部挂载资源 | 视外部授权而定 | 由外部源决定 | 多为只读，写需谨慎 | 由外部源负责 |
| 系统内置资源 | 所有 Agent | 跨会话稳定 | 只读 | 不需要（只读） |

把四类区域统一到一棵目录树，正是「**文件路径作为通用接口**」的价值所在：Agent 间传递产物、主 Agent 向子 Agent 交接输入、乃至跨组织交换产物，传的都是轻量路径字符串，而不是把内容塞进上下文窗口。相当一部分并发冲突与信息泄露，恰恰源于把本应隔离的区域混置。

## 5. 控制平面

文件系统解决产物交换，协作还需要一条控制平面。`spawn_subagent`、`send_message_to_subagent`、`cancel_subagent`、`list_agents` 这组原语，对应进程世界的 fork、消息、kill 与 ps。

### 5.1 消息传递

最简形态是点对点：A 直接调用 `send_message_to_agent_b(content)`，适合拓扑固定、Agent 数量少的场景。Agent 增多且需异步并行时，点对点连接数随 Agent 数呈平方增长，还要求收发双方同时在线；此时应改用**消息总线**——Agent 把消息发布到总线，由总线按订阅关系转发，发送方无需知道消费者是谁。

无论点对点还是经总线，消息通常应携带结构化的**信封**：发送者 ID、目标（指定或广播）、消息类型（`task_assigned` / `status_update` / `result` / `terminate`）以及 JSON 负载。统一信封保证接收方可靠路由与解析，也让协作链路可追溯——这是多 Agent 调试的关键。

### 5.2 状态查询

这是控制平面最易被低估的一环。主 Agent 派出子 Agent 后，若无从获知其进展，既无法判断是否继续等待，也无法在阻塞时及时介入。

直觉做法是定义 `get_subagent_status(agent_id)` 查询接口。但这种拉取式接口并不实用：子 Agent 一经创建就开始执行，直到完成或失败自然会通知主 Agent，并不需要显式查询。更自然的做法是回到两大通信范式：

- **用消息传递获取状态**：主 Agent 发一条「进展如何」，子 Agent 在合适时机回复。发出消息不阻塞自己的执行，对方何时回复、是否回复是另一回事——像经理用即时消息问进度，而不要求下属立刻停手。子 Agent 也可以在关键节点主动汇报，若已架设消息总线，这就是往总线上发一条 `status_update`。
- **用共享文件系统获取状态**：最彻底的形态是**轨迹持久化**——子 Agent 把轨迹实时序列化为 JSON，追加写入日志文件（通常一会话一文件、一行一事件，即 JSONL）。主 Agent 无需任何上报协议，直接读文件就能看到它正在调哪个工具、最近一步在想什么、是否卡在反复失败的重试上。用进程的语言说，这相当于直接读另一个进程的内存。

但轨迹动辄数万 token，主 Agent 读完还得自己提炼，费时又费 token，不宜作为 Agent 间传递信息的主要方式。更合理的是**约定进度文件**：启动时约定「把进度写到 progress.md」，子 Agent 每完成一项就更新任务清单，主 Agent 随时读这个轻量文件即可。这相当于在共享内存里划出一小块约定格式的状态区，暴露的是提炼后的进度而非全部内存。进度文件还能用于**检测卡住**：文件最后修改时间超过 N 分钟没有变化，即可判定子 Agent 无活动并触发超时兜底。

### 5.3 执行终止

并行协作常出现「一个成功，其余不必继续」的情形。终止有两种强度，Unix 用户会认出这正是 SIGTERM 与 SIGKILL 的区别。

**优雅终止**是首选：主 Agent 发出 `terminate`，子 Agent 在当前步骤的安全点响应，先清理资源（关闭浏览器会话、写入未完成文件、释放锁），返回确认后退出。**强制终止**只是兜底：直接终止进程，仅在优雅信号无响应时使用，代价是可能留下悬挂资源与未完成写入。

还有一个问题：主 Agent 终止后，仍在运行的子 Agent 怎么办？最简洁的做法借鉴 Go 的 context——终止沿创建关系向下级联：取消一个 Agent，它派生的所有子 Agent 随之取消，从根上杜绝无人认领的孤儿 Agent。「在安全点检查终止信号」，对应的正是对 `ctx.Done()` 的轮询。反过来，若确实需要一个脱离主 Agent 长期运行的后台 Agent（类似 Unix 的 `nohup`），就让它从一棵新的生命周期树起步，显式声明不随父级终止。

### 5.4 资源与调度

操作系统的核心职能之一是分配稀缺资源。进程世界稀缺的是 CPU 时间与内存，Agent 世界稀缺的是 token 与并发额度。这项工作通常落在管理者 Agent 或运行时身上：启动子 Agent 时设定步数或 token 预算，超限即止；困难任务给强模型，机械任务给低成本模型；并发数设上限，避免几十个 Agent 同时耗尽配额；达到上限后，更紧急的任务可以打断执行中的子 Agent，这就是抢占。

与传统调度器相比，管理者 Agent 的优势在于具备推理能力：它可以并行启动多个子 Agent 探索同一问题，再根据进展决定给谁加资源、终止谁，像公司内部赛马一样。

资源与调度的工程实践远不如操作系统成熟，但它决定了多 Agent 系统的成本上限，应在架构设计阶段就纳入考虑。

## 6. 补记

共享与隔离不是二选一。成熟系统往往是「产物共享、轨迹隔离」：文件系统让产物在 Agent 之间流动，上下文窗口只保留索引与结论。这样既拿到了模块化的并发与权限控制，又避免每个 Agent 都背着全量历史。

三个容易踩的边界：

- 把 Scratchpad 和 Shared Workspace 混成一个目录，临时文件就会污染交付物；
- 把外部挂载当成可随意写回的本地盘，就可能改坏用户的真实数据；
- 把轨迹持久化当成状态同步的主要手段，token 与延迟都会失控。
