# ReAct 循环与轨迹

## 1. 想、做、看

ReAct（Reasoning + Acting）是把 LLM、上下文与工具串起来的核心机制。名字只体现思考与行动，实际循环包含三个环节：

1. **思考**：模型判断当前应该做什么；
2. **行动**：调用工具；
3. **观察**：读取工具返回结果，再进入下一轮思考。

「想 → 做 → 看」不断重复，直到任务完成。Agent 执行任务过程中不断累积的消息历史，就是**轨迹**（trajectory）：用户消息、模型回复（含思考过程与工具调用）、工具执行结果。

每次调用 LLM 时，完整上下文由两部分组成：

```text
上下文 = 静态前缀（系统提示词 + 工具定义） + 轨迹（动态消息历史）
```

模型基于完整上下文生成下一步响应，响应又追加到轨迹中，供下一次调用使用。

## 2. 最小运行骨架

先看机制如何运行。Model 只负责决定下一步；Harness 负责组装上下文、校验并执行工具；Environment 负责产生真实状态变化与观察。

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:       # 独立调用可以并行
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

这是一段机制示意，不是某个 SDK 的可执行代码。真实的 API 消息结构与 `tool_call_id` 关联，后面单独展开。

### 2.1 轨迹里保存了什么

以「根据四个季度、四种货币的收入，计算年度总收入与季度平均」为例：

```text
轨迹 = [
  {role: "user", content: "Q1 2.5M 美元，Q2 2.1M 欧元，Q3 1.8M 英镑，Q4 380M 日元，计算年度总收入和季度平均"},

  # 第一次迭代
  {role: "assistant", reasoning: "需要统一转换为 USD...", content: "",
   tool_calls: [
     {name: "convert_currency", args: {amount: 2100000, from: "EUR", to: "USD"}},
     {name: "convert_currency", args: {amount: 1800000, from: "GBP", to: "USD"}},
     {name: "convert_currency", args: {amount: 380000000, from: "JPY", to: "USD"}}
   ]},

  {role: "tool", content: "EUR->USD: 2282608.7"},
  {role: "tool", content: "GBP->USD: 2278481.01"},
  {role: "tool", content: "JPY->USD: 2541806.02"},

  # 第二次迭代
  {role: "assistant", reasoning: "汇总计算...", content: "",
   tool_calls: [{name: "code_interpreter", args: {code: "total = 2500000 + ..."}}]},
  {role: "tool", content: "Total: $9,602,895.73, Average: $2,400,723.93"},

  # 第三次迭代
  {role: "assistant", reasoning: "所有计算完成...", content: "FINAL ANSWER: ..."}
]
```

轨迹中没有系统提示词与工具定义——它们作为静态前缀，每次调用时自动拼在轨迹前面。整个过程只用 3 次迭代、4 次工具调用。

这种「不断追加」的设计有三个好处：模型能看到任务进行到哪一步、试过什么、得到什么；结构化的轨迹便于解释与调试；大量轨迹还能用于发现行为模式、优化决策路径、改进工具设计，甚至沉淀为训练数据。

## 3. 消融实验：哪些组件真的不可缺

为了验证上下文的五个组件是否都不可或缺，可以做**消融实验**：保留完整基线，再逐一去掉某个组件，观察 Agent 行为变化。系统提示词作为基本身份定义不参与消融——没有它，Agent 连角色认知都没有，测试没有意义。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig1-3.svg)

<p>图 2：上下文消融实验设计</p>

结果揭示了四点：

1. **工具定义**是行动能力的基础。没有它就无法调用任何工具；但失去行动能力不等于沉默——模型照样会给出一份格式工整、语气笃定的答案，数据却来自参数记忆，与真正基于观测得出的答案排版一模一样。它是坦白拒绝还是就地编造，主要取决于模型自身的幻觉率与诚实度；提示词里「不得自行估计」只能降低概率，不能消除。
2. **工具执行结果**是闭环控制的关键。缺失会让 Agent 盲目执行，反复重试直到耗尽迭代预算。
3. **思考过程**记录「为什么这么做」，工具结果记录「发生了什么」。当前者可以从后者重建时，把它从历史中丢掉几乎没有代价。
4. **历史消息**防止冗余操作，避免重复犯同样的错误。

核心洞察：**上下文决定 Agent 能看到什么，而 Agent 只能基于看到的信息做决策**。但组件并不等价，衡量标准是它承载的信息能否从别处重建——「每个组件都不可或缺」这类论断要靠实测，而且模型迭代很快，同一个消融换到新模型上完全可能得出不同结论。

还有一点对工程更重要：**「给出了回答」不等于「完成了任务」**。上下文残缺时，典型失败不是报错退出，而是一个看上去毫无破绽的答案。

## 4. 模型即 Agent：决策内化，执行仍在框架

先进模型正在把工具调用策略内化。以 Kimi K3 为例：约 2.8 万亿参数的 MoE 模型，100 万 token 上下文，原生视觉理解，始终开启思考模式；通过强化学习把「何时调用工具、调用哪个、传什么参数」内化为原生能力，能连续执行 200～300 次工具调用而保持思考一致性。

GPT-5.6 则展示了另一条路径：借助 Responses API 的网络搜索与代码解释器内置工具，在服务端形成「搜索—阅读—分析」的 Deep Research 闭环；自由格式工具调用允许模型直接向工具发送原始文本，省去 JSON 转义；还会在任务开始前通过提问澄清真实意图。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig1-5.svg)

<p>图 3：「模型即 Agent」架构与原生工具调用</p>

这里要分清两件事：

- **强化学习写进参数的是决策**：何时该调用、调用哪个、传什么参数、拿到结果后是否继续、如何把几十上百次调用串成连贯推理；
- **工具本身及执行由框架或 API 提供**：`web_search`、`code_runner` 的真实实现、代码沙盒、调用的发起与结果回传，都在模型之外。

因此，编排循环并没有消失，只是决策权交给了模型。循环跑在哪里取决于接入方式：Responses API 路径把搜索、代码执行与多轮编排整体放在服务端闭环；Kimi 路径中 Formula 只负责在服务端执行搜索本身，「调用模型 → 追加工具结果 → 再次调用」的循环仍由客户端代码驱动。

## 5. 工程边界

理解 ReAct 之后，几个工程判断会更清楚：

- **并行调用**：模型在同一轮发出多个工具请求时，若参数互不依赖，框架可以并行执行；若后一个工具的参数必须来自前一个结果，就只能串行。并行的前提是模型能正确判断依赖关系。
- **停止条件**：必须有明确退出条件——调用最终输出工具、模型返回无工具调用的响应、遇到不可恢复错误、达到最大轮数。缺少停止条件，Agent 容易陷入死循环或过度执行。
- **缓存成本**：轨迹只追加、不改写时，前缀缓存可以持续命中；一旦回改历史或每轮重写前缀，缓存就会从改动点起失效。这直接决定了后面 KV Cache 与压缩策略的设计。
- **观察质量**：工具结果不是「有就行」。格式混乱、缺失关键字段、错误信息不完整，都会让模型在错误的观察上继续推理；这也是后面强调结构化结果与详细错误信息的原因。

## 6. 补记

ReAct 最容易被误解成「让模型多想想」。它真正解决的问题是：**把模型的决策与环境的反馈接成闭环**。闭环成立需要三个条件：模型能看见结果（观察完整）、能采取行动（工具可用）、能从失败中调整（停止与重试策略合理）。

另一个经验是：轨迹既是调试材料，也是成本来源。完整保留轨迹便于解释与恢复，但会持续占用上下文；因此生产系统需要在「保留可重建的信息」与「压缩可丢弃的细节」之间做取舍，这也是上下文压缩要处理的核心问题。
