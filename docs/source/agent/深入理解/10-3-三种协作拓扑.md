# 三种协作拓扑：对等、管理者与去中心化

隔离上下文之后，协作关系本身还有形状：平等双方来回打磨，还是由一个中心调度一片子 Agent，还是让控制权在 Agent 之间接力。三种拓扑各有适用的任务结构，也各有自己的失效方式。

## 1. 对等协作与多样性的前提

对等协作通常涉及 2–3 个平等身份的 Agent，通过多轮迭代互相提供反馈。它的潜在价值是引入独立视角与认知多样性，但「多个实例」不等于「多种思路」：当模型、上下文与脚手架高度相似时，不同 Agent 往往做出相同选择，把局部错误变成系统性故障。

要拿到真正的多样性，需要主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断、再汇总结果。对等协作的实现复杂度在三种拓扑里最低——定义好两个角色、通信机制与终止条件就能跑起来。

## 2. 过早终止与 Loop 工程

对等协作最经典的用途，是解决 Agent 实践中极常见的一类失败：**过早终止**——活干到一半就停。它有三种形态。

一是**偷懒式假完成**：Coding Agent 写完代码，测试没跑、部署没试，就报告「任务完成」；打电话办事的 Agent 办完第一件就把第二件忘了，径直汇报「都办好了」。

二是**过早放弃**：一条路走不通就宣布整件事办不成。联系商家本有电话、表单、邮件多种途径，打了一个电话被拒，就告诉用户「这事办不了」。

三是**假成功**：以为办成了，实际闭环没走完。电话里对方口头同意退款，但用户还需要在 App 上确认一步，Agent 却报告「已办妥」，退款根本没有落地。

三种形态指向同一个根源：**在验证之前，「完成」只是模型的一句宣称，不是证明。**

把宣称变成证明，正是 **Loop 工程**的课题：设计一个让 Agent 持续运转的循环——发现下一件该做的事、执行、验证、记录进度——由验证器而不是模型自己判定「是否真的可以停」，人的角色从「写提示词的操作者」变成「设计循环的工程师」。2026 年 6 月 Addy Osmani 把这个实践总结成这个名词，Claude Code 负责人 Boris Cherny 的说法更直白：「我已经不再直接 prompt Claude 了，我的工作是写 loop。」

业界在这场讨论中形成的共识是：**循环的瓶颈在验证器，而不是模型。** 验证不可靠，循环转得再快，也只是把劣质产出更快地标记为完成。

**LoopX** 把循环从提示词与聊天历史中抽出来，放进一个与 Agent 运行时无关的持久控制面：

```text
LoopX 决策 → Agent 执行 → 独立验证器证明 → LoopX 提交
```

Agent 仍负责推理、调用工具与生成候选成果，LoopX 不替代运行时，只管理跨轮次的连续性。只有通过独立验证的结果才能写入持久进度并消耗配额；验证失败会进入修复或重规划，人工门禁、等待状态与预算上限则在执行前阻止循环继续。这组边界把 Loop 工程的原则变成可检查的系统不变量：**模型可以提出「完成」，但不能批准自己的「完成」。**

**LongHorizon-Harness** 关注另一个方向：同一任务跨越 GUI、CLI、多个桌面应用与多次上下文刷新的连续执行。它把长程执行重新表述为任务状态管理，循环实现为 Manage–Execute–Audit：Manager 根据原始目标、已核实进展、失败证据与剩余工作生成下一项有界子任务；Executor 在全新上下文中通过 GUI 或 CLI 改变环境；Auditor 以只读方式检查真实结果。只有审计通过的内容才能进入下一轮状态，失败则保留为恢复与重规划的依据。

这一方向的价值在于把任务连续性从不断增长的执行历史中分离出来：上下文可以刷新，界面操作也可能失败，但下一轮仍能从最近一次核实的状态继续。在模型与执行后端不变、只改外层 loop 的对照中，论文报告 WeaveBench PassRate 从 51.8% 提升到 80.7%，OSWorld 2.0 二元完成率从 2.8% 提升到 8.3%，Terminal-Bench 2.1 成功率从 69.7% 提升到 77.2%。代价并不固定：前两个基准分别消耗了基线 2.3 倍的总 token 与 3.6 倍的输出 token，Terminal-Bench 2.1 反而减少 24%。部署时还要处理外部环境或用户要求变化造成的旧状态失效，并用轮数、时间与费用预算防止恢复循环无限运行。

## 3. 提议者-审核者

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-3.svg)

<p>图 1：提议者-审核者循环</p>

提议者-审核者是最经典的对等协作范式：Proposer 生成代码，Reviewer 渲染执行结果、用视觉模型评估质量并给出结构化改进建议，两者反复迭代直到达标。同一范式也适用于安全审查（提议者给操作方案，审核者查合规与风险）、内容审核、代码审核。

**为什么不能让一个 Agent 自己生成再自己审查？** 这正是「是否引入新信息」判据的具体体现——审查若不引入新信息，就只是让模型再想一遍。ICLR 2024 的《Large Language Models Cannot Self-Correct Reasoning Yet》发现：让 GPT-4 在没有外部反馈的情况下审查并修正自己的回答，准确率反而下降，把正确答案改错的次数比把错误答案改对的次数更多。TACL 的综述《When Can LLMs Actually Correct Their Own Mistakes?》同样确认：除非提供可靠的外部反馈，纯粹依赖模型自身的「自我纠正」几乎不起作用。CRITIC 的对比实验更直观——用搜索引擎、Python 解释器验证时提升显著，移除工具验证、只留自我评估，大部分提升就消失了。

回到 PPT 生成那个例子：审核者的价值不在于「用同一个模型再看一遍代码」，而在于它**渲染了 PPT 并截取了画面**——截图承载着提议者写代码时完全无法获得的视觉信息；代码场景里测试的通过/失败结果，同样是编写代码时不存在的新信号。

循环的最小不变量是：审核者读取**独立证据**，而不是复述提议者的解释；退回时必须给出可定位的修复条件。

```python
candidate = proposer(task, constraints)
evidence = execute_or_render(candidate)       # tests, state, screenshot, facts
review = independent_reviewer(candidate, evidence)

while review.veto and budget_remaining:
    candidate = proposer.repair(candidate, review.findings)
    evidence = execute_or_render(candidate)
    review = independent_reviewer(candidate, evidence)

if review.pass:
    publish(candidate, evidence, review)
else:
    escalate_or_reject(review)
```

还有一条容易被忽略：审核者不能修改测试、证据采集器或发布门槛，否则「独立验证」会退化成自我批准。

Anthropic 2026 年的长程应用开发实验把这套思路实现为规划者–生成者–评估者三 Agent：规划者把需求展开为产品规格，生成者与评估者先约定每轮完成标准，生成者实现，评估者用 Playwright 操作真实应用并提交缺陷报告，Agent 之间通过文件交接状态。结论是：当任务超出模型单独可靠完成的范围时，带外部证据的独立审核能用显著更高的成本换取更好的开发质量。

## 4. 辩论、头脑风暴、专家小组

**辩论模式**让 Agent 各持立场对抗性对话：A 扮支持者列优势，B 扮反对者指风险，每轮针对对方论点反驳或补充。单一 Agent 分析时常倾向某个观点而忽视反面证据，辩论通过制度化的对抗让正反两面都被论证。

效果在学术上仍有争议。2026 年 Tran 与 Kiela 在多跳推理任务上对比单 Agent 与五种多 Agent 架构（顺序、辩论、集成、并行角色、子任务并行），发现当思考 token 预算被严格控制为相同时，单 Agent 与多 Agent 持平甚至更好。研究者用信息论的数据处理不等式解释：辩论中的多个 Agent 处理的是完全相同的文本，每次串行传递中间结论都只可能丢信息，不可能凭空造信息；一些论文里的辩论收益，很可能只是多花了总计算量。

不过这并不否证另外两类做法：对同一问题**多次独立采样再聚合**（自一致性、多数投票），以及利用**生成与验证的难度不对称**（写出答案难、检验答案易）做生成-验证分工。

**头脑风暴模式**让多个 Agent 独立生成创意再相互启发：一个提出社交分享，另一个受启发提出个性化分享海报，第三个综合前两者提出模板市场。不同 Agent 通过不同提示词或模型拥有不同「思维偏好」，在相互激发中探索更广的解空间。

**专家小组模式**让 Agent 各代表一个领域视角共同讨论跨学科问题：工程师看实现难度，产品看体验与市场，运营看成本与资源。它们不是对抗关系而是互补关系，共同拼出问题全貌。

## 5. 管理者模式

任务涉及大量子任务、需要动态调度、子任务之间还有复杂依赖时，对等协作就力不从心了。Manager Agent 像项目经理：理解整体任务，拆成可分配的子任务，选择合适 Agent 执行，跟踪进度并处理异常（重试、换 Agent、调整计划），最后整合输出。

从系统设计看，管理者模式把每个专门 Agent 建模为 Manager 可调用的工具。Manager 的工具集里不只有搜索、文件操作，还有 Agent 调用接口；从 Manager 视角看，调用一个 Agent 与调用普通工具没有本质区别。这种统一抽象带来良好的可扩展性：新增能力只需开发对应 Agent 并注册为工具，Manager 核心逻辑不必改动；也天然支持异构——不同 Agent 可用不同模型、提示词、工具集，甚至跑在不同硬件上。

代价是 Manager 成为单点瓶颈：它必须理解所有子任务的性质、选对 Agent、准确传递上下文，任何决策偏差都会影响全局；它还要维护整个任务的全局上下文，随着调用增多迅速膨胀。因此 Manager 的提示词质量、上下文管理策略与任务分解粒度格外重要。

Plan-and-Act 论文对 Planner-Executor 架构做了实证分析：**弱规划者是整个系统最关键的瓶颈**。Planner 规划质量足够高时，即使 Executor 比较简单也能取得好结果；反之，分解一错，后续所有执行都建立在错误前提上。该研究在 WebArena-Lite 上取得 57.58% 的成功率，核心贡献正是改善规划能力而非执行能力。启示很直接：应当把最强的模型与最精心设计的提示词分配给 Manager，而不是平均分配资源。

### 5.1 结算点：第一个「已验证成功」

并行管理器必须把结算点定义成「第一个**已验证**成功」，而不是「第一个声称成功」：

```python
workers = launch_independent_workers(subtasks)
while workers.any_running:
    event = next_event()
    if event.type == RESULT:
        if verify(event.artifact, hidden_checks):
            if not settle_once(event):       # atomically claim the winner
                continue
            broadcast_cancel(to=workers - {event.worker_id})
            await_all_ack_or_timeout()
            return assemble(event.artifact, evidence=event.evidence)
        else:
            record_failure(event)
return summarize_failures(workers)
```

`settle_once` 必须幂等（通常由锁或事务保护），否则两个几乎同时到达的成功事件会触发两次汇总。

### 5.2 顺序协调

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-4.svg)

<p>图 2：Manager 顺序协调</p>

Manager 依次调用专门 Agent，每个完成后返回结果，Manager 再决定下一步。控制流线性、简单明了，适合子任务有清晰先后依赖的场景。

书籍翻译是个典型例子。一本技术书要保证术语全书一致、语境准确、整体流畅，而单 Agent 逐章处理时上下文不断累积：术语表、已译章节、当前段落、翻译思考、工具结果，几百页很容易撑爆窗口。更麻烦的是长上下文里的「迷失」：忘了前面的术语约定，第九章用了与第二章不一致的译法；审校阶段重复检查浪费资源；甚至因注意力分散产生幻觉，「记起」并不存在的术语规则。

管理者模式用任务分解与责任分离解决：Glossary Agent 读全书，识别重复术语，查词典与规范，生成结构化术语表并写入共享文件系统，完成后即可销毁；Translation Agent 每次只拿当前章节、术语表与翻译指南，在独立上下文中工作，遇到新术语则推断并标记待审；Proofreading Agent 拿全部译文与术语表做一致性检查，产出审校报告；Manager 的上下文只保留任务描述、执行计划、调用记录与进度状态，不保存完整译文，只维护文件索引，并根据审校报告把特定章节发回重译。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-5.svg)

<p>图 3：书籍翻译 Agent 架构</p>

关键优势是上下文隔离：Glossary 只看术语提取所需内容，Translation 只看当前章节与术语表，Proofreading 虽读全文但只关注一致性。每个 Agent 都在精简专注的上下文中工作，效率更高，也更不容易因信息过载而分散注意力。

### 5.3 并行协调

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-6.svg)

<p>图 4：Manager 并行协调</p>

子任务彼此独立时，顺序执行就浪费了。并行协调让多个 Agent 同时工作，Manager 既要规划并行任务，也要实时监控所有运行中的 Agent、协调通信，并在成功或失败时做全局决策。这通常需要**消息总线**作为基础设施——一块公共公告板，Agent 往上贴消息（发布），也关注自己感兴趣的类型（订阅），异步通信、互不阻塞。

一个具体的双 Agent 场景：用户只给一个网站 URL，要求填写复杂的注册或航班预订表单。Computer Agent 打开页面识别字段，但姓名、证件号、地址等信息不在上下文里，需要向用户收集。直接让用户在聊天框逐项打字慢且易错，改用 Phone Agent 连续询问、确认、重问，把自然语言回答转成结构化字段。

两者通过点对点工具或消息总线交换结构化消息，不需要额外的 Manager 进程——Computer Agent 本身就是编排者，可以像调工具一样调用 Phone Agent。它根据页面、已知信息与任务需要，自主决定是否发起通话（而不是用「字段数量超过阈值」的 Python 规则代替模型决策）。通话开始后，Phone Agent 逐项提问、抽取并校验，Computer Agent 同时截屏、理解页面并填写；每收到一个有效值就发 `info_collected`，Phone Agent 不等网页填完便问下一项；格式错误发 `format_invalid` 并重问，页面异常则反馈 `fill_error` 让话术调整，超时或重试超限则安全暂停。信息收集完成后发 `task_completed`，Computer Agent 校验后提交表单，异常时取消对端并清理浏览器、音频轨道与通话。真人语音须显式同意，提交须显式授权。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-7.svg)

<p>图 5：Phone 与 Computer 双 Agent 架构</p>

同构 Agent 的并行搜索则是另一种形态：给定多所学院的网站，在各院教师名录里找指定教师。Manager 动态创建 10 个 Computer Use Agent，每个对应一个学院，拥有独立浏览器会话，启动时传入 URL、目标姓名与任务标识；子 Agent 定期发状态更新，Manager 维护一张任务状态表；某个 Agent 命中目标后发 `target_found`，Manager 立刻向其余 Agent 广播 `terminate`，等待确认或超时后汇总。这里同时要用到级联终止与竞态处理——若两个 Agent 几乎同时命中，第一个报告到达就锁定状态，后续报告识别为重复并忽略。失败处理则靠超时、错误隔离与「只要有 Agent 成功就返回信息，全部失败则报告各失败原因统计」。

### 5.4 一个产品化实例

灵台是一个本地运行、以文件为本的长期 Agent 居所，它的三种角色正好把前面的概念完整实现：

- **主器灵**：与用户对话的常驻中枢，掌管计划与记忆，把工作派生给其他角色，即 Manager 的位置；
- **分神**：为一件嘈杂而有界的工作分出的短时并行工作者，完成后即弃，只把结论带回主器灵，即「返回结构化摘要而非全量轨迹」与并行协调的产品化；
- **分身**：拥有自己记忆、邮箱与职责的持久专门化队友，用于值得跨多次会话保留的专业分工。

其余设计与前文一一呼应：知识是每个器灵私有的持久记忆文件，技能是所有器灵共享的 Markdown 手册；上下文窗口将满时，器灵会「凝蜕」——给自己写一份总结，带着持久记忆在干净上下文中继续工作；底层模型可以替换而器灵犹在。身份、记忆与能力都以普通文件存放在项目目录里，即「器灵即其文件」。

## 6. 把编排写成代码

前两种形态里 Manager 始终待在循环中：每派发一个子任务都要模型做一次决策，上下文随调用次数增长。还有一种做法是**管理者先把 Agent 工作流写成一段代码，再交给确定性的运行时执行**。

Claude Code 内置的 Workflow 工具就是实例，它提供 `agent()`、`parallel()`、`pipeline()` 几个原语：每个 `agent()` 是拥有独立上下文的子 Agent，schema 约定它只返回结构化结论而非完整轨迹。例如为一篇技术稿件核实七组事实，每组先调研，再逐条独立核实，最后统一汇总：

```javascript
const results = await pipeline(
  DIMENSIONS,                                     // 七个待核实的方向
  d => agent(research(d), { schema: FINDINGS }),  // 阶段一：调研
  r => parallel(r.findings.map(f => () =>         // 阶段二：逐条独立核实
         agent(verify(f), { schema: VERDICT })))
)
await agent(writeProvenance(results.flat()))      // 汇总：等齐所有结果
```

编排一旦成为代码，循环次数、并发度与失败分支都由程序控制，不再消耗 Manager 的上下文。这是「管理者退出循环」的一种形态，也更接近第一章说的确定性工作流。

## 7. 去中心化

有了管理者模式，为什么还需要去中心化？动机主要是模拟人类组织：让多个职责对等的角色分工与制衡，各自从专业视角审视问题、自主决定与谁沟通，而不是把所有判断汇集到一个 Manager。

另一个动机是稳定性。模型或 API 服务出问题时，一些 Agent 可能停止响应、工具调用失败、陷入死循环；在管理者模式中，**Manager 崩溃往往就是系统最大的单点故障**。

微服务领域把两者分别称为**编排**（orchestration）与**编舞**（choreography）：前者由指挥统一调度，后者靠每位舞者自行把握入场时机。

### 7.1 MetaGPT：SOP 驱动的软件公司

MetaGPT 的核心洞察是：人类软件公司积累的**标准作业程序**本身就是被反复验证过的协作协议。把 SOP 编码进多 Agent 系统，每个角色像流水线上的专业工种产出标准化交付物，交付物天然构成角色间的通信接口。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-9.svg)

<p>图 7：MetaGPT 多 Agent 协作网络</p>

各角色沿固定顺序工作：Product Manager 生成结构化 PRD（功能列表、用户故事、验收标准、优先级）；Architect 读 PRD 做架构决策（技术栈、模块划分、接口定义、数据模型）；Project Manager 把设计拆成任务清单与文件级分工，理清依赖顺序再分派；Engineer 可实现多个实例并行；QA 读代码与 PRD，生成用例、执行测试、记录 bug。

一个有效的「移交包」通常包含三部分：**任务描述**（做什么、验收标准）、**已确认的事实与约束**（用户偏好、业务规则、前序决策）、**结构化产物的引用**（文件路径而非文件内容，接收方按需读取）。每个 Agent 不需要理解别人的思考过程，只需理解移交包与产物的格式语义。

MetaGPT 对去中心化通信的真正贡献在信息传递机制：**共享消息池 + 按角色订阅**。角色把结构化消息发布到所有角色可见的消息池，其他角色按订阅配置只取与自身职责相关的消息，而不是点对点传话。发布者不需要知道谁消费自己的输出，新增角色只需声明订阅，无需改动现有角色。把 Product Manager 换成更强的模型，只要 PRD 仍符合规范，其他 Agent 都不用动。

需要如实说明：MetaGPT 在**控制流**上并不去中心化，角色顺序由 SOP 预先固定，整体更接近流水线。「QA 直接找 PM 澄清需求」这类多向动态反馈，是对该架构的自然扩展设想，原版并未实现。

### 7.2 AutoGen 群聊

AutoGen 的 group chat 让多个 Agent 参与同一场会话：每轮由一个「发言者选择器」决定下一个发言者，可以是轮转规则，也可以是 LLM 根据当前对话判断谁最合适；任何 Agent 的发言对所有参与者可见。

它不是完全去中心化的系统：发言者由中心化的 GroupChatManager 裁决，而「轮到谁」本身就是控制流决策。它属于「共享对话记录 + 中心化调度」的混合形态——所有 Agent 看到同一份公共记录，各自保有独立的系统提示词与工具集，调度权集中在选择器手里。

### 7.3 OpenAI Swarm

Swarm 是控制流真正对等去中心化的代表：每个 Agent 配备若干 handoff 选项，可以在任何时刻把控制权移交给网络中任意其他 Agent。系统中没有中心调度者，控制权像接力棒一样在对等 Agent 之间流转，路由决策完全分散在每个 Agent 的判断里。

与共享上下文的协作不同，handoff 只应传递明确的任务包与产物引用，不应默认暴露完整私有轨迹。对等移交的风险是成环：A 交给 B，B 又交回 A，任务在环路里空转，因此需要移交次数上限之类的保护。

最小协议可以写成：

```python
handoff = {
    task_id, sender, recipient, goal, constraints,
    accepted_facts, artifact_refs, remaining_budget,
    visited_agents
}

if recipient in handoff.visited_agents:
    reject("cycle")
elif handoff.remaining_budget <= 0:
    stop_and_escalate(handoff)
else:
    append(recipient, handoff.visited_agents)
    run_local_agent(handoff)
```

它把「上下文隔离」变成可检查的接口：接收者读任务包与引用，按需取证；预算、访问链与循环检测由运行时保留，不能由任一 Agent 自行删除。

2025 年以来「Agent Swarm」成了热门词，但它并不对应单一架构。业界用法大致两类：一类是 Swarm 式 handoff 网络（LangGraph 的 swarm 库、微软 Agent Framework 的 handoff 编排同此），即去中心化模式；另一类是规模化的管理者模式——Kimi K2.5 首发的 Agent Swarm 由主 Agent 动态创建上百个子 Agent 并行执行，把「何时拆、拆几个」直接训练进模型，Anthropic 的多 Agent 研究系统与 Manus 的 Wide Research 同属 orchestrator-worker 星型拓扑。读概念时要看清背后的实质结构，而不被名称迷惑。

### 7.4 同一台机器上的多个实例

以上系统的 Agent 都在合作完成同一件事，还有一类去中心化是各干各的：每个 Agent 有自己的任务，通信不是为了分工，而是协调共享资源。本机多个 Agent 实例可以互相发现、互相发消息：两个 Agent 改同一组文件时协商冲突，机器上只有一块 GPU 而两个实例都要跑训练时协调使用。

## 8. 跨组织协作：A2A

以上系统都假设所有 Agent 由同一团队开发、运行在同一系统内，此时参数传递、共享文件、消息总线足够用。当协作跨越组织边界——你的 Agent 要调用另一家公司的 Agent——就需要标准化的互操作协议。A2A 之于 Agent，就像网络协议之于进程。

2025 年 Google 发布的 **A2A**（Agent2Agent，后捐赠给 Linux 基金会托管）有三个核心要素：

- **Agent Card**：描述能力的元数据文档，发布在约定公开地址，声明能做什么、支持哪些输入输出模态、如何认证——相当于 Agent 的名片，解决跨组织的能力发现；
- **任务生命周期管理**：把协作单元建模为 Task，带明确状态机（已提交、进行中、需要输入、已完成、失败），原生支持长任务与流式进度更新；
- **不透明协作**：只交换任务与产物（Artifact），不暴露内部提示词、思考过程与工具实现——与「不共享上下文」原则一致，也是跨组织协作必要的安全属性。

A2A 可以与 MCP 对照理解：MCP 解决 Agent 与工具的互操作，A2A 解决 Agent 与 Agent 的互操作。它不取代三种通信机制，而是在它们之上、跨信任边界的标准化层。同一团队内部直接用消息总线即可，只有协作方互不信任、实现互不可见时，才需要这样的公开协议。

## 9. 补记

拓扑不是标签，而是控制权与信息流的结构。同一个产品里常常混用：管理者模式负责并行搜集，对等循环负责质量收敛，去中心化移交负责跨角色边界。

三种拓扑的失效方式正好相反：对等协作容易**转不下去**（过早终止、空转），管理者模式容易**卡在中心**（规划错误、单点崩溃、上下文膨胀），去中心化容易**绕圈**（移交成环、责任漂移）。设计时先想清楚这套系统最可能以哪种方式坏掉，再决定加验证器、加预算还是加环检测。

还有一点值得记住：Loop 工程与提议者-审核者解决的是「如何确认完成」，而拓扑解决的是「谁来确认」。两者是正交的——去中心化系统同样需要独立验证器，管理者系统同样会过早宣布完成。
