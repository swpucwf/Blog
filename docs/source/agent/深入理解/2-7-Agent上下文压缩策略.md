# Agent 上下文压缩策略

## 1. 三个压缩动机

前面讨论的都是「往上下文里放什么」：提示工程决定写什么，Skills 决定按需加载什么，状态栏决定注入什么元信息。随着多轮交互深入，上下文会不断膨胀；压缩讨论的是相反方向——**如何做减法**。

压缩有三个截然不同的动机：

1. **长度与成本约束**：窗口有限，工具结果动辄数万字符，几轮就可能撑满；token 越多，API 成本越高，延迟也越长。
2. **提升思考质量**：总结后的知识比原始形式更利于模型使用。即使窗口足够大，把所有原始信息堆进去也不是最优——十几轮搜索的原始结果散落各处，模型每次决策都要在数万 token 中反复检索，注意力被分散，关键信息容易遗漏。先用一次 LLM 调用把已有信息结构化总结成「目前已知：A 是……，B 是……，还缺 C」，后续思考可以直接使用这份精炼表示。
3. **缓解上下文焦虑**：当模型认为窗口即将耗尽时，可能在任务尚未完成前提前收尾。在尚未接近耗尽时提前压缩，可能提升决策质量。

## 2. 检索而非推理

<p>图 1：上下文压缩策略对比</p>

状态栏是给「只有一半的检索引擎」补上提炼层，压缩也一样。区别在于：状态栏往往由**代码**每一步确定性地维护，压缩更多是用一次 LLM 调用把大段原文蒸馏掉。

一个直观例子：上下文中有一段宠物店巡查记录——「笼子 1：黑猫。笼子 2：白猫……共 100 个笼子，90 只黑猫、10 只白猫」。问「黑猫白猫各多少只」时，不启用思维链的模型很难直接答对：**查找**（「笼子 37 里是什么猫？」）是注意力的强项，**统计归纳**（「总共有多少只黑猫？」）却要遍历全部记录并维护计数状态，本质是思考而非检索。启用思维链能数对，但每问一次就要从头数一遍；Agent 场景中这类统计常被反复使用，累积成本很高。提前总结成「黑猫 90、白猫 10」，模型立刻能检索到结论。

长上下文还会导致检索精度下降：窗口远未满，Agent 却突然找不到关键信息，或反复纠结一个早已解决的问题。这是**上下文腐化**（Context Rot），与**上下文溢出**不同——溢出是「装不下」，腐化是「装得下但找不到」。后者更隐蔽：Agent 表面还在正常工作，只是决策质量悄然下降。

因此压缩的设计原则是：**不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识。**

## 3. 压缩与 KV Cache：看似矛盾，实则互补

前面强调 KV Cache 要求前缀不变，压缩却要修改上下文中间的内容。关键是理解压缩发生的**时机与位置**：

- 压缩不是在一次 API 调用过程中修改上下文，而是在**两次调用之间**，由框架对消息列表预处理；
- **System Prompt 与 Tool Definitions 永远不动**，这是最前面的静态前缀，缓存持续命中；
- 压缩对象是对话历史中的 tool results：替换位置之后的缓存会失效，但之前的缓存仍然有效；
- 这是有意识的权衡：不压缩，上下文超出窗口，任务直接失败；压缩后损失部分缓存，但长度可控、信息密度更高。因此**接近阈值时批量压缩**，不要每轮都压。

如果模型把 thinking 绑定在前缀上，压缩的代价不只是缓存：「摘要旧轮次、原样保留最近几轮」会出问题——保留下来的那几轮 thinking 产生时，前面是原始历史而不是摘要，前缀已变，它们会全部失效；原地截短旧工具结果同理。更稳的做法是整段会话压成一条摘要、不再回传旧 thinking，或交给服务端清理上下文。

## 4. 六种策略的实测差异

一个研究任务：识别并追踪 OpenAI 联合创始人的职业状态。需要多步骤聚合，搜索结果从数千到十几万字符不等。把上下文预算限制在 128K，比较六种策略：

1. **无压缩**：保留全部原始结果。七次工具调用累计约 367,000 字符，第五次迭代就超过 128K（约 165,000 token），触发溢出，任务失败。
2. **个体摘要**：每个结果独立生成 2–3 段摘要，压缩率 10.9%。能完成，但需 12 次迭代、276,608 token；多个页面重复描述同一事件，信息碎片化。
3. **组合摘要**：把所有结果合并后生成一份综合摘要，压缩率 4.3%，10 次迭代、93,449 token；但输入超长时必须截断，可能丢末尾信息。前两种的共同缺陷是缺乏语义理解，无法区分相关性。
4. **上下文感知压缩**：把当前查询意图与已积累信息纳入压缩决策，提示中指定 `Given the search query: {query}` 与 `Current context: {context}`。只需 7 次迭代、40,157 token，压缩率约 3.0%；一次把约 150K 字符压到 2K，仍保留了创始人姓名与职位变动等后续需要的关键信息。
5. **带引用的上下文感知**：在智能压缩上增加溯源，每条事实附来源 URL。内容经过语义压缩（有损），但保留源链接（无损索引），可随时回溯。
6. **自适应窗口化**：任务初期不压缩，接近容量才启动。三个机制：阈值触发（prompt token 超过窗口 80% 才激活）、批量压缩（一次压缩所有未标记的工具结果）、防重复（`[COMPRESSED]` 标记）。总 token 较大（174,601），但前几次迭代保留完整原始信息，为初期广泛收集提供最大灵活性。

## 5. 生产级的分层压缩

成熟系统通常不会只用单一策略，而是把多种策略组合成分层机制——不同信息有不同保质期，压缩策略应与预期生命周期匹配。以 Claude Code 为参照，常见五层：

1. **工具结果预算控制**：大体积输出存磁盘，模型只看摘要预览。替换决策一旦做出就冻结，保证缓存一致性。
2. **噪声直接删除**：低价值内容（大量搜索结果中只用了几行的）直接移除，不做摘要——对噪声做摘要只是浪费 token。
3. **API 层微压缩**：通过服务端上下文编辑能力，从前缀中移除指定工具结果，本地消息不变。优势是零本地实现、服务端一次完成；但移除点之后的缓存同样失效，适合在上下文即将溢出、反正要付重建代价时使用。
4. **归档式摘要**：逐轮结构化摘要，像 git log 一样保留每轮独立记录，而不是 squash 成一条，保留对话逻辑脉络。
5. **全量压缩**：LLM 驱动的完整压缩，作为最后手段。即便此时也分两阶段：先压会话记忆，不行再全量；并配连续失败熔断器——生产数据表明，大量会话会困在反复压缩失败的循环里，熔断避免持续烧钱。

## 6. 四条设计原则

- **信息价值非均匀分布**：关键决策点（人员名单）价值高于支撑性证据（新闻细节），更高于冗余噪声（导航栏、页脚广告）。
- **语义完整性**：「Sutskever 于 2024 年 5 月离开 OpenAI」不能压成「Sutskever 离开」——时间与公司名是不可丢的关键信息。
- **任务相关性**：同样内容在「查找创始人名单」与「了解个人背景」下应产生不同压缩结果。检索类任务保留广度，分析类保留深度，创作类保留灵感触发点。
- **压缩即理解**：有效压缩需要深层语义理解，负责压缩的模块本身要接近主模型能力，形成「模型调用模型」的递归结构。好处是显式压缩结果可审查、可跨会话复用。

压缩虽需额外计算（每次压缩就是一次 LLM 调用），但相比节省的 token 与提升的成功率，回报率很高。实验显示，上下文感知压缩把 token 使用量减少 75% 以上。

压缩最容易丢的是早期架构决策、约束背后的理由与失败路径。因此 Agent 需要**定期把进展记录到文档**，而不是把所有信息零散放在执行历史里。就像公司重要信息要文档化，而不是留在聊天记录中。

## 7. 隔离优于压缩

压缩是在信息进入上下文之后做减法；更釜底抽薪的思路是让大体积中间信息根本不进入主上下文——**子 Agent 上下文隔离**。

同一个任务：「在代码库中找到处理支付回调的函数」。

- 主 Agent 亲自搜索：可能把十几个文件的数万 token 原始代码纳入主上下文，找到目标后大部分沦为噪声，还要靠压缩清理。
- 委派给搜索子 Agent：主上下文只增加两条消息——任务描述与结论（「函数位于 `src/payment/callbacks.py` 的 `handle_callback`，另有两处调用点」），中间过程的数万 token 随子 Agent 上下文一起丢弃。

这是**用隔离代替压缩**：压缩是有损、需要额外 LLM 调用的事后补救；隔离让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀也完全不受影响。代价是子 Agent 看不到主 Agent 的完整上下文，任务描述必须自包含、目标明确——上下文质量决定能力上限，对子 Agent 同样成立。

## 8. 补记

压缩的难点不在「怎么压」，而在「压什么、什么时候压」。三个判断最实用：

- **先问信息能否重建**：能从工具结果、文件、日志重建的，可以压；不能重建的（决策、约束、失败原因、来源）必须留。
- **批量而非每轮**：压缩会破坏缓存，频繁压缩等于频繁重建；接近阈值时一次处理，成本更可控。
- **隔离优先于压缩**：能在源头把大块中间结果挡在主上下文之外的，不要先进来再压。
