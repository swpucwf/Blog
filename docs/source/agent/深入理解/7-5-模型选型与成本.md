# 模型选型与成本

## 1. 选型的维度

模型选择不是「选最强」，而是在多个维度之间权衡。

### 1.1 吞吐与延迟

大模型推理分两阶段：

- **Prefill（预填充）**：一次性读入完整上下文，决定用户按下回车到第一个字出现的**首字延迟**（TTFT）。上下文越长，prefill 越慢。
- **Decode（解码）**：逐个 token 生成回答，决定后续出字速度（tokens/秒），也直接决定思考时长——50 tokens/s 的模型生成 2000 个思考 token，光思考就要 40 秒。

关键指标：

- **输入/输出吞吐量**：分别对应 Prefill 与 Decode 速度；
- **TTFT**：排队时间 + Prefill 时间，是用户感知的「反应快慢」；
- **思考延迟**：不同模型生成的思考 token 数差异可达数倍，且思考长度与效果不一定正相关；要在自己的工作负载上实测；
- **p95 尾部延迟**：95% 请求不超过的延迟，比平均值更能反映真实体验——均值会被大量快请求拉低，掩盖少数严重卡顿。

### 1.2 成本与性能

**成本**：输入/输出/缓存 token 定价。一个便宜但成功率低的模型，因频繁重试，实际花费可能更高。要算每个任务的平均成本与成本-性能比。

**性能**：Pass@1、Pass@k、Pass^k、Best@k。日常看 Pass@1；关键操作看 Pass^k，盯「每次都不出错」；探索任务看 Pass@k/Best@k，看能力上限。

**速率限制与可靠性**：RPM/TPM 影响并发，部分 API 高峰期动态调整限额；还要看分布外数据、对抗输入、长时运行稳定性。

**预算—能力曲线**：固定预算下的单点成绩不足以判断长程能力，应报告成功率随墙钟时间、token、工具调用次数变化的曲线。RE-Bench 的人机对照显示：每环境 2 小时预算下，最佳 Agent 得分约为人类专家 4 倍；但人类从更多时间中收益更大，8 小时已略超 Agent，32 小时约为其 2 倍。短预算领先不能直接外推成长时间能力。

实践中可以采用多模型协同：轻量模型处理简单请求，强模型处理复杂任务，专门模型处理图像/代码等子任务，通过子 Agent 协作。**异构组合必须用评估验证**整体收益是否超过系统复杂度，是否在某些场景出现回退——例如把「9.9 和 9.11 哪个大」当简单问题交给轻量模型，导致决策错误。

## 2. 行为策略：模型默认会怎么做

选型不只看「能不能做成」，还看模型默认怎样做。

Coding Agent 中很容易观察到行动阈值差异：面对同一任务，有的模型先广泛探索仓库再修改；有的凭较少局部证据快速定位，先改再用测试反馈补齐认识。前者把过早修改的风险估得更高，后者把「再读一个文件」的机会成本估得更高。

这种倾向有两个来源：Harness 的系统提示词，以及模型的行为策略。后训练是行为策略的关键来源：SFT 轨迹示范「先读到什么程度再动手」，过程奖励奖励或惩罚某种工具路径，结果奖励强化整套成功策略。久而久之，模型学到的不只是写代码，也包括工程习惯。

一个固定 Harness 的实验显示：某模型第一次修改前平均调用工具 6.89 次、读 4.67 个文件；另一模型为 4.56 次、3.56 个文件。差距在局部任务最明显，在明确跨模块任务中几乎收敛。两者首个补丁与最终测试都 100% 通过——这说明「行动策略随模型而变」，而不是「多读或早改必然更好」。

## 3. 成本分析

Agent 场景的成本远比 token 定价复杂：多轮推理、工具调用与上下文累积会让它非线性增长。

### 3.1 三个层次

**模型推理成本**：输入/输出 token，有两个常被忽视的放大因素：

- **上下文累积**：每轮都把历史与工具结果一起发送。没有 KV Cache 时，第 1 轮 1000 token、第 2 轮 2000、第 3 轮 3000，总量是 6000 而非 3000，轮次越多差距越大；
- **思考 token**：不展示给用户，但同样计费。

**工具调用成本**：外部 API 费用、沙盒资源，以及容易被忽视的间接成本——工具结果注入上下文后产生的 token，在后续每轮反复计费。一次网页搜索返回 2000–5000 token，会跟着历史一路计费。

**基础设施成本**：向量数据库、消息队列、关系数据库、日志与追踪存储。

### 3.2 一次八轮任务的实测

固定八轮客服退款任务：查订单、物流、退款政策、知识库，再风控、退款、通知、关单。使用同一模型，分别开关「稳定前缀」与「压缩历史」：

| 方案 | 输入 token | 缓存 token | 总成本 | 比基线节省 |
|---|---:|---:|---:|---:|
| 无缓存、无压缩 | 20,700 | 0 | $0.003776 | — |
| 仅稳定前缀 | 20,386 | 13,568 | $0.002707 | 28.3% |
| 仅压缩历史 | 16,177 | 0 | $0.003115 | 17.5% |
| 稳定前缀 + 压缩 | 16,035 | 6,144 | $0.002643 | 30.0% |

基线每轮输入从 1,113 涨到 3,668 token；工具返回跟着历史反复进入后续请求，八轮累计占 9,544 输入 token。两项优化同时开启后降到 5,248，总费用下降 30%。

但「仅稳定前缀」已省 28.3%，「仅压缩历史」省 17.5%，两者一起只省 30%，不是相加。原因是压缩历史的同时，也缩短了可命中缓存的前缀。**几项上下文优化同时使用时，必须在完整任务中一起实测，不能把各自节省比例直接相加。**

### 3.3 优化手段

输入侧优先测试三类：

- **复用 KV Cache**：尽量保持前缀不变；
- **压缩上下文**：减少旧轨迹与冗长工具返回；
- **分层选择模型**：轻量处理简单请求，强模型处理复杂推理。

这些能力最好都能独立开关，既看清每项作用，也检查合用时是否互相抵消。

另外两项与运维直接相关：

- **异步批处理**：非实时任务积压后批量处理，利用波谷定价；本地部署时提高 GPU 利用率；
- **成本监控与预算控制**：按任务、模型、用户追踪 token 与费用；设置单任务成本上限，Agent 陷入循环或探索过深时自动终止。

## 4. 统计显著性

评估集有限、模型输出随机，分数差异可能只是抽样噪声。若 n 个用例上成功率 p，标准误约：

\[
\mathrm{SE}(p)\approx\sqrt{\frac{p(1-p)}{n}}
\]

100 个用例、70% 成功率，95% 置信区间约 \(70\%\pm9\) 个百分点；「新模型 73% 对旧模型 70%」不足以支持切换。

同一批任务比较两个配置时，应优先做**配对分析**：逐题记录谁胜出，用 McNemar 检验或配对 bootstrap，而不是直接相减两个独立成功率。Agent 每次运行也可能不同，每个配置最好用多个随机种子（3–5 次），报告均值与波动范围；单次运行只能筛选方向。

若预期收益只有 2–3 个百分点，而评估集只有几十题，应先扩大样本，标准误会按 \(1/\sqrt{n}\) 缩小。

```python
for task in paired_tasks:
    for seed in fixed_seeds:
        a = run(config_a, task, seed)
        b = run(config_b, task, seed)
        record_paired_delta(verifier(a), verifier(b))

return paired_bootstrap_or_mcnemar(all_deltas)
```

配对的含义是让两组共享任务与随机条件，而不是分别抽两批样本再比平均值。

并行验证多个假设时还要考虑**多重比较**：收紧显著性阈值，或对正向结果做独立复跑。实务判断标准：分差超过噪声、在配对分析中成立、并且能复现，才值得切换或发布。

## 5. 配对比较与排名

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-6.svg)

<p>图 1：Elo 评分与配对比较排名</p>

**Elo** 通过大量两两对决量化相对能力：分差越大，强者预期胜率越高。A 1200、B 1000，Elo 预测 A 胜率约 76%；B 若爆冷获胜，加分更多，排名快速收敛。统计基础是 Bradley-Terry 模型：每个模型有潜在实力分数，胜负概率由分差决定；Elo 是其在线更新实现。

Chatbot Arena 采用匿名随机对决，用户盲选更优回应，数百万次投票得出排名。优势是不需要绝对标准，只需判断「A 与 B 哪个更好」；局限是结果取决于用户问什么——大量编程题会让擅长编程的模型排名偏高。

LLM 配对评判要防**位置偏差**：评判模型系统性偏向某个位置（通常先出现）。标准缓解是交换顺序各评一次，取平均；更严格是只有两次判决一致才计入，不一致记平局或人工复核。Chatbot Arena 随机化展示位置，让偏差在大样本下抵消。

## 6. 评估驱动的持续迭代

模型选择不是一次性决策，而是随模型演进动态调整。

假设当前基于 Claude 构建，工具调用与复杂编排表现优异。某天新模型发布，公开基准多项超越且更便宜。此时问题不是「它是否比 Claude 强」，而是「**在我的任务上是否更好？好多少？切换成本是什么？**」

有评估体系的团队可以在数小时内回答：跑自己的评估集，对比成功率、工具调用正确率、延迟与成本。可能发现新模型在简单任务更优更便宜，但在复杂多轮编排上成功率下降 5%。确认差异超出噪声后，决策变成「简单任务迁移、复杂任务保留」的差异化策略，而非全量切换。

## 7. 补记

选型最容易犯的错，是只比较单价或公开榜单。Agent 的真实成本由多轮累积、工具结果回流、重试与思考 token 共同决定；真实能力也由 Harness、行为策略与任务分布共同决定。

一个实用顺序：先用配对评估确认「在你的任务上是否更好」，再看总成本与尾部延迟，最后检查行为策略是否与产品要求一致（例如是否过早动手、是否过度探索）。
