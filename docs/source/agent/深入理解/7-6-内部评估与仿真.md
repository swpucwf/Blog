# 内部评估、可观测性与仿真

## 1. 可观测性：评估的数据基础

评估驱动的决策依赖高质量运行数据。

**可观测性**借自分布式系统：你没法直接打开系统内部，只能通过日志、指标、追踪推断发生了什么，像医生通过体温、血压、影像诊断。Agent 让这件事更难：同样输入可能产生不同输出，多轮推理与工具调用使路径极其复杂，模型的「思考」对外完全不透明。

价值有四层：

- **问题诊断**：完整轨迹可回放，而非靠猜；
- **持续优化**：看到哪些任务多轮迭代、哪些工具成功率低、哪些检索总返回空；
- **成本管理**：不同任务成本可差一两个数量级，追踪能识别异常高成本案例；
- **训练数据**：积累轨迹为后训练提供基础。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-7.svg)

<p>图 1：可观测性技术栈</p>

数据基础是**追踪（Trace）**，结构沿用分布式系统的 span 树：一次任务一条 trace，每个 LLM 调用、工具调用、检索都是一个 **span**（记录输入输出、起止时间、token、错误），父子关系构成执行树。

已有标准协议：**OpenTelemetry** 是通用分布式追踪标准，**OpenInference** 在其上定义 LLM 应用语义约定（提示词、模型参数、token 用量）。采用标准协议让采集与分析解耦，同一份数据可对接不同后端，避免平台锁定。

LangSmith 是代表性平台（同类还有 Langfuse、Arize Phoenix），把可观测性、评估、优化整合为闭环：每次执行创建追踪会话，模型调用、工具使用、检索被记录为独立单元，通过因果关系链接成树；每个单元记录完整输入输出、时间、成本与错误；异步批量采集，不影响响应延迟。

平台还支持 A/B 测试（流量路由、指标对比、快速回滚或渐进扩量）、提示词版本管理（每个版本关联运行时性能）、协作式开发（共享追踪与问题案例）。

最有价值的去向是**回流为评估资产**：从生产轨迹筛选失败与可疑案例 → 脱敏 → 沉淀为评估集新用例与回归测试。评估集因此不是一次性静态集合，而是随产品演化的活资产。今天线上暴露的失败模式，明天就是守住底线的回归用例。

## 2. 从 Benchmark 到系统改进

一个 AndroidWorld 调优案例：只跑 API 35 模拟器上的 4 个 Wi-Fi 设置任务，每项做一次配对对照。价值不在证明整体提升多少，而在展示「如何根据一轮结果决定下一轮只改什么」。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-8.svg)

<p>图 2：Benchmark 到改进闭环</p>

从 Harness 视角，这一节讲的是**通过评估定位 Harness 薄弱环节**（上下文不足？约束缺失？验证不够？反馈不及时？），有针对性地改进，再重新评估。

开始分析前有一条容易忽视的原则：**看到 Agent 表现下降时，先检查评测系统本身，再动 Agent。**

常见误区是看到分数下降立刻改代码，却忽略评测系统可能先出问题：资源不足导致进程被杀（随机失败）、验证器 bug 把正确判失败、测试用例与生产脱节。这些问题在数字上都像模型退化，只有审查完整轨迹才能区分。

### 2.1 读报告：先找失败簇

最初报告记录 116 项任务各跑一次，总成功率约 88%。但失败不是零星散落：四项 `SystemWifiTurn*` 任务里三项失败，轨迹反复出现来回导航、无法确认状态。

至少两种解释：Agent 不知道设置入口；或拿到的界面信息不完整。

只盯 88% 总分，这个小而集中的失败簇容易被忽略；只增加最大步数，又可能把「看不见界面」误当「不够耐心」。读报告应先找失败集中在哪些任务与能力上，再回放轨迹，分清问题出在看、想、做还是验。

先把范围缩到四项 Wi-Fi 任务，用低成本判断病因，而不是估算系统整体水平。

### 2.2 从数据到假设

**第一轮 H1**：假设 Agent 只是「不知道路」，只给实验组补 Wi-Fi 导航提示与最终状态检查要求。成功率没变，说明问题不在提示词。

**第二轮 H5**：检查 Agent 到底「看见了什么」。把 API 35 上不兼容的 accessibility feed 换成 UIAutomator 元素树。成功率提高，但完整元素树太长，token 大增。

**第三轮 H5C**：不增加新信息，只删掉元素树中不可见、无文字、不可操作的容器节点，看能否保留成功率同时去噪。

三轮始终使用相同模型、任务参数、种子、步数上限与模拟器，并交替安排两组运行顺序。一轮接一轮缩小范围，比同时堆改动更容易说清因果：上一轮暴露的问题，恰好成为下一轮唯一要验证的改动。

### 2.3 从结果到决策

| 实验 | 只改了什么 | 对照组→实验组 | 实验组/对照组 token | 下一步 |
|---|---|---:|---:|---|
| H1 | 增加导航提示 | 25%→25% | 0.47× | 无提升，沿用原提示 |
| H5 | accessibility feed 换成 UIAutomator | 25%→100% | 2.498× | 明显但太费 token |
| H5C | 精简 UIAutomator 元素树 | 100%→100% | 0.506× | 成功率不变、token 减半 |

结论比某个百分比更有用：

1. **提示写得更详细，补不回 Agent 根本没看到的信息**。这类失败应先查输入，而不是堆提示词。
2. **输入不是越多越好**。完整元素树解决「看不见」，却带来大量无用 token；删除无语义节点后四项仍全过，token 又减半。
3. 全程没换模型，只调整 Harness 如何表示界面，就先后解决「能不能做成」与「做成是否划算」。

### 2.4 持续迭代

H5C 通过四项任务，只说明值得进入下一轮，不等于可部署。下一步要补齐第三方应用，在标准环境对 116 项任务各跑 5 个种子；除成功率不降，还要确认 token 不超过原方案 75%、延迟不超过 1.5 倍。

在这轮完整复测前，不能把子集 4/4 写成系统整体 100%。

**一轮证据只支持与它规模相称的下一步。** 好的 Benchmark 报告不只给分数，还应写清结论适用于哪里、哪些底线没通过、下一轮验证什么。

## 3. 内部评估基础设施

最优秀的 Agent 产品不只接受外部评估，还内建持续自我评估的基础设施。

### 3.1 消融

ML 研究长期用消融理解组件贡献：逐一摘除某个组件，看性能掉多少。

产品工程可以内置总开关，同时禁用多个主要特性（思考模式、上下文压缩、自动记忆、后台任务），创造「裸模型」基线。这样能回答：**某个特性真的改善体验，还是只是感觉有用？**

消融作为常规工程实践有几个要求：

- 开关必须在启动路径极早期注入——在任何模块级常量捕获配置之前，因此要从一开始设计进架构，而非事后加装；
- 定期运行（如每次大版本前），可以发现「特性债务」——曾经有效、随模型进化已不必要的特性；
- **每个主要特性都应可独立关闭，团队定期验证其实际贡献。**

### 3.2 AB 测试

**多臂而非二元**：不仅对比「有/没有」，而是设计多个渐进变体，揭示剂量-效应关系，帮助找最优点。

**区分机制指标与目标指标**：最容易犯的错，是把正在改变的东西当优化目标。例如测试「缩短计划文件长度」，计划长度是机制指标，真正目标可能是「降低会话级成本」。缩短计划可能降成本，也可能因计划不详细导致更多编辑-检查循环，反而增加总输出。始终问：**我改变的东西和我真正关心的东西是同一个吗？**

**设置护栏指标**：即使目标改善，如果满意度下降、操作次数增加或错误率上升，实验也应停止。

**记录基线统计**：样本量、分布百分位、相关性分析，为解读提供上下文。没有基线，无法判断显著性。

### 3.3 双层特性开关

特性开关是远程控制功能开启/关闭、无需重新部署的基础设施，同时服务实验、渐进发布与紧急熔断。

**编译时开关**在构建阶段把代码从产物中物理移除。内部特性在外部构建中根本不存在，逆向工程也发现不了；关闭不是运行时跳过逻辑，而是代码物理不存在。

**运行时开关**由服务端下发，本地磁盘缓存。宁可读到稍旧缓存，也不能让 Agent 等网络阻塞启动。分组决策由实验平台完成；每个特性的曝光事件在每个会话最多记录一次，避免重复污染数据。

对 Agent 开发者，特性开关不是调试工具，而是**一等架构组件**。

### 3.4 提示词敏感性

系统提示是 Agent 行为的核心「代码」，却常缺少与代码同等的版本控制与回归测试。

做法是提供专用工具，在指定 Git 版本上提取完整渲染后的系统提示——包含所有动态条件展开后的最终文本。这样能精确回答：哪次提交改了提示词？对评估集影响是什么？

建议实践：

1. 系统提示应能确定性渲染（相同配置输入，永远相同输出）；
2. 建立版本化快照；
3. 每次变更都在评估集跑回归，像代码变更跑 CI。

### 3.5 隐私感知分析

评估依赖好数据，但 Agent 产品处理的往往是敏感内容。可以用类型系统解决矛盾：分析接口只接受经特殊类型包装的值，类型名本身就是审计线索——明确表示「我已验证这不是代码或文件路径」。这把隐私约束从文档规范变成编译时强制检查。

核心原则：**从一开始把隐私约束设计进去，而非事后加装。** 隐私与评估不对立——隐私感知设计迫使你认真思考真正需要度量什么，反而催生更精准的指标。

## 4. 仿真环境：从评估到后训练

评估的终点不是打分，而是改进。改进有两条路径：调整 Harness，把评估嵌入产品工程；最深入的是训练。

当目标从「评估现有能力」扩展到「培养新能力」，评估环境就要演化为**仿真环境**：一个能让 Agent 反复练习、自动打分的虚拟操场。

与评估环境的核心区别：

- 交互频率高得多（数百万次 vs 数千次）；
- 需要随机化，防止死记硬背特定配置；
- 必须提供即时反馈。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-9.svg)

<p>图 3：仿真保真度谱</p>

评估资产可以近乎无缝转成训练信号：一套清晰的 Rubric 或验证器，本质就是**可验证奖励**（RLVR）的奖励函数——验证脚本直接就是奖励脚本。

但训练提出新要求：

- **可靠的 reset 语义**：每个 episode 必须重置到确定、干净的初始状态，否则梯度信号被上一轮残留污染；
- **远高于评估的吞吐**：评估几千次够出结论，训练要在可接受墙钟时间内喂给模型上百万次交互，环境并行度与单实例开销直接决定可行性。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-10.svg)

<p>图 4：OpenVLA 与 RoboTwin2 具身智能环境</p>

数字环境方面，AWorld 为 GAIA 构建可控的 MCP 服务器沙盒，26 个服务器、126 个工具函数，避免真实 API 封禁与不可控副作用；所有调用可重放、可审计。分布式架构把传统串行 7695 秒缩短到 525 秒（14.6 倍），无状态设计支持高效并行。

具身环境方面，RoboTwin2 基于物理引擎构建双臂操作，随机化物体位置、朝向、外观以提升泛化；观测包括多相机视觉与关节状态，通过动作分块实现实时控制。OSWorld 用虚拟机快照实现可重置，AndroidWorld 聚焦移动应用自动化。

仿真同样需要隔离执行环境与虚拟身份机制：VM/容器隔离、住宅代理、HITL 认证、共享文件系统。

### 4.1 保真度与领域随机化

高保真环境更容易迁移到真实世界，但计算开销大。另一维度是随机化程度：适度随机化提升泛化，过度随机化让任务过难。

**领域随机化**是缩小 sim-to-real gap 的关键：在物理参数、视觉外观、传感器噪声上引入大范围随机变化——好比在各种光照与角度下都练过抓取，真实环境不会因光线变化就失手。

数字环境中，sim-to-real 表现为界面渲染、响应时间差异，可通过引入延迟与失败随机化缓解。

## 5. 补记

评估体系真正的闭环是：**评估环境提供测试基础设施 → 数据集定义端到端与轨迹前缀任务 → 验证器与 Rubric 打分并归因 → Benchmark 与案例分析揭示方向 → 系统改进 → 更新环境与数据集**。

内部评估基础设施回答的是「哪项改动让它变好了」，外部评估回答的是「它有多好」。两者缺一不可：只有外部分数，改不动；只有内部实验，不知道在真实世界的位置。
