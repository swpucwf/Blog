# 四种更新载体

## 1. 经验应该写到哪里

学习信号说明 Agent 应当改变，但没有说明改变应发生在哪里。

- 事实与经验规律 → 知识文档；
- 能用语言清楚表达的策略 → 提示词或 Skill；
- 可精确执行的流程与硬约束 → 程序与 Harness；
- 高维感知、语言风格、隐式策略 → 模型参数。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig9-3.svg)

<p>图 1：持续进化的四种更新方式</p>

| 方式 | 适合承载 | 优势 | 局限 |
|---|---|---|---|
| 经验知识库 | 事实、规律、例外与来源 | 更新快、可追溯、按需检索 | 依赖检索与模型正确应用 |
| Prompt/Skill | 需要理解语境、例外与优先级，但能用语言说明的判断原则 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |
| 程序/Harness | 可确定解析、可执行验证、高风险硬约束 | 可测试、稳定、成本低 | 开发维护成本高 |
| 模型参数 | 高维感知、生成风格、隐式策略 | 泛化强、推理开销低 | 更新与回归成本高 |

四者不互斥。医疗影像 Agent 靠参数识别病灶，用知识库提供最新指南，用代码计算风险指标；客服模型的自然语气来自后训练，企业政策由知识与 Skill 提供，关键合规则由服务端代码兜底。

同一能力可以拆到多个载体：事实进知识库，解释例外的原则进 Skill，不可绕过的权限由程序门控，高维识别进参数。**路由结果只是更新提案，尚未获得发布资格。**

## 2. 将经验沉淀为知识

最轻量的进化方式，是把多次运行中反复出现的经验整理成可检索的知识文档。

它与第三章共享存储、索引与检索技术，但知识来源与验证目标不同：第三章从对话、文档、数据集提取「用户与世界是什么样的」；本篇从行动轨迹与结果提取「在什么条件下应该怎样做」。

例如：

- 「该航空公司要求特殊餐食提前 24 小时预订」是领域知识；
- 「订票前先检查特殊餐食截止时间，避免付款后才发现无法满足」是行动经验。

原始轨迹不适合作为正式知识单元：又长又嘈杂，包含工具原始输出、偶然绕路与环境细节。稳妥系统保留三层数据：

1. **不可变原始轨迹**：用于审计；
2. **单次运行分析**：本次成败与经验草案；
3. **多条同类轨迹的归纳**：面向未来的 Markdown 知识文档。

正式文档写清适用场景、推荐策略、禁止做法、例外条件、证据来源与最近验证时间，而不是复述某次任务的完整过程。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig9-4.svg)

<p>图 2：从已评价轨迹到经验知识文档</p>

这与 User as Code 的两阶段思路一致：先把事实追加到不可变日志，再周期性重建结构化模型。经验学习也先保存证据，再离线生成可变知识。把记录与整理分开，可以避免一次偶发成功或网络故障立即改变 Agent，也让系统在看到多条成败后再判断共性。

经验文档不是轨迹摘要。真正有迁移价值的内容来自对照：同类成功轨迹做了什么，失败轨迹缺少什么；某种策略在哪些环境版本有效，在哪些前置条件下失效。

五步提炼管道：

1. 保存不可变轨迹与环境结果；
2. 为单次运行生成结构化分析（任务类型、所需能力、观察到的策略、错误与例外）；
3. 按任务族聚合同类运行，为每条经验草案建立「哪些轨迹支持、哪些反驳」的证据表；
4. 只有达到支持门槛的草案才写入正式文档；
5. 在未参与提炼的新任务上测试迁移效果。

GAIA 经验学习是直观例子：旧做法是一次任务成功后立刻生成策略摘要并向量化入库；更严格的实现会先用答案验证或其他环境验证器标记成功、部分成功、失败，再比较同一任务族的多条路径。

成功轨迹贡献策略草案，失败轨迹贡献排除性知识，部分成功帮助识别「哪段有效、哪段仍有问题」。

自然语言反思可以参与生成草案，但**反思本身不是证据**；只有与环境结果相符、得到跨轨迹支持、并在新任务上显示正向迁移的内容，才进入正式文档。

## 3. 将经验写成指令

知识库提供「可以参考的资料」，Prompt 与 Skill 规定「应该怎样行动」。

当多条相似轨迹反复暴露同一种策略错误，而且错误能用语言清楚描述时，才值得把经验提升为指令。先分清三个概念：

- **系统 Prompt**：对所有任务生效；
- **Skill**：只在匹配到某领域或工具时按需加载；
- **程序/Harness**：权限与其他硬约束。

这种做法可称为**系统提示学习**：模型遇到问题后，用一句清楚的话提醒未来的自己。DSPy 在开发集搜索指令与示例；OPRO 根据历史提示词与得分提出提案；GEPA 从失败轨迹的自然语言反思中生成并筛选提示提案。

这些方法适合离线批量优化；生产环境更适合可审计的最小更新提案，并保留快速回滚。

系统提示学习与第二章的提示工程不是一回事：后者讨论怎样组织一份好 Prompt；前者讨论什么反馈足以触发修改，以及更新提案怎样安全发布。

修改应是带来源的最小 diff，而不是每次重写整份 Prompt。待验证版本必须同时在**触发失败的边界集**与**正常工作的保留集**上测试：前者要改善，后者不能退化。

### 3.1 转接边界的规则化

τ²-bench 的 telecom 政策中，关于转接人工只有两条原则性规定：请求超出动作范围时才转接，转接前应先尽力解决。

换用较弱模型运行，缺陷暴露：工具返回错误后 Agent 反复重试，最终转接人工，提炼集 20 条任务中 19 条如此结束。

把 19 条失败轨迹交给模型归纳，产出可执行规则追加到政策末尾，在未参与提炼的任务上重跑：通过率由 12.3% 升至 19.3%，原本通过的任务无一被改坏。

三个发现：

- **提炼材料决定能归纳出什么**：只给失败摘要，模型归纳出「同一工具反复报错即不应继续调用」；补充双方工具清单后，归纳出「网络状态、SIM 卡、APN 属于用户设备侧，应引导用户操作而非直接调用」。前者是教训，后者理解职责归属。
- **模型会把观察到的行为当作应然**：第一版有「连续三次失败即转接」「用户两次未提供号码即转接」——轨迹中最频繁的正是转接，模型据此视为合理兜底；但这套评估中转接必然失败，等于把失败写进规范。**提炼产物不能直接发布，须经独立验证。**
- **被修复的往往是极朴素缺陷**：基线中 Agent 需要用户电话，却把「请您提供电话号码」填进查询工具参数，连续五次报错后转接。规则生效后，它先在对话中提出请求，取得号码再查询；检查 SIM 卡被拒后，转而引导用户重新插拔，任务通过。

同样的方法可移植到航空客服：普通政策争议不应转接，只有用户明确要求人工或安全相关情形才必须转接；修法是一条带出处的最小规则。

### 3.2 需求澄清 Skill

用户说「把登录页改成支持企业登录」，立刻开工可能替用户在身份提供商、回退方式、兼容范围上做未考虑的选择；无论任务大小都问十几个问题，又把修改变成访谈。

**问得太少会返工，问得太多会打扰。**

初版流程：判断歧义、风险与返工成本 → 低风险小改动说明假设直接执行 → 涉及架构、数据、权限、公开接口或大范围改动时，集中提出少量真正改变方案的问题 → 生成短 Spec/Plan（目标、非目标、取舍、假设、验收）→ 确认后执行，发现 Spec 不成立时暂停重确认。

持续进化从证据开始：记录任务、澄清问题、Spec 版本、用户修改、执行结果与返工。负反馈可能是「做出来和我想的不一样」或「你问得太多」；正反馈包括一次确认顺利交付、主动改 Spec 减少返工、低风险任务没被多余问题打断。

单独一句抱怨不足以触发更新，必须把反馈与具体轨迹、任务类型、结果关联。

多条轨迹指向同一缺口时，提出最小 Skill 更新：多个认证架构任务都在交付后发现要兼容旧登录，规则草案要求执行前确认「身份提供商、回退路径、兼容范围」；大量拼写修复都被先问一轮，则收窄高风险/高歧义触发范围。

验证要比较「直接执行」「先问再执行」「先问 + Spec 确认」三种策略，并按复杂度分层。指标至少包括需求偏差率、返工次数、澄清轮数、首次有效产出时间、用户放弃率、Spec 修改比例、高风险操作错误率。只有减少偏差且没显著增加打扰，并在未参与提炼任务上通过回归，才进入灰度。

边界也要分清：Skill 负责理解语境、提问、整理 Spec、说明取舍；Harness 负责在缺少确认时否决高风险写入、直接操作 `main` 或绕过发布流程。**否决器不能替模型决定 PR 怎么写，也不能代替模型选择需求方案。**

## 4. 将经验写成程序

当经验描述的是稳定、重复且可验证的操作，每次让模型重读文档并推理并不经济。更合适的做法是把经验编译为工作流、工具或 Harness 代码，使一次探索变成可重复执行的程序。

可修改对象远不止新工具：

- **操作层**：把浏览器轨迹编译为参数化工作流，或为变化的 API 生成适配器；
- **控制层**：修改工具路由、重试、熔断、上下文压缩；
- **验证层**：新增参数检查、状态验证器、回归测试；
- **架构层**：增加 Reviewer Agent，改变规划与执行的信息流。

### 4.1 浏览器工作流

可以类比电子表格的宏录制：第一次发邮件时，多模态 Agent 通过观察—思考—行动寻找「撰写、收件人、主题、正文、发送」；以后发另一封邮件，流程不变，只有收件人与内容不同，没必要再调用模型从像素和 DOM 重新发现整条路径。

把第一次探索的轨迹编译成带参数、状态检查与版本信息的小程序：

1. **捕获轨迹**：记录导航、点击、输入、选择，保存参数、URL、XPath/CSS 定位证据；定位只用于再次寻找，不能证明任务完成；
2. **参数化**：把字面量识别为模板变量，如 `{recipient}`、`{subject}`、`{content}`，其余稳定动作不变；
3. **定义状态检查**：动作前后检查（「发送按钮可见」）与整个工作流最终状态检查；动作成功与任务成功是两件事；
4. **独立回放验证**：把沙盒账号/测试站点重置到独立初始状态，完整回放，所有检查通过才发布；
5. **匹配与回放**：新任务按意图与关键词匹配工作流，提取参数，由 Playwright 直接执行，不逐步调用 LLM；
6. **失效与重学**：找不到元素、状态检查失败、Schema 改变或最终状态错误时，回退完整 Agent 重新探索。

这类程序在重复任务上实现了 8.5–13 倍端到端加速。更重要的结论是：**流程记忆必须同时具备动作前验证、动作后验证与独立回放验证**，否则会得到危险假象——每个按钮都点过，但某字段为空，任务从未完成。

Agent 修改自己的代码不意味着运行中的进程直接覆盖自身。生产系统应从稳定版本创建隔离更新分支，由 Coding Agent 生成最小补丁，依次通过静态检查、单元测试、安全扫描、失败轨迹重放、旧任务回归，再生成可灰度部署的新版本。

这把「自我修改」转化为可审计的软件发布流程。Git worktree 与 Pull Request 是好例子：Skill 指导 Agent 建 worktree、确认 Spec、实现测试、提交有意义的 commit、写清背景/方案/测试/剩余风险；Harness 在准备结束时检查是否直接在 `main` 提交、是否遗漏 worktree/PR，违反就否决。

仅有「补丁尽量小」还不足以支持归因。每个修改请求还应是一份**可证伪的变更契约**：失败证据、推断根因、归属组件、修改提案、预期修复行为、可能受损的既有行为、分别验证两者的用例。

提案输入也不应只有失败案例。Self-Harness 还会提供必须保留的成功行为与此前被拒绝的修改记录：前者告诉 Agent 哪些性质不能在修复时破坏，后者避免换个说法重复提交已失败方案。

工具创造遵循同一协议：Agent 缺字幕读取能力时，搜索并测试 `youtube-transcript-api`，封装为新工具；只有安全扫描、功能测试、后续任务复用都通过，才进入能力库。

### 4.2 一切皆插件：可组合性

DeepSeek Harness 把模型适配器、工具注册表、会话日志乃至 Agent 主循环本身都做成插件——**不存在只能由人类维护的特权内核**。

底座的 Cordis 论文指出：传统组合是**静态**的，函数调用、模块导入、类继承在编译期确定；插件系统与自进化 Harness 需要**动态组合**，组件要在运行中被装入、卸下和重新配置。

动态组合拆成两个正交维度：

- **时间可组合性**：组件被移除时，对共享环境做过的修改能否完整、安全地撤销——要求运行时追踪每次资源分配、事件注册与状态变更；
- **空间可组合性**：组件之间能否以结构化、可验证方式声明、发现和解析依赖，并在依赖变化时协调生命周期。

前者关心「改了什么」，后者关心「依赖什么」。

自进化 Harness 是最尖锐的场景：要撤销的副作用长期存活、带状态；要解析的依赖会在运行中出现、消失或改变身份。缺少时间可组合性，每次自我修改都要整体重启，丢掉进程内状态；缺少空间可组合性，一次代码替换可能静默破坏依赖方，或引入循环依赖。

Cordis 把两个编译期概念提升到运行时：**可撤销效果**（每次上下文变换携带显式逆操作）与**反应式协效果**（组件把依赖声明成规格，上下文变化时按规格通知激活/失活）。可组合性必须可传递。

**自我进化的上限，不取决于模型能写出多好的代码，而取决于承载它的系统有多强的可组合性。**

可组合性解决「能不能安全装卸」，没解决「该不该装」：模型写出的插件只活在进程内存，重启即消失，**不能被自动提升为正式插件**，必须另走 worktree + PR 那条更慢的路。

运行中的插件还会改变模型可见的工具集与提示片段，请求前缀一变，KV Cache 从变化处失效——插件文档需专门描述对上下文与缓存的影响。

## 5. 将经验写入参数

知识、指令、程序都建立在一个前提上：能力能被外部符号较完整地表达。

医疗影像理解、自然语音韵律、消除文本模板化「AI 味」、长程规划等能力，很难压缩成几条规则或工作流，必须通过后训练写入参数。

弯引号的作用域判断处在中间地带：文档语法边界可由程序解析，语境与例外需要 Skill，跨任务的识别习惯才适合后训练内化。

是否参数化不由「任务是否长期稳定」单独决定：新影像设备带来的域偏移仍可能需要 LoRA；快速变化的语言风格也可以通过周期性偏好训练适应。稳定性影响更新频率与成本，真正决定载体的是**能力的表示性质**。

对持续进化而言，关键是把经过评价的生产轨迹转化为训练数据：高质量示范进 SFT，明确偏好形成成对数据，有可靠环境奖励的交互用于 RL。

## 6. 从更新产物到更新「更新方法」

四种方法讨论经验**写到哪里**；另一条正交轴是：系统优化的是某份产物的内容，还是产生、管理、验证产物的方法。

优化对象可逐层扩大：**单条规则/记忆 → 结构化上下文 → 工作流 → Harness 代码 → 产生更新提案的优化器代码。**

这不是五种新载体，而是五种搜索尺度；知识、Prompt、Skill、程序都可能出现在多个层级。

最内层只改产物内容：给系统提示加一条局部规则，给经验文档补一个例外。作用面小、易归因回滚，应是默认选择。

但反复让模型重写整份 Prompt 会产生退化：为追求简洁，旧版本的重要细节可能在多轮改写后消失；相互制约的条件可能被合并成一句过度抽象的原则。Agentic Context Engineering 把上下文维护成带稳定标识符的条目集合，由生成、反思、整理模块提出增量更新，再用确定性逻辑合并去重，而不是每轮重写更短的文本块。

再外一层，优化对象不是「上下文里有什么」，而是「上下文应怎样构造」。Meta Context Engineering 分内外循环：内层在给定管理方法下优化当前上下文产物；外层根据多轮执行与验证结果，修改搜索、选择、过滤、格式化这些操作本身。

同一思想扩展到工作流与整个 Harness：AFlow 把多个 LLM 调用组成的工作流表示为代码图，通过执行反馈搜索节点与控制流；Meta-Harness 让 Coding Agent 读取待验证 Harness 的源码、分数与轨迹，搜索决定信息如何存储、检索、呈现的代码。

**代码不只是生成产物，还可以连同评估历史成为持续搜索的对象。**

外层搜索很快遇到反馈成本：探索策略决定从哪个候选继续、何时分支、并行多少 Worker、何时停止，其好坏要经过很长的生成—评估链条才能显现。

Dream-RSI 把已完成的发现过程保存为**发现树**，再把树当作经验性的**回放模拟器**：根节点是初始工作区；子节点保存从某历史状态继续尝试后的工作区快照、候选产物、诊断与分数。候选策略通过与在线探索相同的接口选择叶节点或开新分支；回放器只揭示节点中已记录的结果，不必再运行底层 Agent 与评估器。

关键是：在线与离线使用相同决策接口，并且只逐步揭示已展开子树。在线阶段被选中节点真正调用 Agent 与评估器；离线阶段相同选择只返回历史后继。策略因此能比较分支、顺序、并行批次与停止时机，又不能偷看未来结果。

三阶段递归闭环：**在线探索**生成新发现树 → **构造回放世界**把树加入历史池 → **离线做梦**让策略开发 Agent 修改探索策略代码，按候选质量、执行成本、并行效率比较版本。入选策略上线后产生新树，扩大下一轮回放范围。

历史回放不是第五种载体，而是**产生并验证更新提案的新机制**。它最终修改探索策略代码，产物仍属程序/Harness；新意在于把过去从上下文或训练数据，变成可反复交互的离线评估环境，把自我进化推进到「如何分配探索计算」的元策略层。

## 7. 补记

四种载体的选择，先看**能力的表示性质**，再看稳定性与成本：

- 能被符号完整表达、需要频繁更新 → 知识；
- 需要语境判断但能用语言说明 → Prompt/Skill；
- 必须不可绕过、可确定验证 → 程序；
- 只能靠高维感知或隐式策略 → 参数。

最容易犯的错，是把所有经验都写进 Prompt。Prompt 会膨胀、冲突、被忽略；能用代码强制的硬约束，放进 Prompt 只是建议。
