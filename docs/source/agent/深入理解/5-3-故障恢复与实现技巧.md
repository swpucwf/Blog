# 故障恢复与实现技巧

## 1. 四层故障

生产级 Harness 首先要把故障分类。按发生位置分四层：

- **API 层**：限流（429）、服务过载、请求超时、连接中断、输出触顶被截断。与任务内容无关，是基础设施噪声。
- **工具层**：幻觉调用（工具不存在）、参数畸形、执行抛异常，以及最危险的一种——工具反复返回同一错误，模型不加改变地反复重试。
- **上下文层**：窗口溢出、压缩失败、轨迹结构损坏（工具调用缺少配对结果）。
- **控制流层**：死循环（反复执行相同操作却无进展）与死亡螺旋（错误恢复逻辑自身又调用 LLM、再次出错、连锁反应）。

## 2. 检测：先分类，再计数

捕获故障后，第一个判断不是「要不要重试」，而是「值不值得重试」。

- **可重试**：限流、过载、网络抖动。重试才有意义。
- **不可重试**：参数不合法、权限不足、工具不存在。原样重试多少次都是同样结果，必须改变输入或策略。

生产级 Harness 维护一张「错误 → 恢复策略」映射表，而不是笼统地「出错就重试」。

单次错误之外，还要检测**模式**：

- **重复调用指纹**：对「工具名 + 参数」计算指纹，相同指纹反复出现就是无进展循环的明确信号；
- **连续失败计数**：每条恢复路径独立计数，为熔断提供依据。

### 2.1 活性与完整性监控

还有一类故障不表现为错误，需要专门监控。

**活性**：流式连接最危险的失败不是断开（会立即报错），而是静默卡死——连接建立成功但数据流停止，像水管通着却不出水。SDK 超时往往只覆盖初始连接，不覆盖传输过程。生产级 Agent 需要独立的空闲看门狗：超过设定时间没有新输出就判定卡死，主动杀死挂起的流并触发重试。

原则：**每个长连接都需要活性信号，不能只依赖连接超时。**

**完整性**：轨迹结构可能损坏，例如工具调用缺少配对的结果消息。系统会在注入上下文前自动修复配对，而不是把结构异常抛给模型或用户。

一个工程细节：部分生产级 Agent 同时运行产品模式与训练数据收集模式——产品模式下可以用占位符修补缺失消息，训练模式下则拒绝修复，因为合成占位符会污染训练数据。「产品宽容、训练严格」的双重标准，体现 Harness 与模型训练的深度耦合。

## 3. 恢复：分级升级，逐级透明

恢复手段按对用户透明的程度分级，能用低级别解决就不升级。

### 3.1 静默重试

可重试错误的默认动作。两个细节决定成败：

- **指数退避叠加随机抖动**，避免大量客户端同步重试造成二次拥塞，并尊重服务端返回的等待时长；
- **区分前台与后台**：主循环请求失败要重试；标题生成、输入建议这类辅助后台调用失败则直接放弃，否则后台重试会挤占主链路配额，形成「重试放大」。

### 3.2 降级与接续

重试无效时，改变请求本身再试。

以输出触顶为例：先静默提升输出上限重发；仍不够，再在消息末尾追加元指令，让模型从断点接续生成。

主模型持续过载时降级到备用模型——需先剥离旧模型私有的格式块，否则新模型无法解析历史消息。高成本模式被限流时，暂时回落到标准模式。

### 3.3 暴露给用户

所有自动手段用尽后才呈现错误，并附上已经尝试过的恢复动作。

### 3.4 工具错误走另一条路

**不终止会话，把错误变成模型的输入。**

- 幻觉调用收到「工具不存在」的结构化错误结果；
- 参数校验失败收到附带输入约束提示的错误；
- 畸形参数（本该是对象却输出字符串）在执行前先经过程序化修复。

这些错误以普通工具结果的身份进入上下文，由模型下一轮自行纠正。**喂回的错误越具体，自我纠正成功率越高。**

核心原则：**错误处理的边界不是单次请求，而是整个恢复循环。** 在确认无法恢复之前，中间错误不应暴露给消费者——恢复期间扣留错误消息，恢复成功则用户毫无感知，全部失败后才统一呈现。

## 4. 接管：把没跑完的轨迹交给另一家模型

主模型持续不可用时，需要换一家把轨迹接着跑完。真正的障碍不是接口地址，而是轨迹里有一部分只属于原厂商。

工具调用与结果各家结构不同但语义一致，重新渲染即可；难办的是模型的思考。思考通常由两部分构成：可读的文字，以及厂商附在其上的凭证，用来证明这段思考确实出自它自己。

**跨厂商接管能带走的是文字，带不走的是凭证。**

各家对凭证要求不一：宽松的不校验，严格的拒绝一切非自己签发的凭证；凭证还可能附在工具调用上。于是「把思考删干净就安全」这条策略，在某些厂商那里反而通不过。

接管方案只能按最严格的一端设计，并为满足不了的情形准备退路：把历史工具调用改写成文字叙述，模型不再把它当作真正调用过的工具，但至少能接着往下跑。

由此得到一条设计原则：**轨迹不该按任何一家的接口格式存储，而应保存为一份中立格式。**

- 每段思考拆成可移植的文字与不可移植的凭证；
- 工具调用只记录名称与参数，标识符在渲染成具体请求时按目标厂商重新生成；
- 切换时凭证一律丢弃，文字以普通内容身份带入，而不是塞回目标厂商放思考的位置。

厂商返回的思考摘要本就是为这种场合准备的可移植副本，保留即可，不必再调用模型压缩。中立轨迹的价值也不限于故障切换：评估重放、训练样本构造、经验提取，依赖的都是同一份产物。

## 5. 终止：每条恢复路径都要有上限

恢复机制本身也可能失效，因此每条路径都必须有熔断上限：

- 上下文压缩连续失败若干次就放弃压缩；
- 权限分类连续失败就回退到人工询问；
- 输出接续最多尝试固定轮数。

阈值从生产数据来，而非拍脑袋。以压缩熔断为例，「连续 3 次」来自真实会话统计——曾有一个会话在这条路径上连续失败三千余次，仅这类无效重试每天就造成约 25 万次 API 调用浪费；逾千个会话出现过 50 次以上的连续失败。3 次正是「绝大多数故障此前已恢复」与「继续重试基本无望」之间的经验拐点。

比单点熔断更隐蔽的是**死亡螺旋**：错误处理路径中的逻辑本身又调用 LLM，再次出错，引发连锁。一个真实案例是：Agent 因上下文溢出停止，触发「结束时自动提交代码」的停止钩子，钩子调用 LLM 生成 commit message，再次溢出，又触发钩子。

防护靠两条：

- 在错误路径上禁用一切会再次调用模型的副作用逻辑（宁可丢掉一次辅助功能，如自动记忆提取）；
- 用递归深度计数器检测并打断残余连锁。

最后还需要全局终止条件：最大迭代轮数、会话预算上限、连续失败超过阈值升级人工。

## 6. 五条实现技巧

工作流是理想状态，真正跑起来还要在保证思考质量的前提下提速、降耗。

### 6.1 并行调用、流式执行与级联中止

串行模式「生成调用 → 执行 → 等结果 → 再决定」浪费大量时间。流式响应下，第一个工具调用的参数一经完整生成并通过校验，就可以立即执行，无需等后续调用生成；彼此独立的调用还可并行。

并行执行要配故障处理：每个工具声明是否支持并发（默认否，失败安全）；某个调用失败时，级联中止同一批并行启动且依赖它的调用，但不波及独立调用与父级操作。

### 6.2 上下文精细化管理

代码库通常很大，上下文有限。即使模型号称支持百万 token，把整个库塞进去也不经济。

- **文件读取**：支持按行号范围读取，而不是每次加载全文；返回内容附行号前缀，模型可精确引用「`src/main.py` 第 42 行」，后续编辑更可靠。
- **命令输出**：编译或测试可能产生数千行。保留头部（错误上下文）与尾部（错误总结），中间用一行提示替代，完整输出存临时文件按需读取。

### 6.3 环境信息动态注入

Coding Agent 高度依赖执行环境。每次推理前，在上下文末尾以状态栏形式注入：

- 当前工作目录；
- Git 分支；
- 最近提交记录；
- 未暂存与已暂存的变更概览。

这些信息不应硬编码进静态系统提示词——会破坏 KV Cache——而应作为动态、追加式的状态栏注入。

### 6.4 命令执行环境的状态持久化

许多操作依赖环境状态：切换目录、激活虚拟环境、设置变量、启动后台服务。如果每条命令都在全新 shell 执行，状态全丢——刚 `cd` 到项目目录，下一条又回到根目录；虚拟环境激活只对当前会话有效。

应维护一个持久化终端会话，Agent 启动时创建，整个交互期间保持活跃。每条命令都在共享终端中执行，保留工作目录、环境变量与会话状态。这也更符合人类开发者的习惯——我们通常就在一个长期运行的终端里工作。Agent 仍应保留启动隔离终端的能力以支持并行任务，但持久化会话是默认。

### 6.5 即时语法反馈

修改代码后，不应等用户要求测试才检查语法。更高效的做法是：文件写入完成，工具层立即运行对应 linter，把结果作为返回值的一部分。

如果检测到语法错误，模型下一轮就看到了详细错误——像程序员在 IDE 里打错括号，编辑器立刻画红线。错误在引入的那一刻被修正，成本远低于等到运行测试才发现。

## 7. 补记

故障恢复的核心不是「重试」，而是**分层决策**：先判断错误类型，再选择恢复级别，最后设置熔断与终止。没有分类的重试会把可重试故障和不可重试故障混在一起，既浪费时间，也可能放大副作用。

另一个经验是：**恢复逻辑本身要按「可能失败」设计**。它会调用模型、写文件、触发钩子，任何一环都可能再次出错。错误路径上禁用副作用、加递归深度限制，比事后排查死亡螺旋便宜得多。
