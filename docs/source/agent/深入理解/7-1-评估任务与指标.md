# 评估：从任务解剖到成功定义

## 1. 评估的对象是模型 + Harness

构建 Agent 时，开发者面对大量没有显然答案的选择：用什么模型、给哪些工具、知识库怎么建、记忆怎么做、提示词与 Skills 如何组织、Harness 加哪些约束。

评估提供科学依据：通过**对比实验**（改变一个变量）与**消融实验**（逐一关闭组件）区分真正的能力提升与表面波动。没有可重复的评估，迭代方向只能靠直觉。

关键认识：**评估对象不应只是模型，而是模型与 Harness 的组合。** 同一个模型在不同 Harness 中可能表现悬殊；一些团队仅优化 Harness 就显著提升了同一模型在终端任务上的表现。

当 Agent 表现不佳时，改进方向可能是换模型，也可能是优化 Harness 的提示词、工具或反馈循环。完善的评估要能区分「模型能力不足」与「Harness 设计缺陷」。

常见手段是**模型替换实验**：固定 Harness，只换更强/更弱的模型。

- 换强模型分数不涨 → 瓶颈在 Harness；
- 换弱模型分数大跌、分数随模型能力大幅波动 → 瓶颈在模型能力本身。

这与消融实验不同：消融是关闭 Harness 的某个组件，定位「哪个部件重要」；模型替换是固定 Harness 只换模型，区分「瓶颈在模型还是 Harness」。

模型快速演进时，公开基准更好不代表在你的任务上更好，甚至可能退化。只有在自己评估集上完整测试，才能做数据驱动的升级决策。完善的评估还让「为未来模型开发产品」可行：先完成产品与评估集，持续追踪新模型，达到门槛就上线。

## 2. 解剖一条评估任务

以 τ²-bench 的 telecom 任务为例，一条任务定义包含四部分。

### 2.1 工单与用户认知边界

```jsonc
{
  "id": "[mobile_data_issue]airplane_mode_on|user_abroad_roaming_enabled_off",
  "ticket": "用户手机无法上网，状态栏显示 'No Service'。客户 John Smith，
             号码 555-123-2002，当前在法国。速度测试结果为 excellent 才算解决。",
  "user_scenario": {"instructions": {
    "known_info": "You are John Smith... currently abroad in France.",
    "unknown_info": null,
    "task_instructions": "…express mild frustration after the first unsuccessful attempt.
      You will consider the issue resolved only when speed test returns excellent...
      Whenever the agent asks you about your device, always ground your responses
      on the results of tool calls. Never make up the results of tool calls."
  }},
  "initial_state": {"initialization_actions": [
    {"env_type": "user", "func_name": "turn_airplane_mode_on"},
    {"env_type": "user", "func_name": "turn_roaming_off"},
    {"env_type": "assistant", "func_name": "enable_roaming", "arguments": {...}}
  ]},
  "evaluation_criteria": {
    "actions": [{"requestor": "user", "name": "toggle_airplane_mode"}, ...],
    "env_assertions": [
      {"func_name": "assert_mobile_data_status", "expected_status": true},
      {"func_name": "assert_internet_speed", "expected_speed": 200, "expected_desc": "excellent"}
    ],
    "communicate_info": null,
    "nl_assertions": null,
    "reward_basis": ["ENV_ASSERTION"]
  }
}
```

四处设计值得说明：

**显式建模用户认知边界。** `known_info` 只有姓名、号码、所在国家；真正的故障原因（飞行模式开启、漫游关闭）不在其中——用户不知情，无法主动陈述，Agent 只能通过提问与引导查询获取。这是**渐进式信息透露**在任务定义层的实现：不靠「不要一次说完」的提示词，而是把用户知识范围建模为独立字段。

多数基准在任务开始就给出完整需求，而真实用户最初往往只说「我上不了网」。把需求澄清到可执行，本身就是 Agent 的能力。

**防止用户模拟器被忽悠。** `task_instructions` 有三类约束：情绪设定（首次失败后轻度不满）、验收口径（只有 excellent 才算解决）、**事实锚定**（设备状态回答必须以工具返回为依据）。缺少事实锚定，模拟用户会顺着 Agent 的引导确认问题解决，评估退化为两个模型互相确认。

**双方都不具备完全信息。** 飞行模式与漫游开关在用户侧，运营商侧 `enable_roaming` 在 Agent 侧。运营商侧已开通、用户设备侧却关闭，Agent 查数据库只能得到「配置正常」——故障位于数据库不可见的一侧，只有引导用户查询才能发现。

**多维度校验。** `env_assertions` 检验终态，`actions` 检验关键动作，`communicate_info`/`nl_assertions` 检验必要信息是否告知。每个任务可检查一个或多个维度。

### 2.2 双控与失败轨迹

一次成功运行中，前十余轮是账户识别。Agent 依号码查到客户，逐一查线路流量，第 17 条给出错误结论：「号码不在活跃线路中」——仅基于一条线路。用户坚持后，Agent 查另一条才对上。

关键转折在第 30 条：**用户**调用了 `check_network_status()`、`check_status_bar()`，工具返回「飞行模式 ON、移动数据开启、漫游关闭」，用户转述并询问是否关闭飞行模式。

发出工具调用的是用户，不是 Agent。这就是**双控**：模拟用户拥有独立工具集——查状态栏、开关飞行模式、重插 SIM、测速。故障正好位于用户侧，Agent 只能引导用户操作。

其后 Agent 要求关闭飞行模式与漫游，用户执行，状态转 5G；测速 275 Mbps、Excellent，两条断言通过，reward=1.0。

这条满分轨迹还含一处未被验证器捕获的问题：政策要求「一次只发一个工具调用」，Agent 第 4 条同时发了两个。验证器没判错，因为本题 `reward_basis` 只看最终状态。这是二元奖励的固有代价：以过程颗粒度换取跨模型可比的单一数字。

失败任务也值得分析：用户号码对应 L1002，Agent 却选 L1001；`get_details_by_id` 明确返回 L1001 的号码是 555-123-2001，Agent 读到却未修正，此后在无关排查上消耗数十条消息，最终转人工。它完成了任务的一半，但线路选错导致流量充值未执行，终态断言全部失败。

**修正判断所需的证据已进入上下文，Agent 未据此回溯。**

## 3. 成功的定义：Pass@k 与 Pass^k

五条任务通过四条，0.8 这个数字本身无法判断系统是否可用。若对应退款客服，每五名用户就有一人没拿到退款；若对应漏洞挖掘，五次命中四次已很可观。差别在业务场景对成功率的要求。

### 3.1 Pass@k：能力上限

许多模型与 Agent 仍处在「技术奇观」阶段：在大量尝试、充足时间与人工筛选下展示能力上限——只要一次成功，就证明「原则上做得到」。

这正是 **Pass@k**：同一任务运行 k 次，至少一次通过即算通过；连续得分则取最好一次，记为 Best@k。

对科研发现、漏洞挖掘、开放式创作，这种上限本身有价值：人类可以从 k 条候选里挑最好的一条。早期 Manus、OpenClaw 完成复杂任务的成功率并不高、成本也高，但通用性强、Pass@k 高，技术上限被大量分享。

### 3.2 Pass^k：业务可靠性

真实业务更关心「多次尝试一次错都不能犯」。

**Pass^k**（Pass consecutive k）：同一任务连续运行 k 次，要求每次都通过，且不能触发安全、合规或幻觉等一票否决项。它回答「能否稳定可靠交付」，而不是「能否偶尔创造奇迹」。

若每次独立、单次成功率 p：

\[
\mathrm{Pass@k}=1-(1-p)^k,\qquad \mathrm{Pass}^{k}=p^k
\]

p=0.6、k=5 时，Pass@5 ≈ 99.0%，看起来几乎总能至少成功一次；Pass^5 ≈ 7.8%，说明连续五次都不出错仍然很难。

前者适合衡量探索时的能力天花板，后者才接近支付、退款、权限变更、生产部署的可靠性要求。报告必须写清口径：是同一任务的 k 次独立采样，还是生产流水线上连续 k 个任务。对会产生副作用的操作，不能「重试直到成功」，而应在沙盒或可回滚环境采样，并把每次失败记入可靠性指标。

## 4. 补记

评估的第一个陷阱，是只测模型不测 Harness。模型替换实验与消融实验要配合使用：一个判断瓶颈在哪一层，一个定位具体哪个组件。

第二个陷阱，是把 Pass@k 当成业务可靠性。探索阶段看上限，生产阶段看连续无错；两者混用，会导致「看起来很强，实际不可用」。
