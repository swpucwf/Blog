
## 上下文工程
上下文的设计和管理—— 即上下文工程（Context Engineering）——不管怎么强调都不为过。所谓上下文，就是**每次你和 AI 对话时，AI 实际“看到”的全部信息。它不仅包含你们之前聊了什么（对话历史），还包含开发者预先写好的行为规则（系统 指令）、AI 可以使用的外部功能说明（工具描述）等各类信息。** 从 Harness 工程视角来看，上下 文工程是 Harness 中“上下文与工具”层面的核心实现——它决定了 Agent 在每个决策点能看到什么信息、以什 么样的结构看到这些信息。一个设计精良的上下文就是一套高效的信息供给系统，让 Agent 的通用思考能力得 以在具体任务中充分发挥。

### 1.1 上下文：决定 Agent 能力上限的关键

**上下文质量决定 Agent 的能力上限**。大模型通用能力强，但缺失业务专属背景信息（产品架构、业务规则、团队规范），导致标准测试效果优异、实际业务落地拉胯。 以 Coding Agent 为例，Agent 完成任务依赖三类核心必备上下文：**实时代码上下文**（目录结构、模块职责、数据结构、代码规范）、**流程规范**（Git 分支策略、提交规则、审读流程、CI/CD 要求）、**环境信息**（开发配置、测试环境、部署规则、密钥管理）。缺失任意一类，会导致代码风格冲突、违规提交、环境报错等各类问题。

上下文工程不只是简单堆砌提示词信息，而是**系统性设计、组织、供给 Agent 所需全部背景知识**的工程体系。其本质兼具双重属性：既是技术问题，更是**组织问题**。团队隐性知识（老员工经验、口头业务规则、私有沟通信息）无法沉淀，是 Agent 能力受限的核心原因。

**文档透明、结构化、可检索的团队协作模式天然适配 AI Agent**，如开源 Linux 内核项目，公开透明的决策记录与文档体系，为 Agent 提供完整上下文支撑。

- AI Agent 如同永久新员工，**充足、精准的上下文是其高效工作的前提**。搭建 AI 原生团队的核心是**完成团队知识文档化、结构化沉淀，而非单纯堆砌工具**。
- 核心结论：**人和模型的核心竞争力都是 Context**。团队协作冲突、AI 无法完全替代人类的核心原因，均来自**上下文不一致、环境信息不互通**。上下文工程的终极目标，是将 Agent 所需的背景信息结构化、系统化供给模型使用。
