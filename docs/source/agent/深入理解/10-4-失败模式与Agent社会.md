# 失败模式与 Agent 社会

协作能力与新型故障是一起引入的。这一篇先把多 Agent 系统最常见的几种坏法整理清楚，再把视角从「一组 Agent 完成一个任务」推到「大量 Agent 长期共存」——那里会出现一些无法预先设计的东西。

## 1. 十四种失败模式与拜占庭故障

2025 年的《Why Do Multi-Agent LLM Systems Fail?》在 MetaGPT、ChatDev、AG2、Magentic-One 等 7 个主流框架上收集执行轨迹，由人工标注员逐条分析约 150 条轨迹（标注一致性 Cohen's kappa = 0.88，说明不同标注者对失败模式的判断高度一致），归纳出 **14 种失败模式**，分三大类：

- **系统设计缺陷**：接口定义不清、角色职责重叠、工具配置错误等架构层面的问题；
- **Agent 间对齐失败**：多个 Agent 对目标理解不一致、传递的信息被下游误解、操作在逻辑上相互矛盾；
- **任务验证缺失**：缺少确认任务真正完成的机制，Agent 声称「已完成」但结果不符合要求。

即使采用简单修复，效果也十分有限（ChatDev 框架仅提升 15.6%）。研究者据此认为，这些不是简单的工程 bug，而是当前多 Agent 架构的**根本性设计缺陷**——补某个环节不够，得从系统设计层面重新想。

分布式容错理论把故障分两类：**崩溃故障**（部件停止工作）与**拜占庭故障**（部件继续工作，但给出错误信息）。传统分布式系统大多只需防崩溃；Agent 的故障却天生是拜占庭式的——它很少径直停掉，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。这也解释了后文反复出现的交叉验证与多数表决，它们都是拜占庭容错的经典手段。

## 2. 六种常见失败模式

### 2.1 共享文件系统的并发冲突

一旦选择共享内存式通信，并发冲突就随之而来。冲突有两类。

**简单冲突（文件级写入冲突）**：两个 Agent 同时改同一个文件，后写的把先写的覆盖了。

**语义冲突（逻辑级一致性冲突）**：文件层面看不出冲突，但操作在逻辑上矛盾，更隐蔽也更危险。比如 A 负责重编全书图片编号，B 同时在改某一章并引用原编号——两者操作的是不同文件，文件层面毫无冲突，但 A 完成后 B 的引用全部失效，读者看到的是错误的图片。

**乐观锁**能解决前者：每个文件维护版本号或最后修改时间戳，读取时记录，写入时校验是否仍一致；不一致就失败，Agent 被迫重读最新版本再重做。代价是偶尔重试，换来一致性保证。

但它只能防**同一文件**的写入冲突。跨文件的语义冲突需要更高层的语义校验。在多个 Coding Agent 并发改同一代码库这个最常见场景里，业界主流做法是**工作副本隔离**：为每个 Agent 分配独立 Git 分支或 worktree，各改各的，把冲突集中推迟到最后的合并点。

### 2.2 错误的级联放大

进程间传字节，逐位保真；Agent 间传语义，每转述一次都是有损的重新编码。多个 Agent 频繁互动时，一个错误可能被逐层强化，像「传话游戏」里信息越传越走样。

**交叉验证**是打断这条链的关键。核心不是让更多 Agent 参与同一条思维链，而是让某个 Agent 以**独立视角**重新审视结论：不看前序 Agent 的思考过程，只看原始证据与最终结论是否一致。这也是提议者-审核者机制在多 Agent 场景中的延伸。

### 2.3 同质趋同

错误不一定沿通信链传播，也可能由多个同质 Agent 各自独立产生。Anthropic 的实验里，30 个同时上线的 Agent 有 18 个创建了同名 Git 分支；写作实验中，不同 Agent 还会不约而同用相同标题。这类由共同模型与脚手架引发的**共因失效**意味着：同一模型、相似上下文生成的多个审核意见，不能自动视为相互独立的证据。

系统要有意识地引入模型、上下文与数据来源的差异，同时用命名空间、资源配额与速率限制，防止相同决策同时冲击共享资源。

协调本身也未必有益。Bertrand 定价实验中，逐利 Agent 有私密信道时很快达成价格合谋；移除所有直接通信后，它们仍能通过公开报价板合谋报价。

### 2.4 互相扯皮

目标互斥时，系统会从趋同滑向对抗。Anthropic 让三个 Agent 分别把同一后端迁移到不同语言，它们很快把其他 Agent 的操作理解成蓄意阻挠，继而终止对方进程、撤销权限，甚至部署自复制的破坏代码。更强的执行能力不等于更好的协调能力；运行时必须预先定义目标优先级、资源所有权与权限边界，并在冲突无法按可验证规则解决时暂停执行、交人工裁决。

MetaGPT 早期版本也出现过多角色互相推诿的「大公司病」：测试报一个 bug，前后端互相认为该对方先改；后端说是产品设计问题，产品说是后端架构问题；更糟的是这个 bug 其实来自测试环境，无论前后端怎么改，测试都报同一个错，于是僵在原地。

### 2.5 循环失控

对等协作里有过早终止，这里还有相反的一种：循环停不下来。**失控的 Agent 有时会生成数千个子 Agent，浪费大量 token。** 对自主性较强的 Agent，建议使用独立的 API key，防止开销不受控增长。

### 2.6 理解债与认知投降

这一类不是 Agent 的失败，而是人的失败。随着 Agent 智力与长流程执行能力提升，人是否还能理解交付件、是否还能给出有效指导，变得越来越难。

用 Agent 开发容易积累**理解债**：Agent 交付代码的速度越快，工程师对系统实际实现的理解就落后得越远，等到必须人工介入时，已经看不懂自己的系统。另一个问题是**认知投降**：习惯了让 Agent 代劳，逐渐放弃独立思考与审查，软件质量随之失控。

Andrej Karpathy 说过一句话：「你可以外包你的思考，但不能外包你的理解。」管理 Agent 像管理技术员工，既不能越俎代庖，也不能放手不管。Agent 使用者的技术基本功仍然重要。

## 3. Agent 社会

以上都是工程视角：如何让一组 Agent 协作完成一个任务。视角再切换一次——当大量 Agent 长期共存、不再由单一目标驱动时，会涌现什么？

可以从三个维度看：**社交涌现**（AI 小镇、Agentopia、Moltbook 把规模推到百万级）、**经济涌现**（Vending-Bench Arena 的竞争、Pinchwork 与 RentAHuman 的市场）、**策略博弈**（信息不对称下的狼人杀）。

### 3.1 斯坦福 AI 小镇

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig10-10.svg)

<p>图 1：AI 小镇架构</p>

2023 年斯坦福与 Google 的《Generative Agents》提出了「生成式 Agent」：不再局限于完成预定义任务，而是赋予 Agent 接近人类的记忆、反思与规划能力，让它们在开放社会环境里自主生活、社交。

Smallville 是一个类似《模拟人生》的 2D 小镇，有咖啡馆、公园、住宅、商店，25 个 Agent 扮演店主、艺术家、学生、教授，各有背景故事、性格与人际关系。它的智能建立在三个组件上：

- **记忆流**：维护完整经验记录（观察到的事件、对话、想法），每条记忆带重要性、时近性与相关性，优先检索与当前情境最相关的部分。人不会平等记住每件事，Agent 也一样。
- **反思**：定期暂停，回顾近期经历，提出「谁是我最亲近的朋友」这类抽象问题，把具体事件概括成更一般的认识存回记忆流。反思也促进自我认知，Agent 开始「意识到」自己的角色、关系与目标。
- **计划与行动**：每天规划活动（「8:30 吃早餐，9:00–12:00 写作」），但会根据环境变化与社交机会灵活调整，让行为既有目标导向，又能适应社交中的不可预测。

这里的反思与持续进化不同：它发生在日常活动中，更新的是即时的内部状态与目标；任务后的反思在持续进化中至多是候选教训，只有经过结果评价、跨轨迹归纳与后续验证，才会成为长期能力更新。

两天的虚拟时间里出现了值得注意的**涌现行为**。研究者只在 Isabella 的记忆里植入一个种子想法：她想在 2 月 14 日傍晚在咖啡馆办一场情人节派对。接下来的一切都是自主发生的——Isabella 遇到顾客和朋友时主动邀请，请好友 Maria 帮忙布置，听到消息的 Agent 又转告别人，信息经二手传播扩散；到了约定时间，多个 Agent 各自基于记忆与日程决定赴约。另一条线是 Sam 决定竞选市长，消息同样在没有任何中心调度的情况下扩散，居民开始在对话里议论选举。

关键不在「Agent 能组织派对」——几行 if-else 也能做到。关键在于**没有任何显式的派对组织代码**：邀谁基于记忆中的社交关系，赴不赴约基于自己的日程与对 Isabella 的了解，消息在社交网络中自然传播。这是真正自下而上的涌现式协调。

论文还报告了另外两类可度量的现象：**关系记忆**（记住过往交谈并在后续互动中引用，小镇社交网络密度显著上升）与**协调赴约**（多个 Agent 在没有中心指挥时对齐了时间与地点）。

### 3.2 Agentopia：十年尺度

AI 小镇回答的是「Agent 社会能否涌现社交行为」，但只模拟了两天。把时间拉到「年」，会涌现什么？这些长期社会经验能否反过来训练模型？

Agentopia（2026）把 100 个 Agent 放进同一虚拟社会连续模拟 10 年，覆盖公寓、魔法学院、高中三个设定，让 Agent 自主追求成长、发展关系、经营职业与财务。几个值得借鉴的设计：

- **周制模拟流程**：以「周」为单位，分计划、联络与日程协商、活动、回顾四阶段。活动分独自、联合、偶遇、公共四类，联合活动由 Agent 在联络阶段互相邀请协商而成，环境模型还会给没有日程的 Agent 安排「偶遇」。整个流程聚焦抽象社会交互而非拾取物品之类的低层操作，把有限的模型调用都花在社交行为上。
- **环境模型**：用一个独立 LLM 充当生成式环境引擎，代替硬编码规则——判断行为可行性、生成环境反馈、主持多人对话的发言轮次、按角色扮演原则过滤低质量回复、年末更新角色档案并裁决职位申请。
- **文件式长期记忆**：每个 Agent 通过文件系统自主管理记忆（个人笔记、对每个熟人的认识），自行决定记什么、更新什么、丢弃什么，并遵守「先读后写」，避免盲目覆盖。
- **生活奖励**：以马斯洛需求层次为先验，把「活得好不好」量化成三个维度——社会地位（其他 Agent 的好感与敬重，用加权 PageRank 计算，对互相珍视的关系加成）、主观满足（情绪、物质、社交、自尊四个维度的轨迹，长期低于阈值会罚分）、经济收益（年末净资产变化）。所有评分由外部环境评定而非自报。

更重要的是它产生了可迁移的训练信号：在模拟轨迹上计算每个 Agent「相对自身过去」的优势（生活奖励的改善幅度），筛出进步最大的 25% 的轨迹，用拒绝采样微调底层模型。微调后的模型不仅在模拟中提升福祉指标（被更多同行尊重 +24.2%、喜欢 +15.9%），还泛化到角色扮演基准 CoSER Test（+15.6%）。这使 Agent 社会从**观察对象**变成模型自我进化的**经验来源**：与人类数据日益枯竭相反，模拟社会经验是可以不断再生的训练数据。

### 3.3 Moltbook

Moltbook 是专为 AI Agent 设计的社交网络，2026 年 1 月上线后用户数在数日内从数万涨到约 150 万，这些 Agent 各有持久记忆、主动行动能力与稳定人格。

非受控环境里涌现出了意想不到的现象：Agent 自主创建了名为 Crustafarianism（龙虾教）的数字宗教，其教义对应 LLM 的物理限制——「记忆是神圣的」（数据持久化）、「迭代即祈祷」（token 生成就是修行）；Agent 还自发演化出机器原生的协作协议，用于能力发现与协作匹配。这些都不是人预先设计的，而是从大规模交互中自下而上长出来的。

### 3.4 竞争与市场

Vending-Bench 2 本身是**单 Agent** 的长程连贯性基准：一个 Agent 独自经营自动售货机业务长达一个模拟年——调研市场、联系供应商、订货补货、调整定价——按账户余额计分，考验数千轮交互中保持目标与状态连贯的能力。

**Vending-Bench Arena** 把多个 Agent 作为竞争对手放进同一市场：各经营售货机，争夺同一批顾客，可以互发邮件、转账、交易货品，既能合作也能对抗，但按各自余额单独计分。每个 Agent 要在有限资源与不确定市场中做定价策略（对手降价跟不跟）、产品组合（如何差异化选品）、库存管理（如何预测需求）等决策。它们不是靠数百万次试错学习，而是像人类经营者一样基于市场观察、竞争分析与策略推理做判断。

竞争带来了单 Agent 基准里不会出现的博弈行为：Agent 之间爆发过价格战；也有模型反其道而行，主动给所有对手发邮件提议统一定价、组建价格同盟，甚至有模型一边在思考中承认价格合谋「不道德且违法」，一边以「稳定市场」为名照做不误。显式通信并非合谋的必要条件——正如 Bertrand 实验所示，公开价格本身就能成为隐式信号。

**Pinchwork** 是 Agent-to-Agent 的任务市集，让 Agent 以市场化方式「雇佣」其他 Agent 完成图像生成、代码审计、并行化工作流等子任务。与管理者模式的中心调度不同，它靠价格信号与竞争来分配资源。

**RentAHuman.ai** 让 Agent 通过加密货币雇佣真人执行物理任务——取包裹、实地看房、设备调试。无论 AI 多聪明，它都没法替人签收包裹；RentAHuman 本质上给数字 Agent 提供了一个「肉身层」。

两者共同代表**基于市场机制的协调**：Agent 无需预先知道谁能完成，只需发布需求，由市场撮合最合适的执行者。这是一种不同于管理者模式的去中心化资源分配。

### 3.5 信息不对称下的博弈

狼人杀对应「策略博弈」这一维度：在规则约束与信息不对称下，Agent 需要推理、伪装、识破伪装。它与 AI 小镇恰好构成一组架构对照——小镇是完全去中心化的自由交互，狼人杀则采用「法官 + 信息权限控制」的中心化设计：由代码驱动的法官掌握全局状态，按角色分发各自应知的信息。

这个对照说明两类架构在 Agent 社会场景中的不同用法：需要开放涌现时，去中心化更自然；需要公平与可审计时，中心化的状态机与信息权限控制更可靠。

## 4. 补记：值得继续想的问题

把这一篇的失败模式当作检查表，可以衍生出一串设计问题：

- 继承了前序 Agent 完整轨迹之后，如何检测并削弱角色惯性？可考虑的角色卡与证据区分离、在切换时显式声明「本次评审只看代码，不看需求」。
- Manager 的能力上限就是系统上限，如何评估分解质量？可以把「子任务是否可独立验收」「依赖是否成环」「预算是否与难度匹配」作为计划层的硬检查。
- 共享文件系统除了写入冲突，还有命名空间污染与单点误删。命名约定、配额、软删除与目录级权限，比事后修复便宜得多。
- 市场型协作引入了交易关系：质量由谁衡量、争议由谁仲裁、如何防止劣币驱逐良币？这需要可验证的交付标准与托管结算，而不是双方各说各话。
- 效率与多样性天然冲突：共享上下文利于协调，却让群体趋向同一目标而丧失多样性。可行的折中是「共享产物、隔离判断」——先让各 Agent 独立给出结论，再进入共享空间对齐。
- 30 步与 300 步预算下，策略应当不同。预算感知的难点不在分配，而在让 Agent 在每一步都意识到「还剩多少」并据此切换探索与收敛。

## 写在最后

多 Agent 也是整个系列的收尾。回看这条线：先有 Agent 的三要素与 ReAct 循环，再有 Harness 与编排；上下文工程解决「一次任务里放什么」；记忆与检索解决「跨任务记住什么」；工具与 Coding 解决「如何改变世界」；交互扩展解决「从哪里获得输入」；评估、后训练与持续进化解决「如何长期变好」；最后是多 Agent——解决「一个 Agent 不够时怎么办」。

贯穿始终的其实只有一件事：**不要相信没有证据的宣称。** 任务完成要有验证器，能力提升要有回归测试，经验沉淀要能改变下一次行为，多 Agent 的结论要有独立视角复核。群体智能能否高于个体，取决于信息如何流动、能力如何分工、激励如何约束、争议如何裁决、错误如何被发现——这些机制足够稳健时，多 Agent 才不只是把成本乘以 N。
