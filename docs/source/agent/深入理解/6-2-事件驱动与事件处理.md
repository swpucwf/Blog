# 事件驱动与事件处理

## 1. 三种内置机制

OpenClaw 通过 Gateway 控制平面接收多渠道消息并路由到 Agent 运行时，提供三种事件驱动机制：

- **Hooks**：响应 Agent 生命周期事件（会话创建、重置等），类似 GitHub Actions 的触发器；
- **Cron**：按 cron 表达式执行周期性任务，如 `0 9 * * 5` 代表每周五上午 9 点；
- **Heartbeat**：每隔 N 分钟唤醒一次 Agent，检查是否有需要关注的事项。

它们赋予 Agent「自主」的外观——即使用户不在线，也能定时生成报告、检查状态、处理例行事务。

但真正让 Agent 在没有用户消息时「自己动起来」的只有 Cron 与 Heartbeat，而它们都是**时间驱动**的：Heartbeat 每隔固定间隔检查，Cron 按预设时间触发；Hooks 的事件来源是框架内部，而非外部。

短板在于：对内置渠道之外的第三方事件源——新邮件、API 回调、紧急通知——缺乏即时接入通道。Agent 无法在事件发生后立即响应，只能等下一个 Cron/Heartbeat 周期才可能察觉。

## 2. 一个实时通道的案例

Pine AI 代替用户拨打真实电话，典型场景包括协商账单、取消订阅、处理保险理赔。通话过程中可能随时需要用户介入：

- **实时身份验证**：客服要求提供安全码或 OTP；
- **三方通话确认**：客服要求与账户持有人直接对话，用户需在几秒内接听；
- **进展同步与决策确认**：对方提出降价方案，用户确认是否接受。

如果依靠 Heartbeat 定时轮询，用户可能在客服等待验证码时迟迟收不到通知，导致客服挂断、通话失败。

PineClaw 的解决方案是引入 **Channel 机制**：在 OpenClaw Gateway 与 Pine API 之间建立实时事件通道。电话接通、需要用户输入、通话结束等关键事件发生时，消息即时推送到 Agent，Agent 立即处理并通知用户。

这揭示了核心价值：**真正的「主动服务」不仅需要 Agent 能定时检查事件，更需要事件能主动通知 Agent。**

## 3. 事件触发工具

要让世界的变化转化为 Agent 可处理的事件，常见三类工具：

**定时器**（set_timer）：处理依赖物理时间的事件。一次性定时器用于明确时间点——「下周一上午 10:00 致电银行」；循环定时器用于周期性任务——每小时检查服务器健康。对不支持主动推送的外部服务，也只能用循环定时器反复查询。

**后台任务监控**（monitor_shell）：长时间运行的后台命令，Agent 不能一直「盯着看」（浪费 token），也不能等完全结束才介入（卡死时无法处理）。成熟做法是监控命令行新增输出或包含特定关键词的输出。

**外部事件通道**（connect_channel）：把新邮件、API 回调、IM 消息实时推送给 Agent。

设计上应定义清晰的触发条件与过滤规则，避免无关事件唤醒 Agent；事件载荷应包含足够上下文，减少被唤醒后的额外查询。

## 4. 用户沟通工具

许多 Agent 采用原生 ReAct 循环，assistant 消息直接发给用户，用户必须在应用中打开会话才能对话，且往往能看到工具调用过程。

OpenClaw 打破了这一范式：用户无需感知会话，也无需关心工具细节；双方可以随时给对方发消息，而不是「用户发一条、Agent 回一条」。因此很多人评价它具备**「活人感」**——像一个秘书通过消息异步沟通。

它不直接把 assistant 消息呈现给用户，而是用专门工具发送消息；消息可附带图片、文件，并根据紧急程度附加推送提醒。

除文本外，还有结构化卡片、提醒邮件，以及生成式 UI（用 HTML 等方式生成交互界面）。设计上应支持异步消息（用户不一定在线）、已读/未读追踪，并在多渠道下保持消息一致。

**多渠道沟通同时也是用户召回机制**：Agent 根据紧急程度、用户状态、内容性质、偏好选择渠道，既不错过重要消息，又避免重复打扰。长任务完成时主动通知用户；定期任务（每日总结、周报）帮助建立固定交互习惯。

## 5. 虚拟身份与隔离环境

Agent 应该直接管理用户的个人账号，还是拥有自己的虚拟身份？

直接管理看似便捷，但一旦 Agent 出错或被攻破，用户的全部数字身份都会暴露。更稳妥的是给 Agent 一套独立虚拟身份——像秘书拥有自己的办公电话与邮箱，包括专属通讯账号、存储空间、计算环境，以透明身份代表用户工作。身份的明确性不削弱信任，反而增强沟通真实性。

虚拟身份部署在隔离环境中：

- **虚拟电脑**（VM/容器）与**虚拟手机**（Android 模拟器）提供操作系统级隔离与完整桌面/移动操作能力；
- 可全天候运行，不受用户设备联网状态影响，也不打扰用户正在使用的应用；
- 错误操作最多导致虚拟环境崩溃，不影响真实设备；
- 隔离环境防止 Agent 随意访问本地文件。

独立身份也带来两个挑战：

- **反机器人机制**：CAPTCHA、IP 信誉检测会拦截自动化访问，使用数据中心 IP 的虚拟环境很容易被识别，实践中常需住宅代理；
- **访问用户真实账号**：任务必须以用户身份登录时，应采用 HITL 认证——通过 VNC/RDP 让用户在可视化环境中亲自登录，看到 Agent 正在操作的界面，理解为什么需要认证；认证后的会话令牌可在有效期内复用。

Agent 与虚拟环境通过**共享文件系统**交换数据：以卷挂载连接 Agent、虚拟电脑与虚拟手机，数据以文件路径引用传递而非内容拷贝，避免占用上下文。例如用户上传 CSV，虚拟电脑中的 Agent 读取、分析、生成图表并保存回共享目录，只把图表路径返回给用户。

## 6. 事件处理机制

一个 Agent 实例可能同时面对用户新消息、工具结果、定时器到期、另一个 Agent 的协作请求。如何高效正确处理，直接影响性能与体验。

骨架是并发编程的**事件循环**：每轮从输入队列取出若干事件，追加到轨迹，调用一次 LLM，执行它决定的工具，再回到循环开头等待下一批事件。

在同步接口实现中，**事件在每轮循环边界被消费**：LLM 正在推理、工具正在执行时，新事件先在队列等待，待本轮到达**安全点**（一段推理结束、一次工具返回）再处理。原生异步允许模型仍在思考或输出时接收新要求，由系统选择时机继续。

两者都有边界，只是边界由不同层管理。工具取消仍需执行器响应取消信号——接收一条「停止」消息本身不会撤销已经发生的动作。

### 6.1 结构化事件

处理的前提是理解。Agent 面对的输入不只来自用户一个人——第三方消息不是用户发的，但 Agent 需要理解、评估重要性、决定如何介入。

因此把每个输入建模为包含语义的**结构化事件**：

- **来源**：用户本人、联系人、陌生人、系统通知；
- **渠道**：电话语音、短信、IM、邮件、社交媒体、定时器、异步工具结果、命令行监控；
- **内容**：文本、情感色彩、紧急程度、是否需要回复；
- **上下文**：是对之前对话的回复还是新沟通，与当前任务的关联。

一封客户退款邮件：

```json
{
  "source": {"type": "email", "sender": "client@example.com"},
  "channel": "gmail_webhook",
  "content": {"subject": "退款请求", "body": "订单 #12345 希望退款..."},
  "context": {"priority": "high", "customer_tier": "vip", "related_orders": ["#12345"]}
}
```

只有结构化建模，Agent 才能在多方通信中保持清晰认知，避免把用户输入误当工具结果，或把藏有指令的工具结果误当用户指令，导致提示注入。

### 6.2 三种处理策略

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-2.svg)

<p>图 1：异步事件处理的三种策略</p>

**取消式**（紧急事件）：本质是为紧急事件**提前制造一个安全点**。停止当前操作（取消流式响应、向同步工具发取消信号）→ 清空待处理队列 → 把队列事件与紧急事件一起追加轨迹 → 立即重新调用 LLM。用户在执行危险操作前输入「停！我说错了」，Agent 会立即重新理解意图。

**队列式**（常规事件）：事件入队，不打断当前操作；等当前操作完成，在任何工具返回时检查队列，非空则一次性追加轨迹，让 LLM 综合处理。Agent 调用搜索工具时用户补充「只看最近一个月」，搜索结果返回时两个事件一起呈现，避免多余往返。

**并行式**（独立轻量查询）：与主任务无关、需要快速响应、成本低的查询，另起一个推理会话执行，结果追加回主轨迹并明确标记「与主任务并行执行」，避免混淆。

### 6.3 紧急度判定

- **紧急**：用户中断、监督指令、Agent 间中断、标记为紧急的外部触发器（系统告警、支付失败）；
- **非紧急**：常规用户输入、Agent 输入、工具结果、定时器触发、常规外部触发器。

硬编码规则有局限，事件语义决定处理方式：「马上停下来」用取消式，「今天天气怎么样」用并行式，「报告用中文发给我」用队列式。建议用**轻量分类 LLM 作为事件路由器**。

取消点必须是工具或推理能安全收尾的位置；未完成的工具结果用显式占位符表示，**不能伪造成功**。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-3.svg)

<p>图 2：事件驱动邮件处理 Agent 架构</p>

一个最小实验是自动邮件助手：监听收件箱，新邮件到达触发分类、摘要、起草回复。事件源可包括邮件、IM/短信、GitHub PR、定时器、Webhook、系统事件；所有事件进入统一队列，每个事件触发一次独立思考循环。三封测试邮件——会议邀请（查日历冲突并起草回复）、客户投诉（提取信息、标记高优先级、通知用户）、营销广告（自动归档）——无需用户介入。

这是最简单的串行事件模式。但当 Agent 需要在长工具执行中响应打断，或同时管理多个并发任务时，简单队列就不够了。

### 6.4 注意力分散

批量处理时，模型可能只回应最后一个事件而遗漏前面的要求。

两个层面干预：

- **提示词**：告知模型「收到多个连续事件时，确保全面考虑所有信息」；
- **状态栏标记**：给每个事件加显式序号与来源，末尾汇总「共有 4 个未处理事件，包括 1 个工具结果、2 条用户消息、1 个系统提醒，请确保回应涵盖所有信息」。

```text
[未处理事件 1/4] Tool result from database_query：...
[未处理事件 2/4] User 补充说明：只看北京地区的数据
[未处理事件 3/4] 系统提醒：报告截止时间还有 30 分钟
[未处理事件 4/4] User 询问：进度如何？
```

## 7. 补记

事件驱动最容易做成「加一个轮询定时器」。真正的区别在于**事件能否主动到达**，以及**到达后能否在不破坏当前工作的前提下被正确消费**。前者靠 Channel/Webhook，后者靠安全点、队列与取消语义。

另一个经验是：事件必须带来源与任务标识。没有归属的结果会被模型当成本轮的新事实，甚至被误当指令；结构化事件既是路由依据，也是防注入边界。
