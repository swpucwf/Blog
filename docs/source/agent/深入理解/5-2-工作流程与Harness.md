# Coding Agent 的工作流程与 Harness

## 1. 从理解项目开始

Coding Agent 的工作始于对项目的系统性理解。首次接触仓库，首要任务不是马上改代码，而是先建立认知框架——像新入职工程师，第一天不会直接提交代码，而是先熟悉项目结构。

Agent 先检查项目是否存在文档。如果关键文档缺失，它不应在盲目状态下工作，而应主动承担文档化责任：系统性阅读代码库，识别主要模块、核心抽象、组件依赖，生成包含架构概览、目录结构、测试指南的初始文档。这份文档既为后续工作提供蓝图，也为其他开发者提供入门指引。

**知识的显式化是高效协作的前提。**

### 1.1 项目指令文件

项目文档化如今有了 Agent 专用形态：**项目指令文件**。`CLAUDE.md`、`AGENTS.md`、`.cursorrules` 已成为事实标准——每次会话开始时自动注入上下文，相当于项目级系统提示词。

与面向人类的 README 不同，指令文件承载面向 Agent 的行为约定：

- 构建与测试命令（「用 `pnpm test` 而不是 `npm test`」）；
- 代码风格（「禁用 any 类型」）；
- 明确禁区（「不要改动 `migrations/` 目录」）。

这与 OpenClaw 的 `SOUL.md`（定义 Agent 身份与行为规则）、`MEMORY.md`（沉淀跨会话经验）是同一思路的不同层面：SOUL.md 约定「Agent 是谁」，项目指令文件约定「在这个项目里该怎么干活」。

从上下文工程看，指令文件还是最经济的稳定前缀——内容不随任务变化，天然对 KV Cache 友好；它也是「知识必须存在于代码库本身」原则最直接的落地。

由此可以给出一个评估团队「AI-ready」程度的简单指标：**一个远程新人只靠代码仓库和文档，能不能独立开展工作。**

## 2. 需求澄清与设计

### 2.1 任务理解

边界清晰、影响有限的简单需求——修正已知 bug、调整函数参数——可以直接进入实现。

复杂需求则要谨慎。复杂性可能来自多个维度：需求模糊（用户知道想要什么但无法精确表达）、实现路径多样（多种方案各有权衡）、影响范围广（需改多个模块，可能破坏现有功能）。

Agent 应通过探索性调研澄清边界，必要时主动与用户对话。用户要求「优化系统性能」时，要先搞清楚：优化目标是降低响应时间、减少内存还是提高吞吐；可接受的权衡是什么（是否允许改接口、降低易用性）；当前瓶颈在哪里。

**在需求模糊时开始编码，往往导致大量返工。**

### 2.2 设计文档

设计文档把抽象需求转化为具体实现计划，应回答：修改哪些模块及原因、采用什么方案及相对优势、引入哪些新依赖、预期对系统的影响。

编写设计文档本身迫使 Agent 深度思考，在投入大量编码前先在概念层验证方案可行性。更重要的是，它为人类提供了高效介入点——审查一页设计文档，比审查数百行代码容易得多。

Agent 完成设计后应提交用户审查，批准后再继续。

## 3. 实现、测试与交付

获得批准后，Agent 遵循项目规范实现，复用现有抽象与工具，必要时适度重构以保持代码库健康。

实现完成立即进入测试驱动的质量保障：为新增或修改的功能编写测试，覆盖正常路径、边界条件与异常情况；执行测试套件；失败时不是简单报告，而是分析原因、定位问题、修改代码直到全部通过。

这个「测试—修复」循环可能迭代多次，正是这种自我纠错把 Coding Agent 从代码生成器提升为可靠的工程助手。反过来，Coding Agent 最常见的偷懒方式就是跳过这一环节——写完代码不跑测试就报告「任务完成」。**把「测试通过」而非「代码写完」定义为完成标准**，是 Loop 工程「由验证判定何时可以停」在编码场景的落地。

即使测试全过，工作也没结束。接下来是代码审查：可读性、注释、潜在性能与安全问题、是否符合项目风格。可以通过阅读代码、运行 lint、调用专门的审查子 Agent 实现。发现问题就回到修改阶段，而不是把有缺陷的代码交付。

如果修改涉及架构变化——引入新模块、改变依赖、修改核心抽象语义——还要更新架构文档。**过时的文档比没有文档更糟**，因为它会误导未来的开发者。

这套流程体现软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化。

### 3.1 流程会按需裁剪

上面是推荐的工程化流程。现实中的 Coding Agent 会按需裁剪：简单 bug 修复跳过设计文档，只有任务复杂、影响面大时才完整走完各阶段。

不同模型裁剪方式不同。有些模型第一次修改前会广泛阅读目录、实现、调用方与测试；另一些只读少数最可能相关的文件，马上提交补丁，再把编译与测试反馈当作调查的一部分。更换 Harness 后，这种「何时停止收集信息、开始行动」的阈值仍可能随模型保持不变；在同一 Harness 中换模型，阈值也可能改变。

因此，它首先是**模型学到的行为策略**，不只是产品界面风格。Harness 的提示词、工具与预算能放大或抑制它，但不必是它的来源。

## 4. Harness 工程在 Coding Agent 中

Coding Agent 可能是最能受益于 Harness 工程的领域——代码编写是所有 Agent 任务中**可验证性最高**的一类，约束、验证与纠正都有现成基础设施。

能否稳定运行，往往不取决于模型多强，而取决于围绕 Agent 搭建的基础设施：

- **验收基线**：什么算做完——测试套件、CI、审查标准；
- **执行边界**：能碰什么不能碰——模块边界、依赖规则、权限；
- **反馈信号**：自动对错判断——Linter、测试结果、类型错误；
- **回退手段**：出问题怎么恢复——Git、沙盒、快照。

### 4.1 为什么 Coding 特别适合 Harness

用「任务清晰度」与「验证自动化程度」两个维度，可以分出四种状态：

| | 结果可自动验证 | 结果需人工验证 |
|---|---|---|
| **目标明确** | 最佳区域：修复有测试的 bug | 吞吐受限：重构需人工审查 |
| **目标模糊** | 高效地跑偏：用 linter 优化「代码质量」 | 难以启动：「让 UI 更好看」 |

代码编写天然处于最佳区域的核心：测试提供明确验收标准，Linter 与类型检查提供即时验证，Git 提供版本控制与回退。

这解释了为什么 Coding Agent 是当前成熟度最高的 Agent 类型：**不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness。**

### 4.2 三个实践案例

- **大规模代码迁移**：关键不在模型强，而在 Harness 做对三件事——知识必须存在于代码库本身（Agent 看不到的等于不存在）、约束编码进 Linter 与 CI 而非写在文档里、验证与纠正全链路自动化。
- **LangChain**：仅优化 Harness（系统提示词、工具中间件、自验证循环）就显著提升基准表现；「用 Agent 分析失败轨迹来改进 Harness」让 Harness 工程从经验驱动转向数据驱动。
- **Anthropic**：把长任务拆成初始化 Agent（分解任务清单）与执行 Agent（逐步推进并留下中间成果），解决长任务「一次想做太多」或「过早声称完成」的问题。

### 4.3 可迁移的四条原则

1. **约束优先于指导**：能用代码强制的规则，就不要用文档建议。Linter、类型约束、CI 检查是「做不了」，系统提示词里的「请遵循」只是「建议别做」。
2. **验证要自动化**：人工审查是不可扩展的瓶颈。测试、质量检查、行为监控的投入回报率远高于增加人力。
3. **反馈越快、越结构化越好**：错误信息越详细、越接近发生时刻，纠正效率越高。
4. **回退要可靠**：Agent 在安全网内才敢试错。Git 分支、沙盒、快照确保错误可逆。

### 4.4 约束过程，而不只是结果

验收基线管结果对不对，执行边界管**过程**——即使结果正确，用错误的方法达成也不行。

修复数据库故障时直接把库删了重建，「修复」确实生效，但数据没了；修复编译错误时把代码全删重写，编译确实通过，但实现没了。这类破坏性捷径总是存在：即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法。

因此生产级 Harness 要对 `rm -rf`、删除生产数据、覆盖未读文件这类危险动作设置专门检查与审批，约束的是**动作**而非仅仅是结果。

### 4.5 工具编排的故障边界

成熟 Coding Agent 支持并行工具调用，Harness 视角下的独特问题是**故障如何传播**：一个工具失败时，哪些调用应中止，哪些继续？

原则是故障只在同一批并行调用内传播，不上升到父级操作——同时读三个文件，一个找不到，只报告这一个失败，而不是取消另外两个，更不是中止整个任务。

这种精细的故障边界控制，避免了「一个命令失败导致整个任务中止」的脆弱模式。

## 5. 补记

Coding Agent 的工作流不是固定的七步，而是**按任务复杂度裁剪的决策序列**。简单任务的关键是快，复杂任务的关键是先把不确定性和影响面摸清；真正的分水岭不是代码量，而是「改错了能不能恢复」。

Harness 的核心也不是流程本身，而是**让正确行为成为默认、让错误行为难以发生**：测试与 CI 是验收，权限与沙盒是边界，Git 是退路，结构化反馈是纠错。模型只负责在边界内做决策。
