# Coding 是通用 Agent 的基础能力

## 1. 通用 Agent 的核心

一个能处理任意任务的通用 Agent，架构长什么样？

答案是：**通用 Agent = Coding Agent + 文件系统**。Coding Agent 能自主编写、修改、执行代码；文件系统是它存储代码、数据、记忆与中间结果的工作空间。从 Manus 到 OpenClaw，成功的开放任务型通用 Agent 都遵循这一范式。

为什么代码生成能担此重任？因为它不只是工具，而是一种**元能力**——能在运行时创造出新的工具与能力。

代码对 Agent 的价值有两个层面：

- **思考**：形式化代码让思考严谨。「年龄大于 18 且已实名认证」用自然语言可能有多种理解，写成代码就毫无歧义。
- **表达**：一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观的对错标准。

## 2. 七个核心工具

一个典型任务：「整理仓库中所有遗留的 TODO 注释，按优先级分类并生成 issue。」完成它需要浏览目录、读取代码、修改文件、运行命令、查找模式——五类操作覆盖了 Coding Agent 的核心动作。

支持这五类操作，只需七个工具：

1. **Code Interpreter**：隔离沙盒中安全执行 Python；
2. **Bash Shell**：执行命令、跑测试、处理特殊格式；
3. **读文件**：读取代码、配置、文档、日志；
4. **写文件**：创建或完整重写；
5. **编辑文件**：局部修改，代码维护的核心；
6. **Glob**：按模式定位文件，如 `**/*.py`；
7. **Grep**：按内容搜索，如查找所有调用某函数的行。

这七个工具构成完整但极简的工具箱，几乎任何 Agent 都能低成本集成。它覆盖感知与执行两类；协作、事件触发、用户沟通仍需其他工具，但不是 Coding Agent 的核心。

一个最小任务：

```text
用户：把项目里所有 TODO 注释整理成清单

Agent → Grep("TODO", glob="**/*.py")
  src/api.py:42: # TODO: add rate limiting
  src/db.py:15:  # TODO: migrate to PostgreSQL
  tests/test_api.py:8: # TODO: add edge case tests

Agent → Write("TODO_LIST.md", content="...")
Agent：共发现 3 个 TODO，清单已保存。
```

整个过程只用了 Grep 与 Write。若任务升级为「统计每个模块的 TODO 数量并画柱状图」，Agent 会再用 Code Interpreter 执行 Python 完成统计与绘图。工具虽少，组合起来能完成非常多样的任务。

为什么是七个，不是六个？事实上一个 Bash 就能覆盖大部分操作。Codex 的工具集更精简：shell 作为唯一通用执行入口，文件修改交给语法受约束的 `apply_patch`——把编辑表达为结构化补丁而非自由文本命令，降低改错文件的概率。七个工具是为了方便理解所需的基本能力。

## 3. 为什么通用 Agent 需要 Coding

因为代码生成不只是写程序，而是通用的问题解决手段：

- 遇到数学推理，写段代码交给求解器算出精确答案；
- 需要固化业务规则，代码比自然语言精确得多；
- 缺少某个工具，临时写一个；
- 数据格式变了，动态生成解析逻辑。

一个具备基本 coding 能力的 Agent，即使工具箱只有七个简单工具，也能在遇到新需求时动态扩展能力边界。

### 3.1 从 Manus 到 OpenClaw

通用 Agent 产品把 Deep Research、Computer Use 与 Coding 融合在一个系统中。为什么 Coding 是核心，而不是另外两者？

因为几乎所有高效的内容生成最终都要落到代码上：

- PPT、Word 本质是 OOXML 格式；
- PDF 报告可由 Markdown、HTML 或 LaTeX 生成；
- 数据分析与可视化可由 Python 脚本完成；
- GUI 操作中成功的浏览器操作序列，也可以固化为可复用代码；
- Deep Research 的搜索与信息综合，可通过代码驱动的 Web 请求与解析实现。

Computer Use 通用性更强，但成本、延迟、稳定性远不如直接通过代码或 API 完成相同操作。**代码生成是效率最高、成本最低、可复用性最强的能力基座。**

一个执行流：

1. **读记忆**：读取 `MEMORY.md`，发现用户偏好 PDF 报告，数据源是 Google Sheets；
2. **调工具**：搜索 Google Sheets API 用法，通过代码执行下载数据；
3. **写代码**：用 Python 生成分析脚本（pandas 聚合、matplotlib 可视化）；
4. **生成产物**：分析结果写入 `report.pdf`，图表写入 `charts/`；
5. **更新记忆**：记录数据源信息，下次无需再问。

文件系统是信息流转的枢纽——记忆从文件读取，产物写入文件，经验也保存为文件。

在 OpenClaw 中，文件系统不仅是存储，更是记忆、知识与能力的中枢。长期记忆存 `MEMORY.md` 与按日期归档的 Markdown 日志。选择 Markdown 而非向量数据库看似反直觉，却极其有效：用户可以直接打开修改（记错了删掉那一行即可），Markdown 天然保留时间顺序，避免语义检索的时间混淆，还能用 Git 版本控制与回滚。

更关键的是，Agent 拥有写文件能力，就具备了修改自身外部产物的技术条件。首次执行任务发现新信息（如某银行要求提供开户行地址），可以先写入记录；记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证。

### 3.2 适用边界

「Coding Agent 是通用 Agent 的核心」主要适用于**以开放任务为目标**的通用 Agent——深度调研、内容生成、数据处理这类任务边界不确定、产物形态多样的场景。无法预先枚举所有工具，代码生成作为元能力提供了动态扩展能力边界的最经济路径。

垂直领域 Agent（如客服）任务空间相对封闭，核心架构围绕固定流程、领域工具与对话策略构建，代码更多是工具箱里的一件工具，而非架构中枢。但即便在后者，coding 也是重要基础能力：精确计算、数据处理、规则校验都离不开它。

## 4. 补记

判断一个 Agent 是否需要 Coding 内核，看任务边界是否可预先枚举。边界开放，工具永远不够用，代码生成是唯一能「现场造工具」的能力；边界封闭，固定工具与流程更可靠，Coding 只需作为基础能力存在。

另一个常被忽略的点是文件系统的角色。它不只是存储，而是 Agent 的**外部记忆与工作台**：计划、中间结果、日志、产物都在这里，模型上下文只保留当前需要的那部分。没有文件系统的 Coding Agent，只能把一切塞进上下文，很快会撞上窗口与注意力限制。
