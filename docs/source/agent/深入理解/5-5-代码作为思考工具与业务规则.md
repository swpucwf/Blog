# 代码作为思考工具与业务规则

## 1. 概率思考的短板

LLM 在自然语言理解与生成上表现惊人，但在精确计算、符号操作或严格逻辑推导上有根本短板。原因在于：模型思考本质是概率性、近似的，而数学与逻辑要求确定性、精确的答案。

一个对比：

```text
问题：一个班 40 名学生，60% 选修数学，45% 选修物理，25% 两门都选。
      只选物理没选数学的有多少人？

纯自然语言推理（容易出错）：
  60% 选数学 = 24 人，45% 选物理 = 18 人，25% 都选 = 10 人
  只选物理 = 24 - 10 = 14 人   ← 误从数学人数中减

代码推理（精确可验证）：
  math = int(40 * 0.60)       # 24
  phys = int(40 * 0.45)       # 18
  both = int(40 * 0.25)       # 10
  only_phys = phys - both     # 8 ✓
```

让 LLM 负责理解问题并写出代码，让代码解释器负责精确计算——两者各司其职。

Wolfram 早就指出过这个分工：在 LLM 之前，已有能做精确数学的**符号计算**系统，用数学符号而非近似数值处理表达式。普通计算器把 \(\sqrt{2}\) 算成 1.414，符号系统会保持 \(\sqrt{2}\) 的精确形式。但它的自然语言理解脆弱、覆盖面窄——依赖内置语法解析，问法稍变就可能失败。

LLM 恰好弥补这个短板：擅长理解各种自然语言表达，但不擅长精确计算。新的协同模式是：**让 LLM 理解问题、识别数学或逻辑结构、转化为形式化语言，再交给符号计算引擎或约束求解器执行。**

这个实验还揭示一个更普遍的规律：**模型与脚手架之间是此消彼长的关系。**

- 模型足够强时，脚手架可以更薄——模型自己就能把逻辑想对，代码求解器带来的增益收窄；
- 模型不够强时，就得在脚手架里做更多事——把关键推理交给代码与约束求解器保证正确性。

所以脚手架该做多厚，取决于手上模型的能力边界。这也是评估一项 Agent 技术时容易被忽视的前提：同一套脚手架，配上不同能力的模型，结论可能截然不同。

## 2. 代码作为业务规则的约束

Harness 的核心原则之一是「约束：编码化而非文档化」——把规则从自然语言文档转化为可执行代码，使其成为系统行为的强制约束，而非建议性指南。

业务规则、办事流程、决策逻辑如果只用自然语言描述，往往充满歧义：

- 什么是「合理的退款请求」？
- 什么算「紧急情况」？
- 「购买后 7 天内可退款」——7 天是自然日还是工作日？「购买」是下单还是发货？

代码提供无歧义、可执行的表达：要么成功运行，要么抛出错误，不存在模棱两可。

### 2.1 自然语言与代码化规则互补

把规则写在系统提示词中的优势：

- 模型可基于规则向用户**解释政策**；
- 可根据规则**寻找变通方案**（如「改签而非取消」）；
- 可在调用工具前初步判断可行性。

编码成校验工具的优势：

- **精确、无歧义**，不会出现理解偏差；
- **确定性**，相同输入必产生相同输出；
- 特别适合**复杂规则组合**——多条件布尔组合、时间计算、跨数据源验证。

实践中应结合：系统提示词包含自然语言规则供理解与沟通，关键决策点配备代码化校验工具作为「守门员」。

代码化规则的真正价值不在优化 token 效率，而在**防止不可逆的错误操作**——取消订单、转出资金、删除数据，一旦执行就无法撤销。代码化校验在操作前设最后一道防线，这种安全价值远超实现成本。

## 3. 合并校验与执行：checklist 与真值

与其设计独立校验工具，不如让执行工具内部先校验。以航空取消政策为例：

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,
    expected_cabin_class: str = None,      # 模型自查用
    expected_has_insurance: bool = None,   # 模型自查用
) -> dict:
    """
    取消航班预订。取消政策（服务端按数据库真值强制执行）：
    - 已使用任何航段的订单不可取消
    - 预订后 24 小时内可无条件取消
    - 航空公司取消的航班总可取消
    - 商务舱总可取消
    - 基础经济舱和经济舱需购买旅行保险才可取消

    调用前请先查询订单详情，逐条核对；expected_* 仅用于陈述判断依据，
    供服务端比对与审计，不影响政策裁决。
    """
    r = db.get_reservation(reservation_id)
    now = server_clock.now()

    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if expected_has_insurance is not None and expected_has_insurance != r.has_insurance:
        log_mismatch(reservation_id, "has_insurance", expected_has_insurance, r.has_insurance)

    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}

    hours = (now - r.booking_time).total_seconds() / 3600
    if hours <= 24:
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Cancelled within 24-hour window"}

    if r.flight_status == "cancelled_by_airline":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Airline cancelled flight"}

    if r.cabin_class == "business":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Business class cancellation"}

    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance:
            execute_cancellation(reservation_id)
            return {"success": True, "reason": f"{r.cabin_class} with insurance"}
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}

    return {"success": False, "reason": "Does not meet cancellation policy"}
```

这个设计的价值分两层。

### 3.1 参数作为思考的 checklist

工具描述列出完整政策，并要求「调用前先查询订单详情、逐条核对」；可选的 `expected_*` 参数促使模型把判断依据显式写出来。

为了填好这些参数，模型必须先调用查询工具获取详情，逐一确认每个条件——填写参数的过程本质上是一个**强制性 checklist**。

当模型查到舱位是经济舱且未购保险时，很可能在准备调用的过程中就注意到规则 5，从而**根本不会发起调用**，而是直接告诉用户「经济舱未购保险无法取消，可考虑购买保险或改签」。

这一层的价值是引导思考、减少无效调用；但它不承担安全责任——`expected_*` 只是模型自我陈述，服务端从不把它当事实。

### 3.2 服务端真值校验才是守门员

代码中的关键设计：舱位等级、保险状态、预订时间、航段使用情况、航班状态，全部由服务端查询数据库；当前时间来自服务端时钟。**没有任何一条政策事实来自模型自报的参数。**

这不是多余的谨慎：模型可能产生幻觉，也可能被提示注入操纵。如果把 `cabin_class`、`has_insurance` 乃至 `current_time` 设计成由模型填写的参数，模型只要报错（或被诱导报错）一个值，「守门员」就形同虚设。

最后一道防线必须建立在模型无法伪造的数据之上——**独立性不仅指独立的模型，更指独立的数据来源。**

### 3.3 三重保障

1. 系统提示词的自然语言规则帮助理解与解释；
2. 工具描述与参数设计作为 checklist，引导模型调用前显式核对；
3. 服务端基于数据库真值的代码化校验作为最后守门员。

前两重减少错误发生，第三重确保错误不会变成不可逆损失。

## 4. 补记

代码作为思考工具，最适合**答案可判定、过程可验证**的任务：数学、逻辑、约束满足、规则校验。它的价值不是让模型「更聪明」，而是把「可能算错」的部分交给确定性执行。

代码作为业务规则，关键要把「引导」与「守门」分开：提示词与 checklist 负责让模型理解与自查，服务端真值校验负责最终裁决。把安全责任放在模型自报的参数上，等于没有安全边界。
