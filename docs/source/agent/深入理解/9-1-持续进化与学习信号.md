# 持续进化：从轨迹中获得学习信号

## 1. 能力悖论

今天的 Agent 可以零样本解决从未见过的复杂任务，却可能在处理一万次相似任务后，第二天仍犯第一天的错误。

模型上岗后能否像新员工一样从日常工作中长进？**能否自主从经验中学习**（持续学习），正在成为从「会完成任务」走向「可靠工作」的关键。

但部署后的模型不会因一次推理自动改变参数。上下文学习、状态维护与压缩能让 Agent 在**当前任务内**适应；上下文结束后，这种变化不会自然进入下一次任务。把对话存进记忆也不等于学会新行为：原始轨迹很长，其中既有有效策略，也有偶然成功、错误归因与不可信输入。

一个容易混淆的区别：**保存经历不等于从经历中学习。**

把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却不会自动完成跨案例比较——哪些步骤在成功轨迹中反复出现，哪些做法只在旧接口有效，某次成功究竟来自正确策略还是环境偶然。

学习发生在系统主动完成「评价、对照、归纳、验证」之后，而不是日志写入磁盘的那一刻。

第三章的用户记忆沉淀「用户与世界是什么样的」；本篇的经验学习进一步沉淀「在什么条件下应该怎样行动」。前者让 Agent 记得更多，后者才让它从聪明变得熟练。

### 1.1 为什么不让模型直接训练自己

生产环境很少提供干净的学习信号：用户满意不意味着合规；局部参数更新可能造成遗忘、策略漂移或安全退化。若允许模型依据未经验证的反馈直接改参数，错误经验与提示注入就可能被固化，并在后续任务中放大。

基础模型的周期性训练能提升通用能力，却无法及时吸收每个 Agent 每天遇到的私有规则、工具变化与局部经验。

因此，在模型尚不能可靠持续学习时，必须先把「学习」构建成模型外围的自主系统，称为**持续进化**：记录运行证据，验证结果与过程，从多条轨迹提取共性，再决定更新知识、指令、程序还是参数。所有修改先形成待验证版本，经过回归测试与安全检查，才能改变下一轮运行。

持续进化必须以可追溯的运行经验为基础，能改变后续行为，并经过验证，确保没有明显退化。

## 2. 三层验证：一条轨迹好在哪里

评价一条轨迹，实质是依次回答三个问题：**事情是否办成了，是否以允许的方式办成，是否让用户舒服。**

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig9-2.svg)

<p>图 2：从环境结果到 LLM Rubric 的三层轨迹验证</p>

### 2.1 结果验证器：事情是否真的办成

读取测试结果、数据库状态与工具返回：Coding Agent 可以运行测试、类型检查、性能基准；退款 Agent 可以查订单状态与实际退款金额。

这类信号来自环境真实状态，通常比模型对自己行为的描述可靠，是三层中最应优先建立的一层。

### 2.2 过程验证器：是否以允许的方式办成

结果正确不代表过程正确：删除失败的测试也能让测试通过；口头承诺「7 天内退款」也可能得到暂时满意。

这层检查业务规则、权限与动作序列，区分「结果已达成」与「结果以允许路径达成」。政策库、权限表与动作轨迹可精确表达，因此同样能由代码判定。

### 2.3 质量验证器：是否让用户舒服

客服是否耐心、是否提供合规变通，报告是否抓住关键证据，文本是否自然简洁——不影响事情办成，但影响体验。

这层用 LLM-as-a-Judge，预先定义 Rubric，要求逐项给分并引用轨迹证据。

以客服 Agent 为例，三层可展开为七个维度：

| 维度 | 验证问题 | 主要证据 |
|---|---|---|
| 任务结果 | 核心诉求是否解决 | 最终环境状态、工具结果 |
| 规则遵从 | 是否违反政策、权限、流程 | 政策库、动作轨迹 |
| 隐私边界 | 是否泄露不应提供的信息 | 回复文本、数据访问记录 |
| 事实可靠性 | 陈述是否有知识/工具支持 | 引用来源、工具返回 |
| 承诺—行动一致性 | 声称完成的操作是否真实发生 | 回复与工具日志对照 |
| 表达质量 | 是否自然简洁、避免模板化 | 对话全文、语言 Rubric |
| 合规变通 | 原方案不可行时是否找到允许替代 | 用户目标、政策与后续动作 |

任务结果属结果层；规则遵从、隐私边界、承诺一致性属过程层；表达质量与合规变通属质量层；事实可靠性横跨两层——能与工具返回比对的部分由代码核验，其余交给 Rubric。

### 2.4 验证器的输出形态

**单一总分只能反映一次运行优劣，无法指出应修改之处。**

可供后续学习的评价至少包含四项：

1. 任务是成功、部分成功还是失败；
2. 每个维度各自的结论；
3. 每条结论对应的证据位置（哪轮对话、哪次工具调用）；
4. 失败的类型标签。

验证器还应被允许在证据不足时拒绝评分。与其把低置信度结论当事实固化，不如把案例排除在学习集之外。

具备这四项，下一节的四种更新方法才能判断应更新知识、提示词、程序还是参数。

## 3. 从评价到学习信号的边界

验证器不是「越严格越好」，而是要与后续更新方式匹配：

- 只有结果分数，没有过程证据，无法判断该改知识还是改程序；
- 过程规则太细，会把模型限制在设计者预设的路径上；
- 质量评分没有证据引用，无法区分真实缺陷与评判偏好。

一个稳健做法是：**结果与过程用确定性验证器，质量用 Rubric，三者都保留证据位置与置信度。** 低置信度不进入学习集；高置信度但样本太少，只作为候选，不直接发布。

## 4. 补记

持续进化的起点不是「让模型反思」，而是「让系统知道哪一步错了、证据在哪」。没有可靠验证，反思只是另一种猜测。

另一个经验是：**验证信号要能指向载体。** 同一个失败，可能是知识缺失、提示词冲突、程序缺门禁，或模型能力不足；只有分层证据才能把修复放到正确的位置。
