# 代码驱动的多媒体与生成式 UI

## 1. 元能力：创造能力的能力

普通能力是 Agent 能做某件具体的事——回答问题、调用 API、生成一段文字。**元能力**是一种「能创造其他能力」的能力：Agent 用它当场写出新工具、新约束、新表达形式来完成任务，而不必事先把所有能力预制好。

代码生成正是这样的元能力——它精确、可执行、可组合，因此既能产出新工具（脚本、API 调用序列），也能产出新约束（断言、校验规则），还能产出新的表达形态（HTML 表单、PPT、视频帧）。

代码作为元能力有六个方向：思考工具、业务规则、内容呈现、系统接口、用户界面、Agent 自身。前两个已经讨论，下面看后四个。

## 2. 代码驱动的多媒体生成

许多复杂文档的创作，本质是结构化数据的组织与呈现。PPT、报告、交互应用，底层都由代码定义——HTML 描述结构，CSS 控制样式，JavaScript 实现交互。

传统文档创作依赖 GUI 的所见即所得，但对 Agent 来说既不直观也不高效——GUI 操作需要视觉理解与精确坐标定位。通过代码生成，Agent 绕开视觉定位难题，获得对文档的精确控制：每个元素的位置、样式、内容都明确定义，可以用程序化方式修改优化。

### 2.1 PPT 生成：提议者—审核者

现代 PPT 框架（如 Slidev）用 Markdown 与 HTML 定义演示内容，对掌握代码生成的 Agent 极其友好。

但仅能生成代码还不够。**Agent 编写完代码后并不知道实际渲染效果**：内容是否太挤、文字是否溢出、图片尺寸是否合适，只有真正渲染才能发现。

因此需要**提议者—审核者**机制，把代码编写与质量评审解耦为两个独立 Agent：

- **Proposer** 生成 Slidev 代码，理解内容逻辑并分解为合理页面；
- **Reviewer** 运行代码把每页渲染为图片，用 Vision LLM 从内容密度、可读性、布局、美感等维度分析，生成**结构化改进建议**——不是「不好看」，而是「第 3 页内容过多，建议拆分」「第 7 页代码字体过小，建议 14pt」。

Proposer 接收反馈修改，新版本再次提交，迭代到质量达标或达到最大轮数（如 5 轮）。「质量达标」与「最大轮数」正是 Loop 工程的两类显式终止条件：前者由审核者判定目标达成，后者用预算上限防止循环失控。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig5-5.svg)

<p>图 1：PPT 生成的提议者—审核者机制</p>

双 Agent 分工而非单 Agent 循环的**核心优势在上下文管理**：Reviewer 每次只处理最新版本的渲染图，不受历史版本干扰；Proposer 只累积结构化文本反馈，token 消耗少且易推理。单 Agent 方案则要在同一上下文累积数十页渲染图的多轮迭代，很快超限。

### 2.2 视频编辑与生成

用通用 Computer Use 做视频编辑面临根本挑战：剪辑软件 GUI 极其复杂，时间轴、图层、效果面板，精确坐标定位与鼠标操作非常困难。

把视频编辑重构为 API 调用与代码生成则大幅降低复杂度。Blender 提供 Python API，FFmpeg 提供命令行接口，核心功能以结构化、可组合的方式暴露。对 Agent 而言，把自然语言需求转化为 API 调用，远比理解 GUI 并模拟点击容易。

视频编辑同样采用提议者—审核者：Proposer 生成 Blender 脚本，Reviewer 渲染关键帧并用 Vision LLM 检查效果。

一个实用技巧是**两步定位**：

1. **粗粒度**：把视频路径、每 10 秒截图间隔、目标问题交给视频分析子 Agent，返回场景区间（「冲浪在第 40–110 秒」）；
2. **精细粒度**：缩小范围，每秒截图，精确定位边界。

把视频分析封装成子 Agent，避免大量截图占用主 Agent 上下文。定位后生成脚本，Reviewer 先快速预览、检查关键帧，迭代达标后再完整渲染。

### 2.3 3D 与工业零件：代码还是生成模型

同样是「生成一个东西」，有两条路：写代码精确构造（CadQuery、OpenSCAD、Blender API），或直接调 3D 生成模型。

判断有两条标准：

1. **产物有没有紧凑的精确描述。** 工业零件天然有：法兰盘的外径、厚度、孔位圆直径、孔径、孔数，五六个参数就完整定义，代码是无损表达。绿植、太湖石、人脸则细节近乎无限，内在复杂度高。
2. **精度要求与可验证性。** 零件每个尺寸都是硬约束——孔径 5mm、公差 ±0.05mm，差一丝就是废品。代码生成的零件可以程序化验证：载入网格，量出尺寸与规格逐项对。3D 生成模型的产物无法直接核对。

还有一个实际差别：**表示形式与可编辑性。** 制造要的是 B-rep 参数化实体——STEP 文件存着特征树与尺寸参数，可直接驱动 CNC。3D 生成模型吐出三角面片网格，曲面靠无数细碎面片逼近。「安装孔从 M5 改成 M6」时，代码路线改一个数字重跑，其余尺寸分毫不差；生成模型只能整体重生成，别的尺寸会不会跑偏全凭运气。

所以走哪条路本身是 Agent 要做的一次决策：掂量产物的内在复杂度与精度要求。实际系统可以混着走——几何体用代码参数化生成，表面纹理交给生成模型。

## 3. 代码作为系统适配器

前几节的代码大多产出「面向人」的东西；这一节的代码连接机器与机器。

真实系统里，外部服务常常没有现成 SDK，接口也未必规范——文档缺失、返回格式非标准、字段随版本漂移。Agent 不必等人预先写好适配层，而是当场阅读文档或观察一两条真实响应，即时生成适配代码：构造 HTTP 客户端、拼装鉴权头、解析非标准结构、转换数据模型。

代码成了连接任意系统的「万能胶」——哪里接不上，就现场生成一段补上。

这种能力还能延伸到**完全没有 API 的系统**：外部系统只暴露 GUI 时，Agent 先用 Computer Use 操作界面，再把成功序列固化为 RPA 工具。未来执行相同任务直接运行代码，速度与稳定性远高于重新视觉思考。

### 3.1 自适应日志解析

数据格式不断变化：添加字段、改变嵌套、引入新类型。为每种格式手写解析，维护成本极高。

代码生成提供新思路：遇到新格式时，基于样本临时生成解析代码，系统自动适应演化。

Agent 日志可视化就是一个典型场景。前端遇到无法解析的格式时，不显示错误，而是把失败信息（原始样本、报错）报告给 Agent；Agent 分析结构，生成能正确解析的前端代码；代码先在虚拟浏览器自动测试（验证解析正确性与可视化效果），通过后热更新到前端。

这形成「检测失败 → 生成代码 → 自动测试 → 热更新」的自修复闭环。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig5-7.svg)

同一思路可用于问题诊断：Agent 读取生产轨迹，结合架构文档与 PRD，判断执行流程是否符合预期，定位问题环节，生成结构化问题报告与回归测试用例；测试用例引用轨迹 ID 与关键交互轮次，通过重放验证修复；最后通过 MCP 对接 GitHub 创建 Issue。

## 4. 代码作为生成式 UI

纯文本交互在线性、单一，很多场景效率低：收集结构化信息时反复问答，呈现复杂数据关系时表达力有限，让用户在多个选项中选择时不如可视化界面直观。

代码生成让 Agent 动态生成表单、交互图表甚至完整 Web 应用，把静态文本对话升级为多模态交互——**生成式 UI**。

### 4.1 声明式界面协议

Agent 直接生成 HTML/JavaScript 存在根本安全问题：生成的代码可能含恶意内容。有人在输入中藏一段指令，Agent 可能被提示注入操纵，生成窃取用户数据的脚本。

成因是**提示注入**，最终在浏览器执行恶意脚本的效果类似传统 Web 的 XSS，但不能把整个攻击直接叫 XSS。

以 A2UI 为代表的声明式协议提供更安全的方向：Agent 不直接生成可执行代码，只输出「界面描述清单」（JSON），如「显示一个 3 行 2 列的表格，标题是销售数据」。客户端收到清单后，用预先准备好的安全组件渲染。

像餐厅菜单：顾客只能点菜单上有的菜，不能进厨房自己做。客户端维护受信任的组件目录（Card、Button、TextField、Table），Agent 只能请求渲染已有组件，无法注入任意代码；同一份描述还能跨 React、Flutter、原生应用渲染，并支持流式增量生成。

要区分 **AG-UI**：它不是界面描述语言，而是事件/传输协议，负责把 Agent 执行状态（消息、工具调用、状态补丁）流式推送到前端，本身可以承载 A2UI 载荷。二者互补而非同类。

声明式适合标准化交互（表单、表格、卡片）；高度定制化需求（自定义可视化、游戏界面）仍适合直接生成代码。

### 4.2 HTML 交付与动态表单

生成式 UI 也改变最终交付形态。传统上 Agent 任务结束产出 Markdown 汇报，但一页页翻读线性 Markdown 并不好读。直接产出 HTML 有几个优势：

- **交互式演示**：可操作地演示系统如何运行，胜过大段文字；
- **更好的数据可视化**：图表而非表格，还能筛选、下钻；
- **可持续完善**：HTML 不必在任务结束时一次性产出，可以在推进过程中不断补充。

一个研究项目网站可以同时承担实验数据追溯、训练指标监控、运行原理展示——既是交付件，也是活文档。

**澄清用户意图**也是典型场景。文本问答每个问题一轮对话，十个澄清点十轮交互；问题间还有依赖（目的地影响交通方式），纯文本难以表达级联关系。

Agent 可以生成结构化表单：文本框、下拉菜单、复选框、日期选择器；再用 JavaScript 实现级联逻辑——选择「往返」才显示返程日期。用户一次填完，无需多轮对话。

### 4.3 SQL 与 Artifact 模式

数据库查询是代码生成显著提升体验的场景。传统依赖 GUI 或手写 SQL，前者繁琐，后者要求专业知识。

Agent 可以把自然语言转 SQL，但有一个关键设计选择：执行 SQL 后用自然语言描述结果，还是把 SQL 作为 artifact 交给前端直接执行？

第一种看似更智能，效率却极低——结果可能数千行，让 LLM 阅读后再用文字描述，消耗大量 token、耗时长，而且「抄写」数据非常容易出错。

更好的方案是 **Artifact 模式**：Agent 不读数据，只生成 SQL 查询代码，作为独立可执行产物交给系统；系统直接查询数据库，把数据渲染成表格。数据从数据库直达界面，完全绕过 LLM 这个「中间人」。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig5-9.svg)

<p>图 5：SQL 查询 Agent 流程</p>

生成的 SQL 与可视化代码不能直接执行。执行层应使用只读数据库账号，解析 SQL 只允许批准的 `SELECT`，拒绝 DDL、DML 与多语句；用户提供的值由服务端参数化绑定；限制查询时间、返回行数、可访问表与时间范围。可视化代码在隔离网络与文件系统的沙盒中运行，只能产生规定格式的结果。

Artifact 模式缩短数据路径，但不能替代权限检查与执行隔离。

更进一步，可以生成两个 artifact 形成流水线：SQL 查询 + 可视化代码。前端把 SQL 结果直接传给可视化代码，LLM 只负责生成代码，不参与数据传递——这正是「代码生成作为接口」的精髓。

### 4.4 动态生成软件的权限边界

代码生成的终极应用，是让 Agent 从零创建软件。完全动态生成成本与延迟高，更务实的方向是**基于已有框架定制**：保留基础软件稳定性，在特定维度开放用户控制——改颜色、加菜单、换字体，Agent 修改前端代码，热加载即时生效。

但动态生成改变了传统软件的安全前提。过去业务代码经过开发、审查、测试、部署后基本稳定，**权限判断通常写在应用层**：业务代码先判断「当前用户能否读写这条数据」，再访问数据库。

当接口、工作流乃至数据访问代码都由 Agent 随时生成或改写时，这一层不再稳定。新代码可能漏掉权限检查、暴露字段，或绕开已有判断。无论原因是生成错误还是提示注入，结果一样：原本由业务代码维持的权限边界可能被悄然破坏。

因此安全目标不能是「保证 AI 每次都把权限检查写对」，而应该是：**即使 AI 写错了代码，权限约束仍然无法被绕过。**

更稳妥的架构是**把信任边界下移到数据层**：

- 动态生成的应用层负责界面、流程与业务编排；
- 数据层由稳定、经人类审查的机制强制执行「谁能对哪条数据做什么」；
- 数据库行级安全策略限制租户数据，约束与校验器拒绝非法状态，受控视图/存储过程只暴露允许操作；
- 每次读写携带由受信任运行时绑定的**访问上下文**（用户、租户、角色、Agent 身份），生成代码只能以受限身份访问，不能伪造，也拿不到可绕过规则的高权限凭证。

应用层仍可做权限预检查以尽早反馈，但数据层保留最终裁决权。同一条规则可以在上层改善体验，在下层提供保证。前提是所有数据访问都必须经过受信任的数据层，生成代码不能绕过它直连数据库。

## 5. 代码创造代码：Agent 自举

把代码生成推向极限，会出现一个问题：Agent 能不能用代码生成能力创造另一个 Agent？

### 5.1 自我修复

Agent 自举的前提是自我修复。OpenClaw 的 `doctor` 命令检测三类问题：

- **配置异常**：过期 OAuth token、遗留配置格式、端口冲突；
- **状态问题**：陈旧锁文件、插件依赖缺失；
- **服务健康**：网关未运行、沙盒镜像缺失。

然后分层修复：安全的修复（配置归一化、锁文件清理）自动执行；有风险的操作（服务重启、强制覆盖）需用户确认。

要避免夸大 Agent 的作用：过期 token、锁文件、端口冲突这类高频问题，本身就有明确检测规则与固定修复动作，`doctor` 以一组确定性检查为基础覆盖它们——与传统运维脚本没有本质不同。

真正体现 Agent 能力的是第二层：对确定性规则未覆盖的疑难问题，交给 LLM 分析日志、理解配置语义、推断因果，生成针对性方案。确定性检查保证常见问题稳定修复，LLM 兜底长尾。

### 5.2 让 Agent 编写 Agent

创造高质量 Agent 远比生成普通应用代码复杂，需要对 Agent 架构模式、最佳实践与常见陷阱有深入理解。常见缺陷：

- **上下文管理随意**：不用标准消息格式，把轨迹转纯文本塞进上下文，忽略结构化消息的缓存优化，工具循环有边界 bug；
- **工具设计不规范**：描述简略、缺少边界与负面清单、参数无示例；
- **技术选型滞后**：倾向使用训练数据中最常见但已过时的模型与 API；
- **生态脱节**：废弃 API、不再维护的库、有缺陷的模式。

最有效的路径不是把规则穷尽在提示词里，而是**提供高质量的 Agent 实现作为参考范例**，让代码生成 Agent 在此基础上修改，而非从零开始。

范例代码本身就是最佳实践的载体：基于范例修改比从零编写更容易做对，架构上的好选择会自然保留，不需要把每条规则都说清楚。

Agent 接到开发新 Agent 的任务时，先复制自己的代码（或其他经过验证的实现），再针对性修改：调整系统提示词匹配新角色，替换或增删工具，修改业务逻辑但保留架构框架。

这种「自我复制 + 适应性修改」类似生物学中的基因复制加变异：既保证新 Agent 继承核心技术优势，又允许在特定维度差异化。

## 6. 补记

代码作为元能力，真正的分界线是**产物有没有可执行的精确描述**：

- 有紧凑参数化描述的（零件、表格、查询、界面结构），代码生成更精确、可验证、可编辑；
- 只有高维感知描述的（人脸、自然风景、纹理），生成模型更合适；
- 两者可以混合——几何用代码，表面用生成模型。

生成式 UI 的安全关键不在「让模型少写错」，而在**把权限放在模型改不到的地方**。应用层可以动态变化，数据层的规则必须稳定。
