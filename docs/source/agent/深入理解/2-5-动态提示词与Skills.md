# 动态提示词与 Skills

## 1. 静态提示词的痛点

Agent 覆盖的业务场景越来越多，系统提示词会不断膨胀：客服的退款规则、编程的代码规范、文档的格式要求，全塞进一个提示词，会带来两个问题：

- **浪费 token**：大部分内容与当前任务无关；
- **注意力被稀释**：无关信息过多，会稀释模型对关键内容的注意力。

从静态提示工程到动态提示词，演进的思路只有一句：**不是把所有知识一次性塞给 Agent，而是让它按需加载。** Agent Skills 就是这套思想的工程实现。

## 2. 一个 Skill 的三层结构

Agent Skills 把能力模块化为独立、可按需加载的知识包。每个 Skill 本质是一套包含领域指导的提示词集合，采用**渐进式披露**（Progressive Disclosure）：先给目录摘要，需要时再加载完整内容。

就像不会把公司所有部门的操作手册堆到新员工桌上，而是先给一份总目录，需要哪本再去取。

### 2.1 元数据

每个 Skill 必须包含 `SKILL.md`，开头是 YAML frontmatter，含 `name` 与 `description`。目录必须在正文加载前对 Agent 可见，使它先判断当前任务是否需要某项能力，而不必为所有能力支付完整上下文成本。

`description` 是路由决策的关键：要足够短（控制常驻 token），写法要像**路由条件**而非功能介绍。可以明确写出「何时使用」「何时不使用」，并给出几条典型反例，减少宽泛匹配造成的误触发。这是写作建议，不是额外格式字段。

描述太宽泛（如「help with backend」）等于任何后端工作都能触发，路由就会失准。**「何时该用我」比「我能做什么」重要得多。**

### 2.2 核心流程

当 Agent 判断任务需要某个 Skill 时，运行时才加载完整 `SKILL.md`。触发方式有两种：

- 用户显式输入斜杠命令（如 `/pptx`），客户端在本地拦截并展开，模型不必先发起工具调用；
- 模型读过目录后自行判断，调用专用 Skill 工具，比前者多一次 ReAct 往返。

两条路径落点相同：完整指令在调用位置作为 user message 加入会话；模型自主触发时，那条 tool result 只是一句占位符，并不承载正文。没有专用激活工具的运行时，则用通用文件读取工具读 `SKILL.md`，正文以 tool result 进入上下文。

以 PPTX Skill 为例，核心流程包括：如何提取文本、如何解压 PPTX 访问 XML、关键文件的路径约定。

### 2.3 细则

主文件可以引用更详细的子文档，例如 `html2pptx.md`（HTML 模板生成 PowerPoint 的详细工作流）、`reference.md`（格式技术细节）。Agent 根据具体需求选择性阅读。

## 3. 如何写一份可用的 Skill

运行时结构解决「什么时候加载、加载多少」，内容还需要有人把经验写成可执行的指令。一份实用的 Skill 不应只是背景知识或一次成功对话的摘要，而应让刚加入团队的人知道：遇到什么任务时使用、按什么顺序行动、哪些情况停下来确认、什么结果才算完成。

建议包含四个部分：

- **角色与读者**：这份 Skill 服务谁、面向什么任务、输出应达到什么标准；
- **核心原则**：只保留三到五条最重要的判断，并为关键原则配正例与反例；
- **禁止清单**：记录高频错误、越权动作与容易误解的表达，同时写清合法例外；
- **参考资料**：术语表、模板、范文与更详细的子文档。

规则尽量写成「作用域 + 动作 + 例外 + 验证方式」，避免把所有情况堆成一张越来越长的禁用词表。

写作型 Skill 可以从三到五篇最满意的原创文章开始：让 Agent 归纳用词、句式、段落结构与语气，生成二十行左右的初版；再用它处理一项真实写作任务，由作者逐句改稿。原文与修改稿的差异比抽象地说「更自然一点」更有信息量——它能告诉 Agent 哪些词被删、哪些长句被拆、哪些地方要补事实。把反复出现的改动整理回 Skill，并为每条规则保留正例、反例与适用范围。

Skill 还可以捆绑可执行代码与模板文件，例如 PPT Skill 包含模板与解析脚本。它的价值不仅在于上下文管理，更在于为领域知识提供可持续积累的路径：每个 Skill 自包含、可独立开发测试、可单独版本控制，能力扩展从集中编辑系统提示词，变成分布式的 Skill 生态——类似 pip、npm 的包管理。

一个对开发者很重要的原则：**选择 Agent 交互模式时，应与模型厂商的训练方法保持一致。** 基础模型公司推行的 Agent 用法，本质是它们专门训练过的模式，同一生态内的模型天然表现更好。

## 4. Skills 在上下文中的位置

理解 Skills 的上下文成本，必须把「元数据目录」与「完整指令」分开：

- **标准层**：规范规定的是加载时序，不是消息角色——目录先于正文可发现，正文在 Skill 被选中后按需加载；具体角色、包装方式、目录是否每轮重建，由 Harness 决定。
- **Claude Code 的实现**：目录作为运行时上下文消息提供，完整指令在调用位置作为 user message 注入。这里的「system prompt」可以描述逻辑上的稳定指令层，但不应理解为所有客户端都使用 API 的 `role: "system"`。
- **OpenAI Codex 的实现**：每轮上下文构造阶段重新渲染 Skills catalog，作为 `developer` 上下文片段提供；显式选中的 Skill 正文以带 `<skill>` 标记的 `user` 片段注入。其他来源的 Skill 也可通过专用工具按需读取。

实现方式不同，但都遵循 **「少量目录常驻、完整正文按需加载」**。

需要厘清一个常见误解：**「对 KV Cache 友好」不等于「零成本」**。目录首次进入请求需要处理，完整正文首次加载也会产生新增计算；当前缀稳定时，后续请求才可以复用缓存。Skills 的共同收益是：无需启动时加载所有正文，也无需在每次调用新 Skill 时回头改写已建立的上下文。

## 5. Skills 与工具的关系

如果把所有专用代码工具的定义都放进系统提示词，数量膨胀会消耗大量 token，也会干扰注意力。而在 **Skill + 通用执行器**模式下，工具数量始终很少，Skill 内容通过渐进式披露按需加载，不影响已缓存的前缀。

两种能力形态的选择可以看一个判断：这项能力是**确定的原子操作**，还是**需要知识与流程的领域任务**。前者做成工具，后者做成 Skill；高风险、强业务约束的操作仍应做成参数明确、权限受限的专用工具，而不是塞进 Skill 文本里。

## 6. 补记

Skills 最容易被当成「更长的提示词」。它真正解决的是**能力的可发现性与上下文预算**：目录常驻让模型知道自己会什么，正文按需加载让无关能力不占预算。

写好 Skill 的关键不在篇幅，而在两处：`description` 决定它会不会被选中，正文结构决定选中后能不能稳定执行。一个短小、可读、能通过真实任务检验的初版，比一开始罗列几十条规则更适合迭代。
