# 单轮 RL 与算法

## 1. 单轮设定

「单轮」指任务在一次交互中完成：模型接收输入、产出输出、获得奖励，无需维护跨步骤状态。

这种简化让我们聚焦 SFT 与 RL 的学习机制差异，而不被多轮复杂性干扰：相同任务、相同基础模型、相同计算预算，唯一变量是训练方法。

先建立最小直觉：本篇 RL 大多基于**策略梯度**——让模型对同一问题生成多条回答，奖励高的提高概率，奖励低的降低概率。

- **PPO**：在概率比超出区间时裁掉代理目标中的额外收益；它抑制大幅更新，但不是硬约束。价值网络估计基线，算出更细的优势。
- **GRPO**：不训价值网络，用同一问题的多条回答互相比较，判断每条相对好坏。

伪代码（GRPO）：

```python
for prompt in batch:
    group = [rollout(policy, env.reset(prompt)) for _ in range(G)]
    rewards = [verify(trajectory) for trajectory in group]
    advantages = normalize_within_group(rewards)
    update(policy, group, advantages)
```

PPO 的价值网络与裁剪：

```python
for trajectory in rollouts:
    returns = discounted_returns(trajectory.rewards)
    values = value_model(trajectory.states)
    advantages = returns - stop_gradient(values)
    ratio = exp(policy.log_prob(trajectory.actions)
                - old_policy.log_prob(trajectory.actions))
    policy_loss = -mean(min(
        ratio * advantages,
        clip(ratio, 1 - epsilon, 1 + epsilon) * advantages
    ))
    value_loss = mean((value_model(trajectory.states) - returns) ** 2)
update(policy, value_model, policy_loss + value_coef * value_loss)
```

GRPO 的「相对」来自同组比较；PPO 的 `old_policy` 是生成这批 rollout 时冻结的策略快照，概率比衡量当前策略移动了多远。两者都依赖可靠环境与奖励。

## 2. 学会「何时不思考」

大型思考模型对所有问题都生成冗长思维链，简单问题造成不必要开销。

先验证直觉：**NoThinking 模式**（通过 `<think></think>` 跳过思考）在简单问题上性能相当甚至更好，只有困难问题 Thinking 的优势才显现。

AdaptThink 用 RL 训练模型自适应选择模式，两个组件：

- **约束优化目标**：鼓励 NoThinking，同时确保整体性能不下降；
- **重要性采样**：平衡 Thinking/NoThinking 样本，解决初始模型几乎总选 Thinking 的冷启动问题。

一次历史训练在 8×H100 上跑到 step 300：MATH500 准确率 0.8100→0.8180（+0.8pp），响应长度 4911→1577（-67.9%）；GSM8K 0.7968→0.8188（+2.2pp），长度 1025→477（-53.4%）；AIME mean@16 0.3146→0.3104（-0.42pp），长度 12119→6402（-47.2%）。

NoThinking 比例分别为 83.8%、84.2%、56.25%，说明数据集汇总层面存在与难度一致的路由信号，但不能称为逐题完美难度感知，也不能声称准确率普遍提升。

这次训练在 step 300 后继续到 410，累计 36.92 小时，随后 W&B 状态变为 crashed；配置的 10 epochs 并未完成。历史记录也提醒：**RL 实验的可复现性依赖版本、脚本与评估路径的严格对齐。**

AdaptThink 可与 Prompt 蒸馏互补，形成「快—慢双系统」：蒸馏降低需要思考的任务比例，AdaptThink 优化剩余任务的触发策略。

## 3. GeneralPoints：记忆与泛化的对照

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig8-12.svg)

<p>图 1：GeneralPoints 实验架构</p>

GeneralPoints 是算术思考卡牌游戏：用四张牌的数字、加减乘除、每数一次，凑出 24。实验设计纯文本 GP-L 与图像 GP-VL 两个变体，分别考察规则泛化与视觉泛化。

**规则变体**：训练时 J/Q/K 都计为 10，测试时分别计为 11/12/13，确保出现训练未见的数字组合。**视觉变体**：训练用黑色花色，测试用红色花色。

基于 Llama-3.2-Vision-11B：先 SFT 初始化，使其具备基本指令遵循；然后在相同计算预算下分别扩展 SFT 与 RL（带价值网络的 PPO），用单一规则数据训练，在 ID 与 OOD 测试集评估。

结果：

- **规则 OOD**：RL 在 GP-L 上 +3.5%（11.5%→15.0%），SFT 下降 8.1%（11.5%→3.4%）；GP-VL 上 RL +3.0%，SFT 下降 5.6%。
- **视觉 OOD**：RL 在 GP-VL 上 +17.6%（23.6%→41.2%），SFT 下降 9.9%（23.6%→13.7%）。

追踪视觉识别准确率发现：RL 通过结果导向优化改善了底层视觉编码器，且改善与整体性能高度相关；SFT 过度拟合思考过程中的 token 模式，忽视视觉 token，识别准确率反而下降。

实验也说明，在本设定下（Llama-3.2-Vision-11B 量级 + 严格结构化输出），RL 需要先用 SFT 初始化：未经 SFT 直接端到端 RL 完全失败，因为基模无法产生结构化输出，奖励无法计算。这是特定设定结论，不是普适规律——足够强的基模可以跳过 SFT 直接 RL。

另一个发现：验证迭代次数越多，测得的泛化越好（10 次 +5.99% vs 1 次 +0.48%），增加测试阶段计算量是泛化提升的重要因素。

为什么 SFT 在分布偏移下下降、RL 更好？一种与观察相符的解释是：有限 SFT 数据强化了「遇到 J/Q/K 就当 10 用」的固定模式；测试时 J=11，模型仍按 10 计算。结果导向的 RL 更可能强化「重新计算直到得到正确答案」的策略。

这是「记忆 vs 泛化」的受控量化，但不是「SFT 必然只能记忆、RL 必然学会通用算法」。

## 4. GRPO：从 16 次 rollout 到一次更新

GRPO 是今天最常用的 RL 算法之一。用 SWE-bench 任务理解它：某 Python 项目的 `parser.py` 在空输入时触发 `IndexError`，要求修复且不能改测试。

### 4.1 四步

**第一步：让策略模型重复尝试。** 把同一份初始代码、同一条问题描述复制到 16 个隔离沙箱，让模型独立解决 16 次。每次包含「阅读代码 → 修改 → 运行测试 → 提交」，整条过程叫一次 **rollout**。采样有随机性，16 次可能走出不同路径：正确补边界检查、只捕获异常掩盖问题、改错文件、试图改测试。

**第二步：计算奖励。** 每条 rollout 结束后，验证器在干净环境应用补丁并运行测试。假设 4 次通过且没改测试，12 次失败，则前 4 条奖励 1，后 12 条 0。coding 里「奖励计算」并不神秘，就是测试与规则；开放式任务才需要人类偏好或奖励模型。

**第三步：计算相对优势。** 奖励只说明成败，**相对优势**说明它相对同组其他尝试有多好。组平均成功率 4/16：通过的 4 条高于平均，得正优势；失败的 12 条低于平均，得负优势。

GRPO 的核心就是组内比较。若 16 条全失败或全成功，奖励完全一样，优势消失。RLVP 的路径信号、过程奖励、部分进展奖励，解决的正是如何在这些组里恢复有意义的差异。

**第四步：梯度下降更新。** 把优势转成损失、算梯度，优化器提高正优势轨迹中选择的概率，降低负优势轨迹中的概率。它不是把某个成功补丁背下来，而是在许多任务与 rollout 上逐步调整：以后遇到类似错误，「先复现、检查边界、修改并运行测试」更容易出现，「掩盖异常、改测试、没验证就提交」更少出现。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig8-13.svg)

<p>图 2：同一任务的 16 次 rollout、验证与相对优势</p>

四步构成一个 **step**：第 k 步用当前策略生成一批 rollout，完成奖励、优势与梯度计算，再更新参数；第 k+1 步用更新后的策略重新 rollout。训练 100 steps 就是重复约 100 轮。

粗略估算：复杂 Agent rollout 数十轮工具调用，即使 16 条并行，阶段墙钟由最慢一条决定；假设最慢 2000 秒，梯度与优化器 600 秒，一个 step 约 43 分钟，100 steps 接近 72 小时。

PPO 与 GRPO 都遵循这个闭环，区别在「拿谁比较」：GRPO 直接比较同一问题的多条 rollout，不需要价值模型；PPO 训练价值模型，估计每步「通常能做到多好」，再判断当前动作是否超预期，更适合细粒度信用分配的长轨迹。两者都限制单次更新幅度。DPO 不同：直接学习事先收集的偏好对，不让当前策略在线生成 rollout。

## 5. 为什么 LLM RL 通常优先 On-Policy

先区分两个词：

- **Online**：数据在训练过程中不断通过与环境交互产生；
- **On-policy**：生成 rollout 的行为策略 μ 与当前要优化的策略 πθ 相同或足够接近。

异步集群即使持续在线生成，只要 rollout worker 落后几个 checkpoint，数据就陈旧，训练已带 off-policy 成分。

策略梯度要估计当前策略下的期望奖励。若数据由另一个策略 μ 采样，要用重要性比率纠正：

\[
\rho_t=\frac{\pi_\theta(a_t\mid s_t)}{\mu(a_t\mid s_t)}
=\exp\left(\log\pi_\theta-\log\mu\right)
\]

真正新鲜的 on-policy rollout 在参数更新前应满足 πθ=μ，所以 ρ=1。这让训练集中在模型实际会进入的状态，避免分布错位带来的高方差修正。

Off-policy 的优点是旧数据可复用、采样与训练可异步、吞吐更高；代价是策略越陈旧，ρ 分布越重尾。自回归长序列上，前缀或轨迹修正会连乘许多 token 比率，少量偏差可能累积成极大或极小权重。

PPO 的 clipping 能限制离群更新，却不能无损恢复丢失的覆盖；裁太多丢梯度，不裁又可能被少数样本主导。因此「On-policy 更好」不是普遍定理，而是在当前 LLM 策略梯度中通常意味着更低的分布偏差与更稳定的优化。

### 5.1 名义 On-Policy，数值上却 Off-Policy

大规模 RL 常用 vLLM/SGLang 生成 rollout，再用 FSDP/Megatron 重算 log probability 与梯度。即使加载同一份权重，浮点精度、归约顺序、张量并行、批大小、KV cache 与 fused kernel 的差异，也可能让同一 token 的 log probability 略有不同。

于是更新前本应为 1 的 ρ 已偏离 1：系统名义上同步了权重，数值上却把 on-policy 变成了 off-policy。受控实验表明，单独存在的微小 token 级训练—推理差异就可能引发训练崩溃。

放大链条：**log probability 小误差 → 指数化概率比偏差 → 长前缀累积 → clipping/优势加权改变 → 梯度方向与有效样本数改变。**

例如 4000 个 token 的 log ratio 都有同方向 \(10^{-3}\) 偏差，轨迹级比率会累积到 \(e^4\approx54.6\)。真实误差未必同号，但长序列会放大「每个 token 看起来很小」的误差。早期 token 的微小概率差还可能改变采样出的 token，使整条状态轨迹分叉。

工程上要把它当核心问题：

- **任何参数更新前**，用同一批轨迹比较 sampler 与 trainer 的 token log probability，监控 ρ 的均值、分位数、最大值、近似 KL 与被裁剪比例——这是最直接的 on-policy 单元测试；
- 同步的不只是权重，还包括 LoRA adapter、tokenizer、chat template、模型 revision 与位置编码；rollout 要保存生成时的 behavior log probability；
- 尽量对齐采样与训练的精度、并行布局与关键内核；做不到就明确视作 off-policy，采用重要性修正并监控有效样本数；
- 保持 rollout 新鲜，限制每批数据的更新轮数与异步 staleness；重用旧数据是经过测量的偏差—效率取舍，不是免费加速。

## 6. 补记

单轮 RL 的核心不是「算法多复杂」，而是**奖励能否在组内产生差异**。全成功或全失败，GRPO 的优势都为零；这时再调超参也没用，应先改任务难度、奖励或课程。

另一个经验是：PPO/GRPO 的选择取决于信用分配粒度。短轨迹、结果清晰，GRPO 简单有效；长轨迹需要细粒度归因，价值网络可能更合适。但无论哪种，环境与奖励的可靠性都比算法更重要。
