# 现代 Agent：LLM + 上下文 + 工具

用过 Cursor 写代码、用 Deep Research 调研课题、用 Manus 操控浏览器、让手机助手订票，或者让 Pine AI 替你打电话协商账单——这些产品形态各异，但都不是「你问一句、它答一句」的被动对话，而是能自主规划步骤、调用工具、根据结果调整策略的智能系统。

理解它们，可以先回到一个最小公式。

## 1. 一个公式与一条边界

**Agent = LLM + 上下文 + 工具**。

这里的加号表示工程组件的组合，不是强化学习里的形式化定义；更重要的是，这个公式只描述 Agent 边界之内的实现，**不包含 Agent 交互的 Environment（环境）**。

- **LLM 是大脑**：不只是模型参数，而是整个决策内核——理解意图、思考规划、做出判断。能力来自预训练积累的世界知识，以及后训练固化的决策策略。
- **上下文是眼睛**：不只是输入的那段文本，而是每个决策点收到并保留的信息表示——环境观察、用户记忆、领域知识、自身状态与任务进展。
- **工具是手脚**：感知或改变外部世界的接口，包括工具定义、调用协议与适配器；从预定义调用到动态生成代码，从委托子 Agent 到主动与用户沟通。

换一种直观说法：**大脑 + 眼睛 + 手脚**。三者缺一不可。

在强化学习与控制论视角下，Agent 与 Environment 是闭环交互的两方，而不是彼此的组成部分：环境返回观察，Agent 选择行动，行动改变环境，新状态产生下一次观察。

<p>图 1：Agent 与 Environment 的闭环，以及 Agent 内部的 Model–Harness 结构</p>

这张图有两个抽象层次。外层是 Agent 与环境的交互：环境包含文件、数据库、网页、用户、其他 Agent 与物理世界，Agent 只能通过观察与行动接口接触它。内层是 **Model–Harness 结构**：Model 负责策略决策；Harness 是 Agent 边界内环绕模型的运行与治理层，负责构造上下文、暴露工具、维护循环与状态，并实施权限、验证与纠正。

因此，LLM 对应 Model，「上下文 + 工具」构成最小 Harness；生产系统还会加入约束、验证与纠正。**Harness 可以创建、隔离或代理环境，却不包含环境自身的状态与转移规律。**

三个组件可以映射到 RL 的策略与交互接口，但不是严格一一等同：

| 直觉 | 实现组件 | 学术概念 | 含义 |
|---|---|---|---|
| 大脑 | LLM | 策略 Policy | 面对当前信息，从可选行动中挑出最合适的一个 |
| 眼睛 | 上下文构造 | 观察与历史 | 把环境观察与已有历史组织成当前决策所需的信息 |
| 手脚 | 工具与适配器 | 观察/行动接口 | 规定能读取哪些观察、发出哪些行动，以及接口格式 |

## 2. 观察空间与动作空间

**观察通道与动作接口共同构成 Agent 与外部环境的边界。** Harness 把环境返回的观察转换为模型能处理的上下文，再把模型选择的行动转换为工具调用。没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。

所以在底层模型固定时，**提升 Agent 表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间**——也就是扩展上下文与工具。许多看似需要「更聪明的模型」的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。

- **Manus**：把 Deep Research、Coding、Computer Use 三条相对独立的路线放进同一个生产级 Agent。虚拟浏览器扩大观察空间，文件系统、代码执行与命令行扩大动作空间。它不是只靠换一个更强的模型，而是取三类 Agent 观察与动作空间的并集。
- **OpenClaw**：把接口延伸到用户的数字生活。通过 WhatsApp、Telegram、Slack、Discord、iMessage 等渠道接收任务与返回结果；用本地 Gateway 连接 Google Drive、Notion 与本地文件系统。分散在不同账号与设备中的数字文件，经用户授权后进入同一个观察空间。

不同产品的差异，本质上就是观察、行动与策略的差异：

| 产品 | 观察（眼睛） | 行动（手脚） | 策略 |
|---|---|---|---|
| Coding Agent | 需求、代码片段、目录、终端输出 | 搜索、读写文件、执行命令 | 增量开发：理解→搜索→编辑→测试→修复 |
| 搜索 Agent | 搜索结果、网页、论文摘要与引用 | 搜索、读网页、生成报告 | 迭代深化，逐步综合 |
| 电脑操控 Agent | 截图、DOM/无障碍树、操作结果 | 点击、输入、滚动、截图、执行代码 | 观察屏幕→定位元素→操作→验证 |
| 手机助手 | 手机截图、App 状态、系统反馈 | 点击、滑动、输入、打开 App | 理解意图→定位 App→操作→确认 |
| 个人办事 Agent | 经授权的账户记录、账单、服务商资料 | 打电话、发邮件、填表、与用户确认 | 收集信息→制定策略→联系→谈判→汇报 |

这些系统的共同特征：**开放式动作空间**（能生成任意自然语言与代码）、**内部思考**（行动前先规划）、**持续交互**（根据反馈调整策略）。

## 3. 工具：Agent 的手脚

工具是 Agent 与外部世界交互的桥梁：感知类工具承载环境到 Agent 的观察，执行类工具承载 Agent 到环境的行动。没有工具，Agent 只能纸上谈兵。

按交互方向可分为五类：

1. **感知工具**：搜索引擎、文件系统、API、数据库，让 Agent 访问信息；
2. **执行工具**：代码执行、文件操作、系统命令、外部 API，把决策变成行动；
3. **协作工具**：委托子 Agent、请求人工确认、多 Agent 协调；
4. **事件触发工具**：新邮件、定时任务、Webhook 回调，由外部事件唤醒 Agent；
5. **用户沟通工具**：文字、语音、邮件，把进展或关怀传递给用户。

**工具调用**（Tool Calling / Function Calling）让模型以结构化方式使用工具。流程四步：上下文里声明有哪些工具（名称、用途、参数）→ 模型判断要不要调、调哪个、传什么参数 → 工具执行结果追加到上下文 → 模型据此决定下一步。这个循环就是 ReAct 的基础。

```text
第一步：声明工具                    第二步：模型决定调用
tools: [{                          assistant: {
  name: "get_weather",               tool_calls: [{
  parameters: {                        function: "get_weather",
    city: "string"                     arguments: {city: "北京"}
  }                                  }]
}]                                 }

第三步：结果追加到上下文              第四步：模型基于结果回复
tool: {                            assistant: {
  tool_call_id: "call_1",            content: "北京今天 28°C，晴。"
  content: '{"temp":28,"sky":"晴"}'  }
}
```

开发者只需定义工具与执行工具调用，模型自主完成「要不要调、调哪个、传什么参数」。

工具设计先从任务所需的最窄能力起步，再随复杂度扩展：只做四则运算，一个参数清晰的计算器就够；要读表格、清洗缺失值、算统计量并绘图，受限的 Python 代码解释器比不断叠加专用工具更容易组合。但通用性也扩大出错与攻击面：代码要在隔离沙箱运行，默认不能访问网络、不能读授权目录之外的文件，并限制执行时间、CPU、内存与输出大小。

**通用工具不总是优于专用工具。** 支付、删除数据、发送邮件、生产部署等高风险或强业务约束操作，仍应封装为参数明确、权限受限、全程可审计的专用工具，必要时加预览与人工确认。核心原则是：**通用基础能力用于组合与探索，专用工具用于约束高风险与强业务规则操作。**

## 4. LLM：Agent 的大脑

LLM 是决策核心：解析真实意图，把模糊任务拆成可执行步骤，执行中持续判断下一步做什么、要不要调工具、调哪个、传什么参数。

LLM Agent 的独特能力是**内部思考**——行动前先规划与推演。这得益于预训练习得的逻辑规则，包括数学定律、因果关系与问题分解策略。因此，今天的 Agent 不是盲目随机探索，而是在结构化知识体系上展开。

### 4.1 模型即 Agent

「模型即 Agent」指先进模型通过后训练（尤其是强化学习）把工具调用内化为原生能力：何时调用、调哪个、传什么参数都由模型自己决定，无需人工编排。

但这不意味着框架层不重要。**Harness 原指马具**——不是限制马的奔跑能力，而是把力量引导到正确方向。模型越强，围绕它的 Harness 越关键：上下文管理、工具接口、安全约束、验证与纠正。

模型自主决策空间越大，出错影响面也越大，因此需要更精细的约束、验证与纠正。厂商的真正优势不是「让框架变薄」，而是对模型与外围 Harness 协同优化。

### 4.2 苦涩的教训与工程节奏

如果模型持续变强，今天的 Harness 会不会被模型吃掉？《苦涩的教训》回顾了 AI 研究七十年反复上演的一幕：研究者一次次把领域理解编码进系统，短期见效，长期却输给能随算力与数据扩展的通用方法。

对这个问题，更务实的态度是：**方向认同，节奏务实**。方向上，模型确实会持续吃掉 Harness——工具调用、长程规划都曾靠外部编排，如今已是原生能力；但节奏上，这个过程比想象中慢：训练以月计，模型也无法一次内化真实业务中的所有约束与偏好。模型此刻的能力边界，就是 Harness 此刻的价值所在。模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

## 5. 上下文：Agent 的眼睛

上下文是每个决策点能看到的全部信息：任务说明、参考手册、沟通记录、最新数据。API 视角下由五部分构成：

1. **系统提示词**：开发者编写，整个对话保持不变，定义身份、权限与行为准则；
2. **工具定义**：声明可用工具的名称、描述与参数，和系统提示词一起构成静态前缀；
3. **用户消息**：用户输入，也可能包含 RAG 检索引入的外部知识；
4. **模型回复**：之前生成的回复，最多含思考过程、文本内容与工具调用请求；
5. **工具执行结果**：框架执行工具后返回的结果，是下一步思考的直接依据。

前两项是**静态前缀**，后三项是随交互增长的**动态消息历史**。Agent 每次调用模型时，上下文 = 静态前缀 + 轨迹。

### 5.1 消融实验的启示

把五个组件逐一去掉，观察 Agent 行为变化，会看到它们并不同等重要：

- **工具定义**是行动能力的基础。缺失后模型照样给出格式工整、语气笃定的答案，但数据来自参数记忆，与基于观测的答案排版一模一样——它是坦白拒绝还是就地编造，主要取决于模型的幻觉率与诚实度。
- **工具执行结果**是闭环控制的关键。缺失会让 Agent「盲目」执行，反复重试直到耗尽迭代预算。
- **思考过程**记录「为什么这么做」，工具结果记录「发生了什么」；当前者可以从后者重建时，丢掉它几乎没有代价。
- **历史消息**防止冗余操作，避免重复犯错。

核心洞察：**上下文决定 Agent 能看到什么，而 Agent 只能基于看到的信息做决策**。组件是否不可或缺，衡量标准是它承载的信息能否从别处重建。还有一点更重要：**「给出了回答」不等于「完成了任务」**——上下文残缺时，典型失败不是报错退出，而是一个看上去毫无破绽的答案。

## 6. 能力从哪里更新

Agent 的行为改变不只发生在训练阶段，按更新位置与持续时间可分三条互补路径：

- **上下文适应**：发生在当前任务中。示例、状态与检索结果进入上下文后，模型立即调整行为，但不会改变下一次会话的持久状态。快、低成本，受窗口与信息组织方式约束。
- **外部产物更新**：让变化跨任务保留——把事实与经验整理成知识文档，把可语言化的策略写进 Prompt 或 Skill，把确定性流程与约束写成程序与 Harness。这些产物可审计、可修订，执行时仍需通过上下文或工具接口被 Agent 使用。
- **参数更新**：面向医疗影像理解、语言风格或隐式决策策略等高维能力，外部规则难以完整表达，需要后训练更新模型参数。部署成本高，但能形成自然、广泛的泛化。

三条路径不是互斥分类，而是不同时间尺度上的协同：上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。

## 7. 补记

这个公式最容易产生的误解，是把它当成「三个零件拼起来」。真正决定 Agent 能力的，是三者的**接口边界**：观察空间决定它能看到什么，动作空间决定它能做什么，策略决定它如何选择。模型固定时，扩展接口往往比换模型更有效；但扩展接口也会同步扩大攻击面，必须配合权限、验证与纠正。

另一个容易被忽略的点是：上下文不是「越多越好」。组件是否值得保留，要看它承载的信息能否从别处重建；不能重建的（工具结果、关键约束、失败原因）必须留下，能重建的（可从工具结果推导的思考过程）则可以压缩。
