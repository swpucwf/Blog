# 上下文与消息结构

第一章把上下文比作 Agent 的「眼睛」——Agent 只能基于它看到的信息做决策。上下文的设计与管理，就是**上下文工程**。

上下文不只包含聊过什么，还包含开发者预先写好的行为规则、模型可以使用的外部功能说明。它是 Harness 中「上下文与工具」层面的核心实现，决定 Agent 在每个决策点能看到什么信息、以什么结构看到。

## 1. 决定能力上限的关键

模型在标准测试中成绩亮眼，到了实际业务却常常让人失望。原因是执行具体任务需要通用模型不知道的背景信息：产品架构、业务规则、内部约定。

想象一位天才工程师加入团队：理论功底深厚、编程能力卓越，但对产品架构、业务逻辑、技术债、团队规范一无所知；关键架构决策散落在不同成员记忆里，代码库也缺文档。这位天才即便智力超群，也难以发挥真正价值——这正是当前 AI Agent 的处境。

以 Coding Agent 为例，同样一句「帮我修复这个 bug」，上下文质量直接决定能否完成：

- **实时代码上下文**：目录结构、模块职责、核心数据结构、代码规范。缺少这些，代码可能语法正确但风格格格不入，甚至引入架构冲突；
- **流程规范**：分支策略、提交规范、评审流程、CI/CD 要求。缺少这些，可能直接向主分支提交未经测试的代码；
- **环境信息**：开发环境配置、测试数据库连接、部署方式、密钥管理。缺少这些，本地跑通的修复到了测试环境可能立刻崩溃。

三类信息构成 Agent 有效工作的最低信息需求。**模型智力只是基础，上下文质量才是能力的真正关键**：一个中等模型配上精心组织的上下文，往往胜过一个顶级模型在信息匮乏下盲目摸索。

这不只是技术问题，更是**组织问题**。大多数团队的关键知识是隐性的：架构决策只有老员工记得，业务规则靠口口相传，重要背景锁在私聊记录里。团队本身是信息黑洞，再好的 Agent 也无计可施。

**对远程工作友好的团队往往也对 Agent 友好**。像 Linux 内核这样的开源项目，全球开发者协作三十多年，靠的是高度透明、文档驱动的沟通文化：讨论公开、决策有记录、新加入者能通过历史理解演化逻辑。这种环境天然对 AI 友好——信息公开、可检索、结构化。

AI Agent 就像一个永远的新员工：给足背景，它能干得很好；什么都不告诉它，再聪明也白搭。所以构建 AI 原生团队，首先是一场文档化运动，而不只是部署新工具。

## 2. 从 ReAct 定义看上下文

ReAct 论文用一句话把 Agent、Environment、Context 与 Action 连了起来：

> Agent 在时间步 t 从环境收到观察 \(o_t\)，依据策略 \(\pi(a_t \mid c_t)\) 采取行动 \(a_t\)，其中 \(c_t=(o_1,a_1,\ldots,o_{t-1},a_{t-1},o_t)\) 是 Agent 的上下文。

最值得注意的不是符号，而是：**下一步行动取决于截至当前的完整交互上下文，而不只是眼前这一条输入**。对 LLM Agent 来说，用户消息与工具结果是环境返回的观察，模型回复与工具调用是 Agent 已采取的行动；观察与行动交替累积，形成交互历史。真实 API 请求还会在历史之前放入系统提示词与工具定义。

模型 API 本身是无状态的，每次调用都必须由 Agent 框架重新构造足够的上下文。最直接、无损的做法是带上完整历史；生产系统也可以摘要与压缩，但不能悄悄丢掉决定下一步行动所需的信息。后文所有布局、状态栏与压缩技术，都在回答同一个问题：**怎样以更低成本向模型提供一个信息充分的 \(c_t\)？**

## 3. 消息的四种角色

以 Chat Completions API 为例，请求的核心是一个**消息列表**（messages），每条消息带一个**角色**（role）：

| 角色 | 含义 | 说明 |
|---|---|---|
| `system` | 系统提示词 | 开发者编写，定义身份、规则、约束，通常只有一条，放在最前面 |
| `user` | 用户消息 | 终端用户输入，是 Agent 需要响应的请求 |
| `assistant` | 助手消息 | 模型之前的回复，含文本与工具调用请求；放回列表让模型「记住」自己说过什么 |
| `tool` | 工具结果 | 框架执行工具后送回，通过 `tool_call_id` 与对应调用关联 |

工具定义（tools）是请求的独立字段，不是消息角色。**四种消息角色 + tools 字段**，恰好覆盖第一章所说的五个上下文组成部分：system、user、assistant、tool 分别对应系统提示词、用户消息、模型回复、工具结果，tools 对应工具定义。

## 4. 单轮对话：最简单的调用

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig2-2.svg)

<p>图 2：单轮 API 调用的请求与响应结构</p>

不涉及工具调用时，请求只有两条消息：

```javascript
{
  "model": "Qwen3-0.6B",
  "messages": [
    {"role": "system", "content": "You are a helpful coding assistant."},
    {"role": "user", "content": "Hello, who are you?"}
  ]
}
```

模型返回一条 `assistant` 消息作为回复。这就是最基本的交互模式——**每次调用都是无状态的，所有需要的信息必须在请求里完整提供**。

## 5. 静态前缀与轨迹

把上面的结构放进 Agent 的多次调用中，会看到两个部分：

- **静态前缀**：系统提示词 + 工具定义，整个对话保持不变；
- **轨迹**：用户消息、模型回复、工具结果，随交互不断增长。

这解释了一个关键事实：**Agent 的上下文 = 静态前缀 + 轨迹**。后续的 KV Cache 优化、状态栏注入、上下文压缩，都建立在这个结构上——理解它，才能理解为什么「前面不能动、后面可以压缩」。

## 6. 补记

上下文工程最容易被误解成「往 prompt 里多塞信息」。真正要做的是三件事：**在正确的时机，把正确的信息，以正确的结构**送到模型面前。信息不足会让模型编造，信息过多会稀释注意力；结构混乱会让模型抓不住优先级。

另一个常被忽略的点是：上下文的质量往往先取决于团队的信息透明度。文档缺失、决策只在私聊里，模型再强也无从推断。把关键知识写下来、结构化、可检索，本身就是 Agent 工程的一部分。
