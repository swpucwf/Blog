# 能力的表达形式：工具、执行器与 Skill

## 1. 同一种能力的三种形态

同一件事——比如「部署应用」——可以做成一个 `deploy_app` 专用工具，可以拆成构建、打包、部署三个更细的工具，也可以不做工具，只写一份 Skill 文档，让 Agent 用 bash 逐步执行。

这些选项构成一条从**专用**到**通用**的谱系：

- **专用工具**：结构化函数调用，确定性高、可测试、参数受 schema 约束；代价是每个工具定义要占数百个 token。
- **Skill**：用自然语言描述操作流程，Agent 通过终端或代码解释器执行；少量通用工具就能覆盖大量场景。一份 Skill 目录项只占几十个 token，正文用到时才读。

「部署应用」的 Skill 可以写成：

```text
1. 运行 npm run build 构建项目
2. 运行 docker build -t app:latest . 打包镜像
3. 运行 kubectl apply -f deploy.yaml 部署到集群
```

Agent 通过 bash 逐步执行，无需为每个步骤创建专用工具。

**这问的是形态，不是数量。** 一项能力做成专用工具还是 Skill，与「一次让模型看见多少条能力」是两个独立决策。形态决定每条能力常驻多少 token、参数怎么传、谁能改；披露策略决定同时有多少条摆在模型面前。

## 2. 默认取向：通用优于专用

**默认取向：通用工具优于专用工具，除非存在明确的安全、权限或性能理由。**

与其提供一个四则运算计算器，不如提供通用的 `code_interpreter`，在沙盒中装好 sympy、numpy、pandas，让 Agent 执行 Python 完成任意数学计算。背后的逻辑是：**LLM 本身具有强大的思考与代码生成能力，应该利用这种能力而不是限制它**。一个 Python 解释器可以代替数十个特定功能的工具，还能处理预先没想到的边缘场景。

即使确实需要专用工具，粒度也应**偏向整合而非细分**。粒度过细会让工具数量激增，增加选择负担；粒度过粗又使单个工具过于复杂。判断是否整合的核心标准是**功能相似性**与**使用场景重叠度**。

以文档处理为例：`extract_pdf_text`、`extract_docx_content`、`extract_pptx_content` 的共性都是从文档提取文本，输入是文件路径，输出是文本。更好的设计是统一的 `read_document`，用 `file_type` 参数区分格式。整合降低了模型的认知负担，使描述更清晰，也便于扩展。

## 3. 四种情况退回专用工具

通用性有边界，以下情况值得保留独立的专用工具：

1. **安全、权限与审计**：生产数据库写操作需要精细的权限控制与审计粒度，一个开放的 `code_interpreter` 做不到。
2. **屏蔽平台差异、给出更好反馈**：文件系统的 grep、find 虽然都能用 bash 实现，但 Mac、Windows、Linux 语法不同；专门的 grep、find 工具能给出行号反馈，并屏蔽平台参数差异。
3. **使用频率极高**：高频操作值得一个专属入口，哪怕功能上已被通用工具覆盖。
4. **参数结构复杂**：涉及嵌套对象、多字段联合校验、复杂类型约束的操作，结构化 schema 能更好地引导模型传参。

### 3.1 参数复杂度为什么格外重要

模型原生工具用 JSON 规定每个工具的输入输出，便于模型遵循指令、生成合法参数，一些推理引擎甚至用限制采样强制格式。而 Skill 完全用自然语言描述，模型需要生成合法的命令行参数，还要处理引号等特殊字符的转义——转义规则比 JSON 复杂得多，而且 Linux、Mac、Windows 各不相同。

因此，**Skill 对模型要求更高，在参数复杂时也更容易出错**。折中办法是在 Skill 中要求 Agent 把复杂结构化参数以 JSON 写入文件，再在命令行中导入。

反过来，**Skill 对人类编写者更友好**：无论是否会编程，都能编写和修改 Skill；它没有严格格式要求，不会像代码那样因局部语法错误「牵一发而动全身」。工具 schema 的花括号、引号不匹配会导致整个 Agent 无法运行；Skill 的修改往往是局部的，少量错误不会让整个系统停摆。

## 4. 四个决策维度

一项能力该做成哪种形态，取决于四点：

- **安全与权限**：需要精细授权、审计留痕，或有不可逆风险的操作，用专用工具封装；其余优先通用。
- **参数复杂度**：嵌套对象、多字段联合校验、复杂类型约束，用结构化 schema；参数简单时 CLI 传参同样可靠。
- **变更频率**：频繁变化的能力用 Skill 维护，改一段文本远比改代码再测试部署轻松；稳定的底层操作更适合专用工具。
- **模型能力**：较强的模型可以用 Skill + 通用执行器表达更多能力、减少工具数量；较弱模型需要结构化 schema 引导调用。

## 5. 再往前一步：用代码编排工具

通用执行器还有一个常被忽视的好处：它让模型可以用代码**串联**多个工具，而不是一次调用一个、把每个中间结果都搬进上下文。

打个比方：传统方式像每做完一步都要写邮件汇报给领导，领导读完再回信告诉你下一步——这些「邮件」就是 token 消耗；代码编排像领导一次性写好完整操作手册，你照着做，只在全部完成后汇报最终结果。

具体来说，LLM 一次性生成一段脚本，中间变量留在代码执行环境，只有最终结果返回模型。例如抓取多个网页再批量提取字段：页面全文只存在于执行环境的变量中，返回上下文的只有汇总后的结构化结果，避免整页内容反复进出上下文，token 消耗可降低约两个数量级。

这属于「代码作为通用 Agent 元能力」的范式，后面会展开。

## 6. 补记

形态选择的核心不是「专用更准」或「通用更强」，而是**这条能力的成本结构**：常驻成本、参数复杂度、变更频率、权限要求。高频稳定的原子操作做成工具；低频复杂、经常改写的流程做成 Skill；两者都不合适时，才考虑拆分或整合。

一个常见误区是把「工具数量」当成能力数量。真正重要的是模型能否在需要时找到并正确使用那条能力——这既取决于形态，也取决于披露策略。
