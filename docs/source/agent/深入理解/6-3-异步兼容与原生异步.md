# 异步兼容与原生异步

## 1. 同步接口如何表达异步语义

如果模型或接口不支持原生异步，当工具尚未返回时用户突然打断，就需要在同步格式中表达异步语义。

假设 Agent 正在起草邮件（工具调用：搜索联系人），搜索没返回时用户说「等一下，先查明天天气」。如果接口要求未完成的工具调用先获得结果，Agent 就无法带着悬空调用处理新消息。

核心思想：**没有打断的常态下，让模型看到标准同步轨迹；只在打断时插入占位符修复格式。**

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-4.svg)

<p>图 1：异步 Agent 的打断与恢复</p>

五条关键规则：

1. **及时记录已完成的 assistant 消息与工具调用项**；服务端管理的 reasoning 状态按提供商协议保留，不自行拼接不可见思考文本。
2. **工具完成时才记录 tool result**。执行中轨迹处于「部分完成」状态。
3. **工具执行中的打断需要占位符**：为未完成的工具生成占位符响应（「工具正在后台执行，请优先处理新事件」），追加打断事件，重新调用 LLM。从模型视角看，assistant 消息仍有配对的 tool result。
4. **没有原生 steering 时，取消未完成生成**，保留已确认的消息与工具状态，追加新事件后重新请求。不能假定半截输出或隐藏推理可以作为合法前缀任意回灌。
5. **非打断事件进入队列等待批处理**，当前周期完成后一次性追加。

以起草邮件被打断为例：

1. Agent 调用 `search_contacts`，assistant 消息立即写入轨迹；
2. 搜索未返回，用户发来天气查询。系统为未完成调用生成占位符 tool result，再把天气查询追加轨迹，重新调用 LLM——此时轨迹格式合法；
3. 天气回复后，搜索真实结果到达，作为新事件追加，Agent 继续起草。

这套方案的作用是维持同步接口要求的工具配对关系。只有需要打断时才引入「未完成」占位符；后台真实结果到达后，再通过带来源与任务 ID 的事件送入轨迹。

占位符也带来语义风险：模型可能把「任务已启动」误当成「任务已完成」，在真实结果返回前作出依赖该结果的判断。应通过明确的任务状态与结果校验防止混淆，并在评估中检查是否编造了未到达的数据。

## 2. 用任务句柄表达异步

无论是否使用原生异步协议，都可以从工具接口设计层面明确异步语义。

传统工具设计隐含「调用即完成」：`phone_call` 暗示拨打电话并等待结束、返回通话记录。异步范式应把「启动」与「完成」解耦：

- `initiate_phone_call`：启动呼叫，立即返回任务 ID 与初始状态（「呼叫已发起，正在拨号」）；
- 进展通过事件通知：`phone_call_connected`、`phone_call_ended`。

关键在于工具名称与描述本身传达异步语义。模型看到 `initiate_phone_call` 会自然推断这是「发起」而非「完成」。描述进一步强化：

> 此工具将启动由子 Agent 处理的电话任务。成功发起后立即返回任务 ID，你可以继续处理其他事项。通话结束后会收到单独通知事件。

## 3. 原生异步：Async Tool Calling 与 Mid-turn Steering

另一条路线是让模型原生理解这种交互节奏：工具还在运行时，自己可以继续做别的事；用户中途补充要求时，可以据此调整后续工作。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-5.svg)

<p>图 2：同步接口兼容与模型原生异步</p>

**异步工具调用**把「发起行动」与「获得结果」分开。Agent 发起耗时查询后，可以继续推理、调用其他工具，或处理不依赖结果的部分。例如查询会议场地时，先整理议程与准备清单；场地信息返回后再比较方案。

关键是分清依赖关系：能独立推进的工作继续做，必须依据结果的决策留到结果到达之后。

**回合中途引导**让用户可以在任务进行中修正方向。Agent 还在思考或组织回答时，用户就可以追加「预算减少了」「参会人数变了」；系统保留已完成工作，把新约束带入后续处理。

这两种能力扩展的是交互时机：工具结果与用户要求都可以在任务推进过程中到达。系统仍要分清来源，记住哪些工作已完成、哪些还在等待。修改计划不等于停止正在运行的工具，更不会自动撤销已经发生的动作；执行、取消与状态管理仍由运行时负责。

## 4. 从「能接收」到「可靠处理」

原生异步解决了消息能否在运行中到达，复杂任务的可靠性还取决于模型如何使用这些消息。至少检查三件事：

1. **结果归属与未完成状态**：能否把延迟到达的结果归入正确任务，在结果缺席时避免编造数据？
2. **任务恢复与动作控制**：能否在处理新要求后继续原任务，并区分「修改计划」与「停止执行」？
3. **多条更新的综合使用**：能否同时遵守预算与人数等约束，而不是只记住最后一条？

可以通过异步环境中的训练改进模型，也可以通过清晰的任务状态、事件来源与执行反馈改进系统。

评估要覆盖两层：**模型是否理解了变化，系统是否按变化正确执行。** 一个会议选址任务可以这样对照：Agent 发起耗时查询后先做不依赖结果的准备；期间用户补充预算与人数；查询完成后根据全部约束选择场地。对比同步工具、原生异步工具与中途引导三种方式，观察等待是否阻塞其他工作、新要求是否进入后续计划、结果到达后能否继续原任务。

## 5. 补记

同步接口上的异步兼容，本质是**用占位符与队列模拟一个本不存在的时序**。它能让旧模型参与异步任务，但代价是额外的状态管理与语义风险——模型看到的「占位结果」不是真结果，必须靠任务 ID 与后续事件纠正。

原生异步省掉的正是这层模拟：模型自己知道「工具还在跑」，可以继续做别的事，也能在接受新要求后调整计划。但原生能力不替代运行时——工具取消、状态管理、结果归属仍需系统负责。
