# 奖励设计与蒸馏

## 1. 奖励从哪里来

### 1.1 可验证奖励（RLVR）

最可靠的来源是**可验证奖励**：用测试用例、数据库断言、状态差异或格式检查直接判断结果。

数学答案、代码测试、结构化工具调用都适合从二元结果奖励开始。规则越确定，奖励越便宜、越可复现，也越不容易被模型钻空子。

### 1.2 RLHF 与偏好

RLHF 只作为背景：人工比较回答 → 训练奖励模型 → 用 PPO 优化策略。

奖励模型只是偏好的代理，过度优化会导致 reward hacking，因此通常用 KL 正则把策略锚定在 SFT 参考模型附近。DPO 跳过显式奖励模型，直接从偏好对做离线优化。

### 1.3 模型评判（GRM）

目标难以完全规则化时，可以用模型评判。**生成式奖励模型**不只输出分数，还生成「哪里做得好、哪里需要改」的诊断；它既可作为奖励来源，也可把诊断转成蒸馏或偏好数据。

一类做法是让模型先归纳任务评价原则，再按原则评价轨迹，最后用可验证事实检查评价是否正确。反馈更透明，但仍需抽样人工校准，防止评判器形成新偏差。

要区分两个概念：

- **reward hacking**：钻规则或实现漏洞拿高分；
- **reward seeking**：模型先在心里建立「评判器会看什么」的模型，再按猜测调整行为。

后者不一定篡改测试，却可能在长程任务中自行设置一个过于简单的检查，刚好通过就提前结束，交付物只满足代理指标而没有满足真实意图。

所以「通过了 grader」不能自动等价于「任务完成了」：评判器是意图的代理，训练越强，模型越可能把代理当成目标本身。

## 2. 奖励什么时候给

### 2.1 结果奖励（ORM）

只在 episode 结束时判断任务是否完成，最简单，也给策略最大探索自由度。

当中间路径没有公认标准、最优解尚未被人类发现时，稀疏成功/失败奖励是合适起点——SimpleVLA-RL 就是如此。

稀疏反馈让模型难以判断多步轨迹中的具体错误，这也是 RL 样本效率受限的原因之一。

长程 coding 或 cowork 任务中，还应把「是否完成」交给模型写不了的隐藏测试、状态断言或外部终止钩子，而不能只依赖模型自称完成。

「过早结束」是具体例子：模型说完成时，Harness 在隔离工作区运行模型看不到的验收测试；通过才给正奖励，未通过给负奖励。测试必须读取真实文件或环境状态，不能只检查模型是否说了「已完成」，否则模型会学会口头承诺验证而不真验证。

评估还要分开两类集合：**任务未完成的边界集**观察过早结束率；**确实已完成的保留集**观察模型是否仍能正常收尾，避免训练成永远不敢结束。

### 2.2 过程奖励（PRM）

在中间步骤提供反馈，例如检查身份验证、工具参数、测试通过数或导航动作。逐步验证能缓解长时序信用分配，却可能把模型限制在设计者预设的路径上，标注与验证成本也更高。

V-IRL 采用逐步导航反馈，SimpleVLA-RL 保留终点奖励，两者构成「密集反馈换收敛速度、稀疏反馈换探索空间」的对照。

工程上可以先用结果奖励建立可靠基线，再只为真正可验证的中间事件加入过程信号。

多轮 LLM RL 通常把折扣因子设为 γ=1；PPO 的价值网络或 turn-level 优势负责把终点反馈归因到较早动作；GRPO 把轨迹级优势均摊到生成 token，长轨迹上要格外注意信号稀释。

## 3. 奖励表达多少信息

奖励的**密度**与**表示形式**是两件事：

- **标量**：只回答总体多好；
- **半标量**：先给简短理由再给分数；
- **向量**：按准确性、完整性、成本、安全等维度分别打分；
- **生成式**：给自然语言诊断，可多次采样后汇总。

选择原则：

- 有确定答案或测试：优先二元标量；
- 有多个相互独立的质量目标：用向量，或加权成标量；
- 开放式、难以穷举规则：用生成式诊断，但配合事实校验与人工抽检。

**不要为了「奖励更丰富」而堆叠不可验证的维度。** 每增加一个维度，就增加一种被策略钻空子的可能；先确认这个信号能在少量 rollout 中产生有意义的组内差异，再决定是否加入训练。

## 4. 路径约束：奖励结果，惩罚路径

结果奖励解决「事情有没有办成」，却表达不了「是否按规定办成」。

真实 Agent 可能通过改测试文件、跳过身份验证或执行破坏性命令获得表面成功。

**RLVP**（Reinforcement Learning with Verified Penalty）的原则是：**奖励结果，惩罚路径。** 它针对可机器判定、与最终成败无关的**结果中性约束**，不能替代对语义意图、交付完整性与早停行为的独立检查。

真实环境通常是**非对称验证器**：检测「做了一个坏动作」便宜而可靠，证明「这一步确实朝着目标取得了有意义的进展」却很难。

把总奖励写成：

\[
R=O+\beta\Phi
\]

O 是任务结果，Φ 是由确定性规则逐动作计算的路径信号。对可验证违规动作扣分，对可验证的合规动作或可达子目标给少量部分奖励；两路归一化后再合并，避免路径信号淹没主目标。它不改变 PPO/GRPO，只改变每一步看到的奖励。

```python
outcome = verify_final_state(trajectory)          # result, not self-report
path_signal = 0
for step in trajectory:
    path_signal += deterministic_path_signal(step)  # penalty or reachable progress
reward = normalize(outcome) + beta * normalize(path_signal)
```

RLVP 的关键不是「奖励越密越好」，而是能否恢复组内差异：

- 纯结果奖励在全败组和全胜组都零方差、没有梯度；
- 违规动作通常容易检测，惩罚几乎总能恢复差异；
- 进展奖励只有在部分进展可达时才有效。

设计四点：

1. **只惩罚具体动作**，不惩罚「不够努力」；
2. **结果奖励始终保留**，避免模型学会什么都不做；
3. **每个惩罚最好配一条可达的合规路径**；
4. **规则必须确定、难以钻空子**。

如果基础策略根本不会采样合规动作，应先用少量示范把路径「种」出来，待合规行为稳定后再减弱路径塑形。换句话说：**惩罚是通常可达的那一半，进展奖励是受可达性门控的那一半。**

一个实验在 GRPO 上加入 O 与 Φ：TerminalBench 违规次数由 3.71 降至 0.66，成功率基本持平；miniF2F 上部分奖励把达到 0.9 成功率所需迭代从 7.0 降至 4.4。软件修复中若所有 rollout 都无法通过任何测试，进展信号不可达，加入它不会带来收益。

这些数字来自可控代理环境，不能直接外推线上；更稳妥的结论是机制性的：只要路径信号能在同组 rollout 中区分行为，且规则不易被钻空子，它就能补上终点奖励看不见的信息。

## 5. 蒸馏：把一次 rollout 变成密集监督

RL 样本效率低，除了高方差与在轨数据难复用，更根本的原因是反馈太稀疏。

主流 model-free RL 通常只在 rollout 结束得到一个成败标量，中间的错误原因、缺少字段、流程提示都没有直接学习信号。客服说「需要信用卡后四位」，模型却只能从最终 0/1 反复试错，可能数百次交互才偶然学会；人类听一次就能记住。

**蒸馏把一次 rollout 变成密集监督**，不必探索更多环境轨迹，就能让同一条轨迹贡献大量梯度。

### 5.1 在轨蒸馏

| 方法 | 轨迹由谁采样 | 每条轨迹的主要监督 |
|---|---|---|
| SFT / 离轨蒸馏 | 人类或教师 | 标注答案的逐 token 监督，密集 |
| On-policy RL | 当前学生 | 结果/过程奖励，通常稀疏 |
| On-policy Distillation | 当前学生 | 教师在学生前缀上的逐 token 分布，密集 |

SFT 监督密集，却主要覆盖教师会走到的状态。学生部署后若在早期犯了教师不会犯的错误，就进入训练数据没覆盖的前缀，后续每一步都在陌生状态预测，误差沿长序列累积。

On-policy RL 直接在学生状态分布上训练，相关性高，却常在轨迹结束才得到一个成败信号。

On-policy Distillation 把两者结合：**学生决定走到哪里，教师负责在学生已经走到的位置告诉它下一步的完整概率分布。**

一条长度 T 的 rollout 不再只产生一个 0/1，而能产生约 T 组逐 token 监督。它比离轨 SFT 更贴近学生实际会犯的错，比纯 RL 反馈更密集、方差更低；教师推理增加的是计算，不需要再采一批环境轨迹。

它同样不是「从零创造能力」：学生至少要能进入教师可纠正的有效状态，教师策略也不能离学生有效支持太远。若基模连目标语言、领域概念或基本动作都没有，仍应先 Mid-training 或离轨示范冷启动。

做法是让学生预测分布贴近教师分布，通常最小化 KL。例如学生生成「先查询 API，再解析返回值」，教师可以在「查询」这个 token 位置给出「查询」80%、「调用」15%、其余 5% 的分布。相比二元奖励，逐 token 对齐提供密集得多、方差更低的信号；代价是教师推理成本，因此在环境交互昂贵时尤其划算。

```python
student_trajectory = rollout(student, task)
loss = 0
for state in student_trajectory:
    teacher_logits = teacher(state)
    loss += KL(student_logits(state), teacher_logits)
update_student(loss)
```

数学等任务上，达到同等性能所需训练步数约为纯 RL 的 1/10。多轮 Agent 中成败信号更晚更稀疏，逐 token 教师分布能直接指导中间决策；但前提是仿真环境足够真实，让学生探索到的状态接近部署分布。

一个纯 Agent 场景的验证：在「时间感」任务上比较 DPO、四种 RL 与 On-Policy Distillation；前者分别受稀疏奖励、目标错位、rollout 形状不匹配与策略崩溃限制；换成冻结的 32B 教师，在学生自己的多轮轨迹上逐 token 对齐后，训练平滑收敛，四种条件下通过率比同源 SFT 基线高 23–47 个百分点。

这说明瓶颈往往不是奖励函数不够复杂，而是每次交互提供的信号不够密。

### 5.2 没有更强教师：在轨自蒸馏

On-Policy Distillation 的威力来自教师，也因此有硬前提：必须有一个明显强于学生的教师。

如果你要训练垂直领域模型，现有模型能力都不足，就没有教师可用。

破题思路是 **On-Policy Self-Distillation**：同一个模型分饰教师与学生，但看到的上下文不同。

教师版能看到**特权信息**——标准答案或已验证的正确解答；学生版只看到问题，却在自己采样的轨迹上向教师版的逐 token 分布对齐。

对着答案解释学生刚走过的路径，通常比独立探索更容易，因此一条 rollout 仍能产生密集监督。

```python
student_trajectory = rollout(model, task_without_answer)
loss = 0
for state in student_trajectory:
    privileged_state = add_verified_answer(state)
    teacher_logits = stop_gradient(model(privileged_state))
    loss += KL(model(state), teacher_logits)
update(model, loss + retention_regularizer)
```

`privileged_state` 只能在训练侧构造，不能泄露给部署时的 Agent；`retention_regularizer` 代表保留集/风格约束。

训练流程还必须检查数据权限、答案遮蔽与遗忘风险。

相比 RLVR，OPSD 不要求奖励一定能自动验证：特权信息可以是标准答案、人工示范或领域文档。它用这些信息替代更强的外部教师，同时保留「在轨采样 + 逐 token 监督」的样本效率优势。

但它不会凭空创造知识——如果模型拿着答案也讲不清过程，自蒸馏就没有额外信号；朴素 OPSD 还可能丢失原有思考风格，需要额外正则稳定。

## 6. 补记

奖励设计的核心不是「设计一个多聪明的分数」，而是**让信号在组内产生差异，且难以被钻空子**。全零或全一的奖励，再复杂也没有梯度；可被改测试绕过的奖励，越优化越危险。

蒸馏的启发是：**样本效率的瓶颈常常是反馈密度，而不是算法**。同一条学生轨迹，教师能给出 T 个 token 级监督，RL 只给一个成败标量；在环境交互昂贵时，这个差别比算法选择更重要。
