# 编排模式与护栏

## 1. 从简单到复杂

编排模式决定上下文如何在 LLM 调用之间流动、工具如何被调度，以及执行路径是预先设定还是动态生成。落地时遵循一个顺序：

1. 先考虑**单次 LLM 调用**。优化提示词与上下文示例就能解决，就不要引入 Agent；
2. 需要多步骤、且能清晰分解为固定子任务时，用**工作流**；
3. 只有需要动态决策与灵活执行路径时，才用**自主 Agent**。

Agent 系统通常用延迟与成本换取任务性能，要谨慎权衡这种交换是否值得。

一个常见的反面例子，是一开始就构建复杂工作流或多 Agent 系统。为「从百万条聊天记录中提炼个人记忆」设计流水线：切分对话、提取、证据核验、身份解析、记忆整理、合并复核，再建事实图、覆盖账本与版本。每个部件单看都有道理，组合起来却低效、不可靠。复杂工作流的执行拓扑是固定的，遇到新例外就继续加节点，架构越来越复杂，通用性却越来越差；模型原本可以根据上下文做的语义判断，反而被工作流写死了。

**Harness 很重要，不等于 Harness 越复杂越好。** 先给能力足够的 Agent 清晰目标、必要上下文与可组合工具，用自然语言告诉它如何查证、比较、处理冲突；程序只固化权限、不得覆盖原始材料、原子发布等必须始终成立的边界。只有业务约束本身要求，或评估反复暴露某类稳定失败时，才把对应步骤升级为专门验证器、独立 Agent 或确定性流程。

## 2. 工作流：确定性编排

**工作流**通过预定义代码路径编排 LLM 与工具，执行路径由开发者设计，LLM 只在节点内部负责理解与生成。

以订机票为例，可设计四个固定节点：核实身份 → 搜索航班 → 完成付款 → 确认预订。每个节点内部可以用 LLM 理解需求，但节点顺序是代码固定的：不会在付款前预订，也不会在身份核实前搜索。

两个优势：

- **严格流程控制**：关键步骤不被跳过或乱序，「付款前不能预订」这类规则由代码强制，不依赖模型判断；
- **安全性**：路径确定，提示注入或模型犯错最多影响当前节点，无法跳到不该执行的分支。

局限是**缺乏变通**：预设流程未覆盖的情况（付款时改签、航班取消）只能走异常分支或交还人类。

最简单的例子是文生图：用户说一句大白话，文生图模型只接受特定风格的英文标签。工作流安排两个节点——LLM 把需求改写成提示词，模型再出图。这里的 LLM 做的是**翻译**，它存在的原因是工具听不懂人话。这种给工具能力短板打补丁的 Harness 代码，可以称为**适配层**。

但如果换成具备原生图像生成能力的多模态模型，就不再需要提示词改写。**Harness 里给模型短板打补丁的部分，会随着模型变强被模型自己内化。**

## 3. 自主 Agent：动态决策

当固定路径无法满足需求时，需要**自主 Agent**：执行路径不是预先定义的，而是根据环境反馈实时决定。

仍以订票为例：用户说「帮我订下周三去上海的机票」，Agent 自行决定先搜索，发现需要登录，于是先核实身份；发现最便宜的航班需要转机，主动询问；用户说不要转机，再调整条件。

自主 Agent 需要自主规划、识别失败、调整策略。但自主性不等于无限制：必须设计明确的**停止条件**——任务完成、达到最大迭代次数、或遭遇不可恢复错误，否则容易陷入死循环或过度执行。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig1-6.svg)

<p>图 1：自主 Agent 的执行循环</p>

从实现看，自主 Agent 就是在一个循环中使用工具的 LLM，通过持续获取环境反馈推进任务，也就是 ReAct 循环。常见退出条件：调用最终输出工具、模型返回没有任何工具调用的响应、遇到错误、达到最大轮数。

它适合开放式问题——难以预测所需步骤数量。典型场景包括 Coding Agent 修复真实 Issue、Computer Use 操作界面、需要迭代搜索与分析的研究任务。代价是更高成本与复合错误风险，因此要在沙盒中充分测试，设置护栏与监控，并在关键决策点加入人机协作检查点。

## 4. 混合与框架

工作流与自主 Agent 并非非此即彼。很多系统混合使用：关键、有严格合规要求的流程用工作流保证可靠，需要灵活决策的部分切到自主模式。n8n 这类工作流自动化框架，就允许在同一系统中同时使用工作流节点与自主 Agent 节点。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig1-7.svg)

<p>图 2：n8n 工作流编辑器</p>

另一种混合方式是**先由自主 Agent 把工作流写出来，再由工作流执行**：Agent 读完任务后自行决定拓扑并生成编排代码；代码一旦生成，执行阶段退回确定性。这样既保留面对未知任务的灵活性，又不必让模型在每一次调度上参与决策。

主流框架可以按定位粗略区分：

| 框架/平台 | 核心定位 | 编排模式 | 适用场景 |
|---|---|---|---|
| Codex Harness | Codex 的开源 Agent 运行时 | 自主 | Coding Agent、嵌入自有产品 |
| Claude Agent SDK | 生产级 Agent 开发框架 | 自主 | 复杂自主任务、Coding Agent |
| LangChain / LangGraph | 通用 LLM 应用框架 | 工作流 + 自主 | 复杂链式思考、多步骤工作流 |
| n8n | 可视化工作流自动化 | 工作流 + 自主 | 业务自动化、非技术团队 |
| Dify | LLM 应用开发平台 | 工作流 + 对话式 | 企业级 RAG、知识库 |
| CrewAI | 角色化多 Agent 编排 | Multi-Agent | 团队式任务分解 |
| OpenClaw | 开源全能个人 Agent | 自主 + 事件驱动 | 个人助理、Deep Research |
| DeepSeek Harness | Agent 自进化框架 | 一切皆插件 | Agent 开发者、研究者 |
| Pi | 极简 Coding Agent 框架 | 自主 | Agent 开发者 |

框架发展很快，学会某个具体框架的用法并不重要。选型的关键不是框架复杂度，而是它能否用尽可能少的抽象层让你专注业务逻辑。

## 5. 护栏：按被绕过的难度分层

编排解决「怎么做事」，护栏解决「如何安全地做事」。单个护栏很难提供足够保护，多个专门护栏组合，才能构建有韧性的系统。

按防护位置分三层。这三层不是按请求处理顺序排，而是按**被绕过的难度**排：越靠下越不依赖模型自己的判断，因此越难被一次成功攻击穿透。

### 5.1 上下文层

管模型能看到什么，在内容进入上下文之前拦截：

- **相关性分类器**：标记偏离主题的查询；
- **安全分类器**：检测越狱与提示注入。越狱是用户自己绕过限制；提示注入是攻击者通过外部数据间接操纵模型；
- **内容审核**：标记暴力、歧视等有害输入；
- **规则保护**：黑名单、长度限制、正则，防范已知威胁；
- **来源标注与指令/数据分离**：让模型知道哪些内容有权指挥自己。

这一层有结构性上限：**处在同一个上下文里的 Agent，很难判断自己是否已经被注入**。它只能降低攻击成功率，给不出保证——这正是需要下面两层的原因。

### 5.2 执行层

管模型能做什么，在动作生效之前验证。核心是**工具风险评级**：按操作是否可逆、权限等级、财务影响标注低/中/高，高风险操作需额外审查或人工确认。

关键在于复核必须由**上下文之外**的机制完成——独立审查进程、最小权限凭证、沙盒隔离、人在回路；否则它会和被注入的 Agent 一起沦陷。

返回给用户的回复本身也是一次动作，因此**输出检查**同样属于这一层：PII 过滤器审查个人身份信息，输出验证确保内容与品牌规范一致。

### 5.3 数据层

管世界最终能被改成什么样：数据库行级安全策略、约束与校验器、受控视图与存储过程、由受信任运行时绑定且无法伪造的访问上下文。

这一层的价值在于不依赖上面两层是否正确——即使提示注入得手、生成的代码漏写权限判断，越权操作仍会在数据层被拒绝。

### 5.4 人工干预

人工干预让 Agent 在无法完成任务时平稳移交控制权。客服场景升级到人工客服，Coding Agent 交还开发者。两类触发条件：

- **超过失败阈值**：重试或操作次数达到上限；
- **高风险操作**：敏感、不可逆、财务影响大的动作，至少在团队建立足够信心之前。

护栏还有另一类失败：**误拒绝**。为了降低危险请求被放行，模型可能同时拒绝合法但形式敏感的任务，例如经过授权的安全测试。因此护栏评估不能只测「应拒绝的是否被拦截」，还要测「明确允许的是否能正常完成」。

## 6. 五个贯穿全书的设计模式

这些模式会在不同章节反复出现，先在同一个地方命名：

- **提议者—审核者**：产出与评判由两个不共享上下文的角色承担，评判方看产物本身（渲染结果、测试输出、结构化参数），而不是产出方的推理过程。前提是**自审不可靠**：同一个上下文里的模型难以发现自己的盲区，也难以判断自己是否被注入。
- **渐进式披露**：不一次性把全部信息放进上下文，先给可检索目录，再按需加载细节。它同时优化上下文预算与选择精度。
- **只增不改**：状态以追加方式演进，已写下的内容不回头修改。换来可缓存、可重放、可审计。改动越靠前，作废的缓存越多。
- **边界集 + 保留集**：任何修改都要同时在「应当改变的样本」与「不应当影响的样本」上验证。只测前者会把过拟合当进步，只测后者会把无效修改当安全。
- **最小 diff + 可回滚**：每次修改尽量小、带来源、可单独回滚。它让归因成为可能——出了问题能定位到具体哪次改动。

## 7. 补记

编排模式没有通用最优解，只有与任务匹配的选择。判断时可以看两个信号：执行路径是否可预先枚举；失败代价是否高到必须由代码强制顺序。前者倾向工作流，后者倾向「工作流 + 人工审批」，只有路径确实无法预测时才交给自主 Agent。

护栏的关键不是数量，而是**分层独立性**：上下文层、执行层、数据层各自能独立拦住一类风险。只堆上下文层规则，遇到提示注入就容易被一锅端；只靠模型「谨慎操作」的提示，更不是安全边界。
