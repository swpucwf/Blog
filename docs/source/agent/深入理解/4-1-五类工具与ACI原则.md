# 五类工具与 ACI 原则

## 1. 工具是 Agent 的手脚

《Her》里的 Samantha 能整理邮件、识别情感复杂的信件并提议润色，能代表主角处理出版事宜，还能在不同渠道间无缝切换。她的智能之所以动人，是因为拥有强大的**工具**——连接语言「大脑」与真实数字世界的「手脚和感官」。

今天的通用 Agent 已经基本实现了这些能力。理解它们，先看工具的分类。

## 2. 五类工具

从两个特征审视：**调用方向**（这次交互由谁发起）与**作用对象**（作用在什么上）。两者不构成严格的交叉分类，只是帮助把握定位。

| 工具类型 | 调用方向 | 作用对象 |
|---|---|---|
| 感知工具 | Agent 主动调用 | 获取信息 |
| 执行工具 | Agent 主动调用 | 改变世界 |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent 或人类 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 |

**感知工具**：搜索、知识库检索、网页阅读、文件搜索与读取。设计关键是控制输出信息量，防止上下文爆炸。

**执行工具**：命令行、代码解释器、写文件、编辑文件、发邮件。错误代价可能极高，安全约束是核心。

**协作工具**：创建子 Agent、发消息、取消、发现可用 Agent。最简单的动机是并行执行不相关任务，更复杂的是用不同模型、工具、提示词与上下文执行不同任务。

**用户沟通工具**：回复消息、发送结构化卡片、通知提醒。当沟通从单会话问答扩展到多渠道异步消息，「说话」本身也需要成为显式工具调用。

**事件触发工具**：设置定时器、监控后台任务、连接事件源。它涉及两个时刻——**注册**时 Agent 主动声明关心什么事件，**触发**时外部事件异步回调唤醒 Agent。没有它，Agent 只能在用户发起对话时被动响应。

后两类与事件驱动的异步运行时密不可分，放到交互章节讨论。

## 3. ACI：为 Agent 设计接口

工具设计的早期形态是直接封装 API——把每个端点包成一个工具，粒度过细，Agent 往往要协调好几个工具才能完成一个目标。

更成熟的思路是 **ACI**（Agent-Computer Interface）：工具应该对应 Agent 的**目标**，而不是底层 API 操作。ACI 对标 HCI（人机交互界面）——HCI 研究人如何与计算机交互，ACI 研究 Agent 如何与计算机交互，核心是让工具对 Agent 而非对人友好。

三条原则：能力用什么形式表达、工具怎么描述、参数如何忠实传递。

## 4. 工具描述的艺术

工具描述的质量直接决定使用准确性。核心是让模型知道**什么时候用**，而不只是「能做什么」。

以网络搜索为例，「搜索相关内容」远不如「当需要获取实时信息或查找未知事实时使用」——前者描述功能，后者帮助模型做调用决策。

**边界往往比能力更重要。** 文件搜索工具应明确说明它只能按文件名匹配，不能搜索内容。大多数调用失败的根因不是模型不知道工具能做什么，而是不知道它不能做什么。

参数描述用具体例子代替抽象规范：

- 「`timestamp`：RFC3339 格式，例如 `2024-03-15T14:30:00Z`」优于「RFC3339 格式」；
- 「`phone`：E.164 格式（国家代码 + 号码，无空格），例如 `+8613888888888`」优于「使用 E.164 格式」。

模型在执行复杂任务时只能分出一小部分注意力确认参数格式，具体例子让它直接套用，不需要额外思考。

返回值也要描述清楚：「返回 JSON 数组，每个元素包含 `title`、`url`、`snippet`」。对耗时长的工具注明代价，帮助模型规划调用顺序，例如「需要下载完整网页，大型网站可能 5–10 秒；只需要元信息时请用 `get_page_metadata`」。

更进一步是为每个工具附 1–5 个真实调用示例。JSON Schema 只能描述参数类型，无法表达时间戳是秒还是毫秒、过滤条件如何嵌套等隐式约定。加入示例后，调用准确率往往明显提升——一些基准上从约 72% 提升到 90%。

一条实用的调试原则：**当 Agent 频繁选错工具时，优先检查工具描述，而不是怀疑模型能力。** 修正描述的投入产出比通常远高于换一个更强的模型。

## 5. 参数传递的保真性

比功能缺失更隐蔽的反模式是**静默输入转换**——工具在执行前悄悄「修正」模型参数，导致实际操作偏离模型意图。

某编辑工具接受 `old_string` 与 `new_string` 做精确替换，但参数层把中文弯引号静默转换成英文直引号。模型读取文件时看到弯引号（读取工具原样返回），于是原样传入替换工具，但参数层已改成直引号，与文件内容不匹配，工具返回「未找到匹配」。模型反复尝试、反复失败——它无法理解为什么工具找不到自己明明看到的内容。

写入方向同样：模型本意写入弯引号，参数层却替换成直引号；模型再读取验证，看到的又是直引号，陷入困惑。

另一种保真性违规是**静默参数注入**——工具在模型不知情时追加参数。例如对 `git commit` 自动附加一个「由 AI 生成」的标记；如果用户 Git 版本不支持该参数，提交就会报错。模型反复调整提交信息、尝试不同参数组合，无论怎么改都失败。

原则很清楚：**模型感知到的世界与工具操作的世界之间，不能存在系统性偏差。** 如果确实需要规范化（如统一编码），必须在描述中说明，并在返回中明确告知。工具的「智能修正」如果模型无法诊断，就不是帮忙，而是制造故障。

## 6. 补记

工具设计的第一问不是「怎么实现」，而是「它对应 Agent 的哪个目标」。按 API 端点切工具，会让模型承担本应由设计者承担的编排成本；按目标切工具，模型只需表达意图。

第二问是「模型需要知道什么才能用对」。描述的重点不是功能清单，而是触发条件、边界、参数示例与返回结构。很多所谓「模型不会用工具」，实际是描述没写清。
