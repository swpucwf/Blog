# Computer Use 与机器人

## 1. 屏幕上的感知-思考-行动

语音把时机压到毫秒级，但观察仍是一维声音流。Computer Use 把同一个问题搬上二维屏幕：观察是持续变化的像素，动作是坐标上的点击与输入。它强调「下一步点哪里」，以及一个语音中不存在的追问——动作执行后，现实是否还与计划一致。

Computer Use（GUI 自动化 Agent）让 AI 像人一样观察屏幕、操作鼠标键盘使用软件。核心是一个循环：

1. Agent 截取当前屏幕；
2. 多模态模型接收截图与任务指令，输出思考与动作；
3. 执行层在真实环境执行动作（移动、点击、输入）；
4. 等待界面响应，再次截图，进入下一轮。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-11.svg)

<p>图 1：Computer Use 的感知-思考-行动循环</p>

要区分「看懂界面」与「完成任务」。前者接近多模态理解，可以用一次截图问答测量；后者要求把理解与动作放进闭环，处理加载、状态变化、误操作与不可逆后果。难点不只是答对截图，而是每一步之后重新确认现实是否仍符合计划。

三个关键设计维度：**动作空间**、**视觉定位**、**模型架构**。

## 2. 动作空间

一个清晰的动作空间设计包含三类工具：

**GUI 操作**：鼠标移动、左/右/中键点击、双击/三击、拖拽、按下/松开；四向滚动；逐字输入（模拟 12ms 间隔）、组合键、长按；截图、获取光标位置、等待。

**命令执行**：持久 Bash 会话，120 秒超时，通过哨兵字符串检测命令结束，多次调用之间保持环境状态（`cd` 后下次仍在该目录）。

**文件编辑**：通过字符串匹配安全编辑，支持查看、创建、替换、插入、撤销，比整文件覆盖更精确。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-12.svg)

<p>图 2：Computer Use 动作空间</p>

这不是某家厂商的私有协议：只要 Harness 能把截图、动作约束与执行结果转换成目标模型支持的消息与结构化输出，Claude、开放视觉模型与自托管端点都可以驱动同一个循环。

## 3. 视觉定位

每一轮，模型都要在截图中找到目标元素——搜索框在哪、提交按钮坐标是什么。当前有三条路线。

### 3.1 Set-of-Mark：把定位变成选择题

用图像分割模型在截图上切出候选区域，为每个区域叠加编号，模型看到的是一张带编号的图，只需报出编号，由系统换算成中心坐标。

这是**纯视觉**方法，不需要 DOM 或界面内部结构，原生桌面软件、游戏界面同样适用——只要分割模型能切出候选区域。

### 3.2 结构化元素索引

当界面能提供结构化信息时，标注可以更精确。现代网页在渲染前就有 DOM 树与语义角色，无障碍树为许多桌面应用提供类似信息。

以 browser-use 为代表的 Web Agent 会从 DOM 枚举可交互元素并编号，流程四步：

1. 通过浏览器调试协议获取 DOM 与无障碍信息；
2. 自动检测可交互元素（按钮、输入框、链接）；
3. 为每个元素标注唯一 ID，并在截图上绘制边界框；
4. 生成文本列表描述每个 ID 对应的元素。

```text
Screenshot: [关键元素标注了 [1]、[2]、[3]...]

Elements:
[1] <input type="text" placeholder="Search" aria-label="Search" />
[2] <button id="submit-btn" aria-label="Submit form" />
[3] <input type="text" placeholder="Enter your name" />
[4] <a href="/docs" aria-label="Documentation" />
```

模型只输出 ID，系统用元素中心坐标点击。这类方案不省 token（标注信息都要发给模型），但定位准确稳定，免去分割模型的漏检误检。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-13.svg)

<p>图 3：Set-of-Mark 与结构化元素索引</p>

### 3.3 纯坐标预测

不做标注，直接让模型输出坐标。以 SeeClick 与 Claude Computer Use 为代表：在海量 GUI 截图与元素位置配对数据上训练，让模型把「点击提交按钮」直接映射到坐标。

坐标预测对分辨率高度敏感。Claude 训练使用 XGA（1024×768）、WXGA（1280×800）、FWXGA（1366×768），输入分辨率不匹配时坐标会系统性偏移。因此工具层要做双向缩放，并**按宽高比选目标分辨率**，避免非等比拉伸。

例如真实屏幕 2560×1440（16:9），应选 FWXGA（1366×768）而非 4:3 的 1024×768。截图缩放到 1366×768 送入模型；模型输出 (683, 384)，反向映射为 (683×2560/1366, 384×1440/768) ≈ (1280, 720)。硬把 16:9 压进 4:3，画面会横向压扁，坐标随之偏移。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig6-14.svg)

<p>图 4：分辨率匹配与双向坐标缩放</p>

选择逻辑：**结构化信息可得时，优先 DOM/无障碍树索引**，最精确稳定；不可得时（原生桌面、Canvas/WebGL、游戏），用视觉标注或坐标预测——前者把定位变成选择题，对通用模型更友好；后者省去标注，对做过 GUI 定位训练的模型更直接。两者在小元素、密集界面上都仍有差距。

## 4. 能看动画、能听声音的观察接口

前面的感知都假设**屏幕是静止的**：截一张图、想一步、点一下，再截下一张。现实屏幕会放视频、弹通知、播放会议人声。一个每 3–5 秒才睁一次眼、且没有耳朵的 Agent，对这些「两帧之间发生的事」既看不见也听不到。

这里该重新设计的不是动作接口，而是**观察接口**：把连续环境观察转换成模型便于处理的离散事件。

- **屏幕关键帧截图**：用小模型判断屏幕是否发生有意义变化，只在显著变化时截图；变化频繁时每秒 1 次已有不错效果。
- **音量门控的语音转写**：有声音时调用语音识别，把文字放入上下文，让 Agent 能「听到」。
- **用文字描述画面**：把截图描述成一句话；即使原图之后被清理出上下文，这句文字仍在，实现多模态交互历史压缩。

## 5. 世界模型：动作前预测后果

观察接口解决「屏幕中间发生了什么」，但不消除规划延迟。Agent 仍是串行的「截图—思考—点击」，每步都重新观察、思考。效率研究显示，即使任务成功，Agent 的操作步骤仍明显多于人类，等待更久；**准确率达到人类水平，不等于足够实用**。

人类操作电脑时不是点击之后才想下一步，而是先预测动作后果：实际变化与预期一致，就沿计划继续；发现偏离，才停下重新规划。

世界模型让 Agent 在行动前预测桌面可能变成什么：

```text
桌面状态 + click/type/scroll/wait → 下一状态的表示
```

桌面状态不只是像素图，还包括窗口、焦点、滚动位置、输入框内容、加载状态、权限、网络返回。可用于 Computer Use 的世界模型至少要能编码当前状态、预测候选动作造成的状态变化，并把预测交给规划器。

例如「在 VS Code 新建 Python 文件并写入 hello world」，可以先预测文件树与编辑器在成功后的关键状态，再选择点击、输入、保存；删除文件则可以先在隔离虚拟桌面预测是否出现不可逆确认框，必要时请求用户确认。

重点不是生成逼真的未来截图，而是预测完成任务所需的、可检查的状态差异。

## 6. 移动端：生态壁垒比技术更难

移动端与桌面确有技术差异：动作空间不是「鼠标坐标 + 键盘」，而是接入无障碍服务 API 读取界面元素、下发点击与输入；交互从鼠标指针变成触摸手势，同一个 `(x, y)` 是单击、长按还是滑动起点，需要额外手势类型界定。

但真正卡住移动端的往往是**生态壁垒**。有厂商尝试在消费级手机集成 AI 助手，自动操作微信、淘宝、支付宝，很快遭遇平台限制。

根本原因是商业模式冲突。传统互联网应用的核心变现逻辑是**流量与注意力**：用户刷信息流看广告、搜索时跟随推荐、浏览时冲动消费。Agent 代替用户操作时，这条链路被绕过：AI 不看广告、不冲动消费，直奔目标完成就走。对靠广告与流量变现的平台，Agent 的每次操作都在侵蚀商业模式。

因此 Computer Use 面对的不只是 CAPTCHA 等技术对抗，更是结构性利益冲突——短期内难以调和。

## 7. 机器人：把闭环推进物理世界

机器人操作比「看图回答问题」难得多：不但要看懂画面，还要在真实世界连续动作，每个动作都会改变下一刻的情况。

XLeRobot 让这种区别很具体：同一台机械臂既可以由人遥操作，也可以把摄像头观察与受约束的动作工具交给 Agent 自主调用。硬件与任务不变，改变的只是操作者。

一个能用的机器人系统至少要回答四个问题：

1. 人想完成什么任务？
2. 接下来先做哪个子任务？
3. 当前技能具体输出哪些动作？
4. 动作执行后，现实是否仍符合计划？

### 7.1 硬件与算法的分工

一个关键事实：几百美元成本的机械臂，通过遥操作已经能完成连续多步桌面任务——人看着摄像头，抓起红杯放进托盘，再把黄纸放进垃圾盒，最后确认状态。

这是明确的诊断证据：**对这类任务，硬件不是瓶颈，算法才是。** 保持摄像头、机械臂、夹爪、桌面布置与成功条件不变，让人接管闭环；人类会持续修正定位、动作选择、时机，并处理抓取失败。自主系统与人的差距，正体现在这些闭环能力上。

当然，这个判断只限该桌面任务：它说明硬件跨过了该任务的负载、精度与工作空间门槛，不意味着几百美元机械臂能胜任所有开放环境。

### 7.2 控制的基本结构

机器人系统通常按时间尺度分层：

| 层级 | 核心问题 | 输出 | 时间尺度 |
|---|---|---|---|
| 任务目标 | 人想完成什么 | 「把杯子和废纸归位」 | 分钟 |
| 长程规划 | 先做什么后做什么 | 先杯子，再废纸，最后检查 | 秒—分钟 |
| 基本技能 | 当前要完成哪个状态变化 | `pick(red_cup)`、`place(...)` | 1–3 秒 |
| VLA/技能策略 | 这个技能具体怎么动 | 一小段动作或连续轨迹 | 1–10 Hz |
| 底层控制与安全 | 如何稳定及时执行 | 关节控制量、限速、急停 | 50–1000 Hz |

这是一种常见工程分工，不是唯一架构。关键是**把「任务顺序」与「眼前动作」分开**：否则高层推理延迟会拖慢底层控制，底层高频控制又会让高层处理大量无关细节。

对 XLeRobot，模型不应直接输出任意关节角；它只选择 `pick`、`place`、`verify_state`、`stop` 等有边界的技能，经过标定、限速、带超时的执行器变成真实动作。

### 7.3 长程规划与任务分解

用户说「把桌面整理干净」，不能直接交给动作模型。规划器要先列出物体与目标，再决定顺序，并为每步写清开始条件、完成条件与风险限制：

```text
处理红色杯子 → 清理黄色纸张 → 检查桌面
```

「处理红色杯子」继续拆成：

```text
pick(red_cup) → place(red_cup, tray) → verify_state()
```

每完成一个技能，就得到一个可检查的节点。抓取失败只重试当前步；物体被挪动或用户改变目标，只重规划受影响的后续步骤。

给 Agent 的工具也应足够简单：一次调用只做一件事，动作范围固定，有超时，执行后立即重新观察。

### 7.4 VLA 控制

VLA（Vision-Language-Action）接收当前画面与技能指令，输出机器人接下来要执行的动作：

```text
当前观察 + 技能指令 → 动作
```

高层规划器只提交 `pick(red_cup)`；VLA 或技能策略根据画面决定从哪个方向接近、夹爪何时闭合、手臂以什么轨迹抬起。执行后重新拍摄桌面；确认杯子被夹住，规划器才允许提交 `place`。

因此，**工具调用定义期望的状态变化，VLA 定义如何通过连续动作实现这个变化。**

RT-2、OpenVLA 把连续动作切成离散 token，像生成文字一样逐个输出；π₀ 直接生成连续平滑轨迹。两者没有简单高下：离散 token 更容易与语言模型结合，连续轨迹更适合平滑运动。

大模型每秒通常只能推理 1–10 次，传统控制器要更新几十到上千次。工程上常用**动作分块**：模型一次生成一小段未来动作，控制线程高频回放，模型在后台准备下一段。

代价是动作段越长，运动越平滑，模型在这段时间看到的新画面越少；杯子在执行中被碰动，机械臂可能仍在执行根据旧画面生成的动作。动作分块是在平滑性与反应速度之间取舍。

### 7.5 VLA 的局限

- **训练数据有限**：机器人演示远少于互联网文本图像。模型见过「杯子」这个词，不代表见过各种材质与摩擦条件下的杯子。
- **只学会模仿，不一定懂后果**：行为克隆学习「示范者下一步怎么做」，没有明确要求回答「这个动作造成什么结果」。
- **机器人各不相同**：自由度、坐标系、夹爪、执行器延迟不同，同一动作不一定能迁移。
- **观察可能过时**：动作块开始执行后，物体可能被移动、遮挡或碰倒。

语言模型知道「杯子」是什么，不代表知道摩擦、接触、液体晃动会怎样改变未来状态。VLA 回答「现在应该做什么」，还需要另一类模型判断「做了之后可能发生什么」。

### 7.6 世界模型与仿真迁移

机器人世界模型是「动作结果预测器」：

```text
当前状态 + 候选动作
  → 预测下一状态或未来片段
  → 比较候选结果
  → 选择动作、重新规划或安全停止
```

它至少要做好三件事：看懂当前状态；预测不同动作的结果；把预测交给规划器或控制器。

只会描述视频的 VLM、只会生成画面的模型，不会自动变成可靠的机器人世界模型。它还必须知道动作是什么，并能预测动作对物体与环境的影响。

三种用法：

1. **动手前**：比较抓取、推动、等待等候选，优先选风险更小的；
2. **执行时**：真实观察与预测对照，偏差大就缩短动作、停止或重规划；
3. **训练时**：用视频、仿真与失败轨迹学习状态变化，减少真机试错。

回到桌面任务：黄纸被红杯部分遮住，系统可以比较「先抓纸」「先移动杯子」「换抓取方向」；世界模型不必生成逼真视频，只要能预测哪些动作更可能让纸可抓、哪些可能碰倒杯子，就能帮助排序。

动作执行后，真实观察仍是最终事实；预测只能帮助选择，不能代替验收。预测越远误差越大，一段逼真的未来画面也可能不符合真实摩擦规律。实际系统仍需短期预测、实时观察、不确定性估计与独立硬件安全控制器。

从仿真到真机，还要处理两个环境的差异：训练可用遥操作、视频或仿真数据；部署时同一个杯子、纸张、托盘会出现在不同背景、光照、相机位置与遮挡中，机械臂还会遇到不同摩擦、传感器噪声与执行器延迟。

实验上可以训练四组结构相同的视觉策略：固定画面、改变背景、改变物体外观、同时改变背景/外观/光照/噪声；在原始环境与变化环境分别测试动作判断准确率。它回答的不是「模拟器等于真机」，而是一个更窄的问题：**主动扩大训练画面的变化范围，是否有助于同一任务适应新的摄像头画面。** 即使改善，真机部署仍需相机标定、执行器测试与完整安全闭环。

## 8. 补记

Computer Use 与机器人共享同一条闭环，但瓶颈不同：

- 屏幕场景的瓶颈是**定位与状态确认**——元素在哪、点击后是否真的变了；
- 物理场景的瓶颈是**后果预测与安全**——动作是否可逆、环境是否被扰动。

两者都说明：**动作空间越大，越需要独立的观察与验证环节。** 模型可以决定下一步做什么，但不能仅凭自己的叙述宣布完成；最终必须由新的观察来验收。
