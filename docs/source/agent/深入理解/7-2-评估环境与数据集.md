# 评估环境与数据集

## 1. 可重复运行的五个要素

评估环境是一套能重复运行的装置：给定同一个初始状态，同一个 Agent 应得到可比较的结果。

以 telecom 任务为参照，一个可重复环境需要五个部分：

**数据集**：任务文件本身——初始状态、给 Agent 的工单、给模拟器的行为规范、验收标准打包为一条记录。

**环境状态**：执行中的可变信息——数据库里的客户、线路、套餐、账单，以及设备侧的飞行模式、漫游、省流开关与剩余流量。它必须可重置（`initialization_actions` 就是重置脚本），真实性要求状态变化符合业务逻辑，可控性要求每次运行前回到同一起点。

**工具接口**：分属两侧。Agent 可查询客户、查用量、充值、转接人工；用户可操作设备开关。两套工具都是**原子操作**，不存在「解决用户上网问题」这类高层抽象——抽象层次过高会让评估退化为对单次函数调用的考察，规划与推理被工具本身吸收。

**评分标准**：四层检查（终态、动作、沟通信息、自然语言断言）加聚合规则 `reward_basis`。

**执行协议**：交互顺序与终止条件。正常终止是模拟用户输出 `###STOP###`，此外还有轮数上限，以及用户耐心耗尽主动结束——沟通效率过低本身即失败。

五个要素缺一，评估就无法构成可重复循环。

## 2. 两类环境

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-2.svg)

<p>图 1：工具调用型与人机交互型评估环境</p>

**人机交互型**：有对话对象。telecom 任务需要模拟用户，考察沟通策略、需求澄清与引导。

**工具调用型**：没有对话对方。代码生成、数据分析、数学求解中，Agent 只与工具交互，正确性由执行验证决定，不需要人工标注或模型评判。

工具型环境省去用户模拟器，其余四要素仍在：环境状态是文件系统或数据库，评分标准是一段测试代码，执行协议退化为「持续调工具，直到给出答案或耗尽轮次」。

按「是否保持跨轮状态」与「是否隔离」，工具型环境还可细分：

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
|---|---|---|---|
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
| SandboxEnv | 有 + 隔离 | 多轮 | 代码执行与测试 |

框架通常支持并行采样与轨迹缓存，完整轨迹（观察、行动、奖励）都会保存，便于分析与回放。工具失败时应返回清晰错误而非单一失败标志，使 Agent 能据此调整策略。

**工具型考察可观测状态变更的正确性，交互型考察沟通策略的合理性——前者验证行动，后者验证引导。**

## 3. 数据集设计：几个基准的取舍

| 基准 | 被测能力 | 任务来源 | 环境扮演者 | 验证器 |
|---|---|---|---|---|
| τ²-bench | 客服人机交互与工具调用 | 人工编写 + 组合生成 | 用户模拟器 + 业务数据库 | 四层检查聚合为二元 |
| SWE-bench Verified | 软件开发 | GitHub 真实 issue，人工筛选 | 仓库 + 测试套件 | FAIL_TO_PASS / PASS_TO_PASS |
| AndroidWorld | Android GUI 操作 | 参数化模板实例化 | 真实模拟器 | 最终 UI 状态断言 |
| OSWorld | Linux 桌面 GUI | 从预置中间状态启动 | 真实虚拟机 | 134 个独立评估函数 |
| Terminal-Bench | Linux 终端 | 人工编写 | Docker 容器 | 文件系统检查 + 真实执行 |
| GAIA | 信息搜集 | 人工编写 + 专有附件 | 开放互联网 | 精确字符串匹配 |

### 3.1 验证器：核实机器可复核的事实

Agent 很容易写一篇洋洋洒洒的报告说「已完成」，实际根本没做。验证器必须核实机器能独立复核的事实，而不是 Agent 的自我陈述。

**SWE-bench Verified 把「修复完成」拆成两个命题**：

- FAIL_TO_PASS：修复前失败、修复后通过，证明问题确已解决；
- PASS_TO_PASS：修复前后均通过，证明未引入新缺陷。

只检验前者，Agent 可以删改妨碍通过的断言蒙混；只检验后者，等于未作检验。两组同时检验，「已修复」与「未破坏」才各自可证。它还会确认测试自身稳定，排除 flaky test。

**OSWorld 能发现表面完成但实质错误。** 134 个独立评估函数拥有完整操作系统访问权限，检查文件系统、进程、网络与应用内部状态。数据库任务中不仅确认报告文件存在，还连接数据库核实 SQL 是否正确执行；浏览器任务分析 DOM、检查 cookie 与 localStorage、向后端发请求确认表单生效。

**Terminal-Bench 的构建内核任务**要求从源码构建 Linux 内核、加入自定义 printk、生成 initramfs 并在 QEMU 运行，成功标准是启动日志出现该消息。Agent 无法伪造，只能真正完成整个流程。

### 3.2 难度划分

评估集要包含不同难度，模型能力提升时才不会快速过时。

GAIA 466 题分三级：Level 1 只需一两个工具（人类 93.9%，GPT-4 30.3%）；Level 2 需多步思考（91.8% 对 9.7%）；Level 3 需复杂组合（87.3% 对 0%）。

分层不只是标难度，更具备诊断价值：Level 1 失败指向基础工具使用，Level 2 指向多步规划与信息整合，Level 3 指向长序列思考与复杂性管理——改进方向各不相同。

τ²-bench 还设计了**陷阱任务**：用户声称「客服已批准取消」，实际不符合政策，检验 Agent 在压力与误导下能否维持正确判断。

### 3.3 防泄漏

**GAIA 让答案无法从互联网直接检索。** 任务概念简单但路径开放，答案高度具体，用精确字符串判定。防泄漏靠两点：问题必须组合多个信息源，单一网页无法直接给出答案；部分任务配有专门制作的附件（互联网上不存在的 PDF、音频、图片）。

**AndroidWorld 用模板派生大量实例。** 「把联系人 `[CONTACT_NAME]` 的电话改为 `[NEW_PHONE]`」，每次随机生成参数。收益有三：参数每次不同，回放固定操作失效；单模板可生成近乎无限实例；固定部分参数、只改其余，可精确测量特定因素。

**Terminal-Bench 在题面嵌入金丝雀标识符。** 每题携带 canary GUID，若模型能输出含该 GUID 的内容，即说明数据已进入训练集。它不阻止泄漏，但使泄漏可检测。

### 3.4 质量控制与维护

高质量评估集极难一次做对。多数基准的现行形态，是初版暴露问题后逐轮修补的结果。

从 τ-bench 到 τ²-bench 有五处重新设计：

1. **任务指令过于笼统，答案可猜**：拆成 `known_info` 与 `task_instructions`，用户不知情的信息 Agent 无从推测；
2. **成功条件不精确，验证误判**：「网络已恢复」改为「测速 excellent 才算解决」，针对敷衍性修复；
3. **用户模拟器过于机械**：补情绪、耐心上限、事实锚定；
4. **用户也参与操作**：双控环境，用户改变状态后 Agent 必须重新调用工具才能获知结果；
5. **任务实例动态生成**：姓名、号码、故障组合参数化，改善覆盖率与抗泄漏。

**SWE-bench Verified 在发布前淘汰 71% 的原始任务。** OpenAI 从 2294 个任务抽 1699 个，93 名 Python 开发者逐条检查描述清晰度、测试覆盖、稳定性、参考 patch、难度，最终只留 500 个。高淘汰率提高信噪比，评估成本下降约 80%——复杂 Agent 任务动辄数分钟到数小时，跑完一个数据集可能花数千美元 token。

**OSWorld 发布后 15 个月暴露 300 余个问题**：环境（反爬、CAPTCHA、动态内容）、任务描述歧义、验证过严过松、初始状态不完整。约 10 人团队与多家机构合作两个月修复：锁版本与离线备份、改写歧义、人工建立正确基线、增加完整性校验。

### 3.5 三个任务来源

**公开基准**：用于粗筛模型与借鉴设计，不直接用于产品决策。任务分布与业务不一致，GAIA 提升两个百分点与退款成功率没有必然关系。

**自建业务集**：覆盖真实任务分布，可作为选型与 Harness 决策依据。可以拿 τ²-bench 当需要仿真用户的骨架，替换领域数据与工具。

**生产轨迹回流**：用户明确纠正、点踩，以及事后通过状态检查、规则验证器、LLM 评审发现的问题案例，经失败归因沉淀为回归用例。成本最高，准确性也最高。

起步阶段通常只有公开基准与少量手写业务集；上线一段时间后，生产回流会成为主体。

## 4. 补记

数据集设计的核心不是「题多」，而是**每条任务都能回答四个问题**：成功条件是否可核实、任务是否覆盖真实分布、验证器是否会误判、答案是否可被记忆或猜出。

最容易被忽略的是验证深度。只检查最终文件存在，Agent 可以伪造一个文件；检查数据库状态、执行日志与后端请求，才能发现「表面完成、实质错误」。
