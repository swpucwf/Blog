# Agent 工程决策十问

模型能力之外，Agent 系统的差异往往来自工程判断。下面十个取舍都围绕同一条链路展开：**观察 → 决策 → 行动**，以及 Harness 在链路外圈补上的约束、验证与纠正。

每个问题按「场景 → 推理 → 结论」展开，结论是一句可执行的工程判断。

## 1. 只能加一样能力，加什么

**场景**：更强的模型、更丰富的上下文、更多工具，只能选一样。

**推理**：LLM 是策略空间，上下文是观察空间，工具是动作空间，三者构成串行链路，任何一环缺失都会让全链路失效——所以问题不是「谁更重要」，而是**最短板在哪**。默认答案偏向补上下文：模型能力由厂商迭代，工程师短期内改不动；信息供给完全在工程侧掌控。消融实验也说明，删除历史消息会让 Agent「失忆」、重复执行，观察侧缺口最常见，也最容易被误判为「模型不行」。选择会改变的条件对应另外两环：推理复杂度超出模型能力时换模型；动作空间缺手段时加工具。

**结论**：优先补上下文，用失败轨迹定位瓶颈——看错信息是感知问题，选错方案是决策问题，调用失败是行动问题。

## 2. ReAct 的缓存读取为何近似二次增长

**场景**：每轮都读取完整轨迹，累计缓存读取量随轮数近似 O(n²)。

**推理**：这是 ReAct 累积性的固有代价：第 i 轮读取的前缀长度约与 i 成正比，n 轮累计为 1+2+…+n。二次增长的是**累计读取费用**，不是轨迹长度或 KV Cache 占用（两者都是线性）。不能简单砍掉「每轮读全量」，否则 Agent 就失去「记住做过什么」的能力，只能改变增长阶或压低常数。

三个缓解方向：**阈值触发批量压缩**，只保留结论与关键状态——不能每轮压缩，否则前缀反复变动，缓存全部失效，还多出压缩调用；**大块中间结果外置**，需要时检索拉回，用观察空间换存储；**子 Agent 隔离**，把产生长轨迹的子任务派出去，主 Agent 只收结论。

**结论**：用「批量压缩 + 结果外置 + 子 Agent 隔离」控制增长，切忌每轮压缩。

## 3. 模型即 Agent 与 Harness 工程为何共存

**场景**：模型越来越自主，Harness 的重要性反而在增加。

**推理**：两个判断看似相反，关键在看清自主范围扩大改变了什么——决策权从代码移向模型后，单次出错的影响面从「生成一句错话」升级为「执行一次错误操作」，可逆性骤降。模型能力是马力，Harness 是缰绳；**马越强，缰绳不是多余，而是必需**。

用「内化迁移」视角统一两个趋势：Harness 中补偿模型缺陷的部分（编排逻辑、调用格式补丁）会随模型进步逐层被内化，价值递减；而模型无论如何内化都不该接手的部分——真实世界的权限、不可逆操作的审批、跨会话的兜底恢复——构成 Harness 的持久价值。框架的核心价值因此从「编排 LLM 调用」转向保障层：权限分类、熔断器、错误恢复、上下文压缩、工具生态。

**结论**：模型内化一层，Harness 向保障层下移一层；框架价值从编排转向保障。

## 4. 无限循环的诱因与终止机制

**场景**：工具结果缺失会让 Agent 反复重试直到耗尽预算；生产环境还有哪些循环诱因？

**推理**：ReAct 是「思考→行动→观察」闭环，工具结果缺失等于**观察环节断裂**——模型看不到「已经试过且失败」，在它的视角里这是第一次调用。把机理一般化：**任何破坏「观察→调整策略」链路的情况都会造成循环**。常见场景包括：工具反复报同一错误（观察信号失真）、模型幻觉调用不存在的工具（行动从未成功）、压缩丢失关键状态（记忆断裂）、思考过程被剥离导致 API 报错（反馈通道故障）、任务本身无解（观察再完整也收敛不到终点）。

防护直接套 Harness 三层：**停止条件**（最大迭代次数）属于约束；**重复检测**（相同工具 + 参数指纹）属于验证；**超过失败阈值转人工**属于纠正。

**结论**：循环的本质是观察链路断裂；防护 = 停止条件 + 重复指纹检测 + 阈值升级人工。

## 5. 用感知、行动、策略分析一个产品

**场景**：拿一个日常使用的 AI 产品，判断它的架构是否合理。

**推理**：三个维度是 RL 三要素的产品化翻译：感知 = 观察空间（能看到哪些信息源），行动 = 动作空间（能改变什么、是否开放式），策略 = 执行循环（单轮、ReAct 迭代，还是人工预编排）。分析时先列信息源清单，再看动作边界，最后看循环模式。

评估合理性就是找**维度间的错配**：动作空间全开放、却没有任何验证反馈，必然产生失控；感知很宽但动作受限，则是安全的渐进设计。成熟 Agent 的共性基准是：开放动作空间、内部思考、基于反馈迭代。

**结论**：三维度分析的本质是把产品放回「观察—决策—行动」链路找短板，改进空间总出现在三者不匹配的那一环。

## 6. 订票客服：工作流还是自主 Agent

**场景**：设计一个航班订票客服系统。

**推理**：先看业务风险特征：含资金操作（不可逆）、有强制时序（付款前不能预订）、输入不可信（用户消息、邮件可能携带提示注入），同时存在大量开放环节（理解模糊需求、航班取消后的替代方案）。

逐项映射：**强制时序**正是工作流所长——身份核实 → 搜索 → 付款 → 预订，顺序由代码保证；**攻击面**上工作流把注入影响限制在单节点，全自主 Agent 的攻击面贯穿整条轨迹；**开放环节**则是工作流「无变通」的短板，必须交给自主模式。混合之后还要补最后一层：大额付款、退款等高风险节点强制人工审批。

**结论**：主体工作流 + 开放环节局部自主 + 高风险节点人工确认。两种模式不是互斥选型，而是按「确定性需求」分配比例。

## 7. 动态风险评估：从工具细化到参数

**场景**：`delete_file` 删普通文件是低风险，删系统文件是高风险，同一工具不同参数。

**推理**：静态评级粒度太粗：按工具整体评「中风险」，两头都错——要么误伤日常操作，要么放行灾难操作。修正方向是把评级对象从「工具」细化为**「工具 + 参数」组合**，评级维度不变（可逆性、权限、影响面），输入从静态注册表变为调用时的实际参数。

下一个问题：谁来判？必须遵守**输入隔离**——安全校验只读结构化数据，不采信模型自由生成的文本。因此用基于规则的确定性检查（路径黑白名单、正则），而不是「让另一个 LLM 判断危不危险」：后者既引入新的注入面，又不可审计。还要防参数欺骗：只看结构化字段，不解释其语义。

**结论**：动态风险评估 = 粒度细化到参数 + 确定性规则 + 只信结构化数据，是约束与验证在工具层的合体。

## 8. 受限动作空间何时更优

**场景**：开放式动作空间常被当作 Agent 的标志，什么场景反而应该限制？

**推理**：动作空间每扩大一分，错误动作的可能性、攻击面、评估难度都同步扩大——开放是能力上限，也是风险上限。在**高合规、高风险、错误不可逆**的场景（退款金额、付款对象），「模型能做什么」远不如「模型能不被允许做什么」重要。

受限动作空间是「约束」最干净的形态：它**让错误在结构上无法发生**，而不是发生后靠验证和纠正补救。这正是防呆（Poka-yoke）的终极体现——约束优于检测，检测优于修复。注意受限的只是执行侧：内部思考、需求理解仍可完全开放，只在最后一步「动作发射」时收敛到合法集合。

**结论**：动作空间开放与否不是能力问题，而是风险预算问题；错误不可逆的场景，受限选项优于事后护栏。

## 9. 用户不在线时如何移交控制

**场景**：Agent 需要人工确认，但用户不在线、响应很慢，或指令模糊。

**推理**：人工干预通常由「超过失败阈值」或「高风险操作」触发，但它有一个隐含假设：**人在**。用户不在线，等于移交通道本身失效，系统必须回答 Fail-safe 状态下默认做什么。

默认值套用**故障安全默认值**原则：宁可停，不可猜——高风险操作未获确认时暂停而非默认执行，因为两种错误代价不对称（暂停可恢复，误执行可能不可逆）。暂停不等于死等：先完成可逆的低风险部分（查询、草稿、预订前准备），把高风险部分固化为待决文档，人和 Agent 都读同一份文档，决策与恢复解耦。再用异步沟通工具通知并设超时，超时后维持安全默认而非降级自动执行。指令模糊时，问题在「理解」而非「授权」，应先澄清，而不是擅自猜测。

**结论**：优雅移交的底线是 Fail-safe——未确认不执行；配套手段是可逆部分先行、状态文档化、异步通知加超时、模糊先澄清。

## 10. 哪些工程手段会随模型进步过时

**场景**：设计原则要穿越模型周期，但具体实现手段可能过时。

**推理**：判别标准：一个手段若在**补偿当前模型的缺陷**，会随模型进步贬值；若满足的是**系统级需求**（互操作、审计、权限、回滚），与模型能力无关，则持久有效。

四个例子：**约束采样强制工具调用格式**补偿的是「模型易输出非法 JSON」，格式能力提高后收益递减；但高风险场景的确定性格式校验属于系统级需求，不贬值。**外部知识库**补偿「模型无法持续吸收新知识」，若持续学习可靠，部分知识会迁回参数；但实时更新、精确检索、权限控制、来源追溯是系统级需求，所以它缩小适用范围而非消失。**一切能力必须走标准工具调用接口**正被 Skills 打破——文本描述能力 + 通用执行器，模型可以理解自定义文本协议；它退化为面向互操作与较弱模型的场景性选择。**提示词与工具定义固定在上下文开头**源于早期模型指令遵循能力弱，动态加载已在打破惯例；但它与 KV Cache 的静态前缀原则存在张力，前缀稳定性是成本问题，可能长期制约实际采用节奏。

**结论**：补偿模型缺陷型手段会持续贬值，服务系统需求型价值穿越模型周期；工程上应显式标注哪些设计属于前者，并为它们预设「退役条件」。

## 补记

十个问题最后都落到同一个判断：**这项设计是在替模型补短板，还是在替系统守边界**。补短板的部分要准备退役，守边界的部分要长期投入。分清这一点，就不会把「当前模型做不到」误当成「架构必须如此」，也不会把「模型变强了」误当成「约束可以撤掉」。
