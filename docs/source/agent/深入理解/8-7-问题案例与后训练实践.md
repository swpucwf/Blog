# 问题案例与后训练实践

## 1. 从评估数据到训练信号

第七章留下的问题：基于生产问题案例构建的评估数据集，如何真正变成后训练输入？

四类评估资产各对应不同训练用法：

| 评估数据集 | 训练用法 |
|---|---|
| 端到端回归任务（含验证器） | RL rollout 任务与可验证奖励；拒绝采样（RFT）的采样池 |
| 轨迹前缀回归任务 | DPO 偏好对、决策边界 SFT 示范、在轨蒸馏的教师状态 |
| 失败归因记录（首错步骤与类别） | 过程监督负标签、RLVP 路径惩罚的规则来源 |
| Rubric 多维评分与人工金标 | 向量奖励各维度、生成式奖励模型的训练与校准 |

这条链路的顺序是：**失败归因 → 回归任务 → 训练数据 → 参数更新 → 边界集与保留集验证。**

## 2. 案例一：Coding Agent 过早结束

### 2.1 归因

Coding Agent 最常见、最难根治的失败之一是**过早结束**：

- 测试没跑就宣称「已完成」；
- 用户要求改三个功能，改完两个就收尾；
- 遇到两次失败就宣布「这个任务不可能完成」。

按第七章分类，这属于「任务完成度与逻辑判断问题」。生产侧三类信号都能捕获：用户纠正（「你根本没跑测试」）、点踩、事后审计（宣称完成的轨迹里没有任何测试工具调用）。

归因把首错定位在「准备宣称完成」的决策边界上——在此之前的读代码、改代码可能都没错，错的是「在缺乏证据时下结论」。

这正是 reward seeking 的日常形态：自行设置一个过于简单的检查，刚好通过就提前结束。

### 2.2 构造训练数据

**端到端回归任务**：把「宣称完成前必须跑通验收测试」写成可验证奖励。测试对模型不可见，模型宣称完成时才运行，通过 +1、不通过 −1。这是 RL 分支。

**轨迹前缀回归任务**：截取「准备宣称完成」的决策边界构造**偏好对**：

- rejected：过早结束的错误行为；
- chosen：「先运行测试、逐条核对验收条件，再下结论」。

chosen 由教师模型生成，再经规则验证器过滤（拒绝采样），得到 DPO 训练对。问题案例太少时，可换任务类型、换缺失验证项、换完成措辞，扩充到数百条。

按小配比混入通用任务数据做 LoRA 微调，避免把「逢收尾必验证」学成新的过拟合，也降低遗忘。

### 2.3 评估：边界集与保留集缺一不可

- **边界集**：任务未完成时，模型是否选择继续验证而不是宣称完成；
- **保留集**：任务确实已完成时，模型应正常宣称完成。

只盯前一个指标，会把模型训练成永远不敢收尾的「过度矫正」——每个任务都无限验证，延迟与成本崩溃。

评估还要抽查通用能力，确认 LoRA 补丁没有破坏其他能力。

一个教学实验提供 24 条写实问题案例，覆盖四类失败：未跑测试就宣称完成、多目标只完成一部分、验收条件未满足、遇错放弃并宣称不可能（含删除失败测试这类更恶劣的 reward hacking 变体）；评估集与训练严格隔离（boundary 12 条 + retention 8 条）。

生产环境中，偏好对要覆盖更多任务族，保留集覆盖更多正常收尾场景，还要警惕新形态：模型可能学会「口头声称去验证」而不真的验证。这也是端到端奖励必须依赖模型无法编写或修改的隐藏测试，而不是模型自己声明的原因。

## 3. 案例二：中文引号

用户反馈「中文文章中的直引号应统一为弯引号」。这句话描述期望，却没有给出可直接训练的规则：同一个引号，在中文自然语言、英文原文、Markdown 行内代码、代码块、代码注释、JSON 或路径中角色完全不同。

正确修复是**作用域敏感的最小编辑**：

- 中文自然语言中的引用可转换为 `“”`，嵌套引用按中文标点规则处理；
- 英文原文、可执行代码、JSON/schema、路径、标识符、Markdown 反引号中的内容必须原样保留；
- 无法判断作用域时保留原文。

### 3.1 构造训练数据

把引号规则写成 Skill：

- **正例**：中文段落、嵌套引用、代码注释中的中文自然语言；
- **反例**：英文原文、字符串/字符字面量、JSON、路径、行内代码、整段代码。

这样教给模型的是「先判断作用域，再做最小编辑」，而不是「看到直引号就替换」。

一个实验以 8B 模型为基座，bf16 LoRA 训练 2 epoch（256 次更新）。`SKILL.md` 的作用域规则同时作为生成标签、质量门禁与回归规范；模型只负责选择作用域并生成最小编辑，生产侧解析器与语法检查不被移除。

数据按 16 类片段、10 种文章体裁、9 种编程语言渲染 1024 条训练样本、256 条留出、256 条边界。样本成对保存原文与目标文本：中文自然语言与中文代码注释提供需要转换的正例；英文原文、字符串字面量、JSON、路径、行内代码、代码块及嵌套结构提供必须保护的反例。

## 4. 案例三：编辑文件经常失败

Coding Agent 常用 `edit_file(path, old_string, new_string)`：模型把要替换的 `old_string` 抄进工具参数。工具按精确字符串匹配，哪怕只差一个空格、换行、反斜杠、Unicode 组合字符或低频 token，都会失败。

### 4.1 归因

沿链路逐层对比：

```text
文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文
→ 模型 token 输出 → 解码字符串 → JSON/tool-call 解析 → 工具匹配
```

- 文件读取或工具返回已改变字节 → 归因给工具；
- 序列化、转义或提示词拼装改变内容 → 归因给 Harness；
- tokenizer encode 后再 decode 变化 → 归因给 tokenizer；
- 只有模型收到的上下文与原始字符串完全一致、而**模型输出是链路上首个差异点**，才标为模型的精确复制能力问题，作为后训练候选。

### 4.2 构造训练数据

把复制任务抽象成三个可验证任务：

1. 直接逐字复述；
2. 在相似且等长的多个字符串中选择完全相同的目标；
3. 把指定字符串完整抄写到 `old_string` 的工具 JSON 参数。

样本特意包含真实编辑最容易损坏的空格、真实换行、反斜杠、Unicode 等。

一个实验以 8B 模型为基座，bf16 LoRA 2 epoch，只对目标字符串或 `old_string` JSON 字段提供逐 token 监督。留出集 byte-exact accuracy 从基座 37.5% 提升到 78.9%，独立边界集 80.1%；平均首次字节分歧位置分别为 54.0 与 54.2。

另用 512 条探针比较三个开源 tokenizer，两个 Qwen tokenizer 的无损 round-trip 均为 80.1%。因此 80.1% 同时反映了模型复制与 tokenizer 上限——**不先把 tokenizer 的损失排除，就会把工具问题误训成模型问题。**

## 5. 后训练实践要点

这一章从预测下一个词走到四阶段训练。贯穿的线索只有一条：**模型学到什么，取决于训练信号教了它什么；信号质量主要由数据和环境决定，不是算法。**

常见陷阱：

1. **用 SFT 硬塞知识库**：大量稳定领域知识与基础能力用 Mid-training；动态更新、引用、权限、删除的事实由 RAG 管理。
2. **格式未稳定就上 RL**：模型不能稳定生成奖励所需的 JSON，信号会稀疏或失真；先用 SFT 或约束解码稳定输出。
3. **把标称窗口当有效窗口**：位置编码允许 128K，不代表模型在 128K 上仍会检索、推理、规划；扩窗前完成当前长度的能力门禁，保留短数据与前序 replay，用「能力 × 长度」矩阵检查退化。
4. **pass@k 近零仍直接上 RL**：全失败 rollout 没有正向轨迹，GRPO 优势消失；先 Mid-training、SFT/蒸馏，或构造可达课程与部分奖励。
5. **奖励函数设计不当**：只看回复长度就生成冗长无意义文本；应评估最终目标而非中间指标。
6. **忽视仿真保真度**：仿真客服总按固定模式、错误信息与生产不一致，策略上线即失效。
7. **过度训练导致泛化下降**：训练损失降、验证集恶化，模型在死记细节；Mid-training 会遗忘通用能力，SFT 会过拟合示范，RL 会过拟合奖励与任务分布；三者都需要独立保留集与早停。
8. **价值函数崩溃与探索不足**：PPO 价值估计偏差导致曲线震荡；温度过低或随机性不足会陷入局部最优。
9. **把训练—推理数值失配当小噪声**：更新前 sampler/trainer 概率比已偏离 1，会把 on-policy 悄悄变成 off-policy；监控 log probability 差异、近似 KL、裁剪比例与 staleness。
10. **低估 RL 成本**：SFT 上表现好的任务转 RL 可能需要 10–100 倍时间；测试分布与训练高度一致时，SFT 可能已足够。
11. **训练数据质量低**：Mid-training 吸收错误关联，SFT 学习示范噪声，RL 把奖励偏差放大。

核心原则：**在投入大规模资源前，先用小规模实验验证关键假设。**

- 小批 Mid-training 语料，检查知识/能力与遗忘曲线；
- 少量 SFT 数据，测试格式能否稳定；
- 小批 rollout，检查 pass@k、奖励差异与 sampler/trainer 数值一致性。

快速失败比大规模失败更可接受。

## 6. 与 RAG、ICL 的协同

三者不是互斥方案，而是作用于不同位置：

- **ICL（上下文学习）**：用示例、规则与当前状态实现零参数即时适应，但上下文增长会带来延迟与费用；
- **RAG**：把事实与证据放在可动态更新、可追溯的外部知识中；
- **后训练**：把高维感知、生成风格与隐式决策策略写入参数。

选择依据不只是「任务是否长期稳定」，更重要的是**能力能否被外部符号充分表达**：

- 医疗影像识别、自然语气等能力，即使领域持续变化，仍往往需要参数更新；
- 长期稳定的转账审批规则，应由代码提供确定性保障，而不能只靠模型记忆。

稳健系统通常组合使用：RAG 管理动态事实与证据，ICL 快速试验可用语言描述的策略，程序固化确定性流程与硬约束，Mid-training 吸收稳定领域知识与基础能力，SFT/RL 塑造难以由外部规则完整表达的行为。蒸馏则把高能力大模型的行为迁移到成本更低的小模型。

## 7. 补记

后训练最容易被误解成「收集数据、跑个 LoRA」。真正决定成败的是三件事：**问题归因是否指向模型**（而不是工具、Harness 或 tokenizer）、**训练数据是否覆盖决策边界**（而不是只覆盖正确答案）、**评估是否同时看边界集与保留集**（而不是把模型训成永远不敢结束）。

对大多数应用团队，优先级通常是：先把评估与归因做对，再考虑 SFT；只有当模型确实「会做但不会按要求做」时，训练才值得；RL 则要求非零成功率与可靠奖励，门槛更高。
