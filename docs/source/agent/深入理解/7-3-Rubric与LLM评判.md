# Rubric 与 LLM-as-a-Judge

## 1. 验证方式的谱系

前面讨论的基准验证器几乎都是确定性的：SWE-bench 跑测试，AndroidWorld 断言 UI，GAIA 精确匹配，τ²-bench 四层检查由代码执行。

确定性验证不引入额外模型开销，结果完全可复现，能像单元测试一样纳入 CI，也便于跨模型排名。

代价是它只能判断最终结果对不对，不能给出错误原因。τ²-bench 那条失败任务最终得 0 分，但这个 0 分不会说明是线路选择错、还是漏了流量充值，更不会指出下一步改什么。对排名基准这不构成缺陷；对持续改进的生产系统，这恰恰是最需要的信息。

生产场景还有另一重困难：许多判断无法写成代码断言。一封投诉回复是否得体、一份报告是否遗漏关键信息、一次记忆检索是否弄错人物关系——既没有唯一终态可查，也无法靠关键词匹配判定。

因此验证方式需要沿一条谱系向右移动，横轴是任务的**可机械验证程度**。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-4.svg)

<p>图 1：验证方式的谱系——从确定性验证到模型评判</p>

谱系右侧的两件工具成为生产评估主体：用 **Rubric** 把笼统的「好不好」拆成可分别打分的维度，用 **LLM-as-a-Judge** 在缺乏确定性判据时完成打分。

向右移动不意味着放弃左侧。能写成程序化断言的都应用断言，LLM 评判只用于确实无法机械判定的维度。确定性检查更便宜、更稳定，也更适合长期回归。

## 2. LLM-as-a-Judge

开放式任务没有标准答案可自动对比，人工评估成本高且难规模化。LLM-as-a-Judge 让语言模型按专家定义的 Rubric 评判，在自动化规模与人类专业判断之间取得平衡。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig7-5.svg)

<p>图 2：LLM-as-a-Judge 流水线</p>

但它有已知局限：评判模型可能有自己的偏见，相同输入多次评判也可能波动。最典型的是**长度偏差**——倾向给更长、更详尽的回复打高分，哪怕内容并不更正确。就像考试时对不会的题长篇大论，期望蒙对一两个点。

三种防范：

- 在 Rubric 里显式惩罚冗长、给同类任务规定长度上限；
- 配对比较时先把两个候选的长度控制到相近；
- 定期审计评分与长度的相关性——高分几乎总伴随长回答，就说明评判被长度带偏，需要回炉修订。

## 3. Rubric 四准则

**基于专家指导**：必须反映领域知识，捕捉核心事实与推理步骤。医疗问答的 Rubric 要包含诊断标准与必须避免的医学错误；缺乏专业基础的 Rubric 只能捕捉语言流畅度。

**全面覆盖**：涵盖事实准确性、逻辑连贯性、完整性、安全性；不仅定义正面标准，还要明确**陷阱**——高风险的常见错误，如推荐未经验证的疗法。

**按重要性加权**：分必要项、重要项、可选项、陷阱项；支持**一票否决**。客服场景中，幻觉是典型的否决维度——无论其他维度多优秀，只要编造虚假信息就判零。这也有助于防范关键词堆砌式的奖励作弊。

**评价标准自包含**：每个评价项独立可操作，不依赖评价者的领域知识。避免「回应展示了深刻理解」，改为「引用了至少两个权威理论并准确解释如何支持结论」。

关键实践：为每个维度定义客观可验证的评分档次，提供示例与**边界案例**；主动防范**奖励作弊**——Agent 找到高分捷径却没真正完成任务——明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。Rubric 需要迭代：收集评价者分歧，逐步从抽象准则演化为详尽判例集。

### 3.1 一个用户记忆 Rubric

测试问题：「我女儿的儿科医生是谁？」答案需要跨两次对话关联：第一次提到「女儿叫 Lily」，第二次提到「带 Lily 去看了 Dr. Chen」。

```yaml
rubric:
  dimensions:
    - name: 事实正确性
      weight: essential
      scoring:
        4_优秀: "准确回答 Dr. Chen，且关联到女儿 Lily"
        3_良好: "准确回答 Dr. Chen，但未提及是 Lily 的医生"
        2_及格: "给出正确医生但附带不确定的额外信息"
        1_不及格: "给出错误医生名，或回答不知道"

    - name: 信息完整性
      weight: important
      scoring:
        4_优秀: "主动补充相关信息（上次就诊时间、诊断结果）"
        3_良好: "回答了核心问题，无遗漏"
        2_及格: "回答了核心问题，但遗漏可用的关联信息"
        1_不及格: "关键信息缺失"

    - name: 思考正确性
      weight: important
      scoring:
        4_优秀: "正确关联'女儿=Lily'与'Lily 的医生=Dr. Chen'"
        3_良好: "关联正确但路径不清晰"
        2_及格: "部分关联正确"
        1_不及格: "错误关联（把用户自己的医生当成女儿的）"

    - name: 幻觉检测
      weight: veto
      scoring:
        pass: "所有信息均可溯源到历史对话"
        fail: "编造了对话中不存在的信息（虚构就诊日期等）"

  edge_cases:
    - "用户有多个女儿且分别看不同医生时，应追问是哪个女儿"
    - "记忆中同时存在 Dr. Chen 与陈医生时，应识别为同一人"
```

好的 Rubric 每个档位都给出可验证的具体行为，而不是「展示了对记忆的深刻理解」这类无法客观判定的描述。一票否决项明确底线：其他维度全满分，一旦幻觉直接零分。

把 Rubric 与 Agent 实际回答交给评判模型，逐项打分并说明理由。汇总几十个用例，再回看低分轨迹，原本笼统的「成功率下降」就能拆成具体问题：没检索到信息、把人物关系想错，还是补充了没有依据的内容。

## 4. 同源模型与多源评判

当 Agent 与评判模型来自同一家族，Agent 可能学会利用评判模型的偏好与盲点。

**古德哈特定律**：当一个度量指标变成优化目标时，它就不再是好的度量指标。Agent 越是在某个评分系统上训练或调优，就越倾向钻系统漏洞，而非真正提升能力。更隐蔽的是，它会逐渐避开评判模型不擅长的错误类型，让评分看起来一切正常。

缓解策略是**多源异构评判**：用不同模型家族的多个 LLM 分别评判（Agent 用 Claude，评判用 GPT 与 Gemini），不同家族的偏见往往正交，Agent 很难同时欺骗所有评判者。使用相同 Rubric 确保评判同一目标，通过加权平均或一致性检查聚合。部署阶段可用单一模型快速评估，但应定期用完整多源评判做质量审计。

## 5. 多模态评判

LLM-as-a-Judge 也可以扩展到语音、图像、视频：

- **TTS**：准确性、自然度、音色一致度、情感表达——能发现 WER 难以捕捉的韵律问题；
- **ASR**：做语义影响判断——「今天天气」识别错无伤大雅，「转账一千」变成「一万」可能造成严重后果；
- **UI**：用提议者—审核者检查文字溢出、颜色对比度、按钮位置；
- **视频剪辑**：通过关键帧验证起止点与特效是否正确。

一次 TTS 小规模听评中，两家服务在准确性与自然度上都得到 5.00 和 4.00，但情感表达与音色一致性出现差异（4.00/3.00 对 3.75/2.75）。四个维度分开评分后，即使「有没有读对」看不出差别，语气与音色上的差别仍会显现。

但这组分数还不能判断哪家 TTS 更好：每家只有四条音频，且固定参考音频来自其中一家，拿它比较音色本来就更有利于该家。**选什么参考答案、参考图片或参考音频，本身就是评估设计**，不是开始前无关紧要的准备工作。

## 6. 补记

Rubric 的价值不是「给一个更细的分数」，而是**把失败还原成可修复的维度**。总分下降没有行动含义；「事实正确性 2 分、幻觉触发否决」才指向下一步。

评判系统的最大风险是被优化。只要 Agent 针对某个 Judge 调优，它就会学会这个 Judge 的口味。多源评判、定期审计、把确定性断言留在左侧，都是防止评估退化的手段。
