# 多 Agent 协作：分类框架与信息增量

此前各篇的主语始终是一个 Agent：先建上下文、知识与工具，再扩展交互能力，最后用评估、后训练和持续进化让它长期变好。从这里开始，问题换成另一个：**如何组织多个 Agent**，让它们通过分工、通信与相互验证，完成单个 Agent 难以承担的任务。

单个 Agent 终究受限于自身模型的能力边界与上下文窗口。但多 Agent 的意义不止于让不同专长的角色取长补短，更根本的一点是：**群体的智能可以高于个体**。人类文明就是现成的例子——单个人的智力有限，经由分工、协作、辩论与知识的代际累积，整体展现出的智能远超任何一位天才个体。

Google DeepMind 在《从 AGI 到 ASI》中把「大规模多 Agent 集体」列为通往超级智能的关键路径之一：众多 AGI 级 Agent 协同形成的群体智能，可能表现出远超成员简单相加的认知能力。

也要留一分清醒：五级能力框架里的「组织（Organizations）」是能力级别，不是架构要求，足够强的单 Agent 理论上也能达到。群体智能的前提是「组织得当」；组织不当，多 Agent 只是把同一个错误并行放大，还多付数倍 token。

## 1. 两个设计维度

第一个维度是**上下文是否共享**，它决定多个 Agent 之间如何传递信息。

**共享上下文**指后续 Agent 接收前一个 Agent 的完整对话历史与轨迹。切换系统提示词与工具集之后，它已经是一个新 Agent——身份、职责、能力都变了——但保留着前任的全部记忆。像团队里需求分析师写完文档后，开发者不仅拿到文档，还能看到分析师与用户的所有沟通记录。好处是信息不丢失，任何阶段的细节都能回溯；代价是上下文迅速膨胀，且容易继承前任的思维惯性。

**不共享上下文**指每个 Agent 维护完全独立的上下文与历史，彼此看不到对方的「思考过程」。这更像不同部门之间的协作：各自在工位上独立工作，通过共享文档与会议纪要交换信息，而不是盯着别人的屏幕。模块化与隔离性更好，新增 Agent 不必改动既有逻辑，只需约定接口与数据格式。

不共享就必须显式通信。这个在分布式系统里早有答案：进程间通信归根结底只有两大范式——**共享内存**（一方写入、另一方读取同一块存储）与**消息传递**（把数据显式发给对方）。Agent 之间同样落在两者之内，常见三种做法：

- **工具调用参数**：把下游 Agent 封装成工具，上游用结构化参数传数据，适合类型明确、结构清晰的场景；
- **共享文件系统**：通过读写共享目录中的文档、代码等中间产物交换信息，适合产物较大或需要持久化的场景；
- **消息总线**：Agent 不直接调用彼此，而是把消息发到中转站，由它按订阅转发。

对应到两大范式：共享文件系统就是 Agent 世界的「共享内存」；工具参数与消息总线则是消息传递的两种形态，前者随调用同步传递，后者经中转站异步投递。Go 语言那句「不要通过共享内存来通信，而要通过通信来共享内存」，在 Agent 系统里同样值得反复掂量。

第二个维度是**协作拓扑**，即控制权与信息按什么结构流动。三种典型形态：

- **对等协作**：少量 Agent 按固定拓扑形成迭代改进循环，例如起草者与评论者反复批注几轮；
- **管理者模式**：一个中心化 Manager 负责任务规划与调度，多个子 Agent 各负责特定子任务；
- **去中心化模式**：没有运行时的中心控制者，Agent 之间像人一样互相沟通、自主移交。

2026 年流行起来的「Graph 工程」正是这套拓扑的显式版本：节点是 Agent、普通程序或人工决策，边定义任务依赖、条件路由与失败去向，结构化状态在节点之间流动。这里的三种拓扑，都是不同的图结构。

## 2. 判据：是否引入新信息

在讨论具体架构之前，先回答一个更根本的问题：**什么时候真的需要多个 Agent，什么时候一个就够？** 近年研究的答案可以压缩成一条判据——**协作过程是否引入了单个 Agent 在生成时无法获得的新信息**。

| 协作模式 | 是否引入新信息 | 效果 |
|---|---|---|
| 同一模型自我审查（重读自己的输出） | 否 | 通常无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| 审核者使用测试执行结果审查代码 | 是（执行反馈） | 显著提升 |
| 审核者查看渲染截图审查前端/PPT 代码 | 是（视觉反馈） | 显著提升 |
| 审核者使用外部工具验证事实 | 是（工具反馈） | 显著提升 |

2025 年的 RLEF 用强化学习训练模型利用代码执行反馈迭代改代码，效果远超让模型独立多次采样——关键在于每次迭代都带回了**真实的执行结果**：编译错误、测试失败、运行时异常，这些信息在模型写代码时并不存在。

同年的 WebGen-Agent 在网页生成任务上搭了一套多层视觉反馈脚手架（截图 + 视觉语言模型描述），据报道让 Claude 3.5 Sonnet 在该基准上的表现从 26.4% 提升到 51.9%，接近翻倍。

这条判据顺带解释了一个矛盾：一些学术研究认为多 Agent 并不能提升能力上限，而工程实践里多 Agent 确实更有效。差别在于两者说的不是同一种多 Agent——学术研究比较的多是「多个 Agent 看着同一段上下文互相讨论」，工程实践中有效的系统往往带着外部反馈环路（代码执行、视觉渲染、工具调用）。前者没有新信息，后者有。

## 3. 开放搜索空间中的信息增量

Anthropic 2026 年的漏洞挖掘实验给出了另一种增量形态。45 个 Agent 通过共享论坛协调搜索、互相审查，再由独立 Agent 仲裁结果：集群用 2700 万 token 找到 266 个漏洞，而独立 Agent 并行方案用 650 万 token 只找到 21 个。

差别不在单个 Agent 更强，而在开放搜索空间里，互相通信让集群可以动态转移搜索重点、形成专门分工，用更高的 token 预算换取更广的覆盖与更多样化的发现路径。这类收益要如实理解为**购买覆盖度**，而不是「多 Agent 无条件更强」；任务本身没有开放搜索空间时，这笔钱很可能白花。

## 4. 步骤预算与成本

一个相关问题是：给 Agent 分配不同的步骤预算（允许的工具调用次数或迭代轮数），会如何影响表现？

直觉是越多越好——30 步只能快速实现核心功能，300 步可以先规划、再实现、再测试、再改进。但 2025 年 Google 的《Budget-Aware Tool-Use Enables Effective Agent Scaling》发现，**单纯增加步骤数并不能保证性能提升**：标准 Agent 缺乏「预算意识」，即使有 300 步，也倾向执行浅层搜索，很快「饱和」。要让更多步骤转化为更好结果，需要显式的预算感知机制，按剩余资源调整策略：前期广泛探索，后期聚焦最有希望的方向。2026 年的 BAVT 进一步做了步骤级价值评估，在每一步按剩余预算比例调整探索与利用的权重——预算越少，越从「广撒网」切向「深挖掘」。

这对管理者模式有直接指导意义：Manager 不该只是把任务分发出去等结果，而应按任务复杂度**动态分配步骤预算**，简单子任务给少、复杂子任务给足；同时引导子 Agent 先规划、再实现、再测试、再改进，而不是一头扎进去直接开干。

**成本**是另一条硬约束。并行探索与反复迭代都要烧 token，多 Agent 的收益必须大到能覆盖数倍乃至一个数量级的额外开销。否则，一个调校得当的单 Agent 往往是更划算的选择。

## 5. 补记

工程上的判断顺序可以固定为三步：

1. 这次协作是否引入了执行、视觉、工具或搜索覆盖上的**新信息**？没有，就先回到单 Agent 把验证器做好；
2. 新信息需要**共享轨迹**还是**隔离上下文**？前者省事但会膨胀，后者要靠移交包与文件系统；
3. 收益能否覆盖**数倍的 token 与延迟**？不能，就缩小协作范围或只保留审核环节。

多 Agent 不是能力升级按钮，而是一种用成本换信息与覆盖度的架构选择。
