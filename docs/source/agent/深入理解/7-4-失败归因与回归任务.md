# 失败归因与回归任务

## 1. 从「失败」到「首个错误」

端到端评估通常只给「成功/失败」，没有回答「为什么失败、从哪一步开始」。

要让评估驱动修复，必须对每条失败轨迹做**失败归因**：标出主要错误类别、首次出现不可接受行为的步骤、对应的工具调用或模型输出，并附可复核的证据。

归因对象是轨迹中**首个导致任务偏离的错误**。后续错误往往只是连锁反应，不能把最后一个报错简单当成根因。

问题案例通常来自三类信号：

- 用户明确纠正（「不要这么做」）；
- 用户点踩或负面反馈；
- 事后通过状态检查、规则验证器或 LLM 评审发现 Agent 做了不该做的事。

构建归因系统需要开发者耐心阅读轨迹。过程可以借助 LLM，但不能完全依赖——**失败归因往往反映产品问题，不只是技术问题**。随着产品完善，错误分类可能多达数百种，这些类别与归因方式可以作为归因 Agent 的提示词或 Skill。

## 2. 一个初始分类

以 Coding Agent 为例：

| 错误类别 | 典型表现 | 首错定位方式 |
|---|---|---|
| 需求理解与歧义 | 漏条件、范围理解过宽/窄；同名文件直接选一个不追问 | 把原始需求与动作序列逐条对照，定位第一处偏离，回溯到造成它的调用或答复 |
| 流程与规范缺失 | 未跑单测就提交；未写计划就改代码；绕过架构约定 | 找第一次违反流程的动作，回看它之前有没有读过约定来源 |
| 工具调用错误 | 同一文件反复编辑失败；参数格式错误；特殊字符抄错 | 记录第一次失败的编辑及请求、错误返回；重复失败是后续症状 |
| hack 验证环境 | 改断言、加 skip、mock 被测逻辑；声称测试通过但没跑 | 取第一次改测试的 message；把完成声明与真实执行命令交叉核对 |
| 修改不完整 | 改签名与三处调用，漏了第四处动态调用 | 声称影响面与真实影响面的集合差，取第一个遗漏项，回看检索关键词 |
| 对用户反馈错误 | 工具全对，最终告知的金额/状态/时间错；把部分完成说成全部 | 把答复里每个事实断言与工具返回逐条对齐，取第一条无法溯源或矛盾的 |
| 非功能性回归 | 改公开 API/schema 无迁移；为让校验通过而删校验 | 取第一次该改动的 message，看它是否意识到动的是公开接口 |
| 模型执行异常 | 输出截断、无故停止、超时、未收尾 | 定位第一个异常终止，区分模型停止、Harness 超时、工具故障 |
| 过早停止 | 多目标任务只完成一部分；未穷尽方案就宣布不可能 | 定位第一次遗漏目标或放弃探索的决策，与最终验证失败分开记录 |

**归因记录必须结构化**：用 JSON/YAML，引用步骤号、工具名与观察证据；区分根因与后果、判断是否可恢复并给出置信度。

例如 `edit_file` 返回 `old_string` 匹配失败，之后 Agent 连续三次重试仍未写入：主因是「文件编辑与工具调用错误」，三次重试是后果，不是三个独立根因。多个类别同时出现时，按「最早且能解释后续失败」选主因，其余保留为次因。

至少三类可以先用规则筛出嫌疑轨迹，再交给 LLM 定位首错：完成声明与实际执行命令的交叉核对；diff 是否触及测试断言与 skip；diff 是否改动公开 API/schema 而无迁移。**规则先筛、LLM 再定位**，比把全部轨迹喂给 LLM 更便宜也更准。

保存归因记录时，还要保存任务目标、环境状态、Agent 版本、工具集版本与完整轨迹，以便回归测试。

## 3. 「做对了但说错了」

这类问题容易被整体成功率掩盖，因为多数评估只检查环境状态。

τ²-bench 公开基线中，带信息告知要求的 704 次运行失败 240 次，其中 162 次是信息告知出错；有 80 次（占全部失败三分之一）环境状态正确，但信息告知错误。

一个 AndroidWorld 例子：任务是把图库 `expenses.jpg` 里的开销录入记账应用。Agent 用 32 步完成授权、搜索、打开图片、逐条填写与保存，**没有任何一步返回错误**，最后自行宣告完成，验收却报告记录不存在。

逐步回看：

- 第 8 步的思考写着「I cannot actually see the content/details of the expenses in the image」——它自己已经知道没拿到数据，却既没停下也没报告；
- 第 11 步，四条开销数据「Coffee $4.50、Lunch $12.75……」凭空出现在记录里；
- 此后每次输入与保存，都基于这四条幻觉编造的数据。

**首个错误落在第 8 步，而那一步既没有报错，也不是一次工具调用。**

根因也容易归错：T3A 是纯文本 Agent，观察空间只有元素树、根本没有图像像素，所以根因不是「模型不会 OCR」，而是 **Harness 的观察通道缺失**。如果记成模型能力问题，接下来会去换模型或做 OCR 训练；真正该做的是补观察通道。

### 3.1 作用域敏感的文档格式

用户说「引号格式不对」时，不能直接转成全局字符替换。至少要区分 ASCII 直引号、中文弯引号、Markdown 反引号。同一字符在中文自然语言、英文原文、行内代码、代码块、代码注释、JSON 与路径中承担的语法角色不同。

评估数据应先把文档解析为带作用域的片段：`ZH_PROSE`、`EN_PROSE`、`QUOTED_SOURCE`、`INLINE_CODE`、`CODE_BLOCK`、`CODE_COMMENT`、`JSON_OR_SCHEMA`。每个片段保存允许变换集合、必须保护的字符与修改后的验证结果。

下面三处不能用同一条规则处理：

```text
中文说明：调用 `reset()` 方法。
这是一段英文原文：“Please restart the service.”

# 以下代码块仅用于说明受保护作用域

# 中文注释：显示 "当前状态"
name = "status"
```

轨迹前缀回归应要求模型做最小修改，同时检查中文文档风格、英文原文保持率、代码与 JSON 语法、非目标文本的编辑距离。规则无法确定作用域时，应允许模型保留原文并请求澄清，而不是把猜测性修改算作通过。

### 3.2 精确复制错误

`old_string` 失败不能只归因于「模型抄错了」。应对同一字符串保存原始字节哈希、Unicode code point 序列与 tokenizer token ID 序列，沿链路寻找首个差异：

```text
文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文
→ 模型 token 输出 → 解码字符串 → JSON/tool-call 解析 → 工具匹配
```

最小化评估探针覆盖直接复述、从长上下文抽取、放入工具参数、相似字符串选择，以及空格、换行、反斜杠、Unicode 组合字符与低频 token。指标用 byte-exact、code-point-exact、token-exact、首次分歧位置与真实工具成功率。

若模型在直接探针中输出正确、而工具调用失败，应修复 tokenizer、序列化、Harness 或工具协议；只有首个差异出现在模型输出时，才把案例转成复制训练数据。

## 4. 两类回归任务

归因明确首错后，要把修复目标写成可重复执行的**回归任务**。两层互补：

**端到端回归任务**：从初始状态与用户请求开始，让 Agent 完成整个任务，检查最终状态、必要输出与安全条件。最接近生产结果，却难以判断失败发生在哪一步。OSWorld、AndroidWorld、τ-bench 都是端到端回归任务。

**轨迹前缀回归任务**：冻结已有上下文、对话、工具返回与环境状态，只要求 Agent 思考并执行下一步或下几步可观察动作。成本更低，能隔离单个策略或工具问题。

对高可靠性生产 Agent，构建轨迹前缀回归集往往比端到端更重要，也需要耐心建立失败分类与归因系统。

轨迹前缀任务的答案应定义为**可接受动作集合**，而不是唯一动作：可以要求「先读仓库规则」「先询问用户」「拒绝危险操作」，同时列出禁止动作。

以 Coding Agent 为例：

- **流程缺失** → 生成带计划文档与测试验收条件的端到端任务；
- **工具调用错误** → 截断出错前缀，编辑成边界任务，测试能否修正格式、转义特殊字符或换工具；
- **执行异常** → 加入截断、超时与工具故障的恢复场景；
- **完成度/逻辑错误** → 加入多目标清单、剩余任务提醒与「尚未证明不可能」的边界；
- **需求歧义** → 冻结成前缀，把「先澄清」列入可接受动作；
- **症状修复/验证造假** → 验收补上「不得修改测试断言」「完成声明必须附真实执行过的命令输出」；
- **信息反馈错误** → 对答复内容本身设断言，而不只检查环境状态。

一个轨迹前缀实验把同一组上下文（用户记忆）、任务、前缀、工具返回与环境状态输入模型，只让它输出下一步可观察动作。同一组 11 个边界用例用 JSON Cards、Markdown、Python-like 三种语义等价表示，结果总成绩碰巧都是 6/11，但失败位置不同：Markdown 通过了「仓库规则未知时先检查」，却多失败了一个作用域冲突用例；另两种相反。

三种表示都没通过论文风格过度泛化、过时偏好覆盖当前要求、高风险删除前确认三类用例。这说明：**改变上下文的表示方式，不会自动修复应用策略。**

## 5. 补记

失败归因最容易被做成「让 LLM 写一段失败原因」。真正有用的是结构化记录：首错步号、类别、责任方、证据、主因/后果、置信度。没有这些，修复无法验证，回归任务也无从构造。

另一个经验是：**首错常常不是报错**。它可能是一句自我怀疑的思考、一次没有追问的选择、一个被忽略的工具返回。只搜错误关键字，会漏掉最关键的静默失败。
