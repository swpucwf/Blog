# 工具太多怎么办：组织与主动发现

## 1. 规模本身会伤害正确性

「能力做成什么形态」问的是每条能力的成本；这一节问另一件事：**不管做成什么形态，一次该让模型看见多少？**

当可用工具从十几个增长到成百上千，工具库本身就成了需要设计的对象：如何组织、如何暴露、Agent 如何找到当下需要的那一个。

规模本身就会伤害正确性：工具数量超过一百个时，即使最先进的大模型也容易在工具选择上出错；全部平铺进上下文还要占大量 token，并让每一次工具集变动都击穿 KV Cache。

答案有三层，一层比一层更「按需」：

1. **层次化组织与按需加载**：工具定义事先备好，但不全量塞进上下文；
2. **主动工具发现**：Agent 在执行中意识到能力缺口，主动声明需求，由系统动态匹配并注入；
3. **Skills**：不把工具当成需要注册、检索、注入的正式定义，而当成可随手翻阅的参考资料。

## 2. 按需加载：只暴露索引

MCP 生态快速扩张带来一个工程问题：仅仅 5 个 MCP 服务器就可能引入数万 token 的工具定义，在 200K 窗口里还没开始对话就用掉近三成。

Cursor 的缓解方案是：把工具描述同步到文件夹，Agent 默认只看到工具名称索引，需要时再查询具体定义。A/B 测试显示，这让 MCP 相关任务的总 token 消耗减少 46.9%。

Pi Coding Agent 更激进：核心不内置 MCP，优先建议把能力封装成带 README 的 CLI 工具，再由 Skills 按需加载；确实需要 MCP 生态时，通过扩展接入。社区扩展展示了一种折中：模型默认只看到一个约 200 token 的代理工具，通过「搜索 → 查看定义 → 调用」按需发现后端工具，MCP 服务器也延迟到首次使用才启动。

这说明：**是否采用 MCP 作为互操作协议**，与**是否在会话开始时暴露所有 MCP 工具定义**，是两个独立决策。后端可以保留 MCP 的生态兼容性，前端仍应以 CLI + Skills 或代理工具实现渐进式披露。

## 3. 层次化组织

除了按需加载，工具数量上百时，层次化组织比扁平列表更有效。一种方式是**按信息源性质分类**：

- **搜索工具**：主动查找信息（网络、知识库、文件搜索）；
- **读取工具**：从已知位置提取内容（网页、文档、数据库）；
- **解析工具**：处理非结构化数据（OCR、视频分析、音频转录）；
- **查询工具**：访问结构化数据源（天气、股价、公开数据库）。

在系统提示词中显式说明分类结构，可以帮助模型快速定位到相关工具组。

**检索式预筛选**更进一步：不把全部定义一次注入，而是按语义相似度先筛一批候选。Anthropic 的实验显示，按需检索使 Opus 4 在工具使用基准上的准确率从 49% 提升到 74%。

## 4. 主动工具发现

检索式预筛选有一个内在局限：它按用户初始查询做**一次性**匹配，而「Debug the file」这类看似简单的请求，实际可能牵出文件访问、代码分析、命令执行等多步骤、跨领域的工具链，任务开始时无法预见所有需求。

更进一步的思路，是让 Agent 从被动接受者变为主动发现者：执行中意识到能力缺口时，主动用自然语言声明「我需要什么能力」，系统再动态匹配并注入。

MCP-Zero 是代表性工作：系统提示词中不预置任何工具 schema，Agent 在思考中生成结构化请求块（如「GitHub 服务器：搜索仓库并返回元数据」），系统通过服务器级 → 工具级两层语义路由，从数千候选里匹配注入，论文报告在约 2800 个工具上比全量注入节省约 98% 的 token。

工程上更常见的等价方案，是系统提示词只保留少数基础工具（web search、code interpreter）外加一个「工具搜索工具」，Agent 用自然语言描述需求即可检索并加载。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig4-2.svg)

<p>图 1：层次化工具匹配（服务器级 → 工具级）</p>

**层次化匹配与降级**：高效匹配的关键是工具组织本身有层次。在 MCP 中，工具按服务器分组（类似手机上的 App，每个 App 提供一组相关功能），于是匹配分两层——先按能力描述定位相关服务器，再在服务器内匹配具体工具，把搜索空间从「数千个工具」缩小为「数十个服务器 × 每个服务器数十个工具」。

工程上这依赖一个离线构建、支持增量更新的嵌入索引；若两层候选相似度都低于阈值，应明确返回「未找到」，让 Agent 改写需求、用基础工具手工实现，或创造一个新工具。

### 4.1 动态加载与 KV Cache

动态加载工具有一个微妙的工程代价：会**破坏 KV Cache**。若把全部工具定义放进静态前缀，每加载一个新工具就使整段缓存失效。

破解思路是把新工具的完整 schema **追加到上下文末尾**：静态前缀保持稳定，schema 固定在轨迹的原位置，此后作为普通历史消息继续命中缓存；状态栏只维护一份简短的工具名列表。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig4-3.svg)

<p>图 2：工具动态加载的 KV Cache 优化</p>

两个工程细节：

- OpenAI 要求后续请求保持 `tool_search_output` 项的原位置，同一工具无需重复加载；Anthropic 在会话历史原位置内联展开 `tool_reference` block，后续每一轮都能保持缓存命中；
- 真正导致重算的只有两种情况：Prompt Cache 的 TTL 过期（整段前缀一起重算，不是工具定义特有的代价），以及修改、移除或重排已加载的工具集（缓存从变动点起失效）。

![配图](https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/aiagent_fig4-4.svg)

<p>图 3：动态发现后的上下文结构——schema 散落在轨迹各处</p>

多轮动态发现后，静态前缀只保留系统提示词、核心工具与工具搜索元工具；历次发现的 schema 散落在轨迹各处，固定在首次注入的位置，后续作为普通历史命中缓存。

这也意味着「工具定义必须在上下文最前面」不再是铁律——前缀依然静态、只增不改，只是工具定义获得了按需进入轨迹的能力；代价是模型必须在后训练中学会理解散落在上下文各处的工具定义。

## 5. Skills：把发现变成按需查阅

主动发现机制虽然有效，工程上却相当繁琐：要离线维护嵌入索引、处理 KV Cache 失效、为弱模型做专门训练。它们共同的前提，是把每个工具都当成一份**面向模型的正式定义**，先注册、再检索、再注入。

Skills 换了一种更轻量的思路：渐进式披露是默认形态。

Agent 启动时只看到一份薄薄的目录——每个 Skill 的 `name` 与 `description`，合计数百 token。当前上下文真的需要某种能力时，模型才去读对应的 Skill，再顺着引用读取脚本或子文档。

这更接近人使用参考资料的方式：没有人会把整本工具书从第一页读到最后一页，而是顺着目录按需查阅。专用工具要达到同样的效果，必须在工具之外另建一层——检索、索引、元工具、命名空间、允许列表，也就是上一节那套基础设施存在的理由。

Skills 的优势在于把渐进式披露内建为默认形态，实现成本更低。MCP 与 Skill Hub 也不是互不相干：MCP 官方已在推动 Skill 经由 MCP 被发现和传递——同一个 Skill 既可以躺在 Skill Hub 等 `npx` 安装，也可以由 MCP 服务器供给。

## 6. 补记

工具太多的解法不是「藏起来」，而是**让模型在正确的时刻看到正确的那一条**。三条路线可以组合：

- 稳定、高频的核心工具放静态前缀；
- 领域工具按层组织，先用索引或检索缩小范围；
- 长尾能力做成 Skill，按需查阅。

判断是否需要主动发现，看一个信号：模型是否经常「不知道有这个工具」或「选错相似工具」。前者需要目录/发现机制，后者需要更清晰的描述、命名与层次。
