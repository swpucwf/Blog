# 数据加载与文本分块

## 1. 数据加载决定上限

「垃圾进，垃圾出」在 RAG 里格外成立。文档加载器要完成三件事：解析不同格式的原始文档（PDF、Word、Markdown、HTML）为纯文本；抽取来源、页码、作者等元数据；整理成统一结构，供后续切分、向量化与入库。

主流加载器的取向差别很大：

| 工具 | 特点 | 适用场景 |
|---|---|---|
| PyMuPDF4LLM | PDF→Markdown，OCR + 表格识别 | 科研文献、技术手册 |
| TextLoader / DirectoryLoader | 基础文本与目录批量加载 | 纯文本、混合格式文档库 |
| Unstructured | 多格式统一接口，识别标题/段落/表格/列表 | PDF、Word、HTML |
| FireCrawlLoader | 网页抓取 | 在线文档、新闻 |
| LlamaParse | 深度 PDF 结构解析 | 法律合同、学术论文 |
| Docling | 模块化企业级解析 | 企业合同、报告 |
| Marker | PDF→Markdown，GPU 加速 | 科研文献、书籍 |
| MinerU | 多模态集成解析 | 学术文献、财务报表 |

## 2. Unstructured：先理解结构，再提取文本

Unstructured 的价值在于「分区」这一步：它把文档拆成带语义标签的元素，而不是一堆纯文本。常见元素包括 `Title`、`NarrativeText`、`ListItem`、`Table`、`Image`、`Formula`、`Header`、`Footer`、`CodeSnippet`、`PageNumber` 等。

直接调用比用框架封装更灵活：

```python
from unstructured.partition.auto import partition

elements = partition(filename="rag.pdf", content_type="application/pdf")
print(f"解析完成: {len(elements)} 个元素")

from collections import Counter
print(Counter(e.category for e in elements))
```

`partition` 会按文件类型路由到专用解析器；PDF 场景也可以直接用 `partition_pdf`，它提供 OCR 语言、图像提取、表格结构推理等更细的参数。实际工程里，PDF 解析更多会选 PaddleOCR、MinerU 这类模型化方案。

## 3. 为什么必须分块

分块不是为了「把文本变小」，而是要同时满足两个硬限制：

- **嵌入模型有输入上限**。常见中文嵌入模型的窗口是 512 token，超出部分会被截断，向量无法代表原文语义；
- **LLM 的上下文窗口要装下所有检索片段**。单个块过大，能塞进去的相关片段就少，参考面变窄。

## 4. 块越大越好的三个反例

**嵌入过程的信息稀释**：嵌入模型最终要把整个块压缩成一个向量，块越长，语义点越多，单向量承载的信息被摊薄，关键细节被模糊。

**生成过程的「大海捞针」**：长上下文里模型更容易记住开头和结尾，中间部分被忽略（Lost in the Middle）。块又大又杂时，关键证据容易淹没在噪音里。

**主题稀释导致检索失败**：一个块里混了三个主题，检索得分会被无关内容拉低。把「技能」「出装」「故事」分开切，查询「怎么出装」时对应块的相似度才会高。

## 5. 四种基础分块策略

| 策略 | 依据 | 优点 | 缺点 |
|---|---|---|---|
| 固定大小 | `chunk_size` + 分隔符 | 简单、快、开销小 | 可能切断语义 |
| 递归字符 | 分隔符优先级 | 平衡语义与大小 | 需要选对分隔符集 |
| 语义分块 | 相邻句向量距离 | 按主题边界切 | 需嵌入模型，成本高 |
| 结构分块 | 标题层级 | 保留文档结构与元数据 | 依赖格式规范 |

### 5.1 固定大小与递归字符

`CharacterTextSplitter` 并不是严格按字符数切：它先按 `"\n\n"` 分段，再合并到接近 `chunk_size`，超长段落会保留并告警。因此它更准确的名字是「段落感知的自适应分块」。

```python
splitter = CharacterTextSplitter(chunk_size=200, chunk_overlap=10)
chunks = splitter.split_documents(docs)
```

`RecursiveCharacterTextSplitter` 改进了超长段的处理：按分隔符优先级逐层递归，段落不行用句子，句子不行用词，最后才按字符硬切。

```python
splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", "。", "，", " ", ""],
    chunk_size=200,
    chunk_overlap=10,
)
```

中文场景要注意分隔符集：默认的 `["\n\n", "\n", " ", ""]` 缺少中文标点，句子边界识别会退化。补上全角句号、逗号、顿号后再切，语义完整性明显更好。代码文档则可以用 `from_language(language=Language.PYTHON, ...)` 走语法结构分隔。

### 5.2 语义分块

`SemanticChunker` 把相邻句子编码成向量，计算相邻距离，再按统计阈值判定断点。默认用百分位法：只有差异最显著的那 5%（第 95 百分位以上）才被当作切分点。

优点是天然跟随主题变化；代价是每条候选边界都要跑一次嵌入，长文档上开销明显。适合结构混乱但语义清晰的文本，不适合批量预处理。

### 5.3 结构分块

`MarkdownHeaderTextSplitter` 按标题层级聚合内容，并给每个块注入标题路径作为元数据：

```python
splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "Header 1"), ("##", "Header 2")]
)
chunks = splitter.split_text(markdown_text)
```

得到的块携带类似 `{"Header 1": "第三章 模型评估", "Header 2": "3.2 评估指标"}` 的元数据，相当于给每段内容一个精确地址。问题是单章节可能仍然过长，所以常见做法是两阶段：先按标题切出逻辑块，再用递归字符分块细分，细分后的块继承标题元数据。

## 6. 其他框架的分块思路

**Unstructured** 的分块建立在「分区」结果上，有两种模式：`basic` 连续组合元素直到 `max_characters`；`by_title` 把 `Title` 视为章节起点，强制在此开新块。后者适合报告、书籍这类结构文档。

**LlamaIndex** 把分块抽象成节点解析器，三类值得区分：

- 结构感知型：`MarkdownNodeParser`、`CodeSplitter`，按源文件结构切；
- 语义感知型：`SemanticSplitterNodeParser` 找语义断点；`SentenceWindowNodeParser` 用单句做检索，但元数据里携带前后 N 句，命中后把窗口一起送进 LLM；
- 常规型：`TokenTextSplitter`、`SentenceSplitter`，按 token 数或句子边界切。

`SentenceWindowNodeParser` 的思路值得单独记：**用小块保证检索精度，用元数据扩展保证生成上下文**，一次解决「切小了没上下文、切大了检索不准」的两难。

## 7. 分块没有通用最优解

几个可以直接落地的判断：

- `chunk_size` 先按嵌入模型窗口的一半起步，再用评测集调；
- 中文必须补全角标点分隔符；
- 结构清晰的文档优先按结构切，再按长度细分；
- 需要精确引用时，务必保留来源与标题元数据；
- 分块效果可以用可视化工具（如 ChunkViz）先看一眼边界与重叠，比盲调参数快。
