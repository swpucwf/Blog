# 项目实战与图 RAG

## 1. 项目一：食谱问答系统

目标很具体：基于 HowToCook 的菜谱数据，做一个能回答「宫保鸡丁怎么做」「推荐几个简单的素菜」「红烧肉需要什么食材」的问答系统。

数据特点决定了实现策略：

- 约 300 多个 Markdown 文件，结构高度规整；
- 单篇约 700 字，篇幅短；
- 统一结构：一级标题是菜名，开头简介与难度，随后是「必备原料和工具」「计算」「操作」「附加内容」。

结构规整是好事：分块可以按章节走，元数据可以稳定抽取（菜名、难度、分类、食材），不必依赖复杂的版面解析。

## 2. 四个模块

| 模块 | 职责 | 关键选择 |
|---|---|---|
| 数据准备 | 解析 Markdown、抽元数据、分块 | 按标题结构切，保留菜名与难度 |
| 索引构建 | 向量化、建索引、缓存 | BGE-small-zh + FAISS |
| 检索优化 | 双路召回 + 融合 + 过滤 | BM25 + 向量 + RRF |
| 生成集成 | 拼上下文、约束回答 | 模板化 prompt + 引用来源 |

模块化的价值在替换成本：换嵌入模型只动索引模块，换融合策略只动检索模块，互不影响。

## 3. 索引构建与缓存

```python
class IndexConstructionModule:
    def __init__(self, model_name="BAAI/bge-small-zh-v1.5", index_save_path="./vector_index"):
        self.embeddings = HuggingFaceEmbeddings(
            model_name=model_name,
            model_kwargs={"device": "cpu"},
            encode_kwargs={"normalize_embeddings": True},
        )
```

两个工程细节值得抄：

- **索引缓存**：首次构建后把 FAISS 索引落盘，后续启动直接加载，启动时间从分钟级降到秒级；
- **元数据随向量一起存**：`FAISS.from_texts(texts, embedding, metadatas)` 把菜名、难度、分类一起写入，检索后可直接用于过滤与引用。

## 4. 混合检索

双路召回的设计理由很直接：

- **向量检索**理解意图，能处理「简单素菜」这类没有精确关键词的查询；
- **BM25** 负责关键词命中，能精准匹配「宫保鸡丁」「五花肉」这类专有名词；
- **RRF** 融合两路排名，避免过度依赖单一路径；
- **元数据过滤**支持按难度、分类缩小范围，例如「简单」对应难度 ≤ 2。

RRF 未必是最优重排，但它的性价比很高：不需要训练、不需要归一化、没有超参要调。等业务稳定后再引入 Cross-Encoder 精排，是更合理的演进顺序。

## 5. 生成集成

生成侧的重点不是模型，而是约束：

- 上下文按「菜名 + 章节」结构化拼接，而不是把文本块随意拼接；
- prompt 明确要求「只依据提供的菜谱回答，没有就说没有」；
- 输出带上来源菜名，便于用户核对。

这一步与前面章节的结论一致：检索决定上限，提示决定下限。

## 6. 项目二：图 RAG

食谱问答用向量检索够用，但换成「哪些菜同时用到五花肉和土豆」「川菜里哪些是凉菜」这类需要沿关系查询的问题，向量检索就开始吃力——它找的是「语义相似」，不是「关系连通」。

图 RAG 引入 Neo4j，把菜谱数据组织成实体与关系：

- 节点：菜谱、食材、分类、菜系、难度；
- 关系：`菜谱-使用-食材`、`菜谱-属于-分类`、`食材-相克-食材`。

图谱建模的关键是「先定问题，再定模型」：需要回答哪些类型的查询，就设计对应的节点与关系。把所有字段都建成节点，只会得到一个难维护的图。

## 7. 智能查询路由

系统同时具备传统混合检索与图检索，就需要一个路由器决定走哪条路。路由依据四个维度分析查询：

| 维度 | 判断内容 | 去向 |
|---|---|---|
| 实体数量 | 提到几个菜/食材 | 多实体倾向图检索 |
| 关系意图 | 是否含「同时」「搭配」「属于」 | 关系查询走图 |
| 查询复杂度 | 是否需要多跳 | 多跳走图 |
| 明确程度 | 是否点名具体菜谱 | 精确菜名走混合检索 |

三种执行策略：

- **传统混合检索**：单实体、语义型问题，如「宫保鸡丁怎么做」；
- **图检索**：多实体、关系型问题，如「哪些菜同时用到 A 和 B」；
- **组合检索**：先用图缩小候选，再用向量检索排序，适合既复杂又需要语义匹配的问题。

## 8. 路由的工程细节

- **规则兜底**：LLM 路由失败或超时时，退回传统检索，保证系统永远有答案；
- **统计埋点**：记录每种路由的命中次数与满意度，才能发现「路由总把问题送错地方」这类系统性问题；
- **可解释**：把路由决策写进日志（命中了哪个维度、选了哪条策略），Bad Case 复盘时才有依据。

## 9. 两个项目的共同经验

- **数据规整就先赢一半**：结构化的菜谱省掉了大量解析与清洗工作；
- **模块边界要按「可替换」划**：索引、检索、生成三块各自独立，升级时不用重写全链路；
- **先够用再先进**：RRF 够用就不急着上 Cross-Encoder，规则路由够用就不急着上 Agent；
- **图不是万能药**：关系型查询用图，语义型查询用向量，混着用才是常态。

## 写在最后

从四步跑通到图 RAG，这条链路覆盖了 RAG 的主要工程环节：数据、索引、检索、生成、评估与路由。真正的落地差异不在某个组件，而在每一步的取舍是否与业务匹配——数据规整度、查询形态、延迟预算，决定了该用哪套组合。
