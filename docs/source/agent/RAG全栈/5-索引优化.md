# 索引优化

## 1. 检索精度与上下文的两难

RAG 里有一对天然矛盾：小块检索准，但上下文不足；大块上下文足，但噪声多、相似度被稀释。

句子窗口检索（Sentence Window Retrieval）用「索引小、生成大」化解这对矛盾：

- **索引阶段**：文档切成单句，每句独立成节点；同时把前后各 N 句拼成「窗口」存进元数据，不参与向量化；
- **检索阶段**：只在单句节点上做相似度搜索，定位最相关的核心信息；
- **后处理阶段**：用 `MetadataReplacementPostProcessor` 把命中的句子替换成它携带的窗口文本；
- **生成阶段**：送进 LLM 的是带上下文的段落，而不是孤立句子。

关键细节是**元数据排除**：窗内容和原句都要写进 `excluded_embed_metadata_keys` 与 `excluded_llm_metadata_keys`，确保向量化只用单句，窗口只供后处理使用。少了这一步，窗口文本会混进嵌入，检索精度立刻下降。

```python
node_parser = SentenceWindowNodeParser.from_defaults(
    window_size=3,
    window_metadata_key="window",
    original_text_metadata_key="original_text",
)
sentence_nodes = node_parser.get_nodes_from_documents(documents)
sentence_index = VectorStoreIndex(sentence_nodes)

engine = sentence_index.as_query_engine(
    similarity_top_k=2,
    node_postprocessors=[MetadataReplacementPostProcessor(target_metadata_key="window")],
)
```

同一份气候报告上的对照很直观：常规 512 字符分块给出的答案抓住了主干但偏概括，句子窗口版则补出了「定量预测置信度低」「观测记录过短」等多个维度。原因不是模型更强，而是送进去的上下文更贴题。

## 2. 结构化索引：先缩小范围，再算相似度

知识库涨到几百个 PDF 后，全库 top-k 搜索会同时遇到两个问题：效率低，且容易被不相关文档干扰。

解决办法是给每个块附加结构化元数据——文件名、创建日期、章节标题、作者、自定义标签，然后在检索时先过滤、再搜索。

「请总结 2023 年 Q2 财报中关于 AI 的论述」这类查询，先按 `document_type == '财报'`、`year == 2023`、`quarter == 'Q2'` 过滤，再在子集内做向量搜索。范围缩小一个量级，相关性和延迟都会改善。

这也解释了前面章节为什么要用 `MarkdownHeaderTextSplitter`：标题路径本身就是最好的结构化元数据。

## 3. 递归检索：先路由，再查询

数据分散在多个来源（例如一个 Excel 的多个工作表）时，需要「路由 + 局部查询」两级结构。

LlamaIndex 的 `RecursiveRetriever` 做法是：给每个子数据源建一个摘要节点（`IndexNode`），用摘要建顶层索引；检索时先匹配摘要，再按 `index_id` 进入对应的查询引擎。

```python
for sheet_name in xls.sheet_names:
    query_engine = PandasQueryEngine(df=pd.read_excel(xls, sheet_name=sheet_name), llm=Settings.llm)
    node = IndexNode(text=f"这个表格包含 {sheet_name} 的电影信息", index_id=sheet_name)
    all_nodes.append(node)
    df_query_engines[sheet_name] = query_engine

recursive_retriever = RecursiveRetriever(
    "vector",
    retriever_dict={"vector": VectorStoreIndex(all_nodes).as_retriever(similarity_top_k=1)},
    query_engine_dict=df_query_engines,
)
```

查询「1994 年评分人数最少的电影」时，日志能清晰看到四步：顶层路由到 `年份_1994` → 进入对应子引擎 → 生成 Pandas 代码 → 执行得到答案。

但这里有个必须点明的风险：`PandasQueryEngine` 让 LLM 生成 Python 代码并本地 `eval()` 执行，属于实验性功能，**不适合生产环境**。

## 4. 更安全的做法：路由与检索分离

把「选哪个表」和「查什么内容」拆成两套索引，就能保留递归检索的能力而避开代码执行：

- **摘要索引**：每个工作表一条简短摘要文档，只用于路由；
- **内容索引**：工作表内容作为文档，附带 `{"sheet_name": "年份_1994"}` 元数据；
- **两步查询**：先在摘要索引定位目标表，再在内容索引加元数据过滤检索。

这套写法在能力上等价，在安全边界上清晰：没有任何一步执行模型生成的代码。

## 5. 索引优化的三条通用原则

1. **检索单元与生成单元可以不同**。句子窗口、父子文档都基于这个思路：用小单元保证召回精度，用元数据或关联节点扩展上下文。
2. **能用元数据过滤的，不要交给向量相似度**。结构化的条件（时间、类型、来源）用过滤执行更快更准，向量只负责语义匹配。
3. **分层比全库搜索更稳**。数据源一多，先路由再检索，既降噪也降成本。

## 6. 关于框架的选择

这条路线同时用了 LangChain 与 LlamaIndex，甚至在安全场景下自己组合底层模块。理由不是框架不好，而是框架有边界：`PandasQueryEngine` 方便但危险，这时候需要理解原理，用 `VectorStoreIndex` + `MetadataFilter` 自己拼一个更安全的版本。

理解原理的收益是长期的：框架会换，`SentenceWindowNodeParser` 的「小检索、大生成」思路不会换。学框架的 API 是「照着菜谱做菜」，理解索引结构才是「会做菜」。
