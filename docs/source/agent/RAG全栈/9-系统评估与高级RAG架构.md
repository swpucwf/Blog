# 系统评估与高级 RAG 架构

## 1. 评估要回答的两个问题

一套 RAG 搭起来之后，评估回答的是：**哪里出了问题**，以及**改动之后是真的变好了吗**。没有分环节的指标，就只能看到一个笼统的总分，既无法定位，也无法判断收益来源。

## 2. RAG 三元组

| 维度 | 评估对象 | 核心问题 |
|---|---|---|
| 上下文相关性 | 检索器 | 检索到的内容与问题相关吗 |
| 忠实度 | 生成器 | 答案是否完全基于给定上下文 |
| 答案相关性 | 端到端 | 答案是否直接、完整地回答了问题 |

三个维度构成诊断视角：

- 上下文相关性低 → 问题在检索侧，先改分块、嵌入或召回策略；
- 忠实度高但答案相关性低 → 模型没答到点上，问题在提示或任务定义；
- 忠实度低 → 模型在自由发挥，需要更强的上下文约束或更少的噪声。

需要提醒的是，三元组不是完整清单。真实项目还要看答案正确性与完整性、不可回答问题的拒答能力、鲁棒性，以及延迟与成本。

## 3. 一套可重复的评估流程

1. **明确目标**：这轮要验证什么假设（减少幻觉、提升关键证据召回、改善拒答），不同目标对应不同指标；
2. **建立数据集**：真实或经审核的问题，标注类型、难度、可回答性；
3. **记录标准运行数据**：输入、检索上下文、回答、参考答案、文档 ID，以及模型、提示词、检索参数、延迟与成本；
4. **跑基线**：固定可复现配置，得到逐样本结果；
5. **分层分析**：按问题类型、难度、来源切片，同时看失败数与低分样本；
6. **分析 Bad Case**：把失败归因到检索缺失、上下文噪声、生成幻觉、答非所问或评估器误判；
7. **设回归门槛**：把确认过的样本沉淀为回归集，门槛来自基线与业务风险，而不是照搬经验阈值。

第 4 步最关键：每次只改一个变量，否则分数变化无法归因。

## 4. 检索指标与生成指标

检索侧借用信息检索的经典指标：

$$
\mathrm{Precision}@k = \frac{\text{前 }k\text{ 个结果中的相关文档数}}{k},\qquad
\mathrm{Recall}@k = \frac{\text{前 }k\text{ 个结果中的相关文档数}}{\text{全部相关文档数}}
$$

- **F1**：精确率与召回率的调和平均，平衡两者；
- **MRR**：第一个相关文档排名的倒数的平均值，适合「用户只看第一条」的场景；
- **MAP**：先算每个查询的平均精确率，再对所有查询取平均。

这些指标都需要标注「哪些文档真正相关」。没有标注时，只能退而用 LLM 评估上下文相关性。

生成侧有两条路：

| 方法 | 代表 | 优点 | 局限 |
|---|---|---|---|
| LLM 评估 | 断言拆解验证忠实度 | 懂语义，能发现「忠实但错误」 | 有成本、有评估者偏见 |
| 词汇重叠 | ROUGE、BLEU、METEOR | 快、便宜、客观 | 不懂同义改写，容易误判 |

实践中常见的组合是：用词汇指标做大规模初筛，再用 LLM 对低分样本做精评。

## 5. 三个主流工具

| 工具 | 机制 | 适合 |
|---|---|---|
| LlamaIndex Evaluation | 内置评估器（忠实度、相关性、命中率），异步运行 | 开发阶段快速验证组件或管道 |
| Ragas | LLM 驱动、可无参考评估、逐样本结果 | 策略对比与版本回归 |
| Phoenix | OpenTelemetry 追踪 + 可视化 + 聚类 | 生产监控、Bad Case 钻取、漂移检测 |

Ragas 的数据模型值得记住，它把评估需要的字段标准化了：

| 字段 | 含义 |
|---|---|
| `user_input` | 用户问题 |
| `retrieved_contexts` | 实际召回的文本块 |
| `response` | 系统最终回答 |
| `reference` | 经审核的参考答案 |
| `reference_contexts` | 真正相关的参考上下文 |

常用指标五个：`Faithfulness`（回答能否被上下文支持）、`AnswerRelevancy`（是否正面回答问题）、`ContextPrecision`（相关块是否排在前面）、`ContextRecall`（参考信息是否被覆盖）、`FactualCorrectness`（事实是否与参考答案一致）。

后两个需要参考答案，前三个可以无参考运行——但「无参考」不等于「无需数据」，忠实度仍然需要真实的上下文与回答。

## 6. 知识图谱 RAG

向量检索的固有局限在复杂查询上暴露得很明显：

- **关系缺失**：语义相似不等于关系正确，「A 收购 B」与「B 收购 A」向量几乎一样；
- **跨文档联结弱**：需要连边才能回答的问题（因果、时间、供应链）召回不足；
- **实体歧义**：同名公司、别名、缩写难以靠相似度区分。

知识图谱用节点与边显式编码关系，优势正好补上这三点：结构化语义表达、可追溯的推理路径、异构数据统一。GraphRAG 的思路是把图检索与向量检索结合：向量负责找入口，图负责沿关系扩展。

代价同样明显：抽取三元组需要额外的信息抽取流程，图的质量直接决定上限；schema 与本体设计需要领域知识；维护成本远高于纯向量库。

## 7. Agentic RAG

传统 RAG 是「一次检索、一次生成」，所有问题走同一条管道。Agentic RAG 把检索变成 Agent 可以反复调用的工具，带来四种能力：

| 能力 | 含义 |
|---|---|
| 查询规划（Plan） | 把复杂问题拆成子问题，并决定先查哪个 |
| 检索决策（Decide） | 判断何时检索、用什么工具、参数怎么给 |
| 质量自评（Critique） | 评估召回结果是否足够回答问题 |
| 迭代改写（Refine） | 诊断失败原因后针对性改写，再检索 |

四种能力里最有价值的是「质量自评」。传统管道对召回结果照单全收，Agent 会先问一句「这些信息够不够」，不够就再查——这一步把「检索失败」从静默错误变成了可观测状态。

代价是延迟与成本上升：多轮调用意味着更长的响应时间和更高的 token 消耗。所以 Agentic RAG 适合复杂、低并发、高价值的场景，不适合把简单 FAQ 也塞进去。

## 8. 两条进阶路线的取舍

- **知识图谱 RAG** 解决「关系与事实」问题，适合多跳、强事实性场景（金融、医疗、供应链）；
- **Agentic RAG** 解决「策略与自适应」问题，适合问题形态差异大、需要多轮探查的场景。

两者可以叠加：Agent 在规划阶段决定「这次走图检索还是向量检索」，在自评阶段决定「是否需要沿关系再扩一跳」。这也是复杂 RAG 系统的常见终态——不是某个单点技术，而是可编排的组件组合。
