# 混合检索与查询构建

## 1. 稀疏向量与密集向量

| 维度 | 稀疏向量（词法） | 密集向量（语义） |
|---|---|---|
| 表示 | 维度极高、绝大多数为 0 | 低维稠密浮点数组 |
| 依据 | 词袋匹配、词频权重（TF-IDF / BM25） | 深度模型学到的语义空间 |
| 强项 | 精确匹配型号、函数名、专有名词 | 同义改写、语义泛化 |
| 弱项 | 不懂语义，OOV 词直接忽略 | 可能漏掉必须精确命中的关键词 |

两者不是替代关系。搜索「RTX 9070 XT 功耗」时，关键词匹配能精准锁定型号；搜索「显卡耗电怎么样」时，只有语义向量能召回同一段内容。

## 2. 融合的两种主流做法

混合检索并行执行两路召回，再把两组异构结果合并成一个排序。两种策略各有适用面。

### 2.1 RRF：只看排名

倒数排序融合不关心原始得分（稀疏与密集的分数根本不同量纲），只看每个文档在各自结果中的排名：

$$
\mathrm{RRF}(d) = \sum_{i=1}^{k} \frac{1}{\mathrm{rank}_i(d) + c}
$$

`c` 通常取 60，作用是压低排名靠前文档的相对权重，让融合更稳健。RRF 的优点是不需要归一化、无需调权重；缺点是丢掉了分数所携带的「置信度」信息。

### 2.2 加权线性组合

先把两路分数归一化到同一区间，再按权重线性组合：

$$
\mathrm{Hybrid} = \alpha \cdot \mathrm{Dense} + (1-\alpha)\cdot \mathrm{Sparse}
$$

`α` 控制语义与关键词的贡献比例：电商搜索调高关键词权重，知识问答侧重语义。代价是需要标注数据或实验来确定 `α`。

| 优势 | 局限 |
|---|---|
| 召回率与准确率都优于单路 | 要维护两套索引，资源开销大 |
| 容错性好，关键词可弥补向量对罕见词的敏感 | 融合权重需要反复调 |
| 适配面广，可按业务调比例 | 融合后的排序理由不易解释 |

## 3. 在 Milvus 里落地

一个集合同时放两种向量，是最直接的实现方式：

```python
fields = [
    FieldSchema(name="id", dtype=DataType.VARCHAR, is_primary=True, max_length=100),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=4096),
    FieldSchema(name="sparse_vector", dtype=DataType.SPARSE_FLOAT_VECTOR),
    FieldSchema(name="dense_vector", dtype=DataType.FLOAT_VECTOR, dim=1024),
]
collection.create_index("sparse_vector", {"index_type": "SPARSE_INVERTED_INDEX", "metric_type": "IP"})
collection.create_index("dense_vector", {"index_type": "AUTOINDEX", "metric_type": "IP"})
```

BGE-M3 这类模型可以一次生成两种向量，写入时分别填进两个字段。检索时构造两个 `AnnSearchRequest`，再用 `RRFRanker` 或 `WeightedRanker` 融合：

```python
from pymilvus import AnnSearchRequest, RRFRanker

sparse_req = AnnSearchRequest(data=[sparse_q], anns_field="sparse_vector", param={"metric_type": "IP"}, limit=10)
dense_req = AnnSearchRequest(data=[dense_q], anns_field="dense_vector", param={"metric_type": "IP"}, limit=10)

results = collection.hybrid_search(
    [sparse_req, dense_req], rerank=RRFRanker(k=60), limit=5,
    output_fields=["text"],
)
```

工程上要注意三点：两路的 `limit` 决定候选池大小，太小融合没有意义；标量字段要建索引，否则过滤会退化成扫描；`metric_type` 在建索引与查询时必须一致。

## 4. 查询构建：让自然语言变成可执行条件

用户说「关于 2022 年发布的机器学习论文」，向量检索只能理解语义，没法表达 `year == 2022` 这种精确条件。查询构建（Query Construction）就是让 LLM 把自然语言翻译成结构化查询。

**自查询检索器（Self-Query Retriever）** 是最直接的实现：给它一份元数据字段说明，它把查询拆成两部分——语义查询字符串 + 元数据过滤器。

```python
retriever = SelfQueryRetriever.from_llm(
    llm=llm,
    vectorstore=vectorstore,
    document_contents="视频元数据",
    metadata_field_info=[
        AttributeInfo(name="author", description="视频作者", type="string"),
        AttributeInfo(name="view_count", description="观看次数", type="integer"),
    ],
)
```

它有两个前提：元数据必须扁平化（嵌套字典会导致字段取不到），字段描述必须写清类型与含义——LLM 靠这段描述决定生成什么过滤条件。

## 5. 自查询的天花板

自查询检索器擅长「等值过滤」，遇到「时间最短的视频」这类排序或比较就无能为力——它只能生成过滤器，不能表达 `ORDER BY ... LIMIT 1`。

一个通用解法是让 LLM 输出结构化指令而非查询语句：

```json
{"sort_by": "length", "order": "asc"}
```

代码解析这段 JSON，在候选集上执行排序。这样 LLM 只负责「理解意图并给出计划」，执行仍由确定性的代码完成，既扩展了能力边界，也保留了可控性。

更复杂的结构化数据（图数据库）同理：文本到 Cypher 把自然语言翻成图查询语言，本质是同一套思路——**用 LLM 做语义到结构的翻译，用数据库做执行**。

## 6. 检索侧的三个判断

- **单路检索几乎总是不够**：关键词与语义各覆盖一半场景，混合是默认选项而非高级技巧；
- **能用过滤器表达的条件，不要交给向量**：时间、类型、来源这类精确条件交给标量过滤，向量只负责语义匹配；
- **让 LLM 输出计划，不要让 LLM 输出结果**：排序、聚合、连接这类操作由代码执行，模型只决定「做什么」。
