# Text2SQL 与查询重构

## 1. Text2SQL 要跨过的三道坎

把自然语言翻成 SQL，看起来只是「翻译」，实际有三个难点：

- **幻觉表与字段**：模型可能编造不存在的列，生成的 SQL 直接报错；
- **Schema 复杂**：几十张表、上百个字段，全塞进 prompt 既超长又互相干扰；
- **问题有歧义**：同一个问题可能对应多种统计口径，需要业务知识才能确定。

对应的工程手段并不神秘，核心是「把相关知识检索出来，再让模型写 SQL」。

## 2. 四条优化策略

**Schema 描述要写人话**。只给 `CREATE TABLE` 语句，模型只能猜字段含义；补上「`amount` 表示含税总金额（元）」这类注释，生成准确率明显提升。

**提供少量高质量示例**。在 prompt 里放几组「问题 → SQL」范例，让模型看到这个库的写法习惯（日期格式、聚合函数、别名规范）。示例不必多，覆盖典型模式即可。

**先检索再生成**。把所有 DDL、字段说明、Q-SQL 示例存进知识库，用户提问时先检索最相关的表结构和相似问法，再拼进 prompt。这是 RAG 思想在 Text2SQL 上的直接应用，也是降低幻觉最有效的一步。

**执行失败就反思重试**。SQL 在数据库上跑一遍，把错误信息回传给模型让它修正。这一步能把「语法错」和「字段名错」这两类问题消掉大半。

## 3. 一个最小框架

参考 RAGFlow 的思路，用 Milvus 存知识、BGE-M3 做检索、LLM 生成 SQL，目标库是 SQLite。知识库统一存三类内容，用 `type` 字段区分：

| 类型 | 内容 | 用途 |
|---|---|---|
| `ddl` | 建表语句与字段注释 | 让模型知道有哪些表与列 |
| `qa_sql` | 问题-SQL 示例对 | 提供写法范式 |
| `description` | 表级业务说明 | 解释口径与使用场景 |

检索时按问题召回 Top-K 知识片段，拼成 prompt：

```text
【数据库结构】
{ddl_and_descriptions}

【相似示例】
{qa_sql_examples}

【用户问题】
{question}

请只输出可执行的 SQLite 查询语句，不要解释。
```

执行环节必须做三件事：只读连接、语句超时、结果行数上限。模型生成的 SQL 永远当作不可信输入处理——`DELETE`、`DROP` 这类语句必须在执行前拦截。

## 4. 查询重构：先修问题，再检索

用户的原始问题往往不是好的检索输入：太长、有歧义、口语化、缺少上下文。查询重构就是在检索前先「润色」问题。

### 4.1 让模型输出计划

最直接的一类重构，是把自然语言转成结构化指令。前面遇到的「时间最短的视频」，用 JSON 指令解决：

```text
请把问题转换为排序指令：
{"sort_by": "length", "order": "asc"}
```

模型只负责理解意图，排序由代码执行。这种「模型给计划、代码做执行」的分工，比让模型直接给出答案稳定得多。

### 4.2 多查询分解

复杂问题常包含多个子主题，直接用整句检索，向量会被多个意图拉扯。做法是先分解再并行检索，最后合并去重：

- 原始问题：「《流浪地球》中刘慈欣对人工智能和未来社会结构有何看法？」
- 子问题：「书中描述的人工智能技术」「描绘的未来社会」「作者对 AI 的观点」

LangChain 的 `MultiQueryRetriever` 把这个过程封装好了：LLM 从不同角度生成多个查询，分别检索后合并结果。代价是请求数增加，适合对召回率敏感的场景。

### 4.3 退步提示

面对细节密集的问题，先让模型「退后一步」，问一个更抽象的问题，拿到通用原理后再回到具体问题推理。

经典例子：问「理想气体温度增 2 倍、体积增 8 倍，压力如何变化」，退步问题是「背后的物理原理是什么」，得到 `PV=nRT` 后再代入计算。先检索原理、再做推导，比直接猜答案可靠。

### 4.4 HyDE：用假设答案去检索

用户的查询短、文档长，两者在向量空间里天然有距离。HyDE 的做法是让 LLM 先写一份「假设的答案文档」，再用这份文档的向量去检索：

三步：生成假设文档（不必真实，只要语义上像一个好答案）→ 编码成向量 → 用该向量检索真实文档。把「查询到文档」的匹配，转成「文档到文档」的匹配，通常能显著改善召回。

代价是多一次生成调用；如果问题本身已经很具体，收益就不明显。

## 5. 查询路由

系统接入多个数据源后，需要决定「这个问题该问谁」：

| 路由类型 | 例子 |
|---|---|
| 数据源路由 | 产品问题走文档库，订单问题走 SQL，关系问题走知识图谱 |
| 组件路由 | 简单 FAQ 直接向量检索，复杂任务交给 Agent |
| 模板路由 | 数学题用分步提示，代码题用代码专用模板 |

两种实现方式：**LLM 意图识别**最灵活，给出候选标签让模型选；**向量相似度匹配**最便宜，把查询与各路由的描述做相似度比较。前者适合标签少但语义复杂的情况，后者适合路由多、延迟敏感的场景。

## 6. 重构与路由的边界

- **重构改变问题的表达，不改变意图**。改写后如果语义漂移，检索只会更差，所以要有回退：重构结果与原问题各检一次，取更优；
- **路由错误比检索错误更致命**。走错数据源，后面的召回与生成全部无效，因此路由要留兜底分支（默认走通用检索）；
- **每一步都要能单独评测**。重构、路由、检索、生成分开量化，才知道收益来自哪一环。
