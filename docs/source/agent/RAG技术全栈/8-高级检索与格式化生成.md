# 高级检索与格式化生成

## 1. 召回之后还有两步

初步召回解决「有没有找到」，接下来要解决「找到的是不是最好的」和「有没有废话」。前者靠重排，后者靠压缩。

## 2. 四种重排方式

| 特性 | RRF | RankLLM | Cross-Encoder | ColBERT |
|---|---|---|---|---|
| 核心机制 | 融合多个排名 | LLM 推理生成排序 | 查询与文档联合编码打分 | 独立编码后做后期交互 |
| 计算成本 | 低 | 中（API 费用与延迟） | 高（每个候选一次推理） | 中（向量点积） |
| 交互粒度 | 仅排名 | 概念 / 语义级 | 句子级 | Token 级 |
| 适用场景 | 多路召回融合 | 高价值语义理解 | Top-K 精排 | Top-K 重排 |

四者的定位很清楚：

- **RRF** 是零成本的融合手段，不需要训练也不需要调权重，适合作为默认起点；
- **RankLLM** 把「哪个文档更相关」交给大模型判断，理解力最强，成本也最高，适合高价值低并发场景；
- **Cross-Encoder** 把查询和候选拼成一个输入过一次模型，精度高但要为每个候选跑一次前向，通常只用于 Top-20 以内的精排；
- **ColBERT** 用「后期交互」折中：文档向量可以离线算好，查询时只做 token 级 MaxSim，兼顾精度与效率。

工程上的常见组合是三级：向量召回 50 条 → RRF 融合多路 → Cross-Encoder 精排前 10 条。

## 3. 压缩：只留有用的部分

召回块整体相关，但块内常有大段无关内容。直接塞进上下文既贵又降质。压缩有两种做法：

- **内容提取**：`LLMChainExtractor` 逐块抽取与查询相关的句子；
- **文档过滤**：`LLMChainFilter` 判断整块是否相关，不相关直接丢弃；`EmbeddingsFilter` 用相似度阈值快速过滤，成本最低。

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

compressor = LLMChainExtractor.from_llm(llm)
retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=vectorstore.as_retriever(search_kwargs={"k": 10}),
)
```

选型原则：延迟敏感用 `EmbeddingsFilter`；需要高质量回答且能接受额外调用时用 `LLMChainExtractor`；介于两者之间用 `LLMChainFilter`。

压缩的收益要算总账：多一次 LLM 调用换来更短上下文，最终成本可能更低，也可能更高，取决于块数量与上下文长度。

## 4. 自定义重排器

框架没有内置某个重排器时，扩展点很清晰：继承 `BaseDocumentCompressor`，实现 `compress_documents`。ColBERT 的 MaxSim 实现大致是这样：

```python
class ColBERTReranker(BaseDocumentCompressor):
    def compress_documents(self, documents, query, callbacks=None):
        query_emb = self.encode_text([query])
        doc_embs = self.encode_text([d.page_content for d in documents])
        scores = self.calculate_colbert_similarity(query_emb, doc_embs)
        ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)
        return [doc for doc, _ in ranked]
```

这段代码的价值不在实现本身，而在展示一个通用方法：**框架缺什么，先看它的抽象基类，再照着已有实现补一个**。给大模型提供基类源码 + 一个参考实现 + 明确目标，生成的代码准确率远高于只描述需求。

## 5. 格式化生成：为什么需要结构化输出

RAG 的答案常常要进入下游程序，而不是直接给人看：

- 电商客服要返回商品卡片列表（JSON）；
- 自然语言转 API 要产出请求参数（JSON）；
- 信息抽取要把事件、时间、地点写入数据库。

LangChain 的 `OutputParsers` 是第一种解法。`PydanticOutputParser` 把数据模型转成 JSON Schema 注入 prompt，再把模型返回的字符串解析并校验：

```python
class PersonInfo(BaseModel):
    name: str = Field(description="人物姓名")
    age: int = Field(description="人物年龄")
    skills: List[str] = Field(description="技能列表")

parser = PydanticOutputParser(pydantic_object=PersonInfo)
prompt = PromptTemplate(
    template="请根据以下文本提取信息。\n{format_instructions}\n{text}\n",
    partial_variables={"format_instructions": parser.get_format_instructions()},
)
chain = prompt | llm | parser
```

`Field` 里的 `description` 会直接变成给模型的指令，写法必须精确。校验失败会抛 `OutputParserException`，这就是结构化输出的第一道防线。

LlamaIndex 的思路一致，但会优先使用底层模型的 Function Calling 能力，不支持时才回退到把 JSON Schema 注入提示词。

## 6. Function Calling：更可靠的一条路

相比「在 prompt 里请求 JSON」，Function Calling 是模型原生支持的接口：

1. **定义工具**：用 JSON Schema 描述名称、功能与参数；
2. **用户提问**；
3. **模型决策**：返回 `tool_calls`，包含要调用的工具与参数；
4. **代码执行**：真正调用 API 或查询数据库；
5. **结果反馈**：把结果以 `role: tool` 的消息回传；
6. **最终生成**：模型结合工具结果给出自然语言回答。

```python
messages = [{"role": "user", "content": "杭州今天天气怎么样？"}]
message = send_messages(messages, tools=tools)

if message.tool_calls:
    tool_call = message.tool_calls[0]
    messages.append(message)
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": "24℃，晴朗",
    })
    final = send_messages(messages, tools=tools)
```

三个优势：可靠性高（原生结构化，不依赖文本解析）、带意图识别（模型自己选工具）、可对接外部世界（Agent 的基础）。

代价是模型与接口的绑定更强：换模型要确认工具调用格式兼容；工具描述写得含糊，模型就会选错工具或传错参数。

## 7. 组合顺序

一个实用的检索后处理顺序：

1. 多路召回 → RRF 融合，得到候选池；
2. Cross-Encoder 或 ColBERT 精排，截到 Top-10；
3. 按上下文预算做压缩；
4. 生成阶段用 Pydantic 约束或 Function Calling 保证结构。

每一步都要能单独评测：没有分步指标，就说不清收益来自融合、精排还是压缩。
