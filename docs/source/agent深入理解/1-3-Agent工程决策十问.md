## 1 Agent 工程决策十问：模型能力之外，拼的是工程判断

围绕 **Agent = LLM + 上下文 + 工具** 的核心公式，以及 Harness 工程在其外圈增加的约束、验证、纠正，本文解析十个 Agent 系统设计中的关键工程决策。每题按**问题 → 推理路线 → 结论**组织：先摆出决策场景，再展示一步步推导的过程，最后收束成一句可执行的工程判断。

### 1.1 能力取舍：只能加一样，加什么

**问题**：如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

**推理路线**：

1.  先拆解三要素的本质：LLM 是策略空间（大脑）、上下文是观察空间（眼睛）、工具是动作空间（手脚），对应强化学习三要素。
2.  三者构成串行链路：观察 → 决策 → 行动，任何一环缺失都会让全链路失效。所以"补哪一样"本质是**找最短板**，而不是比较三者谁更重要。
3.  默认答案偏向**补上下文**：模型能力由厂商持续迭代，工程师短期内改不动；而信息供给完全在工程侧掌控。上下文组件的消融实验也佐证——删除历史消息会让 Agent"失忆"、重复执行任务，观察侧的缺口最常见，也最容易被误判为"模型不行"。
4.  选择会改变的条件，恰好对应另外两个环节：**任务推理复杂度超出模型能力**（如多步数学推演），补观察无用，换更强模型；**动作空间缺手段**（如无法访问公司内部系统），决策再准也执行不了，加工具。
5.  怎么确认短板在哪？方法论就是**分析轨迹（trajectory）**：逐条失败轨迹归因——看错信息属于感知问题、选错方案属于决策问题、调用失败属于行动问题。

**结论**：优先补上下文（扩大观察空间），以失败轨迹分析定位瓶颈；当推理能力或动作手段成为瓶颈时，切换为换模型、加工具。

### 1.2 ReAct 循环的缓存读取成本

**问题**：ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

**推理路线**：

1.  二次增长源于 ReAct 的核心设计：**上下文累积性**——每轮推理都读取完整轨迹（Agent 上下文 = 静态前缀 + 轨迹）。
2.  把它写成数学：第 i 轮要读的前缀长度约与 i 成正比，n 轮累计读取量就是 1 + 2 + ... + n = **O(n²)**。先澄清：二次增长的是**累计缓存读取费用**，不是轨迹长度（线性）也不是 KV Cache 占用（同样线性）。
3.  这个 O(n²) 是"每轮读全量"换来的代价——它正是 Agent 能"记住做过什么"的原因，不能简单砍掉，只能改变增长阶或压低常数。
4.  缓解方向逐一检验：
    -   **批量压缩早期轨迹**：达到 token 阈值才动手，只保留结论与关键状态。为什么不能每轮压缩？KV Cache 的前缀不变原则给出答案——前缀任何改动都会导致缓存全部失效，每轮压缩等于每轮重建缓存，还额外引入压缩调用本身；
    -   **大块中间结果外置**：长文档、大结果不留在轨迹里，需要时检索按需拉回——本质是"用观察空间换存储"；
    -   **子 Agent 隔离**：把产生长轨迹的子任务派出去，主 Agent 只接收结论，主轨迹长度被压住。

**结论**：O(n²) 是 ReAct 累积性的固有代价，用"阈值触发批量压缩 + 结果外置检索 + 子 Agent 隔离"控制，切忌每轮压缩。

### 1.3 "模型即 Agent"与 Harness 工程为何共存

**问题**："模型即 Agent"范式意味着模型在工具调用决策上越来越自主。但 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

**推理路线**：

1.  两个判断看似相反：一边是后训练把工具调用内化为模型原生能力、不再依赖人工编排；另一边是外围工程被论证为核心竞争力。
2.  关键在看清**自主范围扩大改变了什么**——决策权从代码移向模型后，单次出错的影响面从"生成一句错话"升级为"执行一次错误操作"，可逆性骤降。
3.  由此得出共存逻辑：模型能力是"马力"，Harness 是"缰绳"。**马越强，缰绳不是多余，而是必需**——没有约束的高速能力反而更危险。
4.  用"内化迁移"视角统一两趋势（《苦涩的教训》的务实版本：模型内化一层，Harness 下移一层）：Harness 中补偿模型缺陷的部分（编排逻辑、调用格式补丁）会随模型进步被逐层内化、价值递减；而**模型无论如何内化都不该接手的部分**——真实世界的权限、不可逆操作的审批、跨会话的兜底恢复——构成 Harness 的持久价值。
5.  框架核心价值因此迁移：从"编排 LLM 调用"（正在被内化）转向 Harness 五要素中的保障层：**权限分类、熔断器、错误恢复、上下文压缩、工具生态**。

**结论**：两趋势在同一条时间线上互补——模型内化一层能力，Harness 就向保障层下移一层；框架的核心价值从编排能力转向保障能力。

### 1.4 无限循环的诱因与检测终止机制

**问题**：消融实验中"工具结果反馈"的缺失会导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？

**推理路线**：

1.  先理解这个实验现象的机理：ReAct 是"思考→行动→观察"闭环，工具结果缺失等于**观察环节断裂**——模型永远看不到"已经试过且失败"，在它的视角里这是第一次调用。
2.  把机理一般化：**任何破坏"观察→调整策略"链路的情况都会造成循环**。沿这个原则枚举生产场景：
    -   工具反复报同一错误 → 观察信号失真，模型学不到"别再试了"；
    -   模型幻觉调用不存在的工具 → 行动从未成功，观察永远为空；
    -   上下文压缩丢失关键状态 → 模型忘记自己做过什么（记忆断裂）；
    -   思考过程被剥离导致 API 报错 → 反馈通道本身故障；
    -   任务本身无解 → 观察再完整也收敛不到终点。
3.  机制设计直接套用 Harness 三层保障：**停止条件**（最大迭代次数）属于"约束"，前置划定边界；**重复检测**（相同工具 + 参数指纹）属于"验证"，识别执行偏差；**超过失败阈值转人工**属于"纠正"，异常闭环。

**结论**：循环的本质是观察链路断裂；防护 = 约束（停止条件）+ 验证（重复调用指纹检测）+ 纠正（阈值升级人工）。

### 1.5 用感知、行动、策略三维度分析 AI 产品

**问题**：感知、行动、策略是分析 Agent 产品的三个维度。选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理、有哪些改进空间？

**推理路线**：

1.  三维度是 RL 三要素的产品化翻译：感知 = 观察空间（能看到什么信息源），行动 = 动作空间（能改变什么、是否开放式），策略 = 执行循环模式（单轮、ReAct 迭代、还是人工预编排）。
2.  分析任意产品的操作路径：先列信息源清单（只读对话历史？还是能读代码库、屏幕、账户数据？），再看动作边界（只能生成文本，还是能执行代码、点击界面、发起交易？），最后看循环模式（一次输出还是多轮自我修正？）。
3.  评估合理性就是找**维度间的错配**：例如一个号称 Agent 的产品动作空间全开放、却没有任何验证反馈——按 1.4 推导的循环机理，这必然产生失控；反过来，感知很宽但动作受限是安全的渐进设计。成熟 Agent 的共性基准：开放动作空间、内部思考、基于反馈迭代。

**结论**：三维度分析法的本质是把产品放回"观察-决策-行动"链路找短板与错配，改进空间总出现在三者不匹配的那一环。

### 1.6 航班订票客服：工作流还是自主 Agent

**问题**：如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

**推理路线**：

1.  先明确两种编排模式的优劣——工作流：路径代码预定义、强流程管控、攻击面受限，但无变通能力；自主 Agent：动态规划、能处理预设外场景，但成本更高、需停止条件与沙盒测试。
2.  拆解订票业务的风险特征：含资金操作（不可逆）、有强制时序（付款前不能预订）、输入不可信（用户消息、邮件可能携带提示注入）、同时又存在大量开放环节（理解模糊需求、航班取消后的替代方案）。
3.  把特征逐项映射到模式优劣：**强制时序**正好是工作流的"确定性路径"所长——身份核实 → 搜索 → 付款 → 预订四节点，顺序由代码保证而非模型自觉；**攻击面**上工作流把提示注入的影响限制在单节点内，而全自主 Agent 的攻击面贯穿整条轨迹；**开放环节**则是工作流"无变通"的短板所在，必须交给自主模式。
4.  混合之后还要补最后一层：对大额付款、退款这类高风险节点，叠加人工干预机制中的"高风险操作强制审批"。

**结论**：主体工作流 + 开放环节局部自主 + 高风险节点人工确认。两种模式不是互斥选型题，而是同一系统内按"确定性需求"分配的比例——符合"从简单到复杂"的选型原则。

### 1.7 动态风险评估：从工具细化到"工具 + 参数"

**问题**：工具风险评级通常是按工具静态划分的。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

**推理路线**：

1.  基线方案是执行侧护栏的**工具风险评级**——按可逆性、权限、财务影响划分等级，高风险强制人工复核。
2.  静态评级有粒度问题：`delete_file` 删普通文件与删系统文件是同一工具、不同风险，若按工具整体评级为"中风险"，两头都错——要么误伤日常操作，要么放行灾难操作。
3.  修正方向：评级对象从"工具"细化为**"工具 + 参数"组合**，评级维度不变（可逆性、权限、影响面），但输入从静态注册表变为调用时的实际参数——删除是否可逆取决于目标路径，影响面大小取决于路径敏感度。
4.  下一个自然问题：谁来判？必须调用验证模块的**输入隔离原则**——安全校验只读结构化数据，不采信模型自由生成的文本。所以动态评估要用**基于规则的确定性检查**（路径黑白名单、正则匹配），而不是"让另一个 LLM 判断危不危险"——后者既引入新的注入面，又不可审计。
5.  还要防参数欺骗：参数值本身可能来自被注入的外部数据，因此校验只看结构化字段（路径字符串），不解释其语义。

**结论**：动态风险评估 = 评级粒度细化到参数 + 确定性规则判定 + 只信结构化数据，是"约束"（前置分级）与"验证"（调用时检查）两模块在工具层的合体。

### 1.8 受限动作空间的价值场景

**问题**：人们常把"开放式动作空间"当作 Agent 的标志特征。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

**推理路线**：

1.  先反问"开放式动作空间"的代价：动作空间每扩大一分，错误动作的可能性、攻击面、评估难度都同步扩大——开放是能力上限，也是风险上限。
2.  按场景的风险特征决定取舍：在**高合规、高风险、错误不可逆**的场景（退款金额、付款对象），一个错误动作无法回滚，此时"模型能做什么"远不如"模型能不被允许做什么"重要。
3.  受限动作空间在此类场景占优的逻辑：预定义选项本身就是"约束"模块的一种形态——而且是最干净的形态，因为它**让错误在结构上无法发生**，而不是发生后靠验证和纠正补救。这正是工具接口设计里**防呆（Poka-yoke）**原则的终极体现：约束优于检测，检测优于修复。
4.  注意受限的只是执行侧：模型内部思考、需求理解仍可完全开放，仅在最后一步"动作发射"时收敛到合法集合——思考自由、行动收敛。

**结论**：动作空间开放与否不是能力问题而是风险预算问题；错误不可逆的场景，受限选项天然防呆，优于事后护栏。

### 1.9 用户不在线时如何"优雅移交控制"

**问题**：人工干预机制要求 Agent 能"优雅地移交控制"。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

**推理路线**：

1.  人工干预通常有两类触发——超过失败阈值、高风险操作强制审批；但这个机制有个隐含假设：**人在**。用户不在线、响应慢、指令模糊，等于"移交"这个兜底通道本身失效，系统必须回答 Fail-safe 状态下默认做什么。
2.  默认值的选择套用约束模块的**故障安全默认值**原则（能力默认关闭、权限显式开启）：宁可停，不可猜——高风险操作未获确认时**暂停而非默认执行**，因为两种错误的代价不对称（暂停可恢复，误执行可能不可逆）。
3.  暂停不等于死等，按可逆性拆分任务：先完成**可逆的低风险部分**（查询、草稿、预订前的信息准备），把**高风险部分固化为待决文档**——这与长任务 Agent 的实践同构：初始化 Agent 与执行 Agent 之间靠"交接制品"续接状态，人和 Agent 都读同一份文档，决策与恢复解耦。
4.  通知与超时：用异步沟通工具（消息、邮件——工具五分类中的"用户沟通工具"正是为此存在）传递请求并设超时策略，超时后维持安全默认而非降级自动执行。
5.  指令模糊时，移交失败的原因在"理解"而非"授权"，应先澄清意图（追加一轮提问），而不是擅自猜测执行。

**结论**：优雅移交的底线是 Fail-safe——未确认不执行；配套手段是可逆部分先行、状态文档化、异步通知加超时、模糊先澄清。

### 1.10 会随模型进步而过时的工程手段

**问题**："好的设计原则应该穿越模型的迭代周期"，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

**推理路线**：

1.  先建立判别标准（来自"模型内化一层，Harness 下移一层"的演进观）：一个工程手段若是在**补偿当前模型的缺陷**，它会随模型进步贬值；若满足的是**系统级需求**（互操作、审计、权限、回滚），与模型能力无关，则持久有效。
2.  用标准检验四个典型例子：
    -   **约束采样强制工具调用格式**：补偿的是"模型易输出非法 JSON、遗漏参数"这一代际缺陷；模型格式遵循能力提高后收益递减。但高风险场景仍应保留确定性格式校验——这部分属于系统级需求，不随模型贬值。
    -   **外部知识库**：补偿"模型无法持续吸收新知识"。若持续学习能力可靠，部分知识会迁回参数；但实时更新、精确检索、权限控制、来源追溯是系统级需求，所以外部知识库**缩小适用范围而非消失**。
    -   **一切能力必须走标准工具调用接口**：Skills 已展示反例路径——文本描述能力 + 通用命令行执行，模型在通用执行器之上理解一种自定义文本调用协议。模型理解任意接口的能力越强，"必须标准格式"越不再是普遍原则，它退化为面向互操作与较弱模型的**场景性工程选择**。
    -   **提示词与工具定义固定在上下文开头**：源于早期模型指令遵循能力弱，位置稍偏就无法正确识别执行。Skills 按需把提示加载到上下文中间、动态工具发现把定义追加到轨迹之后，已在打破惯例；随针对动态加载的专门后训练普及，"必须放开头"同样退场——但它与 KV Cache 的静态前缀原则存在张力：前缀稳定性是成本问题而非能力问题，可能长期制约"随意动态插入"的实际采用节奏。
3.  归纳：判断"会不会过时"，本质是回答"这个手段在服务模型，还是在服务系统"。

**结论**：补偿模型缺陷型手段（格式约束采样、知识外置兜底、固定前缀位）会持续贬值；服务系统需求型价值（确定性校验、权限追溯、互操作格式）穿越模型周期——工程上应显式标注哪些设计属于前者，为它们预设"退役条件"。
