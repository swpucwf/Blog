## 1.Harness 工程：模型之外的竞争力

**Harness 工程是模型之外的核心竞争力**。基础 ReAct 机制的 Demo 存在明显缺陷：模型易产生幻觉、选错工具、故障无法自愈，Harness 工程用于补齐 Demo 与生产级产品之间的可靠性差距，保障 Agent 在生产环境稳定运行。

两套描述视角：基础公式`Agent = LLM + 上下文 + 工具`描述 Agent 内部组成；Harness 工程是工程实现视角，将 LLM 视作 Model，其余支撑代码统称为 Harness，不限于特定模型。 
生产环境扩展公式：
$$
Agent = Model + Harness = LLM + 上下文 + 工具 + 约束 + 验证 + 纠正
$$
最小 Demo 仅需 LLM、上下文、工具；
生产系统额外增加三层保障外壳：**约束划定行为边界、验证检查执行结果、纠正实现异常补救**。三层保障依附于上下文与工具，并非独立模块。
五大组成模块分工：上下文、工具赋予 Agent 做事能力；**约束、验证、纠正**保障 Agent 不做错事。
-   上下文：提供感知信息，属于核心基础能力
-   工具：提供行动手段，属于核心基础能力
-   约束：定义行为边界，搭建安全围栏
-   验证：自动校验操作结果正误
-   纠正：异常场景下重试、回退补救
行业重心变迁：早期 Agent 框架聚焦上下文与工具，优先实现 “能做事”；**生产级 Agent 重心转向约束、验证、纠正，目标做到 “可靠地做事”**。
以 Claude Code 为例，Harness 大部分代码都是保障机制，工具本身占比很小。 典型 Harness 保障组件：流程状态管理、多层上下文压缩、权限分级、**熔断器**、异常捕获与回滚恢复。马具隐喻：模型如同野马，Harness 作为马具，引导模型能力可控落地。行业正在从 “能做事” 迈向 “可靠地做事”，**Harness 工程构成 Agent 产品差异化竞争力**。

### 1.1 从提示工程到 Loop 工程：工程范式的演进
AI 应用工程范式呈现**层层递进、相互包含**的演进路线，依次为：**软件工程 → 提示工程 → 上下文工程 → Harness 工程 → Loop 工程**。 
- 软件工程是底层基础，包含传统系统架构、测试、部署能力；提示工程聚焦优化输入模型的自然语言指令，是第一波 AI 应用创新；上下文工程更进一步，系统性管理模型可见的全部信息，提示工程属于它的子集；
- Harness 工程将范围拓展到模型运行的整套系统，新增约束、校验、反馈、异常恢复等基础设施，上下文工程是其子集；**Loop 工程**为最新范式，关注跨轮次长期自主运行，负责任务发现、结果校验、任务终止判定，Harness 工程是它的子集。五层范式并非互相替代，上层范式向下包含下层，持续拓宽工程师的设计边界。
随着各大基础模型能力逐步趋同，**模型不再是决定性竞争要素，核心优势转移至模型之外的工程体系**。LangChain 的 Coding Agent 在 Terminal Bench 2.0 评测中，仅通过优化 Harness（增加结果自检、循环检测、优化思考策略），就将任务通过率从 52.8% 提升至 66.5%，排名大幅跃升；OpenAI 团队案例同样佐证，依托 Harness 工程实现开发效率大幅提升，效率提升的关键不在于模型本身，而在于外围工程体系。

### 1.2 Harness 五个功能的核心原则
Harness 包含五大功能模块，各自具备对应的核心设计原则，配套落地示例与对应章节，五个模块形成完整闭环：**上下文与工具支撑 Agent 决策，约束前置预防错误，验证识别执行偏差，纠正完成异常闭环**，任一环节缺失都会造成系统可靠性漏洞。

1.  **上下文**：遵循**信息充分性**原则，保证 Agent 在每一次决策节点拥有充足信息；实践包含系统提示词、知识库、Agent 状态、Sidecar 旁路查询。
2.  **工具**：遵循**接口清晰**原则，工具命名易懂、附带参数示例、明确边界范围；实践包含 MCP 工具、代码解释器、检索搜索工具。
3.  **约束**：遵循**故障安全默认值**原则，全部能力默认关闭，权限需要显式开启，类似 APP 权限管控；例如 Claude Code 工具执行默认需要用户授权。
4.  **验证**：遵循**输入隔离**原则，安全校验仅读取结构化数据，规避提示注入风险，不采信模型自由生成的文本；如 Linter 语法检查、类型校验、工具返回结果核验。
5.  **纠正**：遵循**未确认可恢复前不暴露中间态**原则，异常优先静默重试，不向用户展示半成品结果；包含静默重试、接续生成、熔断后转交人工。

在学习编排模式、安全护栏前，需要先确立 Agent 构建核心原则与模型选型策略，作为后续全部设计决策的底层基础。
![](https://i-blog.csdnimg.cn/direct/39f5650787db440db5c9ffccc6f9aa08.png)

### 1.3  构建有效 Agent 的核心原则
**构建有效 Agent 三大核心原则（来自 Anthropic 实践经验）**
1.  **保持简单**：优先最简方案，仅在必要时增加复杂度。优先原生 API 调用，少用重型框架；优先简洁代码，克制过度抽象。额外抽象层会增加调试盲区。
2.  **保持透明**：对外暴露 Agent 规划步骤、执行日志、决策轨迹。便于调试，同时建立用户信任；黑箱系统出现故障时难以定位、修复问题。
3.  **设计好工具接口 ACI（Agent-Computer Interface）**：站在 Agent 视角设计接口，而非传统程序员视角。命名、参数直观，内置**防呆（Poka-yoke）**设计，从源头规避误用。接口是模型和工具唯一通信通道，接口缺陷会被模型放大，引发系统性故障。

### 1.4  agent 模型选型

模型是 Agent 的智能基座，选对模型的收益通常高于单纯优化提示词。本节不指定具体模型版本，提供选型判断方向：

1.  **御三家闭源模型**：OpenAI GPT/o、Anthropic Claude、Google Gemini。Claude 擅长复杂推理、编程、工具调用；Gemini 优势为超长上下文、多模态，适配图文视频场景；GPT/o 综合能力均衡、用户基数大。**选型不要只看榜单，必须基于自身业务任务做实测评估**。
2.  **国内模型**：国内部署、预算约束场景优先考虑。豆包延迟低，适配实时交互；Kimi 的 Agent 能力突出；通义千问 Qwen、DeepSeek 等开源模型优势在于低成本、可定制。国内模型可通过火山引擎、硅基流动等 API 平台调用，海外模型可借助 OpenRouter 统一接入。不同模型工具调用能力差距明显，落地前必须场景测试。
3.  **开源 vs 闭源**：闭源模型综合能力更强，但成本高，受厂商 API 策略约束；开源模型成本可控、支持私有化部署与微调，适合数据合规、降本需求场景。
4.  **优先具备 Reasoning 思考能力的模型**：Agent 多步规划、工具选择依赖推理能力；仅单步极简任务、固定点位 GUI 点击等少数特例，才可使用无思考能力模型；多步动态决策场景，推理能力属于硬性要求。
5.  **容易忽略的两个指标**：**Token 输出速度**，多轮 ReAct 循环会累积延迟，直接影响端到端体验；**多模态能力**，图片 / 音视频理解场景为必备能力，模型间差距显著。
![](https://i-blog.csdnimg.cn/direct/6cce9c94395b41debbba96ff9ac30b38.png)


### 1.5 编排模式：工作流与自主
**编排模式**属于 Harness 中上下文与工具的组织方式，决定上下文流转、工具调度、执行路径是预设还是动态生成。落地遵循**从简单到复杂**原则：优先单次 LLM 调用；多步骤固定任务选用工作流；开放式、需要动态决策场景选用自主 Agent。自主 Agent 会带来更高延迟与成本，需要权衡收益。

**工作流模式（确定性编排）**：由代码预定义固定执行路径，LLM 仅在单个节点内做理解生成，节点流转顺序不可自主变更。

-   优势：强流程管控，强制业务时序规则；执行路径确定，攻击面受限，安全性高。
-   短板：缺少变通能力，无法处理预设外的突发场景，异常只能走预设分支或转交人工。

**自主 Agent（动态自主决策）**：执行路径由 Agent 依据环境反馈实时决定，底层依托 ReAct 循环。

-   特点：具备自主规划、识别失败、动态调整策略的能力；必须配置停止条件，防止死循环、过度执行。
-   适用场景：开放式、步骤不可提前预判的任务，例如代码修复 Agent、Computer Use、深度研究分析任务。
-   风险：成本更高，存在连锁复合错误；部署前需要沙盒充分测试，增加护栏、监控与人机校验节点。
![](https://i-blog.csdnimg.cn/direct/3b6e635561d4498495dbaef4c32a295f.png)


**两种模式选型与混合**：二者并非互斥，工程上常混合使用。高合规、强关键流程采用工作流保证可靠；需要灵活决策的模块启用自主 Agent。
![](https://i-blog.csdnimg.cn/direct/44a3e2cb09d6491cb8549e5da3dc4849.png)

框架选型趋势：随着模型即 Agent 发展，框架的核心价值不再只是编排调用，**Harness 工程（上下文管理、工具生态、安全约束、错误恢复）更加关键**。选型优先选择抽象薄、便于聚焦业务逻辑的框架。 编排模式解决了工具与上下文的串联问题，下一步需要依靠护栏，落地约束、验证、纠正机制，保障执行正确性与安全性。

### 1.6 护栏与安全性

护栏是 Harness 工程里**约束、验证、纠正**的核心落地手段，构建分层防线，管控隐私、声誉等风险；护栏需要组合使用，单一防护不足以保障安全，可随风险发现迭代新增防护规则。

#### 1.6.1 护栏三大类型

1.  **输入侧护栏**：请求进入 Agent 前拦截
    -   相关性分类器：过滤无关查询
    -   安全分类器：识别越狱、提示注入（越狱是用户绕过限制；提示注入是外部数据间接操控模型）
    -   内容审核：拦截暴力、歧视等有害内容
    -   基于规则保护：黑名单、长度限制、正则，抵御注入类威胁
2.  **执行侧护栏**：工具调用阶段校验
    -   核心为**工具风险评级**，按可逆性、权限、财务影响划分风险等级；高风险操作强制人工复核
3.  **输出侧护栏**：返回用户前校验结果
    -   PII 过滤器，防止个人敏感信息泄露
    -   输出内容校验，保证输出符合品牌规范

> 部分规则（正则过滤）可跨输入、输出侧复用

#### 1.6.2 人工干预

属于关键保护手段，在提升性能的同时保障安全，尤其适合系统上线早期，用于收集失败案例、完善评估体系。触发场景两类：

-   超过失败阈值：重试 / 操作次数达到上限，转交人工
-   高风险操作：敏感、不可逆动作（大额退款、取消订单等），强制人工审批

Anthropic 长任务 Agent 实践：拆分为初始化 Agent（环境初始化、任务拆解）+ 执行 Agent（增量执行、交接制品），依靠 Harness 解决长任务上下文耗尽、提前误报任务完成的问题。
