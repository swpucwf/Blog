## 1. 打地鼠困境

小明的「个人豆瓣」加了评分功能：用户可以打 1-5 星，页面显示均分。功能本身不复杂，很快就跑通了，他自己试了几遍没问题。

第二天朋友说搜索坏了——输入关键词点搜索，页面一片空白。他昨天只改了评分，压根没碰搜索；打开代码才发现，评分功能新加的数据查询函数改了一个公共数据库模块，搜索也依赖它，被「误伤」了。花半小时修好搜索，第二天详情页又打不开了（修搜索时不小心改了路由配置）；修好详情页，晚上一测评分又坏了。

三天三个 bug，每个都是修前一个时引入的——他在打地鼠：锤下去一个，旁边又冒出一个。

需要的不是更快的反应速度，而是一张**安全网**：每次改完代码，有东西自动把功能都检查一遍——搜索还能用吗？详情页还能打开吗？评分正常吗？哪个坏了立刻告诉你，不用等朋友来报 bug。

## 2. 为什么需要测试

### 2.1 回归测试：以前能用的，现在还灵吗

功能之间并不完全独立：共享数据库连接、公共工具函数、路由配置。改了评分时改了 `db.query()` 的默认排序参数，觉得只影响评分，搜索结果的排序却被意外改变。「改了 A 坏了 B」在代码库变大后会越来越频繁，因为依赖链越来越复杂，很难在脑子里追踪所有影响。

**回归测试**就是一组自动化检查，每个检查对应一个功能点：搜索「科幻」能返回结果吗？打 4 星能成功吗？未登录访问评分接口会被拒绝吗？写成代码存在项目里，每次改完跑一遍——全绿说明没有误伤，某个失败说明刚才改坏了什么。

手动点一遍并不慢，十来个功能几分钟能过完，还有独特价值：能发现自动化覆盖不到的体验问题（按钮点击区域太小、加载闪了一下、文案奇怪）。真正让人扛不住的不是慢，而是**重复**：一天改三次就要点三遍，而且每次都要记住上次点了哪些场景。第一遍认真，第二遍走马观花，第三遍可能跳过「觉得不会出问题」的部分——而 bug 往往就藏在那里。人还会做「我只改了评分，搜索肯定没事」的判断，大部分时候对，偶尔错，错的那次就是 bug；机器不会做这种聪明判断。

自动化测试还是**活的文档**：三个月后回来看代码，记不清评分接口该返回什么格式，但测试里写得清清楚楚（`expect(res.body.averageRating).toBeCloseTo(4.0)`）。注释可能过时，测试过时会直接报红。

### 2.2 测试金字塔

| 层级 | 测什么 | 成本 | 稳定性 | 数量 |
|---|---|---|---|---|
| 单元测试 | 最小代码单元（一个函数） | 几毫秒，无需外部依赖 | 极稳 | 最多 |
| 集成/API 测试 | 模块协作（HTTP → 校验 → 数据库） | 中等，需要服务器与数据库 | 较稳 | 适量 |
| E2E 测试 | 用户完整操作流程 | 几秒到十几秒，启动真实浏览器 | 最脆弱 | 最少 |

以评分功能为例：`calculateAverageRating` 接收评分数组返回均分，直接调用看返回值——几毫秒，这就是单元测试，价值在**精确定位**（失败立刻知道是这个函数，不用猜数据库/网络/浏览器）。`POST /api/movies/42/rate` 需要启动服务器、连数据库、发请求、再查库确认——测的是路由解析、请求校验、数据库操作、响应格式化串起来能不能工作，这是集成测试。

集成测试能发现单元测试发现不了的问题：函数本身没问题，但 API 路由把字符串 `"4"` 传进去忘了转数字——单元测试只看函数，发现不了「接缝」处的问题。

再往上：打开浏览器、登录、找电影、点星星、提交、看均分是否更新——E2E 最接近真实体验，但最慢、最脆弱（按钮换位置、加载慢、弹窗挡住都可能失败）。三层像体检：验血快速便宜（单元），B 超检查器官配合（集成），全身 CT 最全面但贵、耗时（E2E），不会每次感冒都做 CT。

**为什么不全部用 E2E**：成本差距巨大。50 个场景全用单元测试不到 1 秒，全用 E2E 可能 5 分钟；UI 改一个按钮位置，相关 E2E 都要改，单元和集成不受影响。金字塔不是教条，而是经济学：用最低成本获得最高信心。

判断标准：**如果这个逻辑不依赖 UI 就能验证，就不要用 E2E**。评分计算对不对 → 单元；接口返回数据对不对 → 集成；用户点按钮能不能完成操作 → 才需要 E2E。

### 2.3 什么时候引入自动化

自动化测试是一笔投资，写和维护都要时间。回报明显的信号：

- 应用有 5 个以上页面；
- 核心业务流程超过 3 步；
- 已经遇到过「修 A 坏 B」；
- **开始害怕改代码**——知道某段代码烂却不敢重构，怕改坏，这是代码腐化的开始。

不该上的时候：还在疯狂改需求的原型阶段（今天评分明天可能砍掉）、一次性项目、纯静态展示页。

**不要为覆盖率而写测试**。覆盖率只告诉你「哪些代码被执行过」，不告诉你「有没有验证正确行为」——你可以调用所有函数但不断言，覆盖率 100% 却什么都没测到。关注测试的**价值**（能不能发现真正的 bug），而不是数字。

**先测什么**：先测核心业务逻辑（评分计算、搜索排序），再测 API（数据进出的大门），最后才考虑 E2E。用 20% 的测试覆盖 80% 的风险。判断方法：问「如果这个功能坏了，后果有多严重？」评分错了很严重，排序方式变了不太严重，404 页面歪了无所谓。

### 2.4 AI 辅助测试的正确姿势

业务代码的需求写在 PRD 或描述里，AI 能直接理解；但测试的价值取决于「测的是不是关键场景」，这需要对业务的理解。Claude Code 会读代码库，已实现的逻辑它都能看到并测到；但一个**还没写进代码的业务规则**（比如「同一用户重复评分应更新旧评分而不是新增」），AI 不会想到要测。

正确分工：**你把控测试策略，AI 执行和补充**。可以让 AI 先分析代码库、建议优先级（它对结构理解往往更全面），但「这个场景值不值得测」「这个边界重不重要」的判断权在人手里。审查生成结果时看两件事：**覆盖度**（正常、校验、权限、边界四类都覆盖了吗，尤其业务特有边界）、**真实性**（数据是否贴近真实——全英文、全正整数可能漏掉中文输入、特殊字符、浮点精度问题）。

```text
阅读我的项目代码，分析哪些模块最需要测试。
列出建议的测试优先级：哪些先写单元测试，哪些需要集成测试，哪些需要 E2E。
```

## 3. API 测试与 E2E 测试

### 3.1 为什么先测 API

评分页面报「提交失败」，可能是前端按钮没正确调接口、接口返回错误数据、或数据库写入失败。没有 API 测试，每次调试都要打开浏览器、登录、找电影、点评分、看结果才能判断问题在哪；有 API 测试，直接发一个请求看返回值——返回 200 和正确数据说明问题在前端，返回 500 说明在后端。**API 测试能把问题定位到「前端还是后端」这一层。**

另一个原因是 **API 比 UI 稳定**：按钮换位置、改样式、加动画都可能让依赖 UI 的测试失败；而「发这个请求返回这个数据」的契约不会因为按钮变色而改变。像检查汽车：单独测发动机（API）快、稳、易定位；开上路跑一圈（E2E）全面但耗时，路况天气都影响结果，大部分问题在发动机阶段就能发现。

### 3.2 一个接口至少测四类场景

| 场景 | 示例 |
|---|---|
| **正常路径** | 已登录用户提交 1-5 的整数，返回 200 和正确均分 |
| **参数校验** | 提交 0 或 6、提交字符串 `"abc"`，返回 400 |
| **权限控制** | 未登录提交，返回 401 |
| **边界情况** | 重复评分应更新还是拒绝；电影 ID 不存在返回 404 |

这不是教条，而是思维方式：正常情况能用吗？错误输入会被拦住吗？没权限的人能访问吗？有没有我知道但 AI 不知道的特殊情况？

```text
阅读 app/api 文件夹下的所有路由，为每个 API 生成 Vitest 测试。
每个接口覆盖：正常请求（200）、参数错误（400）、未授权（401）。
```

怎么验证测试真的在「测东西」？在业务代码里故意引入一个 bug（把评分范围从 1-5 改成 1-10），再跑测试——如果没报红，说明它没真正验证这个约束。这种方法叫**变异测试**，是检验测试质量的好手段。

### 3.3 E2E：API 过了，用户还是用不了

API 测试全过，朋友反馈「点评分按钮没反应」。查下来 API 本身没问题，直接请求能正常返回——问题在前端：重构组件时把提交逻辑移到另一个文件，忘了在新组件引入。TypeScript 编译不报错（函数签名对，只是没被调用），页面也正常渲染（按钮在，点了没反应）。API 测试绕过了前端，测不到这个问题。

**E2E 测的是用户的完整体验**：从打开页面、点击、到看到结果；不关心「API 能不能用」，只关心「用户能不能完成想做的事」。

**Playwright** 是最主流的 E2E 工具（微软开源），自动打开 Chrome/Firefox/Safari，模拟点击、输入、滚动，还能截图录屏。可以理解为一个「机器人用户」按脚本操作并检查结果。它还有**录制模式**：`npx playwright codegen http://localhost:3000`，在浏览器里点哪里、输入什么，自动生成测试代码，作为起点比从零写快得多。

```typescript
test('用户给电影打分', async ({ page }) => {
  await page.goto('/login')
  await page.fill('[name="email"]', 'ming@example.com')
  await page.fill('[name="password"]', 'password123')
  await page.click('button[type="submit"]')
  await page.waitForURL('/')

  await page.click('text=星际穿越')
  await page.waitForURL('/movies/**')

  await page.click('[data-testid="star-4"]')
  await page.click('[data-testid="submit-rating"]')
  await expect(page.locator('.average-rating')).toContainText('4')
})
```

`waitForURL` 是**显式等待**：等页面跳转完成再继续；不等的话脚本可能在页面没加载完就找元素，找不到就报错。

### 3.4 Flaky 测试

同一个测试跑三次：通过、通过、失败——同样的代码和环境，结果不一样。这就是 **Flaky**（有时通过有时失败），是 E2E 最头疼的问题。

| 原因 | 表现 | 解决 |
|---|---|---|
| 异步时序 | 点提交后立刻断言，请求还没返回 | 显式等待（`waitForSelector`、`expect(...).toContainText`） |
| 数据竞争 | 测试 A 留下评分影响测试 B | 数据隔离：每个测试自备数据、结束清理 |
| 环境差异 | 本地够用的等待在 CI 上不够 | 合理超时，不假设瞬间完成 |

Flaky 不能忽略——「偶尔失败」意味着永远不确定结果是否可信；安全网上有个洞，就不敢信任它。判断是 Flaky 还是真 bug：**连续跑 5 次**（`--repeat-each=5`），5 次都失败大概率真 bug，时过时不过就是 Flaky。

修 Flaky 的核心原则：**不要用 `sleep` 等一等**。`waitForTimeout(2000)` 只是把问题藏起来——本地够用 CI 可能不够，今天够用数据量大了可能不够。正确做法是**条件等待**：条件满足的瞬间继续，既不等太久也不等太短。

```text
这个 E2E 测试有时候通过有时候失败，帮我分析原因并修复。
错误信息是：[粘贴错误日志]
```

### 3.5 测试失败三步定位

1. **看错误类型**：`Timeout waiting for selector` 是等待超时（页面没加载完、`data-testid` 改了、前面登录失败）；`Expected "4.0" but received "3.5"` 是断言失败（逻辑有 bug 或测试数据被污染）；`ERR_CONNECTION_REFUSED` 是网络错误（后端没启动或端口不对）；
2. **看截图**：Playwright 失败时自动保存在 `test-results/`——停在登录页说明登录失败，显示错误提示说明 API 报错，页面空白说明前端渲染崩了。一张截图往往就能定位；
3. **看网络请求**：配置 `trace: 'on-first-retry'`、`screenshot: 'only-on-failure'`，用 `npx playwright show-trace` 回放，看评分请求返回 200 还是 500——500 在后端，200 但页面没更新在前端渲染。

### 3.6 API 与 E2E 怎么分工

- **API 测试覆盖「数据对不对」**：状态码、数据格式、业务逻辑，大部分核心逻辑都能在这里验证，快、稳、维护成本低；
- **E2E 覆盖「用户能不能用」**：只用在最关键流程（注册登录、核心业务、支付），不要每个页面都写，维护成本会爆炸。

「E2E 更真实所以更好」是误区——真实不等于更好。评分页改一次布局，相关 E2E 都要更新选择器，API 测试完全不受影响；如果维护 E2E 的时间比写新功能还多，说明写太多了，把逻辑下沉到 API 层。

判断标准：**只有 E2E 能发现的 bug（按钮没绑事件、跳转错误）才用 E2E；API 能发现（返回错误数据、权限没校验）就用 API**。能用轻量方式验证的，不要用更重的方式。

## 4. 自动化工作流

### 4.1 有了测试，但忘了跑

小明花一下午写完测试全绿，然后继续开发新功能，每次都想「等会儿跑一下」，每次都被下一个功能吸引过去。三天后推代码，朋友一跑两个测试挂了——是第一天的 bug。拖了三天、中间改了一堆代码，现在要从三天改动里找出是哪次提交引入的，排查成本翻了几倍。

**bug 发现得越晚，修复成本越高。** 自动化测试的核心价值不是「帮你找 bug」，而是**帮你尽早找到 bug**，在修复成本最低的时候。人会忘，机器不会。

### 4.2 Git Hooks：提交前自动检查

`pre-commit` hook 在每次 `git commit` 前自动运行，脚本失败（非零退出码）就阻止提交。像门禁系统：刷卡进门自动检查权限，不用自己记住「要检查」。这种心理效果比技术效果更重要——不需要「记住」跑测试，提交动作本身就触发测试。

用 **Husky** 管理 hooks：

```bash
pnpm add -D husky
npx husky init
# .husky/pre-commit 内容：pnpm test
```

局限：只在本地运行，`git commit --no-verify` 可以跳过；不同人本地环境也可能不同。所以它是第一道防线，不是唯一防线。合理跳过 `--no-verify` 的场景：WIP 提交、纯文档改动、hook 检查内容与本次改动无关；关键是**有意识地跳过**——如果经常跳过，说明 hook 配得太重（每次跑全量测试），应该优化 hook 而不是绕过它。

### 4.3 GitHub Actions：推送后自动验证

代码推到 GitHub 后，Actions 在全新的干净虚拟机上自动跑测试——这是第二道防线，本地跳过了 hook，CI 会拦住。像工厂质检流水线：工人可能偷懒跳过自检，检测仪不会放过。

它的价值不只是「再跑一遍」，而是在干净环境从零开始——安装依赖、构建、测试。能发现「在我电脑上能跑」的问题：本地有环境变量但没加到 `.env.example`、本地缓存了旧构建产物导致测试意外通过、本地装了全局工具但 `package.json` 没声明。

```yaml
name: Test
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - uses: pnpm/action-setup@v4
      - run: pnpm install
      - run: pnpm test
```

两道防线配合：Hooks 本地快速拦截（几秒），CI 远端全面验证（几分钟）。CI 失败但本地通过时，先看日志——常见原因是环境变量没配（在仓库 Settings → Secrets 配置）、CI 没有本地数据库实例、时区差异（CI 默认 UTC）。这些是环境问题而非代码问题。

### 4.3 TDD：先想清楚再动手

要给「电影短评」加功能：内容最多 500 字。先写测试——想清楚接口接收什么、返回什么：`POST /api/movies/42/reviews` 收 `{ content }` 返回 201；未登录 401；内容为空 400；超过 500 字 400。测试当然全部失败（接口还不存在），然后把测试文件交给 Claude Code：「这是我写好的测试文件，帮我实现对应的 API，让所有测试通过。」

写完会发现，因为先想清楚了接口设计，代码写起来特别顺畅——不用边写边改接口。**测试文件本身就是接口规格说明**：精确描述行为，比口头描述或文档更准确，因为它是可执行的。

**TDD 三步**：Red（写测试，失败）→ Green（写最少代码让测试通过）→ Refactor（重构，保持通过）。「最少代码」防止过度设计——不需要一开始考虑「以后支持半星怎么办」，需求变了先改测试再改代码。

适合：核心业务逻辑（评分计算、权限判断）、需要稳定接口的模块、复杂条件分支。不适合：UI 样式调整、探索性原型、一次性脚本。

TDD 与 AI 配合特别好：传统痛点「写测试费时间」，现在可以用自然语言描述行为让 AI 生成测试代码——工作从「写测试」变成「设计接口」，测试文件成了人与 AI 之间的**契约**：你定义行为，AI 实现行为，测试验证行为。

## 5. 从打地鼠到安全网

一个月前小明改代码心惊胆战，朋友 bug 报告是唯一反馈，而且总是迟到。现在核心接口有 API 测试、关键流程有 E2E；每次 commit Husky 自动跑，推到 GitHub Actions 再跑；红了当场知道是哪次改动引入的问题。

**测试不是负担，是敢改代码的底气**。没有测试不敢重构；有了测试可以大胆重构——改完跑一遍，绿了就没问题。信心转变是渐进的：第一次看到测试拦住一个 bug，就会理解它的价值不是理论上的。

测试是逐步积累的：先给最容易出问题的接口写，再加核心流程 E2E，然后配 Hooks 和 CI。每次修完 bug 顺手加一个测试，确保同样的 bug 不再出现——这叫**bug 驱动测试**：不预测所有 bug，而是被咬一口补一个防护，安全网越织越密。

不需要追求完美覆盖率，80% 的风险可以用 20% 的测试覆盖。重要的是**开始**——哪怕只有一个测试，也比零个强。

## 6. 本篇验收

- [ ] 能解释回归测试要解决什么问题；
- [ ] 能按测试金字塔判断一个功能该写哪一层测试；
- [ ] 知道何时该引入自动化测试、何时不该；
- [ ] 能按「正常、校验、权限、边界」四类场景设计 API 测试；
- [ ] 会审查 AI 生成的测试（覆盖度 + 真实性）；
- [ ] 能解释 Flaky 的三类原因并用条件等待修复；
- [ ] 掌握「错误信息 → 截图 → 网络请求」三步定位；
- [ ] 能配置 Husky 与 GitHub Actions 两道防线；
- [ ] 理解 TDD 的 Red-Green-Refactor 与适用边界。

> **补记**：这一章的核心不是「测试覆盖率」，而是**反馈速度**——bug 发现得越晚，修复成本越高。三层测试是成本与信心的经济学：能用单元验证的不用集成，能用 API 验证的不用 E2E。真正让测试持续起作用的，是两道自动化防线（Hooks + CI）和「修完 bug 顺手补测试」的习惯。
