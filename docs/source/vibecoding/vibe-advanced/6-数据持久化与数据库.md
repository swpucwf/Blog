## 1. 数据是所有业务的基石

界面搭得有模有样之后，很快会遇到一个尴尬问题：刷新网页，刚才填的表单、生成的对话全都不见了。原因是浏览器里的数据默认只存在临时内存中，想要关闭或刷新后依然存在，就需要**数据持久化**。

先记住一条底线：**前端代码丢了可以重写，UI 丑了可以换皮，但数据库里的用户数据丢了、乱了，产品就彻底完了**。这也是后端开发往往比前端更严谨的原因——守护的是产品的灵魂。

## 2. 存储演进：CSV → JSON → 数据库

小明是个重度影迷，想做一个「个人豆瓣」记录观影。这段经历几乎就是数据存储的演进史。

### 2.1 CSV / Excel：能用，但很快不够

一开始用 Excel：电影名、导演、评分、标签、年份、短评。前 20 部很轻松，记到 200 多部时问题接连出现：

| 问题 | 表现 | 本质 |
|---|---|---|
| 多标签存不下 | 标签只能写「科幻/灾难/国产」，查「所有科幻片」容易漏 | 每个格子只能放一个值 |
| 数据不一致 | 同一导演写成「郭帆 / 郭帆导演 / 郭凡」，统计时只算到一部 | 没有校验机制 |
| 关联放不下 | 一部电影十几个演员、一个演员几十部电影，多对多装不进一张表 | 无法表达关系 |
| 多人协作灾难 | 两人同时编辑，覆盖或冲突 | 没有并发控制 |

CSV 适合一次性数据分析、简单配置清单、几十行小数据；数据量上去、关系变复杂、需要多人协作时，就该换方案。

### 2.2 JSON 文件：灵活但撑不住业务

JSON 支持嵌套与数组，「一部电影多个标签」轻松解决：

```json
{
  "movies": [
    {
      "id": 1,
      "title": "流浪地球",
      "director": "郭帆",
      "rating": 7.9,
      "tags": ["科幻", "灾难", "国产"],
      "actors": ["吴京", "屈楚萧", "李光洁"]
    }
  ]
}
```

但做成 Web 应用后，新问题又来了：

- **查询效率低**：查「评分 8 分以上的科幻片」要读入整个文件逐条遍历，几万条时页面明显变慢；数据库有索引可直接定位；
- **没有数据约束**：评分写成「很高」、演员 ID 指向不存在的人，文件不会报错，数据悄悄脏掉；
- **并发写入丢数据**：两个请求同时读、各自改、各自写回，后写的覆盖先写的（竞态条件）；数据库用事务与锁解决；
- **关联查询痛苦**：查「吴京演过的电影平均分」要遍历所有电影再算；数据库有 JOIN，一条语句完成且内部优化。

JSON 适合配置文件（`package.json`、`tsconfig.json`）、API 传输格式、少量静态数据，但作为业务数据持久化撑不住。

### 2.3 数据库：专业的事交给专业工具

小明用 PostgreSQL 把数据拆成 `movies`、`directors`、`actors`、`movie_actors`、`tags`、`movie_tags` 几张表。为什么拆？因为一张大表意味着大量冗余——「吴京」出现在 20 部电影里就要重复存 20 遍，改一处要改 20 个地方，漏改就数据不一致。拆表后用 ID 引用，改一处全部生效。

**关系型数据库的核心思想：通过拆表和关联，消除数据冗余，保证数据一致性。**

一条 SQL 就能查「吴京演过的所有 8 分以上电影」：

```sql
SELECT m.title, m.rating
FROM movies m
JOIN movie_actors ma ON m.id = ma.movie_id
JOIN actors a ON ma.actor_id = a.id
WHERE a.name = '吴京' AND m.rating >= 8.0
```

不需要看懂语法（AI 会写），但要知道它在做什么：从三张表通过 ID 关联，找出符合条件的数据。几百万条数据也能毫秒级返回，因为数据库会自动用索引优化。

### 2.4 什么时候该升级

| 信号 | 该用什么 |
|---|---|
| 数据不到 100 条、结构简单 | CSV / JSON 文件 |
| 数据之间有关联关系（用户 → 订单 → 商品） | 关系型数据库 |
| 需要多人同时读写 | 数据库 |
| 需要保证数据正确性（金额、库存） | 数据库（带约束） |
| 数据量超过几千条 | 数据库（带索引） |
| 需要统计、排序、分组、关联 | 数据库（SQL） |

一个简单判断标准：**如果应用有「用户」的概念，就该用数据库了**——有用户就有登录、会话、权限、角色，这些关联只有数据库能优雅处理。反过来，纯静态网站、不需要登录的工具页、纯前端计算器，用 `localStorage` 或写死数据就够了。

**常见连接问题**：

| 报错 | 原因 | 解决 |
|---|---|---|
| `Invalid URL` | 连接字符串格式错误 | 检查空格、引号匹配 |
| `password authentication failed` | 密码错误 | 平台重置密码，更新 `.env` |
| `connection refused` | 网络不通 | 检查是否需要 `?sslmode=require` |
| `too many connections` | 连接数超限 | 使用连接池（Pooler）地址 |

**连接池**：每个连接消耗 1-3 MB 内存且有上限；每次请求新建连接、用完断开，很快就耗尽。连接池预先建好一批连接，应用借一个、用完还回去复用——100 个并发用户可能只需要 10 个连接。Neon 和 Supabase 都提供连接池地址（Supabase 直连 5432、连接池 6543），**生产环境务必用连接池地址**。

配置到项目：根目录 `.env` 写 `DATABASE_URL`，确认 `.gitignore` 含 `.env`，再告诉 AI「项目已配置好 DATABASE_URL，请用 Drizzle ORM 初始化数据库连接」。

## 4. 核心概念：表、主键、外键与关系

### 4.1 表：比 Excel 强大一百倍

| Excel | 数据库 | 说明 |
|---|---|---|
| 工作表 Sheet | 表 Table | 一类数据一张表，如 `users` |
| 一行数据 | 行 Row | 一个具体用户、一笔订单 |
| 表头列名 | 列 Column | 数据属性，如 `phone`、`address` |

数据库真正的价值在差异：**类型严格**（`integer` 列写文字直接报错）、**约束机制**（UNIQUE、NOT NULL、FOREIGN KEY，违规写不进去）、**表间关联**（JOIN 一次查出关联数据）、**并发安全**（事务与锁保证 100 人同时下单不互相覆盖）。

### 4.2 主键：每行数据的身份证

规则三条：唯一、不能为空、不可变。通常用 `id`，现代 PostgreSQL 推荐 `bigint generated always as identity`：

```sql
CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  phone text   NOT NULL
);
```

手机号虽然唯一，但有业务含义（用户会换号），一旦被其他表引用，改主键牵一发动全身。**最佳实践是用无业务含义的自增 ID 当主键。**

### 4.3 外键：表与表之间的线索

外键是一张表里指向另一张表主键的列，作用是建立关联并保证引用的数据真实存在：

```sql
CREATE TABLE orders (
  id       serial PRIMARY KEY,
  user_id  integer REFERENCES users(id),
  amount   real    NOT NULL,
  status   text    DEFAULT '待支付'
);
```

三个好处：**保证一致性**（不能给不存在的用户建订单）、**建立关联**（从订单追溯到用户，从用户查到所有订单）、**级联操作**（删除用户时自动删订单或阻止删除，建表时配置）。

> **PostgreSQL 不会自动给外键列建索引**。10 万行的 `orders` 查「某用户的订单」时，没有索引会全表扫描，慢 100 倍以上——每个外键列都要手动加索引。

### 4.4 三种关系

**一对多（1:N）最常见**：一个用户多个订单，每个订单只属于一个用户。在「多」的一方加外键（`orders.user_id`）。判断方法：一个 A 可以有多个 B 吗？一个 B 只属于一个 A 吗？两个都是「是」就是一对多。

**多对多（M:N）需要中间表**：一个订单多道菜，一道菜出现在多个订单里。中间表把多对多拆成两个一对多：`order_items`（`order_id`、`dish_id`、`quantity`）。中间表还能存关系本身的属性，比如数量、成绩、打标时间。

**一对一（1:1）用于拆分大表**：`users` 表 50 万用户，每次登录都查，如果塞满头像、简介、偏好等不常用字段，表会变「重」。把不常用字段拆到 `profiles`，并用 `user_id UNIQUE` 保证一对一——没有 UNIQUE 就变成一对多了。

### 4.5 约束与数据类型

| 约束 | 作用 | 生活类比 |
|---|---|---|
| PRIMARY KEY | 唯一标识每行 | 身份证号 |
| FOREIGN KEY | 确保引用的数据存在 | 快递收件人必须是真人 |
| NOT NULL | 不允许为空 | 必填项 |
| UNIQUE | 不允许重复 | 手机号不能重复注册 |
| CHECK | 自定义条件 | 年龄大于 0、评分 1-5 |
| DEFAULT | 未填时自动填入 | 订单状态默认「待支付」 |

为什么代码里校验了还要数据库约束？三个原因：代码可能有 bug，约束是最后防线；数据入口不止一个（API、后台、迁移脚本、定时任务），约束定义一次全部受保护；脏数据清理成本极高。**预防永远比治疗便宜。**

常用类型：`bigint/serial`（主键）、`text`（任意文本，永远不要用 `varchar(n)`）、`integer`、`boolean`、`timestamptz`（带时区，不要用 `timestamp`）、`jsonb`（可建 GIN 索引）、`numeric(10,2)`（金额必须用，不要用 `real`）、`uuid`。

三个常见陷阱：① 金额用浮点数有精度问题（0.1+0.2≠0.3）；② 不带时区的时间戳在不同服务器上产生歧义；③ PostgreSQL 里 `text` 与 `varchar` 性能完全一样，`varchar(n)` 只是多了长度限制。

**SQLite vs PostgreSQL**：SQLite 是文件型数据库，零配置、单写多读，适合本地开发与原型；PostgreSQL 是完整数据库服务器，高并发、类型丰富、`jsonb` 强大，适合生产。Drizzle ORM 支持两者无缝切换。

**让 AI 设计表结构**：

```text
我要做一个 [应用描述]，请帮我设计数据库表结构。
要求：
1. 使用 PostgreSQL + Drizzle ORM
2. 列出所有表、字段、类型、约束
3. 标注表之间的关系（一对多/多对多）
4. 每张表都要有 id、created_at、updated_at
5. 用中文注释解释每个字段的用途
```

## 5. 操作数据库：ORM、CRUD 与事务

### 5.1 ORM 是翻译官

**ORM（对象关系映射）** 让你用 TypeScript 操作数据库，不用手写 SQL。你写 `db.insert(users).values({ phone: '138xxxx', name: '小红' })`，ORM 翻译成 `INSERT INTO users ...` 发给数据库。

直接写 SQL 的痛点：字符串拼接容易出错、没有类型检查（写错列名运行时才发现）、不同数据库语法有差异；对 Vibe Coder 来说最大的问题是复杂 SQL 很难一眼审查。ORM 把表映射成对象、把操作映射成函数调用：列名自动补全、类型检查、写错编辑器报红，代码可读性也更好。

推荐 **Drizzle ORM**：语法贴近 SQL、TypeScript 类型安全、同时支持 PostgreSQL 与 SQLite、社区活跃。另一个选择 **Prisma** 用自己的 Schema 语言，语法简洁但离 SQL 更远。选一个坚持用即可——概念通用，工具可换。

### 5.2 CRUD：四个基本动作

| 操作 | 含义 | 外卖平台例子 |
|---|---|---|
| Create | 插入新数据 | 用户注册、下单 |
| Read | 查询数据 | 浏览菜单、查看订单 |
| Update | 修改数据 | 改地址、更新订单状态 |
| Delete | 删除数据 | 取消订单、注销账号 |

大部分 Web 应用 80% 的功能都是 CRUD。注意：实际项目很少真删数据，更常见的是**软删除**——加 `deleted_at` 字段，标记删除但数据还在，删错能恢复、也方便数据分析。

### 5.3 审查 AI 生成的 CRUD

不需要自己写，但要知道怎么审查：

| 操作 | 审查要点 |
|---|---|
| Create | 必填字段都传了吗？有输入校验吗？唯一冲突有错误处理吗？ |
| Read | 查询条件对吗？需要关联查询吗？有分页/排序吗？有没有 N+1？ |
| Update | WHERE 条件对吗？只更新需要的字段吗？更新 `updated_at` 了吗？ |
| Delete | 真删还是软删？WHERE 条件对吗？关联数据怎么处理？ |

> **WHERE 条件是生命线**。Update / Delete 忘了 WHERE 会影响整张表——想改一个人的地址，结果所有用户地址都被改掉。审查时看到 UPDATE/DELETE，第一件事就是检查 WHERE。

### 5.4 三个性能陷阱

**N+1 查询**：先查所有用户（1 次），再对每个用户查订单（N 次）——100 个用户就是 101 次查询。开发环境几乎感觉不到，生产环境每次查询 1-5ms，页面加载轻松破几秒。正确做法是 JOIN 或批量查询。看到「循环里套着数据库查询」基本就是 N+1。

**分页越翻越慢**：`OFFSET 1000 LIMIT 20` 要先扫描前 1000 行再取 20 行，页数越深越慢。更好的方式是**游标分页**：记住上一页最后一条的 ID，下一页从该 ID 之后取，无论翻到第几页速度一致。

**先查再改的并发陷阱**：用户连点两次保存，两个请求都查到「设置不存在」，都去插入，第二个因唯一约束冲突报错。数据库用 **UPSERT**（`INSERT ... ON CONFLICT DO UPDATE`）原子完成「有就更新、没有就插入」。看到「先 SELECT 再决定 INSERT/UPDATE」就应改成 UPSERT。

### 5.5 事务：要么全成功，要么全失败

下单要同时做三件事：创建订单、创建订单明细、扣减库存。如果前两步成功、第三步发现库存不足，订单已建但菜没了——数据不一致。**事务**把多个操作打包成原子操作：要么全成功，要么全部回滚。

ACID 四特性：原子性（全成功或全失败）、一致性（操作前后数据都合法，库存不会负）、隔离性（并发互不干扰，两人抢最后一份只有一人成功）、持久性（成功后服务器重启数据还在）。

判断标准：**几个操作必须同时成功或同时失败，就放在一个事务里**。常见场景：下单、转账、注册（建用户 + 默认配置 + 欢迎消息）、发帖（建帖 + 计数 + 动态）。

> **事务要短小精悍**。事务期间持有锁并占用连接；如果里面调用外部 API、发邮件，其他请求只能排队。原则：**事务里只放数据库操作，外部调用放到事务提交之后**。

### 5.6 Schema 与迁移

Schema 是数据库蓝图，AI 根据业务生成，审查要点：每张表有 `id` 主键；外键方向正确（外键永远在「多」的一方）；该加的约束加了（点赞表 `userId + postId` 联合唯一）；类型合适（内容用 `text`）；时间戳齐全；常用查询字段有索引。

表结构会随功能迭代变化，直接改生产数据库太危险。**迁移（Migration）** 是数据库的版本管理：每次修改 Schema 生成迁移文件，可追踪历史、团队同步、安全回滚。Drizzle 内置迁移工具：改 Schema 代码 → 运行迁移命令 → 自动对比差异生成 SQL → 执行更新数据库。

> 生产环境迁移要谨慎：删列、改类型可能不可逆。AI 生成迁移后先在开发环境测试，涉及删列改类型先备份。

**工作流**：描述需求 → AI 生成 Schema → 审查表结构/关系/约束 → AI 生成 CRUD → 审查 WHERE/事务/错误处理 → 需求变更走迁移 → 测试后上生产。**角色不是「写数据库代码的人」，而是「审查数据库代码的人」。**

## 6. 设计与优化：那些看不见但致命的东西

老王做了一个读书笔记应用，用户 5000 时笔记列表要等 3 秒、搜索超时。原因只有三个字：**没索引**。`notes` 表有 `user_id`、`book_id` 两个外键都没索引，25 万行全表扫描。加两个索引，查询从 3 秒变 30 毫秒。

### 6.1 AI 交叉论证法（炼蛊）

新手很难一眼看出 Schema 好坏，但另一个 AI 往往能发现问题：

1. 让 **AI 1 号** 根据需求设计表结构；
2. 把代码发给 **AI 2 号**，以「资深 PostgreSQL 架构师」身份审查；
3. 根据反馈让 AI 1 号修改；
4. 重复 1-2 轮。

每个 AI 都有盲点：AI 1 号专注业务逻辑，可能忽略性能；AI 2 号以审查者视角更容易发现「外键没索引」「类型不对」。就像 Code Review——自己写的代码很难发现 bug，同事一眼就能看出。

### 6.2 索引：数据库的目录

没有索引的查询是全表扫描（Sequential Scan），100 行感觉不到，10 万行开始卡，100 万行要等几秒。索引维护一个排好序的「目录」，直接跳到目标位置，查询提升 100-1000 倍很常见。

索引不是免费的：占存储（被索引数据的 10%-30%），增删改时要同步更新，拖慢写入。

| 必须加索引 | 原因 |
|---|---|
| 外键列 | JOIN 与级联删除依赖，不加会全表扫描 |
| WHERE 常用列 | `status`、`email`、`phone` |
| ORDER BY 排序列 | `created_at` 倒序，否则要读全部再排 |

| 不需要索引 | 原因 |
|---|---|
| 很少查询的列 | `bio`、`avatar` 几乎不出现在 WHERE/ORDER BY |
| 布尔值列 | 区分度太低，索引帮不上忙 |
| 小于 1000 行的表 | 全表扫描也很快 |

> **PostgreSQL 不会自动给外键建索引**（MySQL 会）。审查 Schema 第一件事就是检查每个外键列是否有索引——这一条能避免 80% 的性能问题。

**B-tree** 适合绝大多数等值查询与范围查询。特殊场景：`jsonb` 列用 **GIN 索引**（普通 B-tree 对 JSON 内部查询无效）；软删除场景用**部分索引**（只索引 `deleted_at IS NULL` 的行，更小更快）。

### 6.3 行级安全（RLS）

如果权限只在代码里做，一个 bug 就可能导致全部用户数据泄露。RLS 在数据库层面定义规则（「用户只能看到自己的订单」），无论从哪个入口查询都生效。

- **用 Supabase 时 RLS 几乎必须**：客户端 SDK 直连数据库，没有 RLS 等于裸奔；
- **Neon + 自建 API 时不是必须**，但作为额外防线值得考虑，尤其涉及支付与隐私。

审查 RLS 三件事：是否真的 `ENABLE ROW LEVEL SECURITY`（只定义策略不启用等于没设密码）；SELECT/INSERT/UPDATE/DELETE 是否各有策略（漏一个就是漏洞）；策略用到的列是否有索引（否则每次查询都全表扫描做权限过滤）。

### 6.4 连接管理与安全

**连接池**：应用账号每次请求新建连接、用完不释放，50 个用户同时刷页面就能打满（免费套餐总内存几百 MB，约 100-200 个连接）。连接池预先建一批连接复用，100 个并发可能只需要 10 个。部署时务必用连接池地址。

**SQL 注入**：ORM 使用参数化查询，用户输入被当作「数据」而不是「代码」，自动防住。但如果看到手写字符串拼接 SQL（`` `SELECT * FROM users WHERE name = '${userName}'` ``），要警惕，应改成 ORM 或参数化查询。

**最小权限**：应用账号只给读写权限，不给删表、改结构、建用户权限；管理员账号只在迁移与维护时使用。应用是攻击者最容易接触的入口，权限越小，被攻破后的破坏越小。

**备份是底线**：自动备份（不要依赖手动，你一定会忘）、多地备份、**恢复演练**（最容易被忽视——太多人做了备份从未测试，需要恢复时才发现文件损坏或流程跑不通）。备份的价值不在于「有没有做」，而在于「能不能恢复」。

### 6.5 性能诊断四步

1. **确认是不是数据库的问题**：页面慢可能是前端渲染、图片太大、API 慢或网络差。在接口加日志记录查询耗时——查询 10ms 但接口 3 秒，问题不在数据库；
2. **检查缺失索引**：`EXPLAIN ANALYZE` 是查询的「X 光」，看到 `Sequential Scan` 说明缺索引。把输出发给 AI，它能告诉你加在哪个列；
3. **检查 N+1**：一个页面发了几十上百次查询，大概率是 N+1，改 JOIN 或批量查询；
4. **检查连接与事务**：连接数是否接近上限、有没有长事务阻塞；平台监控面板能看到活跃连接、最慢查询、锁等待。

大部分性能问题在前两步就能解决——要么不是数据库的问题，要么是缺索引。
