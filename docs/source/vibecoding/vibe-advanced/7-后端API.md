## 1. 前端与数据库之间缺一座桥

界面有了、数据库也准备好了，点「提交」数据应该入库——但前端和数据库之间还缺一座桥，这就是 **API（应用程序接口）**。前端不能直接连数据库：前端代码运行在用户浏览器里，如果直连，用户打开 F12 就能看到数据库密码，还能随意删除别人的数据。

| 层 | 职责 |
|---|---|
| 前端 | 展示界面、收集输入、发送 HTTP 请求 |
| API | 接收请求、验证参数、调用数据库、返回响应 |
| 数据库 | 存储和检索数据 |

API 是数据库的守门员，所有数据操作必须通过它。

## 2. 路由与 API Route

**路由**就是「URL 路径决定展示什么内容」。豆瓣的电影首页、详情页、短评页、排行榜，URL 不同页面不同；`?` 后面是查询参数，用来进一步筛选。Next.js 用**文件系统路由**表达这层关系：

```
app/
├── page.tsx                    → yourdomain.com/
├── subject/
│   └── [id]/
│       ├── page.tsx            → yourdomain.com/subject/37311135
│       └── comments/
│           └── page.tsx        → yourdomain.com/subject/37311135/comments
└── chart/
    └── page.tsx                → yourdomain.com/chart
```

`[id]` 是动态段，任何电影 ID 都由同一个 `page.tsx` 处理。

**API Route** 是同样的思路，但不返回页面而返回数据。在 `app/api/` 下创建 `route.ts` 就是接口：`app/api/movies/route.ts` → `/api/movies`；`app/api/movies/[id]/route.ts` → `/api/movies/123`。区别只是 `page.tsx` 返回用户看的页面，`route.ts` 返回程序用的 JSON。

在 `route.ts` 中导出对应 HTTP 方法的函数：导出 `GET` 处理 GET，导出 `POST` 处理 POST；两者同时导出，同一个 URL 就同时支持获取与创建。Next.js 版本迭代快，可以让 AI 用 Context7 查最新文档再生成代码。

## 3. 几个必须认识的关键词

**RESTful**：用 URL 表示资源，用 HTTP 方法表示操作。`GET /api/movies` 获取列表、`POST /api/movies` 创建、`DELETE /api/movies/123` 删除。跟 AI 说一句「用 RESTful 风格」，它就会按这套规范来。

**参数的三种来源**：

- **路径参数**：`/subject/37311135` 中的 `37311135`，标识「哪个资源」；
- **查询参数**：`?status=P`，控制「怎么查」；
- **请求 Body**：表单提交时把数据打包成 JSON 放在请求体，传递「要创建或修改的数据」。

**统一响应格式**：项目初期就与 AI 约定——成功 `{ success: true, data: ... }`，失败 `{ success: false, error: { message: "..." } }`。前端先看 `success`，为 true 取 `data`，为 false 显示错误信息。

> API 不只有 REST 一种风格。看到 `trpc.movie.list()` 这样的函数调用，说明用了 **tRPC**——前端像调用本地函数一样调后端，前后端类型自动同步。两者只是风格不同，解决同一个问题。

**工作方式**：不需要手写每个接口，告诉 AI 需求，它生成完整代码；人负责验证三件事——跑起来了吗（`pnpm dev` 页面能操作）、数据库对吗（Drizzle Studio 看写入）、报错了吗（整段复制给 AI 修）。

## 4. 跑通第一个全栈应用

全栈数据流：

```text
用户点击"添加" → 前端发送请求 → 后端 API 接收 → Drizzle 写入数据库
                                                        ↓
用户看到新数据 ← 前端渲染响应 ← 后端返回结果 ← 数据库返回确认
```

对 AI 说：「帮我创建一个 Todo 应用，使用 Next.js + Drizzle ORM + PostgreSQL。需要完整的 CRUD：添加待办、查看列表、标记完成、删除待办。数据库连接用 `.env` 里的 `DATABASE_URL`。」AI 会生成：

```
src/
├── db/
│   ├── index.ts          # 数据库连接
│   └── schema.ts         # 表结构定义
├── app/
│   ├── api/todos/
│   │   └── route.ts      # API 路由
│   └── page.tsx          # 前端页面
```

`schema.ts` 定义数据长什么样（`id` 主键、`title` 非空、`completed` 默认 false、`createdAt` 自动记录）；`route.ts` 是后端接口（`POST` 对应增、`GET` 对应查）；`page.tsx` 是用户界面（加载时 GET、添加时 POST、勾选时 PATCH、删除时 DELETE）。

跑起来三步：`pnpm drizzle-kit push` 把表结构同步到云端 → `pnpm dev` 启动 → 打开 `localhost:3000` 试 CRUD。用 `pnpm drizzle-kit studio` 可以直接看数据库每一行，与页面操作一一对应。

> **核心技能不是读代码，而是验证结果**：数据库里的数据对不对、API 返回的格式对不对、页面显示的内容对不对。能验证这三件事，就能放心让 AI 写后端。

常见问题：添加后列表没更新（让 AI 在 POST 成功后重新获取）；删除报 404（检查 `app/api/todos/[id]/route.ts` 路径）；数据库里没有表（确认执行了 push，检查 `DATABASE_URL`）。

## 5. 一个接口不够用了

小明的电影详情页要显示电影名、年份、海报、导演、演员、评分、标签、简介，数据分散在四五张表。最直觉的做法是前端发五个请求，结果页面「零件一个个往上拼」：标题先出、导演半秒后冒出来、标签再等一会儿；五次网络往返至少几百毫秒，某个请求超时页面还会缺一块。

### 5.1 先问：这个页面真的需要 API 吗

在 Next.js 里，页面组件（`page.tsx`）本身运行在服务器上，可以**直接查数据库**，不需要绕一圈走 API。Server Component 可以直接调用 Drizzle，把五张表的数据一次查好渲染成 HTML，没有任何网络往返。

API Route 主要给两类场景用：

- **前端需要动态交互**：用户点「收藏」按钮，前端要告诉后端写数据；
- **外部消费者**：别人想用你的数据做小程序，需要一个可调用的 HTTP 接口。

「打开页面就展示数据」的详情页不需要 API Route。用户点按钮触发的简单写操作，也可以用 **Server Action**（带 `'use server'` 的函数），不必手写 `route.ts`——AI 会根据场景选择合适方式。

### 5.2 嵌套 vs 扁平

**嵌套**：关联数据嵌在主对象里，一次返回：

```json
{
  "id": 1,
  "title": "千与千寻",
  "year": 2001,
  "director": { "id": 5, "name": "宫崎骏", "nationality": "日本" },
  "tags": ["动画", "奇幻", "冒险"],
  "rating": { "average": 9.4, "count": 2156 }
}
```

前端直接用 `movie.director.name`、`movie.rating.average`，不用再发第二、第三个请求。

**扁平**：只返回关联 ID，前端需要时自己再查：

```json
{
  "id": 1,
  "title": "千与千寻",
  "year": 2001,
  "directorId": 5,
  "tagIds": [1, 3, 7],
  "averageRating": 9.4
}
```

| 场景 | 推荐结构 | 理由 |
|---|---|---|
| 电影详情页 | 嵌套 | 页面要展示完整信息，一次查完 |
| 电影列表页 | 扁平/轻度嵌套 | 只需要标题、年份、海报，带完整导演信息是浪费带宽 |
| 管理后台表格 | 扁平 | 每行只显示关键字段，点行再加载详情 |
| 搜索结果 | 扁平 + 少量嵌套 | 显示标题与评分即可 |

判断标准：**前端拿到数据后，还需不需要再发请求才能渲染页面**？需要说明返回不够，应嵌套更多；拿到就能渲染说明刚刚好。

### 5.3 分页：500 条记录一次全返回，页面卡死

小明把看过的 500 多部电影全录进去后，首页接口返回几百 KB JSON、渲染几千个 DOM 节点，浏览器直接卡住。

**偏移分页（offset/limit）**：`GET /api/movies?page=3&limit=20`，跳过前 40 条取 41-60 条。好处是简单直观，可以显示页码、跳任意页；坏处是翻到后面会变慢——`OFFSET 10000` 要先扫描前 10000 行。数据量小（< 1 万）时完全够用。

**游标分页（cursor）**：`GET /api/movies?cursor=eyJpZCI6NDB9&limit=20`，从上次最后一条之后取 20 条。像在书里放书签，无论翻到第几页速度一样；坏处是不能跳页。社交 feed、评论列表的无限滚动都用它。

| 场景 | 推荐 | 理由 |
|---|---|---|
| 后台管理表格 | 偏移 | 需要页码导航，数据量可控 |
| 商品搜索结果 | 偏移 | 用户习惯翻页、跳到指定页 |
| 社交 feed / 评论 | 游标 | 无限滚动、数据量大、不跳页 |
| < 1 万条 | 偏移 | 简单够用 |
| > 10 万条 | 游标 | 偏移越翻越慢 |

分页响应不能只给数据，还要让前端知道总数、当前页、还有没有下一页：

```json
{
  "success": true,
  "data": [
    { "id": 1, "title": "千与千寻", "year": 2001, "rating": 9.4 }
  ],
  "meta": { "total": 500, "page": 1, "limit": 20, "totalPages": 25 }
}
```

游标分页不返回 `total`、`totalPages`（算总数本身就是全表扫描），而是返回 `nextCursor`；为空说明没有更多数据。

### 5.4 过滤与排序：一个接口 + 查询参数组合

不为每种筛选建新接口，而是用查询参数组合：

```text
GET /api/movies?tag=动画&sort=rating&order=desc&page=1&limit=20
```

参数像乐高积木：只想排序就 `sort=rating&order=desc`；只想筛选就 `tag=动画`；多标签就 `tag=动画&tag=日本`；什么都不传就返回默认排序的分页数据。

| 参数 | 用途 |
|---|---|
| `page` / `limit` | 分页 |
| `sort` / `order` | 排序 |
| `tag` / `genre` | 分类筛选 |
| `year` / `yearFrom` / `yearTo` | 年份 |
| `q` / `search` | 关键词搜索 |
| `minRating` | 最低评分 |

所有参数都应是**可选**的：不传就用默认值，保持向后兼容。**筛选是精确匹配**（标签等于动画、年份等于 2024），**搜索是模糊匹配**（标题包含关键词），实现方式不同；数据量到几十万再考虑全文索引。

接口的进化路径很清楚：V1 返回全部 500 条（页面卡死）→ V2 加分页（找不到想看的）→ V3 加筛选排序（够用）。**先做最简单版本，遇到问题再迭代，不需要一开始设计「完美」接口。**

## 6. 上线后的第一批坑

### 6.1 数据库里多了一条空标题的电影

前端明明有校验，为什么还能提交空数据？朋友用 Postman 直接调接口，什么参数都没传也成功了。**前端校验只能拦住正常使用的用户**——任何人都能绕过前端：开 F12 直接发请求、用 Postman/curl、写脚本批量调用。

- **前端校验是为了体验**：即时反馈，不用等服务器就能提示「标题不能为空」；
- **后端校验是为了数据安全**：不管请求从哪来，脏数据都进不了数据库。

**Zod** 是 TypeScript 生态最流行的校验库，不需要学语法，知道三件事：定义规则（标题 1-100 字符、年份 1888-2030）、校验失败返回具体字段错误、校验规则与类型合一不用写两遍。

```typescript
const createMovieSchema = z.object({
  title: z.string().min(1, '标题不能为空').max(100, '标题太长了'),
  year: z.number().int().min(1888).max(2030),
  directorId: z.number().int().positive('导演 ID 必须是正整数'),
})

const result = createMovieSchema.safeParse(body)
if (!result.success) {
  return Response.json(
    { success: false, error: { message: result.error.issues[0].message } },
    { status: 400 }
  )
}
```

`safeParse` 不抛异常，而是返回 `{ success, error }`，比 `try-catch` 更可控。

**校验严格到什么程度**：核心原则是**不信任任何外部输入，但也不要过度校验**。必须校验：必填不能为空、字符串长度（防止 10MB 字符串撑爆内存）、数字范围、枚举值、外键存在性。不必过度校验：内部服务调用、已有数据库约束的字段。

### 6.2 同一部电影被添加了 10 次

网络卡时用户连点添加按钮，每次点击都发 POST，后端老老实实创建 10 条记录。这就是**重复提交**。

**前端拦一道**：点击后立即禁用按钮、显示「提交中」，能拦住 90% 的情况；但拦不住刷新重提、超时自动重试、脚本调用。

**后端兜一道：幂等性**。电梯按钮是幂等的——按一次去 3 楼，多按五次还是只去 3 楼；投币机不是——投一次出一瓶水，投两次出两瓶。`GET` 天然幂等，`DELETE` 也幂等（第二次返回「已经不存在」），`POST` 默认不幂等。

三种方案：

| 方案 | 做法 | 适用 |
|---|---|---|
| 数据库唯一约束 | 「标题 + 年份」联合唯一，重复插入报错并返回 409 | 有天然唯一标识的场景（最简单） |
| 幂等键 | 前端生成 UUID 放请求头，后端检查是否处理过 | 最通用，支付接口几乎都用 |
| 前端去重 + 后端兜底 | 禁用按钮 + 唯一约束 | 大部分场景的双保险 |

### 6.3 所有报错都显示「出错了」

不管参数不对、数据不存在还是数据库挂了，统统 500 + 「出错了」，用户完全不知道发生了什么。**HTTP 状态码就是错误的分类系统**：

| 状态码 | 含义 | 什么时候用 |
|---|---|---|
| 200 / 201 | 成功 / 创建成功 | 正常处理 / POST 创建资源 |
| 400 | 请求有误 | 参数校验失败 |
| 404 | 资源不存在 | 查询的 ID 不存在 |
| 409 | 冲突 | 重复添加 |
| 429 | 请求太频繁 | 触发限流 |
| 500 | 服务器错误 | 代码 bug、数据库挂了 |

关键原则：**400 系列是调用者的问题，500 系列是服务器的问题**。400 系列要显示具体错误引导用户改正；500 系列用户做什么都没用，只显示「服务暂时不可用」即可。**500 错误绝不能暴露内部细节**——数据库连接串、SQL、文件路径、堆栈都可能被攻击者利用。

统一错误格式：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "标题不能为空",
    "details": [
      { "field": "title", "message": "标题不能为空" },
      { "field": "year", "message": "年份必须是 1888-2030 之间的整数" }
    ]
  }
}
```

`details` 让前端能在对应输入框旁显示错误，而不是只在顶部弹一个笼统提示。

### 6.4 添加成功了但列表没显示：缓存

这不是 bug，是**缓存**。Next.js 有多层缓存：Server Component 可能缓存整个页面渲染结果，`fetch` 本身也有缓存。症状都一样——写入了新数据，读取还是旧的。

解决方式是在写操作后主动告诉 Next.js「这部分数据变了」：调用 `revalidatePath('/movies')` 或 `revalidateTag('movies')`。原则：**读可以缓存，写之后必须清缓存。**

### 6.5 添加成功但用户等了两秒：阻塞与非阻塞

加通知功能后，接口变成串行三步：写数据库（几十毫秒）→ 查关注用户（几百毫秒）→ 逐个发通知（一两秒），全部做完才返回。

但用户只关心「电影有没有添加成功」。数据库写入必须等；发通知可以在返回响应之后再做。Next.js 的 `after()` 专门做这件事：把发通知、记日志、更新统计推迟到响应发送之后。

判断标准：**这个操作的结果需要告诉用户吗**？需要（添加成功、标题不能为空）就必须在响应前完成；不需要（发通知、记日志、刷新缓存）就可以放到响应之后。

### 6.6 某天 API 全部 500：连接池耗尽

几十个人同时访问，免费数据库最大连接数只有 20 个，瞬间打满，后面的请求排队超时。排查三步：

1. 看报错关键词：`too many connections`、`connection pool exhausted`、`timeout waiting for connection`；
2. 检查连接池配置：免费套餐通常限制 20-50 个；一般设为 `CPU 核心数 × 2 + 1`，5-10 个连接就能处理几百个并发（每个请求占用连接时间很短）；
3. 检查连接泄漏：查询报错后连接没释放，池子会被慢慢耗光。

### 6.7 排错的 Prompt 模板

最高效的排错方式是把**完整上下文**丢给 AI：

```text
我的 POST /api/movies 接口报了这个错：[完整报错与堆栈]。
请求的 body 是 [请求内容]。帮我定位问题并修复。
```

```text
数据库 movies 表里出现了标题为空的记录（ID: 42, 43, 47）。
帮我排查是哪个接口没做校验，然后：1）给接口加 Zod 校验；2）清理这三条脏数据。
```

```text
电影列表接口在数据量到 5000 条后变慢，响应时间从 50ms 涨到 3 秒。
帮我分析原因——缺索引、N+1、还是其他？用 EXPLAIN ANALYZE 检查。
```

```text
API 大部分时候正常，但每天晚上 8-10 点偶尔返回 500，报错是 [粘贴]。
这个时间段是访问高峰，帮我排查是不是连接池不够。
```

关键是给具体数据：不说「接口很慢」，说「响应时间从 50ms 涨到 3 秒」；不说「有时候报错」，说「每晚 8-10 点报错，报错信息是 xxx」。

## 7. 把接口当产品打磨

接口多了会遇到三个问题：自己都记不清有哪些接口、改一个字段名前端崩好几个页面、循环调用删除接口又慢又容易只删一半。

### 7.1 文档：OpenAPI + Swagger UI

**OpenAPI**（以前叫 Swagger）是描述 API 的标准格式：每个接口的 URL、方法、参数、响应、错误码全部结构化定义。用 Swagger UI 渲染成可交互网页——不只是看，还能填参数点「发送」实时测试，像内置的 Postman。

```text
帮我根据现有的所有 API Route 生成 OpenAPI 3.0 文档。
然后加一个 /api-docs 页面用 Swagger UI 展示，开发环境可直接测试接口。
```

最怕文档写好但接口改了忘更新，解决方式是**让文档从代码自动生成**（如 next-swagger-doc），每次接口变化文档自动更新。

### 7.2 向后兼容：改接口的安全姿势

把 `score` 改成 `rating`，前端首页、搜索、收藏三个页面全崩了。**接口一旦有人在用，改它就像改公共设施**——把路灯换了位置，所有记住老位置的人晚上都会撞墙。

实用原则：

- **加字段没事，删字段要小心**：新增字段前端不用它，静静待在 JSON 里；删字段会让所有引用崩掉；
- **过渡期两个都保留**：先同时返回 `score` 和 `rating`（值一样）→ 通知使用者改用 `rating` → 等全部迁移完再删 `score`。这叫**废弃（Deprecation）**，不是直接删；
- **大改用版本号**：`/api/v1/movies` 保持不变，`/api/v2/movies` 用新结构，全部迁移后再下线 v1。

只有自己前端调用时可以简化，但「加字段不删字段」的习惯能避免很多「改了后端忘了改前端」的低级错误。

### 7.3 批量操作：一次事务，而不是 50 次请求

前端循环调 50 次 DELETE 的问题：慢（50 次网络往返，哪怕每次 50ms 也要 2.5 秒）、不一致（删到第 30 个断网，前 30 个删了、后 20 个没删）、浪费连接。

更好的做法是批量接口 `DELETE /api/movies/batch`，body 传 `{ "ids": [...] }`，后端在**一个事务**里完成——要么全成功，要么全部回滚，只有一次网络往返。

> **判断标准：当前端在循环调用同一个接口时，就该考虑批量版本。** 批量接口要限制数量（如最多 100 条），防止一次删 10 万条导致事务过大、锁表太久、内存溢出。

### 7.4 文件上传

图片是二进制，放不进 JSON。**multipart/form-data** 是 HTTP 专门传文件的格式，一个请求里可以同时带文本字段和文件。

流程：前端用 `<input type="file">` + `FormData` 打包发送 → 后端取出文件做校验（大小、格式）→ 存到某处，把**相对路径**存进数据库 → 前端拼域名前缀显示。

为什么存相对路径？域名会变——开发是 `localhost:3000`，上线是 `yourdomain.com`，迁移云存储又是另一个域名。存完整 URL 每次换域名都要批量更新数据库；存相对路径前端按环境拼前缀即可。

**文件存哪**：本地存储（`public/uploads/`）简单直接，适合开发；但 Serverless 部署没有持久文件系统，每次部署都会丢，上线要用云存储（COS、R2、S3、OSS）。把上传逻辑封装成统一函数，上线只换实现，前端和业务代码不动。

**安全注意**：限制文件大小（防止 1GB 文件撑爆内存）、限制类型（只允许 jpg/png/webp，不接受可执行文件）、不要用用户提供的文件名（`../../../etc/passwd` 是路径穿越攻击），后端自己生成 UUID 文件名。

### 7.5 实时更新：轮询、SSE、WebSocket

| 方案 | 机制 | 适合 |
|---|---|---|
| 轮询（Polling） | 前端每隔几秒请求一次 | 更新频率低、实现最简单 |
| SSE | 服务器单向推送 | 通知、订单状态、新评论提醒 |
| WebSocket | 双向持久通道 | 在线聊天、协同编辑、实时游戏 |

判断标准：**只需服务器推数据给前端用 SSE；前端也要频繁发数据用 WebSocket；更新频率低（几秒到几分钟）轮询最省事。**

轮询不要手写 `setInterval + fetch`，用 SWR 或 TanStack Query：自带请求去重、自动缓存、组件卸载自动清理、失败重试；SWR 更轻量，TanStack Query 功能更丰富（乐观更新、无限滚动）。

## 8. API 即产品

接口不只是「后端的事」，它是前端和其他消费者的「产品」。好的接口：

- **有文档**——使用者知道怎么用，不用翻代码或问人；
- **向后兼容**——升级不坑老用户，改动有过渡期；
- **批量操作**——效率高，不让使用者做重复劳动；
- **错误信息清晰**——出问题知道是谁的问题、怎么修；
- **支持多种数据格式**——不只是 JSON，还能处理文件；
- **按需实时**——该实时的实时，不该实时的别浪费资源。

不需要一开始就完美：先跑通 CRUD → 数据量和需求增长就加分页过滤 → 上线遇到脏数据和错误就加校验与错误处理 → 接口多了加文档与版本管理。每一步都是被真实问题推动的，**先让它跑起来，再让它跑得好**。
