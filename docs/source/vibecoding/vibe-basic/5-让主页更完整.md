# 让主页更完整：内容引导与基础存档

## 1. 为什么先学「存档」

从第 4 章开始，对项目的修改会变得更频繁，也更容易牵一发而动全身：加一个作品区，顺手改到布局；补联系方式，不小心把首屏间距弄乱；调整聊天入口，结果别的地方一起变形。到这个阶段，如果还没有任何「后悔药」，很容易在改动时变得畏手畏脚，或者干脆因为一次改崩就把前面的努力一起拖下去。

所以这一章先不急着加内容，而是先学最小的存档闭环。这里的 Git 不需要被理解成什么专业协作体系，它在基础版里只有一个非常朴素的作用：**在大胆改的时候，有地方可以退回来**。掌握三个动作就够了：

| 动作 | 现在把它理解成什么 |
|---|---|
| 存一次 | 给当前稳定版本打一个可回来的点 |
| 看历史 | 看看之前存过哪些版本 |
| 退回来 | 某次改崩时，回到上一个可用版本 |

为什么是现在学，而不是更早或更晚？第 1、2 章时项目还很小、改动也相对克制；到了第 4 章，要加内容模块、调整页面结构、改聊天入口的使用方式，很多修改都不是一句文案那么轻。改动开始变大，存档才第一次变得非常值回票价。顺序很重要：**不是项目彻底崩了才去学怎么回退，而是在改动真正复杂起来之前，先给自己留后路**。

如果一听 Git 就紧张，可以把这件事想得更现实一点：它不是要人突然学会分支、PR、合并冲突，而只是给项目装一个最基础的时光机。甚至连操作都不一定要自己硬记命令——完全可以让 AI 帮忙，重点是自己知道「现在为什么需要它」以及「希望它完成什么」。

```text
我现在准备开始给主页补内容。
在动手前，请先帮我做一个最小存档，让我之后改坏了还能退回来。
请一步一步带我完成，不要展开 Git 理论。
```

```text
请帮我查看这个项目目前有没有存档记录。
如果之后我改坏了，告诉我最小回退路径是什么。
只讲这次需要知道的部分。
```

这种说法很适合基础版：不是在上 Git 课，而是在用 Git 解决一个马上会遇到的实际问题。一旦有了这个最小闭环，后面的改动心态会完全不一样：更敢补内容、更敢试不同写法、也更敢让 AI 做稍大一点的调整——不是因为风险消失了，而是因为知道即使改坏了也不是世界末日，有办法回到上一个稳定版本。**这层安全感，往往比「我已经学会了多少 Git」更重要**。

## 2. 从访客视角决定补什么

页面一旦开始像作品，很多人会自然进入下一种冲动：继续加、继续补、继续往里塞更多信息。问题是，内容不是越多越好——对个人主页来说，更重要的是**相关**。别人来到这里，通常不是想把你的一生读完，而是想快速判断你是谁、做过什么、值不值得继续联系或交流。真正决定该补什么的，不是「我还能写多少」，而是「访客最想先知道什么」。

先切换到三类人看页面：

| 访客 | 他们通常最想先知道什么 |
|---|---|
| 朋友 | 你最近在做什么，有没有新作品或新方向 |
| HR / 面试官 | 你是谁，做过什么，能力大概落在哪 |
| 潜在合作伙伴 | 你擅长什么，值不值得继续交流，怎么联系 |

不需要为三类人分别做一套页面，而是从交集里找优先级。很多时候交集其实很稳定：**你是谁、你做过什么、最近在做什么、怎么联系你**。

一个比「我还想加什么」更有用的问题是：

> 如果别人只花 30 秒看我的主页，他最应该记住什么？

这个问题会直接筛掉很多其实不急着加的东西，因为它逼人从「我还能写什么」切换到「别人最该先看到什么」。

**内容不是越多越好，而是越相关越好**。判断标准很实用：这个模块加上去之后，能不能让访客更快回答下面至少一个问题？

- 这个人是谁？
- 他最近在做什么？
- 他做过哪些值得看的东西？
- 如果我想继续联系，应该怎么做？

如果一个模块不能明显帮助回答这些问题，它就很可能没有现在想象中那么重要。

## 3. 只加 2-3 个最有价值的模块

有了访客视角之后，下一步不是「加所有东西」，而是只加 2 到 3 个最有价值的模块。这里最容易犯的错误，是把主页想成一个越完整越好的仓库；基础版更鼓励**做减法后的完整**——不是所有模块都要有，而是先加那些最能帮助别人理解你、联系你、继续互动的内容。

对大多数个人主页来说，最值得优先考虑的通常就那么几类：

| 模块 | 它解决什么问题 |
|---|---|
| 作品展示区 | 让别人更快知道你做过什么 |
| 联系方式 | 让「感兴趣」可以变成「能联系到」 |
| 经历 / 时间线 | 帮别人快速看懂你的背景脉络 |
| FAQ | 回答高频问题，降低访客开口成本 |

不一定全都要，很多时候三选二或四选二就已经足够。关键不在模块名字，而在每加一个模块之前先问：它是不是在帮助访客更快理解我，而不是只是让我感觉「页面更满了」。

按当前最缺什么来选：

- 最缺「别人看不懂我做过什么」→ 优先补作品展示区；
- 最缺「别人想继续交流却不知道怎么找我」→ 优先补联系方式；
- 最缺「别人不知道该问什么」→ 优先补 FAQ 或聊天区引导。

这种节奏有两个好处：页面不会一下变得很杂；也更容易判断到底是哪一轮修改真正让它变完整了。

## 4. 数字分身入口不该只是「有个聊天框」

别忘了一个会聊天的组件，不等于一个容易被使用的入口。很多页面的问题不是「没有聊天功能」，而是别人根本不知道该怎么用它：访客不知道问什么、不知道这里能回答什么、甚至根本没注意到它——那这个功能的价值就很难真正出现。

所以很适合顺手补一点引导：

- 一两句更清楚的提示文案；
- 几个快捷问题按钮；
- 一个告诉别人「你可以在这里问我最近在做什么、我有哪些作品、怎么联系我」的入口说明。

这类引导不花哨，但特别重要，因为它会把「有一个聊天框」推进成「这个聊天框真的有人会用」——这恰恰是作品体验从 demo 往真实使用靠近的地方。

## 5. 操作节奏

在操作层面上，可以把节奏控制得更稳一点：**每加一类模块前先做一次存档，改完再看一次效果**。这样既不会因为改动变大而慌，也能比较清楚地判断到底是哪一轮调整真正让页面变得更完整。

```text
请帮我给个人主页补一个作品展示区和一个联系方式区。
目标是让访客更快知道我做过什么，以及怎么联系我。
请保持现在的整体风格，不要一次新增太多模块。
加完之后，再帮我检查聊天入口是否足够明显。
```

这种说法很适合现在这个阶段：既说清了目标，也把范围收住了。

## 6. 本篇验收

- [ ] 已经知道怎么给项目做最小存档，并在必要时退回来；
- [ ] 页面内容比之前更完整，但没有失控地越加越多；
- [ ] 访客更容易理解我是谁、做过什么、怎么联系我；
- [ ] 数字分身入口比之前更容易被注意到，也更容易被实际使用。

第 3 章解决的是「它看起来更像作品了」，第 4 章解决的是「它终于不再只是一个好看的空壳」。两个变化合在一起，作品进入一个新阶段：别人进来之后，不只是觉得它比以前更顺眼，还会更容易理解你是谁、做过什么、接下来可以点哪里、问什么；自己也不会再因为「万一改坏了怎么办」而缩手缩脚。到这里，页面已经不只是一个 demo，而更像一个开始可以被认真看待的作品。

> **补记**：这一章处理的是「尺度」问题——内容按访客需求做减法、模块按价值做筛选、改动按存档做保护。三者合起来其实是一条小型的工程纪律：**先有退路，再做增量，每次只加最有价值的部分**。这条纪律后面会一直复用到上线和迭代阶段。
