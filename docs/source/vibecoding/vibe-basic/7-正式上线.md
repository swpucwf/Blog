# 正式上线：部署分享与第一轮反馈

## 1. 为什么把「上线」放在最后

第 1 章做完时当然已经可以预览一个版本，但那个阶段更像原型；第 6 章才是正式亮相。之所以把上线放到最后，不是因为它特别神秘，而是因为它本来就应该建立在前面几章的结果之上：页面已经有基本样子、内容已经更完整、数字分身也更像本人了。只有到了这个程度，链接才真正值得被别人点开。

为什么不是第 1 章做完就立刻发出去？因为第 1 章解决的是「先让它出现」，不是「它已经准备好接受别人访问」。一个原型能预览，不代表它已经值得公开：内容可能太空、手机端可能还不稳、聊天入口可能不够清楚、数字分身也可能还不够像你。到第 6 章再上线，反而是对整个项目更负责的节奏——不是在拖延，而是在等它长到一个值得被别人认真看一眼的状态。

做到这里，已经不只是有一个想法，也不只是有一个能跑的页面，而是一个逐步长出来的作品：能展示你是谁、有自己的风格、也有一个开始更像你的数字分身。现在差的最后一步，是把它从「只在自己电脑里存在的项目」变成「别人也能访问的作品」。这一步看起来像发布，实际上更像一次真正的闭环：**一旦它有了公网链接，事情就会发生变化——不再只是对自己解释这个作品，而是开始接受别人怎么理解它、怎么使用它、怎么给反馈**。

## 2. 上线前的朴素自查

上线前最重要的不是马上点部署按钮，而是先做一次很朴素的自查：页面能不能打开、手机端是不是正常、聊天是不是能用、个人信息是不是已经补全、环境变量和密钥是不是放在正确位置。它不需要变成正式测试体系，但至少要保证不是把一个明显还没准备好的版本直接公开出去。

一份很够用的上线前清单：

- [ ] 页面能正常打开，没有明显报错；
- [ ] 手机端阅读没有严重错位；
- [ ] 数字分身可以正常回复；
- [ ] 名字、介绍、作品、联系方式已经不是空白；
- [ ] API Key 没有写死在代码里，环境变量位置正确。

这一步的意义不只是减少翻车，更在提醒一件事：**上线不是额外附加任务，而是作品闭环的一部分**。它不是「顺手发一下」，而是「这个版本现在已经值得进入真实环境了」。

## 3. 从本地到公网的最小发布路径

部署最容易把人吓到的地方，是它表面上涉及很多词：仓库、远程、构建、平台、环境变量、日志。其实对基础版来说，只需要先把闭环跑通：先把代码推到远程仓库（既是备份，也是部署平台读取代码的来源），再把仓库连到部署平台上，用一个国内访问更友好的默认方案（比如 EdgeOne Pages）把项目发出去。

**先记住这条最小路径**：

```text
本地项目
-> 远程仓库
-> 部署平台
-> 公网链接
```

这条链路一旦跑通，作品就不再只活在自己电脑里了。

**为什么要先推到远程仓库**？很多新手会问：明明本地已经有代码了，为什么还要先去 GitHub 或 Gitee？原因很简单，远程仓库在这里同时承担两件事——代码备份，以及部署平台读取代码的来源。所以这一步不是多余动作，而是发布链路的一部分。

**第一次部署只求跑通**，不求一口气理解全部配置。别把自己困在「等我全懂了再部署」，很多默认值本来就可以先用；基础版也不要求在这里进入协作工作流，不需要现在学分支策略、PR、团队流程。最小路径就五步：

1. 创建远程仓库；
2. 把本地代码推上去；
3. 在部署平台连接仓库；
4. 使用默认构建配置先跑一次；
5. 拿到第一个可访问链接。

到这里，这个作品就已经真正离开了自己的电脑。

**如果部署失败，先看日志，再交给 AI**——不要立刻怀疑自己是不是根本不会。先看日志，再把日志贴给 AI，让它判断是构建命令、环境变量，还是平台设置的问题：

```text
这是我在部署平台看到的构建日志。
请先帮我判断最可能的失败原因是什么。
只告诉我下一步先改哪一项，不要一次给太多方案。
```

这和第 2 章本地跑项目时的思路是一样的：先看现象，再收窄范围。

## 4. 上线后自测：真实环境才算数

部署成功不等于作品真的可以用了。很多差异只有在真实环境里才会出现：本地正常的样式，上线后可能有点错位；本地能跑的聊天，到了线上可能因为环境变量漏配而失效；自己看得懂的结构，别人第一次打开时可能根本不知道该看哪里。所以链接出来之后，别急着只顾高兴，先做一轮真实环境自测。

自测顺序可以很简单：

1. 链接能不能正常打开；
2. 首屏和主要内容区有没有明显错位；
3. 手机端读起来顺不顺；
4. 数字分身能不能正常回复；
5. 联系方式和作品信息是不是完整可见。

重点不在「严谨测试流程」，而在「不要把部署成功误以为作品已经完全没问题」。

## 5. 找 2-3 个人，拿第一轮外部反馈

如果可以，再发给两三个人，请他们真的点开看一眼、问一两个问题。真实反馈和自我感觉经常不完全一样：别人卡住的地方、忽略的地方、第一眼理解错的地方，往往就是下一轮迭代最有价值的线索。

不需要设计复杂问卷，只问三件事就很够用：

- 你打开后第一眼觉得我是做什么的？
- 你知不知道该点哪里、该问什么？
- 有没有哪里让你卡住，或者觉得不太自然？

**反馈不是否定，也不是「别人来挑刺」**，而是作品进入真实世界之后最自然会出现的下一批素材。走到这里，真正重要的已经不再是证明自己会不会操作，而是开始学会看见别人怎么使用自己做出来的东西——很多很值钱的改进线索，只有别人真的点开链接之后才会出现。

## 6. 基础版收束

如果从第 0 章一路走到这里，再回头看，会发现这套基础篇其实一直只在做一件事：把一个原本停留在脑子里的想法，慢慢变成一个真正存在、可以运行、可以修改、可以上线、也可以被别人看到的作品。第 1 章让第一个版本出现，第 2 章把它带回工作台，第 3 章让它开始像一个作品，第 4 章让它更完整也更可回退，第 5 章让数字分身更像你，第 6 章把它送到了真实世界。

这条路最重要的意义，不只是学会了几个工具、几个操作、几个说法，而是**已经做完了第一次完整闭环**。从「有想法的人」变成「把想法做成作品的人」——这个变化也许没有考试成绩那么明确，但非常真实：手里现在有东西了、有链接了、有作品了，也有下一轮可以继续改进的方向。

**验收清单**：

- [ ] 已经完成第一次从想法到作品的完整闭环；
- [ ] 有一个别人可以访问的真实链接；
- [ ] 知道这个作品下一步还可以继续往哪里改；
- [ ] 知道可以继续留在当前项目里迭代，也可以进入进阶篇系统学习。

接下来有两个很自然的选择：继续迭代这个项目，把它打磨得更完整；或者进入进阶篇，把环境、调试、UI/UX、API、安全、部署这些话题系统补起来。无论选哪一条，基础篇最该完成的事已经完成了。

> **补记**：这一章把「上线」从一次性动作变成了闭环的一环——先自查、再发布、再真实环境自测、最后拿外部反馈。最值钱的动作其实是最后一步：**找几个真实的人点开链接**，他们卡住的地方往往比任何自我检查都更能暴露问题。
