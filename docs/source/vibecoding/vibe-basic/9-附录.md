# 附录：工具箱速查

## 1. 怎么用这份附录

附录不是预习任务，也不是要通读的第二本书，它更像工具箱：正文里先走主线，遇到卡点、忘了怎么说、忘了怎么问、忘了怎么回退时，再回来按需查。

| 场景 | 查哪一节 |
|---|---|
| 不知道怎么开口写需求 | 第 2 节 常用提示词模板 |
| 页面空白、按钮没反应、部署失败 | 第 3 节 常见错误与问 AI 流程 |
| 想改界面但词不够用 | 第 4 节 UI 速查卡 |
| 改动变多、怕改崩 | 第 5 节 Git 最小操作卡 |
| 接 API 或准备上线 | 第 6 节 API Key 与基础安全 |
| 判断项目该不该这样推进 | 第 7 节 Vibe Coding 的能与不能 |
| 想继续系统补课 | 第 8 节 进阶篇跳转地图 |

## 2. 常用提示词模板

### 2.1 第一次生成作品

```text
我想做一个个人主页，上面有一个数字分身聊天区。

【关于我】
- 名字：______
- 一句话介绍：______
- 我现在主要在做：______
- 我的兴趣：______
- 我一个比较有记忆点的特点：______

【这个主页给谁看】
- 主要访客：______

【页面里至少要有】
- 头像
- 名字和一句话介绍
- 一个简单的个人信息展示区
- 一个可以提问的数字分身聊天区

【数字分身需要知道】
- 我的职业或身份：______
- 我最近在做的事：______
- 我擅长或关心的方向：______
- 别人最可能问我的 3 个问题：______

【风格要求】
- 我希望整体感觉是：______
- 我更偏好的颜色：______
- 是否要适配手机：是
- 其他要求：______

请先帮我生成一个第一版原型。
要求：
1. 先保证结构清楚、能用
2. 不要过度复杂
3. 先做出一个可预览的版本
```

### 2.2 本地只改一处

```text
我现在想修改这个项目里的一个小地方。

目标：______
请先告诉我这部分代码大概在哪个文件里。

要求：
1. 只改这一处
2. 不要动其他布局和样式
3. 改完后告诉我你改了什么
```

### 2.3 界面优化

```text
现在这个页面的主要问题是：______

我希望它改成这样的感觉：______

这次请你只修改这些地方：______
先不要动这些部分：______

另外请兼顾这些最基本的体验：
- 首屏一眼能看出我是谁
- 聊天入口更明显
- 手机端文字可读
- 不要让页面显得更乱
```

### 2.4 添加内容模块

```text
请帮我给个人主页补一个新模块。

模块名称：______
这个模块要解决的问题：______
希望访客看完之后知道什么：______

要求：
1. 保持当前页面整体风格
2. 不要一次新增太多模块
3. 文案先写到够用，不要过度铺陈
4. 如果涉及按钮或链接，请接成真实可点击状态
```

### 2.5 数字分身说明书

```text
你是我的数字分身，用来在个人主页里回答访客关于我的问题。

你的任务：
- 介绍我是谁
- 回答和我有关的问题
- 帮访客了解我最近在做什么、做过什么、怎么联系我

关于我：
- 我是：______
- 我最近在做：______
- 我擅长或长期关注：______

说话方式：
- 语气：______
- 回答尽量：简洁 / 真诚 / 人话一点 / 不装专家

边界：
- 不要编造我没做过的经历
- 不要假装知道我没提供的信息
- 不知道时要明确说不知道

下面是 1-3 组我的真实表达样本，请参考这些样本的表达习惯来回答。
```

> 模板的价值不是「格式标准」，而是把**目标、范围、边界**说清楚。这三件事写清楚，通常就已经比「帮我弄一下」强很多。

## 3. 常见错误与问 AI 流程

### 3.1 通用提问骨架

```text
我现在遇到的问题是：______

现象：______
我刚刚做了什么：______
我原本期望发生什么：______

如果有报错，这是完整报错：
______

请先帮我判断最可能的原因，再告诉我下一步只先检查什么。
```

### 3.2 五类高频故障

| 故障 | 先看什么 | 怎么问 AI | 常见修复方向 |
|---|---|---|---|
| 页面空白 / 打不开 | 是本地还是线上 | 请先判断是启动失败、路由问题还是运行时报错 | 依赖没装好、启动命令不对、运行时报错、部署后构建失败 |
| 按钮没反应 / 链接不能跳 | 是视觉按钮还是真实交互 | 这个按钮看起来能点但点击后没有动作，请检查是不是只有样式、没有绑定真实跳转或事件 | 占位按钮、没绑事件、链接地址没接上、交互逻辑没完成 |
| 聊天区不回复 | 是占位演示还是真实调用 | 请先确认当前聊天区是关键词演示、假数据回复，还是真实接入了模型接口 | 没接 API、环境变量没配、接口请求失败、说明书边界不清 |
| 本地运行 / 构建失败 | 完整日志 | 请先判断最可能是哪一层出了问题，再告诉我下一步只改什么 | 缺依赖、命令不对、Node 版本不兼容、配置有误、环境变量缺失 |
| 部署失败 / 线上与本地不一致 | 部署日志、环境变量、线上现象 | 请先判断是构建命令、环境变量，还是平台配置的问题 | 构建命令不对、环境变量漏配、资源路径不对、平台默认配置不匹配 |

补充信息时优先给：页面截图、浏览器提示、终端完整报错、刚改了哪部分、实际结果与预期差在哪。**不要只说「报错了」**。

### 3.3 一条重要的排错原则

**一次只改一个变量**。不要一看到问题，就同时改模型、改提示词、改布局、改接口、改环境变量。更稳的方式是：先判断更像哪一层的问题，再从那一层开始查——这样更容易知道到底是哪一步真的起了作用。

## 4. UI 速查卡

### 4.1 风格方向词

| 想要什么感觉 | 可以这样说 |
|---|---|
| 简约专业 | 简洁、克制、信息优先、层次清楚 |
| 温暖友好 | 有人味、容易交流、轻松、不生硬 |
| 轻微科技感 | 清爽、数字感、未来感一点点、但不要炫技 |
| 更像作品 | 不像默认模板、有主次、有视觉重点 |

### 4.2 配色表达词

| 想表达什么 | 可以这样说 |
|---|---|
| 干净明亮 | 浅色、通透、清爽、留白多 |
| 稳重克制 | 低饱和、偏深、别太跳 |
| 有重点色 | 只保留一个主色，其余颜色收住 |
| 不想太花 | 不要过多渐变，不要颜色乱跳 |

### 4.3 排版与层次词

| 问题 | 可以这样说 |
|---|---|
| 页面太散 | 首屏信息太散，请加强主次关系 |
| 页面太挤 | 区块之间太挤，请增加留白和呼吸感 |
| 看不出重点 | 请让名字、一句话介绍和主按钮更突出 |
| 像信息平铺 | 请拉开标题、正文和辅助信息的层次 |

### 4.4 交互与体验词

| 目标 | 可以这样说 |
|---|---|
| 让访客知道你是谁 | 首屏打开后一眼就能知道我是谁 |
| 让聊天入口更容易被注意到 | 请让聊天入口更明显，但不要喧宾夺主 |
| 让按钮更像真的能点 | 请给主要按钮明确反馈和真实跳转 |
| 兼顾手机端 | 请确保手机端文字可读、区块不重叠 |

一个够用的界面表达句式：

```text
现在这个页面的问题是：______
我希望它变成这样的感觉：______
请先只调整这些部分：______
不要动这些部分：______
```

能把「问题 + 感觉 + 边界」说清，通常就已经够用。

## 5. Git 最小操作卡

基础版里的 Git 不承担完整协作工作流，只做三件事：存档、看历史、回退。把它理解成项目的「后悔药」就够了。

| 动作 | 理解成什么 | 适合场景 |
|---|---|---|
| 存一次 | 给当前版本打一个「能回来」的点 | 准备做较大改动前 |
| 看历史 | 看看之前都留过哪些点 | 已经改了几轮，想知道还能退回哪里 |
| 退回来 | 出问题时回到最近的稳定状态 | 布局改崩、内容改乱、页面明显退步 |

委托 AI 的三种说法：

```text
我现在准备开始做一轮较大的修改。
请先帮我给当前项目做一个最小存档，作为可回退版本。
只告诉我这次需要知道的步骤，不要展开 Git 理论。
```

```text
请帮我查看这个项目目前有哪些存档记录。
我想知道最近几个可回退版本分别是什么。
```

```text
这一轮修改效果不好。
请帮我回到上一个稳定版本，并告诉我这次回退到了哪个存档点。
```

最重要的一句提醒：**不要等项目已经改崩了，才第一次想起 Git——先存一次，再大胆改。**

## 6. API Key、环境变量与基础安全

基础版不要求一上来学完整安全体系，但有几条最低限度的底线：

> **API Key 不要直接写进代码仓库。**

- **`.env`**：专门放「本来就不该直接写进代码」的配置值，比如 API Key、数据库连接地址、第三方服务密钥——它们往往会随环境变化，也不适合硬编码；
- **`.gitignore`**：告诉 Git 哪些文件不要提交进仓库。最该养成的习惯之一，就是确认 `.env` 这类文件不会被提交出去。

上线前至少检查：

- [ ] API Key 没有写死在源码里；
- [ ] `.env` 这类本地敏感文件没有被提交到仓库；
- [ ] 部署平台需要的环境变量已经正确配置；
- [ ] 线上缺少密钥时，页面不会假装正常工作。

不确定密钥有没有放错地方时，可以直接问 AI：

```text
请帮我检查这个项目里是否有敏感信息直接写在代码里。
重点检查 API Key、环境变量和不应该提交到仓库的配置文件。
如果有问题，请告诉我应该怎么调整。
```

## 7. Vibe Coding 的能与不能

不要神化 Vibe Coding，也不要低估它。它很适合很多场景，但不是所有项目都应该用同样方式推进。

| 很适合 | 为什么 |
|---|---|
| 个人主页、作品集 | 反馈直观，容易快速迭代 |
| 原型验证 | 能很快把想法做出来，判断值不值得继续 |
| 内部小工具 | 范围可控，目标明确，适合快速落地 |
| 活动页、展示页、简单应用 | 页面和交互可以快速推进 |

| 需要更谨慎 | 为什么 |
|---|---|
| 高并发核心系统 | 牵涉性能、稳定性和复杂架构 |
| 金融交易核心链路 | 风险高，错误成本极大 |
| 强合规、强审计系统 | 不是只做出来就够，还涉及流程与责任 |
| 高敏感数据系统 | 安全、权限、审计要求更高 |

这不是说 AI 不能参与这些系统，而是说这些场景不能只靠「先 vibe 一把」来推进。

一个很有用的判断标准：**如果一个项目一旦出错，代价主要是「体验不好、要继续改」，那通常很适合 Vibe Coding 起步；如果一旦出错，代价会变成「资金损失、隐私风险、严重责任问题」，那就必须更谨慎**，甚至需要更专业的工程与审查流程。知道什么时候该快速试、什么时候该慢下来、什么时候该求助专业支持，本身就是成熟的一部分。

## 8. 进阶篇跳转地图

### 8.1 按问题跳

| 最想补什么 | 去哪里继续看 |
|---|---|
| 本地环境、终端、依赖、项目运行基础 | 进阶篇 1-环境搭建 |
| AI 协作工作流、调试、规则、Skills / MCP | 进阶篇 2-AI调优指南 |
| 产品思维、PRD、文档驱动开发 | 进阶篇 3-PRD文档驱动开发 |
| 界面、组件库、交互体验、视觉细化 | 进阶篇 5-UI与UX设计 |
| API、前后端协作、请求链路 | 进阶篇 7-后端API |
| 密钥、环境变量、认证、安全底线 | 进阶篇 8-认证与安全 |
| Git 协作、远程仓库、分支与 PR | 进阶篇 11-Git协作 |
| 部署、平台差异、CI/CD、运维 | 进阶篇 12-Serverless部署与CI-CD |
| 域名、DNS、备案、正式接入 | 进阶篇 13-域名与DNS |

### 8.2 按基础篇章节跳

| 在基础篇哪里卡住 | 最推荐的进阶入口 |
|---|---|
| 第 2 章：把项目带回本地后，环境总是不稳 | 1-环境搭建 |
| 第 3 章：界面会改，但表达总不够准 | 5-UI与UX设计 |
| 第 4 章：内容、结构、需求经常越改越乱 | 3-PRD文档驱动开发 |
| 第 5 章：聊天区、接口、安全开始变复杂 | 7-后端API、8-认证与安全 |
| 第 6 章：上线之后还想更正式、更稳定 | 12-Serverless部署与CI-CD、13-域名与DNS |

不要把进阶篇当成「下一本必须从头读完的书」，而是当成当前项目的补给站：**最先卡在哪，就先跳去补哪一块**，这样学到的东西最容易立刻用回项目里。

> **补记**：这份附录的真正用法是「带着问题来查」，而不是通读。五类模板里最通用的其实是共同结构——目标、范围、边界；五类故障里最通用的动作是「先定位层级，再单变量排查」。把这两点记住，即使忘了具体措辞，也能临时组织出有效提问。
