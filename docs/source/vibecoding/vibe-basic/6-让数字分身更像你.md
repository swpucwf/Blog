# 让数字分身更像你：人设、回答与排错

## 1. 为什么「像你」比「更聪明」更重要

很多人一提到 AI，就下意识追问：它够不够聪明、模型强不强、能不能回答更复杂的问题。但对个人主页里的数字分身来说，真正重要的问题不是「它有多强」，而是「它是不是在代表你」。如果一个回答看起来很完整，却完全不像你的表达方式，也不尊重你的边界，那它再流畅，也很难说是一个好的数字分身。

所以先把评价标准拉回来：**你的数字分身不是通用百科，也不是全知全能客服**。它最重要的任务是介绍你、回答和你有关的问题，并在不知道的时候诚实收住。标准清楚了，后面的调整会简单很多——不是在追求「更万能」，而是在追求「更像你、更稳、更可信」。

可以对比两种回答：第一种很标准、很完整，但像任何网站上的默认机器人都会说的话；第二种也许没那么炫，但会用接近你的方式介绍你，知道哪些能说、哪些不能乱说，不知道的时候会老实收住。对个人主页来说，后者更有价值——因为别人来到这里，不是为了测试模型智商，而是为了认识你。

## 2. 用一句人话理解背后发生了什么

最简单的描述是：**访客在页面里输入问题，项目把问题发给模型接口，模型生成回答，再回到页面显示出来**。现在不需要理解完整后端架构，也不需要把 HTTP、路由、请求细节全部吃透，只要先建立一个够用直觉：页面里的聊天过程不是魔法，而是一条可以被逐步控制的链路。

```text
访客提问
-> 项目把问题送出去
-> 模型结合说明书生成回答
-> 回答回到页面显示出来
```

第 5 章真正要调的，很多时候都发生在这条链路的中间：给了什么信息、立了什么边界、怎样要求它说话。

在这条链路里，最关键的一个东西是「数字分身说明书」——可以理解成系统提示词，或者更口语一点：一份告诉它「你是谁、你该怎么说、你知道什么、不知道时该怎么做」的说明书。有了这层理解，后面所有动作都会落得更实：它不是神秘黑箱，而是在不断修改、补充、校准这份说明书。

## 3. 写第一版数字分身说明书

既然最重要的是「像你」，就不能只交给一个模糊目标，比如「请像我一样回答问题」——这种说法太空。真正让它开始变稳的，是一份边界清楚的说明书：告诉它你是谁、主要知道什么、希望它怎么说话、不知道时该怎么回应，以及哪些内容不应该编。

很容易犯的错误是把说明书写成一堆抽象性格词，比如「真诚、温暖、专业、有逻辑」。这些词不是完全没用，但通常不够落地。真正能让数字分身更像你的，往往是更具体的事实和表达习惯：平时怎么介绍自己、更喜欢先讲结论还是先讲背景、会不会用某些固定句式、遇到不知道的问题时是坦白说不知道，还是先说明知道到哪一步。

一份第一版说明书至少要说清四件事：

| 要写什么 | 为什么重要 |
|---|---|
| 你是谁 | 决定它最基本的身份和事实边界 |
| 你知道什么 | 决定哪些问题它可以稳定回答 |
| 你怎么说话 | 决定回答的语气和表达风格 |
| 你不知道时怎么办 | 决定它会不会乱编 |

很够用的第一版骨架：

```text
你是我的数字分身，用来在个人主页里回答访客关于我的问题。

你的任务：
- 介绍我是谁
- 回答和我有关的问题
- 帮访客了解我最近在做什么、做过什么、怎么联系我

关于我：
- 我是：______
- 我最近在做：______
- 我擅长或长期关注：______

说话方式：
- 语气：______
- 回答尽量：简洁 / 真诚 / 人话一点 / 不装专家

边界：
- 不要编造我没做过的经历
- 不要假装知道我没提供的信息
- 不知道时要明确说不知道，并建议访客通过联系方式进一步确认
```

写到这个程度，就已经比一句「请像我一样回答」强很多了。

## 4. 真正让它像你的，不是形容词，而是样本

写完说明书，还要做一件同样关键的事：用 1 到 3 组真实材料去校准它。不需要很多——几段平时真的会说的话、一两组介绍自己的真实问答，往往比一长串抽象要求有用得多。因为模型最容易模仿的不是「请更有人味一点」这种空指令，而是已经发生过的具体表达。

```text
示例 1
问：你现在主要在做什么？
答：我最近主要在整理自己的作品，也在尝试用 AI 做一些更完整的小项目。

示例 2
问：你擅长什么？
答：我比较擅长把复杂问题讲清楚，也比较关注 AI 应用、内容表达和知识整理这几个方向。
```

1 到 3 组这样的样本就已经很有用——重点不在多，而在真实。

这一步其实也是在整理边界：说明书越清楚，后面答偏、编造、风格失真的概率就越低。不需要写成华丽文件，只要足够清楚，能告诉数字分身——哪些是事实、哪些是语气、哪些问题可以答、哪些问题该收住。到这个程度，它就开始从「会回话」慢慢变成「会代表你」。

## 5. 四类最常见问题与排查思路

开始认真调数字分身之后，最常见的问题其实就那么几类：不回复、答偏、风格不对、编造信息。它们看起来像四件不同的事，但处理思路可以很统一：**先看症状，再猜最可能的原因，然后告诉 AI 希望它怎么查**。这样不会一下同时改太多变量，也更容易知道到底是哪一层出了问题。

| 症状 | 最常见的方向 | 可以怎么问 AI |
|---|---|---|
| 不回复 | 链路、配置、接口没通 | 请先检查聊天请求有没有成功发出，以及报错在哪一层 |
| 答偏 | 说明书不清、上下文不够 | 请先检查当前说明书是否缺少关键信息或边界 |
| 风格不对 | 抽象要求太多，真实样本太少 | 请根据我提供的样本调整语气，而不是只看性格词 |
| 编造信息 | 不知道时的边界没写清 | 请强化「未知就收住」的规则，不要补不存在的事实 |

不回复往往更像链路问题，可能是接口、配置或调用没通；答偏通常说明说明书不够清楚，或者上下文没有给够；风格不对往往是因为给的是抽象要求，而不是具体样本；编造信息基本都和边界没写清有关。把问题先归到这四类里，排查就不会乱，也更容易把情况描述给 AI，而不是只说一句「它又不对了」。

## 6. 一次只改一个变量

这件事非常重要。很多人一看到数字分身答得不对，就会同时去改模型、改说明书、改前端、改文案，最后自己也搞不清到底是哪一步起了作用。更稳的做法是**一次只动一层**：先查链路，再查说明书，再查样本，再查边界。这样更容易定位问题，也更容易让 AI 给出有效帮助。

```text
现在的问题是：聊天能回复，但回答经常答偏。
请先不要改前端代码，也不要换模型。
先帮我检查当前数字分身说明书缺了什么信息。
```

```text
现在它的事实基本对，但说话不像我。
请先基于我提供的 2 组真实表达样本调整语气，不要同时改其他逻辑。
```

## 7. 成本与安全的最小意识

**成本**这件事，在个人项目里不用一开始就搞复杂优化，但至少要有意识：选一个默认够用的模型，别一上来就堆最贵的；控制回复长度，避免无意义地把对话拉得很长。基础版先记住两件事：

- 不要为了个人主页一开始就选过重、过贵的方案；
- 回复能说清就行，不需要每次都写成长文。

**安全**更需要底线：API Key 不要写死在代码里，环境变量在上线前要检查，别把本来应该藏起来的东西直接交出去。如果只记一句话，就记这句：

> 密钥不要直接写进代码仓库。

这条看起来简单，但非常关键——第 6 章上线前还会再检查一次。

## 8. 本篇验收

- [ ] 数字分身的回答比之前更像我，而不是泛泛而谈；
- [ ] 已经写出一版清楚的说明书，知道它知道什么、不知道什么；
- [ ] 知道不回复、答偏、风格不对、编造信息这几类问题该怎么查；
- [ ] 知道 API Key 不能写死在代码里，也知道上线前要检查环境变量。

第 5 章最重要的变化，不是功能数量增加了，而是数字分身终于开始变得更像一个「会代表你说话的人」：不再是挂在页面上的聊天框，而是开始有了自己的边界、语气和稳定性。与此同时，也不再只能被动看结果——不回复先查哪里、答偏该怀疑什么、风格不对该补什么、开始编造说明哪条边界不够清楚。再加上最小的成本与安全意识，这个数字分身现在已经不仅能聊，而且更可信了。

> **补记**：这一章的方法论是「说明书 + 样本 + 单变量排查」三件套——说明书定事实与边界，样本定语气，排查时一次只动一层。三者里最容易被忽略的是样本：形容词再多，也不如两段真实的问答更能决定它「像不像你」。
