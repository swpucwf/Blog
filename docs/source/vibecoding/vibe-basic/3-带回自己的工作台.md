# 带回自己的工作台：从平台到本地

## 1. 为什么要把项目带回本地

第 1 章结束后，已经有了一个能预览、能展示、能简单聊天的 `v1`。它还很早期，但已经说明一件事：这个项目不是想象中的东西了，它已经存在。既然能预览、能点、能聊天，是不是先放在平台里也可以？当然可以停在这里；但如果想继续认真经营这个作品，很快会碰到一个限制——**它还不在自己手里**。

「不在手里」不是指平台不能用，而是掌控感不完整：没有一个固定的位置放它，不知道它由哪些文件组成，也很难形成「这是我会继续维护的项目」的直觉。它更像暂存在别人工作台上的成果，而不是自己书桌上的项目。

把项目带回本地，真正改变的不是技术难度，而是关系：平台像帮你快速搭出雏形的地方，本地工作台像自己的书桌——不一定更高级，但更稳定、更可控，知道东西放在哪、下一次回来从哪接着做。这种感觉会直接影响后面能不能持续推进。

很多人一听「本地开发」，脑子里会自动浮现终端、依赖、框架、目录结构、运行命令、报错排查，心理上先退一步。但这一章不是要把人突然训练成开发者，更像一次交接：把平台里的临时成果搬到自己的工作台上。从这一章开始，不再只是「会生成一个页面的人」，而是开始拥有一个真正能长期经营的作品。

**本地至少解决四件很现实的事**：

| 会得到什么 | 为什么重要 |
|---|---|
| 固定位置 | 知道项目以后放在哪里，不用每次重新找 |
| 长期可改 | 后面每一轮优化都有稳定落点，而不是停在平台聊天记录里 |
| 文件可见 | 开始知道页面、样式、聊天相关代码大概分别在哪 |
| 更可控 | 报错、改动、存档、部署都围绕同一个项目进行 |

后面第 3 章改风格、第 4 章补内容和引导、第 5 章调数字分身、第 6 章上线，都需要一个稳定的落点——这个落点就是本地电脑里的项目文件夹和 AI IDE 工作台。

## 2. 怎么导出：把项目放到正确的位置

不同平台的按钮名字不一样，但路径差不多：在项目页面附近找 `导出代码`、`下载项目`、`同步代码` 之类的入口。目标不是研究平台实现细节，而是把当前这个能运行的版本完整拿下来。

建议顺序：

1. 先确认下载的是当前可用版本，而不是随手点到的旧草稿；
2. 下载后如果是压缩包，先正常解压；
3. 给项目文件夹换一个以后看得懂的名字；
4. 放到一个固定目录，而不是长期丢在下载目录里。

目录可以简单一点，比如 `~/Projects/`、`~/Code/`、`桌面/我的项目/`——重点不是名字多专业，而是以后还能一眼找到。

**文件夹命名**这件事别小看：很多人后面会因为命名太随意，自己都分不清哪个是正式版、哪个是测试版。基础版不需要复杂规则，但至少要有辨识度：

```text
my-homepage
digital-twin-site
linan-homepage
my-site-v1
```

尽量避免这类名字：

```text
新建文件夹
项目最终版
项目最终版2
个人主页最新最终不改了
```

它们的问题不是「不专业」，而是几天后连自己也认不出来。

从这一步起，可以把这个项目目录当成以后反复回来的地方：加内容、改样式、调数字分身、准备上线，都会回到这里。所以这一步看起来像琐事，其实是在建立一种长期关系——这个文件夹不只是「刚刚下载下来的东西」，而是以后工作的主场。如果还在犹豫「是不是先继续在平台里改一改也行」，建议先别拖：第 2 章之后的重点不再是「生成一个东西」，而是「持续把这个东西改好」，而持续修改最好从自己的工作台开始。

## 3. 用 AI IDE 打开并跑起来

项目文件下载到本地之后，下一步是用 AI IDE 打开，让它在自己电脑上跑起来。最容易吓到新手的不是操作本身，而是界面：左边一堆文件，底部一个终端，中间是代码，右边可能还有 AI 对话区——一看到这个场面就立刻觉得「我是不是还没准备好」。其实这一刻完全不需要读懂全部。

这一节最重要的目标很简单：**先让项目跑起来**。只要在浏览器里看到本地页面打开，很多焦虑会立刻下降：原来这个作品不只存在于平台里，它真的已经到了自己电脑上，而且可以继续改。终端里到底执行了什么命令、项目为什么能启动，都可以慢慢理解。

**先只选一个默认工具**。这一步最怕的不是不会操作，而是还没开始就被工具选择劝退。不要做 AI IDE 大横评，也不要在 `Cursor`、`Trae`、`Claude Code` 等编辑器之间来回比较——选一个手边最方便、也最愿意继续用的就够了。标准不是「谁最强」，而是「谁能让我今天把项目打开并跑起来」。基础版更看重闭环，不看重评测。

建议按这个顺序打开项目（可以直接让 AI 陪着走完）：

1. 用 AI IDE 打开刚才那个项目文件夹；
2. 请 AI 先判断这是个什么类型的项目、应该怎么启动；
3. 按 AI 给出的步骤安装依赖、运行项目；
4. 在浏览器里打开本地地址，确认页面真的跑起来了。

不知道怎么开口时，可以直接说：

```text
我刚把一个个人主页项目导出到本地。
请先帮我判断这是个什么项目，告诉我应该怎么在本地跑起来。
如果需要我执行命令，请一步一步告诉我。
如果报错了，请根据报错继续带我排查。
```

这类提问很朴素，但非常有效：它没有假装你懂很多，也没有要求 AI 一次讲完所有原理，只是让它陪当前最重要的事做完。

**如果中间报错，先别自己猜**。新手最容易犯的错误是一看到红字就开始脑补：是不是装错了、是不是平台导出有问题、是不是我根本不适合做这个。绝大多数时候它只是一个具体问题——缺依赖、命令不对、Node 版本不合适、环境没准备好。这时最稳的动作不是乱试，而是把报错原样交给 AI，再补一句：

```text
这是我刚刚运行时的完整报错。
请先判断最可能的原因是什么，再告诉我下一步只做什么，不要一次给太多方案。
```

这句话在帮你把排查节奏收住：先判断，再行动，一次只改一个变量。这个思路在第 5 章还会继续用。

## 4. 认识地图，而不是读全文

项目跑起来之后，下一步也不是「开始逐行读代码」，而是先认识几个最关键的位置。只需要知道三类东西大概在哪：

| 要找什么 | 为什么先找它 |
|---|---|
| 页面入口 | 以后很多内容和布局调整都从这里开始 |
| 聊天相关代码 | 数字分身的展示和交互通常落在这里 |
| 样式或配置 | 改配色、间距、文案体验时经常碰到 |

目标不是读懂全部，而是建立一种很重要的感觉：**我不用懂每一行，但我知道该去哪里找**。

可以直接让 AI 用人话讲结构：

```text
请你先用人话介绍这个项目的结构，告诉我：
1. 主页入口大概在哪
2. 数字分身聊天区相关代码大概在哪
3. 样式主要在哪些文件里
4. 现阶段我最不需要先读懂的部分是什么

不要展开太深，只给我一张够用地图。
```

这样的提问能在最短时间里形成一张地图；有了地图，后面每一次修改都会轻松很多。

## 5. 先完成一次最小修改

项目在本地跑起来之后，最值得立刻做的事不是挑战一个大改动，而是先完成一次很小的修改——越小越好：改一句欢迎语、改一段自我介绍、改一个按钮文案，甚至只是把某个标题换成更像自己的说法。重要的不是结果多惊艳，而是亲手经历一次完整闭环：**我提出修改 → AI 改动 → 本地页面真的发生变化**。

这个闭环对新手特别重要，因为它会把「本地开发」从抽象概念变成身体记忆：原来所谓在本地继续做项目，不是突然开始手写大量代码，而是可以从一个非常小的动作开始。只要看见页面随意图发生变化，后面所有更复杂的修改就都有了落脚点。

推荐的第一次任务（改的不是结构、不是功能，而是一处非常容易看见变化的内容）：

```text
请帮我把首页的一句话介绍改得更像我本人。
目标文案是：一个正在学习用 AI 做产品的内容策划。
请告诉我这句文案在哪个文件里，并只修改这一处，不要动其他布局和样式。
```

这句话的价值在于同时具备三样东西：目标、范围、约束。对 AI 来说，比一句「帮我改一下首页」清楚得多；对自己来说，也在训练一种关键习惯——不是模糊地下指令，而是把动作说清楚。

## 6. 三类高频提问，后面一直会用

到这里很适合顺手建立三类以后高频重复使用的提问方式：

**① 理解类：这个项目结构在做什么？** 帮你快速认识地图，避免每次都像第一次进来一样陌生。

```text
请用人话解释这个项目目前的结构。
告诉我主页入口、聊天相关代码、样式相关文件分别大概在哪。
不要展开太深。
```

**② 定位类：我想改 X，代码在哪？** 帮你在真正动手前先找到入口。

```text
我想修改首页首屏的一句话介绍和主按钮文案。
请先告诉我这两处分别在哪个文件里，再给出修改建议。
```

**③ 约束类：只改这一处，不要动其他地方。** 帮你把范围收住，尤其适合还不想让 AI 一次动太多的时候。

```text
请只修改聊天框的引导语，不要改布局，不要新增模块，也不要调整配色。
```

这三类话术几乎贯穿后面所有章节。它们不花哨，但特别实用，因为直接对应独立 vibe coder 最常见的三个动作：**理解、定位、约束**。

想把这一节做扎实一点，可以连续完成两件小事：先改一句文案，再改一个按钮或一个区块标题。两轮都能顺利跑通，就会开始明显感觉到——自己已经不是在「看平台表演」，而是在真的驱动一个项目往前走。

## 7. 本篇验收

- [ ] 项目已经在电脑上有固定位置
- [ ] 能用 AI IDE 打开它，并在本地跑起来
- [ ] 知道几个关键文件大概在哪里
- [ ] 已经完成过至少一次很小但真实的本地修改

走到这里，说明已经完成了一个很关键但容易被低估的跨越：不是只在平台里生成了一个结果，而是把作品带回电脑、让它在本地跑了起来、也完成过一次真实修改。很多人把这一步看成「只是环境准备」，其实它更像拥有感的开始——从这个项目不再只是「AI 帮我做出来的一个页面」，而是一个知道放在哪里、知道怎么打开、知道怎么继续改的作品。

不需要夸张地给自己下定义说「已经会本地开发了」。只需要确认一件更实际的事：**已经拥有了继续优化这个作品的工作台**。第 3 章要改视觉，第 4 章要补内容和引导，第 5 章要让数字分身更像你，第 6 章要正式上线——这些动作现在都终于有了稳定的落点。

> **补记**：这一章真正的分水岭是「拥有感」——从平台到本地，改变的其实是关系而不是技术。三类提问（理解、定位、约束）是后面所有章节的通用动作，值得在这一章就固化成习惯；尤其是「约束类」，它直接决定后面改动的可控程度。
