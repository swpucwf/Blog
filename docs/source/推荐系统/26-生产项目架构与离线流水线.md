# 生产项目：架构与离线流水线

## 1. 从离线实验到在线系统

论文里的模型只回答「模型好不好」，生产系统还要回答另一组问题：用户打开应用时如何在百毫秒内返回结果？用户刚评完一部电影，下一次推荐怎么立刻变？特征存在哪、模型怎么部署、召回与排序怎么协同？

两者的差别可以列成一张表：

| 维度 | 离线实验 | 在线系统 |
|---|---|---|
| 评估方式 | 离线指标 | 用户真实交互 |
| 数据流 | 静态数据集 | 实时行为 |
| 延迟 | 无要求 | 百毫秒级 |
| 冷启动 | 通常忽略 | 必须处理 |
| 基础设施 | 本地脚本 | 数据库、缓存、搜索、容器 |
| 产出 | 预测文件 | 可访问的 Web 应用 |

本文对应一个完整可运行的项目：MovieLens-1M（100 万评分、3883 部电影、6040 用户），后端 FastAPI + PostgreSQL + Redis + Elasticsearch，前端 Vue 3 + Tailwind，算法上召回用 YoutubeDNN 双塔、排序用 DeepFM、重排做类目与年代打散、冷启动用 UCB 探索。

## 2. 离线与在线的边界

**离线负责生产**：处理全量历史、训模型、算物品向量与相似度。时间宽裕（小时到天），追求质量。产出模型文件、向量矩阵、特征字典。

**在线负责服务**：接请求、调模型、组装结果。百毫秒预算内做取舍，依赖离线产出。

两者通过存储层解耦，四类存储各司其职：

| 存储 | 内容 | 用途 |
|---|---|---|
| PostgreSQL | users / movies / ratings | 业务数据与详情 |
| Redis | 用户画像、行为序列、物品向量 | 在线特征，读延迟 ~1ms |
| 共享目录 | 模型、`item_embeddings.npy`、词表 | 离线写、在线读 |
| Elasticsearch | 标题/类型/演员倒排索引 | 搜索 |

## 3. 两条流水线的分工

**离线五步**：特征工程 → 召回训练 → 排序训练 → 模型部署 → 特征上线。

工程上用一条命令串起来，也支持只跑某几步——只重训排序模型时不必动召回：

```python
steps = args.steps.split(",")
if "all" in steps:
    steps = ["retrieval_preprocess", "ranking_preprocess",
             "retrieval_training", "ranking_training", "ingest", "deploy"]
```

**在线五步**：冷启动检测 → 多路召回 → DeepFM 排序 → 多样性重排 → 结果组装，目标延迟 200ms 以内。

## 4. 特征工程：两个模型，两套样本

### 4.1 召回侧

YoutubeDNN 的样本是「前 k 次观影 → 第 k+1 次」，用滑动窗口生成。三个实现细节值得记：

**编码从 1 开始**。所有类别特征用 LabelEncoder 编码后 +1，把 0 留给未知值与 padding——Embedding 第 0 行专门表示「不存在」。

**左填充**。序列截断到 `MAX_SEQ_LEN=10`，不足的补在左侧，这样最近行为总在右侧，符合时间顺序，RNN/Transformer 处理更自然。

**时序划分**。每个用户最后一条做测试集，之前的部分按前缀逐步生成训练样本。随机划分会造成未来信息泄露——训练时表现好、上线就崩。

### 4.2 排序侧

排序是 CTR 任务，要用户-物品对与正负样本。

**标签定义**：MovieLens 只有评分没有点击。做法是按用户平均分做相对判断：

```python
df_ratings['is_click'] = (
    df_ratings['rating'] >= df_ratings['user_avg_rating'] - 1
).astype(int)
```

用相对偏移而不是绝对阈值，能抵消「有人普遍给高分、有人很严格」的个体差异。

**负采样**：两类负样本搭配——

- **困难负样本**：曝光过但未产生正向交互的物品（模型最容易混的）；
- **随机负样本**：从未交互的物品中随机取（扩充数量）。

比例 1:3（1 困难 + 2 随机）。负样本太少学不出边界，太多会把正负分布拉偏。

**划分**同样按时序，前 80% 训练、后 20% 测试。

## 5. 召回训练：YoutubeDNN 的工程要点

配置里有三处值得单独说：

**Embedding 共享**。历史序列的 `hist_movie_id` 与目标 `movie_id` 共用一张嵌入表（`emb_name` 指向同一个名字）。既省参数，也保证历史偏好与目标物品在同一空间。

**序列聚合用 mean**。变长历史压成定长向量。注意力聚合效果可能更好，但成本上升——这里优先可跑通。

**Sampled Softmax**。物品 3000+，全量 softmax 开销大，只对正样本与 20 个负样本算损失。

训练完会拿到三个模型：完整模型、用户塔、物品塔。在线只需要用户塔（实时算用户向量）+ 预计算的物品向量。

**物品向量预计算**是召回的效率关键：

```python
embeddings = item_model.predict({"movie_id": encoded_ids})
embeddings = embeddings / np.linalg.norm(embeddings, axis=1, keepdims=True)
np.save(config.ITEM_EMB_PATH, embeddings)
```

归一化后内积等价于余弦相似度，取值落在 [-1,1]，设阈值过滤时更直观。

## 6. 排序训练：DeepFM 的配置语义

DeepFM 不需要分塔，所有特征一起进。配置里的 `group` 字段是关键设计：

- `group: ["deepfm", "linear"]` 表示该特征同时参与 FM 二阶交叉与一阶线性项。

一阶捕捉「这个类型整体偏热」，二阶捕捉「这个年龄段 × 这个类型」的组合效应，两者都留着比只留一种稳。

评估用 AUC：不受正负比例影响，衡量「把喜欢的排在不喜欢前面」的能力。

训练完除了模型，还要保存一份**推理用配置**（`feature_dict`、`feature_columns`、`model_config`）——线上特征顺序、词表必须与训练完全一致，否则输入错位，模型直接失效。

## 7. 上线：Redis 写入与模型部署

### 7.1 特征上线

用户画像用 Redis Hash（`user:{id}:profile`），行为历史用 List（保持时间顺序），偏好类目取历史 Top 3 存回画像供召回用。

```python
pipeline = r.pipeline()
for _, row in df_users.iterrows():
    pipeline.hset(f"user:{row['user_id']}:profile", mapping={...})
    if _ % 1000 == 0:
        pipeline.execute()
```

**Pipeline 批量提交**是必做优化：Redis 单命令很快，网络往返才是瓶颈，打包发送能把写入速度拉开一个量级。

### 7.2 模型部署

模型文件几十到几百 MB，不适合塞 Redis。放共享目录，按版本分目录：

```text
deploy/model/user_recall/v1/user_model
deploy/model/user_recall/active.json   # {"version":"v1","path":"model/user_recall/v1/user_model"}
```

**版本指针**是热更新的关键：先传新版本目录，再改 `active.json`，在线服务下次加载即切到新版，不需要停服。

## 8. 四条架构决策

**召回与排序必须分离**。10 万部电影逐条跑排序模型，1ms 一次也要 100 秒——漏斗式架构（召回筛到数百、排序精算）是唯一可行解。

**多路召回要融合**。向量召回依赖表征、协同召回依赖共现、热门召回缺个性化，单一策略都有盲区。项目用 Snake Merge（蛇形合并）轮流取候选，保证每路都有代表进排序。

**冷启动单独走流程**。按交互次数阈值判断新用户：有偏好设置就推该类型优质片，没有就用热门或 UCB 探索，行为积累后平滑过渡到正常链路。

**特征存储与计算分离**。高频特征预写 Redis，避免每次请求打 PostgreSQL——1ms 与几十毫秒的差别，在 200ms 预算里很致命。
