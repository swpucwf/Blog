# 生成式排序：GenRank 与 MTGR

## 1. 先问什么才是本质

HSTU 证明了推荐可以 scale，但它的门槛是万亿参数与数千张卡。小红书团队换了个问法：**生成式推荐的有效性到底来自哪里？** 他们在数千亿曝光日志上做单变量消融。

三个结论：

- **自回归是本质**。在历史位置也算 loss，AUC 明显下降——推荐只训一个 epoch，历史位置上的损失会让模型去「背」每个交互细节，而稀疏 ID 长尾严重，背下来也泛化不了（one-epoch 问题）；
- **因果掩码是本质**。把历史改成全可见，性能下降且模型越大降得越多——双向注意力会学到「因为后面看了美食，所以给科技点赞」这种虚假关联，破坏兴趣演化的因果结构；
- **user-level 组织只是工程便利**。保持序列组织但只在最后位置算 loss，性能几乎不掉，收益主要在训练吞吐与 KV 缓存。

还有两条工程发现：SIM、PPNet、PLE 这些模块在生成式架构下仍然有效；大部分历史聚合特征的价值下降（序列模型能自己学出来），但**实时特征依然重要**，因为它捕捉训练窗口外的新信息。

结论很清晰：**有效性来自架构，不是训练范式的细节**。这就给了优化空间。

## 2. GenRank：把行为当序列主体

HSTU 的序列是内容与行为交替：

$$
[\Phi_0,a_0,\Phi_1,a_1,\dots]
$$

长度 \(2n_c+m\)，注意力复杂度 \(O(4n_c^2d)\)。但排序任务的真相是：**物品是给定上下文，行为才是预测目标**。既然如此，何必让物品单独占一个位置？

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/funrec_action_oriented_arch.png" width="56%" alt="行为导向组织" />
  <p>图 1：物品作为行为的属性，序列长度减半</p>
</div>

GenRank 把行为作为序列主体、物品作为属性：

$$
[a_0^{(x_0)}, a_1^{(x_1)}, \dots],\qquad e_i=\varphi(x_i)+\phi(a_i)
$$

候选位置用特殊的 mask action：\(e_j=\varphi(x_j)+M\)。

**为什么可以直接相加**：行为与物品高度相关，加法让同维度信号增强、独特维度保留。比如「娱乐性」维度上物品 0.8 + 点赞 0.6 = 1.4；「视频时长」只有物品侧有值；「完播率」只有行为侧有值。

收益是直接的：

| 指标 | 变化 |
|---|---|
| 序列长度 | \(2n_c \to n_c\) |
| 注意力计算 | −75% |
| 线性投影 | −50% |
| 激活内存 | −50% |
| KV Cache | 减半 |
| 训练速度 | +78.7% |

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/funrec_action_oriented_mask.png" width="46%" alt="掩码设计" />
  <p>图 2：历史因果、候选可见历史但彼此屏蔽</p>
</div>

掩码也更灵活：历史内部因果，候选可以看全部历史，候选之间互相屏蔽——既保证独立评分，也为序列级重排留了口子。

## 3. 位置与时间：能编码的就别学

HSTU 的相对注意力偏置 \(\mathrm{rab}_{p,t}\) 是 \(N\times N\) 矩阵，前向要读、反向要算梯度，\(O(N^2)\) 的内存访问在长序列上会成为带宽瓶颈。

GenRank 把信息拆成两类，分别用不同手段：

**绝对信息用轻量嵌入**（\(O(N)\)，参数量几百万）：

- **位置编码**：记录序列索引，同请求内候选共享位置；
- **请求索引编码**：捕捉 burst 模式。早上看 5 条科技、中午看 3 条美食，request index 就是 `(0,0,0,0,0,1,1,1)`——模型据此知道前 5 条兴趣连贯，第 5、6 条之间有边界；
- **请求间时间编码**：当前交互距上次请求的间隔分桶。4 小时对高频用户很长、对低频用户不算什么，模型从数据里学这种自适应衰减。

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/funrec_request_time_embedding.png" width="46%" alt="三种编码" />
  <p>图 3：位置、请求索引、请求间时间三种嵌入</p>
</div>

**相对信息用无参数规则**。借鉴 ALiBi，距离越远惩罚越大：

$$
\mathrm{bias}_{i,j} = -m_p(p_i-p_j) - m_t\cdot\mathrm{bucket}(t_i-t_j)
$$

背后是一条设计原则：**复杂的非线性模式用参数学，普适的线性规律直接编码**。距离衰减是强先验，学它既费参数又不稳，直接写成线性惩罚更快也更准。

效果：action-oriented 提速 78.7%，新的位置时间编码再提速 25%，合计 **94.8%**，AUC 还略升。

## 4. GenRank 的取舍

它保持了生成式 formular 的纯粹性——严格自回归，不能「向前看」。代价是**放弃交叉特征**：像「用户对该类目的历史点击率」这种特征，必须同时看用户历史和当前候选属性，天然违反因果约束。

数据与算力充足的场景，这个取舍划算；但资源受限、特征工程已高度优化的场景，代价可能过高。

这就引出了 MTGR 要回答的问题：**用户粒度建模的效率优势，是否必然绑定完整的生成式 formular？**

## 5. MTGR：生成式架构，判别式目标

美团的消融给了一个硬结论：**去掉交叉特征后，即使最大的生成式模型也会退化到不如中等规模 DLRM**，且这个 gap 不能靠 scaling 补——那是信息缺失，不是容量不足。

MTGR 的洞察是：用户粒度建模的效率来自**样本聚合与计算复用**，不要求完整生成式建模。

于是数据组织改成：

$$
[\text{User}, \text{Seq}, \text{RealTime}, [\text{Cross}_1,\text{Item}_1], [\text{Cross}_2,\text{Item}_2], \dots]
$$

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/funrec_mtgr_data_arrangement.png" width="56%" alt="MTGR 数据组织" />
  <p>图 4：用户特征与历史只编码一次，多个候选并行</p>
</div>

历史部分与 HSTU 一致，候选部分不再是历史的延续，而是**待预测目标**，且每个候选 token 直接融合交叉特征：

$$
\mathrm{CandidateToken}_i = \mathrm{MLP}\left(\mathrm{Concat}(\mathrm{Emb}(\mathrm{Item}_i), \mathrm{Emb}(\mathrm{Cross}_i))\right)
$$

即使两个候选的交叉特征相同（同类目、同用户），它们仍是两个独立 token，因为物品 ID、标题等其他维度不同。

效率仍然保留：\(m\) 个候选只编码一次历史，复杂度 \(O((n+m)^2)\) 而不是 \(O(m\cdot n^2)\)。

### 5.1 GLN：分组归一化

四类 token 的激活分布差别很大：Age token 在 \([-1,1]\)，Sequence token 可能到 \([-5,5]\)。全局 LayerNorm 会互相干扰——Age 被过度放大、Sequence 被过度压缩；更糟的是语义混淆，同一个维度在 User token 里是「活跃度」、在 Candidate token 里是「热度」。

于是按组归一化：

$$
\mathrm{GLN}(x_i) = \frac{x_i-\mu_{g(i)}}{\sigma_{g(i)}}\cdot\gamma_{g(i)}+\beta_{g(i)}
$$

实现上只是多带一个组信息，开销可忽略，但它承认了一个事实：**混合范式里，不同类型的信息应在表示空间中保持相对独立**。

### 5.2 Dynamic Masking：因果掩码不够用了

<div align="center">
  <img src="https://raw.githubusercontent.com/swpucwf/MyBolgImage/main/img/funrec_mtgr_customized_mask.png" width="36%" alt="动态掩码" />
  <p>图 5：静态可见、实时因果、候选独立</p>
</div>

causal mask 在这里不再适用，因为序列不是严格按时间组织。三条规则：

1. **静态可见**：User 与 Seq 来自聚合窗口之前，对所有 token 可见；
2. **实时因果**：RealTime token 之间按时间戳下三角，对候选的可见性也按曝光时间判断；
3. **候选独立**：候选之间只有对角线可见，保证评分互不影响。

第二条是防泄漏的关键。设想 12:00 候选 A 点击、12:30 候选 B 未点击、13:00 候选 C 点击，三次曝光聚成一个样本。预测 B（12:30）时绝不能看到 13:00 的点击记录，否则模型学到的是未来信息。掩码按每个样本的实际时间戳**动态生成**，这正是「Dynamic」的含义。

## 6. 三条路线的定位

| 维度 | HSTU | GenRank | MTGR |
|---|---|---|---|
| 序列组织 | 内容/行为交替 | 行为为主体 | 用户 + 历史 + 候选聚合 |
| 建模目标 | 生成式（联合分布） | 生成式（纯自回归） | 判别式（仅候选算 loss） |
| 交叉特征 | 不支持 | 不支持 | 支持 |
| 训练效率 | 高（需大算力） | 很高（+94.8%） | 高（样本聚合复用） |
| 适用场景 | 算力充足的超大规模 | 资源受限、追求吞吐 | 特征工程已成熟的工业系统 |

三者的关系不是替代：HSTU 证明上限，GenRank 证明「少即是多」，MTGR 说明「不必为了效率放弃特征」。选择取决于你手里有什么——算力、特征资产、还是延迟预算。

## 7. 落地判断

- **先做消融再谈架构**：确认自回归与因果掩码在你的数据上是否真的必要，别照抄；
- **交叉特征不要轻易丢**：MTGR 的结论很硬，缺信息无法靠扩模型补；
- **掩码要按时间戳生成**：聚合样本必然带来泄漏风险，静态掩码不够；
- **效率收益要落到延迟上**：训练提速 90% 不等于线上延迟下降，推理侧仍需 KV 缓存与批处理配合。
