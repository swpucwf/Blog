# 生产项目：在线服务

## 1. 一条请求的五段路

在线链路固定顺序：冷启动检测 → 多路召回 → 精准排序 → 多样性重排 → 结果组装，目标 200ms。

整个流程包在一个类里，各阶段的候选数量与开关集中配置，便于压测与灰度：

```python
@dataclass
class PipelineConfig:
    recall_top_k: int = 100
    ranking_top_k: int = 20
    enable_ranking: bool = True
    enable_reranking: bool = True
    cold_start_threshold: int = 5
    cold_start_top_k: int = 20
```

## 2. 冷启动：三种策略 + 动态配额

阈值取 5 次交互：太低用户偏好还没稳定就进正常流程，太高又迟迟体验不到个性化。

命中冷启动后，三条策略并行，配额按用户信息量动态分配：

| 用户状态 | 配额分配 |
|---|---|
| 已有评分记录 | UCB 探索 70% |
| 只设了偏好类型 | 偏好类型 80% |
| 什么都没有 | 热门兜底 100% |

**UCB 探索**用置信上界平衡探索与利用：

$$
\mathrm{UCB}(g) = \bar r_g + c\sqrt{\frac{\ln N}{n_g}}
$$

第一项是利用（历史平均分高者优先），第二项是探索（被推荐次数少的类型不确定性大，给额外奖励）。未探索过的类型直接给最高分，避免一上来就锁死在少数类目。

统计存在 Redis 的 `user:{id}:genre_ucb`，每次评分把 `n` 与 `reward` 累加（评分先归一到 [0,1]）。随着行为增多，利用项自然占上风，同时仍保留对新类型的少量曝光。

**偏好类型策略**走 Elasticsearch，查询加了两个过滤：平均分 ≥ 6.0、评分数 ≥ 20。后者很关键——不设评分数门槛，容易推出一堆高分但只有三个人看过的冷门片。

## 3. 多路召回：三个视角

单一召回的盲区很明显：向量召回依赖表征质量，新片样本少时向量不准；协同召回依赖共现，小众片覆盖差；热门召回缺个性化。于是三路并行：

| 策略 | 逻辑 | 擅长 |
|---|---|---|
| YoutubeDNN | 用户塔算向量，与物品矩阵内积 | 整体兴趣匹配 |
| 物品相似度（I2I） | 取最近观看电影向量，找相似 | 即时兴趣 |
| 偏好类目 | 读 Redis 里 Top3 类型，取该类型热门 | 长期稳定偏好 |

YoutubeDNN 在线要做两件事：把用户特征按离线同样的规则编码（未知值填 0、序列左填充、最近 10 条），再用归一化后的用户向量与物品矩阵做内积。两边都归一化后，内积等价于余弦相似度，取值 [-1,1]，阈值好设。

```python
user_emb = user_model.predict(inputs) / norm
scores = np.dot(user_emb, item_embedding_matrix.T)[0]
```

电影库只有 3000+，直接算内积就够；百万级才需要 FAISS。

I2I 复用同一份物品向量——它本身蕴含协同信息（相似用户喜欢的物品向量接近），所以找相似片的效果不差。

## 4. Snake Merge：不让某一路霸屏

三路合并如果简单按分数排序，通常向量召回会占满候选，另两路白跑。项目用蛇形合并轮流取：

```text
A → B → C → C → B → A → A → B → C → …
```

实现上是一个方向指针来回折返，配一个 `seen` 集合去重。好处是每路都有代表进入排序，候选分布更均衡。

## 5. 排序：批量、一致、可降级

**批量构造**：用户特征对所有候选相同，用 `np.full` 复制；物品特征逐个编码。一次请求 100 个候选，`batch_size` 上限 256。

**编码一致性**是这里最容易踩的坑。线上必须复用离线保存的 LabelEncoder，且规则完全对齐：编码值从 1 开始，0 表示未知；训练时没见过的值也填 0。一旦词表或顺序错位，模型不会报错，只会安静地给出错误分数。

**异步与降级**：模型推理是 CPU 密集，放在线程池里跑，避免阻塞事件循环。模型未就绪或加载失败时切到 `FallbackRankingStrategy`——直接用召回分数排序。质量下降但服务可用，这是生产系统的基本要求。

## 6. 重排：连续打散

排序后可能出现「清一色动作片」。重排规则很简单：**不允许超过 N 个相同属性的物品连续出现**，N 默认 2。

以类型为例，`[动作, 动作, 动作, 喜剧]` 会变成 `[动作, 动作, 喜剧, 动作]`。

算法是「结果列表 + 待定队列」：

1. 按原顺序遍历；
2. 能加入就加入，加入后立刻尝试从待定队列补位；
3. 不能加入就进待定队列；
4. 最后把剩余的追加到末尾。

两个维度链式执行：先类型、再年代（按 10 年分桶）。链式设计的价值在于可以自由加维度（语言、地区），每个策略只管一件事。

**保序性**是这个算法最值得称道的性质：只在违反约束时调整位置，高分片仍然靠前。相关性与多样性不是二选一。

## 7. API 与资源管理

接口层有三处工程细节：

- **物品特征惰性加载**：用回调 `item_features_provider`，只在排序/重排真正需要时查库，召回阶段不加载；
- **结果再组装**：流水线只返回 ID 与分数，标题、海报等展示字段最后统一查库补全；
- **响应带诊断字段**：`is_cold_start`、`ranking_strategy` 一起返回，排障时能直接看出走的是哪条路径。

模型与词表用**单例 + 惰性加载**：进程内只加载一次，首次请求才真正读盘。

```python
class RecallResourceManager:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False
        return cls._instance
```

加载时读 `active.json` 拿版本路径，这与离线的版本指针配套——换模型只改指针。

**健康检查**分组件返回：冷启动有哪些策略、召回几路、排序当前用哪个策略、重排几层。挂到 `/health`，出问题能立刻定位是哪一环。

## 8. 延迟预算怎么花

200ms 的粗分配可以这样理解：

| 阶段 | 量级 | 主要成本 |
|---|---|---|
| 特征读取 | 1～5ms | Redis 读写 |
| 多路召回 | 10～30ms | 向量内积、ES 查询 |
| 排序 | 10～30ms | 100 候选批量推理 |
| 重排 | <1ms | 纯内存遍历 |
| 组装与网络 | 5～20ms | 数据库补详情 |

真正的风险点不在算法，而在**串行依赖**：三路召回必须并行（`asyncio.gather`），否则延迟直接翻三倍；详情查询要按 ID 批量取，不能循环单查。
