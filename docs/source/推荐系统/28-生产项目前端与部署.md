# 生产项目：前端与部署

## 1. 前端：四个页面，四类接口

| 页面 | 主要接口 | 交互要点 |
|---|---|---|
| 首页 | 推荐列表 | 登录后按用户画像拉取，冷启动用户也能拿到结果 |
| 电影详情 | 详情 + 相似电影 | 相似推荐复用 I2I 召回的产物 |
| 搜索页 | ES 搜索 | 关键词模糊匹配标题、类型、演员 |
| 个人中心 | 历史与偏好 | 评分后写库并更新 Redis 特征 |

前端用 Vue 3 + Tailwind，请求统一走 axios 封装：注入 token、统一错误处理、超时重试。两个体验细节值得注意：

- **加载态与空态分离**：推荐接口可能因冷启动返回兜底结果，也可能是空列表，两种情况提示不同；
- **评分后刷新推荐**：用户提交评分后，后端更新 Redis 里的行为序列与 UCB 统计，前端触发一次推荐刷新，让「刚评完就看到变化」成立——这也是这套系统最能体现闭环的地方。

搜索与推荐是两条独立链路：搜索走 ES，推荐走召回-排序-重排，互不阻塞。

## 2. 五个服务，一条命令

系统要同时起 PostgreSQL、Redis、Elasticsearch、后端 API、前端应用。手工装环境的问题很现实：版本不一致、端口冲突、依赖顺序。

Docker Compose 用一个 YAML 声明全部服务、依赖、网络与数据卷，`docker compose up` 一键拉起。四个直接收益：环境一致、启动快、服务隔离、易扩展。

## 3. Compose 配置的四个要点

**服务名即主机名**。后端连数据库不写 `localhost`，而是：

```yaml
environment:
  - DATABASE_URL=postgresql://funrec:funrec123@postgres:5432/funrec_db
  - REDIS_URL=redis://redis:6379/0
  - ELASTICSEARCH_URL=http://elasticsearch:9200
```

同一桥接网络内，Docker 的 DNS 会把服务名解析到容器 IP。

**健康检查决定启动顺序**。Redis 用 `redis-cli ping`，ES 用 `_cluster/health`：

```yaml
healthcheck:
  test: ["CMD", "redis-cli", "ping"]
  interval: 10s
  timeout: 3s
  retries: 5
```

只写 `depends_on` 只能保证「容器起来了」，不保证「服务能用了」。ES 尤其慢，没有健康检查，后端会在启动瞬间连不上而崩。

**命名卷持久化**。`postgres_data`、`redis_data`、`elasticsearch_data` 三个卷，容器删了数据还在。没有卷，一次 `down` 就得重跑离线流程。

**ES 的开发态参数**：

```yaml
- discovery.type=single-node
- xpack.security.enabled=false
- "ES_JAVA_OPTS=-Xms512m -Xmx512m"
```

单节点、关安全、限堆内存——三条都是为开发机妥协，生产必须改。

## 4. 两个 Dockerfile 的构建策略

**后端分层**。先装系统依赖与 Python 包，再复制代码：

```dockerfile
COPY pyproject.toml ./
RUN uv pip install --system -e .
COPY . .
```

改代码不会触发依赖重装，构建从几分钟降到几秒。

**前端多阶段**。构建阶段用 Node 编译出 `dist`，生产阶段只拷产物到 Nginx：

```dockerfile
FROM node:22-alpine as build
RUN npm ci && npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
```

最终镜像里没有 Node 与开发依赖，体积和攻击面都小一圈。

## 5. 启动顺序：六步

1. 装 Docker、Compose、uv，`docker --version` 等三条命令自检；
2. 下载并解压 MovieLens 数据，记下绝对路径；
3. `cp .env.example .env`，填 `FUNREC_RAW_DATA_PATH`（只读数据）与 `FUNREC_PROCESSED_DATA_PATH`（可写中间产物）；
4. `docker compose up -d --build`；
5. `cd backend && uv sync && make run-offline-pipeline`——特征工程、训练两个模型、写 Redis、部署模型，约 10～20 分钟；
6. `make ingest-data-to-database` 建表导数据并创建测试账号，`make index-movies-to-elasticsearch` 建索引。

完成后访问：

| 服务 | 地址 |
|---|---|
| 前端 | http://localhost:3000 |
| 后端 API | http://localhost:8000 |
| Swagger | http://localhost:8000/docs |
| Elasticsearch | http://localhost:9200 |

测试账号 `test@funrec.com / test123456`。

顺序不能乱：离线流程必须在后端启动之后（要写 Redis、要目录挂载），而数据库导入与 ES 索引又依赖 compose 里的基础设施就绪。

## 6. 排障：先看状态，再看日志

```bash
docker compose ps                  # 五个服务是否都 Up
docker compose logs -f backend     # 盯某一服务
curl http://localhost:8000/health  # 后端自检
docker exec -it funrec-redis redis-cli ping
docker exec -it funrec-postgres pg_isready -U funrec
curl http://localhost:9200/_cat/indices
```

四类高频问题及判断依据：

| 现象 | 常见原因 | 检查点 |
|---|---|---|
| 容器 Exited / Restarting | 环境变量缺失、端口占用、依赖未就绪 | `.env` 是否存在、5432/6379/8000/9200 是否被占 |
| 数据库连接失败 | PG 还在初始化 | 日志出现 `ready to accept connections` |
| 模型加载失败 | 共享目录没有模型 | `ls deployed_models/`，为空就重跑离线 |
| 搜索无结果 | 索引未建 | `_cat/indices` 里有没有 `movies` |

再看数据是否真的写进去了：

```bash
docker exec -it funrec-redis redis-cli hget user:6041:profile frequent_genres
docker exec -it funrec-redis redis-cli llen user:6041:history
```

这两条能快速区分「离线没跑完」与「在线读错 key」。

## 7. 从开发态到生产态

当前配置是开发友好的，上生产至少要改六处：

- **关掉 `--reload`**：后端命令改成正式 uvicorn 启动，多 worker；
- **换掉默认口令**：`funrec123` 这类凭据必须从密钥管理注入；
- **开 ES 安全**：`xpack.security.enabled=true` 并配置认证与 TLS；
- **加资源限制**：给每个容器设 CPU/内存上限，避免 ES 拖垮整机；
- **日志集中化**：容器日志输出到 stdout，再由采集侧统一收集；
- **备份与演练**：数据库卷定期备份，模型目录留历史版本以便回滚。

还有两条容易被忽略：前端 Nginx 需要把 `/api` 反代到后端，避免跨域；健康检查要接进编排平台的就绪探针，否则滚动发布时会打到未加载完模型的实例。

## 8. 这套系统串起了什么

回看整条链路，一个用户请求经过的东西正好对应前面各篇：

| 环节 | 依赖的知识 |
|---|---|
| 召回 | 双塔、ItemCF、向量检索 |
| 排序 | DeepFM、特征交叉、AUC |
| 重排 | 打散与多样性 |
| 冷启动 | 群体统计与 UCB 探索 |
| 特征 | Redis 缓存、离线批写 |
| 模型更新 | 版本指针与热加载 |
| 服务 | 异步、降级、健康检查 |

从模型到系统，差的不是算法，而是这些不起眼的工程约束：编码必须与训练一致、召回必须并行、模型必须能降级、配置必须可回滚。
