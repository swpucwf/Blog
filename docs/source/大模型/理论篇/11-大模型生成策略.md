# 大模型生成策略

## 1. 有了「大脑」，还要会「吐字」

前两节用 Llama2 和 MoE 理解了大模型的**网络架构**（大脑怎么构造）。但仅有架构不够——模型前向输出的只是概率分布（Logits），如何把概率一步步变成流畅文本，是本文的**解码策略**。这一篇回到成熟的 **Transformers** 库，以 GPT 为例，避开繁琐公式，直接用**代码调试**的方式追 `model.generate()` 的底层工作原理，看清从「输入 Prompt」到「输出文本」的完整数据流。

> 本文方法是在 IDE 里对 `pipeline("text-generation")` 打断点、反复步入/步过观察变量，下述调试窗口截图来自源教程。

### 2.2 Pipeline 接口的输入输出结构

- **停 `preprocess()`（模型「吃进去」什么）**：文本被 tokenizer 变成 `input_ids` 与 `attention_mask`，pipeline 还保留原始 `prompt_text`（供后处理拼回 FULL_TEXT）。二者形状 `(1, 4)`——第 1 维 batch size=1（本次 1 条 prompt），第 2 维序列长度=4（`I like eating fried` 被切成 4 个 token）。
- **停 `_forward()`（真正解码在哪）**：可见 **Pipeline 只是把参数整理好，真正的解码策略发生在 `model.generate()` 里**——传入前处理的 `input_ids`/`attention_mask`，加上 `generator()` 里的 `max_new_tokens=5`、`num_return_sequences=1`。
- **停 `postprocess()`（还原成文本、决定 FULL/NEW）**：把生成的 token ids 用 `tokenizer.decode()` 还原。`sequence` 来自 `model_outputs["generated_sequence"][0]`（推理结束得到含 `generated_sequence`/`input_ids`/`prompt_text` 的字典）。观察 `sequence`：前四个 `40, 588, 6600, 23018` 是输入 token，后五个 `9015, 553, 531, 262, 582` 是新生成内容，正对应 `max_new_tokens=5`。到 `if return_type == ReturnType.FULL_TEXT:` 看 `prompt_length` 与 `all_text`——`prompt_length` 是 prompt decode 后长度，用来裁掉 `text` 前半段得「新增内容」NEW_TEXT；本次结果 decode 成 `' chicken, but I like'`，`prompt_length=19` 恰对应 `"I"(1)+空格(1)+"like"(4)+空格(1)+"eating"(6)+空格(1)+"fried"(5)=19`。设 FULL_TEXT（默认）则把 `prompt_text` 拼回，最终含原始 prompt。

### 2.3 深入 `generate()` 分析解码流程

只留 `output = self.model.generate(` 一处断点重新调试，转到 `generate()` 定义（`generation/utils.py`）：

1. `_prepare_generation_config(` 处看到 **GenerationConfig**（与模型本地 `config.json` 一致）：

```text
{ "bos_token_id": 50256, "do_sample": true, "eos_token_id": 50256,
  "max_length": 50, "max_new_tokens": 256, "temperature": 0.7 }
```

   `bos_token_id` 起始 token（`inputs=None` 时起头）、`eos_token_id` 结束 token、`do_sample` 是否采样（False 更确定、True 更随机多样）、`temperature` 采样温度（越大越随机、越小越保守）、`max_length` 总长上限（prompt+新生成）、`max_new_tokens` 新增上限（与 max_length 同设时以合并后配置为准）；

2. `get_generation_mode` 处：`model_kwargs` 多了 `input_ids`/`attention_mask`，默认值被传参覆盖；
3. `GENERATION_MODES_MAPPING[generation_mode]` 处：`generation_mode` = `<GenerationMode.SAMPLE: 'sample'>`，走**采样**分支。判定规律：`do_sample=True 且 num_beams=1` → SAMPLE；`do_sample=False 且 num_beams=1` → 贪心；`num_beams>1` → beam 系列；`do_sample=True 且 num_beams>1` → BEAM_SAMPLE。采样即每步不是「永远选最大」，而是在（经 temperature/top_k/top_p 处理的）分布上随机抽，输出更有多样性；
4. `_prepare_model_inputs` 后：`input_ids` 被拆成 `inputs_tensor`，新变量 `model_input_name` 标记输入类型；
5. `num_return_sequences>1` 或 `num_beams>1` 时，同条 prompt 的 `input_ids`/`attention_mask` 在 batch 维复制 `expand_size=max(num_beams, num_return_sequences)` 份并行生成（都=1 则几乎没变化）；`token_healing` 开启时对 `input_ids` 做 `heal_tokens`；
6. `result = decoding_method(` 是逐 token 生成循环入口。其中 `prepared_logits_processor`＝每步选 token 前对 logits 做规则化修正的一串处理器（最小长度、坏词过滤、重复惩罚等在此压低/置 `-inf`）；`prepared_stopping_criteria`＝「何时停止」的判定条件组（达最大长度、遇 eos、自定义）。

步入进 `_sample()`：内部 while 循环——`prepare_inputs_for_generation` 备输入 → forward 得 `outputs.logits[:, -1, :]`（只取最后位置）→ `logits_processor` 修正 → 依 `do_sample` 采样(`multinomial`)或贪心(`argmax`)得 `next_tokens` → `torch.cat` 拼回 `input_ids` → `stopping_criteria` 判停。最终 `(1, 9)` 的 `input_ids` 与后处理看到的 `generated_sequence[0]` 一致。

### 2.4 完整调用链（五步接力）

1. **预处理**：`preprocess()` 调 tokenizer，`prompt_text` → `input_ids` + `attention_mask`；
2. **入口分发**：`_forward()` 携张量调 `model.generate()`，合并用户参数与 GenerationConfig 定最终生成参数；
3. **策略选择**：`generate()` 判断解码模式（Greedy/Sampling/Beam…）动态分发到 `_sample()`/`_greedy_search()`/`_beam_search()`；
4. **解码循环**：`prepare_inputs`（处理 `past_key_values` 缓存）→ forward 得 logits → `LogitsProcessor` 修分布 → 采样/贪心得 Next Token → 拼接 → `StoppingCriteria` 判停；
5. **后处理**：完整 sequence 回 `postprocess()` 用 `tokenizer.decode()` 还原字符串，按 FULL/NEW 截取返回。

## 3. logits 规则链的构造

在 `_get_logits_processor(` 打断点：

- 入参 `input_ids_length=4` 即 input_ids 长度；`model_kwargs` 多两个值——`logits_to_keep=1`（本次 forward 只保留最后 1 个位置的 logits，很多模型靠它省显存算量）、`past_key_values`（自回归解码的 **KV Cache**，缓存每层注意力 K/V 供下步复用，避免整序列从头算；`DynamicCache(layers=[DynamicLayer×12])` 表 12 层 Transformer block 每层一份缓存，随生成逐步增长）。
- `_get_logits_processor()` 内 `processors` 先是空 `LogitsProcessorList()`，「边判断边 append」，`return processors` 时已成规则链：本例含 `TemperatureLogitsWarper(temperature=0.7)` 与 `TopKLogitsWarper(top_k=50, filter_value=-inf)`。若设了 `top_p/typical_p/epsilon_cutoff/eta_cutoff` 也会出现对应 Warper。**它的本质是把生成控制参数翻译成「每步都执行的 logits 处理规则链」并按序组装。**

在 `_sample()` 的 `next_token_scores = logits_processor(...)` 处：`outputs.logits` 形状 `(1, 1, 50257)`（batch=1、只留 1 个位置、词表 50257），`next_token_logits = outputs.logits[:, -1, :]` 变 `(batch, vocab)`。步入 `LogitsProcessorList` 的 `for processor in self:` 逐个遍历 warper：

- **TemperatureLogitsWarper**：`scores_processed = scores / self.temperature`——等价把 logits 除温度 $T$，代入 $\text{softmax}(z/T)$。设 $z=[2,1,0]$：$T=1$ 概率约 `[0.665,0.245,0.090]`；$T=0.5$（更小）先 `[4,2,0]` 得约 `[0.867,0.117,0.016]`——分布更「尖」更确定；$T=2$（更大）先 `[1,0.5,0]` 得约 `[0.506,0.307,0.186]`——分布更「平」更随机；
- **TopKLogitsWarper**：`torch.topk(scores, top_k)` 取第 $k$ 大分数作阈值，`scores < threshold` 得布尔 mask（True=被过滤、不在 top-k），`masked_fill(..., -inf)` 把这些置负无穷，softmax 后概率 0、永不采到。

其它截断规则同理：**top_p**（nucleus）按概率降序保留累计概率达 $p$ 的最小 token 集，其余 `-inf`；**typical_p** 按「局部典型性」筛选（条件概率与分布期望条件概率的接近程度）；**epsilon_cutoff** 在 softmax 概率空间只留条件概率 > $\epsilon$ 的 token；**eta_cutoff** 是 locally-typical + epsilon 混合，token 需满足 $p>\eta$ 或 $p>\sqrt{\eta}\cdot e^{-\text{entropy}}$。

> **top_k vs top_p（都是裁剪规则）**：`top_k` 每步留分数最高 K 个（候选数固定）；`top_p` 每步按概率累加留「累计 ≥ p 的最小集」（候选数动态、看分布尖不尖）。`top_k`/`top_p` 越小越易反复选高分 token、输出更稳但更模板化/重复。实践中 `temperature` 与 `top_p` 分工明确——temperature 把分布变尖/变平（定随机性强弱），top_p 裁掉低概率尾巴（定从哪些 token 抽）。top_p 与 top_k 无联动，同时开＝双重过滤，最终落在两者交集。

跳出 `logits_processor(...)` 后 `next_token_scores` 就是被规则链修正的 logits；过 softmax 并按 `probs` 随机抽样得第一个 token **2057**，查 `vocab.json` 是 `\u0120food`（`Ġ` 前缀表词首），即单词 **food**。`has_eos_stopping_criteria` 判某序列是否结束——结束则后续每步 next_token 设 pad，避免乱生成又保持 batch 等长。`input_ids = torch.cat(...)` 追加新 token，`unfinished_sequences & ~stopping_criteria(...)` 判是否继续。整条链跑完得本次结果 `I like eating fried food. I'm in`。

## 4. 常用解码策略

| 策略 | 触发条件 | 机制与特点 |
|---|---|---|
| **Greedy Search** | `num_beams=1` 且 `do_sample=False` | 每步 `argmax` 选最大分数 token。快、结果稳，适合 baseline/强确定性；易陷局部最优，开放续写易重复套路化 |
| **Sampling** | `do_sample=True`、`num_beams=1` | softmax 得分布后 `torch.multinomial` 抽一个。随机性「不是乱抽，而是先按规则改分布再从改过的分布抽」——temperature/top_p/top_k 在 warper 里提前处理好，保证只在合理候选集抽。LLM 开放式生成最常用 |
| **Beam Sample** | `num_beams>1` 且 `do_sample=True`（`num_beam_groups==1`） | beam 框架不变，但每步扩展引入采样随机性。既保留多候选搜索又不死板；开放对话里相对少见，算可选折中 |
| **Beam Search** | `num_beams>1` 且 `do_sample=False` | 每步维护 `num_beams` 条序列，扩展候选后按累计分数（log 概率求和 + `length_penalty`）排序剪枝留最优 N 条。更近「序列级最优」，翻译/摘要常很稳；开放生成偏保守、易重复、开销大，聊天式生成非首选 |

其它分支知道解决什么问题即可：**Group Beam Search**（beam 分组增多样性、缓解同质化）、**Contrastive Search**（`penalty_alpha` 在「高概率/低重复」间折中）、**Constrained Beam Search**（beam 上加硬约束，如必须含某词，强控制生成）。

## 5. 调试方法论：面对陌生代码怎么办

上文步骤是被「教学化」的线性过程，真实调试不是这样。以第一次拿到 GPT pipeline 代码为例，除导库/环境配置，唯二不认识的只有两行：

```python
generator = pipeline("text-generation", model=model_name, device=device)
pipeline_outputs = generator(prompt_en, max_new_tokens=5, num_return_sequences=1)
```

实操套路：**从第二行打断点看 `generator` 是什么类型**（发现是对象，第一行就只是造对象）→ 步入到「三猫注释」的魔法方法（多是输入格式判断改写）→ 跳到末尾 `return super().__call__(...)` 继续步入 → 到框架胶水代码，仍定位末尾 `return`（`return self.run_single(...)`）步入到 `run_single()`。`run_single()` 里靠变量名就能猜出主流程（`model_inputs`→`outputs`、眼熟的 `forward`）；从 `model_inputs = self.preprocess(...)` 步入、看输出是否有用判断要不要深挖。步过 `output = self.model.generate(...)` 得到大概率有用的 `output`，就在该行下断点重启。`generate()` 里有清晰 1~9 步骤注释帮助定位；不知从哪看就**直接定位末尾 `return result`，用「转到定义」回溯 `result` 来源**（→`result = decoding_method(`），再看它的入参、对某个参数如 `stopping_criteria` 继续转到定义回溯 `prepared_stopping_criteria` 来源并下断点……如此回溯，最后回到 `generate()` 开头，断点已布齐，顺着分析即可完整还原数据流。

> **补记**：一条「回溯法」——面对任何黑盒，先找它的 `return`、从返回值反向追它怎么来的，比正向读代码快得多；再配合「步入看类型、步过看分支、转到定义看来源」三板斧，本文把 HF 的 `generate()` 从头拆到了 `_sample()` 的每一行。解码策略的全部秘密也就收敛成两问：**分布怎么改（logits 规则链）**、**改完怎么选（贪心/采样/beam）**。
