# 评测体系与工程选型

## 1. 为什么调现成模型也不能跳过评测

刚接触多模态时最容易踩的坑是「找总分最高的模型」。真实场景里的选型实际上受制于：任务类型、响应速度、显存预算、中文表现、OCR 能力、多图与多轮支持、长上下文能力、接口与部署难度。

会调用模型和会判断模型能不能干活，是两件不同的事。前者的产出是一次成功的请求，后者的产出是一份能指导后续投入的验收结论：它是直接可用，是改 prompt 就能用，还是必须回到数据与微调那一层。

## 2. 五个评测维度

| 维度 | 关注点 | 主要观测方式 |
|---|---|---|
| 感知能力 | 基本场景、关键对象与关系 | 离线评测集 |
| OCR / 文档理解 | 截图、发票、PPT、网页、图表、公式、表格 | 离线评测集 |
| 推理能力 | 比较、排序、数数、图表归纳、多步问题 | 离线评测集 |
| 幻觉控制 | 图中不存在某元素时是否编造 | 离线评测集 + POPE 类基准 |
| 工程成本 | 显存、吞吐、首 token 延迟、服务稳定性、接口易用性 | 线上观测与压测 |

前四项在离线快照里看，第五项必须和线上链路对齐——首 token 延迟、平均耗时、显存峰值、错误率、典型失败样例，这些字段决定系统能不能上线。

### 2.1 一条合格评测样本的要求

- **可判定**：能说清「怎样算对」，避免只有语感没有标准。
- **可复现**：固定图片版本与问题表述；预处理（缩放、切块）一改，就当作新集重跑。
- **可归类**：用 `tags` 把样本归到一两个维度，便于按维度看失败率。
- **有对照**：能写 `reference` 就写；开放问答也可写「必须包含的关键词」做脚本粗筛，最终仍以人工为准。

## 3. 构建自己的场景评测集

个人项目不必一上来就跑大型 benchmark。最小可行做法是先圈定场景，再落到可跑的 JSONL。

以「截图助手」为例，素材可以按类别配比：

- 20 张网页截图；
- 20 张 IDE 报错截图；
- 20 张后台系统表单截图；
- 20 张中文界面弹窗。

配套的固定问题集：

- 这张图在说什么？
- 是否出现错误信息？
- 关键按钮是什么？
- 下一步需要做什么？

这样的集子比任何公开榜单都更贴近真实价值。样本文件是一行一条 JSON，至少包含 `image` 与 `question`：

```json
{"id":"eval-001","image":"images/sample_ui.png","question":"这张截图的主要功能区域是什么？","reference":"界面主要展示了任务列表和操作按钮。","tags":["ui","description"]}
```

跑完后每行会多出 `prediction`、`status`（`ok` / `error`）、`elapsed_seconds` 等字段，可直接做汇总。

## 4. 公开 benchmark 该怎么看

benchmark 的价值在于建立「能力分类」意识，而不是抄一个分数。看一个基准时先问三件事：

1. 它的输入分布是否接近目标场景？
2. 它更偏感知、OCR，还是偏推理？
3. 评测方式是生成式打分，还是固定答案匹配？

| Benchmark | 类别 | 一句话说明 | 适合测什么 |
|---|---|---|---|
| MMMU / MMMU-Pro | 多学科推理 | 大学级跨学科图文题 | 是否「真懂」知识，而非靠语言偏见猜 |
| MM-Vet v2 | 综合 | GPT-4V 当裁判的开放式评测 | 开放生成质量 |
| OCRBench | OCR / 文档 | 文档密集读字、表格、公式 | OCR 精度与版面理解 |
| MathVista | 数学推理 | 图表 + 数学多步推理 | 图表理解与计算链 |
| POPE | 幻觉 | 针对特定对象问 yes/no | 是否对不存在对象答「是」 |
| HallusionBench | 幻觉 | 图文矛盾检测 | 能否发现图文不一致 |
| RealWorldQA | 常识 | 真实世界物理常识 | 物理常识与空间推理 |
| MMBench / MMBench-cn | 综合 | 中文场景多维度能力 | 中文特化能力 |
| MMStar | 综合 | 纯视觉推理，减少语言偏见 | 视觉-only 推理 |
| BLINK | 感知细节 | 像素级差异识别 | 细粒度感知 |
| Video-MME | 视频 | 视频多模态理解 | 时序与长视频推理 |
| CRPE | 关系推理 | 复杂视觉关系 | 对象间关系理解 |
| AI2D | 图表 | 科学图表理解 | 教育场景图表问答 |

不必一次跑完。个人项目常见的组合是 MMBench-cn（中文综合）+ OCRBench（文档）+ POPE（幻觉），两三个就够建立基线。

## 5. 选型先看失败模式

比起只挑「最好答案」，更实用的做法是先看模型怎么失败。重点观察：

- 遇到小字是否直接忽略；
- 遇到多对象是否混淆；
- 遇到复杂表格是否漏列；
- 遇到不存在的信息是否编造；
- 遇到中文 UI 是否术语漂移。

如果模型在关键场景里的失败方式不可控，它就不适合做主力方案——失败模式的稳定性，往往比平均分更能预测线上事故。

### 6.1 面向场景的优先项

- **截图助手 / 界面理解**：OCR 稳定性、中文界面理解、小字与图标识别、长图处理方式。
- **文档抽取**：版面理解、表格抽取、字段一致性、JSON 输出稳定性。
- **电商内容生成**：商品图感知、文案可控性、风格一致性、幻觉控制。
- **多模态 Agent**：多轮稳定性、工具结果融合能力、多图支持、延迟可接受度。

## 7. 工程侧容易被忽略的指标

只讲准确率的评测是不完整的。上线前还要看：

- 首 token 延迟；
- 平均响应时长；
- 峰值显存；
- 并发能力；
- 图像上传与编码耗时；
- 服务异常时的重试策略。

这些指标经常直接决定系统能否上线，而不是模型够不够强。

## 8. 最小评测脚本

一个通用验收器的思路很简单：读 JSONL，逐条把图片转成 data URL 并请求 OpenAI 兼容接口，把预测、状态与耗时写回。核心循环不到 40 行：

```python
import base64, json, mimetypes, time
from pathlib import Path
from openai import OpenAI

def to_data_url(image_path: str) -> str:
    path = Path(image_path)
    mime = mimetypes.guess_type(path.name)[0] or "image/jpeg"
    return f"data:{mime};base64,{base64.b64encode(path.read_bytes()).decode()}"

client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")
results = []
for line in Path("sample_eval_dataset.jsonl").read_text(encoding="utf-8").splitlines():
    if not line.strip():
        continue
    sample = json.loads(line)
    start = time.perf_counter()
    result = {k: sample.get(k, "") for k in ("id", "question", "reference", "tags")}
    try:
        image = Path(sample["image"])
        image = image if image.is_absolute() else Path("sample_eval_dataset.jsonl").parent / image
        resp = client.chat.completions.create(
            model="your-vlm",
            messages=[{"role": "user", "content": [
                {"type": "text", "text": sample["question"]},
                {"type": "image_url", "image_url": {"url": to_data_url(str(image))}},
            ]}],
            max_tokens=256,
        )
        result["prediction"] = resp.choices[0].message.content
        result["status"] = "ok"
    except Exception as exc:
        result["prediction"], result["status"], result["error"] = "", "error", str(exc)
    result["elapsed_seconds"] = round(time.perf_counter() - start, 3)
    results.append(result)

Path("eval_results.jsonl").write_text(
    "\n".join(json.dumps(r, ensure_ascii=False) for r in results), encoding="utf-8"
)
```

几个实践细节：

- **先检查图片存在**：发请求前把 JSONL 引用的路径全部校验一遍，避免跑到一半才 `FileNotFound`。
- **占位图不等于业务图**：纯色块只能验证链路通不通，测业务意义必须换真实截图。
- **参数可覆盖**：数据集、输出、接口地址、模型名都通过环境变量或命令行参数传入，换模型只改一个值。

结果文件里的单行大致如下：

```json
{"id": "eval-001", "question": "...", "reference": "...", "tags": ["ui"], "prediction": "界面左侧是导航，右侧是任务列表。", "status": "ok", "elapsed_seconds": 1.234}
```

有了 `reference` 就能做粗粒度命中统计（去空白、转小写后判断关键词包含），开放问答只当粗筛：

```python
import json
from pathlib import Path

ok = err = hit = miss = 0
for line in Path("eval_results.jsonl").read_text(encoding="utf-8").splitlines():
    if not line.strip():
        continue
    row = json.loads(line)
    if row.get("status") != "ok":
        err += 1
        continue
    ok += 1
    ref = (row.get("reference") or "").strip().lower()
    pred = (row.get("prediction") or "").strip().lower()
    if ref and ref in pred:
        hit += 1
    elif ref:
        miss += 1

print(f"status_ok={ok}, status_error={err}, rough_ref_hit={hit}, rough_ref_miss={miss}")
```

更完整的汇总脚本会输出错误率、粗粒度命中率、耗时均值与中位数，并按 `tags` 分桶；支持多文件对比与 Markdown 输出。同一份 JSONL 分别换模型 A、模型 B 跑两遍，就能得到一张自家分布上的对比表：

| 指标（同一套 JSONL） | 模型 A | 模型 B |
|---|---|---|
| 请求失败率 `status=error` | 2% | 0% |
| 粗粒度参考命中（含关键词） | 12/20 | 15/20 |
| 平均耗时（秒） | 1.1 | 2.4 |

表中数字仅为示例。真实填表时，建议再单列一栏「典型幻觉样例」并链到具体 `id`，方便团队对齐失败模式。

## 9. 把离线结论接到线上

离线评测集的标签体系会直接变成线上日志的观测字段：

- 请求里带 `eval_id`，线上失败样例可以回溯到离线样本；
- 响应里记 `latency_ms`、输入图像尺寸、token 数；
- 失败分类用固定枚举（漏看 / 幻觉 / 答非所问 / 接口错误），便于统计占比。

这样离线集与线上观测才是同一套语言，评测结论才不会停留在一次性的表格里。

选型的结论不是「哪个模型最强」，而是「哪个模型在我这批图上失败得最少、最可控」。下一篇[推理部署与 Serving](3-推理部署与Serving)沿着这张验收单往下走：从离线快照到线上链路，看请求在哪一环丢图、哪一环变慢，以及该埋哪些日志。
