# 向量知识库选型

## 1. 先看架构路线

2026 年选型的第一层判断不再是「谁 benchmark 更高」，而是架构路线——它决定成本量级与运维方式：

| 路线 | 代表 | 一句话 |
|---|---|---|
| 全托管专用库 | Pinecone、Zilliz Cloud | 不管运维，按量付费，成本最高 |
| 开源自托管 | Milvus、Qdrant、Weaviate | 可控、可私有化，运维自己扛 |
| 寄生于既有数据库 | pgvector、pgvectorscale、LanceDB | 不新增一套数据库系统，2026 年的务实默认 |
| 对象存储原生 | Turbopuffer | 索引放对象存储，闲置数据近乎零成本，代价是冷查询延迟 |

## 2. 主流产品

| 数据库 | 类型 | 特点 |
|---|---|---|
| Pinecone | 云服务 | 全托管闭源，企业级易上手，存储成本偏高 |
| Turbopuffer | 云服务 | 对象存储原生，索引不常驻内存；多租户冷数据场景成本极低 |
| Milvus / Zilliz | 开源 / 云 | 生产级大规模检索，云原生架构 |
| Qdrant | 开源 / 云 | Rust 编写，高性能，高级过滤 |
| Weaviate | 开源 / 云 | 内置向量化模块，GraphQL API |
| Chroma | 开源嵌入式 | 轻量零配置，适合原型与中小规模 |
| LanceDB | 开源嵌入式 / 云 | 进程内运行，列存格式，同表存向量与多模态数据，自带版本管理 |
| pgvector | Postgres 扩展 | 与业务数据同事务查询，主流云数据库默认自带 |
| pgvectorscale | Postgres 扩展 | 在 pgvector 上叠加磁盘索引与量化压缩，突破内存上限 |

## 3. 横向对比

| 数据库 | 部署 | 性能 | 规模 | 过滤 | 上手 | 成本 |
|---|---|---|---|---|---|---|
| Pinecone | 全托管 | 高 | 十亿级 | 强 | 低 | 偏高 |
| Turbopuffer | 全托管（对象存储） | 热缓存快，冷查询需回载 | 千亿级 | 强（元数据 + BM25 + 混合） | 低 | 用量计费 |
| Milvus / Zilliz | 自托管 / 云 | 极高 | 百亿级 | 强 | 中 | 自托管免费 |
| Qdrant | 自托管 / 云 | 极高 | 十亿级 | 强 | 中 | 自托管免费 |
| Weaviate | 自托管 / 云 | 高 | 亿级 | 强（GraphQL） | 中 | 自托管免费 |
| Chroma | 嵌入式 | 中 | 百万级 | 基础 | 极低 | 免费 |
| LanceDB | 嵌入式 / 云 | 高 | 亿级 | 中 | 极低 | 免费 / 云付费 |
| pgvector | Postgres 扩展 | 中 | 千万级 | 强（SQL WHERE） | 极低 | 复用现有 PG |
| pgvectorscale | Postgres 扩展 | 高（磁盘索引） | 亿级 | 强 | 低 | 开源免费 |

一句话取舍：**把速度和运维交给专用库，把成本和「少一套系统」交给 pgvector、LanceDB、Turbopuffer**。没有全面最优解，只有约束不同的解。

## 4. 选型路径

- 原型验证（百万以内）：Chroma，零配置启动；
- 已在用 Postgres：pgvector，内存吃紧时加 pgvectorscale——向量与业务数据同事务查询，备份、权限、连接池全部复用，这是 2026 年最务实的默认选择；
- 生产环境千万到亿级：Milvus 或 Qdrant；
- 不想管运维：Pinecone、Zilliz Cloud；
- 海量冷数据 + 成本敏感：Turbopuffer，适合「用户多、单用户数据平时没人查」的多租户场景；
- 多模态与数据工程栈：LanceDB，与 Pandas、DuckDB、Polars 衔接顺畅；
- 已有 Elasticsearch / OpenSearch：先评估集群自带的向量能力，不急着上新库。

## 5. 四种索引类型

| 索引 | 原理 | 查询速度 | 召回率 | 内存 | 适用 |
|---|---|---|---|---|---|
| HNSW | 基于图的近似最近邻，多层导航 | 极快 | 高 | 较高 | 生产首选、延迟敏感 |
| IVF | 先聚类再搜索，只查相关簇 | 快 | 中 | 低 | 大规模、可接受精度换速度 |
| Flat | 逐个比较，精确搜索 | 慢 | 100% | 低 | 小数据集（十万以内） |
| DiskANN | 图索引与向量存盘，按需流式读取 | 快 | 高 | 低 | 数据超出内存、成本敏感 |

选择经验：百万以内可用 Flat 求精确；百万到一亿用 HNSW；超过一亿考虑 IVF 与 HNSW 组合；内存装不下时换 DiskANN 类磁盘索引（如 pgvectorscale 的 StreamingDiskANN）。

## 6. 混合检索与过滤

纯向量检索会漏掉关键词精确匹配，混合检索同时走向量与关键词：

```text
查询「Python 3.12 新特性」
 ├── 向量检索 → 语义相关文档
 ├── BM25 → 精确匹配「Python 3.12」
 └── RRF 融合 → 重排输出
```

Milvus、Qdrant、Weaviate、Turbopuffer、LanceDB 都原生支持混合检索；Postgres 侧可配合 BM25 扩展补齐关键词一路。融合算法与权重调整，见[RAG 技术全栈的混合检索章节](/source/agent/RAG技术全栈/6-混合检索与查询构建)。

过滤策略有两种，选错会明显影响效果：

- **预过滤**：先按元数据筛子集，再做向量搜索，适合过滤后数据量仍较大的场景；
- **后过滤**：先向量搜索再过滤，可能丢掉结果，需要增大 top-k 补偿。

## 7. 三个容易忽略的运维点

- **索引构建时间**：亿级数据建 HNSW 可能需要数小时，上线前要算进窗口；
- **内存估算**：HNSW 常驻内存，向量维度与条目数相乘再乘索引开销，往往比预期大；
- **更新代价**：频繁增删会让图索引退化，需要定期重建或选择对更新更友好的结构。
