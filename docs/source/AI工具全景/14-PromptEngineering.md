# Prompt Engineering

## 1. 五条核心原则

| 原则 | 说明 | 示例 |
|---|---|---|
| 明确具体 | 模型不会读心 | 「写一封 200 字的邮件」优于「写个邮件」 |
| 给示例 | Few-shot 比纯指令稳定 | 给 1～2 个输入输出样例 |
| 分步引导 | 复杂任务拆步骤 | 「第一步……第二步……」 |
| 指定角色 | 角色影响输出风格 | 「你是一位资深 Python 架构师」 |
| 指定格式 | 明确结构化要求 | 「用 JSON 返回，字段包含 name、age、role」 |

同一个模型，提示词差异能带来数量级的效果差异。调提示词的收益，通常大于换一个更贵的模型。

## 2. 两个可直接套用的框架

**CRISPE**：Capacity（能力）、Role（角色）、Insight（背景）、Statement（任务）、Personality（风格）、Experiment（输出格式）。适合分析类任务。

**RISEN**：Role、Instructions（指令）、Steps（步骤）、Expectations（期望）、Narrowing（约束）。适合交付类任务，约束写在最后一条最有效。

以「编写 Docker Compose 配置」为例，RISEN 的约束是「不使用 latest 标签，所有服务限制内存 512M」——这类边界条件写清楚，返工明显减少。

## 3. Few-Shot：不解释规则，直接示范

```text
将以下产品评论分类为「正面」或「负面」：

评论：这个手机拍照效果超好！→ 正面
评论：电池续航太差了 → 负面
评论：屏幕很清晰但系统有点卡 → 负面
评论：物流快，包装好 → 正面

评论：这款耳机音质不错但降噪一般 →
```

示例的价值在于传递「判断标准」，而不只是格式。选示例时要注意覆盖边界情况——只给典型正例，模型遇到混合评价就容易判错。

## 4. 四个高级技巧

**思维链（CoT）**：让模型一步步思考，显著提升推理准确率。「请一步一步分析」这类引导语即可触发；也可以在示例里展示推理过程，比单纯要求更稳定。

**自我反思**：让模型检查自己的输出。写完代码后追加「检查边界条件、检查性能、有问题就修正后重新输出」，能消掉一批低级错误。

**结构化输出**：明确要求 JSON 或表格，便于程序解析。字段名与类型要写死，不要留给模型自由发挥。

**系统提示词**：设定全局行为，比每条用户消息更持久。适合放编码规范、输出约束、禁止事项。

## 5. 五个常见陷阱

| 陷阱 | 表现 | 对策 |
|---|---|---|
| 指令模糊 | 「帮我优化一下」→ 输出不可控 | 明确目标：「把查询时间从 5s 降到 1s 内」 |
| 负面指令失效 | 「不要用 JSON」→ 模型还是用了 | 改正面指令：「使用 YAML 格式」 |
| 上下文过长 | 关键信息被忽略 | 只给必要上下文，分步代替一次性 |
| 过度约束 | 十条规则互相矛盾 | 规则不超过 5 条，按优先级排列 |
| 忽略温度 | 事实任务用高温 | 事实性任务 temperature=0，创意任务 0.7～1.0 |

其中「负面指令失效」最容易被忽略：模型对「不要做什么」的遵循度远低于「要做什么」。把所有否定式要求改写成肯定式描述，效果立竿见影。

## 6. 与其它环节的关系

- **Skill**：`SKILL.md` 本质是结构化的系统提示词，差别在于带脚本与引用文件；
- **RAG**：检索结果如何拼接进 prompt，直接影响答案质量，拼接顺序与分隔符都是变量；
- **Agent**：指令遵循能力取决于提示词质量，工具描述本质也是提示词；
- **CLI / IDE**：日常对话就是提示词交互，规范写进项目说明文件比每次重复更省事；
- **VibeCoding**：范式切换的本质，是把「提示词约束」换成「规格约束」或「测试约束」。

## 7. 一条判断标准

提示词好不好，不看写得多漂亮，看**换一个模型是否还成立**。过度依赖某个模型特性的提示词，会在换模型时集体失效；而结构清晰、约束明确的提示词，迁移成本低得多。

所以写提示词时值得问一句：这段约束是任务本身的要求，还是我对某个模型行为的猜测？前者保留，后者要准备退化方案。
