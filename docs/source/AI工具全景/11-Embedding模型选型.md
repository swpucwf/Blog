## 2. 别直接横比 MTEB 分数

MTEB 已拆成 v1 与 v2 两套榜单，任务集与计分方式都改过，**两边分数不可直接比较**；同一模型在「英文榜」与「多语言榜」上的名次也常常不一致。

所以看榜时要先确认三件事：榜单版本（v1 / v2）、任务类型（检索 / 分类 / 聚类）、语言范围（英文 / 多语言）。选型时认准与自己场景匹配的那一张，并到最新榜单页确认——排名变动很快，表格里的名次随时可能过时。

## 3. 选型建议

- 中文 RAG：BGE 系列（开源成熟）或 Qwen3-Embedding（榜单靠前）；
- 多语言：Harrier-OSS-v1-27B、KaLM-Embedding（覆盖上千语言）；
- 英文检索基线：Conan-embedding-v2；
- 快速开始：OpenAI text-embedding-3，API 零配置；
- 长文档：Jina Embeddings；
- 企业级：Cohere Embed，有 SLA 保障。

## 4. 维度怎么选

| 维度 | 特点 | 适用 |
|---|---|---|
| 低（256～384） | 存储省、检索快，精度略低 | 大规模初筛、延迟敏感 |
| 中（768～1024） | 精度与性能平衡 | 多数 RAG 场景 |
| 高（1536～3072） | 精度最高，存储与检索成本大 | 高精度、小数据集 |

优先用模型默认维度。存储或检索成为瓶颈时再降维：OpenAI 的模型支持 `dimensions` 参数，BGE 可换 small 版本。降维不是免费的——精度会下降，需要重新评测。

## 5. Chunk 策略

| 策略 | 说明 | 适用 |
|---|---|---|
| 固定长度 | 按字符 / token 数切，加重叠 | 通用场景，简单可靠 |
| 语义切分 | 按段落、章节、句子边界切 | 文档结构清晰 |
| 递归切分 | 优先按分隔符切，超出再递归 | 适用面广，框架默认 |
| 文档解析切分 | 基于 PDF / HTML 结构切 | 表格密集型文档 |

关键参数：`chunk_size` 中文建议 256～512 token，`overlap` 取 10%～20%，避免语义断裂。切分策略的取舍与失败模式，见[RAG 技术全栈的数据与分块章节](/source/agent/RAG技术全栈/2-数据加载与文本分块)。

## 6. 单向量还是多向量

| 方案 | 说明 | 适用 |
|---|---|---|
| 单向量 | 整个段落生成一个向量 | 短文本、段落级检索 |
| 多向量（ColBERT） | 每个 token 一个向量，检索时逐 token 匹配 | 需要细粒度匹配（法条、条款） |
| 多向量（摘要 + 详情） | 摘要与详情分别生成向量 | 长文档先粗筛后精排 |

单向量是默认选择，成本最低；ColBERT 类方案精度更高但存储与计算开销显著；摘要 + 详情是折中，适合长文档。

## 7. 一个容易被忽略的约束

嵌入模型的**最大 token 数决定分块上限**。模型窗口 512，块就不能按 1000 token 切——超出部分会被截断，向量无法代表原文语义。

这意味着嵌入选型与分块策略必须一起定：先确定模型窗口，再反推 `chunk_size`，而不是先切好再找模型适配。
