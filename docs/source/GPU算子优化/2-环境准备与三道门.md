# 环境准备与三道门

## 1. 实验基线

先明确版本，避免后面所有性能数字对不上号：

| 项目 | 基线 |
|---|---|
| 硬件 | AMD Radeon RX 9070 XT |
| GPU 架构 | gfx1201（RDNA4，ISA 名 `gfx12-generic`） |
| ROCm SDK | 10.0.0 |
| HIP 组件版本 | 7.15.26333（`hipcc --version` / `torch.version.hip`） |
| 操作系统 | 原生 Ubuntu 24.04，x86_64 |
| Python 环境 | uv 管理，Python 3.12 |

ROCm SDK 与 HIP 组件各有版本号，装好 ROCm 10.0 后看到 HIP `7.15` 是正常输出。其他 AMD 卡可以参考验证顺序，但包版本、设备名与工具输出都会不同，换卡时要改三处 `device-gfx1201` 再安装。

## 2. 平台边界

验证环境是原生 Linux，不是 WSL2。Windows / WSL2 需先按 AMD 官方矩阵确认显卡、驱动与 ROCm 版本组合，再逐项验证下面的三道门——原生 Linux 的验证结果不能直接当作 WSL2 的结果。

还有一处容易误判：`rocminfo`、PyTorch 与 HIP 程序通过，只说明计算路径可用；`rocm-smi`、`amd-smi` 与硬件性能计数器依赖另外的驱动接口，需要单独确认。状态监控属于选读项，后续 profiling 以各章实际验证过的功能为准。

## 3. 三道门

| 门 | 验证什么 | 通过意味着 |
|---|---|---|
| 第一道 | ROCm 能看到 GPU | 驱动与运行时基本可用 |
| 第二道 | PyTorch ROCm 可用 | 框架层能把计算放到 AMD GPU |
| 第三道 | 最小 HIP 程序能编译运行 | 后续手写 kernel 的路径打通 |

三道必须依次通过。跳过任何一道，后面的报错都会指向错误的方向。

## 4. 第一道门：ROCm 看到 GPU

```bash
rocminfo | grep -E "^[[:space:]]*(Name|Marketing Name|Vendor Name|Device Type|Compute Unit):" | head -20
```

关键看两点：出现 `Device Type: GPU`，且 `Name` 为 `gfx1201`（对应 Marketing Name `AMD Radeon RX 9070 XT`）。两条都对上，说明驱动认得这张卡。

想看 ISA 名可以再补一句 `rocminfo | grep amdhsa`，会看到 `amdgcn-amd-amdhsa--gfx1201` 与 `amdgcn-amd-amdhsa--gfx12-generic` 两条：前者是具体型号 target，后者是 gfx12 系列通用 ISA。

## 5. 第二道门：PyTorch ROCm

在激活后的环境里跑一段最小检查，确认三件事：GPU 可见、设备名正确、HIP 版本能读到。

```python
import torch

print(torch.__version__)          # 2.13.0+rocm10.0.0
print(torch.cuda.is_available())  # True（ROCm 版沿用 cuda 接口名）
print(torch.cuda.get_device_name(0))
print(torch.version.hip)          # 7.15.26333
```

`torch.cuda.is_available()` 返回 `False` 时，先别怀疑模型代码：优先检查激活脚本是否生效、`ROCM_PATH` 是否指向本篇 `.venv`、当前用户是否有 GPU 访问权限。

## 6. 第三道门：最小 HIP 程序

标准骨架只有六步：分配显存 → 拷入输入 → 启动 kernel → 同步 → 拷回结果 → 校验释放。后面写再复杂的算子，外壳都是这个样子。

```cpp
#include <hip/hip_runtime.h>

__global__ void vector_add(const float* a, const float* b, float* c, int n) {
  int idx = blockIdx.x * blockDim.x + threadIdx.x;
  if (idx < n) c[idx] = a[idx] + b[idx];
}

int main() {
  const int n = 1 << 20;
  const size_t bytes = n * sizeof(float);
  float *d_a, *d_b, *d_c;
  hipMalloc(&d_a, bytes); hipMalloc(&d_b, bytes); hipMalloc(&d_c, bytes);

  const int threads = 256;
  const int blocks = (n + threads - 1) / threads;
  vector_add<<<blocks, threads>>>(d_a, d_b, d_c, n);
  hipDeviceSynchronize();
  // 省略：H2D/D2H 拷贝与最大误差校验
  hipFree(d_a); hipFree(d_b); hipFree(d_c);
}
```

几个概念值得先记住：

- **Host / Device**：CPU 与系统内存负责准备输入、发起任务、检查结果；GPU 与显存负责并行计算。
- **H2D / D2H**：主机到设备、设备到主机的拷贝，本例都由 `hipMemcpy` 完成。
- **Kernel**：只在 GPU 上并行执行的函数，不包含前后的数据拷贝。
- **同步**：kernel 启动后主机不一定原地等待，`hipDeviceSynchronize()` 用来等计算完成再拷回结果。

编译与运行：

```bash
hipcc vector_add.hip -o vector_add
./vector_add
```

输出里应包含 `device_name`、`blocks`、`threads_per_block` 与 `max_error: 0`。`max_error` 不为 0 时，先查索引边界与线程数配置，再查拷贝方向。

## 7. 环境同步步骤

仓库用 `uv` 管理 Python 与 ROCm 工具链，不用提前建虚拟环境：

```bash
cd code/part0-intro
uv sync                 # 按 uv.lock 安装 ROCm 10.0 与 PyTorch
source ./activate-rocm.sh
rocm-sdk version        # 10.0.0
```

激活脚本会展开开发文件、刷新设备包链接，并把 `ROCM_PATH` / `HIP_PATH` 指向 `.venv` 下的 `_rocm_sdk_devel`。这样 `hipcc` 与运行时库来自同一个 SDK，不会出现编译用一个版本、运行用另一个版本的情况。

## 8. 排错顺序

按链路顺序排查，比逐条试错快得多：

1. **驱动层**：`rocminfo` 看不到 GPU，先查驱动与用户权限；
2. **框架层**：`torch.cuda.is_available()` 为 `False`，查激活脚本与环境变量；
3. **编译层**：`hipcc` 找不到头文件，查 `HIP_PATH` 与 SDK 安装；
4. **运行层**：结果不对，查索引边界、线程数与拷贝方向。
