# 数据存储与访问

## 1. 一次加法涉及的三处位置

从 `c[2] = a[2] + b[2]` 出发，其中 `a[2]` 是 3、`b[2]` 是 30。数据都在 GPU 上，不等于执行加法的部件已经拿到了操作数——指令要先取得输入，才能执行依赖这些输入的运算。

| 位置 | 职责 | 说明 |
|---|---|---|
| 全局内存（Global Memory） | 存放输入、输出数组 | 描述程序的访问空间；「显存」描述承载数据的硬件 |
| 寄存器（Register） | 保存当前指令使用的临时值 | 编译器安排，源码变量不一定与寄存器一一对应 |
| 执行单元 | 使用寄存器中的值执行运算 | 负责计算，不负责持久存储 |

完整过程是三个动作：**读入两个输入 → 执行加法 → 写回一个结果**。读取之后，原数组里的 3 与 30 仍然保留，线程拿到的只是供计算使用的副本；结果先落在临时位置，直到写回完成，输出数组才更新。

## 2. 合并访存

把视野从一个线程扩大到同一个 wavefront：执行一条数组读取指令时，参与线程各自提供地址，硬件面对的是一组请求，而不是一个数。

同样读 4 个元素，两种排列的代价不同：

- 相邻线程读下标 0、1、2、3：请求集中在一段连续地址；
- 相邻线程读 0、5、10、15：请求分散在四段地址。

存储系统按一定大小的数据块组织与服务访问，**线程需要一个元素，不意味着底层只处理这一个元素**。请求集中时，同一段数据可以满足多个线程；请求分散时，可能涉及更多数据块，而其中只有部分元素被使用。

换个单位看得更清楚：FP32 每元素 4 字节，连续下标 0、1、2、3 对应相对起点的 0、4、8、12 字节。程序选择的下标最终决定硬件处理的地址。

硬件把同一 wavefront 的访存请求尽量合并处理，这个过程叫**合并访存（Memory Coalescing）**。写程序时的经验规则：让相邻线程访问相邻元素。地址由程序决定，实际合并由硬件完成，不能凭示意图断言某张卡一定发生几次事务。

## 3. 缓存不是同一件事

读取还有另一种机会：需要的数据可能已经有一份副本留在更靠近计算部件的存储里。由硬件管理的这层存储叫**缓存（Cache）**，找到副本叫**命中（Hit）**，找不到就继续向后面的存储层级请求。缓存通常按数据块保存副本，这些块叫**缓存行（Cache Line）**。

所以「读取数组」不要求每次都访问物理显存。**合并访存关注这批请求的地址排列，缓存关注所需数据是否已有可用副本**——两者共同影响数据供给，但不是同一个机制。

## 4. Block 内的共享与同步

前面的加法里，每个输出位置都能由一个线程独立完成。把任务换成求和 `[1, 2, 10, 20]` 后就不一样了：甲先算 `1+2=3`，乙先算 `10+20=30`，最后要合并两份局部和。

乙的普通局部变量（寄存器）甲读不到，需要一个双方都能用的交接区域，这就是**本地数据共享区（LDS，Local Data Share）**：

```cpp
__shared__ float shared[2];   // 同一 block 内共享

shared[tid] = partial;        // 各自写入局部和
__syncthreads();              // 等所有线程写完
total = shared[0] + shared[1]; // 再读取别人的结果
```

三个要点：

1. **共享位置存在，不代表值已就绪**：写入有先后，读之前必须同步；
2. **`__syncthreads()` 是块内栅栏**：等同一 block 的所有线程都到达，才继续往下走；
3. **LDS 按块划分**，跨 block 的线程无法直接通过它交换数据。

这份四元素手算只是为了说明交接机制，真正的归约会让每个线程先处理更多输入，再用树状方式合并。

## 5. 访存等待与延迟隐藏

全局内存的访问延迟远高于计算。GPU 的应对方式不是让一个 wave 原地死等，而是**切换到其他就绪的 wave 继续执行**——这就是延迟隐藏（Latency Hiding）。

由此得到两个工程推论：

- **能同时驻留多少 wave，直接决定等待能不能被填满**。寄存器用量、LDS 用量越高，驻留的 wave 越少，隐藏能力越弱；
- **访存模式决定等待次数**。合并访存做得好，一次等待能取回更多有用数据，等效减少了等待。

这也是后续所有 kernel 优化的两个基本杠杆：减少访存量（复用、融合），提高访存效率（连续、对齐、向量化）。
