# Softmax 与 GEMM

## 1. Softmax 的三步与数值稳定

按行做 Softmax，数学上是三步：求行最大值、算指数并求和、逐元素除以该和。

$$
\mathrm{softmax}(x_i) = \frac{e^{x_i - \max(x)}}{\sum_j e^{x_j - \max(x)}}
$$

减最大值不是为了改变结果，而是为了防止 `exp` 溢出：输入稍大时 `e^{x}` 直接变成 `inf`，后续除法得到 `nan`。这一步让 Softmax 从「数学上正确」变成「浮点上可用」。

朴素实现会启动三个 kernel（求最大值、求指数和、做除法），每个 kernel 都要把整行读一遍、写一遍。`4096 × 1024` FP32 下实测约 **0.744 ms**——三次读写同一行的代价很直观。

## 2. 融合：把三次搬运压成一次

融合版本让一个 block 负责一行，块内线程协作完成三段计算，中间结果只留在 LDS 里：

| 实现 | 中位耗时 | 说明 |
|---|---|---|
| `hip-baseline-3kernel` | 0.744 ms | 三个 kernel 顺序执行 |
| `hip-fused-block-lds` | 0.116 ms | 单 kernel，块内协作 |
| `triton-t0-compact` | 0.038 ms | 一行一个 program |
| `triton-t1-wide` | 0.061 ms | 更宽的 block |

在 ROCm 10.0 的分轮实验里，同一形状的 serial / cooperative / fused 三版为 **773 / 149 / 120 µs**；Triton 的四个执行配置为 **37.6 / 41.4 / 51.9 / 56.3 µs**。量级关系一致：融合带来的收益远大于指令级微调。

融合的收益来自两处：**少读写两遍中间结果**，以及**少两次 kernel 启动**。这两者在没有硬件计数器时无法精确拆分，但方向是明确的。

## 3. 一个真实的同步陷阱

融合版本里，线程先从 `shared[0]` 取行最大值，随后各线程要把局部指数和写回同一块 LDS。如果读最大值之后没有屏障，先写完的线程会覆盖其他线程还没读到的值——结果可能仍然「正确」，但那是侥幸。

修正方式是在读完最大值之后补一次 `__syncthreads()`，再开始复用这段共享内存。这件事的启示不在 Softmax：**LDS 复用必须有明确的依赖屏障**，`correct=OK` 不能证明没有数据竞争，只能证明这次没触发。

## 4. 执行配置依赖形状

Triton 侧的对照很能说明问题：`t0-compact`（较窄的逻辑块）比 `t1-wide`（更宽的块 + 更多 warps）快 37%。直觉上「并行度更高应该更快」，实际却被行内归约的通信成本抵消。

更细的观察是形状依赖：主形状 `4096×1024` 下 B4 配置最快（37.6 µs），列数变成 1025 后 B8 反超（62.8 µs 对 73.0 µs）。同一份代码，最优配置随形状改变——**没有脱离 shape 的「最佳 block」**。

## 5. GEMM：从点积到分块复用

矩阵乘 `C = A × B` 的朴素实现是「一个线程算一个输出元素」，每个线程要完整读一行 A 和一列 B。`512³` FP32 下实测约 **0.400 ms**，约 0.67 TFLOP/s——远低于硬件能力，因为同一个 A 元素被 N 个线程重复读取。

分块（tiling）改变了数据复用方式：block 把一段 A、一段 B 载入 LDS，块内线程共享这两段数据，算出一个小输出块。实测 **0.183 ms**，约 1.47 TFLOP/s，提升 2.2 倍。ROCm 10.0 的对照更明显：naive 2.871 ms → tiled16 1.387 ms。

但 tile 不是越大越好：同一轮里 tiled8 与 tiled32 都比 tiled16 慢。tile 变大意味着 LDS 占用上升、可驻留 block 减少，复用收益被占用率抵消。

Triton 的 program 分组也遵循同样的规律：`32×32` 升到 `64×32` 从 0.517 ms 降到 0.358 ms，收益明确；但 `32×64` 与 `64×32` 的范围重叠，group 扫描里数值第一的 g4 在独立确认中变成 g8。差异小且不稳定，就不能宣称「某个 group 固定最优」。

## 6. 与库实现的距离

作为参照，`torch-mm` 在同形状下约 **0.131 ms**（2.05 TFLOP/s），但三个进程的范围很宽（0.064–0.134 ms）。这个宽度本身是一个信息：库实现通常带有更复杂的调度策略，短时测量中更容易受设备状态影响。

教学实现的定位因此要清楚：它的价值是展示「复用怎样降低访存」，而不是追求击败高度调优的库。差距存在，且主要来自流水线、寄存器分块、异步拷贝等工程细节。

## 7. 两个算子的共同经验

- **中间结果是主要成本**。Softmax 三次读写、GEMM 重复读取，都是「数据搬运」在主导时间；
- **融合与分块是同一件事的两种形态**：前者把多趟变一趟，后者把重复读变一次读；
- **配置有形状依赖**：block、warps、tile、group 的最优值都随 shape 变化，任何「默认最佳」都需要复测；
- **同步正确性优先于性能**：屏障少一次，性能可能更好，但结果不可复现。
