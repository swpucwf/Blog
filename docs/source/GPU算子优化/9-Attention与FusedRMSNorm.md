# Attention 与 Fused RMSNorm

## 1. Attention 的物化成本

教学版的注意力先算 `scores = Q × Kᵀ`，再对每行做 Softmax，最后乘 V。问题在于 `S × S` 的中间矩阵要被物化到显存：序列长度翻倍，这块内存翻四倍。

以 `S = 128, D = 64`、FP32 为例，物化基线实测约 **59.7 µs**。这个规模下 `S × S` 还不算大，真正的问题出现在长序列：中间矩阵的写与再读，把一次计算变成三次数据往返。

## 2. 在线 Softmax：不物化也能算对

在线（online）思路是把 key 分块，逐块更新两个统计量：当前最大值 `m` 与指数和 `l`。每来一块新 key：

$$
m_{\text{new}} = \max(m_{\text{old}}, \max(\text{block})),\qquad
l_{\text{new}} = l_{\text{old}} \cdot e^{m_{\text{old}} - m_{\text{new}}} + \sum e^{x - m_{\text{new}}}
$$

输出累加时同样按 `e^{m_old - m_new}` 缩放。这样不需要保存完整的 `S × S` 矩阵，也能得到与物化版一致的结果。

## 3. 同一思路，两种结局

| 实现 | 主形状 `128×64` 中位耗时 |
|---|---|
| `hip-materialized-b256` | 59.7 µs |
| `hip-online-b256` | 230.6 µs |
| `triton-materialized-k32` | 37.9 µs |
| `triton-online-k16` | 18.0 µs |
| `triton-online-k32` | 14.7 µs |
| `triton-online-k64` | 14.3 µs |

同一份在线算法，HIP 版比物化版慢 3.9 倍，Triton 版比物化版快 2.6 倍。差距不在算法，而在实现：

- **同步位置**：HIP 教学版在每个 key 块上都要做块内同步，块小、同步多，开销被放大；
- **状态组织**：running max、running sum、输出累加三份状态在 LDS 与寄存器之间反复搬运；
- **教学化取舍**：为了代码可读，牺牲了 warp 级归约与流水线重叠。

这个负结果值得单独记住：**「不物化中间矩阵」不等于「一定更快」**。算法层面的优势，必须靠工程实现兑现；实现没跟上时，省下的显存反而变成更多的同步。

## 4. 形状与 tile 的耦合

在线版在 `128×65` 这个非对齐形状下，tile 32 的主测为 24.06 µs，tile 64 为 25.44 µs；而在主形状下两者范围重叠。tile 大小与序列长度、寄存器占用、LDS 容量同时相关，单独说「tile 越大越好」或「越小越好」都不成立。

## 5. Fused RMSNorm：三件事合成一件

RMSNorm 的公式很短：

$$
\mathrm{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_i x_i^2 + \epsilon}} \cdot w
$$

三个步骤：求平方和的归约、按 `rsqrt` 缩放整行、逐元素乘权重 `w`。朴素做法是每行一个线程串行处理，`4096 × 1024` 下实测 **694.6 µs**——一行 1024 个元素全由单线程循环，完全没有利用并行。

块内协作版让一个 block 处理一行：线程各自算平方和，LDS 归约后广播缩放因子，再各自写回。实测：

| 实现 | 中位耗时 |
|---|---|
| `hip-serial-b256` | 694.6 µs |
| `hip-block-b64` | 59.8 µs |
| `hip-block-b128` | 69.9 µs |
| `hip-block-b256` | 76.1 µs |
| `triton-r1-w8` | 33.3 µs |

从串行到块协作是 11.6 倍的差距，这是并行化本身的收益；而在块协作内部，**block 64 反而比 128 与 256 更快**。原因是每行只有 1024 个元素，block 越大，参与归约的线程越多，树状合并的层数与同步成本越高——线程数超过有效工作量后，收益转为负担。

## 6. event 与 trace 的差异

短行场景（`4096 × 128`）里有个现象：event 计时在 1/2/4 行时分别是 18.2 / 15.8 / 26.3 µs，但独立 kernel trace 的中位数是 9.14 / 8.68 / 7.08 µs。

两者都没错，只是口径不同：event 覆盖「提交到完成」的区间，包含 CPU 提交空隙与启动开销；trace 计算 kernel 自身的起止时间戳差。短 kernel 上，固定开销占比被放大，于是 4 行的 event 反而比 2 行长——这不代表 kernel 本体退化。

结论：**比较短 kernel 时，event 适合看端到端手感，trace 适合看 kernel 本体**，两者不能混用，更不能相减去「估算开销」。

## 7. 两个算子的共同教训

- **融合的收益要看实现兑现**。Attention 的在线版在 HIP 上输给物化版，RMSNorm 的块协作则稳稳赢过串行——差别在同步次数与状态管理。
- **并行度要与工作量匹配**。RMSNorm 的 block 从 64 增到 256 反而变慢，是这一条最直接的证据。
- **短 kernel 的测量口径必须写明**。event 与 trace 给出不同答案时，先确认在回答哪个问题。
